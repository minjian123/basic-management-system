1. 简介与选型理由

Docker Compose 用一份 YAML 文件声明一组容器服务，一条命令全部起停。BMS 选它的原因：

  • 后端、前端、数据库、Redis、消息队列等一堆服务，用 Compose 一次性编排，本地开发和服务器部署用同一套配置，环境不打架
  • 开发环境需要的中间件（Redis、RocketMQ、ElasticSearch、MinIO）由 Compose 统一提供，本机不用装原生服务
  • MVP 阶段部署规模不大，Compose 足够；等数据量或规模上来，再按规划演进路线迁到 Kubernetes

当前仓库尚无 compose 文件，deploy/ 目录按规划在阶段八完善，本节讲通用用法，第 4 节是 BMS 的设计约定。

2. 安装

Windows 装 Docker Desktop（自带 Docker Engine + Compose v2）：

# 或命令行安装（winget）
winget install Docker.DockerDesktop

macOS / Linux：

brew install --cask docker        # macOS
# Linux 用发行版包管理器装 docker 与 docker-compose-plugin

安装后验证（Compose 现在通常是 docker 的子命令）：

docker --version
docker compose version

3. 常用命令

3.1 生命周期管理

docker compose up -d          # 按 compose.yaml 启动全部服务（后台）
docker compose up -d backend  # 只启动某个服务（含它的依赖）
docker compose down           # 停止并移除容器（默认保留数据卷）
docker compose down -v        # 连同数据卷一起删（慎用，会丢数据）
docker compose restart backend # 重启单个服务
docker compose pull           # 拉取镜像更新

3.2 查看与排障

docker compose ps             # 各服务运行状态
docker compose logs -f backend # 跟踪某个服务的日志
docker compose exec backend sh # 进容器执行命令
docker compose config          # 校验并展开 compose 文件（合并 .env 后）

3.3 compose 文件要点

services:
  backend:
    build: ./backend
    environment:
      - BMS_ENV=prod
    ports:
      - "8000:8000"
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8000/readyz"]
      interval: 30s
      timeout: 5s
      retries: 3
      start_period: 10s
    stop_grace_period: 10s      # 优雅停机宽限期
    depends_on:
      redis:
        condition: service_healthy
  redis:
    image: redis:7
    volumes:
      - redis-data:/data
volumes:
  redis-data:

要点：environment 里的密钥类变量从 .env 或宿主环境注入，不写死在 compose 文件；数据要落盘的（数据库、Redis、MinIO、ES）一律挂数据卷；depends_on 配合 condition: service_healthy 才能等依赖真正就绪而不是「容器起了就冲」。

4.1 服务编排清单

服务说明
backendFastAPI 后端，多副本无状态、可横向扩展（规划部署拓扑：nginx → backend 多副本）
celery-worker / celery-beat异步任务 worker 多副本、定时调度单副本；broker 用 Redis（RocketMQ 替换 RabbitMQ 后，Celery broker 改用 Redis，见规划消息队列节）

frontendnginx 镜像：托管 PC + 移动端静态资源，反代 /api 到 backend，负载均衡 / TLS 终止 / 子域名租户路由

elasticsearch全文检索（主数据/审计日志/文件内容），事件驱动异步同步

数据库按环境选 MySQL 或 PostgreSQL（双库 CI 均验证）
监控栈Prometheus / Loki / Grafana / Alertmanager（指标、日志聚合、告警）

本机开发时 Compose 只提供中间件（Redis、RocketMQ、ES、MinIO），应用以源码方式跑（uv 起后端、pnpm dev 起前端）；完整编排在部署环境用。

4.2 nginx 与 WebSocket

Socket.IO 长连接必须放行升级头，并且连接固定在同一后端实例，否则多实例下连接会抖动断线：

# nginx 配置要点（规划约定）
location /socket.io/ {
    proxy_pass http://backend_upstream;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
}
# 上游亲和：ip_hash 或 Cookie 亲和（sticky session）二选一

另有 TLS 与安全响应头（CSP、HSTS、X-Frame-Options 等）在 nginx 层统一配置，cookie Secure 标志随环境启用。

4.3 健康检查与优雅停机

  • 后端提供 /healthz（存活）与 /readyz（依赖就绪，DB/Redis 连通），compose 的 healthcheck 用 /readyz 判断依赖就绪，编排滚动发布与流量摘除也靠它
  • backend 等服务的 stop_grace_period 设足够时长，让进程处理完在途请求再退出（优雅停机）
  • /readyz 实时探测不缓存，保证编排判断准确（阶段一已实现）

5. 常见问题

现象处理
端口冲突（3306/6379 被本机服务占用）改 compose 里映射的宿主端口（如 "16379:6379"），应用连接串同步改；或停掉本机原生服务
docker compose down 后数据没了确认数据是否挂了 named volume；没挂卷的容器数据删了就没了。要保留数据必须声明 volumes
后端连不上 Redis/数据库容器内要连「服务名」而不是 localhost（compose 网络里每个服务名即 DNS）；检查 depends_on 的 health 条件
服务一直 unhealthy看 healthcheck 命令在容器内是否可用（如镜像里没有 curl，换 wget 或 python）；再 docker compose logs 服务名 看具体报错
构建慢/拉镜像慢Docker Desktop 设置里配国内镜像加速；后端依赖层做好缓存，代码变更不触发全量重装
磁盘占用大docker system prune 清理悬空镜像与无用缓存（有数据卷的不要带 -a 删卷）
多副本下 WebSocket 频繁断线确认 /socket.io 放行 Upgrade/Connection 头，且上游启用了 ip_hash 或 Cookie 亲和（见 4.2）
