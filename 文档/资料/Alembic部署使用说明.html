1. 简介与选型理由

Alembic 是 SQLAlchemy 官方出品的数据库迁移工具，用一串带版本号的迁移脚本管理 schema 演进，每个脚本里有成对的 upgrade() 和 downgrade()，能升能降。BMS 选它的理由：

  • 与 SQLAlchemy 同源，autogenerate 可以直接拿 ORM 模型和现有库比对，自动生成迁移脚本，省掉手写建表语句
  • 迁移脚本是普通 Python 文件，进版本库、走代码 review，部署时按版本逐个执行
  • 支持多套环境：同一份代码可以配多个 ini，正好对应 BMS 的平台库、租户库分库场景

本机核实版本：alembic 1.19.0，运行于 Python 3.14.4。

2. 安装

alembic 已经写进 backend/pyproject.toml 的运行依赖（alembic>=1.19.0），Windows PowerShell 里进 backend 目录同步即可：

cd backend
uv sync

验证安装：

uv run alembic --version

3. 常用命令

3.1 初始化与双套环境

单套环境的标准初始化（BMS 实际用双套，见第 4 节）：

uv run alembic init alembic

生成的 ini 文件里两个关键项：script_location 指向迁移脚本目录，sqlalchemy.url 填目标库连接串（BMS 里连接串从 config.toml / 环境变量来，不在 ini 里写死）。

3.2 生成迁移

# 自动比对模型与当前库，生成迁移脚本
uv run alembic -c alembic_platform.ini revision --autogenerate -m "add probe table"

# 手动建空迁移，upgrade/downgrade 自己写
uv run alembic -c alembic_platform.ini revision -m "manual change"

autogenerate 只对「它能连到的库」做比对，生成后一定要人工检查一遍再提交——它不保证生成的东西在三库里都合法（见 3.3 的方言提示和常见问题）。

3.3 升级与回滚

uv run alembic -c alembic_platform.ini upgrade head    # 升级到最新
uv run alembic -c alembic_platform.ini upgrade +1      # 只升一步
uv run alembic -c alembic_platform.ini downgrade -1    # 回滚一步
uv run alembic -c alembic_platform.ini downgrade base  # 回滚到空库

downgrade 会执行 downgrade() 里的语句，可能删表丢数据，回滚前想清楚；生产环境建议先 upgrade head --sql 只生成 SQL 人工审一遍。

3.4 查看状态

uv run alembic -c alembic_platform.ini current   # 当前库停在哪个版本
uv run alembic -c alembic_platform.ini history    # 全部迁移记录

4. 与 BMS 的集成

迁移工具属于阶段一任务 8，目前尚未开始实施。下面写的是规划形态，任务 8 落地后生效。
  • 双套 Alembic 环境：alembic_platform.ini（平台库）+ alembic_tenant.ini（租户库），迁移脚本分目录存放——app/migrations/platform/ 与 app/migrations/tenant/，各自维护互不干扰；平台库和租户库的 schema 演进独立管理
  • SQLite 开发库自动建表：开发/测试环境启动时经 Base.metadata.create_all 建表，不维护 SQLite 迁移脚本（规划约定）；MySQL / PostgreSQL 生产库必须走 Alembic 迁移
  • 分方言验证：迁移脚本要过 MySQL 8 和 PostgreSQL 16 两套方言（CI 集成测试用 mysql:8 + postgres:16 服务容器兜底），所以脚本里禁用方言特有写法，比如别在迁移里写 MySQL 独有的类型或 PG 独有的语法
  • 批量迁移：scripts/migrate_tenants.py 读取平台库 sys_tenant 注册表，逐个租户库执行升级；阶段三有 sys_tenant 表后完整启用，阶段一先实现框架与单租户演练路径（config.toml 的 dev_tenants = ["demo"] 就是给演练用的预注册租户）

日常操作示例（平台库 / 租户库分别指定 ini）：

uv run alembic -c alembic_platform.ini upgrade head
uv run alembic -c alembic_tenant.ini upgrade head
uv run python scripts/migrate_tenants.py

生产环境注意：平台库连接串走环境变量 BMS_DATABASE_PLATFORM_URL 覆盖，密码不落配置文件，迁移命令在部署流程里按平台库、租户库顺序执行。

5. 常见问题

现象处理
autogenerate 生成的脚本缺列或多列比对基准只认「能连到的库」，检查 ini 里 sqlalchemy.url 是否指向正确的库；生成的脚本人工过一遍再提交
平台库升了，租户库还是旧 schema两套环境独立，别只跑一个 ini；批量场景统一走 scripts/migrate_tenants.py
MySQL 能过、PG 报错（或反过来）迁移里用了方言特有语法；脚本保持三库通用写法，CI 双库集成测试兜底
误操作想回滚downgrade -1 只回滚一步；先看 history 确认要回到哪个版本
SQLite 开发库也要写迁移？不用。BMS 约定 SQLite 开发库启动时 create_all 自动建表，不维护 SQLite 迁移；迁移脚本只服务 MySQL/PostgreSQL
多个 alembic 目录混在一起分不清平台库只动 app/migrations/platform/，租户库只动 app/migrations/tenant/，对应各自的 ini
