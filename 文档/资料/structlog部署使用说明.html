1. 简介与选型理由

structlog 是 Python 的结构化日志库：记日志时把键值对直接写进日志条目，再统一渲染成 JSON 等机器易读的格式，和标准库 logging 兼容。它解决了传统日志「拼字符串、日志一多就没法查」的问题。

BMS 规划选型 structlog 的理由：生产环境输出 JSON，一行一条，Loki 可直接聚合检索；request_id 贯穿请求全链路，跨实例排查问题靠它串起上下游；与标准 logging 集成后不影响第三方库（uvicorn、SQLAlchemy 等）的日志输出。

本机实测版本：structlog 26.1.0（2026-08-05）。注意 structlog 属于 BMS 的运行依赖（在 pyproject.toml 的 dependencies 中，不在 dev 组），因为它不只服务开发调试。

2. 安装

BMS 后端已在 backend/pyproject.toml 声明 structlog>=26.1.0，在 backend 目录执行 uv sync 即完成安装，无需单独操作。

新项目手动添加（PowerShell）：

uv add structlog

验证安装：

uv run python -c "import structlog; print(structlog.__version__)"

3. 基本用法

3.1 直接记日志

用键值对代替字符串拼接，输出由渲染器决定：

import structlog

log = structlog.get_logger()

log.info("request_start", method="GET", path="/healthz")
log.warning("db_timeout", host="redis", timeout=0.5)
log.error("tenant_not_found", tenant="abc", code=80001)

3.2 绑定上下文

用 bind_contextvars 把贯穿整个请求的字段（如 request_id）挂上去，之后所有日志自动携带，请求结束再清理：

from structlog.contextvars import bind_contextvars, clear_contextvars

bind_contextvars(request_id="9f8e2c1a")
log = structlog.get_logger()
log.info("hello")   # 这条自动带 request_id
clear_contextvars() # 请求结束清理，防止泄漏到下一个请求

这是 BMS 里 request_id 贯穿的关键机制：中间件绑定、请求结束清理，全程不需要手工传参。

3.3 打印调试

开发环境如果还没配渲染器，可以用 print_logger 直接打印键值对：

log = structlog.print_logger()
log.info("debug_value", value=42)

4. 与 BMS 的集成

当前实施状态：app/core/logging.py 属阶段一任务 3，尚未开始，以下为设计约定（依据《阶段一_项目骨架说明》第 5 节）。
要点约定
输出格式生产环境 JSONRenderer，一行一条，Loki 直接聚合；dev 环境 ConsoleRenderer，可读的控制台文本
request_id 贯穿请求进入时生成（或沿用客户端 X-Request-ID），写入 contextvars（app/core/context.py），由请求中间件（app/core/middleware.py）绑定与清理；异常响应同样携带 request_id
标准 logging 集成经 structlog.stdlib 的 ProcessorFormatter 挂到标准 logging，uvicorn、SQLAlchemy 等第三方库日志汇入同一管线，统一注入公共字段
公共字段timestamp、level、logger、request_id、env；请求日志另含 method、path、status、cost_ms
敏感字段密码、token、密钥一律脱敏，不落原始值

日志 JSON 示例（来自阶段一设计）：

{"timestamp":"2026-08-05T10:00:00Z","level":"info","logger":"bms.api","request_id":"9f8e2c1a","method":"GET","path":"/healthz","status":200,"cost_ms":3,"env":"dev"}

日志级别由配置 [log] level 控制，环境变量 BMS_LOG_LEVEL 可覆盖（见《阶段一_项目骨架说明》第 4 节）。

5. 常见问题

现象处理
JSON 输出中文变成 \uXXXX 转义JSONRenderer 默认 ensure_ascii=True，如需可读中文可传 JSONRenderer(ensure_ascii=False)（一般仅调试用，生产保留转义更稳）
日志出现两份/重复输出多因日志处理器挂载了多次，集中在配置入口做一次 logging.config.dictConfig，勿在多个模块重复配置
记的是 dict 而不是 JSON 字符串没走渲染器链，或加载了错误的配置（如 dev 配置上了生产）；确认渲染器处理器已挂到根 logger
生产日志级别不对检查 [log] level 与环境变量 BMS_LOG_LEVEL，环境变量优先
第三方库（uvicorn/SQLAlchemy）日志不带公共字段属于预期内的集成问题，需等 core/logging.py 落地 ProcessorFormatter 后统一注入，当前阶段无此实现
