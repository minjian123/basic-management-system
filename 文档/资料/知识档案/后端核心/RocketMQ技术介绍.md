## 1. 技术概述 <a id="overview"></a>

**Apache RocketMQ** 是 Apache 软件基金会的顶级项目，一个分布式消息队列与流平台。
它源自阿里巴巴高并发、高可用的电商生产环境（双十一等场景），
主打**低延迟、高吞吐、可靠 FIFO 顺序消息、事务消息**，具备百万级消息堆积能力。

- **定位**：BMS 的**事件总线**底座——操作日志异步化、Webhook 推送、审计链按租户分区有序消费、模块解耦。
- **版本**：5.x（RocketMQ 5.0 起引入 gRPC 协议与计算存储分离架构；截至 2026 年最新 5.5.0）。
- **许可**：Apache-2.0，OSI 认证开源，商用无限制。
- **架构**：nameserver + broker 两角色（见下节）。
- **语言**：服务端 Java 编写；提供 Java / Go / Python / C++ / Rust 多语言 SDK。

## 2. 核心概念与原理 <a id="principles"></a>

| 概念 | 一句话说明 |
| --- | --- |
| Nameserver | 轻量级名称服务器：管理 broker 的路由信息（哪些 broker、有哪些 topic/queue），无状态、可多副本，客户端定期拉取路由 |
| Broker | 核心节点：负责消息的存储、转发与消费管理，是消息真正落盘的地方，需持久化与高可用部署 |
| Topic | 消息主题：消息的逻辑分类，生产者发到 topic、消费者订阅 topic |
| Queue（队列/分区） | topic 下的物理分区：顺序消息在同一 queue 内严格有序，多 queue 用于并行与扩展 |
| Producer | 消息生产者：把业务事件封装成消息发到 topic |
| PushConsumer / SimpleConsumer | 两种消费模式：Push 由服务端推送、Simple 由客户端主动拉取，5.x 均基于 gRPC |
| 分区有序消息（FIFO） | 同一 queue 内消息严格先进先出：BMS 用它保证同一租户的审计记录顺序 |
| 事务消息 | 「半消息 + 回查」机制：保证消息发送与本地事务一致，本地事务回滚则消息作废，兜底防「发了消息但事务没提交」 |
| 消息轨迹（Trace） | 消息全链路追踪：记录一条消息从生产到消费经过的每个节点，便于排查 |
| 死信队列（DLQ） | 消费多次失败的消息最终转入死信队列，人工介入处理，不丢消息 |
| 事件总线 | 以 RocketMQ 为底座的事件分发中枢：系统内各处事件统一发布（publish）、订阅消费（subscribe），实现模块解耦 |

## 3. 在 BMS 项目中的用途 <a id="usage"></a>

RocketMQ 在 BMS 里承担**事件总线**角色，是「模块之间异步通信」的主干道。
核心思路：业务动作发生后不直接调用下游，而是发一条事件消息，下游按需订阅消费，从而解耦、削峰、可追溯。

- **操作日志异步化**：操作日志、登录日志经 RocketMQ 异步写入，降低主库写压力（见《[项目规划说明](../../../规划/项目规划说明.md#perf)》14 节）。
- **Webhook 推送**：事件发生后经事件总线异步推送至外部系统注册的 URL，HMAC 签名校验、指数退避重试、失败记录（见《[项目规划说明](../../../规划/项目规划说明.md#integ-in)》9.2 节）。
- **审计链分区有序消费**：审计类日志（操作/登录/开放接口/数据变更）逐条哈希串联成链，写入经 RocketMQ **按租户分区有序消费**保证链序，防篡改（见《[项目规划说明](../../../规划/项目规划说明.md#audit)》13 节）。
- **模块解耦**：事件命名 `{域}.{动作}`（如 `wf.instance.started`、`purchase.order.created`），各模块按事件名订阅，互不感知（见《[项目规划说明](../../../规划/项目规划说明.md#integ-event)》9.3 节）。
- **全文检索数据同步**：ElasticSearch 索引数据走 RocketMQ 事件驱动异步消费（独立 event-worker 进程），索引重建时重放事件。
- **AI 管线事件驱动**：embedding 管线、帮助文档智能维护等经 RocketMQ 事件驱动（阶段十五）。
- **事务消息兜底**：关键业务「本地事务 + 发消息」用事务消息保证一致性。

> 重要边界：RocketMQ 只作**事件总线**，不作 Celery 的 broker。
> 因为 Celery 官方不支持 RocketMQ broker，定时任务 Celery 的 broker 用 Redis（官方支持，复用现有 Redis），
> 事件总线与任务队列两条链路解耦（见《[Celery 技术介绍](Celery技术介绍.md)》）。

## 4. 选型对比 <a id="compare"></a>

| 候选技术 | 优缺点 | 结论 |
| --- | --- | --- |
| **RocketMQ（选中）** | Apache 顶级、分区有序消息、事务消息、生态完整、阿里生产验证；Python SDK 可用 | 分区有序契合审计链，事务消息兜底，保留生态扩展空间，首选 |
| Kafka | 吞吐极高、流处理强；但顺序按分区、事务模型不同、运维偏重，Python 生态弱 | 本项目消息量级未到 Kafka 场景，引入成本高、收益不明显 |
| RabbitMQ | 功能全、协议灵活（AMQP）；但无原生分区有序、非流平台、集群运维复杂 | 顺序保证与流式能力不足，不契合审计链有序需求 |
| Redis 作消息队列 | 轻量、已在栈内；但持久化弱、无顺序/事务/堆积保证，更适合做 Celery broker | 用作 Celery broker 合适，但不足以承担事件总线 |

## 5. 常见问题与注意事项 <a id="pitfalls"></a>

- **别拿它当 Celery broker**：Celery 官方不支持 RocketMQ broker，强行接会踩坑；Celery broker 用 Redis，两条链路解耦。
- **nameserver 与 broker 角色分清**：nameserver 无状态可多副本（只存路由），broker 有状态需持久化与高可用，部署时别混淆。
- **分区有序要路由到同一分区**：要让同一租户的审计消息有序，必须把该租户的消息路由到同一 queue（按租户做分区键），否则顺序不保证。
- **消费要幂等**：消息可能重复投递（网络抖动、重平衡），消费者必须按业务 ID 去重，保证幂等。
- **事务消息回查机制**：用事务消息要实现「回查」接口，broker 会反向询问本地事务最终状态，漏实现会导致消息悬挂。
- **关注消息堆积**：消费能力不足会堆积，需监控堆积量并告警；死信队列的消息要有人工处理流程。
- **Python SDK 选型**：Python 侧用 `rocketmq-client-python`（基于 C++ 客户端），注意其与 5.x gRPC 协议的兼容版本，阶段一验证。
- **消息体控制**：消息只放事件元数据（业务 ID + 关键字段），详情让消费者回查数据库，避免大消息与双写一致性问题。
