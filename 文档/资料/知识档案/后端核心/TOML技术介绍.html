1. 技术概述

TOML（Tom's Obvious, Minimal Language，「明显且极简」）是一种 简单、无二义、不深度嵌套的配置文件格式，2018 年定稿 v1.0.0 规范至今稳定。 它用 key = value 表达数据，支持注释、表格分组、数组与内联表， 专为「人和机器都好读」的配置场景设计。 在 BMS 中它是统一配置格式：config.toml 承载应用配置， 敏感项（数据库 URL、密钥）在部署时由环境变量覆盖，遵循 12-factor 原则。

  • 定位：BMS 应用配置格式（config.toml + 环境变量覆盖）。
  • 版本：TOML v1.0.0（规范 2018 年定稿，长期稳定）。
  • 许可：格式/规范可自由使用（它是格式而非库）；Python 读写库各自独立许可。
  • 语言：语言无关；Python 3.11+ 标准库 tomllib 原生读取。

2. 核心概念与原理

概念说明
key = value基本语法：一行一个键值对，键为裸键或带引号键，值为标量/数组/表
数据类型字符串、整数、浮点、布尔、日期时间、数组、内联表，类型显式、解析无歧义
表（[table]）用 [section] 分组配置，形成层级；避免 JSON/YAML 式深层嵌套
注释（#）整行或行尾注释，配置项可就地说明用途，可读性强
tomllibPython 3.11+ 标准库，只读解析 TOML，无需第三方依赖
tomlkit / toml需要「写回」TOML 时的第三方库；tomlkit 保留注释与格式，适合生成配置
12-factor 配置「配置存于环境」：代码与配置分离，敏感值经环境变量注入，不写死在文件里
环境变量覆盖部署时以环境变量覆盖 config.toml 中的敏感项（DB URL、密钥），同一镜像适配多环境
UTF-8 编码TOML 规范要求 UTF-8，中文键值可正常使用

3. 在 BMS 项目中的用途

  • 统一配置格式：应用配置集中在 config.toml，单文件易读、易评审（见《项目规划说明》2.1 节）。
  • 敏感项（数据库 URL、各类密钥）不入库明文，部署时用环境变量覆盖，遵循 12-factor（见《项目规划说明》17 节「环境与配置」）。
  • Alembic 迁移的数据库 URL 来自 config.toml，迁移脚本与运行时读同一份配置，避免漂移。
  • 配置加载顺序约定：默认值 → config.toml → 环境变量（优先级递增），便于本地、CI、生产三态复用同一镜像。
  • 凭据与配置管理边界见《开发部署规划》6 节「配置与凭据管理」。
  • 命名与结构遵循《命名规范》，配置键采用 snake_case。

4. 选型对比

候选技术优缺点结论
TOML（选中）语法简单、类型显式、支持注释、Python 标准库原生读取配置文件首选，人读机读都友好
YAML表达力强、多文档，但缩进敏感、易因空格出错、类型弱更适合 k8s 等场景，应用配置偏重
JSON通用、无注释、结构易冗长，手写配置体验差适合数据交换，不适合人工维护的配置
INI极简，但只支持扁平键值、无数组/嵌套、类型弱表达力不足，无法承载复杂配置
.env适合纯环境变量，但无结构、无类型、难注释分组作为敏感项覆盖手段，不作主配置格式

5. 常见问题与注意事项

  • tomllib 只读：标准库 tomllib 只能解析、不能写回；需要生成/修改 TOML 时用 tomlkit 等第三方库。
  • 敏感信息不入库：数据库密码、密钥等严禁明文写进 config.toml 并提交，一律走环境变量覆盖（见《安全开发规范》）。
  • 覆盖优先级要清晰：明确「默认值 → 文件 → 环境变量」的覆盖顺序并在代码中固化，避免不同环境行为不一致。
  • 日期时间格式：TOML 的日期/时间有固定语法（如 1979-05-27T07:32:00Z），写错会解析失败，注意与本地时区约定（本项目时间 UTC 存储）。
  • 类型显式：整数、浮点、布尔要写对类型，tomllib 解析后类型固定，业务侧不要依赖隐式转换。
  • 编码：文件须为 UTF-8，避免 BOM 或 GBK 混入导致解析异常。
  • 版本兼容：Python 3.11 以下无 tomllib，需第三方 toml 库；本项目 3.14+ 直接用标准库即可。
