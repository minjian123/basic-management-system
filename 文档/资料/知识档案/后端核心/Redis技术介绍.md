## 1. 技术概述 <a id="overview"></a>

**Redis**（Remote Dictionary Server）是一个开源的**内存数据存储**，
常被称为"数据结构服务器"：它不只是键值对，还原生支持字符串、哈希、列表、集合、有序集合等数据结构。
读写全在内存中完成，配合持久化选项与主从/集群机制，是业界最常用的缓存与会话存储设施。

- **定位**：BMS 集群的统一缓存源，承载缓存、会话标记、限流计数、验证码、token 黑名单、分布式锁等场景。
- **版本**：服务端采用 8.x（项目规划口径）；客户端用官方 redis-py 库（异步 `redis.asyncio`，RESP2 兼容）。
- **许可**：服务端 8.0 起为 AGPL-3.0（7.x 及以前为 RSALv2 + SSPLv1，source-available）；本项目仅作独立服务使用，无传染；客户端 redis-py 为 MIT。
- **协议**：RESP 协议（文本/二进制），本项目用官方客户端以 RESP2 通信。

## 2. 核心概念与原理 <a id="principles"></a>

| 概念 | 说明 |
| --- | --- |
| 键值存储 | 以 key 定位 value 的存储模型，key 用冒号分层命名（如 `bms:global:captcha:{uuid}`），本项目统一按《命名规范》的 key 格式组织 |
| TTL（过期时间） | 每个 key 可设生存时间，到期自动删除；本项目规定**所有 key 必须携带 TTL**，缓存类加随机偏移防雪崩 |
| redis.asyncio | redis-py 官方异步客户端，与 FastAPI 异步栈无缝配合，I/O 不阻塞事件循环 |
| SETNX / 分布式锁 | `SET key value NX EX ttl` 原子地"不存在才写入"，是实现分布式锁与幂等拦截的基础（配合唯一约束兜底） |
| INCR（原子自增） | 单条命令完成计数自增，用于限流计数、字典全局版本号（`bms:{tenant}:dict:version`）等场景 |
| 缓存三防 | 穿透（查询不存在的数据缓存空值）、击穿（热点 key 过期用 SETNX 互斥锁单实例重建）、雪崩（过期时间加随机偏移） |
| 持久化 | RDB（定时快照）与 AOF（追加日志）两种持久化；缓存类数据可关持久化，状态类数据按业务需要开启 |
| 高可用形态 | Sentinel（哨兵）做主从自动故障切换；Cluster（集群）做数据分片；本项目生产按需选用，key 设计均含租户前缀适配共享集群 |
| 发布/订阅 | Pub/Sub 消息广播机制；本项目实时推送不依赖它，Socket.IO 多实例广播走 Redis 适配器（RedisManager） |
| Key 命名规范 | 统一格式 `bms:{租户标识|global}:{域}:{业务键}`，租户数据必含租户前缀，平台数据用 global（见《[命名规范](../../../规范/命名规范.html)》） |

## 3. 在 BMS 项目中的用途 <a id="usage"></a>

按《[项目规划说明](../../../规划/项目规划说明.html#stack-backend)》2.1 节与 3.1 节，Redis 承担以下职责：

- **集群统一缓存源**：只读热数据（字典、系统参数、菜单树、业务/动作权限码）走 Redis 缓存，短 TTL；集群内多实例共享同一份缓存，避免本地内存缓存造成的数据不一致（19.2 节集群设计要点）。
- **会话状态**：会话有效标记存 Redis（`bms:{tenant}:sess:{session_id}`），鉴权时随 access token 一并校验（每请求一次 Redis 读，毫秒级开销），强制踢出即时生效（12 节认证与安全）。
- **token 黑名单**：登出时 refresh token 加入黑名单（`bms:global:token:blacklist:{jti}`）即时失效；找回密码 token 存 Redis（TTL 15 分钟、单次有效）。
- **图形验证码**：验证码答案存 `bms:global:captcha:{uuid}`，短 TTL 5 分钟（见《[Pillow 技术介绍](Pillow技术介绍.md)》）。
- **限流计数**：slowapi 的 Redis 后端，集群共享计数；Redis 故障时降级 memory 后端（见《[slowapi 技术介绍](slowapi技术介绍.md)》）。
- **分布式锁**：SETNX 实现，用于防并发与幂等拦截（19.2 节）。
- **其他**：i18n 消息缓存（键含 locale 维度）、Socket.IO 跨实例广播适配器、Celery 定时任务 broker（3.1 节：事件总线用 RocketMQ，任务队列 broker 复用 Redis）。

集群设计口径（19.2 节）：**统一走 Redis 作为共享缓存源；一般业务数据不引入本地内存缓存**。唯一的例外是字典只读热配置——进程内内存缓存 + 全局版本号惰性比对，细节见《[dogpile.cache 技术介绍](dogpile.cache技术介绍.md)》。

## 4. 选型对比 <a id="compare"></a>

| 候选技术 | 优缺点 | 结论 |
| --- | --- | --- |
| **Redis（选中）** | 数据结构丰富、读写极快、官方 Python 异步客户端成熟，Sentinel/Cluster 高可用生态完备 | 与 BMS 缓存/会话/限流/锁场景完全契合，社区与资料最丰富 |
| Memcached | 极简高速，但仅字符串、无持久化、无锁/计数原语，集群管理能力弱 | 功能不足以支撑会话、分布式锁等场景，不采用 |
| etcd | 强一致 KV，适合服务发现/配置中心，但性能与数据结构面向协调场景 | 术业不同（本项目 etcd 仅随 Milvus 部署），不承担缓存职责 |
| 进程内内存缓存（dogpile 等） | 零网络开销，但多实例各自独立、数据不一致 | 仅用于字典只读热配置，与 Redis 分层协同，不替代 Redis |
| 自研内存存储服务 | 可控但成本高、易错、无生态 | 不必要，直接用 Redis |

## 5. 常见问题与注意事项 <a id="pitfalls"></a>

- **所有 key 必须带 TTL**：这是《命名规范》与缓存策略的硬要求——缓存类短 TTL + 随机偏移；状态类（token 黑名单、会话标记、分布式锁、幂等键）TTL 与业务有效期对齐，防止 Redis 内存无限增长。
- **key 命名必须含租户前缀**：多租户共享集群，租户数据 key 必含租户标识，平台数据用 `global`，漏加前缀会造成跨租户数据串扰。
- **Redis 操作要短超时快速失败**（如 500ms）：Redis 故障时不能拖垮请求，按 14 节降级策略处理——缓存失效直连 DB + 日志告警、限流降级 memory 后端。
- **不要用本地内存缓存替代 Redis 存一般业务数据**：多实例内存独立会造成数据不一致；唯一例外是字典只读热配置（dogpile + 全局版本号，见 19.2 节）。
- **缓存一致性：先写库后删缓存**：写操作后同一会话内读主库，避免读到从库旧数据（14 节缓存策略）。
- **Redis 许可口径**：8.x 服务端为 AGPL-3.0、7.x 及以前 RSALv2+SSPLv1——仅作独立服务、不改源码即无传染，禁止为性能修改 Redis 源码（2.5 节许可合规红线）。
- **连接池与超时**：连接数按 worker 规划，避免实例增多时连接耗尽；同步阻塞调用禁用（用 redis.asyncio，勿在 async 接口里调同步客户端）。
- **验证码与限流叠加**：验证码单次有效、短 TTL，Redis 中取值后立即删除，防止重放；与 slowapi 限流配合防爆破（12 节）。
