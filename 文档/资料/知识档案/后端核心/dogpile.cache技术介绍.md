## 1. 技术概述 <a id="overview"></a>

**dogpile.cache** 是 SQLAlchemy 项目组出品的 Python 缓存工具库，
核心思路是"给缓存过程加锁"：多个进程/线程同时发现缓存过期时，只允许一个去重建缓存，
其余等待/用旧值，避免瞬间大量回源打垮数据库。它的名字来自经典互联网故障
**"dogpile 效应"**（又译"雷鸣效应"/缓存雪崩）——这个库正是为治理该问题而生。

- **定位**：BMS 的**进程内内存缓存**（字典等只读热配置），以 Region 分域管理，配合 Redis 组成"远程共享缓存 + 本地进程缓存"双层结构。
- **版本**：持续迭代的 1.x 系列，API 稳定。
- **许可**：MIT，OSI 认证开源。
- **后端（Backend）**：支持内存、Redis、Memcached 等多种后端；本项目使用进程内字典内存后端（memory backend）。

## 2. 核心概念与原理 <a id="principles"></a>

| 概念 | 说明 |
| --- | --- |
| Region（缓存域） | 一组缓存配置（后端、TTL、key 生成器）的集合，不同数据用不同 Region 隔离管理；本项目字典缓存分双 Region：小字典整类型 + 超大字典已查条目局部子集 |
| dogpile 效应 | 缓存过期瞬间大量并发请求同时回源重建，像一堆狗挤同一道门；本库的防击穿设计即由此得名 |
| 防击穿锁（Mutex） | 缓存未命中时通过区域锁（基于 threading 锁或 redis 分布式锁）只放行一个线程重建缓存，其余线程拿旧值或等待，避免回源风暴 |
| 内存后端（Memory Backend） | 以进程内 dict 为存储，读写零网络开销；进程退出即清空，适合只读热配置 |
| JIT 构建 | `region.get(key, creator)` 的"缓存未命中时回调生成值"机制，业务无需先查缓存再查库两段代码 |
| key 生成器（Key Generator） | 默认根据参数自动生成缓存键，也可自定义；配合 Region 前缀避免多 Region 键冲突 |
| 失效策略（Invalidation） | 主动失效（删除 key）与全局版本号失效；本项目采用**全局版本号惰性比对**实现多实例一致（见下节） |
| 软过期（Soft TTL） | 值已过期但仍可短暂返回旧值（staleness），把重建压力分散到时间轴上，进一步防雪崩 |
| 与 Redis 的分工 | Redis 是集群共享缓存源；dogpile 只缓存"全实例可复算、无脏读风险"的只读热配置，两不相混 |

## 3. 在 BMS 项目中的用途 <a id="usage"></a>

按《[项目规划说明](../../../规划/项目规划说明.md#sel-backend)》3.1 节与 14 节"缓存策略"，dogpile.cache 承担**字典内存缓存**：

- **双 Region 分域管理**：小字典整类型整表缓存；超大字典只缓存"已查条目"的局部子集，防止整表常驻内存。
- **多实例一致性靠全局版本号**：Redis 维护 `bms:{tenant}:dict:version`，字典变更时 INCR 版本；各实例下次请求发现版本变化自动重载——惰性比对，多实例天然同步，无需每次请求都查 Redis。
- **零网络往返**：后端业务翻译（导出/通知/报表/审批/明细行批量）与字典查询接口共用该内存缓存，避免大量字典查询打 Redis/DB。
- **防 N+1**：超大字典批量翻译走"局部缓存 + 一次性 IN 查询"（1000 行明细 × 30 字段 = 30 次查询而非 30000 次）。
- **防击穿**：字典缓存重建走 dogpile 的互斥重建机制，多 worker 同时过期时只重建一次，避免回源风暴。

口径边界（19.2 节）：**一般业务数据不引入本地内存缓存**，统一走 Redis 共享缓存源；进程内内存缓存仅限字典这类只读热配置。

## 4. 选型对比 <a id="compare"></a>

| 候选技术 | 优缺点 | 结论 |
| --- | --- | --- |
| **dogpile.cache（选中）** | Region 分域 + 防击穿互斥重建开箱即用，与 Redis 分层协同成熟，SQLAlchemy 同源生态 | 正好满足"进程内热配置缓存 + 全局版本号一致"的规划设计 |
| cachetools | 轻量简单，但只有 TTL/淘汰算法，无分域管理、无防击穿互斥重建 | 功能不足，防 dogpile 效应需自行实现，不采用 |
| functools.lru_cache / 手写 dict | 零依赖，但无失效、无淘汰、无版本控制，多实例无法同步 | 只适合无失效诉求的纯计算缓存，不满足字典热配置需求 |
| 仅用 Redis 缓存字典 | 集群一致但每请求一次网络往返，高频批量翻译放大开销 | 作为共享源保留，但进程内缓存不可省（规划明确双层结构） |
| 自研内存缓存组件 | 可控但重复造轮子，防击穿/版本失效等细节易出错 | 不必要，直接用 dogpile.cache |

## 5. 常见问题与注意事项 <a id="pitfalls"></a>

- **禁止缓存可变业务数据**：进程内缓存多实例独立，只有"只读 + 可惰性重载"的字典热配置才能进 dogpile；可变数据一律走 Redis 共享缓存，否则多实例数据不一致。
- **全局版本号必须由变更方 INCR**：字典变更后必须 INCR `bms:{tenant}:dict:version`，否则各实例永远带着旧字典；版本比对要放请求前段、开销极小。
- **超大字典不得整表缓存**：必须用"已查条目局部子集"Region，否则内存持续膨胀；批量翻译用一次性 IN 查询回填，防 N+1。
- **内存后端进程内有效**：多 worker 部署时每个 worker 各有一份内存缓存（靠版本号对齐），不是共享存储；重启即清空，属预期行为。
- **防击穿锁别用全局重锁**：重建锁粒度按 key/Region 收敛，锁持有时间必须短（只覆盖一次字典查询），避免反成性能瓶颈。
- **不要与 Redis 职责混用**：token 黑名单、会话标记、限流计数等状态类数据不能放进程内缓存（登出/踢出需集群即时生效）。
- **测试环境注意**：单元测试中内存缓存可能"穿透"（绕过缓存直查库），断言缓存行为时需按 Region 显式清理，避免用例间污染。
