## 1. 技术概述 <a id="overview"></a>

**ElasticSearch**（常缩写为 ES）是一个基于 Lucene 构建的**分布式全文检索引擎**。
它把文本按「分词 → 建倒排索引」的方式组织起来，让「按关键词快速搜出相关文档」这件事变得又快又灵活，
并通过 REST/JSON 接口对外服务，任何语言都能调。除全文检索外，它也擅长日志检索、聚合统计，是业界使用最广泛的搜索组件之一。
BMS 用它承载全局搜索、审计日志检索与文件内容检索（阶段十四引入）。

- **定位**：BMS 唯一全文检索服务，只负责「检索匹配 + 高亮」，详情数据仍回查数据库。
- **版本**：8.x 系列（项目锁定版本；官方 9.0 已于 2025.4 发布，8.18 为 8.x 维护线，升级另行评估）。
- **许可**：默认 Elastic License 2.0 + SSPLv1（source-available，非 OSI 开源）；8.15+ 提供 AGPL-3.0 选项。仅作独立检索服务使用无合规影响，见《[项目规划说明](../../../规划/项目规划说明.html#stack-license)》2.5 节。
- **语言**：服务端 Java；BMS 用官方 Python 客户端 elasticsearch-py 访问。
- **部署**：Docker Compose 独立容器，端口 9200（HTTP）/9300（节点通信），仅内网。

## 2. 核心概念与原理 <a id="principles"></a>

| 概念 | 说明 |
| --- | --- |
| 索引（Index） | 结构相同的一批文档的集合，类似关系库的「表」；BMS 按用途建索引：`bms-main`（主数据）、`bms-file`（文件内容）、`bms-log-操作-202608`（日志按月） |
| 文档（Document） | 存储的基本单位，一个 JSON 对象；BMS 只存「业务 ID + 可搜索字段」，详情留在数据库 |
| 映射（Mapping） | 字段的类型与分析器定义，决定文本怎么被索引、怎么被搜索；建索引时定好，后期改动成本高 |
| 分析器（Analyzer） | 把文本切成词（分词）的管线，索引时和搜索时都要过一遍；中文必须配中文分词器（如 IK），否则按单字切分、检索效果差 |
| 倒排索引 | ES 的核心数据结构：从「词 → 包含该词的文档列表」建索引，所以关键词检索极快 |
| 分片（Shard） | 索引被拆成的多份，分散到不同节点，是并行处理与容错的基本单位 |
| 副本（Replica） | 分片的备份副本：既提升读吞吐，又保证节点故障时数据不丢、自动迁移（BMS 生产集群开启） |
| 查询 DSL | JSON 描述的查询语言：关键词匹配、模糊、范围、bool 组合（must/should/filter）等，BMS 租户过滤用 `filter` 子句 |
| 高亮（Highlight） | 返回命中片段并把命中词标记出来，BMS 全局搜索结果列表的「关键词标黄」就靠它 |
| 别名（Alias） | 指向一个或多个索引的虚拟名，用于索引切换（重建索引时零停机切流） |
| ILM（索引生命周期） | 按时间自动把索引在热/温/冷/删除间流转，BMS 用于日志类按月索引的归档与清理 |
| 近实时（NRT） | 文档写入后约 1 秒内可被搜到，不是「写完立即可搜」；事件同步链路设计时要知道这个延迟 |

## 3. 在 BMS 项目中的用途 <a id="usage"></a>

- **三类检索场景**（见《[项目规划说明](../../../规划/项目规划说明.html#sel-backend)》3.1 节）：
  - 主数据全局搜索：用户/部门/角色/字典/采购单据/文件元数据/帮助文章，一个搜索框全站找；
  - 审计日志检索：操作/登录/开放接口/数据变更日志，按月索引、与日志分片表对齐；
  - 文件内容检索：PDF/Word/Excel/TXT 由 Celery 任务解析文本后入库索引，扫描件 OCR 由阶段十五 AI 支持（见《[PaddleOCR 技术介绍](PaddleOCR技术介绍.md)》）。
- **数据同步走事件驱动**：业务写库后发 RocketMQ 事件，独立 event-worker 进程异步消费并更新索引（复用现有事件模型，见《[RocketMQ 技术介绍](RocketMQ技术介绍.md)》）；**索引重建 = 重放事件**，不依赖「双写」。
- **ES 只承担检索匹配**：查询返回业务 ID + 高亮片段，详情一律回查数据库取最新数据——从架构上避免双写一致性难题。
- **租户隔离**：所有索引文档均含 `tenant_id` 字段，查询强制携带租户过滤与数据权限条件，代码层统一注入，不靠人工自觉。
- **索引命名**：`bms-{用途}` 小写连字符，日志按月 `bms-log-{类型}-{yyyyMM}`（见《[命名规范](../../../规范/命名规范.html)》第 10 节）。
- **部署形态**：MVP 单节点；生产多节点集群（索引多副本、故障自动分片迁移）；检索服务故障时降级为数据库模糊查询兜底（见《[项目规划说明](../../../规划/项目规划说明.html#deploy-cluster)》19.2 节）。
- **验收口径**：阶段十四「全文检索」——检索命中与高亮正确、权限与租户过滤验证通过、索引重建可用、降级兜底生效（见《[项目规划说明](../../../规划/项目规划说明.html#plan)》20 节）。

```python
from elasticsearch import Elasticsearch

es = Elasticsearch("http://127.0.0.1:9200")

# 全局搜索：命中业务 ID + 高亮，详情回查数据库
resp = es.search(
    index="bms-main",
    query={
        "bool": {
            "must": [{"match": {"name": "张三"}}],
            "filter": [{"term": {"tenant_id": 1}}],
        }
    },
    highlight={"fields": {"name": {}}},
    size=20,
)
for hit in resp["hits"]["hits"]:
    print(hit["_id"], hit["highlight"]["name"])
```

## 4. 选型对比 <a id="compare"></a>

| 候选技术 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| **ElasticSearch（选中）** | 生态成熟、中文分词插件丰富、ILM 管理按月索引、Kibana 排障方便、Python 客户端官方维护 | ELv2/SSPL 为 source-available（独立服务使用无影响）；JVM 内存开销需规划 | 全文检索 + 日志检索 + 文件检索三场景全覆盖，团队资料最多 |
| OpenSearch | Apache-2.0 许可、AWS 分叉、兼容 ES 7.10 接口 | 插件生态与中文资料略少，版本分叉后资料混杂 | 合格备选，本项目资料与插件面 ES 更全 |
| Apache Solr | 老牌搜索引擎、功能完整 | 配置与运维偏重、生态趋缓、Python 生态弱 | 不采用 |
| PostgreSQL 全文检索（tsvector） | 不新增组件、事务一致 | 中文分词弱（需 pg_jieba 等扩展）、大数据量性能与按月索引管理弱 | 仅作 ES 故障时的降级兜底思路，不作主检索 |

## 5. 常见问题与注意事项 <a id="pitfalls"></a>

- **中文分词**：默认 standard 分析器按单字切中文，检索相关性差；上线前必须装中文分词器（如 IK）并验证「采购申请」这类词能整词命中。
- **别把 ES 当数据库**：ES 只存「业务 ID + 可搜索字段」，详情回查数据库；大文本、大 JSON 不要塞进索引，既费存储又拖慢检索。
- **租户过滤必须代码层强制**：`tenant_id` 过滤条件由公共查询构造器统一注入，禁止各接口手写，防止漏加导致跨租户泄漏。
- **索引重建走事件重放**：重建时先建新索引、灌数、校验条数，再切别名；不要直接删旧索引，避免重建失败无回退。
- **内存规划**：JVM 堆建议为物理内存一半且不超过 32GB（Lucene 依赖文件系统缓存），单节点内存别盲目加堆。
- **日志索引会膨胀**：按月索引要有 ILM 或 Celery 定时清理策略，明确保留期，别让磁盘被旧日志索引吃满。
- **降级兜底要测**：ES 不可用时切数据库模糊查询的降级路径，要在阶段十四验收中实际演练（规划 19.2 节）。
- **许可边界**：不改 ES 源码、不修改后分发；需要官方支持或高级功能时走商业许可（规划 2.5 节）。
