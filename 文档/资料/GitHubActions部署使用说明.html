1. 简介与选型理由

GitHub Actions 是 GitHub 自带的 CI/CD，把工作流文件放进仓库的 .github/workflows/，推送或提 PR 时自动跑。BMS 选它的原因：

  • 与代码仓库一体，PR 的 CI 状态直接显示在合并按钮上，「CI 通过方可合并」的执行成本最低
  • 公共仓库免费额度够用；工作流用 YAML 写在仓库里，改 CI 本身就是一次代码评审
  • 支持服务容器（跑 MySQL/PostgreSQL 集成测试）和依赖缓存，适合 monorepo 的双端检查

当前仓库 .github/workflows/ 尚未创建，CI 属于阶段一任务 10，以下为设计约定。

2. 启用与基本结构

工作流文件放在仓库根目录 .github/workflows/（如 ci.yml），推送到默认分支后 GitHub 自动识别。基本骨架：

name: CI
on:
  pull_request:
  push:
    branches: [main]
jobs:
  backend:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: 运行检查
        run: echo "hello"
      - run: echo "job 内每个 step 独立 shell"

结构就三层：on 声明什么时候触发，jobs 声明跑什么（可多个 job 并行），每个 job 里是依次执行的 steps。每个 job 是全新环境，job 之间不共享文件，需要共享的东西走缓存或产物。

3. 常用做法

3.1 触发条件

on:
  pull_request:              # PR 触发（含更新）
  push:
    branches: [main]         # main 分支推送触发（发布用）
  schedule:                  # 定时触发（如 dependabot 之外的定期检查）
    - cron: "0 2 * * 1"

3.2 服务容器

在 job 里声明 services，runner 上会起一个容器供测试连接：

services:
  mysql:
    image: mysql:8
    env:
      MYSQL_ROOT_PASSWORD: root
    ports: ["3306:3306"]
  postgres:
    image: postgres:16
    env:
      POSTGRES_PASSWORD: postgres
    ports: ["5432:5432"]

集成测试连 127.0.0.1 的映射端口即可。

3.3 缓存

- uses: actions/cache@v4
  with:
    path: ~/.cache/uv        # uv 缓存目录（Windows 为 %LOCALAPPDATA%\uv\cache）
    key: uv-${{ runner.os }}-${{ hashFiles('backend/uv.lock') }}

锁文件变了才换缓存 key；pnpm store 缓存同理（key 用 pnpm-lock.yaml）。缓存命中能把流水线从几分钟压到几十秒。

4. 与 BMS 的集成

CI 阶段一任务 10 未开始，.github/workflows/ 尚未创建。以下为《阶段一·项目骨架说明》第 10 节的设计约定。

4.1 ci.yml 设计

PR 触发，两个独立 job：

job步骤服务容器
backendsetup-uv → uv sync（uv.lock 锁定）→ uv run ruff check → uv run pytest（SQLite 单测 + 双库路由集成测试）mysql:8 + postgres:16，集成测试连真实双库验证平台/租户路由与方言差异
frontendsetup-node（读取 .nvmrc 的 Node ≥ 20.19）→ pnpm install → eslint → vitest run → 双端 build（frontend + frontend-mobile）无

工具版本：Node 本机 v24.15.0 已核；pnpm 11.20.0 已核；Python 3.14 由 uv 管理（setup-uv 后 uv sync 自动装解释器）。缓存：uv 缓存 + pnpm store 缓存。

步骤示意（frontend job）：

steps:
  - uses: actions/checkout@v4
  - uses: actions/setup-node@v4
    with:
      node-version-file: frontend/.nvmrc
  - uses: pnpm/action-setup@v4      # 安装 pnpm（版本见 packageManager 字段）
  - run: pnpm install
  - run: pnpm lint
  - run: pnpm --filter frontend --filter frontend-mobile exec vitest run
  - run: pnpm -F frontend build && pnpm -F frontend-mobile build

阶段十起的 Playwright E2E 作为独立 job：服务容器起 backend（SQLite）与前端产物，覆盖登录/RBAC/核心 CRUD 主流程（规划约定）。

4.2 main 分支发布

阶段八引入镜像仓库后：main 分支推送触发构建镜像并推送仓库，同时导出后端 swagger.json 契约快照；阶段一只做 PR 检查，不做发布。

4.3 dependabot

随仓库初始化一并提交 .github/dependabot.yml，自动提依赖升级 PR：

version: 2
updates:
  - package-ecosystem: "npm"        # 前端依赖
    directory: "/"
    schedule: { interval: "weekly" }
  - package-ecosystem: "pip"        # 后端依赖
    directory: "/backend"
    schedule: { interval: "weekly" }

依赖升级 PR 同样走 CI 检查，通过才可合并；漏洞扫描也靠它兜底（规划安全节提及）。

5. 常见问题

现象处理
PR 更新后工作流没跑确认触发条件写的是 pull_request 而不是别的；.github/workflows 文件本身改动可能不触发，推到 PR 分支任意提交即可
setup-node 报 Node 版本不满足node-version-file 指向的 .nvmrc 内容应为版本号（BMS 是 ≥ 20.19 的固定版本），或直接给 node-version
集成测试连不上 MySQL/PG服务容器连 127.0.0.1 映射端口；确认数据库就绪（加 health-options 或用轮询脚本）再跑测试
缓存不生效key 里的锁文件哈希变了就会 miss，这是正常的；缓存目录写错也会 miss，先看 cache 目录对不对
需要密钥（镜像仓库登录等）在仓库 Settings → Secrets 配置，工作流里用 secrets.xxx 引用，明文不落仓库（阶段八用）
job 之间要传文件（如 swagger.json）用 actions/upload-artifact / download-artifact，job 环境是隔离的
