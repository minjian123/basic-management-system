1. 简介与选型理由

Redis 是内存键值数据库，BMS 拿它做统一缓存：图形验证码、token 黑名单、会话标记、字典/系统参数/菜单树/权限码这些只读热数据、限流计数，都放 Redis。客户端用的是官方 redis-py，它的 redis.asyncio 异步接口和 FastAPI 异步栈是配对的。

选型理由：

  • 官方客户端，async 支持成熟，事件循环里不阻塞
  • SETNX、EXPIRE 这些原子命令是「缓存三防」里互斥锁和 TTL 的基础
  • 带 TTL 的键天然适合缓存与限流，过期自动清理
  • 多实例部署下共用同一个 Redis 才能保证缓存一致，所以集群统一缓存、弃用本地内存缓存（每台机器的本地内存各存一份，数据不一致）

本机核实版本：redis-py（Python 客户端）8.1.0，运行于 Python 3.14.4。Redis 服务端版本未在本机核实，本文档不写服务端版本号。

2. 安装

服务端（本地开发）用 Docker 起一个，一条命令的事：

docker run -d -p 6379:6379 --name bms-redis redis

项目里 deploy/ 目录预留了 Docker Compose 编排，后续统一由 deploy/compose 管理。Windows 本地不建议用 Windows 原生版 Redis（老旧且不维护），用 Docker Desktop 或 WSL 更省心。

客户端：redis>=8.1.0 已经写进 backend/pyproject.toml，进 backend 目录同步：

cd backend
uv sync

验证：

redis-cli ping

返回 PONG 即连通。

3. 常用命令

3.1 服务端与客户端

docker ps                 # 容器是否在跑
docker logs bms-redis     # 看服务端日志
docker restart bms-redis  # 重启
redis-cli                 # 交互式客户端

想可视化看键值，可以用 RedisInsight（GUI 工具），开发时查 key 比较方便。

3.2 键操作命令

SET bms:global:captcha:a1b2 ab12cd EX 300   # 写入并设 TTL 300 秒
GET bms:global:captcha:a1b2                   # 读取
SETNX bms:global:lock:hotkey 1                # 不存在才写入（互斥锁用）
EXPIRE bms:global:lock:hotkey 10              # 给已有 key 设 TTL
DEL bms:global:lock:hotkey                    # 删除
TTL bms:global:captcha:a1b2                   # 查剩余秒数
SCAN 0 MATCH bms:* COUNT 100                  # 按前缀遍历 key

线上排查别用 KEYS bms:*，键多了会阻塞服务端，用 SCAN 游标遍历。

3.3 验证连通性

redis-cli ping          # PONG
redis-cli info          # 服务端信息（内存、连接数）
redis-cli dbsize        # 当前库键总数
redis-cli client list   # 当前连接
redis-cli monitor       # 实时打印所有命令（调试用，别长时间开）

4. 与 BMS 的集成

app/db/redis.py 封装属于阶段一任务 6「数据库接入」，目前尚未实现，落地后生效。
位置说明
backend/pyproject.toml声明 redis>=8.1.0（redis-py）
backend/config.toml（[redis] 段）url = "redis://localhost:6379/0"、timeout = 0.5（单次操作超时秒数）；生产用环境变量 BMS_REDIS_URL 覆盖（密码不落配置文件）
app/db/redis.pyredis.asyncio 异步客户端封装，统一超时与连接管理
GET /readyz连通性检查：对 Redis 执行 PING，500ms 短超时快速失败；Redis 停止时 /readyz 返回 503，恢复后自动转 200

key 命名规范：统一 bms:{租户|global}:{域}:{键} 三段式，租户数据必带租户前缀，平台数据用 global。BMS 里的实际例子：

key用途
bms:global:captcha:{uuid}图形验证码
bms:global:token:blacklist:{jti}登出后 refresh token 黑名单
bms:{tenant}:sess:{session_id}会话有效标记
bms:{tenant}:dict:{locale}:{type}字典缓存（键含 locale 维度，多语言不串）
bms:global:rate:{维度}:{目标}限流计数

所有 key 必须携带 TTL：缓存类短 TTL + 随机偏移；持久状态类（token 黑名单、会话标记、分布式锁、幂等键）TTL 与业务有效期对齐。

缓存三防：

问题对策
穿透（查不存在的 key 打到 DB）查询不存在的数据缓存空值，短 TTL
击穿（热点 key 过期瞬间大量请求打 DB）热点 key 用互斥锁（Redis SETNX）单实例重建缓存，其余请求等锁
雪崩（大量 key 同时过期）过期时间加随机偏移，避免一批 key 在同一秒失效

一致性：先写库后删缓存；写操作后同一会话内读主库，避免读到旧值。降级：Redis 故障时缓存失效直连 DB 并日志告警，限流降级为本地计数，接口短超时（0.5s）快速失败，不拖垮请求。

5. 常见问题

现象处理
redis-cli ping 不通先 docker ps 看容器在不在，docker logs bms-redis 看日志；端口被占则换 -p 映射
应用连不上但 redis-cli 能连多半是连接串问题：redis://localhost:6379/0 的库号、密码（redis://:密码@host:6379/0）、以及生产环境变量 BMS_REDIS_URL 是否生效
请求被 Redis 拖慢检查 config.toml 的 timeout = 0.5 是否生效；单个操作超时会快速失败，不该让请求长时间挂起
key 越堆越多、内存涨大概率有 key 没设 TTL；SCAN 查一遍，TTL 看剩余时间，规范要求所有 key 必须带 TTL
缓存查询每次都穿透到 DB检查空值缓存与三防是否落实；热点 key 要配互斥锁重建，TTL 要加随机偏移
连接数被打满client list 看连接来源；客户端连接池配置收紧，确认没有连接泄漏
