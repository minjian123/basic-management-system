### 2.2 放行规则总表 <a id="rules"></a>

| 规则 | 来源 | 端口 | 用途 |
| --- | --- | --- | --- |
| ALLOW IN | Anywhere | 22/tcp（含 OpenSSH 应用规则） | 系统 SSH |
| ALLOW IN | `<内网网段>` | 2222, 5050, 8080/tcp | GitLab SSH / Registry / HTTP |
| ALLOW IN | `<内网网段>` | 3306, 5236, 5432, 6379, 9000, 9001/tcp | MySQL / 达梦 / PostgreSQL / Redis / MinIO |
| ALLOW IN | `<内网网段>` | 8060/tcp | Kiwi TCMS |
| ALLOW IN | `<内网网段>` | 3389/tcp | xrdp 远程桌面 |

| 默认策略 | — | incoming: deny；routed: allow | Docker 发布端口走 FORWARD 链（见 6.2） |

仅绑定回环地址、无暴露风险的监听：53（systemd-resolved）、631（cups 打印）、3350（xrdp-sesman）。

## 3. 启用步骤 <a id="enable"></a>

本次启用的完整操作（复现或重做时照此执行，均需 sudo）：

```bash
# 1. 放行 FORWARD 链（关键：Docker 发布端口绕过 ufw INPUT，直接走 FORWARD；
#    不加此条则 enable 后所有容器映射端口全部不通）
sudo ufw default allow routed

# 2. 放行 docker 自定义网络接口（关键：runner/job 容器经宿主 IP 回访 GitLab 等
#    服务时源地址是 172.x 网桥网段，不在内网段白名单内，会被 INPUT 链 DROP；
#    接口名以 ip -br addr 实查为准，compose 网络重建后后缀会变，需重新核对）
sudo ufw allow in on br-189d0dae6c70

# 3. 启用（--force 免交互确认；SSH 22 已有全局放行，不会断连）
sudo ufw --force enable

# 4. 核对规则
sudo ufw status numbered
```

## 4. 验证 <a id="verify"></a>

启用后从 mjpc 对全部相关端口做 TCP 连通性实测，结果：

| 结果 | 端口 |
| --- | --- |
| OPEN（12 个，全部符合预期） | 22、2222、3306、5236、5432、6379、8060、8080、9000、9001、3389 |
| BLOCKED（符合预期） | 4236（未放行的 dmap） |

> 2026-08-26 说明：8070 端口随服务移除已从放行规则中删除，因而不计入 OPEN 清单。

其中 5050 实测 BLOCKED，排查确认**与防火墙无关**：GitLab 容器内部并未监听 5050（gitlab.rb 未配置 `registry_external_url`），宿主机 5050 只是 docker-proxy 空映射，从部署起即为预留状态（见 6.3）。

单端口验证模板（PowerShell，mjpc）：

```powershell
$c = New-Object Net.Sockets.TcpClient
$t = $c.BeginConnect('<mjbk-IP>', 8060, $null, $null)
$t.AsyncWaitHandle.WaitOne(1500) -and $c.Connected   # True=通 False=不通
$c.Close()
```

## 5. 日常运维 <a id="ops"></a>

| 操作 | 命令 |
| --- | --- |
| 查看状态与规则 | `sudo ufw status numbered` / `verbose` |
| 新增内网放行 | `sudo ufw allow from <内网网段> to any port <端口> proto tcp comment '<用途>'` |
| 删除规则 | `sudo ufw delete <编号>`（编号取 `status numbered`） |
| 重载规则 | `sudo ufw reload` |
| 临时停用 | `sudo ufw disable`（恢复用 `sudo ufw enable`） |
| 开机自启确认 | `systemctl is-enabled ufw` |

新增服务的规则维护流程：先在《开发部署规划》第 9 节登记端口规划，再按上表命令放行，最后从 mjpc 连通性验证，并在本文档 2.2 总表同步登记。

## 6. 已知边界与注意事项 <a id="limits"></a>

### 6.1 Docker 发布端口不受 INPUT 规则约束 <a id="docker-bypass"></a>

Docker 通过 iptables NAT 直接把容器映射端口挂在 FORWARD 链，**绕过 ufw 的 INPUT 规则**——即 `3306` 这类端口即使只对 `<内网网段>` 放行，容器发布后实际上对任何能路由到 mjbk 的来源开放。当前风险可控：mjbk 位于内网路由器之后（NAT，外网不可达），FORWARD 默认 allow 仅影响内网侧。若日后拓扑变化（如端口映射到公网），需改用 `DOCKER-USER` 链限制来源网段。

### 6.2 routed 策略必须为 allow <a id="routed"></a>

`default allow routed` 是 GitLab 部署时踩过的坑（《[GitLab部署使用说明](GitLab部署使用说明.md)》排障表）：ufw 启用后 FORWARD 链默认 deny，所有容器端口立即不可达。本口径已固化在启用步骤第 2 步，勿省略。

### 6.3 Registry 5050 为预留端口 <a id="registry"></a>

GitLab Registry 尚未启用（gitlab.rb 无 `registry_external_url`），5050 处于「防火墙已放行、服务未启动」状态。启用动作随 main 流水线（准备期任务 02-4 收口）落地：配置 gitlab.rb → `gitlab-ctl reconfigure` 后即可用。

### 6.4 容器回访宿主端口的网桥放行 <a id="bridge"></a>

容器内进程经宿主 IP（如 runner 访问 GitLab `http://<mjbk-IP>:8080`）时，流量走 INPUT 链且源地址为 docker 网桥网段（172.x.x.x），不属于 `<内网网段>` 白名单——若不放行，表现为 i/o timeout（DROP）。已按接口整体放行（`ufw allow in on br-189d0dae6c70`，该接口是 compose 项目自定义网络）。注意：**compose 网络删除重建后接口名后缀会变**，届时旧规则失配、需按新接口名重新放行并清理旧规则。

## 7. 排障记录 <a id="trouble"></a>

| 问题 | 现象 | 处理 |
| --- | --- | --- |
| systemd active 但 ufw 不活动 | `systemctl is-active ufw`=active，`ufw status`=inactive | ufw.service 只负责开机拉起，实际开关由 `ENABLED` 标志决定；以 `ufw status` 为准，用 `ufw --force enable` 激活 |
| 启用后容器端口全不通 | mjpc 访问 3306/8080 等全部超时 | `ufw default allow routed` 未设置，FORWARD 链被 deny；补设后恢复（见 6.2） |
| 5050 放行后仍不通 | TCP 连接被拒而非超时 | 排查顺序：宿主 `ss -tlnp` 有监听 → 本机 curl 也失败 → 容器内 `netstat` 无 5050 → 定位为 Registry 服务未启用，与防火墙无关（见 6.3） |
| 启用后 runner 接不到 job | runner 日志刷 `POST http://<mjbk-IP>:8080/api/v4/jobs/request: i/o timeout`；job 全部 pending | 容器回访宿主端口的源地址是 172.x 网桥网段，被 INPUT 链 DROP（mjpc 验证全通所以未暴露）；`ufw allow in on <docker网桥接口>` 后恢复（见 6.4）。2026-08-22 启用当日实际踩中，runner 断连约 10 分钟 |
