1. 模块概述与职责

本节对应《项目规划说明》「功能模块」之系统监控模块，以及「部署与运维」（监控告警、健康检查、基础设施编排）、「缓存策略」「认证与安全」章节； 架构设计依据《架构设计》22-可观测性 节点（日志、指标、链路、告警、健康检查）。

  • 模块定位：面向运维与管理员提供统一可观测视图：健康检查、指标与日志聚合、告警、缓存管理、依赖状态与链路追踪入口，技术栈 structlog + Prometheus + Loki + Grafana + Alertmanager + OpenTelemetry（Jaeger）。
  • 职责边界：BMS 应用暴露 /healthz、/readyz、/metrics 供采集编排；Grafana 独立部署，BMS 内页面跳转/嵌入展示；缓存管理面向 Redis 运维操作（key 分布/清理/热数据刷新）。
  • 协作关系：告警经 Alertmanager 推送（邮件/企业微信/钉钉/短信，短信经 BMS 内部接口转换）；链路追踪经 otel-collector 上报 Jaeger；缓存管理基于统一 Redis key 命名规范（bms:{租户|global}:{域}:{业务键}）与缓存三防策略。

2.2 业务规则

  • 健康检查分离：/healthz 仅查进程存活；/readyz 检查 DB/Redis 连通性，不健康时编排系统不路由流量（滚动发布依据）；两项为公开端点不鉴权。
  • 指标口径：/metrics 请求量、延迟、依赖状态（DB/Redis/MinIO）、Socket.IO 连接数、RocketMQ 消费积压，由 Prometheus 周期拉取；敏感信息不出现在指标与日志。
  • 日志规范：structlog 结构化 JSON，request_id 贯穿请求链路；敏感字段（密码、token、密钥）脱敏后记录，不落原始值；Loki 聚合跨实例检索。
  • 链路关联：应用经 otel-collector 上报 trace 至 Jaeger，trace_id 与 structlog 的 request_id 关联，随 Grafana 以 Jaeger 数据源统一可视化。
  • 告警路由：Alertmanager——邮件走原生 SMTP receiver；企业微信/钉钉群机器人经 webhook receiver 转 BMS 内部接口转换格式后推送；短信经 BMS 内部接口（复用短信模板与发送渠道 sys_sms_template）；告警面板在 Grafana 同步可见。
  • 缓存管理边界：key 分布与内存占用按 Redis 统计查看；按前缀清理与热数据一键刷新仅限缓存类 key（短 TTL），持久状态类 key（token 黑名单、会话标记、分布式锁、幂等键）禁止清理，防误删导致会话/幂等失效。
  • 嵌入安全：nginx 统一配置 X-Frame-Options（SAMEORIGIN），兼容同源 Grafana iframe 嵌入；嵌入经统一鉴权入口。

2.3 流程步骤

  1. 采集：Prometheus 按周期拉取 /metrics；Loki 汇聚 structlog 日志；应用上报 trace 至 Jaeger（经 otel-collector）。
  2. 展示：Grafana 统一看板（指标 + 日志 + 告警面板 + Jaeger 数据源）；BMS 系统监控页跳转/嵌入，另展示依赖状态与缓存概览。
  3. 告警：Prometheus 规则触发 → Alertmanager 按路由分发（邮件/企业微信/钉钉/短信）→ 告警面板同步可见。
  4. 缓存运维：监控页查看 key 分布与内存占用 → 按前缀定位异常 key → 执行清理（monitor:cache）或热数据一键刷新。
  5. 异常分支——依赖故障：DB/Redis/MinIO 连通性异常时依赖状态展示异常，/readyz 返回不健康，触发告警；Redis 故障时缓存失效直连 DB 并告警，限流降级 memory 后端。

3. 关键时序与协作

指标与日志链路：
  后端应用 ──/metrics──▶ Prometheus（请求量/延迟/依赖状态/Socket.IO 连接数/消费积压）
  后端应用 ──structlog JSON 日志（request_id）──▶ Loki ──跨实例聚合检索──▶ Grafana
  后端应用 ──OpenTelemetry──▶ otel-collector ──trace──▶ Jaeger（trace_id ↔ request_id）

告警链路：
  Prometheus 规则触发 ──▶ Alertmanager
      ├─ 邮件 ──▶ SMTP receiver
      ├─ 企业微信/钉钉 ──▶ webhook receiver ──▶ BMS 内部接口转换格式 ──▶ 群机器人
      └─ 短信 ──▶ BMS 内部接口（sys_sms_template 渠道）
  告警 ──▶ Grafana 告警面板同步可见

缓存管理：
  监控页 ──key 分布/内存占用查看──▶ Redis（MONITOR 统计只读）
  监控页 ──按前缀清理 / 热数据一键刷新（monitor:cache）──▶ Redis（仅限缓存类 key）

与部署编排协作要点：/healthz、/readyz 供 Docker Compose / 编排系统滚动发布探针；优雅停机 SIGTERM 后停止接收新请求、等待在途请求完成。 与事件总线协作要点：RocketMQ 消费积压与死信纳入指标与告警。

4. 数据模型与表设计

本模块不新增业务表：指标、日志、trace 与告警数据分别存于 Prometheus/Loki/Jaeger/Alertmanager 的存储中（监控组件独立部署）；BMS 侧仅提供只读视图与运维操作。

数据载体说明
Prometheus指标时序数据（请求量、延迟、依赖状态、Socket.IO 连接数、消费积压）
Loki结构化 JSON 日志聚合（request_id 检索）
Jaeger链路追踪数据（trace_id 与 request_id 关联）
Grafana看板与告警面板（Prometheus/Loki/Jaeger 数据源统一可视化）
Redis（监控目标）缓存 key 分布/内存占用为运维查看对象；缓存 key 遵循统一命名规范 bms:{租户|global}:{域}:{业务键}，全部携带 TTL
  • 数据流转：应用埋点/埋日志 → 采集组件（Prometheus/Loki/otel-collector）→ 存储（TSDB/日志存储/Jaeger）→ 看板展示与告警触发。
  • 安全：指标与日志不落敏感字段；缓存清理操作落操作日志（谁在何时清理了哪些前缀）。

5.2 公共要求

  • 公开端点（/healthz、/readyz、/metrics）不鉴权、不受用户限流影响，供编排与采集；其余接口走标准鉴权与限流。
  • 缓存清理接口幂等：重复清理同一前缀不报错；清理范围参数化校验（仅允许配置过的缓存前缀，防止误清持久状态类 key）。
  • 缓存清理/刷新操作落操作日志（module=monitor、action=monitor:cache）。

5.3 发布事件

本模块不发布业务事件；告警经 Alertmanager 分发（邮件/企业微信/钉钉/短信），短信推送经 BMS 内部接口转换，发送记录落 sys_sms_log。

6. 权限与配置

  • 权限码：业务 monitor（系统监控含缓存管理，默认归属普通角色）；动作 view、cache；典型权限码 monitor:view（查看监控/依赖状态）、monitor:cache（缓存清理与热数据刷新）。
  • 菜单挂接：菜单「系统监控」「缓存管理」→ 表单 → 业务权限 monitor；缓存操作按钮（清理/刷新）按 monitor:cache 动作权限显隐。
  • sys_config：可配置项包括告警接收人/群机器人地址、短信告警开关、缓存前缀白名单、Grafana 嵌入地址等。
  • 种子数据：monitor 业务与 view/cache 动作权限码为平台种子；系统监控/缓存管理菜单挂接随平台菜单种子下发；监控组件（Prometheus/Loki/Grafana/Alertmanager/Jaeger）由部署编排随 Compose 启动。

7. 错误码与异常处理

错误码 5 位数字，万位为模块段、后 4 位为段内序号，一经发布稳定不变；文案由前端按 i18n 映射（error.{code}），后端不承担文案拼装。本模块错误码段：

段区间覆盖模块
9xxxx90001-99999报表/审计/归档/监控（本模块规划于 93xxx 段内序号）
  • 错误码覆盖：缓存前缀不在白名单、清理目标为持久状态类 key 被拒绝、依赖状态查询失败、Grafana 跳转鉴权失败等。
  • 异常处理要求：依赖组件（Prometheus/Loki/Grafana）故障不影响 BMS 业务主链路（监控只读降级展示）；Redis 故障时缓存管理接口返回明确错误并告警，业务侧缓存失效直连 DB；缓存清理失败整体回滚不留半清理状态，操作全程落操作日志。
