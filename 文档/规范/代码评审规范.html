1. 目的与适用范围

规定 BMS 代码评审的流程与关注点，在合入 main 前发现功能、性能、安全与规范问题。 流程入口见《Git协作规范》第 5 节 MR 流程；本规范约束评审本身。

2. 评审流程

  1. 前置：CI 全绿（ruff、pytest、ESLint、Vitest、构建）后进入评审。
  2. 指派：作者指派至少 1 名评审人；涉及数据库/安全变更需指定对应领域评审。
  3. 评审：按第 3-6 节清单逐项检查，在 MR 上留行内评论。
  4. 处理：作者逐条回复（已修复 / 已说明理由），全部 resolved 后批准。
  5. 合入：评审通过 + CI 通过 → Squash 合并 → 删除源分支（见《Git协作规范》）。

3. 通用评审清单

  • □ 变更范围与 MR 描述一致，无「顺便改」
  • □ 命名符合《命名规范》（无拼音/缩写不明/风格不一致）
  • □ 提交信息规范，提交粒度合理
  • □ 有对应测试（新功能/修复必须），CI 覆盖
  • □ 无死代码、调试残留、硬编码魔法值
  • □ 依赖变更（pyproject/package.json）有理由说明

4. 后端重点

  • 接口符合《API接口规范》：URL/响应/错误码/幂等。
  • 鉴权与权限码完整（含数据范围），归属校验（越权防护，见《安全开发规范》）。
  • SQL 参数化、无 N+1、批量操作分批（见《数据库开发规范》）。
  • 类型注解完整（pyright 严格模式）、异常处理合理（不吞异常、不裸 except）。
  • 日志符合《日志规范》：级别正确、无敏感信息、含上下文。
  • 异步链路：await 使用正确、连接池与会话生命周期（SQLAlchemy AsyncSession）正确释放。

5. 前端重点

  • 组件/页面命名与目录规范（《命名规范》第 9 节）；路由 path kebab-case。
  • 权限指令 v-perm 使用正确；接口调用统一走 src/api 模块。
  • 类型来自 OpenAPI 生成（openapi-typescript），无手写漂移（《API接口规范》第 8 节）。
  • 无 v-html 渲染不可信内容；表单校验与后端一致。
  • i18n 文案走语言包，无硬编码中文（《国际化规范》）。
  • 组件复用与性能：虚拟列表/懒加载，无大列表直接渲染。

6. 数据库变更重点

  • 迁移脚本三库可执行（方言兼容，见《数据库开发规范》第 5-6 节）。
  • 字段/索引命名合规，索引数量与冗余检查。
  • 数据迁移脚本幂等、可重跑；大表变更分批。
  • 变更需在三库 CI 用例通过（main 流水线）。

7. 评审意见规范

  • 意见明确可执行：指出问题 + 期望结果（必要时给示例）；不只有「这里不对」。
  • 区分严重度：阻塞（安全/数据丢失/功能错误，必须修复后才可合入）、建议（可后续优化，作者记录 TODO）。
  • 语气就事论事；评审对象是代码不是作者。
  • 作者对「建议」级意见可用理由拒绝并在 MR 中说明，评审人确认后 resolved。

8. 时效与规模

项约定
评审响应工作日内 24h 内给出首轮意见
MR 规模单 MR ≤ 400 行变更（数据库迁移与生成的类型文件除外）；超限拆分
阻塞项不修复不合入；紧急修复（fix）可放宽到 2 人快速确认
