1. 目的与适用范围

统一 BMS 前端两个工程（frontend PC 管理端、frontend-mobile 移动端 H5）的开发方式。 两工程同源同规：本文档约定对两者同时生效，差异处单独标注。 与《命名规范》《项目规划说明》配套；后端约定见《后端开发规范》。

2. 工程结构

  • frontend 与 frontend-mobile 组成 pnpm workspace：共享 ESLint/Prettier/TS 基础配置包，源码各自独立
  • src 目录固定分层（两工程一致）：api / router / stores / views / layouts / components / i18n / utils
  • views 与 components 按模块分组：views/user/UserList.vue、components/xxx/；模块目录用单数名词
  • 业务代码禁止放 utils 之外的非约定目录；新增目录需在代码评审中说明理由

3. 组件规范

  • 单文件组件（SFC），组合式 API（<script setup>）；组件名 PascalCase 单数名词（UserForm.vue、DeptTree.vue）
  • 通用组件放 components/common/（可复用、无业务依赖）；业务组件就近放模块下，禁止跨模块乱放
  • props 用 defineProps + 类型声明，必填项标注 required；事件用 defineEmits 且动词命名（submit、cancel）
  • 组件尽量无副作用：数据获取放页面层或 composable，组件内部不直接调 API（通用组件尤其严格）
  • Element Plus 组件二次封装遵循原有 API 命名习惯，不另起名字

4. 页面与路由

  • 页面文件 views/模块/页面.vue（PascalCase）；一个菜单/表单对应一个页面组件（对应后端 sys_menu/sys_form 挂接）
  • 路由动态生成：由后端菜单接口返回的菜单树注册，前端不硬编码路由表；路由 path 用 kebab-case、name 用 PascalCase
  • 路由守卫：登录态校验（无 token 跳登录）；菜单级权限已由后端过滤，守卫只做兜底
  • 页面骨架：列表页（筛选区 + 表格 + 分页 + 工具栏）、表单页（表单 + 校验 + 提交）统一模式，复用通用封装

5. 权限控制

  • 按钮与操作显隐用 v-perm="'业务:动作'" 指令（默认无按钮权限，未授权即隐藏）；字段显隐/禁用由表单元数据中的字段权限状态驱动
  • 菜单可见性：后端已按业务权限过滤菜单树，前端不得自行放行无权限入口
  • 权限码只作为显隐依据，接口安全由后端强制校验；前端隐藏不等于安全
  • 权限相关配置（业务码/动作码）改动走平台侧菜单管理，前端不硬编码权限码清单（除通用动作常量）

6. 状态管理

  • Pinia store 命名 useXxxStore（useUserStore、useDictStore）；按领域模块化，禁止巨型 store
  • 服务端数据不进 store（页面内 onMounted 拉取或 composable），store 只存跨页面共享态（用户信息、菜单树、字典、语言偏好）
  • 持久化仅限必要项（语言偏好 localStorage）；token 存内存，refresh token 走 httpOnly cookie（不落前端存储）

7. API 层

  • src/api/模块.ts，函数命名 getXxxList / getXxx / createXxx / updateXxx / deleteXxx，与后端 RESTful 对应
  • Axios 统一封装（utils/request.ts）：注入 access token、401 静默刷新、统一错误提示（按错误码映射 i18n）、请求取消支持
  • 类型契约：经 openapi-typescript 由后端 OpenAPI schema 自动生成 TS 类型，禁止手写与后端重复的接口类型；后端字段变更同步再生成
  • 分页请求/响应类型统一（PageResult），列表页封装统一分页逻辑

8. 国际化

  • vue-i18n：语言包运行时从后端拉取（/api/v1/i18n/messages），localStorage 缓存语言偏好；新增语言免发版
  • key 命名点分：模块.页面.字段（user.form.username、common.confirm、error.20001）
  • 界面文案禁止硬编码；后端返回的提示文案不做二次翻译（后端文案已入库维护）
  • RTL 语言由 sys_i18n_locale.rtl 标记驱动布局切换，样式开发时考虑 RTL 兼容

9. 样式规范

  • SCSS：Element Plus 主题变量定制放全局 styles/；组件样式 <style scoped lang="scss">
  • 类名 kebab-case，BEM 简化（.user-form__title）；禁止内联 style（动态值除外，动态值用 CSS 变量）
  • 移动端（Vant）与 PC（Element Plus）主题分别维护，公共样式放 workspace 共享包
  • 响应式：PC 管理端桌面优先；H5 移动优先；公用断点变量统一声明

10. 代码风格

  • ESLint + Prettier（vue 官方插件链）；TS 严格模式；CI 与本地提交前必须通过
  • 命名：变量/函数 camelCase、组件/类型 PascalCase、常量 UPPER_SNAKE、路由 path/CSS kebab-case（见《命名规范》）
  • 函数单一职责，禁止超长函数（超 60 行拆分）；注释中文，说明「为什么」
  • 禁止：any 滥用（确需时注明原因）、console.log 遗留、未使用的导入与变量

11. 测试规范

  • Vitest：组件测试文件 组件名.spec.ts（UserForm.spec.ts）；覆盖 props/事件/校验逻辑，API 用 mock
  • Playwright E2E：功能.spec.ts（login.spec.ts）；覆盖登录、主体链 RBAC 权限（按钮/字段显隐）、核心 CRUD 主流程；移动端用视口模拟
  • E2E 环境：CI 起 backend（SQLite）与前端产物；测试数据独立种子
  • 前端类型变更触发 API 类型重新生成后，相关页面编译错误即 CI 拦截，不得跳过

  • □ 组件 props/emits 类型完整，通用组件无业务 API 调用
