1. 目的与适用范围

规范 BMS 各环境的部署与发布：环境分层、镜像版本、发布与回滚流程，保证可重复、可追溯。 部署拓扑与编排见《开发部署规划》第 7/9/10 节与《架构设计-部署与运维》。 <mjbk-IP> 取值见《本地资源》。

2. 环境管理

环境标识用途数据
开发BMS_ENV=dev本地开发（mjpc），内网访问 mjbk 共享服务SQLite / bms_dev

  • 环境间数据与配置隔离，密钥仅存在对应环境。

3. 镜像与版本

  • 镜像命名：bms-backend、bms-frontend（《命名规范》第 10 节）。
  • 镜像标签与 Git 标签一致：bms-backend:v1.2.0；临时构建用 main-<短sha>，禁以 latest 覆盖发布版本。
  • 镜像存 GitLab Registry（:5050）；生产拉取走内网或镜像同步。
  • 构建产物可复现：Dockerfile 多阶段构建 + 依赖锁定（uv.lock / package-lock.json）。

4. 发布流程

  1. 准备：main 合入发布提交；打标签 vX.Y.Z（《Git协作规范》第 6 节）。
  2. 构建：CI main 流水线构建 bms-backend/bms-frontend 镜像并推送 Registry（见《开发部署规划》第 7 节）。
  3. 迁移：先执行数据库迁移（Alembic），再发布应用（迁移先行，应用向后兼容一个版本）。
  4. 部署：Compose 滚动更新（backend 多副本逐个替换）；前端静态资源由 nginx 托管。
  5. 验证：/healthz、/readyz 通过；核心冒烟用例（登录 → 主体链 CRUD）执行。
  6. 记录：发布记录（版本、时间、变更、负责人）登记；发布后监控关键指标 30 分钟（阶段八起）。
演进：数据量或规模增长后迁移 Kubernetes（规划第 7 节），发布流程平移为滚动/蓝绿。

5. 回滚

  • 应用回滚：Compose 回退镜像标签至上一版本（bms-backend:v1.1.0），重启完成。
  • 数据库回滚：迁移先行策略下应用回滚即可；结构回退需评估（破坏性迁移不可逆时走数据修复脚本）。
  • 数据备份前置：生产发布前数据库每日备份 + PITR（Binlog/WAL）；归档库纳入备份（《项目规划说明》「备份与恢复」）。
  • 回滚时限：发现严重问题 30 分钟内回滚；回滚后复盘根因并补充回归用例。

6. 发布前检查

  • □ 代码评审通过、CI 全绿、三库集成测试通过
  • □ 迁移脚本已评审并在测试环境执行过
  • □ 镜像标签与 Git 标签对应，Registry 可访问
  • □ 环境变量与密钥就位（BMS_ENV 正确）
  • □ 备份任务正常、可回滚版本确认
  • □ 发布窗口与值班人确认（生产）

7. 检查清单

  • □ 环境配置分层正确，密钥不入代码
  • □ 镜像标签语义化，构建可复现
  • □ 迁移先行、应用兼容上一版本
  • □ 健康检查与冒烟验证通过，发布有记录
  • □ 回滚方案与备份就绪
