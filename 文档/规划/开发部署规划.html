1. 目的与依据

本文档规划 BMS 项目开发环境的整体部署方案：在《本地资源》记载的两台 Windows 11 机器上， 搭建可支撑《项目规划说明》全部 14 个开发阶段、直至 MVP 验收（含 500 并发压测）的完整开发环境， 包括代码托管与 CI/CD、开发依赖服务、常驻数据库、监控与备份。

依据与约束：

  • 《项目规划说明》「环境与配置」「部署与运维」「开发计划与验收标准」各节的技术选型与阶段划分
  • 《架构设计-部署与运维》的部署拓扑与集群设计要点
  • 《命名规范》对基础设施命名（Compose 服务名、环境变量、数据库、容器镜像）的约定
  • 《文档生成规范》对文档格式与布局的要求

本文档为规划性质，确定方案、目录、端口与落地节奏；命令级细节（Compose 文件内容、环境变量清单、备份恢复演练步骤）由阶段八交付的《部署手册》细化。

采用「一台常开服务器承载全部服务、一台高性能开发机纯本地开发」的模式：

2.3 网络拓扑

  • 两台机器同处 192.168.0.0/24 内网网段，直连互访，无需域名与证书。
  • 开发期租户识别不启用子域名（《项目规划说明》已定：dev 环境以 token 内租户标识替代子域名），因此不需要泛域名 DNS 与泛 TLS 证书。
  • mjpc 后端/前端开发服务器指向 mjbk 的 192.168.0.107 各服务端口；mjbk 上 Windows 防火墙按第 4.6 节放行。
  • mjbk 需可访问外网（下载容器镜像、GitLab 向 GitHub 的 push mirror 同步、Renovate 拉取依赖更新）；不可达时镜像同步与依赖升级暂缓，见第 11 节。

4. 开发服务器 mjbk 部署

4.1 基础环境准备

  1. 确认 WSL2：Windows 11 专业版已内置支持。PowerShell 检查： 
    wsl --version
    输出为 WSL 2.x 即可；若提示未安装，执行 wsl --install 后重启。
  2. 安装 Rancher Desktop（官网 rancherdesktop.io，或 winget）： 
    winget install RancherDesktop.RancherDesktop
  3. 切换容器运行时为 dockerd：Rancher Desktop 默认使用 containerd 运行时，需在 「设置 → Container Engine → Docker (dockerd)」切换为 dockerd（moby），保证 docker 与 docker compose 命令及行为与规划一致。切换后验证： 
    docker info
docker compose version
  4. 数据目录重定向：Rancher Desktop 的镜像与虚拟机磁盘默认落在 C 盘 AppData，在 「设置 → General → Data directory」改为 D:\bms-data\rancher，避免 C 盘膨胀（见 4.2）。
  5. WSL2 内存上限：mjbk 上 WSL2 默认最多占宿主机 50% 内存，按需限制。在 %UserProfile%\.wslconfig 写入： 
    [wsl2]
memory=24GB
processors=8
swap=4GB
    保存后执行 wsl --shutdown 使配置生效。24GB 上限为容器与 GitLab 预留，同时保住宿主机可用内存。
  6. 开机自启：设置 Rancher Desktop 开机自启（设置 → General → Start on login），保证开发依赖服务常开。

4.2 磁盘规划

盘容量存放内容目录约定
C 盘（SSD） 512 GB MySQL / PostgreSQL / 达梦 DM8 数据卷、ES 数据、MinIO 数据、Redis 持久化（IO 敏感） Compose 命名卷（mysql_data、postgres_data 等）
D 盘（HDD） 1 TB 容器镜像存储（Rancher Desktop data）、GitLab 数据、CI 构建缓存、数据库备份 D:\bms-data\rancher（引擎数据）
D:\bms-data\gitlab（gitlab 数据卷挂载目录）
D:\bms-data\backup（备份，见第 8 节）
ES 与数据库数据严禁放 HDD：ES 段合并、数据库随机读写会明显拖慢开发联调体验。镜像与 GitLab 仓库读多写少、顺序读写占比高，HDD 可承受。

4.4 常驻数据库

  • MySQL 8、PostgreSQL 16 与达梦 DM8 三库常驻 mjbk，供开发联调与 CI 三库方言集成测试共用（决策 3、决策 7）。达梦用官方镜像 dmdbms/dm8（含试用授权，商业交付需采购商业许可）。
  • 日常开发仍以本地 SQLite 为主（零部署）；需要验证方言行为时，后端以环境变量覆盖数据源连接指向 mjbk 三库。
  • 库名遵循《命名规范》第 7 节环境库约定与多租户库划分（达梦以模式 schema 承载库语义）：
用途MySQL / PostgreSQL / 达梦库名说明
开发联调bms_dev（平台库 + 租户库模拟可再建 bms_platform、bms_tenant_*、bms_archive）开发期按需创建，模拟多数据源拓扑
CI 集成测试bms_test 前缀（job 内建库 → 迁移 → 测试 → 删库）每次 job 独立、互不污染，与开发数据隔离
  • 账号与密码只写入 deploy/.env（不入库、不入镜像、不写入本文档），详见第 6 节。
  • 三库均开启慢查询日志（开发联调排查用）；MySQL 字符集 utf8mb4、PostgreSQL 与达梦 UTF8（规划「数据规范」节约定）。
  • 达梦 Python 驱动 dmPython 为官方同步驱动（dialect dm+dmPython），对 Python 3.14 兼容性未知，纳入阶段一逐依赖验证，不兼容则按规划口径整体回退 Python 3.13。

4.5 GitLab 与 CI 基础设施

  1. GitLab CE 容器（deploy/compose/gitlab.yml）：
    • 镜像 gitlab/gitlab-ce，端口映射 HTTP 8080（容器内 80）、Registry 5050；SSH 22 端口可选映射 2222（内网开发走 HTTP 即可，不强制）。
    • 数据目录挂载 D:\bms-data\gitlab（配置、仓库数据、备份），避免 C 盘膨胀。
    • 首次访问 http://192.168.0.107:8080 设置 root 密码；访问地址需写入容器 external_url 配置，否则 GitLab 生成的仓库/克隆 URL 不正确。
    • GitLab 内存 ≥ 4GB 预算（《项目规划说明》要求），mjbk 32GB 满足。
  2. gitlab-runner 容器（同文件）：
    • 镜像 gitlab/gitlab-runner，挂载宿主机 docker.sock 供 executor=docker 使用。
    • 注册命令（token 在 GitLab 管理界面生成）：
    docker exec -it gitlab-runner gitlab-runner register \
  --url http://192.168.0.107:8080 \
  --token <runner-registration-token> \
  --executor docker \
  --docker-image python:3.14-slim \
  --docker-volumes /var/run/docker.sock:/var/run/docker.sock \
  --tag-list bms,docker
    • runner 并发限制：mjbk 为 6 核 12 线程，注册后设置并发上限（config.toml 中 concurrent = 2），避免 CI 抢占 GitLab 与开发服务的资源。
  3. Renovate：阶段二起以容器方式随 gitlab.yml 编排，自动提依赖升级 MR；需 mjbk 可访问外网。
  4. GitHub 归档镜像：GitLab 配置 push mirror 将 main 单向同步至 GitHub 归档仓库；同样依赖外网，不可达时暂缓。

4.6 防火墙与访问控制

  • Windows 防火墙仅对 192.168.0.0/24 内网放行第 9 节端口清单（PowerShell 管理员执行，示例）：
New-NetFirewallRule -DisplayName "BMS-Dev-LAN" -Direction Inbound `
  -Protocol TCP -LocalPort 8080,5050,3306,5432,5236,6379,9000,9001,9876,10911,9200,9090,3100,3000,9093,16686,4317,4318 `
  -RemoteAddress 192.168.0.0/24 -Action Allow
  • 各容器仅绑定内网可访问范围（Compose 端口映射默认 0.0.0.0，配合防火墙限制来源即可）。
  • 敏感端口（MySQL/PostgreSQL/达梦/Redis）密码强度按第 6 节管理，避免仅靠防火墙单点防护。

6. 配置与凭据管理

  • 三套环境 dev / test / prod 由 BMS_ENV 指定，config.toml 按环境分层 + 环境变量覆盖（《项目规划说明》「环境与配置」节）。
  • 仓库只提交 deploy/.env.example（键名模板、无真实值）；真实 deploy/.env 加入 .gitignore，仅存在于 mjbk。
  • 密钥类配置（DB/Redis 密码、JWT secret、MinIO 凭据、GitLab token）只走环境变量，不落配置文件、不入库、不入镜像、不写入本文档。
  • 机器登录凭据以《本地资源》为准，本文档不重复记载。
  • GitLab root 密码、runner 注册 token、数据库账号初始密码在首次部署时生成并记录于 mjbk 本地密码管理器（或仅限本机的密钥文件），不随文档与仓库流转。

7. 开发工作流与 CI

  1. 分支模型：main 保护分支；开发在 feature/xxx 分支进行，push 至 mjbk GitLab 后提 Merge Request。
  2. MR 流水线（gitlab-runner 在 mjbk 执行）：
    • 后端：ruff 检查 + pytest（SQLite）
