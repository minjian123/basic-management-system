## 1. 概述 <a id="overview"></a>

帮助中心子系统承载系统使用帮助文档：帮助分类与文章维护（在线编辑入库）、前台展示（PC + 移动端）、页面内帮助按钮、阅读反馈与统计，并纳入全文检索与 AI 问答知识源。对应[《项目规划说明》](../../规划/项目规划说明.md)的「帮助中心」模块。与公告区分：公告为全员临时通知，帮助为常驻知识库。

**定位（2026-10-31 口径）**：帮助中心**不是内容管理模块，而是与权限同级的横切机制**——功能声明自己要哪篇帮助（锚点），运行时按上下文解析并展示，内容既可后台维护也可随产品包装载。三层结构，各自可独立验收：

| 层 | 内容 | 缺了会怎样 |
| --- | --- | --- |
| **声明面** | 菜单 / 表单 / 字段 / 动作元数据上的 `help_key`（与权限码同一登记面，产品清单装载） | 退化成「人工建文章 + 手填 target」，新功能上线无人知道要补帮助，也查不出谁漏了 |
| **装载面** | 平台定规范的 `help/*.yaml` 帮助包：装载 / 升级 / 卸载 / 冲突 | 每个产品的帮助只能逐篇人工录入，版本与升级无人管，卸载留垃圾 |
| **内容面** | 分类、文章（草稿/发布/下架/置顶）、多语言附表、阅读与反馈统计 | 没有可读内容与质量反馈 |

**与权限的关系**：权限回答「能不能做」，帮助回答「怎么做」。两者共用同一套登记面（业务码 / 动作码 / 表单键 / 字段键），因此帮助覆盖率可以与权限清单逐项对账（见 §3.4），这是「横切机制」与「内容模块」的实质差别。

## 2. 分类管理 <a id="category"></a>

- sys_help_category：parent_id、name、sort、status——分类树（如 快速上手/系统管理/业务操作）
- 多级分类（树状），前台按分类导航；删除分类前需先处理其下文章（迁移或级联下架）
- 分类排序 sort 控制展示顺序；status 控制前台可见性

## 3. 文章管理 <a id="article"></a>

### 3.1 文章状态机 <a id="article-state"></a>

| 状态 | 迁移 | 说明 |
| --- | --- | --- |
| 草稿（draft） | 新建/编辑保存 → 草稿；发布 → 已发布 | 仅后台可见，不进入前台与检索 |
| 已发布（published） | 发布 → 已发布；下架 → 已下架；编辑保存 → 草稿或直接发布新版本 | 前台展示；发布后触发 sys.help.article.published 事件（检索同步） |
| 已下架（offline） | 下架 → 已下架；重新发布 → 已发布 | 前台隐藏，检索同步删除 |

- 置顶（is_top）：分类内置顶展示；发布时间 publish_at 控制
- 删除：物理删除（帮助内容可重建，软删除不必要）——或复用软删除规范；定案：复用软删除（deleted_at），回收站可恢复

### 3.2 在线编辑与 i18n <a id="article-edit"></a>

- 后台在线编辑（富文本/轻 Markdown），内容入库 sys_help_article.content；作者 author_id 记录
- 多语言：标题/内容存 sys_help_article_i18n（article_id + locale 联合主键），前台按当前 locale 展示，缺省回退默认语言
- 保存前内容校验（长度限制、XSS 过滤——富文本按白名单清洗）

### 3.3 产品帮助包与装载注册 <a id="package"></a>

各产品仓（biz / mdm / cw）与平台内建都通过**帮助包**提供内容，而不是在后台逐篇录入。

- **包格式（平台定规范）**：`help/*.yaml`，顶层 `product_key` / `package_version` / `articles[]` / `checksum`；单篇文章含 `source_key`（包内稳定键，升级比对用）、`category_path`（按路径定位分类，避免硬编码 ID）、`target_type` / `target_key`、`anchors[]`（可挂多个锚点）、各 `locale` 文案与 `status`
- **装载器**：`ops.help_package`（命令行 + 服务层同一实现），幂等键 `(product_key, source_key, package_version)`；支持 `--dry-run` 输出将新增 / 更新 / 下线的条数
- **升级同步**：包内新增 → 插入；内容变更 → 更新**但保留租户本地覆盖层**（`local_override` 标记的行不被覆盖）；包内移除 → 标 `offline`（不物理删，保留审计与回收站可恢复）
- **卸载**：按 `product_key` 下线该包的**全部**来源文章；租户自建文章（`source=manual`）不受影响
- **冲突策略**：同一 `target` 命中多篇时按来源优先级 `builtin > product > tenant` 取用，同来源取 `package_version` 高者；产品包**不得覆盖**平台内建同 target 的文章，装载时记告警并跳过
- **表**：`sys_help_package`（package_id、product_key、package_version、checksum、article_count、loaded_at、status），文章表增 `source` / `package_id` / `source_key` / `local_override`

### 3.4 锚点声明与覆盖率门禁 <a id="anchor"></a>

- **声明位置**：`help_key` 声明在菜单 / 表单 / 字段 / 动作元数据（`sys_menu` / `sys_form` / `sys_field` / `sys_action`），与权限码、能力声明同一登记面；平台内建与产品清单同面装载，不在业务代码里硬编码文章 ID
- **注入时机**：菜单接口与表单元数据接口随响应下发 `help_key`（前端据此决定帮助按钮显隐与跳转锚点），不由前端写死模块名
- **覆盖率门禁**：CI 脚本对账「有权限码的动作 / 菜单」与「已声明 `help_key` 的动作 / 菜单」，差集输出为**可计数的台账**（按产品 / 模块分组）；默认不阻断构建、进阶段报告，强档可配置为阻断
- **口径**：动作级覆盖率 =（有 `help_key` 的动作数）/（有权限码的动作数）；缺失项不是「文档没写」，而是「机制没接」——必须落到具体的动作码上才可整改


## 4. 前台展示 <a id="apps/desktop"></a>

### 4.1 入口 <a id="frontend-entry"></a>

- PC：工作台快捷入口卡片 + 个人中心菜单项 + 帮助中心页面（分类树 + 文章列表 + 文章详情）
- 移动端：工作台/个人中心入口，帮助文章列表与详情页（复用后端接口）
- 前台阅读无需额外权限（登录即可）；后台维护需 help:manage

### 4.2 页面内帮助按钮 <a id="frontend-button"></a>

- **解析链（按优先级逐级降级）**：字段（`field_key`）→ 动作（`action_code`，如「新建」「导出」）→ 表单（`form_key`）→ 模块（`module_key`）→ 全局；命中即弹文章并定位锚点，全不命中给「该功能暂无帮助」+ 打开所属分类列表（不留空白，也不假装有内容）
- **定位依据**：请求上下文（路由 / `form_key` / `field_key` / `action_code`）由前端从元数据取，不在前端硬编码模块名；`help_key` 由菜单与表单元数据接口下发
- **按钮显隐**：解析链上任一级命中才显示按钮；未命中不显示（避免「点了没反应」）
- **多篇命中**：同 target 多篇时按来源优先级 `builtin > product > tenant`（见 §3.3 冲突策略）取一篇，其余在「相关内容」中列出

## 5. 阅读反馈与统计 <a id="feedback"></a>

- sys_help_feedback：article_id、user_id、feedback（helpful/unhelpful）、comment、created_at；联合主键（article_id + user_id）防重复反馈（可改投）
- 阅读计数：打开文章详情 +1（view_count）；有帮助/无帮助计数（helpful_count / unhelpful_count）展示于文章底部
- 后台统计视图：按文章/分类查看阅读与反馈，驱动文档优化

## 6. 检索与 AI 联动 <a id="search-ai"></a>

- 纳入全文检索（后续）：sys.help.article.published / updated / deleted 事件驱动 ES 同步（bms-main 主数据索引含帮助文章），前台帮助中心与全局搜索可命中
- 纳入 AI 知识源（后续）：知识库问答机器人与语义搜索可引用已发布帮助文章（RAG 上下文遵守数据权限——帮助文章属租户库，按租户隔离）
- 草稿/下架文章不进入检索与 AI 知识源

## 7. AI 智能维护（后续） <a id="ai-maintain"></a>

帮助文档智能维护为阶段十九 AI 第八项能力（见[26-AI服务节点](26_架构设计_子系统_AI服务.md)）。**本节点先行定义架构位与边界**，阶段八只交付「可被 AI 消费的输入面」与「人工维护闭环」，不实现生成能力。

### 7.1 为什么帮助文档适合 AI，以及 AI 的边界 <a id="ai-why"></a>

帮助文档的特殊性决定了它的可自动化程度远高于代码：**它只是功能的提炼与说明，只读产出，不改任何功能、代码或数据**；但它必须紧跟功能调整，逐条逐页维护，极其繁琐细致——这正是 AI 的强项，也是人工最容易欠账的地方。

| 维度 | 口径 |
| --- | --- |
| **可写范围** | 只写帮助内容（文章正文、标题、分类归属、锚点建议）与**草稿**；不得改功能、权限、菜单、表单、字典、参数、代码与业务数据 |
| **产物形态** | 一律 `draft`（草稿）+ `provenance`（`author=ai` / `model` / `reviewed_by`）；未审核不进包、不对前台可见 |
| **决策权** | 发布与否由人决定；AI 不得覆盖已发布文章，只能提「更新草稿」 |
| **可追溯** | 每次生成落 `ai_chat_log`；草稿的采纳/驳回/改写留痕，用于评估 AI 质量 |
| **运行环境（2026-10-31 口径）** | **生产默认关闭生成**，只保留人工编辑 + 装载；AI 生成在研发 / CI 期执行，产物随帮助包发布（见 §7.6） |

### 7.2 输入面（阶段八就要准备好的四类数据） <a id="ai-inputs"></a>

四类输入**按环境可用**：研发 / CI 全量；预发只给元数据与包内容；生产不读代码与设计文档（见 §7.6）。

1. **设计文档**：架构 / 概要 / 布局 / 规划节点（功能意图与边界）。
2. **元数据**：`sys_menu` / `sys_form` / `sys_field` / `sys_action` + 业务码 / 动作码清单（功能的结构化事实，含 `help_key` 覆盖情况）。
3. **代码结构摘要**：路由表、能力声明、字段校验规则——**只给结构化摘要，不给实现代码与注释**；摘要在构建期生成并缓存，运行期不读源码（避免把实现细节写进用户文档，也避免生产环境挂源码）。
4. **运行反馈**：帮助命中的搜索无结果、页面内帮助未命中率、文章反馈（有帮助/无帮助）、客服高频问题。

> 阶段八的交付义务：把 2 与 4 做成**可查询的稳定接口**（覆盖率台账 + 命中/反馈统计），否则阶段十九的 AI 只能读文档臆测，产出必然失真。

### 7.3 触发矩阵 <a id="ai-triggers"></a>

| 触发 | 场景 | 产物 |
| --- | --- | --- |
| 手动 | 维护人在某功能页点「生成/更新帮助草稿」 | 单篇草稿 |
| 事件驱动 | `sys.form.updated` / 菜单与字段变更 / 能力声明变更 | 受影响功能的更新草稿 + 变更摘要 |
| 缺口驱动 | 覆盖率台账里「有权限码但无 `help_key` / 无文章」的动作 | 待补清单 → 批量生成草稿 |
| 定时 | 质量巡检（陈旧度、断链锚点、无帮助热点路径） | 改进建议报告 |

### 7.4 生成与审核链路 <a id="ai-flow"></a>

```text
缺口/事件/手动 → 取输入面（设计 + 元数据 + 反馈）→ 生成草稿（含 provenance 与「依据了哪些输入」）
→ 人工审核（采纳 / 改写 / 驳回）→ 入库 draft → 发布 published
→（可选）汇入产品帮助包的新版本候选（见规范/帮助包规范.md）
```

- **质量门槛**：草稿需声明「依据的输入项」与「不确定处」，审核人据此判断；不确定处不得编造（缺信息就留 `TODO` 并标注）。
- **回写路径**：平台内建帮助直接入库；产品帮助走帮助包（AI 产出作为包的新版本候选，不直接改已发布包）。

### 7.5 质量度量与控制 <a id="ai-quality"></a>

- **覆盖率**：有权限码的动作 / 菜单中已声明 `help_key` 且有已发布文章的比例（分产品、分模块）。
- **陈旧度**：功能变更事件发生后 N 天内未更新对应文章的条目数。
- **有效性**：页面内帮助命中率、文章「有帮助」率、搜索无结果率。
- **成本控制**：按产品/模块配额限流；批量生成只对缺口清单执行，不做全量重写。
- **失败降级**：AI 不可用或超配额时，回到「人工维护 + 覆盖率台账」的既有路径，不阻塞发布。

### 7.6 环境与开关（生产默认关闭） <a id="ai-switch"></a>

AI 能读设计与代码，是它能把帮助写准的原因，也是它**唯一不该在生产发生的理由**：帮助内容随产品版本走，天然可以在研发期生成、随包发布；生产里改帮助是补漏，人工足够。

| 环境 | 生成能力 | 可用输入 | 说明 |
| --- | --- | --- | --- |
| 研发 / CI | 开 | 设计文档 + 元数据 + 代码摘要 + 运行反馈 | 主力场景：改完功能顺手生成草稿，汇入帮助包新版本 |
| 预发 | 关（只跑校验） | 元数据 + 包内容 | 校验锚点可解析、覆盖率对账，不生成正文 |
| 生产 | **默认关** | 仅元数据 + 已发布帮助（且须人工开启） | 只做人工编辑 + 装载；不读代码与设计文档 |

- **开关设计**：总开关 `help.ai.enabled`（按环境给默认值：dev/ci=`true`、staging=`false`、prod=`false`）+ 四类输入分开关 `help.ai.inputs.{design,metadata,code,feedback}`，可做到「开 AI 但禁读代码」。
- **代码输入边界**：只允许结构化摘要（路由表 / 能力声明 / 字段校验规则）；摘要由构建期任务产出并缓存，运行期不读源码、不挂载仓库；实现代码与注释一律不进入模型上下文。
- **生产开启的例外**：确需在生产生成时，须同时满足「内网模型 + 审批留痕 + 配额」三项，且输入收窄为元数据与已发布帮助，**禁读代码与设计文档**；未满足任一项即走人工路径。
- **产物隔离（兜底）**：AI 只能写 `draft`，而帮助包只接收 `published` / `offline`——即使有人在生产误开生成，未审核内容也进不了包、上不了前台。
- **审计**：每次生成记 `ai_chat_log`（模型、输入清单、token、耗时、审核结论）；生成能力被关闭时接口直接返回「未启用」，不做静默降级为人工提示。

- **[模块注册](11_架构设计_子系统_模块注册.md)**：`help_key` 与业务码 / 动作码 / 表单键 / 字段键同一登记面；平台内建与产品清单装载时一并登记锚点，不在业务代码里写死文章 ID

- **[审计哈希链](19_架构设计_子系统_审计哈希链.md)**：文章内容变更落字段级审计（内容合规可追溯）
- **[数据架构](07_架构设计_数据架构.md)**：表存租户库（租户维护各自帮助），i18n 附表遵循统一规范
- **[初始化数据](33_架构设计_部署与运维.md)**：初始帮助分类与基础文章种子（快速上手/系统管理/业务操作）
