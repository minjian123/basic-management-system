# 架构设计 · 子系统 · 模块注册

> BMS · 业务模块注册表 sys_module 与注册校验机制

## 1. 概述 <a id="overview"></a>

模块注册是 BMS 的平台级基础机制：平台库 `sys_module` 统一登记业务模块的模块简称、表前缀、
错误码段与事件域，启动与 CI 校验唯一，为产品业务模块（biz 的采购/收付款/供应商/销售/仓储、cw 等）提供注册制接入底座。
对应[《项目规划说明》](../../规划/项目规划说明.md)「平台扩展接入流程」「核心数据表清单」章节，
属**阶段一项目骨架**交付能力，早于 RBAC（后续）落地，后续阶段均基于注册机制建模块。

> **微服务形态（2026-09-22）**：本注册表由「业务模块注册」**升格为「服务目录与契约登记」**——模块即服务，服务清单、注册要素与契约版本同源登记，见第 6 节。目标架构见《[微服务演进规划](../../规划/微服务演进规划.md)》。

## 2. 注册表结构与数据 <a id="data"></a>

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| sys_module | module_key、service_key、name、table_prefix、business_code、errcode_segment、event_domain、service_group、build_batch、service_version、contract_version、product_key、status | 【平台库】服务目录与契约登记表：服务与模块同源登记——`module_key`（行登记标识，模块简称 / 服务标识）、`service_key`（服务维度标识）与注册要素（表前缀 / 业务码 / 错误码段 / 事件域）、归属分组（`service_group`）、建设批次（`build_batch`）、服务与契约版本、产品归属（`product_key`）；多语言模块名存 sys_module_i18n；租户侧可见、不可增删 |

- **平台域内置种子**：sys（系统）、wf（工作流）、rpt（报表）、ai（AI 域）同样注册，校验规则统一覆盖，防止业务模块前缀与平台域冲突
- **字段约束**：table_prefix 形如 {简称}_（如 pur_）；errcode_segment 为两位数字字符串——平台保留 `01`~`09`（如 sys=01、wf=02、rpt=03、ai=04），业务模块 `10` 起（列宽留余量，段位不足时放宽为 3 位、错误码顺延，既有段不变）；event_domain 默认与 module_key 一致，为多事件域模块预留扩展
- **表位置**：平台库（bms_platform），与 sys_business / sys_action 同模式——平台统一维护、种子下发、租户可见不可增删

## 3. 存储选型与升级同步 <a id="storage"></a>

### 3.1 为何用数据表而非配置文件 <a id="storage-why"></a>

模块注册表是**契约元数据**而非**运行时配置**：配置文件回答"本环境怎么跑"
（每环境可不同、环境变量可覆盖），sys_module 回答"系统里存在哪些模块"（跨环境必须完全一致、
与建表/代码绑定），故不放入配置文件。具体理由：

- **数据库级唯一约束**：table_prefix / errcode_segment / event_domain 唯一索引从物理上杜绝冲突，配置文件只能靠代码校验
- **与建表原子演进**：新增模块 = Alembic schema 迁移（建表）+ 数据迁移（注册），同一流水线版本化、可回滚；配置文件是第三处状态，易与库结构脱节
- **与权限码体系同构**：sys_business / sys_action / sys_menu 均为平台库表（平台统一维护、租户可见不可增删），模块注册融入同一机制，不产生例外
- **CI 校验自然**：流水线在测试库"迁移后查重"直接用 SQL；配置文件校验需单独写解析器
- **可查询可审计**：平台超管运营视图从库读取；将来若要审计"谁改过注册"表天然支持

### 3.2 升级同步机制 <a id="storage-upgrade"></a>

- **Alembic 数据迁移**：新增模块 = 一个迁移 revision（建表 schema 迁移 + 注册种子数据迁移），随版本号演进、可回滚；注册数据与表结构在同一个迁移流水线中原子落地
- **平台库单库执行**：sys_module 位于平台库（bms_platform），全系统唯一，迁移执行一次即可；区别于租户库的批量迁移（遍历 sys_tenant）
- **既有同模式先例**：sys_business / sys_action（平台码）、sys_dashboard_card（平台升级由批量迁移同步新增内置卡）均为"平台库种子随迁移升级"，本节点沿用同一模式
- **发布闭环**：新增模块 → 写迁移脚本 → MR → CI 在测试库执行迁移并查重校验 → 生产发布执行迁移 → 新版本启动校验兜底（注册与实现一致）

### 3.3 运行时只读边界 <a id="storage-readonly"></a>

- 平台注册表运行时不提供增删改：无注册表写接口，平台超管运营视图为只读查询（GET /api/v1/modules）
- sys_module.status（启用/规划中）为**种子状态标记**（未交付模块的登记态），不是运行时启停开关
- 升级同步归版本化迁移管理，运行时改动反而需新增"在线改 + 校验 + 审计"机制——明确不做
- 租户级模块开关（运行期可配）与平台注册表分离，见 3.4

### 3.4 租户模块开关 <a id="storage-tenant"></a>

不同租户需要不同的模块子集（如某租户仅采购，另一租户采购 + 销售 + 仓储；模块归属 biz 等产品仓库）。模块的**平台注册**（sys_module，开发期契约）与**租户开通**（sys_tenant_module，运行期可配）分离：

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| sys_tenant_module | tenant_id、module_key、status（enabled/disabled）、opened_by、opened_at、closed_at | 【平台库】租户-模块关系表：租户开通的模块清单与启停状态；module_key 逻辑引用 sys_module（只允许已注册且启用的模块） |

- **开通**：租户开通流程中人工勾选模块清单（未勾选默认不开通）；开通后平台超管在租户管理内随时启停（写接口 + 审计）
- **生效机制**：停用模块的菜单/按钮经动态菜单下发过滤（与权限计算引擎联动）；接口鉴权叠加模块状态校验（require_permission 前检查租户模块状态）；不可新建单据
- **数据保留**：停用不影响存量数据查询；重新开通即恢复；进行中流程与审批不受影响
- **操作方**：仅平台超管（租户管理模块内），租户侧不可自启停
- **校验关系**：sys_tenant_module.module_key 必须存在于 sys_module（启用状态），防止注册平台不存在的模块

### 3.5 模块契约与产品下线 <a id="storage-contract"></a>

注册要素（module_key / table_prefix / errcode_segment / event_domain）一旦注册即成为**对外契约**——产品代码依赖这些值，变更会破坏已接入的产品：

- **契约属性**：注册值稳定不变；错误码段注册即定、不回收改派，表前缀与事件域同理（同《项目规划说明》「错误码段规则与注册」节）。
- **变更约束**：确需变更按破坏性变更流程处理——提前至少一个次版本公告 + 过渡期（新旧并存）+ 迁移步骤，口径见《[平台可扩展性规划](../../规划/平台可扩展性规划.md)》5.5。
- **产品级注册**：产品（biz / cw 等）以产品为单位登记归属（`sys_product` 或 `sys_module` 上的产品标识字段，随 R4.1 落地），用于区分模块归属、支撑按产品维度的版本兼容核对与下线处置。
- **两级停用/下线**（租户级与产品级分离）：

| 动作 | 范围 | 处置 |
| --- | --- | --- |
| 租户级停用 | 单租户 | `sys_tenant_module.status = disabled`：菜单与接口禁用、数据保留、可重新开通（见 3.4） |
| 产品级下线 | 全局 | 数据导出归档 → `sys_module.status` 置**注销态**（不物理删除，保留注册记录便于回溯）→ 移除前端合并产物与后端扩展包；**错误码段不回收**、事件域不再使用 |

- **契约承诺（对外）**：
  - 契约范围：注册要素（module_key / table_prefix / errcode_segment / event_domain）与模块对外接口、前端模块入口属对外契约；**平台内部重构**（内部类、目录、非对外接口调整）不视为破坏性变更。
  - 破坏性变更：提前至少一个次版本公告、提供过渡期（新旧并存）与迁移步骤；能力下线按产品级下线流程（见上表）并同步公告。
  - 通知渠道：随版本发布说明与产品接入联系人同步（阶段四起随平台版本公告）。
- **独立服务边界**：独立服务（不注册 `sys_module`）以 OIDC + `/api/open` 接入；菜单以**外链菜单**挂 `sys_menu`（新窗口跳转，不参与框架内路由与页签）；事件经 Webhook / 事件订阅**回传**，平台不直连其数据库、不共享事务，边界见[《平台可扩展性规划》](../../规划/平台可扩展性规划.md)与 [09-接口与集成](09_架构设计_接口与集成.md)。
- **接入验收与运行期隔离**：产品接入以五项验收为准——注册唯一性（前缀 / 错误码段 / 事件域）、契约测试通过、权限与审计复用、前端模块可加载、数据隔离（租户 / 数据范围）；运行期按租户配额与模块开关隔离，异常可按产品维度停用（见 3.4）。
- **不做的事**：下线不删表、不回收表前缀与错误码段；历史数据按归档策略纳管（见[数据架构](07_架构设计_数据架构.md)与归档管理）。版本兼容、升级顺序与下线流程的治理口径见《[平台可扩展性规划](../../规划/平台可扩展性规划.md)》5.6。

## 4. 注册时机与唯一性校验 <a id="check"></a>

- **种子注册**：新增业务模块以平台种子数据方式注册（Alembic 数据迁移或种子脚本），随版本发布
- **启动校验**：应用启动时读取 sys_module，校验服务标识与注册要素（表前缀 / 错误码段 / 事件域）唯一且格式正确（{简称}_、两位段号、小写域），校验库中登记与清单一致；服务自报契约版本与登记值**主版本兼容**；冲突即启动失败并给出冲突项。空目录（未播种）仅告警放行，库不可读 / 表缺失按启动失败处置
- **CI 校验**：流水线对种子与迁移脚本执行同规则校验（测试库迁移 + 种子后查重与清单对账），并核对各服务包自报契约版本与清单登记值主版本；冲突不允许合并
- **只读边界护栏**：仓储只读面、服务目录路由仅 GET、启动校验只读（不改登记）由自动化用例固化，防回归
- **维护方式**：注册表不提供页面增删（新增模块走开发期种子）；平台超管运营视图提供只读查询与状态查看

## 5. 与新增模块流程的关系 <a id="flow"></a>

1. 模块注册是内置模块标准接入流程（规划 23.2）第 1 步：确定模块简称、表前缀、业务码、错误码段、事件域，先注册于 sys_module（种子），再建表、建代码
2. 注册后与既有机制自动对齐：业务码注册 sys_business、动作码注册 sys_action（平台种子），菜单/表单/按钮/字段种子挂接动态路由，前端免发版
3. 错误码段与事件域以 sys_module 登记值为权威：错误码段分配表（10xxxx 起，段号两位）与事件命名 {域}.{动作} 均以注册值为依据
4. 独立服务轨不注册 sys_module（不进租户库与平台库），仅经认证 / 开放接口 / Webhook 集成

## 6. 服务目录与契约登记（微服务） <a id="catalog"></a>

微服务目标下，本注册表由「业务模块注册」升格为**服务目录与契约登记**：模块即服务，服务与模块同源登记。服务目录是「服务可发现 + 契约可校验 + 版本可追踪」的单一权威。

| 登记项 | 说明 |
| --- | --- |
| 服务 / 模块标识 | service_key / module_key；服务清单按分批建设（平台地基 / 能力 / 产品服务），见《[微服务演进规划](../../规划/微服务演进规划.md)》「目标架构与服务清单」节 |
| 注册要素 | 表前缀 / 业务码 / 错误码段 / 事件域，唯一性校验同第 4 节 |
| 契约版本 | 每服务公开契约（OpenAPI）版本与服务版本，服务包自报、启动与 CI 双端校验主版本兼容；破坏性变更按 oasdiff 门禁与兼容承诺（见 [09-接口与集成](09_架构设计_接口与集成.md)、[37-服务间通信与分布式一致性](37_架构设计_子系统_服务间通信与一致性.md)） |
| 归属 | 平台地基服务 / 平台能力服务 / 产品服务；产品以产品为单位登记归属 |

- 服务只经公开契约互相访问，禁止跨服务访问内部实现与非自身数据库（服务化地基 S1）
- 独立服务（产品默认接入形态）以 OIDC + `/api/open` 接入，登记 scope 与事件订阅（见 3.5）
- 服务目录与「模块」共用同一注册机制（注册 → 契约校验 → 装配 → 生命周期），保持两轴同构（见第 7 节）

## 7. 与其他子系统的协调 <a id="coordination"></a>

- [数据架构](07_架构设计_数据架构.md)：sys_module、sys_tenant_module 均属平台库表，表名前缀规则（平台域固定 + 业务模块注册制）与本节点一致
- [多租户路由](12_架构设计_子系统_多租户路由.md)：租户模块开关随租户上下文生效，停用模块的请求在路由/鉴权层拒绝
- [权限计算引擎](15_架构设计_子系统_权限计算引擎.md)：模块注册先行、业务/动作码注册随后，两者均为平台库种子，机制并行
- [接口与集成](09_架构设计_接口与集成.md)：错误码分段（10xxxx 起）与事件模型（{域}.{动作}）以注册值为权威
- [总体架构](03_架构设计_总体架构.md)：后端模块目录与前端模块目录与模块键对齐（目录约定见《[后端开发规范](../../规范/后端开发规范.md)》《[前端开发规范](../../规范/前端开发规范.md)》）
- [前端架构](08_架构设计_前端架构.md)：动态路由按菜单种子生成，模块新增无需前端发版
- [平台可扩展性规划](../../规划/平台可扩展性规划.md)：注册是产品接入第 1 步（其 4.6 / 5.2），注册要素的契约与兼容性承诺见其 5.5，接入后的版本兼容、升级与产品下线见其 5.6，独立服务轨不注册 sys_module 见其 5.7
- [扩展点与插件化](10_架构设计_子系统_扩展点与插件化.md)：模块注册是「横向」产品接入（注册要素为模块标识），与「纵向」平台能力实现替换共用同一套「注册 → 契约校验 → 装配 → 生命周期」机制——两轴同构、注册要素不同（模块标识 vs 能力实现名）
- [API 网关与边缘](36_架构设计_子系统_API网关与边缘.md)：服务目录为网关路由与服务发现提供依据
- [服务间通信与分布式一致性](37_架构设计_子系统_服务间通信与一致性.md)：契约版本登记与兼容门禁的依据
