## 1. 概述 <a id="overview"></a>

产品（mdm、biz、cw 等）各自独立仓库、独立发版；平台内建模块与产品之间、产品与产品之间必然存在**能力依赖**——平台的角色管理要消费产品的组织角色，产品的只读出口要消费平台的用户明细，产品之间的主数据要被多个产品共同消费。

本子系统定义这类协作的**语义层**：把「跨产品协作」从「各消费方各自写死对端标识与访问面」收敛为「**能力目录 + 按能力名寻址 + 装载即校验**」，使产品侧改名、改路径、改分支动作时，消费方无需跟着改代码，且断链在**启动期**即暴露、不在运行期静默降级。

**本节点回答**：能力是什么、谁声明、谁消费、契约要素归谁、版本如何演进、缺失与不可达如何处置、依赖方向与红线。
**本节点不回答**（分归相邻节点）：服务如何调用与重试（37）、注册要素与目录登记项（11）、对外路由如何拼装（36）、前端模块产物如何加载（35）、具体清单格式与代码落点（登记清单与详细设计）。

## 2. 问题与边界 <a id="problem"></a>

**要解决的问题（已发生的事实）**：产品服务标识归并（`org` → `mdm`）时，平台侧五类消费点各自持有对端标识与访问面，全部静默断链；读取侧因存在降级路径，运行期表现为「能力少一半」而非报错，直到阶段收口才被发现。根因不是实现疏漏，而是**架构上缺少“能力”这一层**——只有“服务级登记”，没有“能力级契约”，消费方除了写死对端别无他法。

**范围内**（架构语义）：

1. 三类协同方向的定义与约束（§3）；
2. 能力目录的语义（能力命名、归属唯一、消费方登记）（§4）；
3. 协同契约要素的**类别**与归属（§5）；
4. 契约版本与兼容原则（§6）；
5. 消费方寻址与缺失 / 不可达的失败语义（§7）；
6. 依赖方向与红线（§8）。

**范围外**：具体清单结构与字段、代码落点与文件清单、脚本与命令、字段级结构——按《文档生成规范》「架构节点的语义与实现分层」节落《跨产品协同登记清单》与详细设计。

## 3. 三类协同方向 <a id="directions"></a>

| 方向 | 典型形态 | 约束 |
| --- | --- | --- |
| **平台内建 → 产品能力** | 平台的角色 / 用户保存要写入产品的组织分配；平台权限计算要读取产品的组织角色链 | 平台内建模块**只依赖能力名**，不持有产品标识与访问面；产品缺失时平台相关能力按 §7 失败语义处置 |
| **产品 → 平台能力** | 产品出口取平台用户明细；产品写操作落平台审计与事件 | 走平台既有公开面与服务身份（[14](14_架构设计_子系统_认证与会话.md)、[37](37_架构设计_子系统_服务间通信与一致性.md)）；平台**不感知具体产品**，只按调用方身份与配额约束 |
| **产品 ↔ 产品** | 主数据产品被多个业务产品消费；业务产品回写主数据 | **默认经平台中转**；**获得分配记录的直连同样合法**（见 §4.1），并纳入审计与监控；无有效分配即越界 |

产品间协作的判定口径：**是否存在一条有效的分配记录，覆盖该能力与该消费方**。有则合法（直连或经平台中转均可），无则越界，由运行期校验与机器护栏（§8）双轨拦截。

## 4. 能力目录 <a id="catalog"></a>

**能力**是跨产品协作的**最小可消费单元**，是提供方对外承诺的契约，而非实现细节的投影。

| 语义 | 规定 |
| --- | --- |
| 能力名 | 全局唯一、语义化、**与提供方实现标识解耦**（提供方改名不改能力名）；能力**绑定提供方「业务域」**（稳定边界），**不绑定部署单元、服务标识或库名**——业务域由哪些部署单元承载随租户拓扑变化（见 39 节点）；命名口径遵循《[命名规范](../../规范/命名规范.md)》 |
| 提供方 | 每项能力**有且仅有一个**提供方；同一语义不得两处声明（避免双事实源） |
| 消费方 | 显式登记；未登记的使用视为越界（与“私下直连”同判） |
| 归属 | 目录**由提供方自持声明、部署期由平台装载校验**；平台不写产品能力、不维护第二份手写副本 |
| 粒度 | 一项能力对应一组**同类访问面**（读出口 / 写通道 / 事务分支 / 参考数据出口 / 权限码集合 / 前端命名空间），不按单个端点拆碎 |
| 可发现性 | 装载后形成**运行期只读能力视图**，供消费方与前端查询；视图是投影，不是第二份源 |

**能力与注册要素的关系**：注册要素（服务行、表前缀、错误码段、事件业务域、产品路由）回答「**产品是谁**」；能力目录回答「**产品对外能做什么**」。二者同源（同一份产品自持声明），但读者不同：前者是平台基础设施，后者是跨产品消费方。

### 4.1 能力分配与授权 <a id="assignment"></a>

**分配**是平台对「能力 × 消费方」的**授权记录**，粒度**能力级**（一个能力一组访问面；数据范围仍由既有数据权限体系约束，不在分配里重复定义）。

- **两层分工**：产品自持声明写「默认允许谁消费本能力」（文件级、随产品发布）；平台装载后落**分配记录**（运营期数据）；运营期可在平台侧调整、撤销，**变更留审计**。
- **派生三件事**：① **入站校验**（谁能调我）＝本能力的有效分配；② **出站授权**（我能调谁）＝消费方维度的有效分配，落实为服务令牌 scope；③ **可观测归因**＝按「调用方 × 能力」聚合调用量、失败率与越权尝试。
- **合法性判定**：存在**有效分配记录**即合法；无有效分配即越界——运行期拒绝并报明确错误，装载期无法解析的分配直接拒启。
- **直连与中转**：默认经平台能力中转；**获得分配的直连同样合法**，且与中转调用一样进入审计与指标——不存在「绕过平台就监控不到」的盲区。
- **撤销即时生效**：撤销分配在同一缓存失效周期内生效，不依赖调用方自觉下线。
- **审计**：分配、调整、撤销三类动作进审计链；能力调用本身沿用既有操作审计与调用日志口径。
- **监控口径**：指标维度固定为「调用方 × 能力」（可叠加结果与耗时），面板随可观测性阶段落地，本节点只定维度语义。


## 5. 协同契约要素（类别与归属） <a id="contract"></a>

一项能力至少声明以下**类别**的要素，具体字段与格式归《跨产品协同登记清单》：

| 要素类别 | 语义 | 权威归属 |
| --- | --- | --- |
| 身份 | 能力名、提供方**业务域**（不是服务标识） | 提供方 |
| 访问面 | 该能力的访问入口类别（契约读出口 / 内部写通道 / 事务参与分支 / 参考数据出口）与对端契约中的位置 | 提供方（须能在对端公开契约中被校验到） |
| 业务语义要素 | 该能力涉及的业务码 / 权限码 / 分支动作名 / 数据源标识 | 提供方（平台不代写） |
| 前端面 | 该能力对应的前端命名空间（供前端按能力取址） | 提供方（domain 段由提供方自持） |
| 版本 | 随提供方服务契约版本（见 §6） | 提供方 |
| 种子 | 该能力实施所需的默认数据种子（如有），声明为可被平台统一调度的入口 | 提供方声明、平台调度执行（见 §8 红线） |

**归属原则**：凡随产品演进变化的内容（路径、动作名、权限码、数据源、种子）**一律归提供方**；平台只保留「按能力名解析」的语义与校验责任。这条原则是「新增产品零改基座」的前提。

## 6. 契约版本与兼容 <a id="version"></a>

- **版本随提供方服务契约**：能力契约不引入独立版本体系，与提供方公开契约同版本、同门禁（破坏性变更拦截沿用 [37](37_架构设计_子系统_服务间通信与一致性.md)「契约版本与兼容」节）。
- **只加不删**：能力可新增要素、新增可选分支；删除 / 改名 / 收窄语义属破坏性变更，须升大版本并保留过渡期。
- **能力下线**：下线须先在目录标记弃用、给出替代能力、经一个发布周期后移除；消费方在弃用期内必须完成迁移（口径同 [11](11_架构设计_子系统_模块注册.md)「模块契约与产品下线」节）。
- **装载即校验**：装载期校验「能力声明存在 + 提供方已登记 + 访问面能在对端契约中定位 + 版本兼容」，不满足即拒启（§7），不做“先跑起来再说”。

## 7. 消费方寻址与失败语义 <a id="resolve"></a>

**寻址语义（两段解析）**：消费方以**能力名**取用 → ① **能力 → 业务域**（稳定，本节点定义）；② **业务域 → 部署单元与库**（可变，按租户拓扑解析，见 [39-产品与服务划分](39_架构设计_子系统_产品与服务划分.md)）。消费方**不得**在代码、配置、种子中直接持有对端的产品标识、服务标识、路径、动作名或权限码——**服务标识本身是拓扑解析结果，不属于契约内容**。

**失败语义（三档，按不可逆性区分）**：

| 时点 | 情形 | 处置 |
| --- | --- | --- |
| 装载 / 启动期 | 能力未声明、提供方未登记、访问面不在对端契约、版本不兼容 | **拒绝启动**（fail-fast）——断链不留到运行期 |
| 运行期（写 / 强一致路径） | 提供方不可达或返回失败 | **fail-closed**：整体失败并报明确错误码，不得“只写一半”或静默跳过 |
| 运行期（读 / 弱一致路径） | 提供方不可达 | 允许**有界降级**（返回空集或旧副本），但必须：①有明确降级标志与日志；②纳入可观测指标；③不得作为缺省行为掩盖契约问题 |

**禁止**：把“降级”做成无差别的默认路径（历史教训：读取侧降级为恒空集，断链不可见）。降级必须是**逐能力显式声明**的策略，而非全局缺省。

## 8. 依赖方向与红线 <a id="rules"></a>

- **依赖方向**：消费方 → 能力目录 → 提供方。禁止反向依赖（提供方不得依赖消费方的实现）；禁止服务间直接 `import` 彼此内部实现（服务边界纪律，见 [37](37_架构设计_子系统_服务间通信与一致性.md)）。
- **红线一（产品标识不入基座）**：平台源码、平台种子与基座常量的**逻辑面**不得出现具体产品标识；产品标识只允许出现在**产品自持声明**与**消费方按能力名的取用**中。由机器护栏（engkit 通用规则）拦截。
- **红线二（单一权威）**：能力目录的权威**只在提供方仓库**；平台侧只做装载、校验与只读投影，不得手写第二份源。
- **红线三（种子归属）**：产品能力所需的默认数据（业务码、权限码、动作码等）由**产品声明**，由**平台统一调度执行播种**，并统一幂等与冲突报错；平台种子不代写产品数据。
- **红线四（前端不写字面量）**：前端产品键与产品命名空间经目录视图获取，不在前端常量中手抄。
- **红线五（越界即拦）**：未登记的产品间直连、未登记的能力消费，一律按越界处理，由护栏与评审双轨拦截。
- **红线六（分配唯一）**：跨产品调用的合法性**只以分配记录为准**；代码常量、配置文件里的调用方清单、口头约定都不构成授权，也不得作为白名单来源。

## 9. 与既有注册机制的统一口径 <a id="registry"></a>

协同层**不另建机制**，而是并入既有的产品登记与装载体系（[11-模块注册](11_架构设计_子系统_模块注册.md)）：

| 维度 | 统一口径 |
| --- | --- |
| 登记模型 | 能力是产品自持声明的**第五类登记记录**，与产品档案、服务行、产品路由、数据源**同源、同装载入口、同合并视图族、同唯一性纪律**（同键同值合并、同键异值即拒，产品不得覆盖平台）。不新增第二套注册表。 |
| 装载通道 | 两条通道分工固定：**文件级**（部署期装载、跨进程可读）承载注册要素与能力声明；**代码级**（进程内自报身份）承载表归属、表单标识与服务行自报。判据是「**是否需被其他进程消费**」——需要即走文件级。能力声明**恒走文件级**（消费方不得依赖提供方实现）。 |
| 目录下发 | 能力与产品键经**既有服务目录快照**一并下发（扩既有出口，不新开端点）：服务启动接库对账、跨服务查询、前端取址共用同一份，避免多份目录各自演进。 |
| 种子执行 | 既有平台种子族视为「平台自身种子」，产品种子按声明追加，统一由平台种子编排入口按序执行；幂等、冲突报错与失败隔离只有一套实现。 |
| 校验 | 「能力声明 ↔ 对端契约定位」的校验并入**既有清单对账**（清单 ↔ 代码清单零漂移同一条命令），CI 与本地同源，不新增并行校验入口。 |

> 判据一句话：**协同层只增加“记录种类”，不增加“机制种类”**。凡出现第二套注册表、第二个目录出口、第二个播种入口或第二个校验入口，均视为偏离本节点。
>
> 与 39 节点的分工：**业务域是架构边界**（代码、表归属、能力提供方都按业务域表达）；**部署单元与库是运营拓扑**（同一业务域在不同租户可由不同部署单元承载）。协同层只认业务域，不认服务标识。

## 11. 演进与开放项 <a id="evolution"></a>

- **能力分档治理**：能力数量增长后按“基座级能力 / 产品级能力”分层，基座级能力（如组织角色链）比产品级能力有更强的稳定性承诺。
- **能力冲突**：同一语义出现两个提供方时，目录**拒绝装载**（不静默择一），由治理决策收敛。
- **跨产品编排**：多个能力需按序组合（如“保存用户 + 写入组织分配”）时，编排归平台侧的业务编排器，能力仍是原子单元；跨服务原子性沿用 [37](37_架构设计_子系统_服务间通信与一致性.md) 的 TM + XA。
- **分配策略演进**：默认分配随产品声明维护；运营期临时分配（排障 / 迁移窗口）应设有效期、到期自动失效，避免临时授权长期留存。
