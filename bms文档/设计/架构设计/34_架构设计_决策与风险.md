## 2. 架构决策记录（ADR） <a id="adr"></a>

| 决策点 | 选择 | 理由 |
| --- | --- | --- |
| 多租户落地方式 | 一租户一独立库 | 数据隔离最强、备份恢复与迁移独立；配合引擎懒加载控制连接成本 |
| 微服务 vs 单体 | 单体模块化 + 独立 worker 进程 | 业务量级无需微服务，跨域调用走事件总线解耦 |
| 任务队列 | Celery（Redis broker）+ 自研数据库调度器 | 生态成熟；任务定义入库、页面动态管理、beat 单副本 + 锁防重；与 RocketMQ 事件总线解耦 |
| 事件总线 | RocketMQ 5.x | 分区有序保证审计链顺序、事务消息兜底生产一致性；保留生态与扩展空间 |
| 全文检索 | ElasticSearch 8.x | 覆盖主数据/审计日志/文件内容三类检索；事件驱动异步同步、可重放重建 |
| 向量检索 | Milvus（阶段十九） | 亿级向量能力，独立部署（etcd + MinIO 复用） |
| 认证 | JWT 双 token + Redis 会话标记 | 无状态可扩展 + 强制踢出即时生效；refresh 轮换防重放 |
| 密码哈希 | PBKDF2（标准库） | 零依赖，高迭代次数下满足安全基线 |
| 接口限流 | slowapi（limits 库，Redis 后端） | 装饰器声明、集群共享计数、Redis 故障降级 memory 后端 |
| 实时推送 | Socket.IO + Redis 适配器 | 自动重连、跨实例广播；替代原生 WebSocket |
| 分片方案 | 应用层自研 ShardingRouter | Python 生态无成熟中间件；MVP 仅审计类日志按月分片 |
| 审计防篡改 | 哈希链 + RocketMQ 分区有序写入 | 链序由有序消费保证，逐条可校验；成本可控 |
| 事件生产一致性 | 事务性发件箱（Outbox）+ 消费幂等 | 业务与事件同库同事务、可无 MQ 独立工作、可重放；阶段二占位、事件总线阶段对接 RocketMQ；消费侧 `event_id` 唯一约束去重（见 [16-事件总线](16_架构设计_子系统_事件总线.md)） |
| 工作流引擎 | SpiffWorkflow（BPMN 2.0） | Python 生态最成熟 BPMN 引擎；线程池运行于异步栈；Python 3.14 兼容风险有回退预案 |
| 前端包管理 | npm（双工程彻底独立） | 官方自带、零额外配置、不生成额外配置文件；不引入 workspace 机制 |
| 数据库支持 | SQLite / MySQL / PostgreSQL / 达梦 DM8 四库兼容 | 开发零部署，生产三库并行（达梦信创选配），ORM 层禁用方言特有功能 |
| 链路追踪 | OpenTelemetry + Jaeger | otel-collector 统一采集，Grafana Jaeger 数据源统一可视化 |
| i18n 方案 | 文案入库 + i18n 附表 + Babel 提取 | 新增语言免发版；业务文案与固定文案分层管理 |
| 软删除与唯一约束 | (唯一字段, deleted_at) 复合唯一索引 | 四库多 NULL 不冲突（达梦按 Oracle 兼容口径，阶段一验证），删除即释放唯一键，回收站复用 |
| 平台能力可替换（插件化） | 能力基类（端口）+ `BasePluggable` 中间层 + 注册表 + 配置选择 | 对冲开源供应链风险（上游停维护 / 换维护者 / 许可变更）与客户指定商业组件；三阶段演进（配置切换 → 运行时热插拔 → entry points 第三方），进程内、不引入微服务，不做插件市场与运行时远程加载（见 [10-扩展点与插件化](10_架构设计_子系统_扩展点与插件化.md)） |
| 前端运行时组合（微前端） | Module Federation + 宿主薄壳 + 模块契约/清单（最小闭环） | 新业务页面按模块形态独立构建发布，支撑多团队独立发版与渐进迁移；`iframe` / `qiankun` 沙箱式不采用；阶段四搭骨架、阶段五完成运行时加载与首个模块样例，治理随阶段补齐（见 [08-前端架构](08_架构设计_前端架构.md) 与知识档案《[微前端](../../资料/知识档案/微前端/01_微前端_总览.md)》） |

### 2.1 微服务拆分评估 <a id="adr-micro"></a>

「微服务 vs 单体」决策的完整评估（规划「明确不采用」的展开）：

| 维度 | 收益（若拆分） | 代价（对本项目） |
| --- | --- | --- |
| 部署与伸缩 | 独立部署、按模块扩缩容 | worker 进程已提供独立伸缩；拆服务需每服务维护租户路由、连接预算、部署编排 |
| 故障隔离 | 单服务故障不扩散 | 依赖链（审批→通知→审计）跨服务后故障面反而扩大；熔断/重试复杂度上升 |
| 数据一致性 | 服务自治存储 | 分布式事务：审计哈希链串行追加、软删除 (唯一字段, deleted_at) 复合唯一约束、乐观锁、事务消息均为强一致场景，拆分后需 Saga/两阶段提交 |
| 性能 | 按热点独立优化 | 跨服务网络调用威胁 P99 ≤ 1s 目标（审批链路穿 3-4 个服务）；单体内同进程调用零开销 |
| 权限与租户 | 服务级安全边界 | require_permission 贯穿全部模块、数据范围过滤注入查询、一租户一库路由均为横切基座，拆分后难以统一 |
| 运维与监控 | 故障定位到服务 | 基础设施已 8+ 组件（RocketMQ/ES/Milvus/Redis/MinIO/三库/监控），再拆分服务令 Compose/监控/链路追踪规模爆炸 |
| 团队协作 | 服务边界=团队边界 | 小团队（单团队）维护单体更高效 |
| 测试 | 服务内独立验证 | 集成/E2E/安全专项需跨服务编排，成本显著上升 |

**结论**：单体模块化 + 独立 worker 进程已通过事件总线（RocketMQ）获得模块解耦与独立伸缩的大部分收益，同时避开分布式事务与网络开销；维持不拆分，演进条件见第 4 章。

**可替换作为风险对冲**：上述组件均为开源，上游无持续维护承诺，且非商业版功能深度有限。因此平台把「可替换」（插件化）作为选型配套策略：关键能力以能力基类（端口）+ 注册表 + 配置选择 + 提供者组织，**上游停维护、许可变更或客户指定商业组件时，切换实现而不改业务代码**（机制见 [10-扩展点与插件化](10_架构设计_子系统_扩展点与插件化.md)）。

## 3. 架构风险与应对 <a id="risks"></a>

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| Python 3.14 生态兼容 | 核心依赖（FastAPI/SQLAlchemy/psycopg/Celery/SpiffWorkflow/dmPython）未适配 | 阶段一逐依赖验证，任一不兼容整体回退 3.13（已定口径） |
| RocketMQ 运维复杂度 | nameserver + broker 部署与调优成本 | Compose 标准化部署；MVP 单机起步，生产集群化；故障降级同步直写 |
| 三库方言维护 | MySQL/PostgreSQL/达梦 DM8 三套迁移与方言差异 | ORM 层禁用方言特性；CI 三库集成测试（达梦复用 mjbk 常驻库）；SQLite 自动建表 |
| 多租户引擎连接膨胀 | 租户库增多后连接数失控 | 懒加载 + 闲置回收 + 池上限 + 活跃租户数上限；连接预算公式约束 |
| ES 资源占用 | 单节点内存需求高 | MVP 单节点按需分配；索引按月拆分可裁剪；故障降级兜底 |
| 审计链性能瓶颈 | 串行消费限制写入吞吐 | 单租户日志量级有限；跨租户分区并行；必要时按表拆分消费组（链内保持有序） |
| AI 依赖（阶段十九） | 外部 API 不可用/成本/合规 | 适配层可切私有化端点；独立限流与预算；全量审计；默认仅辅助 |
| SpiffWorkflow 兼容性 | Python 3.14 / 异步栈集成风险 | 线程池运行隔离；版本回退预案；测试覆盖完整流转 |

> 本节为**架构实现层面**风险；完整风险登记册（含 MVP 范围、法律合规、bus factor 等，带概率/影响评级与复审机制）见《[项目规划说明](../../规划/项目规划说明.md)》「风险管理」节（含单机性能达标、外部 LLM 成本、AI 两开关误用、开发基础设施单点、数据迁移、合规不确定等条目），两处互补、阶段末复盘一并走查。

## 4. 演进路线 <a id="roadmap"></a>

- Kubernetes 化部署（当前 Docker Compose，数据量或规模增长后迁移）
- 产品业务演进（biz pay）：基于平台预留的渠道抽象层接入银企直连/第三方支付（微信/支付宝等），配套对账与流水核销
- 产品扩展：biz 其他模块（sale_/wh_）等按《[项目规划说明](../../规划/项目规划说明.md)》「平台扩展接入流程」节登记接入；大型独立业务系统按「独立服务集成」接入
- 阶段十八 全文检索：ES 接入、文件内容解析、全局搜索页面
- 阶段十九 AI 能力：LLM 适配层、Milvus 向量库、OCR、智能报表助手、智能审批辅助、知识库问答
- 前端运行时组合（微前端）：阶段四搭骨架（宿主薄壳 + 模块契约）、阶段五完成 Module Federation 运行时加载与模块清单，首个业务页面作为首个模块样例；治理（隔离 / 版本发现 / 灰度）随阶段补齐
- 持续评估点：消息量级增长时评估 Kafka；数据规模增长时评估分片范围扩展与专用向量库升级；部署规模增长时评估 K8s

## 5. 架构变更流程 <a id="process"></a>

1. 提出变更：说明动机与影响范围（哪些子系统/节点受影响）
2. 逐项确认：技术选型、方案取舍按《AGENTS.md》要求逐项列出候选与推荐，用户确认
3. 更新文档：先更新《项目规划说明》，再更新本架构设计对应节点（新增 ADR），最后传导到下游（[概要设计](../概要设计/01_概要设计_总览.md)/详细设计）
4. 回归验证：涉及结构/机制变更需同步测试策略与验收标准
