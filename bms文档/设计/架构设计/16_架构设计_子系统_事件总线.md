## 1. 概述 <a id="overview"></a>

事件总线基于 RocketMQ 5.x：作事件总线承载操作日志异步化、Webhook 推送、审计链分区有序消费、
模块解耦与跨域数据同步。对应[《项目规划说明》](../../规划/项目规划说明.md)的「消息队列」「事件总线事件模型」「Webhook 管理」章节。

> **微服务形态（2026-09-22）**：事件是**服务间解耦与跨服务一致性的主通道**；「业务写 + 事件发布」以**事务性 Outbox** 保证原子（服务化地基 S3）。与 [37-服务间通信与分布式一致性](37_架构设计_子系统_服务间通信与一致性.md) 分工——本节点管事件模型 / 消费 / 推送，37 管 Outbox 基座 / 跨服务强一致事务（Saga / 补偿已作废）。

## 2. 事件模型 <a id="model"></a>

- 事件信封 EventEnvelope：event_id（幂等键）、type（`{域}.{对象}.{动作}`）、tenant_id（租户主键，雪花 id 十进制字符串）、occurred_at、payload
- 事件租户位：信封 `tenant_id` 与平台事件负载 `tenant_id` 同名同值（租户主键统一表达）；`db_key` 负载保留（库名基派生）
- topic 命名：`bms-{事件域}-{对象}`（如 `bms-log-operation`、`bms-wf-task`；产品事件域按 sys_module 登记）——**段分隔符用连字符**：消息中间件的 topic / 消费组名只接受 `[%a-zA-Z0-9_-]`，点号在发送前即被客户端拒绝——**派生规则**：取事件名前两段（域 + 对象），同对象的多个动作落同一 topic（`wf.task` 承载 created / completed / rejected），topic 数量不随动作数膨胀；订阅仍按事件名精确匹配，topic 只承担通道与分区职责
- 事件命名：`sys.user.updated`、`wf.task.completed`、`pur.apply.submitted`、`pay.approved` 等（完整清单见 [09-接口与集成节点](09_架构设计_接口与集成.md)）
- 默认清单开发期可扩展；Webhook 订阅按事件名匹配

## 3. 同步 / 异步判定 <a id="sync-async"></a>

> 本节判定**跨模块协作的形态**，不是「能不能用 MQ」。默认同步，只有明确落在异步清单内的协作才走事件；**判错方向（把读或强一致写成异步）比不做异步更危险**。

| 协作形态 | 判定 | 做法 | 典型场景 |
| --- | --- | --- | --- |
| 副作用（写后附加动作） | **异步（默认走事件）** | 业务事务提交后发布事件，消费端幂等；主链路不等待结果 | 审计落库、操作 / 登录日志、通知与站内信、Webhook 推送、ES 索引同步、embedding、待办生成 |
| 读（跨模块取数） | **同步（禁止异步化）** | 经服务层接口 + DTO 或本地只读投影；可异步的只有**投影刷新** | 列表展示部门名 / 用户名 / 字典翻译 |
| 强一致写（跨模块写与状态迁移） | **同步 + 本地事务 / 跨服务写走 TM + XA** | 同库同事务完成；跨服务写走全局事务（TM + XA），不得拆成事件 + 补偿 | 审批状态机、软删除复合唯一约束、乐观锁、哈希链序 |

- **判定流程**：① 结果是否需立即返回调用方（读 / 状态迁移）→ 同步；② 是否为权威主数据写入 → 同步本地事务；③ 其余（通知、记录、索引、推送、外部集成）→ 异步事件。
- **读己之写**：异步投影存在延迟，写操作须返回更新后的完整对象（或由前端本地合并），不得依赖「写完立刻从投影读回」。
- **例外登记**：确需把某条同步读降级为异步投影（或把跨服务写改为全局事务）时，在对应概要设计登记「原同步语义 / 一致性影响 / 幂等与一致性方案 / 用户体验兜底」，经评审后执行；**不得因性能或解耦目的擅自改判**（Saga / 补偿已作废，不再作为选项）。
- **总线未就绪时的过渡**：RocketMQ 与 Outbox 投递器落地前，异步清单内的协作先同步直写 / 进程内调用实现并预留发布点；事件发布失败不阻塞主事务（MQ 故障时审计 / 日志降级为同步直写，见[故障降级](31_架构设计_性能与安全.md)）。
- **前置依赖**：消息队列部署、发件箱与投递器实现之前，本节异步清单不具备实施条件（现状：事件域为接口占位 + 默认实现）。

## 3. 生产一致性 <a id="produce"></a>

- **基线采用事务性发件箱（Outbox）**：业务事务内同时写业务数据与 `sys_outbox`（事件与业务同库同事务），由投递器（轮询，后续可切 CDC）转发到 RocketMQ——可无 MQ 独立工作、可重放、与审计链协同；随**阶段二（后端基座与服务化地基）**落 `sys_outbox` 表与投递器实现（服务化地基 S3），Outbox 基座细节见 [37-服务间通信与分布式一致性](37_架构设计_子系统_服务间通信与一致性.md)
- **消费侧幂等**：事件 ID 唯一约束 + 短窗口原子去重，保证至少一次投递下「效果一次」
- 生产者封装统一事件发布组件，业务代码不直接操作 MQ 客户端；备选：RocketMQ 事务消息（半消息 → 本地事务回调 → 确认发送），若启用则替换投递器方案并重新评估（当前不作基线）

## 5. 消费组架构 <a id="consume"></a>

| 消费组 | 职责 | 有序性 |
| --- | --- | --- |
| 审计链组 | 审计日志（操作/登录/开放接口/数据变更）串行追加 + 哈希链计算 | 分区有序（分区键=租户） |
| 日志落库组 | 操作日志/登录日志异步落库（降低主库写压力） | 并行 |
| Webhook 推送组 | 事件按订阅匹配推送（HMAC 签名、退避重试） | 并行 |
| 通知组 | 站内信落库 + 触发 Socket.IO 推送 | 并行 |
| ES 同步组（后续） | 主数据/审计日志/文件内容索引同步 | 并行 |
| embedding 组（后续） | 文件分段向量化入 Milvus | 并行 |

**消费组运行时语义**：

- **声明归提供方**：消费组（组名 + 订阅事件 + 是否强有序）由各服务自持声明，基座装配期统一装载——基座不预置任何业务组、不出现产品标识；订阅声明同时进入事件契约覆盖校验（升主版本前须覆盖全部订阅）。
- **拉取而非推送**：消费方主动长轮询拉取并显式确认，控制权在应用——停机时先停拉取、等在途任务跑完，避免「回调里等业务完成再确认」与异步运行时混用导致的卡死。
- **顺序实现**：同聚合键（空回落租户、再回落事件 ID）在组内串行、不同键并行；强有序组（审计链组）退化为全组串行——**不依赖消息中间件的 FIFO 语义**（gRPC 客户端不提供该保证）。
- **宿主形态**：同一运行器可随服务进程启动，也可由独立 worker 进程启动；**同一组不得在两个宿主同时消费**（会竞争消费、破坏顺序）。正式服务化（独立服务目录 / 镜像 / 编排）在需要独立扩缩容时再落，声明与运行时无需改动。

## 6. 幂等与重试 <a id="reliability"></a>

- 幂等：event_id 去重分两层——**短窗口（Redis）只读预判 + 成功后再标记**，**业务唯一约束兜底**（如日志表事件 id 唯一）。刻意**不用处理前 SETNX 占位**：处理前占位会让「处理失败回滚」后的重投被跳过，把至少一次退化成至多一次（事件永久丢失）。短窗口不可用时降级放行（唯一约束仍在，语义正确），不得 fail-closed 停掉事件流
- 重试：消费失败指数退避重试（有限次）→ 超限转死信；**死信以库表为唯一载体**（不另建死信 topic：库表已是权威看板，再建 topic 只增加订阅与消费方成本），落库后监控告警、人工处置。**死信落库失败的消息不确认**，留给中间件重投——宁可重复不可丢
- 重放：Outbox 是**事件账本**（保留期内可按类型 / 区间重放）；消费端按 event_id 幂等，重放安全
- 事件契约：事件是长期契约——**主版本内字段只增不删、新增可选**；**破坏性变更升主版本**（升主版本后允许删除 / 改名 / 类型与必填性变更）；消费方按订阅读旧新兼容
- 审计链消费分区键 = 租户：保证同租户日志串行追加，哈希链不乱序（见审计哈希链子系统）

## 7. Webhook 推送 <a id="webhook"></a>

- 订阅管理：sys_webhook（name、url、events、secret、status、fail_count），Webhook 管理页面注册（open 业务）
- 推送：HMAC 签名校验（sha256(secret, body)）；指数退避重试；失败记录 sys_webhook_log（webhook_id、event、payload、status、retry_count、next_retry_at、error_msg）
- 出站调用统一 httpx 封装（超时/重试/熔断）
