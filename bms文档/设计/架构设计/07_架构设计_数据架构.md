## 1. 概述 <a id="overview"></a>

本节点定义 BMS 的数据架构：库划分与数据分布、核心数据表清单、数据规范、缓存架构与迁移策略。
对应[《项目规划说明》](../../规划/项目规划说明.md)的「核心数据表清单」「多数据源策略」「数据库兼容」「数据规范」「缓存策略」章节。
这是数据库详细设计（逐表字段）与数据访问子系统设计的依据。

## 2. 数据分布 <a id="distribution"></a>

微服务形态下采用 **database-per-service**：**每服务独立库 × 每租户**；每服务只访问自己的库，**禁止跨服务直连与跨库 JOIN**，跨服务读经契约 / 事件或只读投影。

| 库类别 | 名称 | 内容 | 归属 |
| --- | --- | --- | --- |
| 平台服务库 | `bms_{service}`（平台层） | 各平台地基/能力服务在平台层的数据（如租户注册归租户配置服务、平台超管归认证身份服务、平台菜单与业务/动作权限码归权限服务、AI 端点配置归 AI 服务） | 所属服务（跨租户） |
| 服务租户库 | `bms_{service}_{tenant}` | 每服务 × 每租户一库：该服务在该租户的全部业务数据 | 所属服务（租户物理隔离） |
| 归档库 | `bms_archive` | 统一收存各租户归档数据（带 tenant / 原服务与表标识，只读查询） | 治理（只读） |

- 数据所有权：每份数据只有一个**权威服务**（写方唯一）；其他服务经契约 / 事件读，不共享库、不跨库 JOIN
- 跨库引用一律用逻辑外键（code），不建物理外键
- 读侧出口：跨服务报表 / 聚合走**只读投影**或数据查询提供者，不直接读他库
- **每服务每租户建库与路由**：库键由「服务标识 + 租户编码」派生（相对键 / 全限定键，见《[多租户路由](12_架构设计_子系统_多租户路由.md)》「三库命名与建库标准」节）；平台服务库按服务**真实拆分**（服务只连自身库）；租户开通按「服务 × 租户」幂等建库；**跨服务取库即拒**（数据所有权 10008），跨服务建库 / 迁移经运维通道显式豁免
- 开发环境用多个 SQLite 文件模拟各服务库与归档库（库键经连接串模板 `{service}` / `{tenant}` / `{database}` 解析）
- 环境库命名：`bms_dev` / `bms_test` / `bms_prod`（按服务与租户派生）

## 3. 核心数据表清单 <a id="tables"></a>

全部业务表统一规范：雪花 ID 主键、软删除（deleted_at）、审计字段（created_at/created_by/updated_at/updated_by）、乐观锁（version）、时间 UTC 存储；关联表用唯一联合主键。表前缀：平台域固定——系统 sys_、工作流 wf_、报表 rpt_、AI 域 ai_；产品业务模块表用各模块独立前缀（注册制，登记与分配见《[项目规划说明](../../规划/项目规划说明.md)》「平台扩展接入流程」节：biz 五模块 pur_/pay_/sup_/sale_/wh_，其他产品 15xxxx 起顺延）。

## 4. 数据规范 <a id="rules"></a>

- **数据所有权（服务化地基 S2）**：每份数据的写方唯一归属某服务；其他服务只读经契约 / 事件，禁止跨服务直写、共享 ORM 关系与跨服务 JOIN；跨服务读侧出口走只读投影或数据查询提供者，例外登记于《[后端开发规范](../../规范/后端开发规范.md)》「模块边界与数据所有权」节
- **字段级约定不在本节点重复**：主键 / 软删除 / 审计 / 乐观锁 / 时间 / 字符集 / 多值 / 布尔 / 索引等**字段级约定**以《[数据库设计 · 数据规范](../数据库设计/02_数据库设计_数据规范.md)》为唯一事实源；各库落点与差异以《[数据库设计 · 方言特性](../数据库设计/方言特性/01_MySQL.md)》各库文档为唯一事实源；强制口径见《[数据库开发规范](../../规范/数据库开发规范.md)》「表与字段口径」「索引口径」节
- **本节点保留的语义级原则**：数据写方唯一归属（见上）；软删除保留可恢复语义、审计类数据物理保留、唯一性在「软删除后可复用」口径下成立；时间统一 UTC 存储、展示按本地时区；多值与布尔等以跨方言逻辑类型表达、应用层归一到单一实现；字符串 / 数值等类型不引入方言专用能力

### 4.1 字典与系统参数管理 <a id="rules-dict"></a>

- 字典（sys_dict_type / sys_dict_item）与系统参数（sys_config）：平台库存默认，租户库可覆盖/自建（租户开通种子自动下发默认项）
- 字典多语言 label 存各自 _i18n 附表，按 locale 关联查询
- 缓存：只读热数据 Redis 缓存（`bms:{tenant}:dict:{locale}:{type}`），短 TTL + 随机偏移；字典/参数变更后删除缓存 key（先写库后删缓存协议）并递增全局版本号 `bms:{tenant}:dict:version`；后端进程内内存字典缓存（双 Region：小字典整类型 + 超大字典已查条目局部子集，按版本惰性比对；Redis 共享层与 L1 由 `CacheRegion` 真实实现承载——**redis-py（asyncio）自写**，2026-09-21 口径回写）供字典查询接口与业务翻译（导出/通知/报表/审批/明细行批量）共用，零网络往返；超大字典批量翻译走「局部缓存 + 一次性 IN 查询」防 N+1
- 字典/参数是权限体系与业务模块的通用依赖（状态、类型等基础字典），页面管理权限码 dict:manage / config:manage
- **字典取数契约（2026-09-20 登记，前端组件库 06_06 / 07_05）**：按类型取数支持**版本比对**（版本一致 `items` 返回空以省流量，与「空字典」以 `None` / 空集区分）、**批量合并**（表单多字典字段合并为一次请求）、级联父子过滤与按值子集；后端翻译（value → label）与取数共用同一份进程内缓存。统一出口为取数契约 `BaseDictSource`（单类型 / 批量）、翻译契约 `BaseDictTranslator` 与缓存域扩展 `DictCacheRegion`（固定 `domain="dict"`，key `bms:{tenant}:dict:{locale}:{type}` + 版本键 `bms:{tenant}:dict:version`，进程内 L1 经缓存 Region 承载、`INCR` 版本键惰性比对）。版本号与进程内缓存的关系见 §5.2「字典内存缓存失效」。真实取数 / 缓存 / 写路径与扩展属性（`attr_json` 不入普通链路）随通用能力·字典模块阶段；扩展属性高级查询经查询提供者（02-28），本契约只覆盖普通取数与翻译。契约与调用面见《[后端基类清单](../../后端基类清单.md)》「跨阶段基座」节。
- **用户偏好（2026-09-20 登记，前端组件库 08_03_01 / 07_05 / 07_04）**：用户偏好（列表个性化、向导开关、通知偏好、工作台布局）统一落 `sys_user_preference`（用户维度、键唯一、按域前缀命名、单键上限统一）；偏好只作**展示与交互**状态，不承载业务事实，跨端以服务端为准、离线可本地回退；读写统一经后端 `BasePreferenceStore`（`get` / `set` / `reset`，键 `{域}.{键}`、单键上限统一，占位实现固定回退默认值），列表偏好键 `list.{form_key}`——各模块不自建偏好存储

### 4.2 回收站机制 <a id="rules-recycle"></a>

- 无独立表：回收站复用软删除字段（deleted_at），软删除数据查看与恢复（权限码 recycle:restore）
- 恢复动作落操作日志与字段级审计（sys_data_audit_log）——审计留痕；恢复即清除 deleted_at
- 过期软删除残留由 Celery 定时物理清理，与归档清理任务衔接（清理顺序：先归档可归档数据，再物理清理过期残留）
- 唯一约束 (唯一字段, deleted_at) 复合唯一索引保证删除后释放唯一键、恢复不冲突

## 5. 缓存架构 <a id="cache"></a>

统一 Redis 缓存作为共享缓存源；一般业务数据不引入本地内存缓存（多实例内存独立会造成数据不一致），**字典为只读热配置例外**——进程内内存字典缓存（整类型 dict，全局版本号惰性比对保证多实例一致，见 4.1）。key 格式 `bms:{租户|global}:{域}:{业务键}`，全小写冒号分隔，所有 key 必须携带 TTL。

### 5.1 key 空间规划 <a id="cache-keyspace"></a>

| 域 | key 示例 | TTL 策略 |
| --- | --- | --- |
| 缓存类 | `bms:{tenant}:dict:{locale}:{type}`、`bms:{tenant}:dict:version`（字典全局版本，INCR）、`bms:global:menu:{locale}`、`bms:{tenant}:perm:{user_id}:{version}` | 短 TTL + 随机偏移（防雪崩）；版本键持久（随变更 INCR） |
| 会话与认证 | `bms:{tenant}:sess:{session_id}`、`bms:global:token:blacklist:{jti}` | 与业务有效期对齐（14 天 / 黑名单短窗） |
| 验证码与限流 | `bms:global:captcha:{uuid}`（5 分钟）、`bms:global:rate:{维度}:{目标}` | 短 TTL，与策略窗口对齐 |
| 锁与幂等 | `bms:global:lock:{资源}`、`bms:{tenant}:lock:{资源}`（分布式锁，键统一经基座拼接）、`bms:{tenant}:idem:{key}` | 带过期，防死锁 |
| 空值缓存 | 查询不存在的 key 值 = EMPTY 标记 | 短 TTL（防穿透） |

### 5.2 三防与一致性协议 <a id="cache-protocol"></a>

- 防穿透：不存在数据缓存空值（短 TTL）
- 防击穿：热点 key 过期用互斥锁（SETNX）单实例重建
- 防雪崩：TTL 加随机偏移，避免大量 key 同时失效
- 一致性：先写库后删缓存；写操作后同一会话内读主库，避免读到从库旧数据
- 权限缓存失效：权限相关变更 → 权限版本号 +1，用户缓存按版本校验，保证变更即时生效
- 字典内存缓存失效：字典变更 → INCR 全局版本键，各实例按版本惰性比对自动重载（与权限版本号同模式）

## 6. 迁移策略 <a id="migration"></a>

- Alembic 按 **服务 × 数据源**分别维护迁移脚本，只管理各库 schema；迁移脚本按数据源分链（平台库 / 租户库 / 归档库）组织，且**一套方言无关脚本在 MySQL / PostgreSQL / 达梦 DM8 三库执行**（不写方言 SQL；跨方言类型承载落点，各库差异与实测结论以《[数据库设计 · 方言特性](../数据库设计/方言特性/01_MySQL.md)》各库文档为唯一事实源）
- **多服务多库**：建库 / 迁移编排按**服务 × 租户**批量执行（平台服务库与各服务租户库分别管理）；新租户 / 新服务开通自动执行对应迁移
- SQLite 开发库自动建表（按数据源链表集在建表，不依赖迁移脚本；真库一律走迁移）
- 测试环境与开发环境一致使用 SQLite；三库方言差异以 CI 集成测试覆盖；主从路由、分片路由与归档流转以集成测试覆盖
