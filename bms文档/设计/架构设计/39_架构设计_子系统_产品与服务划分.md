## 1. 概述 <a id="overview"></a>

产品（mdm / biz / cw 等）按业务域提供能力；不同租户的业务重心不同——有的以采购为重、有的以仓储为重、有的大型企业每个业务域都要独立扩缩。若「业务域」与「部署单元」一一绑定，就只能全局一套拆分：要么所有租户共担巨型服务，要么所有租户都被拆成十几个服务。

本节点定的是：**业务域稳定、部署单元可变**——业务域是代码与数据归属的固定边界，部署单元（服务 + 库）是业务域的**组合**，按租户拓扑决定；同一套代码在最小形态下可单库单进程运行，在极端形态下可一租户一业务域一服务一库。

**本节点回答**：业务域怎么划、业务域怎么组合成部署单元与库、拓扑怎么记录与生效、边界怎么在合并部署时仍然成立、发布与迁移怎么走。
**本节点不回答**：能力契约与分配（归 38）、注册要素明细（归 11）、部署脚本与编排细节（归 33 与详细设计）。

## 2. 三层模型 <a id="layers"></a>

| 层 | 稳定性 | 语义 | 变化方式 |
| --- | --- | --- | --- |
| **能力** | 最稳定 | 对外承诺的协作单元（见 38 节点） | 随契约版本演进，只加不删 |
| **业务域** | 稳定 | 领域边界：代码归属、表归属、能力提供方都按业务域表达 | 极少变化（拆业务域是架构级决策） |
| **部署单元** | **可变** | 一个或多个业务域的集合，对应一个服务进程与一套库 | 按租户拓扑组合，随时可重建 |

**数据单元**是部署单元的属性：库按部署单元划分，**表归属按业务域**——同一部署单元内的多个业务域共享一个库，各业务域的表前缀与所有权不变。

## 3. 业务域划分判据 <a id="criteria"></a>

**何时拆业务域（新增一个业务域）**——满足两条及以上：

1. **数据所有权独立**：有自己的聚合与生命周期，不被其他业务域的事务边界覆盖；
2. **业务语义独立**：有独立的业务规则与外部承诺（可被单独授权、单独计价）；
3. **扩缩需求独立**：读写量级或峰值形态与其他业务域显著不同，合并会成为瓶颈；
4. **变更节奏独立**：演进频率与发布窗口明显不同。

**何时加业务域（在既有服务内新增业务域）**：与既有业务域共享所有权与事务边界、且没有独立扩缩需求时，只在既有业务域内加聚合，不新开业务域。

**何时开产品（而非只在平台内加业务域）**：具备**独立仓库、独立发版节奏、独立团队或独立商业定价**中至少两项时，作为产品独立仓；否则归平台内建。

**反例（不构成拆业务域理由）**：表数量多、代码行数多、命名上“看着像另一个业务”——这些是规模与整洁问题，不改变所有权与边界。

## 4. 部署拓扑（业务域 → 部署单元与库） <a id="topology"></a>

**拓扑是租户级运营配置**：每个租户一份「业务域 → 部署单元与库」的映射，平台侧记录、发布时生效、变更留审计。

连续谱（同一套代码皆可运行）：

| 形态 | 部署单元 | 库 | 适用 |
| --- | --- | --- | --- |
| 最小 | 一个进程承载全部业务域（含平台业务域） | 一库 | 小微 / 试用 / 开发测试 |
| 分组 | 按业务重心分组（如采购独立、仓储与销售合并） | 每组一库 | 业务重心明显的租户 |
| 独立 | 每业务域一个部署单元 | 每业务域一库（按需合库） | 大型企业 / 强隔离要求 |

- **拓扑模板**：允许以模板（小 / 中 / 大 / 特定行业）预置常见组合，单租户可在此基础上调整；模板只减少配置量，不改变语义。
- **拓扑与能力寻址的关系**：能力绑定业务域（38 节点），消费方按「能力 → 业务域 → 当前租户拓扑下的部署单元」两段解析；**因此同一能力在不同租户可由不同服务承载，消费方无感**。
- **平台业务域的处理**：平台业务域（认证、权限、租户、文件、通知等）同样按业务域表达，最小形态与业务域同进程同库，独立形态各自成服务；平台业务域不因“是平台”而免除边界纪律。

## 5. 边界纪律（按业务域断言，不按进程） <a id="boundary"></a>

合并部署会让“进程边界”消失，因此**所有边界纪律必须按业务域表达并在代码层断言**：

| 纪律 | 语义 |
| --- | --- |
| 依赖方向 | 业务域之间只允许上层依赖下层；**跨业务域访问只经能力契约**（38 节点），禁止直接引用他业务域实现 |
| 表归属 | 每张表有且仅有一个归属业务域；跨业务域读表视为越界（合并部署时尤其要守住） |
| 事务边界 | 单业务域内本地事务；跨业务域写走强一致事务或事件（37 节点），不因同库同进程就“顺手”写他业务域表 |
| 配置与密钥 | 业务域级配置隔离，不因合并部署而共享凭据 |
| 观测 | 指标、日志、审计按业务域标注，合并部署后仍能区分归属 |

> 判据一句话：**合并的是部署，不是边界**。任何“因为现在同库同进程，所以可以直接访问”的写法，均视为架构违规，由业务域级护栏拦截。

## 6. 数据与库 <a id="data"></a>

- **库是部署单元属性**：一个部署单元一套库；库名由部署单元标识派生，不由业务域派生。
- **表归属按业务域**：表前缀体现业务域，而非体现当前部署单元——拓扑变更（拆 / 合）不改变表名，只改变表落在哪个库。
- **迁移链按业务域**：每个业务域一条**独立**迁移链（业务域内线性、业务域间互不依赖），部署单元在运行时**执行其包含的各业务域的链**——因此拆 / 合拓扑不切迁移历史，任一形态下库结构等于“所含业务域各链的并集”。
- **跨业务域读**：只经能力契约或只读投影，禁止跨库跨业务域直读（沿用 37 节点数据所有权纪律）。
- **归档与备份**：按库执行，归档策略按业务域声明（同一部署单元内不同业务域可有不同保留期）。

## 7. 发布与版本 <a id="release"></a>

- **发布单元 = 部署单元**：一个部署单元一次发布，包含其内全部业务域的当次版本；业务域版本是部署单元版本的组成部分。
- **产品版本与服务版本解耦**：产品按自身节奏发版；产品所用业务域的版本随部署单元发布体现，产品只需声明“依赖哪些能力（业务域）及其契约版本”。
- **合并部署的版本对账**：同一部署单元内多业务域同时发布，须校验业务域间契约版本兼容（沿用 38 节点契约版本口径），不兼容即拒绝发布。
- **回滚**：按部署单元整体回滚；避免“只回滚某业务域”造成同单元内版本错配。

## 8. 拓扑迁移 <a id="migration"></a>

拓扑变更（合并 → 拆分、拆分 → 合并、换库）是**运营动作**，须满足：

1. **先加后切**：新部署单元先上线并成为可服务状态，再切换流量，最后下线旧单元；
2. **数据先行**：按业务域维度搬迁数据（表归属按业务域、迁移链按业务域），搬迁期间双写或停机窗口按租户等级选择；
3. **能力地址不变**：消费方按业务域寻址，拓扑切换对消费方透明；切换期允许短暂双活，但同一能力不得长期由两处提供；
4. **可回滚**：切换前保留旧单元与数据快照，回滚窗口内可整体退回；
5. **审计与告知**：拓扑变更留审计，涉及停机窗口的须提前告知租户。

## 10. 现状差距（2026-10-24 核查） <a id="gap"></a>

按现有实现核对「业务域稳定、部署单元可变」的可达性，结论：**当前做不到**，但可复用基础比预期多。差距分三类，配套措施已排入 07C 的四阶段（见专项计划）。

**可直接复用**：

| 已有能力 | 复用方式 |
| --- | --- |
| 模块注册四类记录 + 合并视图 + 同键异值即拒 | 业务域与部署单元作为新的记录种类并入同一装载与视图 |
| 产品路由含 domain 段 | 对外路径保持按业务域稳定 |
| 库名派生已参数化（前缀 + 服务段 + 库名基，同值去重） | 服务段改为部署单元标识即可 |
| 表归属登记（登记表 + 表文件 + 校验脚本） | 归属取值由服务扩为业务域 |
| 服务身份与 scope、契约版本门禁、网关按清单生成 | 分配授权与版本来账的载体已存在 |

**必须补齐（按难度）**：

| # | 卡点 | 现状事实 | 补齐方向 |
| --- | --- | --- | --- |
| 1 | 业务域在代码里不成体系 | 模型层已按目录分为 `identity` / `platform` / `tenant` 与横切根目录（平台 44 张表全在基座），但 `platform` 一个目录混了 6 个业务域，且服务侧除 `ai` / `notification` / `txn` 外无自有表与业务域载体 | 业务域登记 + 按业务域分包 + 表归属按业务域（阶段一） |
| 2 | 表归属与库归属粒度是服务 | 表归属记录的服务字段、库键解析的跨服务拒绝 | 归属改为业务域；库键服务段改为部署单元；归属校验改为「业务域 ∈ 本部署单元」（阶段一） |
| 3 | 无进程内直调传输 | 服务间调用只有 HTTP 与占位两种实现 | 新增同部署单元内直调；能力寻址第二段返回本地 / 远端（阶段二） |
| 4 | 边界护栏按服务包断言 | 合并部署后同进程内一切可达 | 按业务域包断言，合并场景必须有反例用例（阶段一） |
| 5 | 服务令牌身份粒度是服务 | 令牌主体为服务标识，能力分配按业务域授权 | 令牌携带业务域声明，或部署单元声明其承载业务域，两者对账（阶段四） |
| 6 | 网关路由按服务生成 | 外部路径按服务键生成 | 生成规则改为「业务域 → 部署单元 → 上游」（阶段四） |
| 7 | 观测与配置按服务标注 | 日志、指标、配置均以服务为单位 | 按业务域标注；配置能表达“本部署单元启用哪些业务域”（阶段四） |

> 详细现状事实与逐项对策见 07C `01_01` 详细设计的前置评估章节。

## 11. 演进与开放项 <a id="evolution"></a>

- **拓扑模板治理**：模板数量增长后需收敛为少量标准档位，避免“一租户一套手工拓扑”导致运维不可控。
- **跨租户共享部署单元**：当前按租户独立拓扑；若未来出现“多租户共享部署单元”，须重新论证数据隔离与噪音邻居，不默认支持。
- **业务域数量与治理成本**：业务域越细，边界越清但编排越复杂；业务域清单需定期复核（合并同类、拆分过载），判定沿用 §3 判据。
- **未定项**：业务域级版本号是否对外可见（对租户承诺层面）——留待出现“按业务域单独承诺可用性”的需求时再定。
