## 1. 概述 <a id="overview"></a>

本子系统承载微服务形态下服务间的**通信与分布式一致性**：服务契约与同步调用、事务性 Outbox、
幂等消费、**强一致事务（TM + XA）**，以及跨服务的数据所有权与读侧出口。对应《[微服务演进规划](../../规划/微服务演进规划.md)》「服务化地基要求与门禁」S1 / S2 / S3 / S7；
通信与一致性模式的原理见知识档案《[微服务 · 05 通信与分布式一致性](../../资料/知识档案/微服务/05_微服务_通信与分布式一致性.md)》，选型见《[微服务 · 12 选型对比（BMS）](../../资料/知识档案/微服务/12_微服务_选型对比.md)》。

与 [16-事件总线](16_架构设计_子系统_事件总线.md) 分工：本节点管**契约、Outbox 基座、幂等与跨服务强一致事务**；事件总线管**事件模型、消费组与 Webhook 推送**（事件通道）。

## 2. 服务边界与契约 <a id="contract"></a>

- **服务边界（S1）**：每服务唯一公开契约（OpenAPI），是服务间唯一访问面；**禁止跨服务访问内部实现与非自身数据库**
- **公开契约设计得像未来的服务 API**：无进程内假设（传值不传引用）、显式幂等、稳定字段只增不删
- **契约版本与兼容（S7）**：契约快照入 CI，破坏性变更用 **oasdiff** 门禁拦截（「只加不删」、破坏性变更升大版本）；注册与版本登记见 [11-模块注册](11_架构设计_子系统_模块注册.md)
- **数据所有权（S2）**：每份数据的权威服务唯一（写方）；其他服务只读经契约 / 事件；**所有权 ≠ 物理分库**——同一服务边界内的数据**默认同库**（表级唯一归属 + 边界守卫强制），仅在需要独立扩缩 / 选型 / 硬隔离 / 故障域隔离时才按服务拆库（口径见《[微服务演进规划](../../规划/微服务演进规划.md)》§1.1 原则 2 / §1.2）

## 3. 同步调用 <a id="sync"></a>

| 项 | 语义 |
| --- | --- |
| 协议 | REST + JSON（OpenAPI 契约）；演进见第 8 节 |
| 韧性 | 每个下游调用设**显式超时 / 重试 / 熔断降级 / 限流**（复用基座），避免调用链拖死 |
| 调用链 | A→B→C→D 同步链延迟为各段之和、可用性为各段之积——**能异步就异步**，缩短关键链 |
| 读 | 跨服务读经契约返回 DTO 或本地只读投影；不直接读他库 |
| 高扇出参考数据 | **主数据 / 参考数据**（组织 / 供应商 / 客户 / 物料等）**单一写者 + 高读扇出 + 弱一致 + 独立生命周期**，是服务化的优等生；读侧**去同步化**——**事件驱动本地只读投影**（首选，变更少、读多、可降级用旧副本）或**同步契约 + 缓存 + 降级**（近实时、小体量）；**消费方绝不直连权威库**，防「人人用 = 运行时单点 + 发布耦合」（口径见《[微服务演进规划](../../规划/微服务演进规划.md)》§1.3） |
| 边界 | 服务间调用不经网关（东西向直连），鉴权用服务身份（见 [14-认证与会话](14_架构设计_子系统_认证与会话.md)） |

## 4. 事务性 Outbox <a id="outbox"></a>

解决「本地事务提交」与「事件发布」无法原子化的双写不一致：

- 业务事务内同时写业务数据与 `sys_outbox`（**事件与业务同库同事务**），由投递器（轮询，后续可切 CDC）转发到 RocketMQ
- 投递语义为**至少一次**：投递器崩溃在「已发未标记」时会重发，消费端按 event_id **幂等**收敛为「效果一次」
- Outbox 是**事件账本**：保留期内可重放；已发布记录归档后清理，死信进看板人工处理
- 顺序：同聚合按序投递（顺序消息），保证同聚合事件因果有序
- 选型：**本地事务 + 自研薄 Outbox + 幂等**为基线（可移植三方言、可重放/审计、不绑 broker）；RocketMQ 事务消息为备选（需 5.x + 待实测）；**排除 2PC / XA（默认路径；2026-10-09 修订）**——理由是「默认路径 + 可用性 / 运维代价」，**非「技术上不可行」**（「Python 无事务管理器、dmPython 无 XA」的说法已被 05_05 / 05_06 实测推翻：达梦经 `dmxa` 已可用、三库 XA 已实测）。**（2026-10-06 真库实测**：① 三库**服务器**均支持 XA——达梦 `DBMS_XA` 包（Python 经 SQL 实测 `XA_START/XA_END/XA_PREPARE/XA_COMMIT/XA_ROLLBACK` 全通过）、MySQL `XA`、PostgreSQL `PREPARE TRANSACTION`；② 受限在**应用驱动层**——MySQL / PostgreSQL 的 **SQLAlchemy 异步 API 不暴露 `begin_twophase`**、达梦 `dmSQLAlchemy` **同步方言未接 `DBMS_XA`**；③ 仅「**同步引擎 + 单进程**」可两阶段（实测 MySQL×PG 通过；达梦经 `DBMS_XA` 亦可，需自定义方言）；**跨服务 2PC 仍需外部 TM**。故仍**以「本地事务 + Outbox + 幂等」为基线**；引入应用级 2PC 须另立「自定义方言（接 `DBMS_XA` / XA）+ 外部 TM」专项评估。详见《[数据库设计 · 方言特性](../../设计/数据库设计/方言特性/03_DM8.md)》各库「事务与连接」节）
- **分布式事务方案评估结论（2026-10-06，需求 05-5 / 任务 05_06）**：① **单库原子优先**——要求「要么全成功要么全失败」的数据（如结构化权限的「角色 + 用户分配 + 权限项」）优先**收敛到单一服务库**、用**本地事务**保证原子；② **跨服务写统一走强一致**（TM + XA 全局事务，2026-10-10 拍板；Saga / 补偿已作废，见 §6），**事件 / 读侧**以「本地事务 + Outbox + 幂等」为基线并以**一致性屏障**（执行前校验目标变更是否已应用 / 有界等待 / 超时报错）补足「执行前已收敛」，避免读到半成品；③ 跨服务 2PC 由 **TM 协调服务 + 各参与方 XA**（`[transaction_manager].provider` 配置启用）落地（三库 XA 实测见知识档案《[分布式事务](../../资料/知识档案/分布式事务/01_分布式事务_总览.md)》与任务 05_07）。口径见《[后端开发规范](../../规范/后端开发规范.md)》§10 与知识档案《[一致性屏障](../../资料/知识档案/分布式事务/04_分布式事务_一致性屏障.md)》。**（2026-10-09 修订 / 任务 03_04）**：Redis 提升为**基础（必需）能力**（统一客户端能力域 + 短超时 + fail-closed，见《后端开发规范》§10「强一致场景口径」）；屏障存储不可用由「放行」改为报 `10012` / 503

## 5. 幂等与重放 <a id="idempotent"></a>

- 幂等消费：每个消费者维护「已处理事件」记录（consumer + event_id 唯一），与业务副作用**同一本地事务**写入，命中唯一键即跳过
- 业务幂等：写接口支持幂等键（如支付指令 `idempotency_key` 唯一索引），重复请求返回原结果
- 重放：消费端按 event_id 去重，故 Outbox 重放安全；用于故障恢复与投影重建
- 事件契约：只增不删、破坏性变更升版本（见 [16-事件总线](16_架构设计_子系统_事件总线.md)）

## 6. 跨服务一致性（强一致事务） <a id="strong-consistency"></a>

> **口径（2026-10-10 拍板，统一向强一致）**：跨服务写**不再使用 Saga / 补偿**——**Saga / 补偿 / TCC / 编排式 Saga（Temporal）作为分布式事务机制整体作废**（缘由：补偿＝**手工编写的伪回滚**，依赖逐用例正确实现、不可靠，本质缺回滚机制）。统一改用**数据库级强一致事务**（回滚由数据库原生保证）。

**三段式归属**：

| 场景 | 机制 |
| --- | --- |
| 单服务写 | **本地事务**（单库原子） |
| **短流程跨服务写**（毫秒~秒级，如角色 / 用户保存：platform + mdm） | **全局事务：TM 协调服务 + 各参与方 XA（2PC）**——`prepare` 前两侧变更对业务均不可见，真回滚、无残留（`[transaction_manager].provider` 配置启用，见任务 05_07） |
| **长流程 / 含人工审批** | **工作流（`wf`）业务状态机 + 业务反向操作**（驳回 / 撤回 / 作废）——**非 Saga、非分布式事务**；每步各自本地事务，失败靠**业务动作**而非数据库回滚 |
| 事件 / 读侧 | 事务性 Outbox + 消费幂等 + **一致性屏障**（读侧收敛，保留） |

- **单库原子优先**：要求「要么全成功要么全失败」的数据（如结构化权限的「角色 + 用户分配 + 权限项」）优先**收敛到单一服务库**、用**本地事务**保证原子
- **跨服务物理原子**：无法收敛单库且中间态零容忍时，走 **TM + XA 全局事务**（回滚＝`XA_ROLLBACK`，数据库原生）
- **分布式事务是模式、不是服务**：协调器（**TM**，如 `txn` 服务）属**基础设施**（与网关 / MQ / 缓存同类），**不是业务微服务**；且**优先避免需要它的拆分**（能不拆库就不拆，见《微服务演进规划》§1.2）
- **一致性屏障**：跨服务变更经事件最终一致时，「执行前」可经一致性屏障校验「目标变更是否已应用」——未应用则有界等待、超时报错（可重试），**不静默放行旧值 / 半套状态**；缺省不启用（`null` 即返回），按需切真实实现。屏障是增强手段、非强约束，绕过屏障直读他库仍受数据所有权纪律约束（见 [07-数据架构](07_架构设计_数据架构.md)）；**存储不可用时抛 `10012` / 503，不静默放行旧值 / 半套状态（03_04 起 degrade-open 作废）**

## 7. 强一致场景处理 <a id="strong-consistency"></a>

| 场景 | 处理 |
| --- | --- |
| 审计哈希链 | 链按 `(service, tenant)` 分条、服务内本地强一致；业务变更 + 链追加 + Outbox 同库同事务；跨服务由审计服务幂等消费汇总，只校验不重算；绝不把一条链拆到多服务维护 |
| 财务 / 收付款 | 收敛到单一账务服务（库内 ACID）；幂等键 + 分录唯一约束；跨服务写走 **TM + XA 强一致**；显式状态机 + 乐观锁；对账兜底 |
| 软删除复合唯一 | `(唯一字段, deleted_at)` 复合唯一（见 [07-数据架构](07_架构设计_数据架构.md)）；属单库问题，不涉分布式事务 |
| 审批状态机 | 单服务内显式状态 + 合法迁移 + 本地事务 + Outbox；跨服务长流程归 **`wf` 工作流**（业务状态机 + 业务反向操作，非 Saga） |
| 结构化权限保存 | 「角色 + 用户分配 + 权限项」优先**收敛 platform 单库**、本地事务原子；平台 ↔ mdm 组织域的跨服务写（角色 / 用户保存）走 **TM + XA 全局事务**（2026-10-10 拍板；见 [15-权限计算引擎](15_架构设计_子系统_权限计算引擎.md) 与任务 05_07） |
| 跨服务变更后执行 | 变更经事件最终一致时，执行前经**一致性屏障**确认「目标变更已应用」；未收敛有界等待、超时报错（可重试），不读半成品状态 |

## 8. 通信演进 <a id="evolution"></a>

- 现期：REST / JSON + 事件
- 演进：随内部高频 / 流式场景增多，**参考 gRPC**（官方 `grpcio` / `grpc.aio`）并评估**自研高性能服务间同步通信**；须与生态（可观测 / 契约 / 服务身份）兼容，按实测收益评估，不阻塞地基
- 边界：无论何种协议，服务契约与数据所有权纪律不变
