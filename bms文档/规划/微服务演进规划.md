## 1. 目标与原则 <a id="goals"></a>

**目标**：把 BMS 演进为**微服务架构**——平台内部模块与产品（biz / cw）**全服务化**；且**从一开始就按分布式构建**，从架构上一次性设计到位，避免「先做单体、以后再拆」的返工。

> 本规划改写《[项目规划说明](项目规划说明.md)》「明确不采用」节原「不引入微服务」条目。决策依据、收益代价与行业证据见《[微服务 · 02 单体与微服务取舍](../资料/知识档案/微服务/02_微服务_单体与微服务取舍.md)》，本项目约束代入与触发条件见《[微服务 · 10 项目评估（BMS）](../资料/知识档案/微服务/10_微服务_项目评估.md)》，技术选型见《[微服务 · 12 选型对比（BMS）](../资料/知识档案/微服务/12_微服务_选型对比.md)》。

### 1.1 设计原则 <a id="principles"></a>

1. **一开始就分布式构建**：逻辑多服务 + 物理单机多容器（Docker Compose），架构按「可平滑迁多机 / k3s」设计；**分部署即微服务，不保留单体运行形态**。
2. **数据所有权为准，物理分库按需**：准则是**每服务拥有其数据**（表级唯一归属、只经契约 / 事件访问），**不共享写**、不跨服务 JOIN；**物理分库是手段而非教条**——同一服务边界内的数据**默认同库**（不为分而分），仅在需要**独立扩缩 / 独立选型 / 硬隔离 / 故障域隔离**时才按服务拆库。所有权由「表级归属登记 + 边界守卫（静态校验 + 运行时护栏）」强制（见 §3 S2 与 §1.2）。
3. **按限界上下文 / 业务能力垂直切分**：禁止按技术层拆（否则得到分布式单体）。
4. **地基先行**：无网关、契约、分布式一致性与可观测地基，拆分只会得到「分布式单体」——服务化地基必须先于业务服务落地。
5. **保留既有产出、重构为分布式**：阶段一~五已交付的分层、基类体系、`sys_module` 注册、事件总线、前端模块化**保留**，按服务边界重组，不推倒重来。
6. **横切能力数据所有权收敛、承载按需服务化**：认证、权限、租户、审计、可观测等横切能力的**数据所有权**各自唯一（不逐服务复制），**承载形态按需**——同一服务边界内默认**同服务能力单元**（如权限随 platform 地基服务），仅当其被多产品高频复用且需独立部署 / 扩缩时，才拆为独立服务。
7. **先求不拆、再谈分布式事务**：**能同库就不拆库**，避免教条分库「人为制造」分布式事务需求；必须跨服务时按**三段式**（见 §1.2）——**单服务写 → 本地事务；短流程跨服务写 → TM + XA 强一致；长流程 / 含人工审批 → 工作流状态机**；**Saga / 补偿已作废**。
8. **前后端解耦推进**：本轮只登记「前端经网关 / BFF 接入后端服务」这一对接事项；微前端（Module Federation）治理另有《[微前端](../资料/知识档案/微前端/01_微前端_总览.md)》专题，另行讨论。

### 1.2 数据所有权与分布式事务口径 <a id="data-txn"></a>

> **2026-10-10 拍板**：澄清「数据所有权 ≠ 分库」「分布式事务 ≠ 服务」两条易混口径，供服务归属与拆分决策统一遵循。

- **所有权 ≠ 分库**：微服务的准则是「**每服务拥有其数据**」（owns its data / schema），**物理分库只是达成它的手段之一**；独立性与所有权同样可由「**同库 + 表级唯一归属 + 边界守卫**（静态校验 + 运行时护栏）」达成（本项目现即此形态）。
- **分库是分布式事务的代价**：跨库即失去本地事务，必然引入跨服务一致性成本；因此决策顺序为 **「先问数据是否真的需要独立部署 / 扩缩 / 选型 / 硬隔离」→ 不需要则同库 → 需要才拆库 → 拆了才谈分布式事务**，不可倒置。
- **分布式事务是模式，不是服务**：其**协调器**（**TM**，如 `txn` 服务）属**基础设施**（与网关 / MQ / 缓存同类），**不是业务微服务**；**Saga / 补偿 / TCC / 编排式 Saga（Temporal）作为分布式事务机制整体作废并已删除**（2026-10-10 拍板；缘由：补偿＝手工伪回滚、不可靠）。
- **三段式（2026-10-10 拍板）**：① **单服务写** → 本地事务（单库原子）；② **短流程跨服务写**（毫秒~秒级）→ **TM + XA 全局事务（强一致，数据库原生回滚）**；③ **长流程 / 含人工审批** → **`wf` 工作流**（业务状态机 + 业务反向操作，非 Saga / 非数据库回滚）。**事件 / 读侧**走事务性 Outbox + 消费幂等 + 一致性屏障。口径与实现见[架构设计 37](../设计/架构设计/37_架构设计_子系统_服务间通信与一致性.md)。

### 1.3 主数据（参考数据）服务化与读侧形态 <a id="master-data"></a>

> **2026-10-10 拍板**：主数据（组织 / 供应商 / 客户 / 物料等）**应当服务化**（独立服务 + 独立库作权威源）；**「被所有人使用」决定的是读侧形态，而非是否服务化**。

- **服务化判据（主数据几乎全中）**：**单一写者 + 高读扇出 + 弱一致 + 独立生命周期**——参考数据是服务化的优等生（与权限「紧耦合用户 / 角色、强一致」留 platform 能力单元恰好相反的结论，同一把尺子：耦合强度 / 一致性 / 变更频率 / 读写比）。
- **读侧去同步化（关键）**：「人人用」若理解为**同步直连**，权威源即成为**运行时单点 + 性能瓶颈 + 发布耦合**。三形态按需选：
  - **事件驱动本地只读投影**（**首选**）：消费方在自己库里维护**所需的那部分**主数据副本，经事件刷新——解耦运行时、可降级用旧副本、性能好；代价为最终一致 + 副本存储；
  - **同步契约 + 缓存 + 降级**：近实时、小体量适用（如组织读出口）；
  - **混合**：热 / 小体量走同步，大体量 / 高频走投影。
- **铁律**：消费方**绝不直连权威库**（否则所有权崩、无法独立演进），一律经契约或投影；读侧副本是**只读投影**，权威仍在主数据服务。
- **落地（现状）**：组织主数据已随 mdm 独立服务化（bms `org` 服务 2026-10-07 退役），bms 经 `/api/mdm/v1/org/*` 读出口 + `OrgSourceAdapter` 消费、对不可达**降级**；可补演进为**事件驱动投影**（出现高频读 / 强可用要求时）。

## 2. 目标架构与服务清单 <a id="architecture"></a>

### 2.1 架构形态 <a id="shape"></a>

```mermaid

    C[客户端 PC / H5] --> GW["API 网关（APISIX）<br/>认证 / 路由 / 限流"]
    GW --> G["平台地基服务<br/>认证身份 · 租户配置 · 权限 · 模块注册 · 审计"]
    GW --> B["平台能力服务<br/>用户/角色/菜单（登录鉴权） · 工作流 · 表单 · 报表 · 文件 · 通知 …"]
    GW --> P["产品服务<br/>biz 采购/收付款/… · cw 创作域"]
    G & B & P --> MQ[["RocketMQ 事件总线"]]
    G & B & P --> DB[("每服务数据所有权唯一<br/>物理分库按需（默认同服务同库）")]
    G & B & P --> OBS["OpenTelemetry<br/>Trace / Metrics / Log"]
    classDef svc fill:#e8eef4,stroke:#38a,color:#111
    classDef ext fill:#e8f4e8,stroke:#3a7,color:#111
    class G,B,P svc
    class MQ,DB,OBS ext
```

- **进程模型**：一服务一容器；**数据默认同服务同库**，按服务拆库**按需**（触发条件见 §1.1 原则 2）；服务间同步走 REST，异步走 RocketMQ；服务身份与认证走网关 + OIDC / JWT。
- **寻址**：服务间按稳定主机名寻址（Compose DNS → 迁 K8s 后原生 Service），地址收敛进配置层，禁止硬编码 IP。
- **注册升格**：现有 `sys_module` 模块注册表升格为**服务目录与契约 / 版本登记**。

### 2.2 服务清单与建设批次 <a id="services"></a>

划分原则：按限界上下文 / 业务能力垂直切分；**每服务拥有其数据**（表级唯一归属；物理分库按需、默认同库）、独立发布；横切收敛为地基服务或能力单元。**下表只到分批与分组**，具体服务目录与注册要素（表前缀 / 业务码 / 错误码段 / 事件域）留到「阶段二」需求基线登记。

| 批次 | 服务 | 说明 |
| --- | --- | --- |
| **第 0 批（地基）** | 网关 / 边缘、认证与身份（含 SSO / IdP、会话令牌、服务身份）、租户与配置（租户开通 / 域名 / 配额、系统参数）、**权限**、模块注册 / 服务目录、审计（操作 / 登录 / 哈希链）、事件与可观测基座 | 分布式起步的前置；无此则得到分布式单体 |
| **第 1 批（边缘独立、低耦合）** | 文件、通知（站内信 / 推送 / 邮件短信）、任务调度、全文检索、报表、AI | 失败可降级、资源画像独特，先建以验证地基 |
| **第 2 批（平台核心与业务能力）** | 用户 / 角色 / 菜单（登录鉴权基础数据）、工作流、表单定制、公告 / 帮助、导入导出、开放接口 / Webhook、归档 / 备份 / 回收站、首页工作台 | 强一致与横切最多，地基稳定后建 |
| **第 3 批（产品服务）** | biz（采购 / 收付款 / 销售 / 仓储，按 biz 域拆）、**mdm（组织 / 供应商 / 客户 / 物料等主数据域）**、cw（创作域） | 产品仓库按服务独立部署；主数据为**参考数据**（单一写者 + 高读扇出 + 弱一致），读侧按 §1.3 去同步化（事件投影 / 契约缓存） |

> **顺序说明**：认证 / 权限 / 审计属**地基**，虽为强一致最重、风险最高，仍须先建（因「从零分布式」而非「从单体抽取」，与知识档案《[09 渐进式演进](../资料/知识档案/微服务/09_微服务_渐进式演进.md)》「核心链路最后拆」的顺序不同）。
>
> **权限归口（2026-10-10 拍板）**：权限（角色 / 权限码 / 菜单表单字段 / 数据范围 / 用户-角色）**归 platform 地基服务内的能力单元**——与被授权的用户 / 角色 / 菜单**同库同事务**，避免为「用户→角色→权限」这条强一致链**人为制造**跨服务事务；**独立 `permission` 服务为可选演进**（当被多产品高频复用且确需独立部署 / 扩缩时再拆，届时连库一并拆）。校验器保持**进程内**（读权限快照，不逐请求远程调用），与「权限是否独立服务」解耦。

### 2.3 仓库形态 <a id="repos"></a>

- **平台**：`bms` monorepo 内多服务工程，共享基座库与工具链；CI 按服务粒度构建；服务边界靠 CI 校验强制。
- **产品**：biz / cw 独立仓库，按服务独立部署（《[平台可扩展性规划](平台可扩展性规划.md)》「代码复用能力边界」节）。

### 2.4 技术选型（已确认） <a id="stack"></a>

| 子项 | 选型 | 子项 | 选型 |
| --- | --- | --- | --- |
| API 网关 | Apache APISIX | 服务身份 | 网关 OIDC + 双类 JWT（Keycloak 自托管） |
| 容器编排 | Compose 现网 → 触发时直上 k3s | 可观测 | OpenTelemetry + Tempo + Prometheus / Grafana + Loki |
| 服务发现 | DNS（Compose DNS → K8s Service） | CI/CD 构建 | 父-子流水线（monorepo 多服务） |
| 配置中心 | `config.toml` + 环境变量（暂不引入） | 发布回滚 | 不可变镜像 + 一键回滚 + 健康检查门禁 |
| 服务间通信 | REST + RocketMQ 事件（演进见第 4 节） | 契约测试 | Schemathesis + OpenAPI 契约快照 |
| 后端语言 | 单一 Python / FastAPI | API 兼容 | oasdiff（breaking 门禁） |
| 一致性 | 本地事务 + 自研薄 Outbox + 幂等 | 容器编排升级 | 单机多容器 → 多机 / k3s（见第 4 节） |

> 候选对比、推荐理由与参考链接见《[微服务 · 12 选型对比（BMS）](../资料/知识档案/微服务/12_微服务_选型对比.md)》；落选方案（Kong / Traefik / 服务网格 / 2PC-XA / Nacos 等）与排除理由同见该页。

## 3. 服务化地基要求与门禁 <a id="foundation"></a>

服务化地基要求取代原「可拆分性七项」，作为**横切门禁贯穿各阶段**（不单列阶段，随对应阶段自然落地并卡门禁）：

| # | 要求 | 门禁口径 |
| --- | --- | --- |
| S1 | 服务边界与契约 | 服务清单 / 服务目录齐备；每服务唯一公开契约（OpenAPI）；禁止跨服务访问内部实现与非自身数据库 |
| S2 | 数据所有权 | **每服务拥有其数据**（表级唯一归属；物理分库**按需**、默认同库）；写侧唯一归属；读侧经契约 / 事件或只读投影；禁止跨服务 JOIN |
| S3 | 事件与一致性 | 事务性 Outbox + 消费幂等 + 去重 + 重放；事件契约版本与「只加不删」；**跨服务写按三段式用本地事务 / TM + XA 强一致 / 工作流**（Saga 已作废，口径见 §1.2） |
| S4 | 服务身份与认证 | 网关统一认证；服务间 OIDC / JWT（必要时 mTLS）；横切能力数据所有权不逐服务复制（**权限归 platform 地基服务的能力单元**，独立服务为可选演进），校验器进程内 |
| S5 | 运行时无状态与外部化 | 会话 / 缓存 / 文件 / 定时任务外部化；每服务健康与就绪检查、按服务可观测 |
| S6 | 分布式可观测 | OpenTelemetry 全链路 Trace + Metrics + 日志聚合；跨服务问题可定位 |
| S7 | 度量与门禁 | 服务边界越界数、跨库访问数、契约破坏数、服务独立发布成功率等度量，挂 CI 与阶段门禁 |

> 落地：以上要求主要随「阶段二 后端基座与服务化地基」交付（见第 5 节）；后续阶段引入新服务时，对应门禁项逐条判定，未达标不放行。

## 4. 演进路线（E1~E5） <a id="roadmap"></a>

原「何时从单体拆」的触发条件（T1~T8）随分布式起步失效，改写为「**何时升级运行与治理能力**」：

| # | 触发条件 | 动作 |
| --- | --- | --- |
| E1 | 单机多容器资源触顶 | 迁多主机 |
| E2 | 容器编排复杂度超 Compose | 引入 k3s / 服务网格 |
| E3 | 服务数量与团队规模上升 | 引入配置中心 / 服务发现 / 契约注册的托管方案 |
| E4 | 跨服务一致性问题频发 | 强化 TM（跨服务强一致）的容量与可观测；长流程编排需求上升时引入工作流引擎（非 Saga） |
| E5 | 合规 / 隔离要求 | 物理隔离部署 |

**通信演进**：现期 REST / JSON + 事件；随内部高频或流式场景增多，**参考 gRPC 并评估自研高性能服务间同步通信**（须与生态——可观测 / 契约 / 服务身份——兼容，按实测收益评估，不阻塞地基）。

**能力替换与服务化的关系**：插件化（进程内能力可替换）继续保留，对冲上游供应链风险；微服务针对**业务域与数据所有权的独立部署**，两者不互斥（边界见《[微服务 · 11 常见误区](../资料/知识档案/微服务/11_微服务_常见误区.md)》）。

## 5. 与现状差异及迁移 <a id="migration"></a>

### 5.1 与现状的差异 <a id="diff"></a>

| 维度 | 现状（阶段一~五） | 目标 |
| --- | --- | --- |
| 部署形态 | 单体进程 + 独立 worker | 多服务多容器、独立发布 |
| 数据 | 平台库 + 租户库 | **每服务数据所有权唯一**（表级归属；物理分库按需、默认同服务同库） |
| 模块边界 | 模块注册 + CI 唯一性校验（进程内） | 服务目录 + 契约 / 版本登记（跨进程） |
| 一致性 | 本地事务为主 | 三段式：本地事务 / 短流程跨服务 TM + XA 强一致 / 长流程工作流状态机；事件读侧 Outbox + 幂等 + 一致性屏障（按 §1.2） |
| 横切 | 进程内基座 | 地基服务 / 能力单元（认证 / 权限 / 审计 / 可观测；**承载按需服务化**） |
| 交付 | 单体一次发布 | 按服务构建、独立发布与回滚 |

### 5.2 迁移方式 <a id="how"></a>

- **保留产出、按服务重组**：阶段一~五的分层、基类、`sys_module`、事件总线、前端模块化保留，重构为分布式，不推倒重来。
- **无「抽取」环节**：因从零分布式，不采用 Strangler Fig 的「包旧系统」路径；但数据落地仍按「先包访问 → 独立库 + 导入同步 → 切权威库」的思路逐步完成（见《[微服务 · 09 渐进式演进](../资料/知识档案/微服务/09_微服务_渐进式演进.md)》「数据拆库三步」）。
- **回退预案**：若拆分不达预期，按「合并关键依赖路径、用模块而非网络分区」回退（DHH 清单），保留插件化与模块化纪律。

## 6. 风险与待实测 <a id="risk"></a>

| # | 风险 / 待实测 | 说明与对策 |
| --- | --- | --- |
| 1 | 运维负载 × 服务数 | 单人兼职下服务数 ×（部署 + 监控 + 日志 + 告警 + 升级）是最大风险；S6 / S7 地基不是可选项 |
| 2 | 租户库爆炸 | 「**按需拆分**的每服务库 × 每租户一库」库数量乘法（默认同服务同库可大幅收敛），须自动化建库 / 迁移；现有 `ops` 批量迁移需重做 |

| 5 | 初始成本 | 实证初始成本 +20%~30%、ROI 2~3 年；须与单人兼职投入权衡 |
| 6 | 基础设施 | 已 8+ 组件，再叠加网关 / 追踪 / 编排，单机资源与认知负载上升 |
| 7 | 边界切错 | 服务边界未验证即固化 → 分布式单体；以限界上下文划分 + 门禁逐阶段校验 |
