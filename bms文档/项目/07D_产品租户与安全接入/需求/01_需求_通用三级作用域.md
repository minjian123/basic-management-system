## 1. 域说明 <a id="intro"></a>

本域把产品的资源归属统一为 `tenant_id / module_key / resource_key` 三级，并补齐注册、解析、校验、上下文与错误码。它是 07D 的核心新增能力：基座已有租户身份与模块注册，但没有把 `module_key` 作为作用域层级，也没有 `resource_key` 的注册与校验。

覆盖范围：作用域模型、作用域注册、解析与校验、作用域上下文、错误码。依据见《[架构设计 · 产品租户与安全接入](../../../设计/架构设计/41_架构设计_子系统_产品租户与安全接入.md)》第 4、5.1 节。

## 2. 需求 01-1：作用域模型与注册 <a id="r01-1"></a>

优先级：2（高）

**背景与动机**：现有基座只有 `tenant_id` + 库键，`module_key` 只是注册要素，`resource_key` 没有模型。产品要做资源级隔离（如消息平台的主题、文件平台的存储桶）时，只能各自定义命名空间，导致无法统一校验、无法判断越界、无法在审计里定位资源。

**内容**（[架构 41 §4](../../../设计/架构设计/41_架构设计_子系统_产品租户与安全接入.md#scope)）：

1. 定义三级作用域的值对象语义：`tenant_id`（雪花内部身份、不可变）、`module_key`（已登记且启用的模块键）、`resource_key`（产品定义、必须注册）。
2. `module_key` 复用模块注册，不新造命名空间概念；`resource_key` 在产品自持声明中登记**类型、命名规则、所属 `module_key`、生命周期**。
3. 作用域注册记录至少包含：产品、`module_key`、`resource_key` 类型、命名规则、状态（启用 / 停用）、版本；注册变更留审计。
4. 注册校验：`module_key` 必须已登记且启用；`resource_key` 类型在产品内唯一、全局不冲突；未登记即拒绝（fail-closed），不做「先跑起来再补登记」。
5. 明确与业务域 / 部署单元的关系：`module_key` 是模块注册键，不等于业务域；`resource_key` 归属 `module_key`，不归属部署单元；拓扑变化不改变三级标识。

**完成标准**：三级模型有唯一权威定义；作用域类型可登记 / 查询 / 停用；未登记或未启用的 `module_key` 被拒；`resource_key` 类型冲突被拒；与架构 41 §4 一致。

**参考文档**：《[架构设计 · 产品租户与安全接入](../../../设计/架构设计/41_架构设计_子系统_产品租户与安全接入.md)》「通用三级作用域」节；《[架构设计 · 模块注册](../../../设计/架构设计/11_架构设计_子系统_模块注册.md)》；《[架构设计 · 产品与服务划分](../../../设计/架构设计/39_架构设计_子系统_产品与服务划分.md)》第 2、4 节。

## 3. 需求 01-2：作用域解析与校验 <a id="r01-2"></a>

优先级：2（高）

**背景与动机**：管理面走 HTTP 中间件、数据面走帧入口、异步消费走任务循环，三条路径如果各自解析，就会出现「管理面看到 A 租户、数据面看到 B 租户」；消息平台的 h2 数据面已经踩过这个风险。作用域解析必须一套口径、三条路径同结论。

**内容**（[架构 41 §4.2 / §5.1](../../../设计/架构设计/41_架构设计_子系统_产品租户与安全接入.md#scope-rules)）：

1. 解析顺序固定：`tenant_id` → `module_key` → `resource_key`；来源与优先级由基座统一，产品不得在入口自行拼装。
2. 管理面复用基座中间件注入的租户上下文；数据面在帧入口复用同一套解析函数；异步路径在每轮或每批入口调用同一守卫。
3. 校验顺序固定：租户可用性 → `module_key` 已登记且启用 → `resource_key` 已注册且归属正确 → 产品自定义规则；前三步由基座统一，产品只追加最后一步。
4. 失败语义：租户不存在 / 已停用、`module_key` 未登记 / 未启用、`resource_key` 未注册 / 越界，分别拒绝并映射到产品登记的错误码；对外不泄露存在性；租户源不可达按 fail-closed 返回 503。
5. 禁止产品自建解析、信任客户端自报头、自建状态缓存覆盖基座判定；数据面不得用连接建立时的租户覆盖后续请求。

**完成标准**：同一请求在管理面、数据面、异步路径解析出同一组三级标识；跨租户、跨 `module_key`、未注册 `resource_key` 被拒；租户停用即时生效；租户源不可达返回 503 不静默放行；代码中无第二套解析实现。

**参考文档**：《[架构设计 · 产品租户与安全接入](../../../设计/架构设计/41_架构设计_子系统_产品租户与安全接入.md)》第 4.2、5.1 节；《[架构设计 · 多租户路由](../../../设计/架构设计/12_架构设计_子系统_多租户路由.md)》「租户解析链」节；消息平台租户接入详细设计的「两个入口、一套解析」口径。

## 4. 需求 01-3：作用域上下文与错误码 <a id="r01-3"></a>

优先级：2（高）

**背景与动机**：作用域解析出来之后，需要在请求、消费、任务之间传递，并保证不可变；同时，租户、模块、资源三层失败要有稳定错误码，管理面与数据面必须同码。缺少统一上下文与错误码，产品会在业务层各自拼响应，审计也无法按作用域定位。

**内容**（[架构 41 §5.1 / §5.4](../../../设计/架构设计/41_架构设计_子系统_产品租户与安全接入.md#ext-scope)）：

1. 定义作用域上下文：`tenant_id`、`module_key`、`resource_key`、产品自定义扩展；上下文不可变，生命周期为请求级或批次级，禁止全局单例持有。
2. 上下文注入：HTTP 依赖、数据面帧上下文、异步守卫返回值三处统一；业务模块只经上下文取作用域，不得再解析。
3. 错误码至少覆盖：租户不存在、租户停用、`module_key` 未登记、`module_key` 未启用、`resource_key` 未注册、`resource_key` 越界；产品码在登记段内，文案键由 i18n 管理。
4. 管理面与数据面同码；错误码映射经 02-2 的统一渲染单点，不在业务层拼装 HTTP 响应。
5. 审计上下文注入：作用域字段进入审计条目，涉及具体记录的操作可带记录级定位字段（见 02-4）。

**完成标准**：三类入口都能取到不可变的作用域上下文；六类错误码逐条有定义并登记；管理面与数据面同码；审计条目带作用域字段；无业务层自行拼装响应的实现。

**参考文档**：《[架构设计 · 产品租户与安全接入](../../../设计/架构设计/41_架构设计_子系统_产品租户与安全接入.md)》第 5.1、5.4 节；《[架构设计 · 接口与集成](../../../设计/架构设计/09_架构设计_接口与集成.md)》错误码节；《[架构设计 · 审计哈希链](../../../设计/架构设计/19_架构设计_子系统_审计哈希链.md)》「审计捕获」节。

## 5. 需求 01-4：租户生命周期与产品资源清理 <a id="r01-4"></a>

优先级：2（高）

**背景与动机**：租户生命周期的权威在基座，但产品手里握着实际资源——消息平台的主题、位点、延迟区与连接，文件平台的存储桶，mdm 的组织与主数据。现有口径只写了「停用即拒绝」，租户删除或归档之后产品资源会变成孤儿；反过来，如果产品自己轮询租户表、自建状态机，又直接违反租户权威红线。需要把「基座发生命周期事件、产品做资源动作」的分工写成固定契约，否则各产品会在删除事件里各写一套、失败后静默丢资源。

**内容**（[架构 41 §4.3 / §7.1](../../../设计/架构设计/41_架构设计_子系统_产品租户与安全接入.md#scope-domain)；[架构 12](../../../设计/架构设计/12_架构设计_子系统_多租户路由.md) 租户生命周期节；[架构 16](../../../设计/架构设计/16_架构设计_子系统_事件总线.md)）：

1. **单一权威**：租户的开通、停用、恢复、删除、归档只由基座决定并落状态；产品只消费 `tenant.*` 事件，不得自建租户状态表、状态机，不得轮询基座租户表反推状态。
2. **事件契约**：至少覆盖 `tenant.created` / `tenant.suspended` / `tenant.activated` / `tenant.deleted`（停用 / 启用沿用已登记的 `suspended` / `activated`，不另立同义事件；归档按需另立）；事件须带 `tenant_id`、`db_key`、变更后状态与版本戳（`sys_tenant.version`）；投递语义为至少一次，产品按「`tenant_id` + 事件类型 + 版本戳」幂等，重复投递不得重复执行。
3. **状态动作固定**：`created` → 产品资源懒初始化（命名空间、默认配额等，失败不阻塞开通）；`disabled` → 拒绝收发（复用基座版本戳，不自建 TTL 缓存）；`enabled` → 恢复受理；`deleted` → 按资源类型生命周期的保留策略归档或物理删除，断开该租户连接、清理延迟区、按保留期处理位点与消息。每个动作必须幂等、可重入。
4. **失败语义**：产品侧清理失败不反向阻塞基座已提交的删除事务；失败进事件重试与死信，必须有日志与指标，**不得静默丢弃**；重试耗尽后进入可运维的死信处置通道。
5. **保留与合规**：资源类型登记时声明保留期（见 01-1）；保留期内的数据只读留存，到期物理删除；审计记录不随资源删除而删除（见 02-4）。
6. **禁止**：产品自建租户生命周期状态机；在删除事件处理器里反向调用基座改租户状态；以「清理失败」为由让租户删除长期挂起；把资源清理做成一次性脚本而无事件驱动与幂等。

**完成标准**：四类生命周期事件可被产品消费并逐条验证动作；重复投递不产生重复副作用；停用拒绝与恢复受理即时生效；删除后资源按声明保留期归档 / 清理且可核对；清理失败可重试、可观测、有死信出口；产品仓库无自建租户状态表或轮询实现。

**参考文档**：《[架构设计 · 产品租户与安全接入](../../../设计/架构设计/41_架构设计_子系统_产品租户与安全接入.md)》第 4.3、7.1 节；《[架构设计 · 多租户路由](../../../设计/架构设计/12_架构设计_子系统_多租户路由.md)》「租户生命周期」节；《[架构设计 · 事件总线](../../../设计/架构设计/16_架构设计_子系统_事件总线.md)》；消息平台需求 05-6。
