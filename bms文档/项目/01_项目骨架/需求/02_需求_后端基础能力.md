## 1. 域说明 <a id="intro"></a>

本域对应阶段一域「后端基础能力」（WBS 02），收窄后覆盖三块（原「异常与错误码骨架」「SQLAlchemy 数据访问底座」已迁入阶段二 后端基座）：

- **配置管理**：config.toml 分区与键清单、`BMS_` 环境变量覆盖、启动校验
- **日志体系**：structlog 结构化输出（dev=console / test·prod=JSON）、上下文字段、脱敏、请求日志中间件
- **健康检查**：`/healthz` 与 `/readyz` 探针契约、依赖检查项、鉴权豁免

**依据**：《[项目规划说明](../../../规划/项目规划说明.md)》「环境与配置」「部署与运维」节、《[后端开发规范](../../../规范/后端开发规范.md)》「目录与分层职责」节、《[日志规范](../../../规范/日志规范.md)》、《[API接口规范](../../../规范/API接口规范.md)》、《[架构设计 · 后端基础类体系](../../../设计/架构设计/33_架构设计_后端基础类体系.md)》。
**目标**：三块基础能力就位，服务可配置化启动、日志结构化可检索、探针可用于编排与门禁。

## 2. 需求 02-1：配置管理 <a id="r02-1"></a>

优先级：2（高）　|　状态：未开始　|　完成日期：—

**背景与动机**：配置若散落在代码与各处环境变量里，三套环境（dev/test/prod）切换与密钥注入会失控；配置须集中声明、分层覆盖、启动即校验，密钥类只走环境变量。

**内容**（《项目规划说明》「环境与配置」节、《后端开发规范》「目录与分层职责」节）：

1. `backend/config.toml` 分区与关键键清单：`[app]`（name / env / debug）、`[server]`（host / port / workers）、`[log]`（level / format / slow_request_ms）、`[database]`（platform / tenants / archive，每库 primary / replicas + 连接池参数）、`[redis]`、`[minio]`（占位）、`[security]`（占位）、`[cors]`；逐项中文注释。本需求只锁定分区清单与每分区关键键，新增普通键由详细设计补充，不回改本需求。
2. 环境分层：`BMS_ENV` 指定 `dev` / `test` / `prod`（未设置时默认 `dev`，取非法值启动失败）。
3. `BMS_` 前缀环境变量覆盖机制（12-factor）：部署时用环境变量覆盖敏感项（DB URL、密钥），不落配置文件；嵌套键用双层下划线映射嵌套路径，如 `[database].platform.url` → `BMS_DATABASE__PLATFORM__URL`（pydantic-settings 标准形态，命名见《命名规范》「基础设施命名」节）。
4. 启动加载与校验：`app/core/config.py` 以 pydantic-settings 建模、lifespan 内加载；必填缺失、类型/取值非法、出现未知或拼错的分区/键一律启动即报错并指出键名；密钥类配置不入库、不入镜像、不写日志。
5. 环境变量模板：新增 `backend/.env.example`，列出全部 `BMS_` 应用键与占位示例值；基础设施凭据（库 root 口令、令牌等）仍只留在 `deploy/.env`，两者不混。

**完成标准**：`BMS_ENV=dev|test|prod` 三套环境按分层覆盖正确加载（未设置时默认 `dev`）；`BMS_DATABASE__PLATFORM__URL` 注入后覆盖生效；缺必填键、类型/取值非法、`BMS_ENV` 取非法值、未知/拼错键四类情形均启动失败并指出键名；三环境差异处（日志级别、CORS）加载结果正确；密钥类配置不出现在 `config.toml`、`.env.example` 与日志中。单测覆盖加载 / 覆盖 / 校验失败路径，覆盖率随全局门禁，用例同步 Kiwi（若已部署）。

**参考文档**：《项目规划说明》「环境与配置」节、《后端开发规范》「目录与分层职责」节、《命名规范》「基础设施命名」节

## 3. 需求 02-2：日志体系 <a id="r02-2"></a>

优先级：2（高）　|　状态：未开始　|　完成日期：—

**背景与动机**：无结构化日志与请求上下文，跨实例排障与审计关联无从下手；`request_id`/`trace_id` 须贯穿请求链路，敏感字段须脱敏。

**内容**（《[日志规范](../../../规范/日志规范.md)》、《后端开发规范》「目录与分层职责」节）：

1. structlog 输出，字段口径遵循《日志规范》「日志格式」节；渲染形态由 `[log] format` 单开关控制：`dev` 为 console 可读渲染，`test`/`prod` 强制单行 JSON；日志只写 stdout，不落文件。
2. 上下文字段由中间件注入：`request_id`（兜底）、`trace_id`（入站读 `X-Trace-Id`、缺失生成 UUID4，并一律回写响应头 `X-Trace-Id`）、`tenant`（阶段二租户解析接入后启用）、`user_id`/`user`（阶段四认证接入后启用）、`client_ip`、`duration_ms`。
3. 脱敏：密码/令牌/凭据等敏感字段统一脱敏，禁写日志；清单口径见《日志规范》「脱敏要求」节。
4. 请求日志中间件：记录方法/路径/状态码/耗时；探针（`/healthz`、`/readyz`）与文档路径（`/docs`、`/redoc`、`/openapi.json`）排除在请求日志之外（不记 INFO 或仅 DEBUG），避免编排高频轮询刷爆日志。
5. 慢请求分级：阈值走 `[log] slow_request_ms`（`dev` 严、`prod` 松），超阈值请求记 WARNING；依赖异常分级（阶段六前以 warning 兜底不告警）。

**完成标准**：`test`/`prod` 下日志为单行 JSON 且含上下文字段（`dev` 为 console 渲染）；`X-Trace-Id: abc` 请求日志 `trace_id` 为 `abc` 且响应头回写同名值，缺失时生成 UUID4 并回写；密码/token/验证码/连接串密码等敏感字段全量日志无明文；请求日志中间件对业务路由生效，探针与 `/docs` 路径不产生 INFO 行；未捕获异常 ERROR 行堆栈单行、响应不回显堆栈；超 `[log] slow_request_ms` 的请求记 WARNING。单测覆盖上下文字段注入、脱敏与探针路径排除，覆盖率随全局门禁，用例同步 Kiwi（若已部署）。

**参考文档**：《日志规范》、《后端开发规范》「目录与分层职责」节、《架构设计 · 可观测性》相关节

## 4. 需求 02-3：健康检查 <a id="r02-3"></a>

优先级：2（高）　|　状态：未开始　|　完成日期：—

**背景与动机**：编排与 CI 门禁需要可判定的存活与就绪探针；探针须与依赖状态挂钩，且不泄露连接串等敏感信息。

**内容**（《项目规划说明》「部署与运维」「基础设施编排」节、《[API接口规范](../../../规范/API接口规范.md)》）：

1. `/healthz`：GET，进程存活即 200，响应 `{"status": "ok"}`（`status` 取值域 `{ok}`），不触碰 DB/Redis；用于存活判定，不随依赖状态变化。
2. `/readyz`：GET，依赖检查——全部就绪 200 / 任一不可达 503，顶层 `status ∈ {ok, down}`；`checks` 为动态键（接入哪个依赖就出现哪个键），每项 `{ok: bool, error: str|null}`，`ok=false` 时 `error` 只写异常类名（如 `ConnectError`），不暴露连接串/堆栈/SQL。
3. 检查项与启用阶段：`redis`（阶段一，`PING`）；`database`（阶段二数据访问底座落地后启用，平台库 `SELECT 1`）；`minio`（阶段六文件管理接入后启用）。未接入前该项从 `checks` 中省略，不做「未接入即失败」判定。
4. 执行与超时：各检查项并发执行，单项超时 2 秒、整体总超时 5 秒；编排侧 `timeoutSeconds` 建议 ≥5s。
5. 启动状态：lifespan 启动初始化未完成期间 `/readyz` 一律返回 503（`status: "down"`），避免编排把尚在初始化的实例接入流量。
6. 鉴权豁免：两探针不在 Bearer 校验范围（与登录/刷新同列豁免清单），不受认证中间件干扰。
7. 路由注册：`app/api/health.py` 独立 APIRouter 统一 include；不计限流（阶段四排除清单预留）。

**完成标准**：本地起服务后两探针均 200 且响应体结构正确（`/healthz` 为 `{status:"ok"}`；`/readyz` 顶层 `status="ok"` 且 `checks.redis={ok:true,error:null}`）；停 Redis 后 `/readyz` 503 且顶层 `status="down"`、`checks.redis.ok=false`、`error` 为异常类名，`/healthz` 保持 200；`error` 与响应体无密码/连接串/堆栈信息；`database` 检查项在阶段二数据访问底座就位后启用并验证（停平台库 → `/readyz` 503 且 `checks.database.ok=false`），`minio` 随阶段六接入。单测覆盖两探针 200/503 两态与 `checks` 结构，覆盖率随全局门禁，用例同步 Kiwi（若已部署）。

**参考文档**：《项目规划说明》「部署与运维」「API 设计规范」「基础设施编排」节、《API接口规范》「URL 与资源设计」「统一响应」节

> 注：本需求由原 02-4 重编为 02-3；因数据访问底座迁入阶段二，`database` 检查项在本阶段以「未接入则省略」实现，随阶段二数据访问底座落地后启用。

> 注：两探针**豁免《API接口规范》「统一响应」节**的 `{code, message, data}` 包裹，直接返回裸结构（编排按裸字段判定）；HTTP 状态码保留传输层语义（就绪 200 / 未就绪 503），不套用「业务失败统一 200」约定。
