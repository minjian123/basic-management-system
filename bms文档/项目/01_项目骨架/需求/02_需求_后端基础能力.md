## 1. 域说明 <a id="intro"></a>

本域对应阶段一域「后端基础能力」（WBS 02），收窄后覆盖三块（原「异常与错误码骨架」「SQLAlchemy 数据访问底座」已迁入阶段二 后端基座）：

- **配置管理**：config.toml 分区与键清单、`BMS_` 环境变量覆盖、启动校验
- **日志体系**：structlog 结构化 JSON、上下文字段、脱敏、请求日志中间件
- **健康检查**：`/healthz` 与 `/readyz` 探针契约、依赖检查项、鉴权豁免

**依据**：《[项目规划说明](../../../规划/项目规划说明.md)》「环境与配置」「部署与运维」节、《[后端开发规范](../../../规范/后端开发规范.md)》「目录与分层职责」节、《[日志规范](../../../规范/日志规范.md)》、《[API接口规范](../../../规范/API接口规范.md)》、《[架构设计 · 后端基础类体系](../../../设计/架构设计/33_架构设计_后端基础类体系.md)》。
**目标**：三块基础能力就位，服务可配置化启动、日志结构化可检索、探针可用于编排与门禁。

## 2. 需求 02-1：配置管理 <a id="r02-1"></a>

优先级：2（高）　|　状态：未开始　|　完成日期：—

**背景与动机**：配置若散落在代码与各处环境变量里，三套环境（dev/test/prod）切换与密钥注入会失控；配置须集中声明、分层覆盖、启动即校验，密钥类只走环境变量。

**内容**（《项目规划说明》「环境与配置」节、《后端开发规范》「目录与分层职责」节）：

1. `backend/config.toml` 分区与键清单（app / db / redis / minio / log 等），逐项注释说明；`BMS_ENV` 指定环境分层。
2. `BMS_` 前缀环境变量覆盖机制（12-factor）：部署时用环境变量覆盖敏感项（DB URL、密钥），不落配置文件。
3. 启动加载与校验：缺键/非法值启动即报错；密钥类配置不入库、不入镜像、不写日志。

**完成标准**：三套环境按 `BMS_ENV` 正确加载；环境变量覆盖生效；缺键/非法值启动报错；密钥类配置不出现在配置文件与日志中。

**参考文档**：《项目规划说明》「环境与配置」节、《后端开发规范》「目录与分层职责」节、《命名规范》「配置命名」相关节

## 3. 需求 02-2：日志体系 <a id="r02-2"></a>

优先级：2（高）　|　状态：未开始　|　完成日期：—

**背景与动机**：无结构化日志与请求上下文，跨实例排障与审计关联无从下手；`request_id`/`trace_id` 须贯穿请求链路，敏感字段须脱敏。

**内容**（《[日志规范](../../../规范/日志规范.md)》、《后端开发规范》「目录与分层职责」节）：

1. structlog 结构化 JSON 输出，字段口径遵循《日志规范》「日志格式」节。
2. 上下文字段由中间件注入：`request_id`（兜底）、`trace_id`（入站读 `X-Trace-Id`、缺失生成 UUID4）、`tenant`（阶段二租户解析接入后启用）、`user_id`/`user`（阶段四认证接入后启用）、`client_ip`、`duration_ms`。
3. 脱敏：密码/令牌/凭据等敏感字段统一脱敏，禁写日志。
4. 请求日志中间件：记录方法/路径/状态码/耗时；慢查询与依赖异常分级（阶段六前以 warning 兜底不告警）。

**完成标准**：日志为结构化 JSON 且含上下文字段；`X-Trace-Id` 透传与生成正确；敏感字段已脱敏；请求日志中间件对全部路由生效。

**参考文档**：《日志规范》、《后端开发规范》「目录与分层职责」节、《架构设计 · 可观测性》相关节

## 4. 需求 02-3：健康检查 <a id="r02-3"></a>

优先级：2（高）　|　状态：未开始　|　完成日期：—

**背景与动机**：编排与 CI 门禁需要可判定的存活与就绪探针；探针须与依赖状态挂钩，且不泄露连接串等敏感信息。**范围调整**：本需求由原 02-4 重编为 02-3；因数据访问底座迁入阶段二，`database` 检查项在本阶段以「未接入则省略」实现，随阶段二数据访问底座落地后启用。

**内容**（《项目规划说明》「部署与运维」「基础设施编排」节、《[API接口规范](../../../规范/API接口规范.md)》）：

1. `/healthz`：GET，进程存活即 200，响应 `{"status": "ok"}`，不触碰 DB/Redis。
2. `/readyz`：GET，依赖检查——全部就绪 200 / 任一不可达 503；响应体 `{status, checks: {redis: {ok, error}}}`；`database`（平台库 `SELECT 1`）与 `minio` 检查项在依赖接入后补充（阶段二 / 后续阶段）；每项超时 2 秒；`error` 仅写异常类别，不暴露连接串/堆栈。
3. 鉴权豁免：两探针不在 Bearer 校验范围（与登录/刷新同列豁免清单）。
4. 路由注册：`app/api/health.py` 独立 APIRouter 统一 include；不计限流（阶段四排除清单预留）。

**完成标准**：本地起服务后两探针均 200 且响应体结构正确；停 Redis 后 /readyz 503 且 `checks.redis.ok=false`、/healthz 保持 200；响应体无密码/连接串信息；`database` 检查项在阶段二数据访问底座就位后启用并验证。

**参考文档**：《项目规划说明》「部署与运维」「API 设计规范」「基础设施编排」节、《API接口规范》「URL 与资源设计」节
