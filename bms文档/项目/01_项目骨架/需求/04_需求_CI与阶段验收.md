## 1. 域说明 <a id="intro"></a>

本域对应阶段一「CI 流水线激活与阶段验收」，覆盖四块：流水线激活（冒烟层 / 重验证层 / exists 守卫 / 覆盖率门禁 / CI 基础镜像）、三库集成与流水线收口（**接口占位**）、M1 验收门禁核对、阶段测试报告与 README。原「后端基座」域的三库集成 / 门禁核对 / 测试报告三条需求并入本域（后端基座并入阶段一后，验收口径统一为 M1）。

**依据**：《[总体项目规划](../../../规划/总体项目规划.md)》「监控与报告」节「里程碑」节（M1）、《[开发部署规划](../../../规划/开发部署规划.md)》「开发工作流与 CI」节、《[测试规范](../../../规范/测试规范.md)》、《[架构设计 · 测试与质量](../../../设计/架构设计/29_架构设计_测试与质量.md)》。

**目标**：含代码改动的 main 推送自动跑冒烟层且全绿；重验证层就绪项全绿；覆盖率低于阈值即红；M1 门禁（骨架三项 + 基座六项）有可复现证据；阶段测试报告与 README 收口。

## 2. 需求 04-1：CI 流水线激活 <a id="r04-1"></a>

优先级：2（高）　|　状态：进行中　|　完成日期：—

**背景与动机**：流水线框架已在准备期落地但空载；阶段一代码落地后必须以真实代码激活，门禁才有意义——否则覆盖率、构建、健康检查等无自动校验，后续阶段的「CI 通过」完成标准无据可依。

**内容**（《开发部署规划》「开发工作流与 CI」节、《测试规范》）：

1. 激活口径（单人开发期直推 main 不走 MR）：`.gitlab-ci.yml` 既有 job 以 exists 守卫——`backend/` 存在跑 Python 系、`frontend/` 存在跑前端系；纯业务文档推送免 CI，基座文档改动（`bms文档/规范`、`资料`、`资源`、`基座文档清单.md`）触发 `base-integrity`
2. main 冒烟层：gate-smoke + base-integrity（基座路径改动时）+ ruff check + pyright + pytest（SQLite）+ ESLint + Vitest + 双端构建；任一步失败 pipeline 红
3. CI 基础镜像：`deploy/ci/Dockerfile.backend`（python3.14 + uv + 预建 backend venv）与 `deploy/ci/Dockerfile.frontend`（node22 + 双工程 node_modules 预装），按锁文件哈希写 label；`ci-base-build` 自动重建
4. 重验证层（仅 main）：Playwright E2E、三库集成测试、镜像构建推 Registry、Trivy 扫描（CVSS ≥ 9 阻断，外网不可达暂缓）、swagger.json 契约快照、Allure 归档导入 Kiwi TCMS；以激活开关守卫，逐项修复就绪后开启
5. 覆盖率门禁：pytest-cov（骨架期整体按 ≥ 70% 起步）与前端 Vitest coverage 接入，低于阈值 pipeline 红

**完成标准**：含代码改动的 main 推送自动跑冒烟层且全绿；重验证层就绪项全绿（Trivy 暂缓项按暂缓口径标注）；覆盖率报告产出且低于阈值时 pipeline 红；纯业务文档推送不触发 CI，基座文档改动触发 `base-integrity` 且通过。

**参考文档**：《总体项目规划》「监控与报告」节、《开发部署规划》「开发工作流与 CI」节、《测试规范》「覆盖率要求」节

## 3. 需求 04-2：三库集成与流水线收口（接口占位） <a id="r04-2"></a>

优先级：2（高）　|　状态：未开始　|　完成日期：—

**背景与动机**：开发与单测用 SQLite，生产支持 MySQL / PostgreSQL / 达梦 DM8，方言差异只有真库集成测试能暴露；数据访问底座（独立需求域）本阶段只落**接口占位**，故三库集成在本阶段以**占位与流程就绪**收口，真实跑通随首个落库阶段。

**内容**（《测试规范》、《开发部署规划》「开发工作流与 CI」节）：

1. `bms_test` 前缀测试库流程**脚本占位**：建库 → 迁移 → 集成用例 → 删库清理（job 内独立、互不污染），本阶段以 `--dry-run` 输出固定库清单，不真实建库
2. 拓扑路由用例骨架：租户库路由、跨租户隔离、批量迁移正确性的用例文件与断言位就位（对占位实现断言固定数据）
3. 重验证层三库集成 job 以 `deploy/ci/verify-enabled` 开关继续守卫（本阶段不激活真库 job），流水线文档标注激活条件
4. 达梦方言口径（软删除复合唯一索引、迁移脚本、schema 前缀）登记为后续实测项，不通过按《项目规划说明》「数据库兼容」节口径调整并修订对应需求

**完成标准**：测试库流程脚本与用例骨架就位、`--dry-run` 输出固定库清单、开关守卫口径明确；三库真库集成为后续阶段待办项且已在计划登记；`pytest`、`ruff`、`pyright` 全绿。**不连真库**（实现期要点：MySQL / PostgreSQL / 达梦三库迁移与集成用例全绿随后续落库阶段）。

**参考文档**：《测试规范》「三库方言测试」节、《开发部署规划》「开发工作流与 CI」节、《数据库开发规范》

## 4. 需求 04-3：M1 验收门禁核对 <a id="r04-3"></a>

优先级：2（高）　|　状态：未开始　|　完成日期：—

**背景与动机**：里程碑必须有可复现证据留痕（命令 / 日志 / 流水线链接），否则「骨架 + 基座可用」无法对外证明，也无法判断能否进入下一阶段（前端组件库阶段）。

**内容**：

1. 逐项核对 **M1 门禁**——骨架三项（本地起服务 / `/healthz` `/readyz` 正常 / CI 流水线激活通过）与基座五项（继承链基座就位 / 异常体系生效 / 配置·安全·日志基座占位就位 / 跨阶段基座登记齐备 / 机制底座占位——数据访问底座·多租户拓扑·模块注册表 **（占位口径标注）**），每项给出核对命令与证据索引
2. 核对结论回写阶段一需求总览「M1 验收门禁」表（达标 / 不达标 + 证据索引）；本阶段 29 条需求状态与完成日期同步更新
3. 文档收口：阶段一需求 / 任务 / 计划文档全部更新为终态（已完成 + 完成日期 + 结论记录）

**完成标准**：门禁表结论全部落文档且均有证据索引（占位项明确标注口径与后续阶段待办）；29 条需求状态与完成日期回写完毕；阶段一文档全部终态收口；评审结论落档。

**参考文档**：《总体项目规划》「里程碑」节 M1 行、《项目管理规范》「状态与工时」节

## 5. 需求 04-4：测试报告与 README <a id="r04-4"></a>

优先级：2（高）　|　状态：未开始　|　完成日期：—

**背景与动机**：阶段末需有测试汇总与现状一致的 README，作为进度与问题的正式沟通产物；报告数据由 CI 采集，减少人工统计成本。

**内容**：

1. 阶段末测试报告（`bms文档/项目/01_项目骨架/测试报告_阶段一.md`，四章节固定）：用例执行统计（pytest / Vitest / Playwright 用例数与通过率，CI 数据脚本汇总 + AI 初稿 + 人工补充结论）；缺陷统计（本阶段 GitLab Issue 列表与状态，`defect-auto` 标注）；覆盖率（后端行 / 分支覆盖 vs 门禁阈值）；风险与遗留项（跨阶段基座回补窗口与机制类占位待办逐条登记）
2. README 更新（根 + 三工程）：快速启动命令与现状一致；目录结构同步；文档导航补阶段一链接
3. 报告初稿由脚本采集 + AI 汇总生成，第二 AI 交叉审核后提交给人处理异常项（见《项目规划说明》「治理机制的落地方式」节）

**完成标准**：测试报告四章节齐备且数据来自 CI 采集；README 与现状一致；遗留项（跨阶段基座回补窗口、机制类占位实现）逐条登记。
