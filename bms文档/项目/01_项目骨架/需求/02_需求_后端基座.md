## 1. 域说明 <a id="intro"></a>

本域对应阶段一「后端基座」，是**后端全部模块的前置地基**——基座体系先立，认证 / RBAC / 通用能力等模块才有统一写法。按《[架构设计 · 后端基础类体系](../../../设计/架构设计/33_架构设计_后端基础类体系.md)》「基座分层」组织为四个子域，共 16 条需求：

| 子域 | 需求 | 本阶段口径 |
| --- | --- | --- |
| 01 根基类与集合体系 | `02-1` | 工程骨架已交付，本域**登记核对** |
| 02 四层基类（业务对接基类层） | `02-2` ~ `02-12` | 四层基类**落地**；与业务对接的最下层基类（数据访问 / 三库声明 / 平台库表 / 租户上下文 / 引擎注册 / 批量迁移入口 / 模块注册与查询）**接口占位** |
| 03 core 横切基座 | `02-13` ~ `02-15` | 异常体系与统一响应**落地**；配置 / 安全 / 日志基座**结构占位** |
| 04 跨阶段基座 | `02-16` | 六类基座**登记 + 回补窗口** |

**「接口占位」口径（本阶段统一约定）**：只落**接口 / 抽象声明 + 占位实现**——依赖注入可解析、应用可启动不报错、占位返回**固定或批量数据**以便上层先跑通链路；**不连真库、不跑迁移、不建表**；实现要点保留在本域需求中，随对应后续阶段填实现（不需重新立项）。

**依据**：《[总体项目规划](../../../规划/总体项目规划.md)》「工作分解结构（WBS）」节「里程碑」节（M1）、《[项目规划说明](../../../规划/项目规划说明.md)》「开发计划与验收标准」节、《[架构设计 · 后端基础类体系](../../../设计/架构设计/33_架构设计_后端基础类体系.md)》「基座分层」节「阶段落地（地基波 + 回补）」节、《[后端开发规范](../../../规范/后端开发规范.md)》「后端基座体系」节、《[API接口规范](../../../规范/API接口规范.md)》、《[数据库开发规范](../../../规范/数据库开发规范.md)》。

**目标**：基座体系架构建成——基类分层与继承关系就位、异常体系与统一响应生效、与业务对接的最下层基类接口齐备（占位可跑）、跨阶段基座登记齐备；M1 门禁「异常体系生效」为本域直接承载。

**边界说明**：

- 基座对**配置**只提供统一入口的方法与结构（占位实现，不真实读取），真实 `config.toml` 读取与启动校验由「[03 后端基础能力](03_需求_后端基础能力.md)」配置管理落地——基座先于依赖它的能力。
- 机制类（数据访问 / 三库 / 租户 / 迁移 / 模块注册）本阶段只做占位，真实落库与多租户数据拓扑随后续阶段（首个落库模块）填实现。
- 认证与会话安全基座的**具体实现**、RBAC 数据范围**规则**、真实分片与缓存三防加固、事件与任务**业务实现**归对应后续阶段。

## 2. 需求 02-1：根基类与集合体系登记 <a id="r02-1"></a>

优先级：2（高）　|　状态：未开始　|　完成日期：—

**背景与动机**：`BaseObject` 与集合体系（有序 / 进程内并发 / 跨副本 Redis）是全部后端类的根与公共能力落点，已于工程骨架交付但**未在架构登记**（设计目录零提及），后续模块不知继承什么、公共能力加在哪，口径必然发散。

**内容**（《架构设计 · 后端基础类体系》「基类清单与继承链」节「有序与并发集合」节）：

1. 根基类 `BaseObject`（`app/core/base.py`）：`to_dict` / `to_json` / `__str__` / `__repr__` / `__eq__` / `__hash__`——公共方法唯一落点，登记职责与继承链
2. 集合体系：有序集合（`BaseSorted` → `SortedList` / `SortedDict` / `SortedSet`）、进程内并发集合（`BaseConcurrentSorted` → `ConcurrentSorted*` 四种锁策略）、跨副本 Redis 封装（Lua 复合操作）——登记职责、继承关系与代码位置
3. 登记回写：《架构设计 · 后端基础类体系》与《后端开发规范》保持同源；标注「模块类不得重复实现基类公共方法」的强制约定

**完成标准**：基座分层图与基类清单（L0 + 集合体系）在架构节点与规范一致、无缺项；各基类职责 / 继承关系 / 代码位置可核对；继承约定纳入规范且可核对。

**参考文档**：《架构设计 · 后端基础类体系》「基类清单与继承链」节「有序与并发集合」节、《后端开发规范》「后端基座体系」节

## 3. 需求 02-2：仓储 / 服务 / 请求响应基类 <a id="r02-2"></a>

优先级：2（高）　|　状态：未开始　|　完成日期：—

**背景与动机**：四层基类中承上启下的三套基类（数据访问 / 业务逻辑 / 请求响应）是模块类的直接父类；工程骨架已交付同步内存基线，须在基座阶段定型（含数据库实现占位），否则各模块各自实现 CRUD 与序列化。

**内容**（《架构设计 · 后端基础类体系》「各层基类与模块约定」节、《后端开发规范》「后端基座体系」节）：

1. `BaseRepository[T]`：通用 CRUD 模板方法（`_build` / `_apply`）+ `exists` / `count` 派生方法；数据库实现**占位**（不连库）；数据源 / 分片路由钩子预留
2. `BaseService[T]`：通用 CRUD 委派仓储 + 统一不存在语义（`NotFoundError` → `BizError` 体系）
3. `BaseSchema`：Pydantic 公共配置（`from_attributes` / `str_strip_whitespace`）与统一序列化（继承 `BaseObject`）
4. 继承约定收口：模块类必须继承对应基类、只写差异部分

**完成标准**：三套基类可继承、`exists` / `count` 与不存在语义行为正确（基类单测通过）；数据库实现为占位且不连库；`pytest`、`ruff`、`pyright` 全绿。

**参考文档**：《架构设计 · 后端基础类体系》「基类清单与继承链」节「各层基类与模块约定」节、《后端开发规范》「后端基座体系」节

## 4. 需求 02-3：模型基类与表规范 <a id="r02-3"></a>

优先级：2（高）　|　状态：未开始　|　完成日期：—

**背景与动机**：全库表结构与字段行为（雪花 ID / 审计 / 软删除 / 乐观锁 / 四库类型映射）在此一次定义；不先立，几十张表建完再补基类字段将全量返工。

**内容**（《架构设计 · 数据架构》「数据规范」节、《数据库开发规范》第 2/3 节）：

1. `app/models/base.py` 的 `BaseModel` 字段（每表必备，ORM 层定义一次）：
   - 主键 `id`：雪花 ID（yitter/IdGenerator，BIGINT 跨库类型），生成器封装于 `app/core/id.py`（`generate_id()`）
   - 审计：`created_at` / `created_by` / `updated_at` / `updated_by`——由 ORM 事件自动填充（insert/update 监听），业务代码禁止手动赋值
   - 软删除：`deleted_at`（NULL=未删）；乐观锁：`version`（更新时比对，冲突返回明确错误码）
2. 四库类型映射表（基类字段跨方言实现，写入模型定义注释）：

   | 字段 | SQLite | MySQL | PostgreSQL | 达梦 DM8 |
   | --- | --- | --- | --- | --- |
   | id | INTEGER | BIGINT | BIGINT | BIGINT（自增列口径，雪花值写入） |
   | created_at 等 | DATETIME | DATETIME | TIMESTAMP | TIMESTAMP |
   | version | INTEGER | INT | INTEGER | INT |
   | 布尔（通用约定） | INTEGER 0/1 | TINYINT(1) | SMALLINT | SMALLINT（达梦无 BOOLEAN 时口径） |

   - 时间统一 UTC 存储，前端本地时区展示；金额 NUMERIC(20,4)、字符串 VARCHAR（长度显式）、禁用方言专用类型（JSON / ENUM / SERIAL）
3. 软删除机制：查询默认过滤 `deleted_at IS NULL`（repository 基类统一注入）；唯一约束统一建为 `(唯一字段, deleted_at)` 复合唯一索引；删除写时间戳释放唯一键、恢复清 NULL
4. 索引与表级规范：排序 / 逻辑外键 / 数据权限过滤字段必须建索引，命名 `idx_字段` / `uq_字段`，每表索引不超过 5 个；表名单数 snake_case、平台域前缀 `sys_`/`wf_`/`rpt_`/`ai_`、每表与字段 COMMENT 必填

**完成标准**：`BaseModel` 字段与四库类型映射定义落地、表规范写入模型注释；**建表与四库迁移验证按接口占位处理**（不连真库、不跑迁移），随后续阶段实测审计自动填充、软删除复合唯一与乐观锁冲突。

**参考文档**：《架构设计 · 数据架构》「数据规范」节、《数据库开发规范》第 2/3/4 节、《命名规范》「数据库命名」节

## 5. 需求 02-4：数据访问接口占位 <a id="r02-4"></a>

优先级：2（高）　|　状态：未开始　|　完成日期：—

**背景与动机**：数据库接入与异步化必须集中在基类一次完成，否则每个模块各自实现异步会话，事务边界与连接预算失控；本阶段先落**接口与占位实现**，把与业务对接的数据访问边界定下来。

**内容**（《架构设计 · 数据访问与分片》、《后端开发规范》「SQL 与数据访问规范」节「异步与并发」节）：

1. 异步引擎工厂接口：按数据源创建 / 缓存 `AsyncEngine` 的签名（连接池参数、超时、`pool_pre_ping`），**占位实现不真实建连**
2. AsyncSession 工厂接口：`async_sessionmaker` 形态与请求级会话依赖注入签名；事务边界约定（`with session.begin()`）；禁止异步会话跨请求共享
3. 四库方言接口：MySQL（aiomysql）/ PostgreSQL（psycopg 3）/ 达梦 DM8（dmPython，同步驱动经 `asyncio.to_thread` 封装例外口径）/ SQLite（aiosqlite）；URL 取值经配置基座读取接口
4. 基类异步切换：`BaseRepository[T]` / `BaseService[T]` 异步签名与分页 / 软删除过滤回填基类（只加基类，模块类不改）；同步内存基线保留为测试替身
5. 读写分离占位：读写路由接口（按上下文标记选引擎），本阶段主从同源

**完成标准**：数据访问接口 / 抽象声明就位、依赖注入可解析、应用可启动不报错、占位返回固定 / 批量数据可支撑上层链路；基类异步签名一致；`pytest`、`ruff`、`pyright` 全绿。**不连真库、不跑迁移**（实现期要点：四库连通与集成用例随后续落库阶段）。

**参考文档**：《架构设计 · 数据访问与分片》、《后端开发规范》「异步与并发」节、《数据库开发规范》「迁移」节

## 6. 需求 02-5：三库拓扑与建库接口占位 <a id="r02-5"></a>

优先级：2（高）　|　状态：未开始　|　完成日期：—

**背景与动机**：多租户隔离是本系统核心约束（一租户一库）；库模型 / 命名 / 字符集 / 跨库规则先以**声明与占位**定死，后续建库与迁移才不各写各的。

**内容**（《架构设计 · 数据架构》「数据分布」节、《命名规范》「数据库命名」节）：

1. 三库模型**声明**：平台库 `bms_platform`（租户注册、平台统一菜单 / 权限码）、租户库 `bms_tenant_{code}`（一租户一库，`code` 全小写）、归档库 `bms_archive`（归档数据统一收存，只读，通用能力阶段起用）
2. 开发环境库模拟声明：多 SQLite 文件（`bms_platform.db` / `bms_tenant_demo.db` / `bms_archive.db`）一文件一库；环境库命名 `bms_dev` / `bms_test` / `bms_prod`
3. 建库标准（字符集 MySQL utf8mb4、PostgreSQL UTF8、达梦 UTF8；达梦 schema 前缀与小写标识符口径）写入声明与注释
4. 跨库引用原则：一律逻辑外键（code），不建物理外键；跨库查询禁止 JOIN

**完成标准**：三库模型声明与建库标准在代码 / 文档登记齐备、依赖注入可解析、应用可启动；`pytest`、`ruff`、`pyright` 全绿。**不真实建库**（实现期要点：三库实例建库与字符集核对随后续阶段）。

**参考文档**：《架构设计 · 数据架构》「数据分布」节、《命名规范》「数据库命名」节、《数据库开发规范》「多租户与分片」节

## 8. 需求 02-7：租户解析中间件接口占位 <a id="r02-7"></a>

优先级：2（高）　|　状态：未开始　|　完成日期：—

**背景与动机**：请求必须能确定「数据落哪个租户库」；本阶段先把解析链与 `TenantContext` 接口立起来（占位 tenant），后续阶段填真实解析与隔离。

**内容**（《架构设计 · 多租户路由》「租户解析链」节、《项目规划说明》「环境与配置」节）：

1. 解析链**接口**（按优先级取第一个命中）：子域名 → 请求头 `X-Tenant-ID` → token 内 tenant_id（认证阶段接入）；本阶段以固定 demo 租户占位
2. `TenantContext`（`app/core/tenant.py`）声明：tenant_code / db_key / 引擎引用构造与依赖注入签名；**禁止全局单例持有租户引擎 / 上下文**
3. 中间件行为声明：未知租户 → `HTTP 404 + 业务码 80001`（8xxxx 租户段）；租户上下文注入日志 `tenant` 字段（与需求 03-2 联动）

**完成标准**：解析链与 `TenantContext` 接口就位、占位实现按 `X-Tenant-ID` / 缺省返回 demo 上下文（批量请求返回固定 tenant）、应用可启动不报错、豁免路径不受影响；`pytest`、`ruff`、`pyright` 全绿。**不连平台库**（实现期要点：真实解析与并发隔离随后续阶段）。

**参考文档**：《架构设计 · 多租户路由》「租户解析链」节、《项目规划说明》「环境与配置」节、《API接口规范》「错误码」节

## 9. 需求 02-8：引擎注册表与池管理接口占位 <a id="r02-8"></a>

优先级：2（高）　|　状态：未开始　|　完成日期：—

**背景与动机**：租户库按需建连接、不管理池会拖垮数据库；本阶段先落 `EngineRegistry` 接口与连接预算校验入口，避免后续各自实现。
