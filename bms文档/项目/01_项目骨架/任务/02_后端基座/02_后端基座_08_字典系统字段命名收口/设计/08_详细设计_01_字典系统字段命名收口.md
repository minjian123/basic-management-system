## 1. 目的与范围 <a id="purpose"></a>

把字典侧**列名**对齐《[数据库开发规范](../../../../../../规范/数据库开发规范.md)》「系统字段」节 §3.1.3 的字典清单（规范 §3.1.4 收口项），使「基础系统字段 + 表单 + 字典」三处口径在数据库层一致。

- **范围内**：`sys_dict_type.type` → `code`、`sys_dict_item.label` → `name`、`sys_dict_item.type_id` / `sys_dict_attr.type_id` → `dict_type_id`；含 ORM 属性、索引名与唯一约束列、迁移、表文件与相关设计文档。
- **范围外**：**API 契约字段名与前端字段名保持不变**（契约仍为 `type` / `label` / `type_id`，见决策记录 2）；字典 i18n 附表的承载列 `label` / `name` 维持现状（规范允许「既有历史命名以登记为准」）；通用能力（系统字段驱动的清单）另册登记。

## 2. 口径与依据 <a id="basis"></a>

- 规范 §3.1.3：字典类型 = `code` / `name` / `status` / `sort`；字典条目 = `code` / `name` / `status` / `sort` / `parent_id`（+ 主表 ID）。
- 规范 §3.1.1：明细「主表 ID」口径 = `{主表}_id` ⇒ 引用 `sys_dict_type` 的外键列为 `dict_type_id`（与 `sys_dict_type_i18n.dict_type_id` / `sys_dict_item_i18n.dict_item_id` 同形态）。
- 规范 §3.1.4 收口项（本任务逐项落地）；02_07 已完成 `parent_id` 改 `BIGINT` 自引用 `id`。

## 3. 改名映射 <a id="mapping"></a>

| 表 | 旧列名 | 新列名 | 类型 / 可空 | 同步项 |
| --- | --- | --- | --- | --- |
| `sys_dict_type` | `type` | `code` | 不变（`VARCHAR(64)` / 否） | 唯一约束 `uq_dict_type_code_deleted_at` 列改 `(code, deleted_at)` |
| `sys_dict_item` | `label` | `name` | 不变（`VARCHAR(128)` / 否） | 索引 `idx_dict_item_label` → **`idx_dict_item_name`**（`(dict_type_id, name)`） |
| `sys_dict_item` | `type_id` | `dict_type_id` | 不变（`BIGINT` / 否） | 唯一约束列改 `(dict_type_id, code, deleted_at)`；索引 `idx_dict_item_value` / `idx_dict_item_parent_sort` 列跟随；`index=True` 生成索引 `idx_sys_dict_item_type_id` → **`idx_sys_dict_item_dict_type_id`** |
| `sys_dict_attr` | `type_id` | `dict_type_id` | 不变（`BIGINT` / 否） | 唯一约束列改 `(dict_type_id, attr_key, deleted_at)`；索引 `idx_dict_attr_sort` 列跟随、`idx_sys_dict_attr_type_id` → **`idx_sys_dict_attr_dict_type_id`** |

**纯改名**：不改类型与可空性、不动数据、无数据回填（与 02_07 的「先数据后改型」不同）。

## 4. 迁移设计 <a id="migration"></a>

`alembic/versions/platform/tenant/0011_dict_field_names.py`（`Revises: 0010_dict_item_parent_id_bigint`）：

1. **执行序**：先 `drop_index` 两个待改名索引（旧列名）→ `batch_alter_table` 改列名（`alter_column(new_column_name=...)`）→ `create_index` 新名索引。
2. **四库兼容**：一律经 `batch_alter_table`（SQLite 重建表；MySQL 8 / PostgreSQL / 达梦按方言生成 `RENAME COLUMN`），不写方言 SQL、不用方言专用类型；复合索引与唯一约束列随列改名自动跟随（约束均为具名约束）。
3. **`downgrade`**：列名与索引名回退（对称实现）。
4. **缓存影响**：缓存 key 由**类型码取值**（`dict_key(tenant, locale, dict_type)`）拼装，类型码取值不变 ⇒ **key 不变、无需缓存版本 bump**；ORM 属性改名不改变快照结构。

## 8. 决策记录 <a id="decisions"></a>

1. **只改列名与 ORM 属性**：规范 §3.1 是**数据库开发规范**，其口径对象是列名；改名范围收敛在 DB / ORM 层（含索引与约束），不扩散到跨端。
2. **API 契约字段名保持**（`type` / `label` / `type_id`）：契约字段属《API接口规范》与《命名规范》范畴（`label` 与 `value` 成对是选项语义惯例），且改契约会牵动前端与 `api-types`（`DictItem.label` / `DictTypePayload.type` 等），收益低、风险高；**列名与契约字段名的映射由表文件与本节登记**。
3. **`sys_dict_attr.type_id` 一并改**：与 `sys_dict_item.type_id` 同属「主表 ID」口径，避免留一处不一致（规范 §3.1.4 只登记了条目表，本任务按同口径一并收口）。
4. **i18n 附表列名不动**：规范 §3.1.3 只约束主表清单；附表承载列 `label` / `name` 依《数据规范》「按表文件声明」保留，避免连带改 i18n 链路与种子。
5. **无数据回填**：纯改名，列取值不变；缓存 key 与快照结构不变，无需版本 bump。
