## 2. 任务内容 <a id="content"></a>

1. `/healthz`：GET，进程存活即 200，响应 `{"status": "ok"}`（`status` 取值域 `{ok}`），不触碰 DB / Redis，不随依赖状态变化
2. `/readyz`：GET，依赖检查——全部就绪 200 / 任一不可达 503，顶层 `status ∈ {ok, down}`；`checks` 为动态键（接入哪个依赖出现哪个键），每项 `{ok: bool, error: str\|null}`，`ok=false` 时 `error` 只写异常类名，不暴露连接串 / 堆栈 / SQL
3. 检查项与启用阶段：`redis`（阶段一，`PING`）、`database`（数据访问底座真实实现后启用，平台库 `SELECT 1`）、`minio`（文件管理接入后启用）；未接入前该项从 `checks` 省略，不做「未接入即失败」判定
4. 执行与超时：各检查项并发执行，单项超时 2 秒、整体总超时 5 秒；编排侧 `timeoutSeconds` 建议 ≥ 5s
5. 启动状态：lifespan 初始化未完成期间 `/readyz` 一律返回 503（`status: "down"`），避免编排接入尚在初始化的实例
6. 鉴权豁免：两探针不在 Bearer 校验范围（与登录 / 刷新同列豁免清单）；`app/api/health.py` 独立 APIRouter 统一 include，不计限流
7. 聚合与注册表复用 02-3-12 交付的 `BaseHealthCheck` / `BaseHealthCheckRegistry`（依赖标识取 `DEPENDENCIES`），本任务只落真实探针路由与检查项

## 3. 完成标准 <a id="accept"></a>

本地起服务后两探针均 200 且响应体结构正确（`/healthz` 为 `{status:"ok"}`；`/readyz` 顶层 `status="ok"` 且 `checks.redis={ok:true,error:null}`）；停 Redis 后 `/readyz` 503 且顶层 `status="down"`、`checks.redis.ok=false`、`error` 为异常类名，`/healthz` 保持 200；`error` 与响应体无密码 / 连接串 / 堆栈信息；`database` 检查项在数据访问底座真实实现后启用并验证（停平台库 → `/readyz` 503 且 `checks.database.ok=false`），`minio` 随文件管理接入。单测覆盖两探针 200 / 503 两态与 `checks` 结构，覆盖率随全局门禁，用例同步 Kiwi。
