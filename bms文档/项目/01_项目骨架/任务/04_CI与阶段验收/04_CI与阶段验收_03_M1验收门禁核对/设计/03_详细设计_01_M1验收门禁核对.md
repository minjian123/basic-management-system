### 4.2 证据采集口径 <a id="collect"></a>

- **只记事实**：命令、输出摘要、时间戳、版本按实测记录；禁止编造与「应该能过」式推断（《任务文档规范》§5 口径）。
- **不入私密信息**：Redis 连接串、账号、内网地址一律以「取 `deploy/.env` 现值」表述，不写入文档。
- **不复制长日志**：流水线以「id + 状态 + job 清单」为证据，日志正文留 GitLab；命令输出只留关键行。
- **可复现优先**：每项给出可粘贴执行的命令；环境差异（端口占用、依赖可达性）用配置覆盖而非改环境。

## 5. 一致性核对脚本设计 <a id="script"></a>

### 5.1 定位与形态 <a id="script-form"></a>

| 项 | 取值 |
| --- | --- |
| 路径 | `scripts/tools/check-docs/check-status.py` |
| 依赖 | Python 3.14 标准库（无第三方依赖，可在 CI `python:3.14-slim` 内直跑） |
| 调用 | `python3 scripts/tools/check-docs/check-status.py [--stage 01_项目骨架] [--root .] [--strict] [--all]`（默认只核对阶段一；`--all` 含历史阶段，准备期为早期口径仅作人工参考） |
| 输出 | 逐条 `[硬]` / `[软]` 行 + 汇总（检查项 / 通过 / 不合规）+ 退出码（硬规则不合规 → 1，否则 0） |

### 5.2 检查项与规则 <a id="rules"></a>

**硬规则（默认阻断）**——只覆盖**结构性约束**（任何时点都必须成立）：

| # | 规则 |
| --- | --- |
| H1 | 需求编号集合一致：域文档章节编号 = 总览总清单编号，无缺漏 / 重复；编号格式 `{域两位}-{序号}` |
| H2 | 状态取值合法（未开始 / 进行中 / 部分完成 / 已完成 / 搁置） |
| H3 | 已完成 ⇒ 完成日期为 `YYYY-MM-DD`；非已完成 ⇒ 完成日期为 `—` |
| H4 | 需求元信息行（状态 / 完成日期）与总览总清单表**逐行一致**（同一编号两处） |
| H5 | 任务文档「对应需求」指向的需求存在；任务已完成 ⇒ 对应需求已完成（不出现「任务完成而需求未完成」） |
| H6 | 计划已完成任务表与剩余排期表**编号互斥**；编号与任务文档编号一致 |
| H7 | 工时三处可对齐（任务信息表工时 = 计划表工时，重估以计划为准并须一致） |
| H8 | 排期窗口格式合法（区间 / 单日 / 搁置，区间分隔符固定 ` ~ `） |

**软提示（默认告警，`--strict` 时阻断）**——覆盖**统计与叙述类**（在途阶段可暂不一致）：

| # | 规则 |
| --- | --- |
| S1 | 统计数字与明细一致（如计划头部「已完成 N 项，剩余 M 项」、§1 工时合计、域地图「x / y 已完成」） |
| S2 | 甘特图节点与剩余排期表条目一致 |
| S3 | 已完成任务的留痕记录齐备（任务目录 `实施/` 存在；父任务可由嵌套子任务目录承担） |

### 5.3 落点与 CI 接入 <a id="ci-hook"></a>

- `scripts/README.md` 工具链清单新增一行 `tools/check-docs/`（文档状态一致性核对）。
- `.gitlab-ci.yml` 的 **`base-integrity` job** 在 `check-base.py` 之后追加一行执行本脚本（默认非 `--strict`）。
- **不新增 job、不新增触发面**：`base-integrity` 既有守卫（`bms文档/规范`、`资料`、`资源`、`基座文档清单.md`）不变，避免与 04-1 完成标准「纯业务文档推送不触发 CI（不建流水线）」冲突。

## 8. 交叉审核设计 <a id="review"></a>

单人开发期不设评审会（需求 04-3 完成标准），以「第二 AI 独立复核」替代：

```mermaid
flowchart LR
    A[核对采集与回写] --> B[check-status.py 硬规则 0 不合规]
    B --> C[第二 AI 独立复核<br/>10 项逐项挑战]
    C --> D{有异常项?}
    D -- 有 --> E[人工处理<br/>当场修 or 登记去向]
    D -- 无 --> F[留痕]
    E --> F
    F --> G[实施记录 §4 / §6]
```

**复核要点**（第二 AI 逐项挑战，不看结论只看证据）：① 命令是否可复现（可粘贴执行）；② 证据是否**直接**支撑结论（不靠推断）；③ 占位项是否标注口径与后续阶段待办；④ 状态回写在需求 / 任务 / 计划三处是否一致；⑤ 是否写入私密信息。

**留痕**：复核结论与人工异常项处理按《任务文档规范》§5 固定章节记入 04-3 实施记录——处理过程记 [§4 问题与处置](../实施/03_实施_01_M1验收门禁核对.md#issues)，未闭环项记 [§6 偏差与遗留](../实施/03_实施_01_M1验收门禁核对.md#deviations)（**不新增固定章节**）。

## 13. 风险与开放项 <a id="risk"></a>

| 风险 / 开放项 | 说明 | 处置 |
| --- | --- | --- |
| 本地依赖可达性影响探针核对 | 就绪 200 需 Redis / 平台库可达；本地默认 `redis://localhost:6379/0` 未必有服务 | 以 `BMS_REDIS__URL` 指向可达实例取 200；以不可达端口取 503（**不启停 mjbk 常驻服务**） |
| 起服务端口冲突 | 8000 / 5173 / 5174 可能被占用 | 核对前确认端口空闲；后端可用 `--port` 临时换端口（探针命令同步调整） |
| 第 6 项核对手法 | 初稿以「未匹配路由」探测统一响应，实测该路径由框架默认处理（`{"detail":"Not Found"}`），不属统一响应口径 | 改用业务异常路径 `/api/v1/demos/{不存在 id}` → `code=10002`（对齐 02-9 既有口径），并核对临时 404 处理器无残留（[§4.1](#points) 第 6 项） |
| 脚本硬规则误伤在途文档 | 阶段进行中状态不一致属常态 | 硬规则只覆盖结构约束（H1 ~ H8）；统计类为软提示，仅收口时用 `--strict` |
| `base-integrity` 追加核对后变红 | 基座文档推送时若状态不一致即红 | 收口后三处已一致，风险低；紧急时以「先修文档」处置，不回退接入 |
| 私密信息外泄 | Redis 连接串 / 账号 / 内网地址 | 文档一律写「取 `deploy/.env` 现值」，不落具体值（[§4.2](#collect)） |
| 证据链断点 | 流水线过旧或记录缺失导致某项无证据 | 以本任务推送后的新流水线补齐；仍缺则记「不达标（附去向）」而非放宽结论 |
