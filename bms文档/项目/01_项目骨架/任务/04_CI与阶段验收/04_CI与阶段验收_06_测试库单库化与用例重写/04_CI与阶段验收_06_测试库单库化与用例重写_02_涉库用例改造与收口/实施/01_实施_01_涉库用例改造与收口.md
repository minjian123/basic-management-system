### 2.4 批 2 试探与顺序修正 <a id="batch2-probe"></a>

批 2 开箱先试了「套件级切换」：把 `services/platform/tests/conftest.py` 的 `platform_db_url` 改为共享库薄壳，并把 `tests_support/permission_admin.setup_min_tenant` 改为指向共享租户库。结果：

- 单文件抽样通过（`account_lock`、`health`、`api/test_role_api` 等 24 例）；
- 但**多文件同跑互相污染**：`icon/test_icon_registry.py` 4 例失败——该文件用固定图标码（`purchase_order` / `receipt`）并断言「清单为空 / 重复即 10003」，共享库叠加后前序文件的数据成了「他人数据」，正是需求要消灭的「假设空库」写法。

**结论（顺序修正）**：批 2~4 改为 **先逐文件改造（ns 限定 / 回滚会话 / 精确断言改语义），最后再切套件夹具**——与设计 §5 写的「先接线共享夹具、再改目录」相反。原因：套件级切换会一次性把「假设空库」的用例全部暴露为互相污染，失败面过大且难定位；逐文件改造每步都可回归。已按此把两处改动撤回（主分支保持绿），设计 §5 的批次内节奏按本条执行。

**同步补的基座能力**（本轮已交付）：准备集是异步的，而异步夹具（`pytest_asyncio` 的 `async def` 夹具）里不能再 `asyncio.run`，故新增——
- `ensure_shared_db_async`：协程准备集直接 `await`；同步回调退化为同步实现（避免嵌套事件循环）；缺省建库走 `_default_prepare_async`；
- `tests_support/shared_db.prepare_platform_async` / `prepare_tenant_async`：准备集的异步入口；
- 共享库引擎夹具 `shared_platform_engine` / `shared_tenant_engine`（用例直连共享库时不再自建引擎）。

覆盖率：`bms_core/testing/fixtures.py` **100%**（行 + 分支），`testing` 套件 97 passed。

#### 2.10.1 服务子 job 并发建表撞 `table ... already exists`（6 个服务）

| job | 服务 | 现象 |
| --- | --- | --- |
| 11148 | file | `table sys_file_part already exists`（135 passed 后 2 errors） |
| 11151 | notification | `table sys_job_error already exists`（1 failed / 1 error；`test_dependency_provider_resolves` 同因） |
| 11154 / 11157 / 11160 / 11166 | search / tenant / ai / report | 同 `sys_job_error already exists`（各 1~2 failed + 1 error） |

**根因**：`MetaData.create_all(checkfirst=True)` 的存在性判断查的是**已提交**的库目录，看不到他人尚未提交的
建表事务。单库叠加后多 worker 共用一份 SQLite，两个 worker 同时首次建同一张表时双方 `has_table` 都为假
→ 都发 `CREATE TABLE` → 后提交方收到 `already exists`。这不是锁等待问题（`busy_timeout` 兜不住），
而是「查」与「建」之间的 TOCTOU 窗口。

**为什么不在用例侧逐处改**：用例侧 `create_all` 有 80+ 处（fixture 补表 / 临时库建表 / 种子准备），
逐处换实现改不完也易漏；**DDL 本身就该串行**，统一挂钩最稳。

**处置**：

| 落点 | 内容 |
| --- | --- |
| `bms_core/testing/locks.py`（新增） | 把 `file_lock` 从 `tests_support/locks.py` **上移到基座**（产品仓与基座测试共用同一把锁，两处实现会「互相看不见」）；`tests_support/locks.py` 转为薄壳 re-export |
| `bms_core/testing/ddl.py`（新增） | `serialize_ddl()` 幂等包装 `MetaData.create_all`：取目标库 `database` 路径的 SHA-1 前 12 位作锁名（`ddl-<digest>`），**同一库文件**跨进程互斥、不同临时库互不阻塞；内存库 / 非 SQLite 不取锁 |
| `bms_core/testing/plugin.py` | `pytest_configure` 里 `ddl.serialize_ddl()` 安装（所有加载测试基座的路径自动生效，含 9 个服务子工程 addopts） |

**验收**：清空共享库后 `notification + search + ai + report` 四套件合跑 `-n 12` 3 轮 → **每轮 92 passed**，
无 `already exists`；file 套件 `-n 6` → **137 passed / 4 skipped**。

#### 2.10.4 接口层 ID 类型审计（按「内部数值、接口字符串」规范全仓检查）

**规范口径**：内部（ORM 列 / 领域实体 / 仓储与服务签名）一律 `int`；只在接口层做字符串与数值转换。
`SnowflakeIdStr = Annotated[int, PlainSerializer(str, return_type=str, when_used="json")]` 即该规范的实现——
校验按 `int` 收（lax 模式接受数字字符串），`model_dump()` 保持 `int`，仅 JSON 输出转 `str`。

**审计发现的系统性缺口**：运行期兜底 `stringify_ids` 与文档侧 `_stringified_value_schema` 共用的判定是
`is_id_key()`，只认 `id` 与 `*_id` 结尾，于是两类字段掉在规范外：

| 缺口 | 后果 |
| --- | --- |
| `*_ids`（复数，如 `menu_ids` / `role_ids`） | `"menu_ids".endswith("_id")` 为假 → 文档标 `integer`、前端生成 `number[]`、运行期输出数字，长 ID 丢精度 |
| `*_by`（如 `locked_by` / `granted_by`） | 同上（已由 `7ba9da2e1` 显式标 `SnowflakeIdStr` 修掉） |

**另一类不一致**：`id` / `*_id` 被 `_stringified_value_schema` 在**文档**里声明为 `string`，但运行期只有显式
`SnowflakeIdStr` 才真转字符串——未标注的字段属于「文档说 string、实际输出 number」，契约与实现长期不符。

**修正（21 处，均属接口层）**：

| 类别 | 位置 | 改法 |
| --- | --- | --- |
| 请求/响应 ID 集合 | `menu_ids`（`menu_form`，含同文件 `list[str]` 与 `list[int]` 并存的不一致）、`role_ids`、`user_ids`、`post_ids`、`dept_ids`、`business_ids`、`action_ids` | `ConcurrentStableList[int]` / `[str]` → `ConcurrentStableList[SnowflakeIdStr]` |
| 响应主键 | `sso.tenant_id`、`outbox.tenant_id`、`release.id`、`tenant_topology.tenant_id` | `int` / `str` → `SnowflakeIdStr` |
| 手工字符串化（删除） | `identity` sso 绑定清单的 `str(row.tenant_id)`；`menu_form` 服务的 `str(item)` 生成式；端点 `_menu_id_strings()` 辅助函数（唯一作用就是转字符串） | 直接传 `int`，交给 JSON 边界转换 |
| 内部对象（不动） | `role/dto.py`、`platform_registry/dto.py`、全部 ORM 列 | 保持 `int` |

**两处刻意不改**（标识字段，值域不保证是数字）：

- `IconResponse.id`：`IconInfo` 的占位实现用 `null:{code}` 前缀键充当 id；
- `TenantSummaryResponse.id`：`TenantSummary` 的占位实现用租户编码（`demo`）充当 id。

二者若改 `SnowflakeIdStr` 会在占位实现上直接校验失败，故保持 `str` 并在 `description` 写明「占位实现以…充当」。

**实测（改后，直接构造契约对象）**：

```text
IconResponse(id=1234567890123456789)          → JSON "1234567890123456789"，内部 int
TenantSummaryResponse(id=1001)                → JSON "1001"，内部 int
RoleAssignmentsRequest(user_ids=["123","456"])→ 内部 [123, 456] int，回显 JSON ["123","456"]
```

**连带产物**：`deploy/contracts/platform.json` 1 行（`role_ids.items`：`integer` → `string`）、
前端 `api_types/src/platform.ts` 同 1 行；其余字段因文档侧本已声明 string，快照零漂移。

**验收**：全仓 pyright **0 error**；开发环 **1375 passed / 188 文件**；前端 vitest 887 + 15 + 25 + 24 passed。

> 教训：ID 字符串化不能只靠「兜底函数」——兜底按字段名匹配，命名一变（`_id` → `_ids`、`*_by`）就漏；
> 接口字段必须**显式**标 `SnowflakeIdStr`，兜底只作安全网。同理，文档侧的类型改写不能替代运行期转换，
> 两者必须由同一处显式声明驱动。

### 2.11 identity 会话撤销并发冲突（CI #1441 / #1451 / #1461 唯一残留红） <a id="session-revoke-race"></a>

**现象**：`identity` 子流水线 `service-test` 每次稳定挂 1 例，均为 `tests/auth/test_login.py` 里登录断言拿到
**409**：

| 轮次 | 失败用例 | 断言 |
| --- | --- | --- |
| CI #1451 | `test_login_rate_limited` | `assert 409 == 200` |
| CI #1461 | 同上 | 同上 |
| 本地 `-n auto` 第 4 轮 | `test_login_continuous_failure_forces_captcha` | 同上（携带有效验证码的登录被拒） |

修复前本地 `-n auto` 复现率约 1/4，加 `print` 调试后反而 8 轮不复现（打印改变时序）——这类 flake 不能靠
「重跑就过」，也不能靠打印观察。

**定位链**（CI job 日志，`aiosqlite` DEBUG 段）：

```text
SELECT sys_session.session_id, ... WHERE sys_session.session_id = ?     -- 查到会话
UPDATE sys_session SET revoked_at=?, updated_at=?, version=?
  WHERE sys_session.id = ? AND sys_session.version = ?                  -- 参数 version=1
rollback                                                                -- 影响 0 行
POST /api/v1/auth/login → 409（duration 214ms）
```

**根因**（不是用例写法问题，是并发写路径）：

1. `SessionIssuer.issue` 在登录成功后调用 `SessionService.enforce_max_active(user_id, max_active=...)`，
   按**用户维度**扫 `sys_session` 未撤销未过期会话，超限则逐个 `revoke`（置 `revoked_at`）；
2. `revoke` 原实现是「先 `get` 判 `revoked_at is None`，再走 ORM `update`」——`update` 内部
   `flush` 带版本条件，`StaleDataError` 经 `_guard_version` 转译成 `ConcurrentConflictError`（409）；
3. 单库叠加后，`sys_session` 里 `admin` 的会话行**跨用例可见**（改造前每用例独立库看不到），
   多 worker 同时登录 `admin` → 同时超限 → 同时撤销**同一批行** → 后到者版本对不上 → 409。

**修法**（`services/identity/src/bms_identity/domains/auth/repositories/session.py`）：`revoke` 改为
**条件置位更新**——

```sql
UPDATE sys_session SET revoked_at=?, updated_at=?, version=version+1
 WHERE id=? AND revoked_at IS NULL
```

并发撤销同一条会话时后到者影响 0 行，即「已被他人撤销」，与函数自身的**幂等**契约一致；不再走 ORM 版本
判定，也就不会把正常并发冒成 409。Core 语句不触发 ORM 事件，更新后补 `refresh(item)` 让同会话对象与
落库值一致（否则同事务内再读仍是旧属性）。

**为什么不选「捕获 `ConcurrentConflictError` 视为成功」**：`StaleDataError` 之后事务已被污染，
吞异常会让外层 `uow.begin()` 整体回滚，把本次已经撤销成功的其它会话一并回滚掉。

**验收**：修复前 `-n auto` 4 轮 1 次复现；修复后 **10 轮全绿（10/10）**；`test_session_repo` 的
「已撤销不被二次覆盖」语义保持（`revoked_at` 非空时不更新）。

**顺带**：`test_login.py` 两处登录断言补上 `resp.text` 消息——失败时直接带出 `code` / `message`，
不必再靠临时打印（打印会改变时序，让 flake 隐身）。

## 5. 问题与处置 <a id="issues"></a>

| # | 现象 | 原因 | 处置 |
| --- | --- | --- | --- |
| 1 | 护栏把 `tests_support/shared_db.py` 判成「用例自建库」 | 增量模式对清单内任意 `.py` 判定，而全量模式只扫 `test_*.py`——两种模式判据不一致 | 增量模式收敛到同一命名判据；并给共享基座加配置项 `base_modules`（模块粒度、可审计，替代文件级 exclude 清单） |
| 2 | 模块级 `pytestmark = [pytest.mark.own_db("…")]` 未被识别为白名单 | 判定只看装饰器列表 | engkit 增 `_pytestmark_reason`（含 `AnnAssign` 形式与理由缺失判定），并补自检向量与分支用例 |
| 3 | 新用例被「集合声明」护栏判红（`list` / `dict` / 同构 `tuple`） | 该护栏对测试文件同样生效 | 测试内集合改用 `ConcurrentStableList` / `ConcurrentStableDict`；查询结果行也走 `ConcurrentStableList` |
| 4 | 整目录跑 `testing/` 时共享平台库偶发「no such table」 | `test_db_dir()` 按当前 cwd 解析，会话级夹具在某个已 `chdir` 的用例上下文里解析时会把库落到临时目录，后续用例连到另一个路径 | 本轮先用「工程根暴露准备集夹具」保证准备内容与首例顺序无关；`test_db_dir` 钉工程根作为遗留项（§6-1） |
| 5 | `测试改动内容` 的 pyright 步骤报 `No module named pyright` | devloop 用系统 Python 调 `-m pyright`，该解释器未装 pyright（`uv run pyright` 正常） | 环境问题，不改仓配置；本轮 pyright 以 `uv run pyright --project backend <改动文件>` 单独复核（0 errors） |
| 6 | `bms/backend/.coverage` 被卫生护栏判为散落产物 | 本地 `--cov` 直接跑 pytest 时默认落 cwd | 删除该文件；覆盖率采集统一走 `engkit.toml` 的 `[coverage].data_file`（`.cache/coverage/`） |
