## 3. 实施过程 <a id="process"></a>

### 3.1 ID 口径定案（实测驱动）

- 复现 JS 精度问题：`{"id": 1800000000000000123}` 解析为 `…000`，末位丢失（按此 id 查/改/删会错行）；
- Node 22 微基准：number 与 string 在 Map.set/get、严格相等、JSON.parse 上无显著差异（排序 1e5 才差 0.6ms）；
- 定案 **A：数据库 BIGINT 与 JOIN/索引不变；仅 JSON 边界与前端用 string**（出参 `str(id)`、入参 `int(id)`）；
- 登记：02-3 任务（序列化口径）、03-2 任务（字段注记）、需求 01-4 第 6 条。

### 3.2 四类基础件（双端）

- `api/types.ts`：新增 `BaseEntity`（id string、createdAt/updatedAt）与 `BasePageQuery`；
- `api/base.ts`：`BaseApi` 基类（get/post/put/delete 拼 `basePath` 并复用 `request<T>`）；因 TS6 `erasableSyntaxOnly` 禁用参数属性，采用显式字段 + 构造赋值；
- `stores/base.ts`：`createCrudStore` 工厂（list/total/loading + fetchList/fetchOne/create/update/remove），以组合式函数实现「BaseStore」能力；
- `utils/serialize.ts`：`stableStringify`（对象键排序、Set/Map 确定序、BigInt→字符串、Date→ISO）；
- frontend 实现后同款复制到 frontend-mobile（基线一致）。

### 3.3 规范与测试

- 《前端开发规范》§2 增补「基础类与继承约定（强制）」5 条；
- 双端 `tests/base.spec.ts`：BaseApi 四种方法、createCrudStore 全动作、stableStringify 边界；用例扩充后覆盖率从 91.8% 提升至 **100%**。

## 4. 问题与处置 <a id="issues"></a>

| # | 问题 / 现象 | 原因 | 处置 | 落点 |
| --- | --- | --- | --- | --- |
| 1 | `TS1294：参数属性在 erasableSyntaxOnly 下不允许` | TS6 禁非可擦语法 | 改为显式字段 + 构造函数赋值 | `api/base.ts` |
| 2 | number 型 id 丢精度（…123→…000） | JS IEEE 754 double 上限 2^53−1 | 定案 A（BIGINT + 字符串传输），实测性能无差异 | 设计 §4、02-3/03-2 |

## 6. 偏差与遗留 <a id="deviations"></a>

- 53-bit 雪花方案未采用（用户定案 A），ID 容量与后端 BIGINT 口径不变。
- `createCrudStore` 不含服务端排序/筛选拼装等模块级扩展（由业务 Query 类型与模块 API 承担）。
- 前端覆盖率门禁（全量 `src/**` + 阈值）随 05-1 流水线门禁任务接入。
- 业务模块 API/Store 随阶段二按本基线派生。
