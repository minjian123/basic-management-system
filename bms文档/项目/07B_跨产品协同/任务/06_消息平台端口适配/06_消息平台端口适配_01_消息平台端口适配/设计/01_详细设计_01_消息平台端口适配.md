[文档首页](../../../../../../文档首页.md) › [01 协议链上移与消息平台端口适配](../06_消息平台端口适配_01_消息平台端口适配.md) › 设计

## 1. 目标与边界 <a id="scope"></a>

**目标**：切断「msg → bms-core」与「bms 适配 → msg」的仓级循环依赖，把消息平台的**帧协议 + 远程调用客户端 + 错误语义 + 幂等重试**整条链上移到 `bms_core` 新增能力域 `msgclient/`，使每个继承 `bms-core` 的产品仓**天生附带消息客户端**（无需额外部署、无需跨仓装配）；随后在 `bms_core` 内实现 `BaseServiceClient` / `EventPublisher` 的 msg 版适配与 `provider` 切换，业务代码零改动。

**范围内**：

1. 依赖方向与循环依赖的根治方案（`bms_core/msgclient`）；
2. 逐文件「上移 / 切割 / 留仓」清单与判据；
3. 基座侧命名、登记、产品字面量通用化与契约快照归口；
4. msg 仓本地副本退役与两仓回归口径；
5. `provider` 键名与切换粒度、装配与拒启语义；
6. 错误码 / 超时 / trace / 租户映射表；
7. 回滚窗口三态处置与演练步骤；
8. 实施步骤与归口、测试设计、覆盖率与门禁口径、风险与开放项。

**范围外**：bms 端口契约改造（`BaseServiceClient` / `EventPublisher` / `ServiceCallPolicy` 形状不变）、产品业务迁移（8B_08）、事务消息与 outbox relay 替换（8B_04）、多实例选主与失败摘除（04-6 / 8B_05）、多语言 SDK（8B_03 后续）、按方法灰度切换（开放项）。

**本文档不落实现代码**：立项阶段只定稿设计；代码由「协议链上移」前置子任务与后续适配实施执行（§7）。

## 2. 现状与依赖事实 <a id="current"></a>

### 2.1 依赖图（核过源码）

```text
现状：
  msg/backend/services/msg  ──路径依赖──▶  bms-core（bms 仓）+ engkit
  bms 单仓 CI 只 clone bms，镜像与构建都拿不到 msg 包
  04-1 详细设计只写「保证 bms_msg.client 可被 04-5 import」，未给跨仓方案

若 bms 适配层直接 import bms_msg.client：
  bms ──▶ msg ──▶ bms-core（同属 bms 仓）  ⇒ 仓级循环 + CI 断链
```

实测「只搬 `client/`」也**不能**断环：`bms_msg/client/` 还引用 `bms_msg` 自己的 `protocol/frame.py`、`errors.py`、`core/config.py`（远程调用常量）、`rpc/deadline.py`、`rpc/naming.py`、`rpc/registry.py::RpcReply`；这些模块又依赖 `bms_core`。因此真正要上移的是**整条协议链**，而非单个包。

### 2.2 架构红线（不可回退）

| 红线 | 出处 | 对本设计的约束 |
| --- | --- | --- |
| 禁止服务间直接引用彼此内部实现、禁止反向依赖 | 架构 38 §8 | `bms_core` 不得出现任何 `bms_msg` 符号 |
| 产品标识不入基座 | 架构 38 §8、`05_01` 零命中硬门禁 | 帧常量改通用语义名；业务异常与数据面常量留 msg 仓 |
| 通用能力归位基座、天然下发各产品仓 | 架构 38 §8「通用能力的归位」、架构 39 §2「通用能力不属于任何业务域」 | 依赖恒为「产品 → 基座」；不新建部署单元、不新增能力声明 |
| 能力目录权威只在提供方仓库、消费方不得依赖提供方实现 | 架构 38 §2 / §7 | 协议实现唯一，不写第二份 |
| 只准上层依赖下层 | 《AI开发规范》架构铁律 | 依赖方向恒为「产品 → 基座」 |
| 服务间调用必须走基座 | 《后端开发规范》 | 适配层落在 `bms_core` 插件体系内，不另造装配路径 |

### 2.3 既有可复用契约（本次不改）

| 契约 | 位置 | 复用方式 |
| --- | --- | --- |
| `BaseServiceClient.call(ServiceRequest)` / `ServiceResponse` | `bms_core/servicecall/base.py` | 适配实现继承 / 实现之，形状不变 |
| `EventPublisher.publish()` / `publish_transactional()` | `bms_core/events/base.py` | 同上 |
| `ServiceCallPolicy`（max_retries / retry_backoff / timeout / circuit_breaker / rate_limit / retry_statuses） | `bms_core/servicecall/base.py` | 韧性字段映射到 04-4 的 `RetryPolicy` |
| `BaseCircuitBreaker` / `CircuitState` / `service_dependency()` | `bms_core/circuit/base.py` | 04-4 三态实现已继承该契约 |
| `IdempotencyStore`（begin / load / save）与 `build_idempotency_key` | `bms_core/idempotency/base.py` | 幂等键与去重语义沿用 |
| `PluginSelection` + `resolve_plugin` | `bms_core` 插件装配 | `provider` 取值切换，不新增配置节 |
| `HttpServiceClient` / `NullCircuitBreaker` 等既有实现 | `servicecall/` / `circuit/` | 回滚目标与缺省占位 |

### 2.4 04-4 已交付的协议能力（上移对象）

`ErrorCategory` 五类 + `classify()` 三元组、`Outcome` 三值、`RetryPolicy`（2 次 / 100ms / ×2 / 封顶 2s + full jitter）、`RetryBudget`（帧头 + `ContextVar`）、幂等键与进程内去重、熔断三态、`Retry-After` 双来源；帧头 `idempotency_key` / `retry_budget` / `deadline_ms`，错误帧 `category` / `retryable` / `layer`。流式 `RpcStream` 与一元 `RpcClient` 同链上移，但**流式错误重试仍归后续阶段**，本任务不改变该归口。

## 3. 目标设计 <a id="design"></a>

### 3.1 依赖方向：协议链上移 bms-core <a id="direction"></a>

上移后依赖图：

```text
  bms-core（含 msgclient/）         ← 唯一协议实现
      ▲                    ▲
      │                    │
  msg 仓服务端           其余产品仓 / bms 适配层
（删本地客户端副本）     （直接 from bms_core.msgclient import …）
```

- `bms_core` 不引用 `bms_msg`；msg 仓删除本地副本后统一引用基座。
- 环被切断，`bms` 单仓 CI 只 clone bms 即可完成导入、静态与测试。
- 协议**只有一份实现**：不存在「基座一份、msg 一份」的漂移面，也不存在额外部署单元。
- 各产品仓因路径依赖 `bms-core` 而**天生附带客户端**，接入成本退化为「配 `provider` + 给实例地址」。

**否决过的方案**（决策留痕）：抽独立 `msg-protocol` 包会把协议实现劈成两份；纯端口 + 部署期注入会让 04-4 韧性能力在端口层重表达且仍要定注册协议；适配层放 msg 仓会让 bms 服务反向加载产品仓插件；只登记架构缺口则依赖实质未闭合。

### 3.2 上移清单（逐文件核过） <a id="uplift"></a>

**A 类 · 整体上移**（无产品业务语义，纯协议 / 客户端）

| 模块 | 行数 | 依赖面 |
| --- | --- | --- |
| `client/` 全 10 文件（`__init__` / `rpc` / `stream` / `retry` / `circuit` / `transport/` 5 件） | **3129** | 只依赖 `bms_core`（circuit / core / servicecall）+ 下表 B/C 类；`transport/` 只依赖 client 内部 + `h2` |
| `protocol/frame.py` + `codec.py` | 298 + 76 | 只依赖 `bms_core`（concurrent / serialization）+ 帧非法异常 |
| `protocol/payload.py` | 230 | 同上（**须随上移**，否则 codec 断链） |
| `rpc/deadline.py` / `naming.py` | 143 / 32 | 只依赖 `bms_core`（exceptions / roots）+ 常量 |
| `rpc/registry.py` 中 `RpcCall` / `RpcReply` | 2 个值对象 | 只依赖 `bms_core`（concurrent / roots） |
| `core/config.py` 的 `RPC_*` 常量段 | 约 27 个 | 纯常量，无依赖 |

**B 类 · 切一刀上移**（`errors.py` 512 行混着业务异常，不能整体搬）

| 上移 | 留 msg 仓 |
| --- | --- |
| `ErrorCategory` / `Outcome` 两个枚举、`MsgError` 基类、帧非法 / 载荷过大 / 版本不支持三个**协议异常** | 其余 **25 个业务异常**（主题 / 租户 / 组 / 延迟 / 重放 / 水位 / 远程调用方法未注册等）与 `MsgErrorMapper`（产品码覆盖） |

**C 类 · 明确留 msg 仓**（进基座即违反「产品标识不入基座」）

`RpcRegistry` 及 `RpcHandler` / `RpcStreamHandler`、`rpc/service.py`（限流 / 预算 / 取消）、`rpc/idempotency.py`（进程内去重）、`rpc/builtin.py`、`rpc/contract.py`、`api/**`、`broker/**`、`schemas/**`、`core/config.py` 数据面常量、`errors.py` 的 25 个业务异常。

**判据**：被客户端调用链**必需**且不含产品业务语义 → 上移；承载服务端装配态或产品业务标识 → 留仓。迁移时以「`bms_core` 全仓零 `bms_msg` 引用 + 零产品字面量命中」两条机器断言收口，不靠人工走查。

### 3.3 基座落点：`bms_core/msgclient/` <a id="landing"></a>

新增能力域，与 `servicecall` / `events` / `circuit` / `idempotency` 并列：

```text
bms_core/msgclient/
  base.py          端口与装配入口（供 resolve_plugin 取用）
  frame.py         帧编解码（含 codec / payload 合并或分包，实现阶段确定）
  client.py        一元 + 流式客户端
  retry.py         RetryPolicy / RetryBudget / 退避与抖动
  circuit.py       三态熔断（继承 bms_core.circuit 契约）
  errors.py        两个枚举 + 协议异常基类 + 三个协议异常
  values.py        RpcCall / RpcReply
  deadline.py      预算传播
  naming.py        名称校验
  constants.py     通用命名常量 + RPC_* 缺省值
  transport/       传输层（h2 / ASGI 替身接缝）
  adapter/         BaseServiceClient / EventPublisher 的 msg 实现
```

- 不并入 `servicecall/`（帧协议、流式、幂等不属于「服务间同步调用」语义，会变成大杂烩），也不并入 `events/`（远程调用客户端与事件域语义不符）。
- 能力域登记进《[后端基类清单](../../../../../../后端基类清单.md)》§9；契约实现细节归《后端基类实现契约》后续补登。
- 缺省值（2 次 / 100ms / ×2 / 2s / TTL / 熔断阈值）仍由基座 `constants.py` 提供，各产品仓开箱即用，不要求每个产品重复给一遍。

### 3.4 命名与产品字面量通用化 <a id="naming"></a>

- **帧字节、码值、契约形状一律不变**，只改符号名：`FRAME_MAGIC` / `x-msg-frame` / `msg:rpc` 一类改为通用语义名（如 `FrameMagic` / 帧媒体类型符号 / `rpc` 能力名）。
- msg 仓作为**首个接入产品**在声明中给出具体值；产品字面量不进 `bms_core` 源码。
- 与 `05_01` 已收口的「零命中硬门禁」保持兼容：上移后 `product_literals` 护栏对 `bms_core` 全仓仍应零命中；若通用化过程中出现残留，视为缺陷而非加白名单。
- 契约快照（`deploy/contracts/msg.json`）**仍由 msg 仓导出**，但 `protocol/contract.py` / `rpc/contract.py` 的字段值改为读取 `bms_core.msgclient.constants`，保证单一事实源；快照断言随改名同步回归，不列为「以后再改」的开放项。

### 3.5 msg 仓本地副本退役 <a id="retire"></a>

- 删除 `bms_msg/client/` 与帧协议本地实现；服务端、用例、测试替身统一 `from bms_core.msgclient import …`。
- **不保留薄别名层**（别名层会留下两个出口，新人继续往里加东西）；**不保留双份 + 一致性护栏**（护栏只能验形状、验不了行为）。
- 需同步更新的引用面：服务端 `api/rpc/*` 的帧头装配、`rpc/service.py` 的错误分类、契约快照构造、全部 `tests/client/*` 与 `tests_support/rpc_transport.py`、04-1 ~ 04-4 详细设计 / 实施记录中的 import 口径。
- msg 仓只剩 broker 服务端业务；契约导出、错误码对账、门禁口径保持不变。

### 3.6 provider 键名与切换粒度 <a id="provider"></a>

- 复用既有 `[service_client].provider` / `[event].provider`，取值 `http`（缺省）/ `msg` / 空串（null 占位）；**整进程全局切换**，一次配置作用于全部调用。
- 走既有 `resolve_plugin`，**不新增 `[msg_adapter]` 配置节**、不另造装配路径；适配参数（实例地址 / 租户 / 超时）沿用既有配置面。
- **缺实现即拒启**：`provider = "msg"` 但 `msgclient` 不可用或实例地址未配时，启动期报明确错，不静默回退到 `http`（与 07B「断链即拒启」口径一致）。
- 回滚 = 改回一个字符串；切换前后业务代码零改动。
- **开放项**：按 `service.method` 的细粒度灰度（`routes` 表）不在首期，评估归后续阶段。

**装配落点（步 2 定稿）**：登记只有一处——`core/assembly.py` 的 `register_plugin` 段，与 `service_client/http`、`event/rocketmq` 并列两行：

```python
register_plugin("service_client", "msg", MsgServiceClientFactory(settings))
register_plugin("event", "msg", MsgEventPublisherFactory(settings))
```

- `PLUGIN_WIRINGS` **不改**：`service_client` / `event` 两个能力域键已登记，`provider` 只是一等公民里的实现名；装配期预热仍按 `wiring.plugin_key` + `settings.<section>.provider` 解析。
- **实例地址解析（唯一一处）**：工厂按 `[service_client].endpoints["msg"]` → 回落 `[service_client].options.base_url_template` 派生（`{service}` 取 `msg`）；`event` 侧同源复用同一地址（`/api/v1/msg/publish` 与 `/rpc/*` 同属一个进程）。
- **拒启语义**：地址解析失败（无覆盖且模板缺 `{service}` 占位、或派生结果非 `http(s)://`）→ 工厂 `create()` 抛 `ConfigError`；文案带 `provider` 名与配置键（示例：`[service_client].provider = "msg" 但消息平台实例地址未配置（[service_client].endpoints.msg 或 options.base_url_template）`）。抛点在装配期（`resolve_plugin` → 工厂），**不是首次调用期**，也不静默回退 `http`。
- 登记项为实现类或零参工厂的既有约束不变：两个实现类构造需注入依赖，故**不参与自动登记**（`_requires_constructor_args` 剔除），只经工厂登记——与 `HttpServiceClient` / `RocketMqEventPublisher` 同款。

### 3.7 错误与上下文映射 <a id="mapping"></a>

以 04-4 的 `category` 为**唯一分类输入**（不在适配层重写码值分类表）：

| `category` | bms 侧映射 | 保留字段 |
| --- | --- | --- |
| 参数错误 | `ParamError`（`10001`） | 原始码 / `retryable=false` / 改参放弃 |
| 业务拒绝 | 上抛业务异常（不自动重试） | 原始码 / `retryable=false` |
| 瞬时故障 | `ServiceUnavailableError`（`10007`）/`RateLimitError`（`10005`），按原始码细分 | `retryable=true` / `attempts` / `backoff_ms` / `Retry-After` |
| 超时未知 | 保留 `350004` 原始码与 `Outcome.UNKNOWN`，**仅在带幂等键时**允许谨慎重试 | `outcome` / `retryable=false` 原值 |
| 服务端 bug | 上抛并告警，不重试 | 原始码 / `retryable=false` |

- `ServiceCallPolicy.timeout`（秒）→ `deadline_ms`（毫秒）换算在适配层**唯一一处**完成；`max_retries` / `retry_backoff` / `circuit_breaker` / `rate_limit` 映射到 `RetryPolicy` 与熔断注入，不重复实现退避算法。
- `retry_statuses`（HTTP 状态码）与帧错误码**无语义对应**：帧层可重试性由 `category` + `retryable` 判定（04-4 唯一出处），故适配层**忽略该字段**，不把 HTTP 状态码塞进帧协议、也不据此改写帧层判定。
- `trace_id` / `tenant_id` / 服务 JWT 透传，沿用 bms 既有租户解析链；不新增认证协议、不绕过租户守卫。
- **逐码映射表（步 2 定稿）**：分派只按 `category` 选异常类，码值只进 `data` 供排障与对账，**不新增码表**；`layer` / `retryable` 全部照搬 04-4 判定。

| `category` | 原始码（示例） | bms 异常 | `data` 保留 |
| --- | --- | --- | --- |
| 参数错误 | `350018` / `350019` / `350006` / `10001` | `ParamError`（10001） | `code` / `category` / `layer` |
| 业务拒绝 | `350023`（方法未注册）/ `350001` / `350011` / `350012` / `350013` / `350014` | `BizError`（**原始码**，`http_status` 取 200 业务失败口径） | `code` / `category` / `attempts` |
| 瞬时故障 | `350005`（限流） | `RateLimitError`（10005） | `code` / `retry_after_ms` / `attempts` / `backoff_ms` |
| 瞬时故障 | `350020` / `350021` / `350022` / `350007`，及连接失败（`code=0`） | `ServiceUnavailableError`（10007） | `code` / `category` / `attempts` / `backoff_ms` |
| 超时未知 | `350004` | `ServiceUnavailableError`（10007） | `code=350004` / `category` / `outcome="unknown"` |
| 服务端 bug | 其余 `system` 层不可重试码 | `ServiceUnavailableError`（10007） | `code` / `category`；另记 `msg_rpc_server_bug` 告警事件 |
| 兜底 | `code=0` 且分类不可判定 | `ServiceUnavailableError`（10007） | `code` / `category` |

- **不做**「逐码 switch」：码值到异常类的映射一律先经 `category`，只有「瞬时故障里 `350005` 单独进限流」这一条按码分流——它是唯一有独立 bms 语义（10005）的码。
- 映射表逐码实测在两仓联调阶段完成，实测结论回写本节。

### 3.8 回滚窗口三态处置 <a id="rollback"></a>

| 窗口态 | 风险 | 处置口径 |
| --- | --- | --- |
| 在途请求 | 切换瞬间旧链路请求未返回，回滚后重复执行 | 切换前 **drain 在途**（停止接新请求、等在途收敛或超时）；切换点以**配置版本戳**标记，日志与指标带戳便于对账；带幂等键的请求由服务端去重兜底 |
| 未确认事件 | 事件已发但未确认，回滚后丢事件或重投 | 事件侧**不双写**：先停旧 provider、确认在途事件收敛，再启新 provider；未确认事件保留在 outbox 由既有重投链路补发 |
| 双写窗口 | 两 provider 同时在线导致重复副作用 | 首期明确**禁止双写**；确需灰度的场景归开放项，须先定「按能力分流 + 幂等键全覆盖 + 版本戳对账」三件套再评估 |

**演练步骤**（进测试设计）：① 构造在途请求与未确认事件 → ② 切到 `msg` 并断言业务结果一次生效 → ③ 切回原实现并断言同一调用行为恢复、无重复副作用 → ④ 断言缺实现时启动期拒启且错误信息定位到 provider 名。

### 3.9 适配层实现（步 2 定稿） <a id="adapter"></a>

**落点**：`bms_core/msgclient/adapter/`——与协议包同域，整块可替换、可删除；策略换算与错误映射各只有一个出处，避免两处漂移。

```text
bms_core/msgclient/adapter/
  __init__.py         出口（两个实现类 + 纯函数）
  policy.py           ServiceCallPolicy → RetryPolicy / deadline_ms / 熔断 / 限流 的唯一换算处
  mapping.py          目标方法归一化 + RpcCallError → bms 异常 的逐码分派
  service_client.py   MsgServiceClient（plugin_name = "msg"，继承 BaseServiceClient）
  event_publisher.py  MsgEventPublisher（plugin_name = "msg"，继承 EventPublisher）
```

**依赖方向**：`msgclient`（协议）→ `servicecall` / `events` / `circuit` / `ratelimit` / `oauth`（端口与复用件）；端口**不**反向依赖协议，`bms_core` 仍零 `bms_msg` 引用。适配层是「端口契约的下游消费者」，换回 `http` 时删掉 `adapter/` 即可，协议包不受影响。

#### 3.9.1 `MsgServiceClient` <a id="adapter-call"></a>

| 项 | 口径 |
| --- | --- |
| 继承与插件名 | `BaseServiceClient` / `plugin_name = "msg"`；`contract_version` 沿用基类默认，不单独升降 |
| 构造注入 | `rpc_client: RpcClient`（含实例地址、传输、重试与熔断）、`rate_limiter`、`token_issuer`、`attach_service_token`、`caller`、`tenant` |
| 端口校验 | 先 `validate_service_request`（服务目录启用 + `/api/v1` 公开面 + 策略合法），越界 `ParamError`、**不发起调用**；与 http 通道同一道闸 |
| 目标方法 | `path` 去 `/api/v1` 前缀 → 去尾斜杠 → `/` 换 `.`（`/api/v1/foo/bar` → `foo.bar`）；`path` 恰为 `/api/v1`（无可归一末段）→ `ParamError` |
| 请求体 | `json_body` → `json.dumps(normalize_collections(...), sort_keys=True, ensure_ascii=False).encode()`；`content` 原样；两者皆空 → `b""`；**两者同时给 → `ParamError`**（不猜优先级） |
| 查询串 | 逐项写入帧头 `query.<name>`；首期只承诺透传，**不承诺等价 HTTP query 语义**（正式语义归步 3 联调） |
| 身份与租户 | 入站 `Authorization` 一律剥离；`attach_service_token` 开 → 按调用方服务标识签服务 JWT 附 `Authorization`；租户经 `X-Tenant-ID` 与帧头 `tenant`（服务端仍以解析链为准） |
| `local` | 远程调用通道无「本进程直连」语义，`ServiceRequest.local` **忽略**（不静默改写调用语义；该优化只有 http 通道具备，切换期差异登记为偏差） |
| 响应回填 | `RpcReply.payload` → `ServiceResponse.content`、`RpcReply.headers` → `headers`、`status_code = 200`；非 2xx 在帧层已成错误帧，走不到回填 |
| 失败分支 | 一律经 `mapping.to_bms_error()` 转 bms 异常后抛出，端口不暴露 `RpcCallError`；逐码见 §3.7 |
| 流式 | **不暴露** `stream()`：端口无流式方法、流式不进重试层、消费方未就绪 → 归 8B_03 |

#### 3.9.2 `MsgEventPublisher` <a id="adapter-publish"></a>

| 项 | 口径 |
| --- | --- |
| 继承与插件名 | `EventPublisher` / `plugin_name = "msg"` |
| 通道 | `POST {msg_base}/api/v1/msg/publish`（既有 HTTP/1.1 数据面基准，OpenAPI 有声明）；根路径 `/msg/publish` 是 HTTP/2 帧入口，首期不走 |
| topic | 复用基座 `topic_for(event.event_type)`（`bms-{域}-{对象}`），**不新造映射规则** |
| 消息体 | 复用 `encode_event(event)`（确定性 JSON），base64 进 `payload` |
| 消息属性 | 复用 `event_attributes(event, traceparent=…)` 进 `headers`；`event_id` / `event_type` / `event_version` / `tenant_id` / `aggregate_key` 由此透传 |
| 分区键 / 链路 | `aggregate_key` → `key`；`trace_id` 取 `event.trace_id`，缺省 `current_trace_id()` |
| 命名空间 | `[event].options["namespace"]` → 回落 `[app].service`；**两者皆空即拒启**（msg 侧按已启用 `module_key` 校验，空串会被判 `350010`） |
| 失败 | 非 2xx / 传输异常 → `EventPublishError`（发件箱投递段 `10009`）；**本层不重试**，重试归发件箱投递器 |
| 事务消息 | `publish_transactional` 首期委托 `publish`（事务消息归 8B_04） |
| outbox | **不改 relay**：`outbox_dispatcher` 仍调 `EventPublisher.publish`，切 provider 后自动改道；适配层不写 outbox、不参与确认 |

#### 3.9.3 `policy.py`：换算唯一处 <a id="adapter-policy"></a>

| 输入（`ServiceCallPolicy`） | 输出 | 说明 |
| --- | --- | --- |
| `timeout`（秒） | `deadline_ms = int(timeout * 1000)` | 与 `RPC_CLIENT_TIMEOUT_SLACK_MS` 冗余口径无关：局端超时由 `RpcClient` 自持 |
| `max_retries` | `RetryPolicy.max_retries` | 缺省 2 与远程调用缺省同值，无需换算 |
| `retry_backoff`（秒） | `RetryPolicy.base_ms = int(retry_backoff * 1000)` | `multiplier=2` / `cap_ms=2000` / `jitter=FULL` 取远程调用常量，**不再由调用方配** |
| `circuit_breaker: bool` | `True` → 三态熔断生效；`False` → 本次调用不参与熔断 | 三态实现复用 `InProcessCircuitBreaker`；逐调用开关经 `PolicyCircuitBreaker` 代理 + `ContextVar` 表达（`RpcClient` 的熔断器是实例级），关闭时**恒放行且不计数**，不新写算法 |
| `rate_limit` | 调用前经 `BaseRateLimiter.require` | 与 http 通道同款，超限 `RateLimitError` |
| `retry_statuses` | **忽略** | 帧层可重试性由 `category` 判定（§3.7） |
| `scopes` / `tenant_id` | 服务 JWT 签发入参 | 沿用 http 通道口径 |

- `RetryPolicy` **逐调用**换算后传 `RpcClient.call(policy=…)`，不固化进客户端实例：同一进程内不同调用点给不同策略时行为才可解释。
- 熔断与重试**只有一层**：`RpcClient` 内部已含退避与熔断，适配层不再包外层循环（否则重试次数相乘、`backoff_ms` 失真）。

**边界**：不改端口契约（`BaseServiceClient` / `EventPublisher` / `ServiceCallPolicy` 形状不变）、不新增配置节、不改 `PLUGIN_WIRINGS`、不做按方法灰度、不做回滚三态演练（步 3）、不替换真实 `HttpServiceClient` 调用（步 3）、不暴露流式。

### 3.10 步 3 收口：三态演练与真实调用替换 <a id="closing"></a>

**生产代码零改动**：步 3 只补用例与文档——适配层、装配、端口契约一律不动（若要改才能演练，说明设计有问题，回到 §3.9 修设计）。

#### 3.10.1 真实调用点 <a id="closing-real"></a>

| 项 | 口径 |
| --- | --- |
| 调用点 | `bms_core/catalog/base.py::fetch_catalog_snapshot`（`GET /api/v1/modules/snapshot` → `platform.modules.snapshot`） |
| 为什么是它 | 无 body / 无 query / 无租户、纯读可重复；返回体经统一响应包裹并由业务函数解析成 `ModuleRecord`，断言「同一业务函数两通道等价」最干净；且它是全部服务启动接库校验的入口，替换价值最高 |
| 双通道断言 | `http` 通道（`HttpServiceClient` + `httpx.MockTransport`）与 `msg` 通道（`MsgServiceClient` + `ScriptedRpcTransport`）产出相同 `ModuleRecord` 列表；不可达 / 非 2xx / 响应非法三种失败都收敛为 `ServiceUnavailableError` |
| 真帧验收 | msg 仓用 `AsgiRpcTransport` 驱动**真实 msg 应用**（真路由 → 真帧 → 真处理器），bms 侧用同一个 `fetch_catalog_snapshot` 发起调用；目标方法 `platform.modules.snapshot` 的处理器在用例内注册（`platform` 服务本体不在场，处理器是等价的测试替身） |

**8B_03 退出条件判定**：进程内真 msg 应用 + 真实业务函数 + 真帧往返 = 「可替换一个真实 `HttpServiceClient` 调用」达成；**生产集群实测归部署阶段**（本地无 msg 编排，不在此断言）。

#### 3.10.2 三态演练口径 <a id="closing-tri"></a>

| 窗口态 | 演练方式 | 断言 |
| --- | --- | --- |
| 在途请求 | 脚本传输：首次不给响应（本地兜底超时 `350004`），第二次成功；同一 `ServiceRequest` 连续调用 | 重试全程**同一幂等键**（帧头 `idempotency_key` 不变）；业务结果**一次生效**；切回 `http` 后同一调用仍成功 |
| 未确认事件 | 投递器 A（发布器恒抛 `EventPublishError`，模拟 msg 不可达）→ 投递器 B（可用）共享同一发件箱 | A 轮次 `published=0`、行保留且失败计数递增（**不丢**）；B 轮次**每个 `event_id` 只成功一次**；切回 A 后不再重投已投递行（**不双写**） |
| 双写窗口 | `resolve_plugin` 单值解析 + 装配只产出一个发布器 | 首期**无双写路径**：进程内同时存在两个 provider 的通道不存在，灰度归开放项 |

**drain 口径**：生产侧「在途请求 drain」由服务关闭顺序承担（先停止接收、再等在途收敛、最后释放资源），**不加 drain API、不改生命周期**；演练以「同进程切换 + 幂等键去重」证明收敛等价。

**跨仓夹具**：六类（请求 / 响应 / 错误 / timeout / cancel / 幂等键）单一来源落 msg 仓 `backend/tests_support/bms_port_contract.py`（msg 依赖 `bms-core`，反向不成立），用例 `services/msg/tests/client/test_bms_port_contract.py` 消费；bms 仓用自有替身，不重复声明同一份 wire 期望。

**差异收敛结论**：`local` 忽略、`query` 仅透传、`retry_statuses` 不参与帧层判定三条**保持现状**并转入运维口径——前者是远程调用通道固有语义差，后两者要改服务端（msg 仓本轮只新增测试，不动已交付源码）。

### 3.11 返修：内部租户 id 传递（2026-11-06） <a id="tenant-id"></a>

**触发**：msg 04-5 真链路契约用例实测——`MsgEventPublisher` 把 `event.tenant_id`（雪花 id）写进 `X-Tenant-ID`，而 `resolve_request_tenant()` 只接受租户编码，msg 数据面返回 `350012`，事件发布失败。按系统口径「**内部统一传 id，与外部系统交换才用 code**」，接收侧应接受 id，而不是让发布器把 id 查成 code。

**改动**：

- `bms_core/db/tenant.py::resolve_request_tenant`：解析链第二段由「请求头（按 code）」改为「请求头（**code / id**）」——纯数字走 `source.by_id`，字母开头走 `source.by_code`；两种形态互斥（编码必须以字母开头，主键纯数字），无歧义。
- 次序不变：子域名 → 请求头（code / id）→ 令牌租户位；请求头命中仍优先于令牌。
- 文档串同步：`TenantMiddleware` / `db/tenant.py` / `edge/headers.py` 注明「外部门户 / 网关传 code，内部服务调用传 id」。
- 不改 `MsgEventPublisher`：`event.tenant_id` 直写 `X-Tenant-ID` 符合内部口径；`MsgServiceClient` 的 `request.tenant_id` 同口径受益。
- 不改 msg 仓源码：msg 侧只新增真链路用例（04-5）。

**兼容性**：编码形态（字母开头）与主键形态（纯数字）互斥；外部网关继续传 code；内部调用传 id；非法值（含 IP 字面量 / 域名）仍等同未提供。

**测试**：`tests/db/test_tenant.py` 新增 header-numeric → `by_id` / header-alpha → `by_code` / 次序 / 非法值；`test_tenant_middleware.py` 回归；msg 真链路事件用例（04-5）转绿。Kiwi 2443。

## 5. 覆盖率与门禁口径 <a id="gate"></a>

- **覆盖率**：两仓变更模块**行 + 分支 100%**；一次 pytest 会话采集，同时给 `MSG_COVERAGE_DATA`（绝对路径）与 `MSG_COVERAGE_SOURCE="bms_msg,services,ops"`（bms 侧按其仓内口径）；判定在仓根跑 `engkit coverage --data-file … --out … --module <点分模块> …`，`--out` 必填、`--module` 清单宁多勿漏。
- **一次会话清单**必须含所有会被覆盖到的模块；改了既有大模块（如 `deps.py` / `config.py`）时，模块级判定要求整文件覆盖，需把触发既有提供者 / 工厂的用例并入同一会话，**不得用 `pragma` 或缩减 `--module` 清单**。
- **静态**：`ruff check` + `format --check` 覆盖全部改动文件；pyright 带 `--pythonpath .venv/Scripts/python.exe`；契约快照 `check` 零漂移。
- **文档三项**：`check_links.py`（断链 0 / 失效锚点 0）、`check_docs_scope.py`（违规 0）、`engkit eol`（行尾违规 0）；改文件后按 `HEAD` 逐文件核对行尾（HEAD 本为 CRLF 的保持 CRLF，不一律回正）。
- **本地执行**：一律 `CODEBUDDY_SAFE_DELETE_ENABLED=0`；并行档偶发超时先用 `--jobs off` 复跑定性，不急着改代码。
