## 1. 目标与边界 <a id="scope"></a>

**目标**：让平台仓 CI 在**只能拿到本仓**的前提下，仍然能对「跨仓两条漂移链」做出判定，并把断链前移到合入之前：

- **链 A（跨仓契约）**：产品自持声明 ↔ 产品自己的公开契约（能力访问面能否在契约里定位、主版本是否兼容、错误码段位与反向对账、种子入口形态）；
- **链 B（注册表一致性）**：声明（平台 + 各产品）↔ 注册表六表（能否注册通过、跨产品是否撞键、注册表回读与本仓声明是否逐字段一致）。

两条链的失败都必须**可定位**（到能力名 / 错误码 / 契约路径 / 服务行键）且**不得静默跳过**。

**范围内**：

1. 两层校验的形态定义（L1 跨仓文件校验、L2 临时库注册与对账）与各自的校验项；
2. `ops.check_modules` 的跨仓模式（参数、建库、注册编排、输出、退出码）；
3. CI 作业、克隆片段、变量、失败语义与开销控制；
4. 本地等价入口（预检步骤）与「本地可验证 / CI 兜底」的分工口径；
5. 承接两项遗留：`registry.product_manifests` 退役（`02_06` §5 第 6 条）、服务行格式前置校验（计划 §7 第 16 项）、`[seeds.tables]` 表名存在性校验（`03_03` 遗留）；
6. 实测暴露的接库对账口径不一致（11 项）的修正。

**范围外**：

- 装载与校验的算法本体（`02_01` / `02_05` / `02_06` 已交付，本任务只复用与扩参数）；
- 产品字面量护栏（`04_01`）、产品仓自身 CI（各产品仓自持）、**真库 / 两进程端到端（`03_01` 剩余）**——口径修正（2026-10-29 实测）：**本机可做**（三库端口可达、platform/identity/tenant 已实测起得来），此前「部署窗口」表述不成立；本任务 §3.13 修完 mdm 启动缺陷后由 `03_01` 补验；
- 「基线为空 + 全仓零命中」终态验收（`05_01`）。

## 3. 设计 <a id="design"></a>

### 3.1 两层形态 <a id="layers"></a>

| 层 | 回答什么问题 | 取源 | 需要库 | 失败即红 |
| --- | --- | --- | --- | --- |
| **L1 跨仓文件校验** | 产品自持声明与**它自己的契约**是否一致？跨产品之间是否撞键 / 版本不兼容？ | 本仓 `deploy/registry/*.toml` + 各产品仓 `deploy/registry/*.toml` + 各自 `deploy/contracts/<key>.json` + `deploy/boundaries/domain_layout.json` | 否 | 是 |
| **L2 注册表一致性** | 这些声明**能不能注册进去**？注册表回读与声明是否逐字段一致？ | 同 L1（清单）→ 注册进**一次性临时库** | 是（`tempfile` 生成的 SQLite，用完即删） | 是 |

为什么必须两层（缺一不可）：

- 只有 L1：`02_06` 之后「注册表才是权威」，L1 查不到「声明注册不进去 / 注册表回读漂移」；
- 只有 L2：`inspect_product_manifests` 的「访问面不在对端契约」等四项校验属**注册方本地职责**，平台侧注册校验**不重复做**（`02_06` §3.2），砍掉 L1 就丢了需求 04-2 原定的「契约定位校验」；
- 两层都只复用既有函数，**不新写判定逻辑**。

### 3.2 L1：跨仓文件校验 <a id="l1"></a>

**取源**：清单集合 = 本仓 `deploy/registry/*.toml`（`local_manifest_paths()`，平台在前） + 每个产品仓 `deploy/registry/*.toml`（按仓名、文件名排序）；一次 `inspect_product_manifests(全部路径)`（跨清单的一致性——能力重名、`branch_id` 跨域、错误码撞码——依赖「一次装载」，不能逐仓分次）。

| # | 校验项 | 实现归属（复用） | 严重度 |
| --- | --- | --- | --- |
| 1 | 清单可解析、必填字段齐备、记录归属与 `product_key` 一致 | `load_product_manifest` / `_validate_manifest_entries` | 红 |
| 2 | 能力要素匹配（`kind` 与要素组合）、`branch_id` 形态与跨域、前端命名空间可推导 | 同上 | 红 |
| 3 | 访问面在**产品自己的**契约中可定位（`_contract_path` 同仓优先） | `_contract_spec` / `_validate_manifest_entries` | 红 |
| 4 | 契约主版本兼容（能力 / 错误码 vs 服务行） | 同上 | 红 |
| 5 | 错误码段位、跨产品撞码、契约反向（契约声明的码须已登记） | `_validate_error_codes` | 红（未声明 `x-error-codes` 的端点只统计） |
| 6 | 种子入口可解析（同机可导入时强校验） | `_seed_entry_importable` | **CI 降级为告警**（CI 不装产品依赖，见 §3.2.2） |
| 7 | `[seeds.tables]` 表名存在性 | 新增 `validate_seed_tables()`（§3.6） | **仅平台自身**判红；产品只告警 || 8 | 使用声明可兑现（降级限制、写 / 强一致能力不得声明降级） | `_validate_usages`（`03_01`） | 红 |
| 9 | `default_consumers` 未登记 | `_validate_manifest_entries` | 告警（`03_01` 决策：消费方是否已登记不在装载期判错） |
| 10 | 域布局：业务域须登记且承载服务键一致 | `_layout_registry_map`（平台本仓 + 各产品仓 `deploy/boundaries/domain_layout.json` 并集） | 红 |

#### 3.2.1 契约缺失的唯一出口 <a id="l1-skip"></a>

沿用既有开关 `BMS_REGISTRY__SKIP_CONTRACT_CHECK`（非空且非 `0/false/no` 即跳过并警示）。**不新开第二个跳过口**：CI 的 `CROSS_REPO_ALLOW_MISSING` 只控制「整条跨仓链是否允许缺席」（§3.8），不控制单项契约校验。

#### 3.2.2 种子入口在 CI 的降级口径 <a id="l1-seed"></a>

L1 在 CI 里跑时，产品包（如 `mdm`）未安装 → 入口不可导入是**环境限制而非声明错误**。处置：可导入则强校验（本机工作区、产品仓自身 CI 是这种情况），不可导入则输出告警并计入「跳过项统计」，退出码不受影响。实测已确认当前 `mdm` 走的就是告警分支。

### 3.3 L2：临时库注册与对账 <a id="l2"></a>

**步骤（单进程顺序执行）**：

| 步 | 动作 | 复用 |
| --- | --- | --- |
| 1 | 建临时库：`tempfile.mkdtemp()` 下 `registry.db`（**不进工作区、不读配置**），按平台单元建表（26 表） | `ops.init_schema` 的单库建表同源入口（`apply_unit_schema` + `unit_metadata`） |
| 2 | 装载清单 + 登记域布局（`register_domain_services(inspection.domain_services)`） | `inspect_product_manifests` |
| 3 | 注册**平台自身**：`platform_payload()`（本仓 `platform.toml` + `SERVICE_CATALOG` 中 `product_key` 为空的行——与 `declaration_bootstrap` 同口径，见 §3.4） | `DeclarationRegistryService.register` |
| 4 | 注册**各产品**：按 `product_key` 升序逐个 `from_manifest(manifest)` → `register()` | 同上 |
| 5 | 双向对账：① 常量平台行 ↔ 库（`check_catalog_db`，§3.4 修正后）；② 声明 ↔ 注册表（`diff_platform_declarations`，每个声明方各跑一次） | 既有函数 |
| 6 | 清理：`shutil.rmtree`；`--keep-tmp` 时打印目录并保留（便于复现） | — |

**顺序为什么「平台先、产品后」**：平台声明里的 `default_consumers` / `usages` 指向产品能力，产品未注册时只出 warnings（实测确认）；反过来（产品先）会让平台侧「被消费能力尚未注册」的告警消失得更晚，定位更绕。固定「平台 → 产品（按 key 排序）」与部署顺序一致。

**幂等**：L2 每次在**新库**上跑，不复用任何既有库；同一份声明重复跑结果一致（注册协议本身幂等）。

**为什么不连部署库**：CI 无部署库；连真库会把「外部环境状态」引入门禁，且 `02_06` 已把部署态对账放在 `release.py gateway`（`deploy` 前置，fail-closed）。本任务只做「代码态 ↔ 注册表结构」的一致性。

### 3.4 接库对账口径修正（实测 11 项） <a id="reconcile-fix"></a>

实测（§2.5 第 4 条）在临时库上跑 `ops.check_modules --url` 报 11 项，全部是 `02_06` 遗留的口径不一致。**不修则 CI 首跑必红**，故本轮一并修正：

| 类 | 现象 | 根因 | 处置 |
| --- | --- | --- | --- |
| A（6 项） | `services｜pur / pay / sale / wh / sup / cw：注册表缺该声明（未注册或已退役）` | `ops.check_modules.platform_payload()` 把**整个 `SERVICE_CATALOG`** 并进平台载荷（含 `product_key` 非空的计划产品行）；注册后按 `product_key` 落为 `biz` / `cw` 名下，回读 `owner_of` 判「不是平台的行」→ 报缺。而 `declaration_bootstrap` 只并 `product_key` 为空的行（`02_06` 修正 #3） | `platform_payload()` 改为**只并 `product_key` 为空**的平台自身行，与 `declaration_bootstrap` 同口径（一处口径，两处调用都指向同一函数） |
| B（3 项） | `mdm：product_key 未登记（mdm）` / `库中登记行不在清单：mdm` / `产品档案库中登记行不在清单：mdm` | 接库对账基准仍是常量 `SERVICE_CATALOG` / `PRODUCT_CATALOG`，而产品行**本就不在常量里**（产品自己声明） | 接库对账基准改「**声明集 ∪ 注册表已有集**」：常量退回「平台自身行的形态与覆盖基准」；产品行只与声明比 |
| C（2 项） | `产品档案库中缺登记行：biz` / `：cw` | 常量 `PRODUCT_CATALOG` 含计划产品 `biz` / `cw`，但**没有任何清单声明**它们，也无服务进程会注册 | 常量有、声明无的产品档案 → **警示**（提示「该产品尚未自持声明」），不判红；登记为待办（`biz` / `cw` 接入时补，归计划 §7 第 18 项一并） |

修正后的判定矩阵（`ops.check_modules` 接库档）：

| 维度 | 基准 | 不一致时 |
| --- | --- | --- |
| 平台自身服务行（`product_key` 为空） | 常量 `SERVICE_CATALOG` ∩ 平台声明 | 红 |
| 产品服务行 / 产品档案 | 该产品的清单声明 | 红（缺声明 / 指纹漂移 / 库多出） |
| 常量有、声明无的产品档案（`biz` / `cw`） | — | 警示 |
| 注册表 ↔ 各自声明（八类逐类） | `diff_platform_declarations` | 红 |

### 3.5 服务行格式前置校验（`02_06` §5 第 8 条 / 计划 §7 第 16 项） <a id="service-rows"></a>

**问题**：现状只校验声明类要素，服务行形态（模块键 / 表前缀与键一致 / 段位 / 事件域 / 分组 / semver / 唯一性）由**各服务启动时的离线校验**兜底；非法行一旦被投影，会污染**同进程后续**的启动校验。

**做法（单一实现，不复制规则）**：

1. 把 `ModuleRegistry._validate_record()` 的单条规则抽成模块级函数 `validate_module_record(record, product_keys)`（`bms_core/services/module_registry.py`），`_validate_record` 改为调它（行为零变化，既有用例守）；
2. `validate_declarations()` 增一段：对 `payload.services` 逐行调该函数，`product_keys` = 声明产品集 ∪ 注册表现有产品集；
3. 唯一性：`payload.services` 的 `module_key` / `table_prefix` / `event_domain` / `service_key` / `errcode_segment` 与**注册表中其他产品行**合并判重（同 `product_key` 的旧行不参与，避免「本产品改前改后自撞」）；
4. 违例即 `CatalogError` 拒收（与 §3.8 fail-closed 一致），信息含 `module_key` + 违例字段 + 冲突方。

### 3.6 `[seeds.tables]` 表名存在性（`03_03` 遗留） <a id="seed-tables"></a>

新增 `validate_seed_tables(payload)`（`bms_core/registry/declarations.py`）：

- **仅对 `product_key == "platform"` 判红**——只有平台自己的模型元数据在进程内；产品种子（如 mdm）的表在其自身库与工程，bms 进程判不了，继续沿用现有告警口径，归产品仓自测（开放项 1）；
- **表集来源与建表 / 迁移同源**：按种子声明的 `db_key` 解析出（部署单元, 库类别），取 `unit_metadata(unit, datasource)` 的表集——不直接读 `Base.metadata`（未导入模型模块时是空集，实测会把合法表名全判成缺失）；
- 调用点两处（同一实现）：L1 的 `ops.check_modules.check_manifests`（装载期即暴露）、L2 的 `validate_declarations`（注册期再兜一次）。**不进 `inspect_product_manifests`**，避免产品进程为一条平台专属校验额外拉模型元数据。

### 3.7 入口与参数（`ops.check_modules` 扩展） <a id="script"></a>

不新增脚本，扩既有入口（需求 04-2「不新增并行校验入口」）：

| 参数 | 语义 | 缺省 |
| --- | --- | --- |
| （无参数） | 现状：离线校验 + 接库（URL 读配置） | — |
| `--offline` | 只离线，不接库 | — |
| `--url <url>` | 接库对账（显式覆盖配置） | 按配置解析 |
| `--manifest <path>`（可重复） | 追加外部清单（替代已退役的 `product_manifests`） | 空 |
| `--cross-repo` | 开启跨仓档：L1 + L2（建临时库跑注册与对账；与 `--url` / `--offline` 互斥，冲突退出码 2） | 关 |
| `--product-root <path>`（可重复） | 产品仓根 / `<仓>/deploy/registry` 目录 / **克隆容器目录**（CI 的 `../product`，逐个子目录展开） | 自动发现同级克隆 |
| `--ephemeral` | 用一次性临时库（与 `--url` 互斥） | `--cross-repo` 时隐式开 |
| `--keep-tmp` | 不删临时库与目录，打印路径 | 关 |
| `--allow-missing` | 取不到任何产品仓时跳过（输出警示） | 关（**取不到即失败**） |

**输出**（逐产品一行 + 汇总 + 失败明细带定位）：

```
[跨仓] 产品仓：mdm（../mdm）@ <rev>
[跨仓] L1 装载校验：2 份清单（platform + mdm）→ 0 错误 / 2 警示
[跨仓] L2 注册：platform(16 服务行/5 能力/9 种子) → mdm(1 服务行/8 能力/25 错误码)
[跨仓] L2 对账：声明↔注册表 0 差异；常量平台行↔库 0 差异；警示 1（biz/cw 未自持声明）
[跨仓] 通过（L1 0 错误；L2 0 差异；跳过 1 项：mdm 种子入口不可导入）
```

**退出码**：`0` 通过；`1` 校验失败（含取不到产品仓且未 `--allow-missing`）；`2` 参数 / 环境错误（`--ephemeral` 与 `--url` 并用、临时库建不起来等）。

### 3.8 CI 作业与变量 <a id="job"></a>

新增独立作业（stage: lint，与 `base-integrity` 并行）：

```yaml
# ---- 跨仓契约校验（07B 04_02）：L1 产品声明 ↔ 产品契约；L2 声明 ↔ 注册表（一次性临时库）----
# 取不到产品仓 / 清单 / 契约即失败（不静默跳过）；仅 CROSS_REPO_ALLOW_MISSING=1 时跳过并警示。
cross-repo-check:
  stage: lint
  image: $REGISTRY_IMAGE_PREFIX/ci-backend:py314
  script:
    # 1) 克隆 PRODUCT_REPOS 到 $CI_PROJECT_DIR/../product；失败时仅 CROSS_REPO_ALLOW_MISSING=1 才放行
    - |
      if ! sh scripts/tools/ci/product_repos_setup.sh; then
        if [ "${CROSS_REPO_ALLOW_MISSING}" = "1" ]; then
          echo "[product] 产品仓准备失败，但 CROSS_REPO_ALLOW_MISSING=1：以 --allow-missing 继续（job log 留痕）"
        else
          exit 1
        fi
      fi
    # 2) 与 base-integrity 同口径：工作区包按工作树重装
    - cd backend && uv sync --frozen --reinstall
    # 3) 跨仓档（一次性临时库；--product-root 传克隆容器目录，逐仓展开）
    - |
      cd "$CI_PROJECT_DIR/backend"
      if [ "${CROSS_REPO_ALLOW_MISSING}" = "1" ]; then
        uv run python -m ops.check_modules --cross-repo --product-root "$CI_PROJECT_DIR/../product" --allow-missing
      else
        uv run python -m ops.check_modules --cross-repo --product-root "$CI_PROJECT_DIR/../product"
      fi
```

| 变量 | 缺省 | 说明 |
| --- | --- | --- |
| `PRODUCT_REPOS` | **无缺省** | 逗号分隔 `group/repo`（**仓库文件不写产品仓地址**；接入新产品的唯一开关）。未配置即 job 失败并提示配置位置——一次性运维动作，见《部署发布规范》 |
| `PRODUCT_REV` | `main` | 产品仓分支 / 标签 / SHA（**固定稳定分支**，不跟随 MR 临时分支） |
| `PRODUCT_REPO_BASE_URL` | 由 `CI_SERVER_URL` + `CI_JOB_TOKEN` 拼 `<group>/<repo>.git` | 产品仓基址（自建 GitLab / 迁移时覆盖） |
| `CROSS_REPO_ALLOW_MISSING` | 未设置 | 置 `1` 时以 `--allow-missing` 运行并输出警示（仅紧急放行，留痕在 job log） |

**克隆片段** `scripts/tools/ci/product_repos_setup.sh`（**执行**用法；不需导出变量，故不像 `engkit_setup.sh` 那样 source）：

- 目标目录 `$CI_PROJECT_DIR/../product/<repo>`（**不落仓库树**，不受工作区卫生护栏约束）；
- 每个仓：已有克隆 → `remote set-url` + `fetch`（跨 job 复用时 origin 里的旧 `CI_JOB_TOKEN` 会 401）+ `checkout --detach`；浅克隆 `--depth 1`（首建）；
- 任一仓克隆失败 → 脚本退出非零（不吞），由脚本层决定是否 `--allow-missing` 继续；
- 打印每个仓的实际 `HEAD`（失败复现用）。

**失败语义**：

| 情形 | 行为 |
| --- | --- |
| 产品仓克隆失败（网络 / 权限 / 仓不存在） | 作业失败，输出仓名 + 地址 + git 错误；`CROSS_REPO_ALLOW_MISSING=1` 时跳过并警示 |
| 产品仓内无 `deploy/registry/*.toml` | 作业失败（声明是该仓的接入前提） |
| 清单不可解析 / 契约缺失 / 任一 L1 校验不过 | 作业失败，定位到清单路径 + 能力名 / 错误码 / 契约路径 |
| L2 注册被拒（结构 / 跨产品冲突） | 作业失败，输出类别 + 键 + 冲突方（`CatalogError` 原文） |
| L2 对账有差异 | 作业失败，输出「声明 ↔ 注册表」逐条差异 |
| 临时库建不起来 / 参数冲突 | 作业失败（退出码 2） |

**为什么独立作业而非并入 `base-integrity`**：失败原因不同（外部仓可达性 / 跨仓一致性 vs 本仓静态问题），独立作业便于定位、重试与单独放行；并行执行不延长流水线总时长。`base-integrity` 已串行十余步，再叠克隆 + 建库会把单 job 拉到 10 分钟级。

**成本**：浅克隆 1 仓（mdm 约 4MB）+ 建 26 表（实测 ~1.5s）+ 两次注册（实测 ~1s）；不装产品依赖、不构建镜像。

### 3.13 第九类声明：业务域（`[[domains]]`）——2026-10-29 重开补充 <a id="domains"></a>

#### 3.13.1 为什么要加这一类 <a id="domains-why"></a>

`03_01` 交付时域布局是**独立文件**（`deploy/boundaries/domain_layout.json`）。本任务实测（2026-10-29）暴露其结构性缺陷：

| 现象 | 实测证据 |
| --- | --- |
| 产品进程启动即崩 | `mdm` 进程 `ConfigError：registry.product_manifests：Extra inputs are not permitted`（该键本任务已退役，mdm 侧未同窗口跟改） |
| 修完配置后注册被拒 | 手工调 `PUT /platform/internal/declarations` 返回 40003：**8 条 `mdm.org.*` 能力全部报「提供方业务域未登记（org）」** |
| 根因 | 平台注册期 `validate_declarations(domain_services=domain_service_view())` 的域视图只来自**平台自己的** `domain_layout.json`（无 `org`）；产品仓的域布局是文件，注册通道**不传文件** |

**结论**：域布局必须是**声明**（随注册通道走），不能是**文件**（依赖部署编排把文件送到对方机器）。否则「产品自持声明」在平台侧永远缺一块，每接一个产品都要在平台仓手抄一份域——正是本专项要根治的问题。

#### 3.13.2 协议定义 <a id="domains-proto"></a>

清单新增第九类记录（与既有八类同解析器、同装载校验、同注册通道）：

```toml
product_key = "mdm"

# 顶层：域外路径（装配面 / 基座横切面 / 基础设施与不归域文件；缺省空）
domain_shared_paths = []

[[domains]]
domain_key = "org"                    # 必填；形态同既有域标识（小写字母开头 + 小写字母/数字/下划线）
service_key = "mdm"                   # 必填；承载服务键，须为本清单已声明的 [[services]].service_key
status = "placement"                  # 必填；placement / legacy / planned
paths = ["backend/services/org/src/mdm/org/**/*.py"]   # placement 必填；legacy 须逐文件；planned 可空
public_api = ["mdm.org.public"]       # 可选；≤1 个
```

| 字段 | 类型 | 必填 | 校验 |
| --- | --- | --- | --- |
| `domain_key` | str | 是 | 形态 `^[a-z][a-z0-9_]*$`；**同一产品内唯一**；**跨产品不得撞键**（同键不同 `service_key` 即拒） |
| `service_key` | str | 是 | 须出现在本清单 `[[services]]` 的 `service_key` 集合中（防笔误） |
| `status` | str | 是 | ∈ {`placement` / `legacy` / `planned`} |
| `paths` | list[str] | 按状态 | `placement` / `legacy` 非空；路径形态相对**仓库根**的 posix 串（产品仓不校验文件存在性——平台侧无该仓文件） |
| `public_api` | list[str] | 否 | 长度 ≤1（D2 唯一跨域引用面） |

#### 3.13.3 装载、注册与视图 <a id="domains-flow"></a>

| 环节 | 变更 |
| --- | --- |
| 解析 | `ProductManifest` 增 `domains: ConcurrentStableFrozenList[DomainRecord]` 与 `domain_shared_paths: ConcurrentStableFrozenList[str]`；`parse_manifest_text` 解析 `[[domains]]` 与顶层键 |
| 装载校验 | `inspect_product_manifests`：第九类形态校验（§3.13.2 全表）；`domain_services` 改由**各清单的 `[[domains]]`** 合并派生（不再读 `domain_layout.json`） |
| 注册载荷 | `DeclarationPayload` 增 `domains`；`from_manifest` 透传；`validate_declarations` 校验跨产品域撞键 |
| 落库 | 新增注册表 `sys_domain`（一类一表，与既有六表同构）：`product_key` / `domain_key` / `service_key` / `status` / `paths` / `public_api` / `content_hash` |
| 视图 | `domain_service_view()` 由**注册表快照**派生（`project_registry` 重建），与能力视图同源；不再从任何文件读 |
| 生成物 | 本仓清单 → `--render-domain-layout` → `deploy/boundaries/domain_layout.json`（形态不变，消费方零改动） |

**注册期跨产品域撞键的判定**：与能力重名同口径——同 `domain_key` 且 `service_key` 不同即拒；同键同服务（多产品共用一个域承载服务）放行并记警示。

#### 3.13.4 L1 / L2 校验项增补 <a id="domains-l1"></a>

| 层 | 新增校验项 | 严重度 |
| --- | --- | --- |
| L1 | 第九类形态（§3.13.2 全表） | 红 |
| L1 | `service_key` 在本清单 `[[services]]` 中（防笔误） | 红 |
| L1 | 跨产品域撞键（同键不同承载服务） | 红 |
| L1 | 原第 10 项「域布局：业务域须登记」改由**声明**判定（读清单，不读文件） | 红 |
| L2 | `sys_domain` 注册后与声明逐字段一致（走 `diff_platform_declarations` 既有九类循环） | 红 |
| 生成物 | `--render-domain-layout --check`：`domain_layout.json` 与清单渲染结果逐字一致 | 红 |

#### 3.13.5 与 07C 的关系 <a id="domains-07c"></a>

07C `03_01` 的域布局定义（`03_01` 详设 §3.1）同步改为本口径，两处**同一次改动**完成：

## 6. 风险与边界 <a id="risk"></a>

| 风险 | 处置 |
| --- | --- |
| 平台流水线依赖产品仓可达性 | 固定 `PRODUCT_REV`（稳定分支）+ 浅克隆 + 复用克隆；失败原因明确；跳过硬门禁只能显式变量 |
| `CI_JOB_TOKEN` 读不到产品仓 | 需在 mdm 项目放行 bms 的 job token（运维配置，写进《部署发布规范》）；首次触发即验，不通则报障不硬试 |
| **跨仓改动漏改对端仓（本次重开根因）** | 改 bms 侧口径时须同窗口检查 mdm 侧：配置键退役、声明结构变更、协议字段增删三类改动都要在**两仓同一次提交窗口**完成；预检加一步「跨仓声明可装载」（`ops.check_modules --cross-repo`）作为兜底 |
| **生成物被手改** | `--render-domain-layout --check` 进预检与 CI，不一致即失败；文件头写「生成物，勿手改」 |
| 产品仓声明变更导致平台 CI 随机红 | 平台侧门禁只看**稳定分支**；产品侧改动走自身流水线，MR 期不跟随临时分支 |
| 临时库与常量口径再次漂移 | §3.4 的「基准矩阵」写进代码注释与测试用例（14~16 各自守一条） |
| 预检变慢 | 实测建库 + 注册 + 对账 3~5s；不进 `--fast`，只在定向 / 全量档 |
| Windows 本地 SQLite 连接串 | 实测：必须绝对 Windows 路径（`sqlite+aiosqlite:///D:/…`），`/tmp` 风格路径会 `unable to open database file`；临时目录用 `tempfile.mkdtemp()` 生成，不硬编码 |
| 产品种子表名判不了 | 明确归产品仓自测（开放项），不在本任务扩成「bms 装产品依赖」 |
