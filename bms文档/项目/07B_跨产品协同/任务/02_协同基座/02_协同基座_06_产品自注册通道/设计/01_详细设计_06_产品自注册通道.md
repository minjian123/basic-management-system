# 产品自注册通道详细设计

> 跨产品协同 · 02 协同基座 · 06 产品自注册通道 · 详细设计（开发核心文档）

[文档首页](../../../../../../文档首页.md) › [06 产品自注册通道](../02_协同基座_06_产品自注册通道.md) › 设计

## 1. 目标与边界 <a id="scope"></a>

**目标**：把「各进程各自装载清单文件」换成「产品向平台注册、平台形成唯一权威视图、谁需要就问平台要」——平台在**零产品清单文件**的前提下拥有完整登记视图，消费方不再持有别家清单副本。

**范围内**：

1. 注册表：新建 6 张声明表（产品路由 / 数据源 / 能力 / 使用声明 / 种子 / 错误码），并把服务行（`sys_module`）与产品档案（`sys_product`）的写入口改到注册通道；
2. 注册协议：产品启动时单次全量上报本产品八类声明，平台按「本产品维度整体对账」落库（新增 / 覆盖 / 幂等 / 退役）；
3. 权威视图：平台启动自库构建进程内视图；产品启动经服务身份出口拉取快照并装入同一组视图；
4. 取数改源：`resolve_capability()` 读的位置不变（`collaboration_catalog_view()`），**变的是视图来源**（不再是本进程装载别家清单）；
5. 口径重写：`ops.seed_module`（服务目录种子）、`ops.gateway_config`（网关路由生成）、`ops.check_modules`（装载校验）改对注册表校验；`registry.product_manifests` 配置退役；
6. 失败语义：注册被拒、跨产品冲突、拉取失败、权威源不可读一律**拒启**并给出可定位信息。

**范围外**：租户拓扑与部署单元（07C）；能力分配记录机制（`02_04` 已交付，本任务只把「声明基线」改为自注册表重算）；前端目录消费（`03_02`）；后端消费方收编本身（`03_01`，本任务交付后按新取数源一次到位）。

**下游依赖**：`03_01` 暂停中，等本任务交付后按平台权威视图收编（见[《03_01 详细设计》§1 前置](../../03_消费方收编/03_消费方收编_01_后端消费方收编/设计/01_详细设计_01_后端消费方收编.md#scope)）。

## 2. 现状与缺口 <a id="current"></a>

| 项 | 现状 | 后果 |
| --- | --- | --- |
| 落库面 | 只有 `sys_module`（服务行）与 `sys_product`（产品档案）落库；产品路由 / 数据源 / 能力 / 种子 / 错误码 / 使用声明**均为内存视图**，来自清单装载 | 声明没有跨进程真相，重启即重算，无法对账 |
| 装载方式 | `load_product_manifests(paths)`：配置项 `registry.product_manifests` 注入路径 + 本仓 `deploy/registry/*.toml` 自动发现 | 平台要消费产品能力就得挂产品仓路径 → **跨仓文件依赖**；bms 单仓 CI 读不到 |
| 注册语义 | 无「注册」动作；产品是否已登记只能靠文件与装载日志推断 | 声明与视图无法对账，拼写错误只在拒启时暴露，且无法区分「未部署」与「写错了」 |
| 消费方取数 | `resolve_capability()` 读本进程装载视图 | 每个进程各持一份「真相副本」，对端改名/改路径要所有消费方同批改配置 |
| 校验基准 | 装载期校验以「本次装载的全部清单」为基准 | 部分装载即误判（见[03_01 设计 §2.3](../../03_消费方收编/03_消费方收编_01_后端消费方收编/设计/01_详细设计_01_后端消费方收编.md#current-gaps)） |

> 结论：**根因是「声明没有权威落点」**。`03_01` 卡在 `default_consumers` / `[[usages]]` 无法在本地判定，正是这一根因的表象。

## 3. 设计 <a id="design"></a>

### 3.1 注册表结构 <a id="tables"></a>

一类一表，与既有 `sys_module` / `sys_product` 同风格（`BaseModel` 公共字段、软删除、乐观锁、不做物理外键）：

| 表 | 承载 | 归属 | 表文件 |
| --- | --- | --- | --- |
| `sys_product_route` | 产品级路由（产品键 / 域段 / 承载服务键） | 平台服务库 `bms_platform` | [sys_product_route](../../../../../设计/数据库设计/数据表设计/sys_product_route.md) |
| `sys_data_source` | 数据源登记（键 / 类型 / 来源 / 路径 / 白名单 / 策略） | 同上 | [sys_data_source](../../../../../设计/数据库设计/数据表设计/sys_data_source.md) |
| `sys_collaboration` | 能力声明（第五类记录） | 同上 | [sys_collaboration](../../../../../设计/数据库设计/数据表设计/sys_collaboration.md) |
| `sys_collaboration_usage` | 消费方使用声明（第八类记录，含降级策略） | 同上 | [sys_collaboration_usage](../../../../../设计/数据库设计/数据表设计/sys_collaboration_usage.md) |
| `sys_seed` | 产品数据种子声明（第六类记录） | 同上 | [sys_seed](../../../../../设计/数据库设计/数据表设计/sys_seed.md) |
| `sys_errcode` | 错误码声明（第七类记录） | 同上 | [sys_errcode](../../../../../设计/数据库设计/数据表设计/sys_errcode.md) |
| `sys_module` / `sys_product` | 服务行 / 产品档案（**既有表，改写入方**） | 同上 | [sys_module](../../../../../设计/数据库设计/数据表设计/sys_module.md)、[sys_product](../../../../../设计/数据库设计/数据表设计/sys_product.md) |

统一口径（字段级结构只在表文件维护，本节不复制）：

- **归属列**：每表带 `product_key`，注册只能写自己名下记录；平台自身声明 `product_key = "platform"`。
- **唯一键**：`(product_key, <业务键>, deleted_at)`；跨产品同名即冲突（服务键 / 域段 / 事件域另按全局唯一校验）。
- **退役不删行**：本次全量上报未出现的记录置 `status = retired` + `retired_at`；再次出现恢复 `enabled`（历史可追）。
- **内容指纹**：每行存 `content_hash`（声明要素序列化后的稳定哈希），用于「内容未变不写」与变更检测。

### 3.2 注册协议（上报） <a id="protocol"></a>

| 项 | 口径 |
| --- | --- |
| 端点 | `PUT /api/v1/internal/declarations`（服务身份：`aud=service` 服务 JWT；`sub` 即注册方服务键） |
| 语义 | **单次全量**：请求体携带本产品八类声明全集，服务端按「本产品维度整体对账」 |
| 请求体 | `{product_key, service_key, contract_version, declarations: {products, services, product_routes, data_sources, collaborations, seeds, errcodes, usages}}`（各段为数组，缺段视为空集） |
| 响应体 | `{created, updated, unchanged, retired, warnings, snapshot_version}`（逐类计数 + 警示） |
| 幂等 | 同内容重复上报 → 全 `unchanged`，不写库；内容变化 → 覆盖并记变更日志（§3.3） |
| 跨产品冲突 | 同一键被其他 `product_key` 占用 → 409（`CatalogError`），响应含冲突键与占用方 |
| 契约定位 | **由注册方在本地完成**（它持有自己的 `deploy/contracts/<product>.json`）；平台侧只做跨产品一致性与形态校验，不再读产品仓契约文件 |
| 版本 | `contract_version` 随服务行；不一致按既有「契约主版本兼容」口径判定 |

**为什么单次全量**：服务重启幂等天然成立，且声明被删除时注册表能感知（整体对账 → 退役），避免「旧行永存」。

### 3.3 平台侧处理 <a id="server"></a>

`DeclarationRegistryService`（平台域 `platform_registry`）执行四步，全程在一个事务内：

1. **结构校验**：复用 `02_01` 的清单解析与要素校验（八类记录的 `kind` 要素匹配、分支标识长度与业务域一致性、错误码段位与撞码、种子入口可解析等）。
2. **跨产品一致性校验**（对注册表现状，而非本次提交）：
   - 能力名 / 服务键 / 域段 / 事件域 / 错误码全局唯一，冲突即拒；
   - 提供方业务域必须在域布局登记且承载服务键一致；
   - `default_consumers` 与 `[[usages]]` 的被消费能力必须**已注册**（这正是 `03_01` 卡住的那条校验，现在有真视图可判）；
   - 使用声明的写 / 强一致能力不得声明降级。
3. **落库对账**：按内容指纹分派 `created` / `updated` / `unchanged` / `retired`；`updated` 记结构化变更日志（`declaration_changed`，含类别、键、变更字段名）。
4. **视图刷新**：把本次结果投影进进程内视图族（`register_*`），并按 `02_04` 口径重算声明基线授权（`declare_capability_grants()` → `plan_grant_sync()` 落库）+ 失效授权视图快照。

**变更留痕**：结构化日志先落；变更进审计链登记为开放项（审计表分片归 29-审计合规）。

### 3.4 权威视图与出口 <a id="view"></a>

| 使用方 | 视图来源 | 时机 |
| --- | --- | --- |
| 平台进程 | **本库直读**（启动时把八类表投影进视图族） | 启动期（早于能力使用校验与授权同步） |
| 产品进程 | **拉取平台快照**（`GET /api/v1/internal/declarations/snapshot`，服务身份） | 启动期（早于任何取用与校验） |
| 浏览器 / 前端 | 既有目录出口 `GET /api/v1/modules/snapshot?with=products,collaborations`（**不含 path 与授权信息**，口径不变） | 运行期 |

- 服务身份完整面（新出口）返回八类声明的**完整要素**（含访问面路径、分支标识与动作名、承载服务键、访问面类别），供消费方取址与对账；
- 出口带 `snapshot_version`（注册表版本号，每次落库成功即递增），供消费方判定是否需要刷新；
- **不下发** `default_consumers` / 授权信息（归 `02_04` 的授权出口）。

### 3.5 取数改源与刷新 <a id="resolve"></a>

- `resolve_capability()`、`collaboration_catalog_view()`、`seed_catalog_view()`、`error_code_catalog_view()` 等**接口不变**，只换填充源（§3.4）；
- 产品进程在启动钩子里完成拉取并把八类记录 `register_*` 进视图，**晚于此步的任何取用**都能命中；
- 刷新策略：本任务为「启动期一次 + `snapshot_version` 记录」；运行期主动刷新（TTL / 推送）记为开放项，与 `02_02` §8 的缓存项合并评估；
- 平台进程不启动 HTTP 拉取（自己就是权威），避免自调用。

### 3.6 平台自身声明 <a id="self"></a>

平台也是声明方（`product_key = "platform"`）：启动时读**本仓** `deploy/registry/platform.toml`（不涉跨仓文件），走同一 `register()` 逻辑本地直调落库，再构建视图。**同一套校验、同一套表、无特例**。

`registry.product_manifests` 配置项退役：`config*.toml` 与 `backend/.env.example` 的注释同步删除，代码路径仅保留「本仓清单发现」用于平台自身与单仓自检。

### 3.7 口径重写 <a id="rewrite"></a>

| 入口 | 改造后 |
| --- | --- |
| `ops.seed_module`（服务目录种子） | 不再写 `sys_module` / `sys_product` 的产品行；退化为「引导性校验」——库空时提示先注册，库非空时校验平台自身行齐全（写方只剩注册通道） |
| `ops.gateway_config`（网关路由生成） | 支持两档：`--from-registry`（读库，部署态）与 `--from-manifest`（本仓清单自检，单仓 CI）；两档产物须一致 |
| `ops.check_modules`（装载校验） | 库可用时对「注册表 ↔ 本仓清单」双向对账（缺行 / 多余行 / 字段不符）；库不可用时只跑本仓清单自校验（单仓 CI），并显式提示「未接注册表」 |
| 权限码 / 菜单种子（`seed_menu` 等） | 不动（仍走 `02_03` 的平台统一调度，种子声明来自注册表） |

### 3.8 失败语义 <a id="failure"></a>

| 场景 | 处置 |
| --- | --- |
| 产品上报被拒（结构 / 一致性 / 冲突） | 产品**拒启**，错误信息含类别、键、冲突方（不静默降级） |
| 产品拉取快照失败 | 产品**拒启**（断链在启动期暴露） |
| 平台库不可读 / 未建表 | 平台**拒启**（权威源不可用；不再沿用「降级放行」） |
| 注册表为空（首次部署） | 平台自身注册完成后即可启动；产品首次上报即注册 |
| 声明内容变化 | 覆盖 + 结构化变更日志（不算失败） |

## 5. 行为等价与回归口径 <a id="equivalence"></a>

| 项 | 回归要求 |
| --- | --- |
| 视图内容 | 同一份声明经「注册 → 视图」后与「直接装载」逐字段一致（对账用例） |
| 服务目录 | `sys_module` 内容与改造前一致（平台行来自平台声明、产品行来自注册） |
| 种子编排 | `ops.seed_platform` 仍能取到产品种子声明并执行（来源改注册表，行为不变） |
| 错误码渲染 | 合并视图含平台码与产品码、无重复，渲染口径不变 |
| 网关路由 | `--from-registry` 与 `--from-manifest` 产物一致 |
| 取址 | `03_01` 收编后消费方取址结果与常量逐字一致（由 `03_01` 用例承接） |

| 14 | 拉取失败 | 产品拒启，信息含出口与状态码 |
| 15 | 注册失败 | 产品拒启，信息含类别 / 键 / 冲突方 |

| 20 | 字面量护栏 | 上述新增源码不引入产品字面量（`04_01`） |

## 7. 风险与边界 <a id="risk"></a>

| 风险 | 处置 |
| --- | --- |
| 产品启动依赖平台就绪（启动顺序耦合） | 明确「平台先起」的部署顺序（部署说明回写）；产品注册失败拒启并给出可操作信息 |
| 首次部署注册表为空 | 平台自身注册在启动早期完成，产品随后注册；顺序写进部署说明 |
| 声明演进导致视图频繁重建 | 内容指纹比对，未变不写；视图按类增量投影（不整表重建） |
| 拉取快照体积随产品数增长 | 出口只下发**注册表全量**（去重后按产品×类别组织）；规模评估归开放项 |
| 注册表与代码常量漂移（平台自身） | `ops.check_modules` 双向对账纳入预检；平台常量仍是平台自身声明的来源，注册即对账 |
| 退役记录误伤（产品临时只上报部分段） | 协议规定**八段全量**；缺段视为空集并在响应 `warnings` 明示退役条数（不静默） |
