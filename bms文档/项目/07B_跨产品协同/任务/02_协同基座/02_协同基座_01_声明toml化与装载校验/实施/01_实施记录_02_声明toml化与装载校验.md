## 2. 决策确认 <a id="decisions"></a>

实施前逐项确认 15 项设计决策、实施中确认 3 项范围变更（详见计划表「偏差与遗留」）：

| # | 事项 | 结论 |
| --- | --- | --- |
| 1 | 契约文件定位 | 清单同仓推导 `deploy/registry/x.toml` → `deploy/contracts/x.json`；取不到按后端工程根兜底；零新增配置 |
| 2 | 校验时点与阻断 | 装配期跑完整六类，任一失败抛 `CatalogError` 拒启；契约缺失同样拒启，仅显式环境变量可跳过并警示 |
| 3 | 业务域基准 | 平台 `deploy/boundaries/domain_layout.json` ∪ 清单同仓同类文件；本次为 mdm 新建域布局登记 `org` |
| 4 | mdm 能力段范围 | 8 个全量（`user-roles` / 4×`*.assign` / `dept-data` / `post-data` / `admin-codes`） |
| 5 | 种子段深度 | 清单写 `[[seeds]]` + mdm 可调用占位入口（不写库，真实播种归 `02_03`） |
| 6 | `default_consumers` 取值域 | 只允许服务键 / 产品键；前端可见性由能力快照下发决定（架构 §4.1「前端不参与分配」） |
| 7 | 访问面形态 | `kind` 单值 + `path`（内部写通道）与 `branch_op` 同时登记 |
| 8 | path 模板填充 | 记录自带 `path_template` + `render_path(**params)`（占位符缺失 / 多余即报错） |
| 9 | 字段映射写法 | 显式构造，与既有四类记录同风格（`kind` 条件必填就地判定） |
| 10 | 清单段名 | `[[collaborations]]`（与 `collaboration_catalog_view()` 一致） |
| 11 | 无产品包时种子校验 | 跳过并输出警示（不静默） |
| 12 | `frontend_prefix` 缺省 | 产品段取 `product_key`；域段取清单 `product_routes` 域段（**须唯一**），不可推导即拒启；`codes` 类不校验 |
| 13 | `branch_id` | **清单必填**（`txn-branch`），基座只校验全局唯一 + ≤ 16 字符（`MAX_BRANCH_ID_LENGTH`），不派生 |
| 14 | `tenant_base` | 本任务不落地（属服务行，归 `03_01` 恒开通清单去产品化）；已回写设计澄清 |
| 15 | 「缺能力」反例 | 只落「清单无能力段 → 装载成功、能力视图为空」；「声明未登记能力即拒启」归 `02_02` |
| 16 | mdm 侧是否同批收编基座新口径 | **同批收编**（前移 `bms-core` rev 会同时暴露 07C 按域改造的 API 漂移，必须一并适配） |
| 17 | 两仓切换前提 | 平台侧已解绑 mdm 清单路径（`config.dev.toml` 清空），两仓不再强制同批；本次仍同窗口完成 |
| 18 | 推送顺序 | bms 先推送（本地门禁全绿），mdm 随之（`bms-core` rev 依赖 bms 提交可达） |

## 3. 平台侧实施（bms） <a id="bms"></a>

| # | 落点 | 变更 |
| --- | --- | --- |
| 1 | `registry/products.py` | `tomllib` 解析（`.json` 直接拒收并提示「须为 toml」）；类型收紧（`build_batch` 非整数 / `cascade` 非布尔 / 字符串数组含非字符串即拒）；`ProductManifest` 增 `collaborations` / `seeds`；新增 `inspect_product_manifests()`（六类校验，装配期与门禁共用） |
| 2 | `services/module_registry.py` | `CollaborationKind`（`read` / `write` / `txn-branch` / `dataset` / `codes`）、`CollaborationStatus`（含 `deprecated`）；`CollaborationRecord` / `SeedRecord`（`BaseValueObject`，不落库）；`normalize_capability_path()`；`render_path()`；注册 / 视图 / 复位函数各一对 |
| 3 | 六类校验 | 能力重名（跨清单同名异值即拒）/ 提供方业务域未登记 / 归属不符 / 访问面不在对端契约（模板归一化比较）/ 契约版本主版本不兼容 / 种子入口不可解析；补充 `kind` 要素匹配、`default_consumers` 未登记、`branch_id` 唯一与长度、`frontend_prefix` 可推导 |
| 4 | `ops/check_modules.py` | 新增 `check_manifests()`：有配置则装载并校验（错误进明细、警示打印），无配置跳过并提示；校验入口唯一（未新增并行脚本） |
| 5 | 口径同步 | `datasource/registry.py` / `module_registry.py` / `products.py` 注释与 `config*.toml` / `.env.example` 的清单路径说明统一为 `.toml` |

## 6. 问题与处置 <a id="issues"></a>

| # | 问题 | 处置 |
| --- | --- | --- |
| 1 | 设计写「改 `config.dev.toml` 清单路径后缀」，实际该配置已于 2026-10-26 清空（产品字面量去基座），路径改由 `backend/.env` 注入 | 只改 `.env.example` 注释与注释口径；设计 §2/§4 回写偏差 |
| 2 | 设计示例 `default_consumers = ["platform","desktop"]` 与架构「前端不参与分配」冲突 | 确认取值域只允许服务键 / 产品键，`dept-data` / `post-data` 只写 `platform` |
| 3 | 设计 `frontend_prefix` 缺省「取同 `domain` 路由域段」在真实数据上不成立（能力域 `org` ≠ 路由域 `mdm`） | 规则改为「产品段取 `product_key`，域段取清单 `product_routes`（须唯一）」，并落可推导性校验 |
| 4 | 设计把 `tenant_base` 列进能力字段表，但示例写在 `services` 段，且 `ModuleRecord` 无该字段（接库对账会受影响） | 本任务不落地，回写设计澄清其属服务行、归 `03_01` |
| 5 | 能力 `branch_id` 设计称「缺省按业务域派生」，但 XA 分支标识有 16 字符硬上限（`MAX_BRANCH_ID_LENGTH`，根因为 MySQL `xid` ≤ 64 字节） | 确认改为清单必填，基座只校验唯一与长度 |
| 6 | mdm 锁定的 `bms-core`（`d2ba8c48`）早于 07C 按域改造：`MigrationChain` / `chain_tables` / `TableRecord.domain` 等 API 已变 | 本次一并收编（决策 16）：迁移清单按域、表归属补域、夹具改 `unit_tables` |
| 7 | 迁移测试的零漂移断言因基础设施表与版本记录表（`alembic_version_org`）报差异 | 断言口径明确：基础设施表与版本记录表不进域清单元数据，只比对域表 |
| 8 | 种子入口用例原放 `backend/tests/`，选测范围（`services/*/tests`）未覆盖，覆盖率门禁判缺行 | 用例移到 `services/org/tests/test_seeds.py`，与包代码同工程 |
