# 声明 toml 化与装载校验详细设计

> 跨产品协同 · 02 协同基座 · 01 声明 toml 化与装载校验 · 详细设计（开发核心文档）

[文档首页](../../../../../../文档首页.md) › [01 声明 toml 化与装载校验](../02_协同基座_01_声明toml化与装载校验.md) › 设计

## 1. 目标与边界 <a id="scope"></a>

**目标**：把产品自持清单由 json 改为 toml，并在既有四类记录（产品档案 / 服务行 / 产品路由 / 数据源）之上**新增两类记录**——能力（第五类）与种子；装载期完成六类校验，缺项即拒启；平台侧只读装载，不保存第二份手写源。

**范围内**：

1. 清单格式（toml）与字段语义；能力段与种子段的记录模型；
2. 解析器改造（`tomllib`）与既有字段映射保持等价；
3. 六类装载校验与错误信息（定位到能力名 / 种子名）；
4. 能力视图与种子视图（与既有视图族同构）；
5. 校验并入既有 `ops.check_modules`（不新增并行脚本）；
6. 两个仓的同批切换步骤与回滚口径。

**范围外**：消费方取用与失败语义（`02_02`）、能力分配记录（`02_04`）、种子调度执行（`02_03`）、平台种子去产品化（`03_03`）、能力文案与国际化的落地细节（随实施）。

## 2. 现状与读取点 <a id="current"></a>

**唯一解析器**：`bms_core/registry/products.py::load_product_manifest(path)` —— `json.loads` → `_as_mapping` → 四类记录构造（`_service_record` / `_data_source_record` / 产品档案 / 产品路由），产品归属逐条校验，`register_manifest()` 一次注册四类。

**既有视图族**：`service_catalog_view()`（平台常量 + 已装载服务行）、`product_catalog_view()`（平台种子 + 已装载产品档案）；数据源与产品路由各自有注册与视图；唯一性纪律统一为「同键同值合并、同键异值即拒」。

**读取点（2026-10-24 检索）**：

| 仓 | 文件 | 是否直接解析 json | 处置 |
| --- | --- | --- | --- |

| bms | `scripts/tools/deploy/release.py`、`scripts/tools/base_check/check_system_fields.py`、`check_service_boundaries.py` | 待实施时逐个确认 | 若有直读则同步改 |
| mdm | `backend/ops/check_modules.py`、`check_forms.py`、`contract_snapshot.py`、`migrate.py`、`event_contracts.py` | 否（经装载器 / 路径参数） | 确认参数与扩展名 |

## 3. 目标设计 <a id="design"></a>

### 3.1 清单格式（toml） <a id="format"></a>

单文件自持，六段并列；除 `product_key` 外各段可缺省（缺省视为空数组，与现状一致）。

```toml
# 产品自持声明（示例：mdm）
product_key = "mdm"

[[products]]
product_key = "mdm"
name = "主数据管理"
frontend_package_source = "mdm#frontend"
status = "enabled"

[[services]]
module_key = "mdm"
service_key = "mdm"
name = "mdm 主数据服务"
table_prefix = "mdm_"
business_code = "mdm"
errcode_segment = "33"
event_domain = "mdm"
service_group = "product"
build_batch = 3
service_version = "0.1.0"
contract_version = "0.1.0"
tenant_base = true          # 租户恒开通（角色 / 用户组织归属依赖，关闭将使主体链不可用）

[[product_routes]]
product_key = "mdm"
domain = "mdm"
service_key = "mdm"
description = "主数据对外命名空间"

[[data_sources]]
data_source_key = "mdm_dept"
name = "部门"
kind = "dict"
data_source = "mdm.mdm.dept"
origin = "product"
path = "/data-source/dept-tree"
allowlist = ["code", "label"]
cascade = true
strategies = ["select", "region", "match"]

# ---- 能力（第五类记录）----
[[collaborations]]
name = "mdm.org.user-roles"
domain = "org"
kind = "read"
path = "/api/v1/mdm/user-roles"
contract_version = "0.1.0"
default_consumers = ["platform"]

[[collaborations]]
name = "mdm.org.user-posts.assign"
domain = "org"
kind = "txn-branch"
path = "/api/v1/mdm/internal/user-posts/{user_id}"
branch_op = "mdm.user-posts.assign"
contract_version = "0.1.0"
default_consumers = ["platform"]

[[collaborations]]
name = "mdm.org.dept-data"
domain = "org"
kind = "dataset"
path = "/api/v1/mdm/data-source/dept-tree"
data_source_key = "mdm_dept"
frontend_prefix = "mdm"
contract_version = "0.1.0"
default_consumers = ["platform", "desktop"]

[[collaborations]]
name = "mdm.org.admin-codes"
domain = "org"
kind = "codes"
contract_version = "0.1.0"
permission_codes = ["mdm:query", "mdm:create", "mdm:update", "mdm:delete"]
default_consumers = ["platform"]

# ---- 种子 ----
[[seeds]]
name = "mdm-admin-codes"
module = "mdm.seeds.permissions"
entry = "seed_admin_codes"
after = []
description = "管理面业务码与权限码"
```

**字段语义**：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `name` | 是 | 能力名，全局唯一，形如 `{product}.{domain}.{capability}`；与 provider 实现标识解耦 |
| `domain` | 是 | 提供方**业务域**标识（须在业务域清单登记，见 07C `01_01`） |
| `kind` | 是 | `read`（契约读出口）/ `write`（内部写通道）/ `txn-branch`（事务参与分支）/ `dataset`（参考数据出口）/ `codes`（业务语义要素集合） |
| `path` | 视 kind | `read` / `write` / `txn-branch` / `dataset` 必填；须能在对端契约 `paths` 中定位（参数模板按 `{name}` 归一化） |
| `product_key` | 否 | 能力对外暴露的**产品命名空间段**（前端取址用）；缺省取清单 `product_key` |
| `branch_id` | `txn-branch` 必填 | 事务参与者的稳定短标识（XA 分支标识）；缺省按业务域派生，历史映射保留（如 `mdm` → `m`），**一经确定不随版本漂移** |
| `branch_op` | `txn-branch` 必填 | 分支动作名 |
| `data_source_key` | `dataset` 必填 | 关联的数据源登记键 |
| `permission_codes` | `codes` 必填 | 业务码 / 权限码集合 |
| `frontend_prefix` | 否 | 前端命名空间前缀；缺省取 `product_routes` 中同 `domain` 的域段 |
| `contract_version` | 是 | 与 `services` 段登记的 `contract_version` 主版本须一致 |
| `default_consumers` | 否 | 默认分配消费方（能力分配见 `02_04`）；引用者须为已登记的服务键或产品键 |
| `status` | 否 | `enabled` / `disabled` / **`deprecated`**（弃用），缺省 `enabled`；弃用期间仍下发，但标注替代能力 |
| `replacement` | `deprecated` 必填 | 替代能力名（弃用期消费方的迁移目标） |
| `tenant_base` | 否 | 布尔，缺省 `false`；为真表示该模块**租户恒开通**（基座恒开通清单由「平台常量 + 已装载且置真的产品模块」合成，产品标识不再写进基座常量） |

**种子字段**：`name`（唯一）/ `module`（点分模块路径）/ `entry`（入口函数名）/ `after`（依赖的其他种子名，可空）/ `description` / `status`。

**补充校验**：`tenant_base = true` 的模块须为 `product` 分组，且其 `table_prefix` 与 `module_key` 一致（沿用既有校验口径）；`tenant_base` 与非产品分组同时出现即报错。

### 3.2 解析与映射 <a id="parse"></a>

1. **解析**：`tomllib.loads(path.read_text(encoding="utf-8"))`；`TOMLDecodeError` → `CatalogError("产品清单 TOML 非法：{path}（{exc}）")`；`OSError` 沿用现有错误文案。
2. **结构等价**：toml 解析结果与现 json 结构的差异只有「数组表」形态，映射后**逐字段等价**——`_as_mapping` / `_require` / `_strings` / `_records` 全部复用，不重写。
3. **类型收紧（新增）**：`build_batch` 若为非整数、`cascade` 若为非布尔、`allowlist` / `strategies` / `default_consumers` / `permission_codes` / `after` 若含非字符串项 → 报结构非法（现状静默转换，改为显式拒绝，避免 toml 与 json 类型差异带来隐性错值）。
4. **扩展名分派**：读取器**只接受 `.toml`**；遇 `.json` 直接报「请改用 toml 自持声明」（直接切换口径），不复留兼容分支。

### 3.3 记录模型与视图 <a id="records"></a>

**新增数据类**（与既有记录同风格：`@dataclass(frozen=True)`、继承 `BaseRegistryRecordContract`）：

- `CollaborationRecord`：字段同 §3.1 能力段；唯一键 `name`。
- `SeedRecord`：字段同 §3.1 种子段；唯一键 `name`。

**注册与视图**（与既有视图族同构，不新建第二套注册表）：

| 函数 | 语义 |
| --- | --- |
| `register_collaboration_records(records)` | 装载能力记录；同 `name` 同值合并、异值即拒（`CatalogError`） |
| `register_seed_records(records)` | 同上（唯一键 `name`） |
| `collaboration_catalog_view()` | 能力合并视图（平台侧为空 + 已装载记录，插入序） |
| `seed_catalog_view()` | 种子合并视图 |
| `reset_*_records()` | 测试隔离用（生产路径不调用） |

`ProductManifest` 增加两个字段 `collaborations` / `seeds`（`ConcurrentStableFrozenList` 类型），`register_manifest()` 同步注册六类。

### 3.4 六类装载校验 <a id="validate"></a>

装载期逐条校验，**任一不满足即 `CatalogError` 拒启**，信息统一带「清单路径 + 段名 + 记录标识」：

| # | 校验 | 判定 | 错误信息示例 |
| --- | --- | --- | --- |
| 1 | 能力重名 | 同一清单内或跨清单出现相同 `name` 且字段不一致 | `产品清单能力重名：mdm.org.user-roles（清单 a.toml 与 b.toml）` |
| 2 | 提供方业务域未登记 | `domain` 不在业务域清单（07C `01_01` 的清单常量或登记视图） | `能力 mdm.org.user-roles：提供方业务域未登记（org）` |
| 3 | 归属不符 | 记录的 `product_key`（若声明）与清单 `product_key` 不一致（沿用现状口径，扩到能力与种子） | 现有文案扩展 |
| 4 | 访问面不在对端契约 | `kind != "codes"` 时，`path` 归一化后不在 `deploy/contracts/<product_key>.json` 的 `paths` 键集合内 | `能力 mdm.org.user-roles：访问面不在对端契约（/api/v1/mdm/user-roles）` |
| 5 | 版本不兼容 | `contract_version` 主版本与 `services` 段登记的 `contract_version` 主版本不同 | `能力 mdm.org.user-roles：契约版本不兼容（能力 0.1.0 / 服务 0.2.0）` |
| 6 | 种子入口不可解析 | `module` 可导入且 `entry` 可调用（仅在提供方包可导入时校验；CI 单仓无产品包时**跳过并输出警示**，不得静默通过） | `种子 mdm-admin-codes：入口不可解析（mdm.seeds.permissions:seed_admin_codes）` |

**补充校验**（与分配相关，落地在 `02_04`，本节只提供判定函数）：`default_consumers` 中的标识须为已登记服务键或产品键，否则报「默认消费方未登记」。

**契约缺失语义**：清单要求定位但契约文件不存在 → 报错（不静默通过）；仅当显式声明「跳过契约定位」环境变量时跳过并输出警示（供无契约的极简环境使用）。

### 3.5 校验入口并入既有脚本 <a id="entry"></a>

- `ops.check_modules` 增加两段：**能力段校验**（§3.4 的 1~5）与**种子段校验**（§3.4 的 6），复用同一 `validate_manifest()`；
- 不新增 `check_collaboration` 脚本（拍板口径：校验入口唯一）；
- `--offline` 语义保持：离线只做清单自校验与服务包声明比对，接库部分不变。

### 3.6 两仓切换步骤 <a id="switch"></a>

直接切换（不留 json 兼容分支），同一提交窗口内完成：

1. **mdm**：`deploy/registry/mdm.json` → `mdm.toml`（内容按 §3.1 补齐能力段与种子段）；确认 5 个 ops 的清单参数与扩展名；
2. **bms**：解析器改 toml、新增记录与视图、`config.toml` / `config.dev.toml` 的 `product_manifests` 路径改 `.toml`；
3. **同一窗口推送**（中间窗口允许一方短暂红）；
4. 两仓各跑：`ops.check_modules`（离线 + 接库）、`preflight --fast`；bms 侧另跑装载与视图单测。

**回滚**：两仓回退到切换前提交即可（tf 无迁移、无数据变更，回滚只涉及文件与代码）。

## 4. 影响面 <a id="impact"></a>

| 类别 | 对象 | 变更 |
| --- | --- | --- |
| 修改 | `bms_core/registry/products.py` | toml 解析、类型收紧、两类新记录、六类校验 |
| 修改 | `bms_core/services/module_registry.py` | 新增 `CollaborationRecord` / `SeedRecord` 的注册与视图（沿用同键同值/异值即拒） |
| 修改 | `ops/gateway_config.py` | 若直读清单则改经装载器 |
| 修改 | `config.toml` / `config.dev.toml` | `product_manifests` 后缀改 `.toml` |
| 修改 | mdm `deploy/registry/mdm.json` → `mdm.toml`；mdm 侧 5 个 ops 参数确认 | 清单文件与读取口径 |
| 修改 | `ops/check_modules.py` | 增能力与种子两段校验 |

| 不变 | 装配与接库对账、网关路由生成、表结构变更清单 | 不涉 |

**行为兼容**：`product_manifests` 为空时行为与现状完全一致（空清单、平台照常）；清单缺段视为空数组。

## 5. 测试设计 <a id="test"></a>

| # | 用例 | 断言 |
| --- | --- | --- |
| 1 | 完整 toml 装载（六段齐备） | 六类记录数量与字段逐一正确；`service_catalog_view()` / `product_catalog_view()` / `collaboration_catalog_view()` / `seed_catalog_view()` 合并顺序正确（平台在前） |
| 2 | 缺段清单（仅 `product_key`） | 装载成功、各视图等于平台侧内容，无异常 |
| 3 | 能力重名（跨清单同名异值） | 抛 `CatalogError`，信息含能力名 |
| 4 | 提供方业务域未登记 | 抛错，信息含业务域名 |
| 5 | 访问面不在契约（路径拼错 / 参数模板不同写法） | 拼错即抛错；参数模板归一化后视为同一路径（正例） |
| 6 | 版本不兼容（能力主版本 ≠ 服务主版本） | 抛错，信息含两侧版本 |
| 7 | `kind` 与要素不匹配（`txn-branch` 缺 `branch_op`、`dataset` 缺 `data_source_key`） | 各自抛错 |
| 8 | 种子入口不可解析（模块不存在 / 入口不存在 / 不可调用） | 三种均抛错并定位 `module:entry` |
| 9 | 种子入口校验在无产品包环境 | 跳过并输出警示（不静默通过） |
| 10 | 以 `.json` 交付清单 | 抛错并提示改用 toml |
| 11 | 类型收紧（`build_batch` 为非整数、`cascade` 为非布尔、数组含非字符串） | 各自抛结构非法 |
| 12 | 同键同值重复装载（幂等） | 不报错、视图不重复 |
| 13 | 契约文件缺失 | 抛错；显式跳过变量下跳过并警示 |
| 14 | 既有四类行为回归 | 服务行 / 产品路由 / 数据源 / 产品档案装载与对账结果与切换前一致 |

## 6. 风险与边界 <a id="risk"></a>

| 风险 | 处置 |
| --- | --- |
| toml 与 json 的数组表写法被写错（多段少段） | 装载期结构校验 + 清单模板随仓提供；错误信息定位到段名与记录标识 |
| 直接切换导致一侧短暂红 | 已知并接受；同一窗口推送 + 切换后立即各跑自检 |
| 契约定位过严（路径参数模板写法差异） | 归一化：`{任意名}` 统一为 `{}` 比较；对 `path` 只比对路径形态，不比对参数名 |
| 业务域清单尚未在代码内可用 | 本任务以 07C `01_01` 的清单为来源，先落为常量/登记视图；业务域授权码化由 `03_01` 承接 |
| 种子入口校验依赖产品包可导入 | 不可导入时跳过并警示；CI 拉产品仓清单场景（`04_02`）下可完整校验 |

## 7. 开放项 <a id="open"></a>

| # | 事项 | 归口 |
| --- | --- | --- |
| 1 | 能力 `kind` 是否再细分读写（当前 `read` / `write` 已分） | 出现"同能力既要读又要写"时按两能力登记，不新增枚举 |
| 2 | `frontend_prefix` 缺省取值的最终规则 | `03_02`（前端取址）落地时定 |
| 3 | 业务域清单在代码中的载体（常量或登记文件） | `03_01` / `03_02` 落地时定，本任务只依赖其可用性 |
| 4 | 能力文案与国际化（错误信息、快照描述） | 随实施，不阻塞机制 |
