# 能力分配与授权详细设计

> 跨产品协同 · 02 协同基座 · 04 能力分配与授权 · 详细设计（开发核心文档）

[文档首页](../../../../../../文档首页.md) › [04 能力分配与授权](../02_协同基座_04_能力分配与授权.md) › 设计

## 1. 目标与边界 <a id="scope"></a>

**目标**：把「谁能用谁的能力」落成**授权记录**（能力 × 消费方），并由此派生出站 scope、入站校验与监控维度——使「有授权即合法（直连或中转）、无授权即越界」可判定、可审计、可归因。

**范围内**：

1. 授权记录的存储（`sys_capability_grant`，表结构见数据库设计表文件）与两层来源（声明默认 / 人工授予）及其优先级；
2. 三类派生：出站 scope、入站校验、监控维度；
3. 合法性判定与拒绝语义；撤销与有效期；
4. 审计与指标；管理面 API；
5. 与既有 `require_service` 白名单的**迁移口径**。

**范围外**：能力声明与装载校验（`02_01`）、能力取用与降级语义（`02_02`）、拓扑解析（07C `02_02`）、各消费方收编（`03_01`）。

## 2. 现状 <a id="current"></a>

| 项 | 事实 |
| --- | --- |
| 授权 | 无记录。跨产品调用靠**代码里的调用方白名单**（platform 三处入站：用户只读出口 / 权限失效 / 系统参数内部读），改一次要改代码 |
| 出站 | 服务令牌按 `aud=service` 签发，scope 由调用方自填（形如 `mdm:write`），无「是否被授权」的校验 |
| 入站 | `require_service("<服务标识>")` 硬编码；未登记服务一律拒（`330101` 类） |
| 归因 | 调用侧日志有服务标识，但无「调用方 × 能力」维度；越权尝试无专门指标 |

## 3. 目标设计 <a id="design"></a>

### 3.1 记录与表 <a id="record"></a>


**唯一性**：`(capability_name, consumer_key, deleted_at)` 一行一条；撤销不删行。

**为什么落库而非只靠声明**：声明是部署期产物（随产品发版），而授权需要**运营期调整与撤销即时生效**，并要留审计——两者性质不同，故「声明给默认、库表管现状」。

### 3.2 两层来源与优先级 <a id="priority"></a>

| 场景 | 处置 |
| --- | --- |
| 启动装载：声明中有、库中 `source=declared` | 幂等更新（状态、直连许可、有效期以外的声明字段） |
| 启动装载：声明中移除了某消费方，库中 `source=declared` | 置 `status=disabled` + `revoked_at` + `note="声明移除"`（**保留历史**，不物理删） |
| 启动装载：库中 `source=manual`（无论声明有无） | **不覆盖、不禁用**；仅在装载报告中输出「声明与人工不一致」警示 |
| 人工授予 | UPSERT 为 `source=manual, status=enabled`，记 `granted_by/granted_at/note` |
| 人工撤销 | `status=disabled` + `revoked_at` + `source=manual`（声明装载不会把它重新打开） |

**一句话**：**声明是基线，人工是覆盖**；人工一旦介入该条记录，声明不再改动它。

### 3.3 三类派生 <a id="derive"></a>

| 派生 | 输入 | 输出 | 用途 |
| --- | --- | --- | --- |
| **出站 scope** | `consumer_key` = 当前服务 | 该消费方被授权的 `(提供方业务域, kind)` 集合 | 签发服务令牌时生成 scope（`{domain}:read` / `{domain}:write`；`txn-branch` 视作 `write`） |
| **入站校验** | `capability_name` = 当前端点对应能力 | 允许的 `consumer_key` 集合 | 中间件校验调用方是否被授权 |
| **监控维度** | 调用发生时的 `(capability, consumer)` | 指标标签 | 调用量 / 失败率 / 越权尝试按「调用方 × 能力」聚合 |

**缓存与失效**：三类派生结果进进程内缓存，键含「授权版本号」；授予 / 撤销后版本号递增，同一失效周期内生效（不要求跨实例强一致，但要求**有界**）。

### 3.4 合法性判定与拒绝 <a id="decide"></a>

```
授权有效 ⇔ 存在 (capability, consumer) 行 且 status=enabled 且 (expire_at 为 NULL 或 expire_at > now)
```

- **未授权**：入站拒绝并报明确错误（错误码沿用「服务身份未授权」语义，信息含 `capability` 与 `consumer`）；同时 `warning` 日志 + `capability_denied_total{capability, consumer}` 指标；
- **直连的唯一判据是有无有效分配**：有分配则直连与中转都合法；无分配只能经平台中转——不设独立于分配的“直连许可”维度；
- **已过期**：按未授权处置，错误信息标注「授权已过期」。

### 3.5 撤销与有效期 <a id="revoke"></a>

| 项 | 口径 |
| --- | --- |
| 撤销即时性 | 版本号递增 + 缓存失效，**有界生效**（不超过一个缓存周期） |
| 有效期 | `expire_at` 到期后运行时判定为无效；不依赖定时任务扫描 |
| 重授 | 同一 `(capability, consumer)` 行重新置 `enabled`，清 `revoked_at`，`granted_*` 更新 |
| 临时授权 | 必填 `expire_at` 与 `note`（理由），装载 / 授予时校验——避免长期留存的“排障授权” |

### 3.6 审计与指标 <a id="audit"></a>

| 项 | 要求 |
| --- | --- |
| 审计 | 授予 / 撤销 / 声明装载引发的状态变更三类动作进审计链（`sys_data_audit_log`），含 `capability` / `consumer` / 变更前后状态 / 来源 |
| 指标 | `capability_denied_total{capability, consumer}`（越权尝试）、`capability_grant_active{capability}`（有效授权数，可选 gauge） |
| 日志 | 拒绝为 `WARNING`；装载不一致为 `WARNING`；声明移除为 `INFO`（附 `note`） |

### 3.7 与既有 `require_service` 的迁移口径 <a id="migrate"></a>

| 阶段 | 入站校验来源 |
| --- | --- |
| 迁移期（本任务落地后、收编前） | 已声明能力的端点 → 按授权记录判定；未声明能力的端点 → 沿用既有 `require_service` 白名单 |
| 收编后（`03_01` 完成） | 全部端点按授权记录判定；代码内不再有调用方字面量 |

**端点 → 能力的反查**：按能力声明的 `path`（参数模板归一化为 `{}`）与 HTTP 方法匹配；一个端点命中多个能力时取首个匹配并记录 `INFO`（设计上应一一对应，出现多命中视为清单问题）。

### 3.8 管理面 API <a id="api"></a>

| 方法 | 路径 | 语义 |
| --- | --- | --- |
| GET | `/api/v1/capability-grants` | 分页查询（按能力 / 消费方 / 状态筛选） |
| POST | `/api/v1/capability-grants` | 授予（幂等键 + 有效期 + 理由） |
| DELETE | `/api/v1/capability-grants/{grant_id}` | 撤销（软撤销，保留历史） |

权限：复用平台管理面权限码（实施时按《[命名规范](../../../../../../规范/命名规范.md)》定码，归平台注册与目录业务域）；写操作进审计。

## 5. 测试设计 <a id="test"></a>

| # | 用例 | 断言 |
| --- | --- | --- |
| 1 | 声明默认装载（库中无记录） | 插入 `source=declared` 行，`status=enabled` |
| 2 | 重复装载（幂等） | 不产生重复行、字段不变 |
| 3 | 声明移除消费方 | 行置 `disabled` + `revoked_at`，历史保留 |
| 4 | 人工撤销后又装载声明 | 人工撤销**不被覆盖**，仍为 `disabled`，报告含不一致警示 |
| 5 | 人工授予后再装载声明 | 行保持 `source=manual`，声明值不覆盖 |
| 6 | 出站 scope 派生 | scope 集合与授权记录一致；`txn-branch` 归入 `write` |
| 7 | 入站校验：有授权 | 放行 |
| 8 | 入站校验：无授权 | 拒绝，错误信息含能力名与消费方，`capability_denied_total` +1 |
| 9 | 入站校验：授权已过期 | 拒绝并标注“已过期” |
| 10 | 无有效分配时的直连 | 视为越界拒绝（直连的唯一判据是有无分配） |
| 11 | 撤销后调用 | 一个缓存周期内变为拒绝 |
| 12 | 临时授权缺 `expire_at` 或 `note` | 拒绝授予（校验错误） |
| 13 | 端点反查能力（参数模板不同写法） | 归一化后命中同一能力 |
| 14 | 一端点多能力命中 | 取首个并记 `INFO`（不报错） |
| 15 | 管理面三端点 | 分页 / 授予 / 撤销行为正确；写操作进审计 |
| 16 | 迁移期分流 | 已声明端点走授权表、未声明端点仍走既有白名单 |
| 17 | 消费方未登记 | 装载期报错（授权引用完整性） |

## 6. 风险与边界 <a id="risk"></a>

| 风险 | 处置 |
| --- | --- |
| 声明与人工授权互相打架 | 优先级固定为「人工覆盖声明」，装载报告输出不一致清单；不静默择一 |
| 缓存导致撤销不即时 | 明确“有界生效”，文档与错误信息不含“立即失效”承诺；关键场景可主动失效 |
| 端点反查能力不准（参数模板 / 同路径多方法） | 归一化比较 + 多命中记 `INFO`；清单层面要求一能力一路径 |
| 迁移期两套校验并存 | 按端点是否声明能力分流，边界清晰；收编后统一，登记于 `03_01` 完成标准 |
| 授权行数增长（能力 × 消费方） | 唯一索引 + 按消费方 / 能力两个方向索引；量级受能力数约束，不分片 |
