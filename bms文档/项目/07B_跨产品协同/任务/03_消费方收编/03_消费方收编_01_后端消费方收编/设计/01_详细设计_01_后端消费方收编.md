## 1. 目标与边界 <a id="scope"></a>

**目标**：把后端五类跨产品消费点从「写死对端标识与访问面」改为「按能力名取用」与「按授权派生白名单」，**行为等价**地去掉产品字面量。

**范围内**：

1. 权限解析器（读出口）；
2. 用户保存编排（内部写通道 + 事务分支动作名 + 分支标识）；
3. 角色保存编排（同构两组）；
4. 三处入站白名单中与产品相关的部分；
5. 基座「租户恒开通模块」清单中的产品标识。

**范围外**：平台内部服务间白名单（`identity` 等，属平台内部，不在本专项）；前端（`03_02`）；平台种子（`03_03`）；能力视图与授权机制的实现（`02_02` / `02_04`）；产品→平台注册通道与权威视图（`02_06`）。

**前置（2026-10-27 补充）**：本任务的**取数源**改为 `02_06` 交付的平台权威视图——消费方不再各自装载对端清单。故本任务暂停、排在 `02_06` 之后；本设计保留的「清单声明」（§3.5.1 / §3.7）在 `02_06` 之后作为**注册输入**，内容与口径不变（§9 偏差 13）。

### 2.3 与代码不符的设计假设（两处缺口） <a id="current-gaps"></a>

**缺口 A：`platform.*` 三项能力与平台清单缺声明**

| 事实 | 证据 |
| --- | --- |
| 三个能力名全仓只在文档出现（本设计 §3.5、《跨产品协同登记清单》§2、`02_04` 设计示例），源码与清单零命中 | 全仓检索 `platform.user.query` / `platform.permission.invalidate` / `platform.config.snapshot` |
| `deploy/registry/platform.toml` 只有 `product_key` 与 9 条 `[[seeds]]`；无 `[[collaborations]]`，也无 `[[services]]` / `[[product_routes]]` | 清单全文 |
| 平台服务未覆写 `capability_usages()`（`backend/services/` 全仓零命中）——平台作为 mdm 消费方的降级策略目前无处声明 | 检索 `capability_usages` |

按现有装载器与入站依赖实现读出的后果：

1. `require_capability("<能力名>")` → `check_capability_access()` → `capability_domain()` 对**未登记能力抛 `CatalogError`（拒启级）**，不是 403；未声明就切换端点，未授权场景会退化成 500。
2. 能力名第二段是**业务域**且须在 `deploy/boundaries/domain_layout.json` 登记并带 `service_key`；平台侧已登记域为 `user` / `role` / `permission_meta` / `menu_form` / `platform_config` / `platform_registry` / `task`——设计所用的 `permission` 与 `config` **不是已登记域**。
3. 非 `codes` 能力须能推导 `frontend_prefix`（`product_routes` 域段唯一或显式声明）；platform.toml 无 `product_routes`，须逐条显式声明。
4. `default_consumers` 须落在「已登记服务键 / 产品键」集合（`SERVICE_CATALOG` 常量 + 本次装载清单）：产品字面量已从平台常量移除（`02_01`），`mdm` 只在装载 mdm 清单时可见 → **bms 单仓（`registry.product_manifests` 为空）声明 `default_consumers = ["mdm"]` 会被判「默认消费方未登记」**。
5. 访问面须能在 `deploy/contracts/platform.json` 定位：三个路径均在（`/api/v1/platform/internal/users/query`、`/api/v1/platform/internal/permissions/invalidate`、`/api/v1/platform/internal/configs/resolve`）——此项无障碍。

**缺口 B：`tenant_base` 清单字段与 `tenant_base_module_keys()` 不存在**

| 事实 | 证据 |
| --- | --- |
| `tenant_base` 字段在服务行解析（`registry/products.py`）、`ModuleRecord`、mdm 仓 `mdm.toml` 服务行均无 | 检索 + 清单 |
| `tenant_base_module_keys()` 全仓不存在；现状是**常量** `TENANT_BASE_MODULE_KEYS`（`module_registry.py` 741，`"mdm"` 在 753） | 源码 |
| 该常量被**直接读取**两处：`bms_tenant` 的 `tenant_module.py` 192（开通恒开通模块）/ 273（勾选拦截）；另有 `bms_core` 测试断言它与可勾选清单不相交 | 源码 |

后果：

1. 设计 §3.6「函数签名与返回类型不变、调用方零改动」的前提不成立——须新增函数并改两处调用点（常量在 import 期求值，早于清单装载，无法承载「已装载声明」）。
2. `tenant_base = true` 须写在 **mdm 仓** `deploy/registry/mdm.toml` 的服务行，属跨仓改动；不声明就直接移除常量中的 `"mdm"`，恒开通集合随之改变（RBAC 主体链所在模块被移出恒开通）。
3. 服务行新增字段属清单结构扩展，须同步装载器解析与校验（沿用既有「产品分组 + 表前缀一致」口径）。

## 3. 设计 <a id="design"></a>

### 3.1 权限解析器（读出口） <a id="resolver"></a>

| 项 | 改造前 | 改造后 |
| --- | --- | --- |
| 服务标识 | 常量 `MDM_SERVICE_KEY = "mdm"` | 删除；由 `resolve_capability("mdm.org.user-roles").target.service_key` 提供 |
| 路径 | 常量 `/api/v1/mdm/user-roles` | 删除；由 `resolve_capability(...).path` 提供 |
| 请求构造 | 手写 `ServiceRequest(service=…, path=…)` | `build_capability_request(endpoint, method="GET", query=…)`（目标服务与路径均取自已解析能力） |
| 降级 | 异常一律降级为空集 | 非严格模式经 `call_capability(..., fallback=空集)`，策略在平台服务 `capability_usages()` 声明 `CapabilityUsage("mdm.org.user-roles", degrade="empty", reason=…)`；降级日志与指标由基座一次完成 |
| 严格模式 | 失败抛 `InternalError`（10002） | **不变**：严格模式不走 `call_capability` 的降级通道（声明是一次性的、不能按实例分档），改由 `resolve_capability` + 直接调用 `_fetch()`，异常按既有 `_degrade()` 口径抛 `InternalError` |
| 指标 | 无 | 非严格模式由 `call_capability` 打点；严格模式失败仅上抛（与现状同，不新增指标口径） |

**行为等价**：能力解析结果与既有常量一致（同一服务键、同一路径、同一 `data.role_ids` 解析）；严格模式仍抛 `InternalError`；非严格模式仍返回空集——差别仅在「降级现在有声明、有日志、有指标」。

> 声明按「已装载视图过滤」落（§9 偏差 5）：单仓未装载 mdm 清单时不声明，`call_capability` 无声明即上抛，故平台单仓环境该路径不做降级（该环境本无组织域可取数）。

### 3.2 用户保存编排（写 + 事务分支） <a id="user-assign"></a>

| 项 | 改造前 | 改造后 |
| --- | --- | --- |
| 库键派生 | `build_tenant_db_key(..., service=MDM_SERVICE)` | 先取拓扑解析结果 `endpoint.target.db_keys`；**为空集时回退** `build_tenant_db_key(..., service=endpoint.target.service_key)`（`CapabilityTarget.db_keys` 契约原文：空集＝未由拓扑解析，消费方沿用既有按服务键派生） |
| 分支规格 | `BranchSpec(branch_id=BRANCH_ID_MDM, service=MDM_SERVICE, db_key=...)` | `BranchSpec(branch_id=branch.branch_id, service=branch.service_key, db_key=branch.db_key)`（`branch=branch_target(整组端点)`，见 §3.4 与 §9 偏差 14 / 15） |
| 分支执行请求 | `ServiceRequest(service=MDM_SERVICE, path=BRANCH_EXECUTE_PATH)` | `service=branch.service_key`、`path` 仍为 `BRANCH_EXECUTE_PATH`（平台级参与端点约定，非产品访问面，不属能力声明范围） |
| 顺序提交路径 | `path=MDM_INTERNAL_USER_POSTS_PATH.format(user_id=...)` | `build_capability_request(endpoint, method="PUT", params={"user_id": …}, json_body=…, headers=…, tenant_id=…)`（`{user_id}` 由模板渲染，幂等键经 `headers` 传） |
| 分支动作名 | `ops.add((MDM_USER_POSTS_OP, ...))` | `ops.add((endpoint.branch_op, ...))`（岗位 / 部门各取各自能力的 `branch_op`） |
| 能力名 | — | `mdm.org.user-posts.assign` / `mdm.org.user-depts.assign` |
| 解析时机 | — | 每次 `apply()` 惰性解析（不缓存到实例）：声明变更即时生效，且与「装配期不解析」口径一致 |
| 失败语义 | 失败即抛（现状已是 fail-closed） | 保持 fail-closed；解析失败（能力缺失 / 禁用）与调用失败一律整单失败；**禁止**新增降级声明 |

**等价性**：路径模板、方法与动作名均取自能力声明，与既有常量逐字一致（`mdm.toml` 已声明 `branch_id = "m"` / `branch_op = "mdm.user-posts.assign"` / `path = "/api/v1/mdm/internal/user-posts/{user_id}"`）；XA 与顺序提交两条路径的判定条件不变。

### 3.3 角色保存编排（同构） <a id="role-assign"></a>

改造方式与 §3.2 完全同构，能力名换为 `mdm.org.role-posts.assign` / `mdm.org.role-depts.assign`，库键、分支规格、分支执行请求、动作名、内部通道路径同样取自已解析能力；失败语义同为 fail-closed。

### 3.4 分支标识的派生（不再写死单字符） <a id="branch"></a>

现状 `BRANCH_ID_MDM = "m"` 是 XA 事务内的参与者标识。改造后的口径：

| 项 | 口径 |
| --- | --- |
| 取值来源 | `endpoint.branch_id`（`mdm.toml` 的 `[[collaborations]].branch_id`，`02_02` 已装载）；实现上由 `branch_target()` 汇总为值对象 `OrgBranch`（§9 偏差 14） |
| 历史兼容 | 声明里的值就是历史值 `"m"`——**保留历史映射不是新增一层映射表，而是保持声明值不变**；升级前已进入 `txn_global_branch` 的事务仍能按原 ID 恢复 |
| 唯一性 | 装载期校验已断言「同一 `branch_id` 不得跨业务域混用」；运行期同一事务内平台侧仍用 `BRANCH_ID_PLATFORM`（`"p"`，平台自有、非产品字面量，保留） |
| 稳定性 | 声明值一经确定不得随版本漂移（清单注释与装载校验共同约束） |

> 该字段是事务账本的对外形态，改动须保守：**只换取值来源，不换值**。平台分支标识 `"p"` 属平台自身，不纳入本任务。

### 3.5 三处入站白名单 <a id="inbound"></a>

| 落点 | 改造前 | 改造后 |
| --- | --- | --- |
| 用户只读出口（`internal_users.query_router`） | `require_service("mdm")` | `require_capability("platform.user.query")` |
| 权限失效入口（`permission.router`） | `require_service("mdm")` | `require_capability("platform.permission_meta.invalidate")` |
| 系统参数内部读（`internal_config`） | `require_service("identity", "mdm")` | 同一路由挂两个依赖，按调用方分道：`sub=identity` 走 `require_service("identity")`（平台内部，范围外）；其余走 `require_capability("platform.platform_config.snapshot")` |
| 权限数据只读出口（`permission.read_router`，`/subject`、`/metadata`） | `require_service("identity")` | 两条路由**逐条**声明各自能力：`platform.permission_meta.subject` / `platform.permission_meta.metadata`（两项能力不同，不能挂路由组级依赖）；拒绝码由 401 改 **403**（已认证无分配 / 网关代发），伪造与无票据仍 401 |

**能力名第二段是业务域**（须在 `deploy/boundaries/domain_layout.json` 登记并带 `service_key`）：`user` / `permission_meta` / `platform_config` 三个域均已登记且承载服务为 `platform`。设计早稿的 `platform.permission.invalidate` / `platform.config.snapshot` 的第二段不是登记域，装载即拒启（§9 偏差 2）。

**`require_capability` 语义**（依赖 `02_04` 的授权视图）：取调用方服务身份 `sub` → 查该能力的有效分配 → 未授权即拒（错误含 `capability` 与 `consumer`）→ 命中则放行；能力未登记则抛 `CatalogError`（拒启级，**不是 403**），故必须先落声明再切端点。

**为什么能替掉白名单**：白名单本质是「谁被允许调我」，正是授权记录的表达；能力声明的 `default_consumers` 提供默认授权，装载后落库，运营期可调（`02_04`）。

**平台内部调用不动**：`identity` 等平台服务之间的白名单仍走 `require_service`——它们不是跨产品协同，纳入会扩大范围且无收益（登记为开放项待评估）。

### 3.5.1 平台侧能力声明（缺口 A 的落地） <a id="platform-decl"></a>

`deploy/registry/platform.toml` 现只有 `product_key` 与 9 条 `[[seeds]]`；本任务补能力声明与使用声明（不新增 `[[product_routes]]`）：

| 段 | 内容 | 说明 |
| --- | --- | --- |
| `[[collaborations]]` ×5 | `platform.user.query`（`kind=read`，`/api/v1/platform/internal/users/query`）、`platform.permission_meta.invalidate`（`kind=write`，`/api/v1/platform/internal/permissions/invalidate`）、`platform.permission_meta.subject`（`kind=read`，`/api/v1/platform/internal/permissions/subject`）、`platform.permission_meta.metadata`（`kind=read`，`/api/v1/platform/internal/permissions/metadata`）、`platform.platform_config.snapshot`（`kind=read`，`/api/v1/platform/internal/configs/resolve`） | 三条路径均能在 `deploy/contracts/platform.json` 定位；`contract_version` 随平台服务契约（`0.1.0`）；`frontend_prefix = "platform"` **逐条显式声明**（平台无 `[[product_routes]]`，推导路径不可用）；`default_consumers` 按现有调用方登记（`mdm`；`platform_config.snapshot` 另含 `identity` 时为「平台内部亦走授权」，本任务不纳入，故只登记 `mdm`） |

> **为何不加 `[[product_routes]]`**：`validate_product_routes()` 要求「`product_key` 已在产品档案登记 + 目标服务为 `product` 分组 + 服务行 `product_key` 与路由一致」；平台服务行是 `module_key="sys"` / 分组 `foundation` / `product_key=None`，平台又无产品档案——自指路由会被判「`product_key` 未登记」+「目标服务非产品分组」。故前缀逐条显式声明（§9 偏差 9）。

**消费方登记校验**（§9 偏差 4 / 13）：`default_consumers` 与 `[[usages]]` 的可兑现性**不在装载期判定**——本地无法知道别的产品是否已注册，判错会误伤「平台 + 任一非 mdm 产品」的部署与用例。权威校验归 `02_06` 的注册通道（对着平台权威视图校验，异值即拒）与 `04_02` 的 CI 对账；本任务只在装载期给出告警。

### 3.6 租户恒开通模块清单 <a id="tenant-base"></a>

现状是**常量**（`TENANT_BASE_MODULE_KEYS`，含 `"mdm"`）且被 `bms_tenant` 直接读取两处——设计早稿「函数签名不变、调用方零改动」的前提不成立（§9 偏差 6）：

| 项 | 改造前 | 改造后 |
| --- | --- | --- |
| 常量 | `TENANT_BASE_MODULE_KEYS` 含 `"mdm"` | 移除 `"mdm"`，仅保留平台自身模块；注释中以 `org` 追述历史的句子改为通用表述 |
| 清单字段 | 无 | 服务行可选 `tenant_base`（缺省 `false`）：加在 `ModuleRecord` 与清单解析，`true` 者视为恒开通 |
| 落库 | 无 | `sys_module` 增 `tenant_base` 布尔列（缺省 `false`）——注册通道逐字段写库 / 读回会丢弃非列字段（实测），不落库则注册后标记即丢；同时纳入接库对账严格字段，声明与库中行不一致即拒启 |
| 基座取值 | 无 | 新增 `tenant_base_module_keys()` = 平台常量 + 已装载且 `tenant_base=true` 的模块键（插入序、同键去重）——**平台侧视图**，供目录出口派生标记 |
| 跨进程传递 | 无 | 目录出口（`ModuleResponse`）增 `tenant_base` 布尔字段，按上式派生；`bms_tenant` 的 `CatalogModule` 随之读入（**租户服务不装载产品清单**，故不能只靠基座视图） |
| 判定入口 | 两处直接读常量 | 新增 `is_tenant_base_module(item)` = 目录行标记 **或** 基座常量（对端旧版本缺字段时兜底）；`bms_tenant` 的 `open_base_modules()`（192）与 `validate_optional()`（273）改用它 |
| 校验 | 无 | 声明 `tenant_base = true` 的服务行须为 `product` 分组（`table_prefix` 首段与模块键一致由既有校验覆盖），违规即装载期 / 启动校验拒启 |
| 跨仓声明 | — | **mdm 仓** `deploy/registry/mdm.toml` 的 `[[services]] module_key = "mdm"` 行加 `tenant_base = true` |

**为何必须落库**：`02_06` 的注册通道按**显式字段表**写 `sys_module` 并用 `ModuleRecord.from_row` 读回，随后 `project_registry()` 复位并重建进程内视图。若 `tenant_base` 只存在于清单解析层，则注册（平台自启动注册 / 产品上报）后标记丢失——平台派生的目录标记变 `false`，租户侧 `mdm` 掉出恒开通（基座常量已不含它），RBAC 主体链受影响。落列后该属性随注册表权威视图贯通，跨进程与跨版本语义一致。

**行为等价**：装载 mdm 清单后，恒开通集合与改造前一致（仍含 `mdm`）；未装载清单的环境（纯平台部署 / 单仓测试）集合自然不含产品模块——这正是期望语义。常量在 import 期求值，故必须改成「函数 + 目录标记」两段（声明要到装载期才知道，租户服务又在另一个进程）。

### 3.7 消费方使用声明的清单段（第八类记录） <a id="usage-decl"></a>

`02_02` 交付的使用声明钩子 `ApplicationFactory.capability_usages()` 是**代码级**入口，但声明内容必然是产品能力名（`mdm.org.*`），而 `04_01` 字面量规则把「生产源码」列为禁入位置、把「产品自持声明」列为允许位置。故使用声明改为**清单承载**：

| 项 | 口径 |
| --- | --- |
| 清单段 | `[[usages]]`（第八类记录）：`name`（能力名）、`degrade`（`none` / `empty`，`stale` 仍拒启）、`reason`（`degrade != none` 时必填） |
| 消费方 | **声明方即消费方**：取声明清单归属（`platform.toml` → `platform`），不写 `consumer` 字段（与能力 / 种子声明的归属口径同构） |
| 落视图 | 装载期登记为「消费方 → 声明列表」视图（与 `capability_usage_view()` 同键同值口径，冲突即拒） |
| 装配期 | 基座装配把「代码声明 ∪ 清单声明」登记为 `app.state.capability_usages`；清单声明按**已装载能力视图过滤**（§9 偏差 5），过滤后仍走 `validate_capability_usages()` fail-closed |
| 装载期校验 | 用法同 `default_consumers`：能力名不在「本次装载清单的能力」中时，**未装载外部产品清单**则告警（单仓），装载后判错；`degrade`/`reason` 的合规性由 `inspect_capability_usages()` 复用既有判定 |

平台清单本轮登记五条（对应 §3.1~§3.3 的五个 mdm 能力）：

| 能力 | 降级 | 理由 |
| --- | --- | --- |
| `mdm.org.user-roles` | `empty` | 组织域不可达时主体链只保留直接角色（与改造前降级语义一致） |
| `mdm.org.user-posts.assign` / `mdm.org.user-depts.assign` / `mdm.org.role-posts.assign` / `mdm.org.role-depts.assign` | `none` | 写 / 强一致路径，失败即整单失败（声明降级即装载期拒启） |

### 3.8 mdm 侧入站收编（提供方，跨仓） <a id="mdm-inbound"></a>

mdm 是 `mdm.org.*` 能力的提供方，入站判定原按 `require_service` 白名单；本任务一并切到能力授权，否则「有分配即合法」只覆盖平台提供方一侧：

| 项 | 口径 |
| --- | --- |
| 端点切换 | mdm 组织出口（`mdm.org.user-roles`）与内部写通道（四个 `*.assign`）改 `require_capability("<能力名>")`；能力名取自 mdm 自身声明的同一份取值（mdm 清单是这些能力的**声明方**，不算「平台源码产品字面量」） |
| 授权视图来源 | mdm 装配期登记 `RemoteCapabilityGrantSource`（经 platform 的 `/api/v1/internal/capability-grants` 拉取），并在启动钩子内预热（本服务承载域的 `provider` 视图） |
| 失败语义 | 视图不可用 → 首访 fail-closed（`CatalogError`，与 `02_04` 口径一致）；未授权 → 403 且信息含能力名与消费方 |
| 用例 | mdm 侧新增「已授权放行 / 未授权拒绝 / 来源不可用拒启」三例；既有白名单用例改为按分配构造 |

> 该跨仓改动与平台侧**同一窗口**完成：mdm 端点切到能力授权后，若 platform 侧未落声明与授权同步，mdm 入站将全拒。

### 3.9 本机联调寻址与全套纳管（第六批） <a id="local-stack"></a>

**问题**：收编后「真库 / 两进程端到端」是验收必需项，但本机裸跑只能起平台三服务——产品服务（mdm）的启动规格写在平台仓脚本里，等于让平台仓知道产品仓的路径与模块名；而服务间基址模板 `http://{service}:8000` 又要求 `{service}` 能被解析，本机只能靠**系统 hosts 别名**（写 hosts 需管理员权限、跨平台不一致）。

**设计（两段拆开）**：

| 项 | 口径 |
| --- | --- |
| 运行规格归属 | 各仓自持一份**固定路径声明** `deploy/local_stack.toml`（`key` / `module` / `backend` / `host` / `port` / `db_dir` / `frontend_prefix` / `env` / `after`）；`本地全套.py` 扫「本仓 + 工作区平级仓」装载。与域布局同口径：**产品各自持有、装载注册**，平台仓不出现产品仓字面 |
| 缺省范围 | 装载到什么就起什么（扫描成本可忽略）；`--services` 退化为过滤器（调试单服务 / 腾位） |
| 启动顺序 | 声明可选 `after`（前置服务键）；脚本按前置关系**分批起**——前一批健康后再起后一批。产品进程启动期要向平台上报声明并拉快照，并发起必然踩「平台未就绪」竞态 |
| 寻址 | 基座增**服务端点覆盖**：`[service_client].endpoints`（服务键 → 基址，独立环境变量 `BMS_SERVICE_CLIENT__ENDPOINTS`）；服务间调用与能力寻址**同口径**取 `service_base_url()`（覆盖优先、基址模板兜底）。本机由脚本按声明注入，容器部署不注入（按 Compose DNS 模板派生）——两形态行为同构，且**不再需要写系统 hosts** |
| 为何不塞进 `options` | `options` 是**实现参数**字典，经环境变量注入会整字典替换，连带冲掉 `attach_service_token`；故派生 `ServiceClientSettings(PluginSelection)` 加同层字段（与 `PermissionSettings` 同构） |
| 库重置 | `--reset-db` 按各声明库目录（`database/<仓>`）备份移走 `*.db`，不再只认平台库目录 |
| 对账范围修正 | 平台接库对账取数面收敛为「**平台行 + 本产品行**」：产品行由注册通道按声明方作用域对账；否则产品注册后平台重启即报「库中登记行不在清单」、常量里的产品计划行又报「缺行」 |

**边界**：声明只承载**本机开发事实**，不进部署契约（部署口径仍在 `deploy/compose/` 与 `Dockerfile`）；容器内无该文件亦不影响启动。

### 3.10 产品进程断点调试与生成物门禁（第七批） <a id="debug-entry"></a>

**问题**：① 本机全套把产品进程纳入纳管后，**产品进程无法断点调试**——`backend/ops/dev_run.py` 的做法是「注入环境后 `runpy` 进服务入口」，而 `runpy` 只能进**本仓**模块，产品服务模块（`mdm`）在另一仓、另一 venv；② 域布局降为生成物后**没有门禁**——清单改了忘记重渲染不会红（bms 侧 `ops` 不在覆盖率采集包，无任何自动化兜底）。

| 项 | 口径 |
| --- | --- |
| 调试入口 | 产品进程改走 IDE **原生 `module` 启动**（调试器直接起产品仓解释器跑 `-m <模块>`）+ **`envFile`** 注入环境——断点 / 变量 / 调用栈与命令行 `python -m <模块>` 完全一致，且不需要任何跨仓包装代码 |
| 环境文件 | 由 `本地全套.py` 的 `env` 子命令（`up` 收尾自动调用）按声明为**每个服务**写 `<仓>/deploy/.dev-env.<服务键>.local`：回环别名 / 端口 / Redis / 端点覆盖 / `PYTHONUNBUFFERED` / 声明 `env` / 开发密钥。它是「声明 + 密钥」的确定性产物，每次重写（勿手改）⇒ 调试进程与脚本起进程**同源同口径** |
| 平台服务为何不改 | 平台服务仍用 `ops/dev_run.py`（本仓模块，`runpy` 可行，且它带「目标地址已占用即报错并提示 stop」的护栏）；两套入口的差别只是**能否跨仓**，环境口径同源 |
| 生成物门禁 | bms / mdm 两仓 `engkit.toml` 预检各增一步 `ops.check_modules --check-domain-layout`（`cwd = backend`）：生成物被手改、或清单变更未重渲染即红；生成物**只读**，重渲染用 `--render-domain-layout` |
| 门禁归属 | 属**配置**（`engkit.toml` 步骤），不改工具包代码；不新增用例——步骤本身即门禁，且 `ops` 不在覆盖率采集包 |

**边界**：调试环境文件是本机开发产物（`*.local` 已忽略），不进部署契约；预检步骤只做「生成物 = 清单渲染」的比对，不替代语义校验（语义仍在装载校验与域级护栏）。

## 5. 行为等价与回归口径 <a id="equivalence"></a>

| 项 | 回归要求 |
| --- | --- |
| 权限结果 | 既有主体链并集 / 降级 / 严格模式用例全绿，结果与改造前逐条一致 |
| 分配写入 | 用户 / 角色保存的 XA 与顺序提交两条路径结果一致（同一路径模板、同一动作名、同一库键）；失败无半写 |

| 恒开通 | 装载 mdm 清单后集合与改造前一致（含 `mdm`）；不装载时不含产品模块；常量本身已无 `"mdm"` |
| 事务账本 | 升级前后 `branch_id` 值不变（仍为 `"m"`）；升级前未完成事务可恢复 |
| 声明驱动 | 改清单里的 `path` / `branch_op` / `branch_id` / `target.service_key`，消费方行为随之变化（新增用例） |

## 7. 风险与边界 <a id="risk"></a>

| 风险 | 处置 |
| --- | --- |
| 分支标识改动影响事务恢复 | 只换取值来源不换值；声明值一经确定不再变更；升级前先确认无未完成事务（运维检查） |
| 白名单改授权派生后“少一条授权即全线拒” | 声明里 `default_consumers` 覆盖现有调用方；上线前对账现有白名单（逐项比对） |
| 单仓校验放宽掩盖消费方拼写错误 | 仅「未装载任何产品清单」时降为告警，装载后仍判错；由 `04_02` 跨仓契约校验兜底 |
| 声明按装载视图过滤导致能力名拼错静默 | 单仓退化为调用期 `ParamError`；装载环境仍拒启；`04_02` 增跨仓对账 |
| 能力解析在装配期依赖装载顺序 | 解析入口在使用时惰性取视图；装配期不解析（避免启动顺序耦合） |
| 平台内部白名单未纳入导致“两套” | 明确范围外并登记开放项，避免被误认为遗漏 |
| `tenant_base` 新增字段改变清单结构 | 可选字段，缺省 false，不破坏既有清单 |
| `sys_module` 增列无迁移链 | 测试库与 CI 均为新建库；开发 / 演示库按「删库重建 + 重新注册」升级（§3.6） |
| 平台 `frontend_prefix` 为人工声明，可能与平台命名空间漂移 | 值恒为产品命名空间段（`platform`）；`03_02` 取址前对账一次，必要时收进 `04_02` 契约校验 |
| 清单新增 `[[usages]]` 段改变结构 | 段可选；缺省无声明即「不降级」，既有清单零改动 |
| mdm 入站与平台声明不在同一窗口生效导致全拒 | 两仓同一窗口提交并同步推送；平台侧先落声明与授权同步，再切 mdm 端点 |
