## 1. 目标与边界 <a id="scope"></a>

**目标**：把后端五类跨产品消费点从「写死对端标识与访问面」改为「按能力名取用」与「按授权派生白名单」，**行为等价**地去掉产品字面量。

**范围内**：

1. 权限解析器（读出口）；
2. 用户保存编排（内部写通道 + 事务分支动作名 + 分支标识）；
3. 角色保存编排（同构两组）；
4. 三处入站白名单中与产品相关的部分；
5. 基座「租户恒开通模块」清单中的产品标识。

**范围外**：平台内部服务间白名单（`identity` 等，属平台内部，不在本专项）；前端（`03_02`）；平台种子（`03_03`）；能力视图与授权机制的实现（`02_02` / `02_04`）。

### 2.3 与代码不符的设计假设（两处缺口） <a id="current-gaps"></a>

**缺口 A：`platform.*` 三项能力与平台清单缺声明**

| 事实 | 证据 |
| --- | --- |
| 三个能力名全仓只在文档出现（本设计 §3.5、《跨产品协同登记清单》§2、`02_04` 设计示例），源码与清单零命中 | 全仓检索 `platform.user.query` / `platform.permission.invalidate` / `platform.config.snapshot` |
| `deploy/registry/platform.toml` 只有 `product_key` 与 9 条 `[[seeds]]`；无 `[[collaborations]]`，也无 `[[services]]` / `[[product_routes]]` | 清单全文 |
| 平台服务未覆写 `capability_usages()`（`backend/services/` 全仓零命中）——平台作为 mdm 消费方的降级策略目前无处声明 | 检索 `capability_usages` |

按现有装载器与入站依赖实现读出的后果：

1. `require_capability("<能力名>")` → `check_capability_access()` → `capability_domain()` 对**未登记能力抛 `CatalogError`（拒启级）**，不是 403；未声明就切换端点，未授权场景会退化成 500。
2. 能力名第二段是**业务域**且须在 `deploy/boundaries/domain_layout.json` 登记并带 `service_key`；平台侧已登记域为 `user` / `role` / `permission_meta` / `menu_form` / `platform_config` / `platform_registry` / `task`——设计所用的 `permission` 与 `config` **不是已登记域**。
3. 非 `codes` 能力须能推导 `frontend_prefix`（`product_routes` 域段唯一或显式声明）；platform.toml 无 `product_routes`，须逐条显式声明。
4. `default_consumers` 须落在「已登记服务键 / 产品键」集合（`SERVICE_CATALOG` 常量 + 本次装载清单）：产品字面量已从平台常量移除（`02_01`），`mdm` 只在装载 mdm 清单时可见 → **bms 单仓（`registry.product_manifests` 为空）声明 `default_consumers = ["mdm"]` 会被判「默认消费方未登记」**。
5. 访问面须能在 `deploy/contracts/platform.json` 定位：三个路径均在（`/api/v1/platform/internal/users/query`、`/api/v1/platform/internal/permissions/invalidate`、`/api/v1/platform/internal/configs/resolve`）——此项无障碍。

**缺口 B：`tenant_base` 清单字段与 `tenant_base_module_keys()` 不存在**

| 事实 | 证据 |
| --- | --- |
| `tenant_base` 字段在服务行解析（`registry/products.py`）、`ModuleRecord`、mdm 仓 `mdm.toml` 服务行均无 | 检索 + 清单 |
| `tenant_base_module_keys()` 全仓不存在；现状是**常量** `TENANT_BASE_MODULE_KEYS`（`module_registry.py` 741，`"mdm"` 在 753） | 源码 |
| 该常量被**直接读取**两处：`bms_tenant` 的 `tenant_module.py` 192（开通恒开通模块）/ 273（勾选拦截）；另有 `bms_core` 测试断言它与可勾选清单不相交 | 源码 |

后果：

1. 设计 §3.6「函数签名与返回类型不变、调用方零改动」的前提不成立——须新增函数并改两处调用点（常量在 import 期求值，早于清单装载，无法承载「已装载声明」）。
2. `tenant_base = true` 须写在 **mdm 仓** `deploy/registry/mdm.toml` 的服务行，属跨仓改动；不声明就直接移除常量中的 `"mdm"`，恒开通集合随之改变（RBAC 主体链所在模块被移出恒开通）。
3. 服务行新增字段属清单结构扩展，须同步装载器解析与校验（沿用既有「产品分组 + 表前缀一致」口径）。

## 3. 设计 <a id="design"></a>

### 3.1 权限解析器（读出口） <a id="resolver"></a>

| 项 | 改造前 | 改造后 |
| --- | --- | --- |
| 服务标识 | 常量 `MDM_SERVICE_KEY = "mdm"` | 删除；由 `resolve_capability("mdm.org.user-roles").target.service_key` 提供 |
| 路径 | 常量 `/api/v1/mdm/user-roles` | 删除；由 `resolve_capability(...).path` 提供 |
| 请求构造 | 手写 `ServiceRequest(service=…, path=…)` | `build_capability_request(endpoint, method="GET", query=…)`（目标服务与路径均取自已解析能力） |
| 降级 | 异常一律降级为空集 | 非严格模式经 `call_capability(..., fallback=空集)`，策略在平台服务 `capability_usages()` 声明 `CapabilityUsage("mdm.org.user-roles", degrade="empty", reason=…)`；降级日志与指标由基座一次完成 |
| 严格模式 | 失败抛 `InternalError`（10002） | **不变**：严格模式不走 `call_capability` 的降级通道（声明是一次性的、不能按实例分档），改由 `resolve_capability` + 直接调用 `_fetch()`，异常按既有 `_degrade()` 口径抛 `InternalError` |
| 指标 | 无 | 非严格模式由 `call_capability` 打点；严格模式失败仅上抛（与现状同，不新增指标口径） |

**行为等价**：能力解析结果与既有常量一致（同一服务键、同一路径、同一 `data.role_ids` 解析）；严格模式仍抛 `InternalError`；非严格模式仍返回空集——差别仅在「降级现在有声明、有日志、有指标」。

> 声明按「已装载视图过滤」落（§9 偏差 5）：单仓未装载 mdm 清单时不声明，`call_capability` 无声明即上抛，故平台单仓环境该路径不做降级（该环境本无组织域可取数）。

### 3.2 用户保存编排（写 + 事务分支） <a id="user-assign"></a>

| 项 | 改造前 | 改造后 |
| --- | --- | --- |
| 库键派生 | `build_tenant_db_key(..., service=MDM_SERVICE)` | 先取拓扑解析结果 `endpoint.target.db_keys`；**为空集时回退** `build_tenant_db_key(..., service=endpoint.target.service_key)`（`CapabilityTarget.db_keys` 契约原文：空集＝未由拓扑解析，消费方沿用既有按服务键派生） |
| 分支规格 | `BranchSpec(branch_id=BRANCH_ID_MDM, service=MDM_SERVICE, db_key=...)` | `branch_id=endpoint.branch_id`（见 §3.4）、`service=endpoint.target.service_key`、`db_key=` 上式结果 |
| 分支执行请求 | `ServiceRequest(service=MDM_SERVICE, path=BRANCH_EXECUTE_PATH)` | `service=endpoint.target.service_key`、`path` 仍为 `BRANCH_EXECUTE_PATH`（平台级参与端点约定，非产品访问面，不属能力声明范围） |
| 顺序提交路径 | `path=MDM_INTERNAL_USER_POSTS_PATH.format(user_id=...)` | `build_capability_request(endpoint, method="PUT", params={"user_id": …}, json_body=…, headers=…, tenant_id=…)`（`{user_id}` 由模板渲染，幂等键经 `headers` 传） |
| 分支动作名 | `ops.add((MDM_USER_POSTS_OP, ...))` | `ops.add((endpoint.branch_op, ...))`（岗位 / 部门各取各自能力的 `branch_op`） |
| 能力名 | — | `mdm.org.user-posts.assign` / `mdm.org.user-depts.assign` |
| 解析时机 | — | 每次 `apply()` 惰性解析（不缓存到实例）：声明变更即时生效，且与「装配期不解析」口径一致 |
| 失败语义 | 失败即抛（现状已是 fail-closed） | 保持 fail-closed；解析失败（能力缺失 / 禁用）与调用失败一律整单失败；**禁止**新增降级声明 |

**等价性**：路径模板、方法与动作名均取自能力声明，与既有常量逐字一致（`mdm.toml` 已声明 `branch_id = "m"` / `branch_op = "mdm.user-posts.assign"` / `path = "/api/v1/mdm/internal/user-posts/{user_id}"`）；XA 与顺序提交两条路径的判定条件不变。

### 3.3 角色保存编排（同构） <a id="role-assign"></a>

改造方式与 §3.2 完全同构，能力名换为 `mdm.org.role-posts.assign` / `mdm.org.role-depts.assign`，库键、分支规格、分支执行请求、动作名、内部通道路径同样取自已解析能力；失败语义同为 fail-closed。

### 3.4 分支标识的派生（不再写死单字符） <a id="branch"></a>

现状 `BRANCH_ID_MDM = "m"` 是 XA 事务内的参与者标识。改造后的口径：

| 项 | 口径 |
| --- | --- |
| 取值来源 | `endpoint.branch_id`（`mdm.toml` 的 `[[collaborations]].branch_id`，`02_02` 已装载） |
| 历史兼容 | 声明里的值就是历史值 `"m"`——**保留历史映射不是新增一层映射表，而是保持声明值不变**；升级前已进入 `txn_global_branch` 的事务仍能按原 ID 恢复 |
| 唯一性 | 装载期校验已断言「同一 `branch_id` 不得跨业务域混用」；运行期同一事务内平台侧仍用 `BRANCH_ID_PLATFORM`（`"p"`，平台自有、非产品字面量，保留） |
| 稳定性 | 声明值一经确定不得随版本漂移（清单注释与装载校验共同约束） |

> 该字段是事务账本的对外形态，改动须保守：**只换取值来源，不换值**。平台分支标识 `"p"` 属平台自身，不纳入本任务。

### 3.5 三处入站白名单 <a id="inbound"></a>

| 落点 | 改造前 | 改造后 |
| --- | --- | --- |
| 用户只读出口（`internal_users.query_router`） | `require_service("mdm")` | `require_capability("platform.user.query")` |
| 权限失效入口（`permission.router`） | `require_service("mdm")` | `require_capability("platform.permission_meta.invalidate")` |
| 系统参数内部读（`internal_config`） | `require_service("identity", "mdm")` | 同一路由挂两个依赖，按调用方分道：`sub=identity` 走 `require_service("identity")`（平台内部，范围外）；其余走 `require_capability("platform.platform_config.snapshot")` |

**能力名第二段是业务域**（须在 `deploy/boundaries/domain_layout.json` 登记并带 `service_key`）：`user` / `permission_meta` / `platform_config` 三个域均已登记且承载服务为 `platform`。设计早稿的 `platform.permission.invalidate` / `platform.config.snapshot` 的第二段不是登记域，装载即拒启（§9 偏差 2）。

**`require_capability` 语义**（依赖 `02_04` 的授权视图）：取调用方服务身份 `sub` → 查该能力的有效分配 → 未授权即拒（错误含 `capability` 与 `consumer`）→ 命中则放行；能力未登记则抛 `CatalogError`（拒启级，**不是 403**），故必须先落声明再切端点。

**为什么能替掉白名单**：白名单本质是「谁被允许调我」，正是授权记录的表达；能力声明的 `default_consumers` 提供默认授权，装载后落库，运营期可调（`02_04`）。

**平台内部调用不动**：`identity` 等平台服务之间的白名单仍走 `require_service`——它们不是跨产品协同，纳入会扩大范围且无收益（登记为开放项待评估）。

### 3.5.1 平台侧能力声明（缺口 A 的落地） <a id="platform-decl"></a>

`deploy/registry/platform.toml` 现只有 `product_key` 与 9 条 `[[seeds]]`；本任务补两段（能力声明与前端前缀推导）：

| 段 | 内容 | 说明 |
| --- | --- | --- |
| `[[product_routes]]` | `product_key = "platform"`、`domain = "platform"`、`service_key = "platform"` | 装载期据此推导 `frontend_prefix`（本清单路由域段唯一即填 `platform`）；平台自指路由，会进入前端目录出口（`03_02` 消费方需知悉） |
| `[[collaborations]]` ×3 | `platform.user.query`（`kind=read`，`/api/v1/platform/internal/users/query`）、`platform.permission_meta.invalidate`（`kind=write`，`/api/v1/platform/internal/permissions/invalidate`）、`platform.platform_config.snapshot`（`kind=read`，`/api/v1/platform/internal/configs/resolve`） | 三条路径均能在 `deploy/contracts/platform.json` 定位；`contract_version` 随平台服务契约（`0.1.0`）；`default_consumers` 按现有调用方登记（`mdm`；`platform_config.snapshot` 另含 `identity` 时为「平台内部亦走授权」，本任务不纳入，故只登记 `mdm`） |

**消费方登记校验的单仓口径**（§9 偏差 4）：装载校验对「未登记的 `default_consumers`」改为——**本次未装载任何产品清单时降为告警**（单仓看不到产品仓，提示由 `04_02` 跨仓契约校验兜底），装载了产品清单时仍判错。理由：bms 单仓 `registry.product_manifests` 为空，产品字面量已从平台常量移除（`02_01`），`mdm` 唯有装载其清单才可见。

### 3.6 租户恒开通模块清单 <a id="tenant-base"></a>

现状是**常量**（`TENANT_BASE_MODULE_KEYS`，含 `"mdm"`）且被 `bms_tenant` 直接读取两处——设计早稿「函数签名不变、调用方零改动」的前提不成立（§9 偏差 6）：

| 项 | 改造前 | 改造后 |
| --- | --- | --- |
| 常量 | `TENANT_BASE_MODULE_KEYS` 含 `"mdm"` | 移除 `"mdm"`，仅保留平台自身模块；注释中以 `org` 追述历史的句子改为通用表述 |
| 清单字段 | 无 | 服务行可选 `tenant_base`（缺省 `false`）：加在 `ModuleRecord` 与清单解析，`true` 者视为恒开通 |
| 取值入口 | 两处直接读常量 | 新增 `tenant_base_module_keys()` = 平台常量 + 已装载且 `tenant_base=true` 的模块键（返回 `ConcurrentStableList[str]`，插入序）；`bms_tenant` 的 `open_base_modules()`（192）与 `validate_optional()`（273）改调该函数 |
| 校验 | 无 | 声明 `tenant_base = true` 的服务行须为 `product` 分组且 `table_prefix` 与模块键一致（沿用既有归属校验口径），违规即装载期拒启 |
| 跨仓声明 | — | **mdm 仓** `deploy/registry/mdm.toml` 的 `[[services]] module_key = "mdm"` 行加 `tenant_base = true` |

**行为等价**：装载 mdm 清单后，恒开通集合与改造前一致（仍含 `mdm`）；未装载清单的环境（纯平台部署 / 单仓测试）集合自然不含产品模块——这正是期望语义。常量在 import 期求值，故改函数是唯一可行口径（声明要到装载期才知道）。

## 5. 行为等价与回归口径 <a id="equivalence"></a>

| 项 | 回归要求 |
| --- | --- |
| 权限结果 | 既有主体链并集 / 降级 / 严格模式用例全绿，结果与改造前逐条一致 |
| 分配写入 | 用户 / 角色保存的 XA 与顺序提交两条路径结果一致（同一路径模板、同一动作名、同一库键）；失败无半写 |
| 白名单 | 未授权调用被拒（错误码与信息可定位能力名）；已授权放行；`identity` 侧不受影响 |
| 恒开通 | 装载 mdm 清单后集合与改造前一致（含 `mdm`）；不装载时不含产品模块；常量本身已无 `"mdm"` |
| 事务账本 | 升级前后 `branch_id` 值不变（仍为 `"m"`）；升级前未完成事务可恢复 |
| 声明驱动 | 改清单里的 `path` / `branch_op` / `branch_id` / `target.service_key`，消费方行为随之变化（新增用例） |

## 7. 风险与边界 <a id="risk"></a>

| 风险 | 处置 |
| --- | --- |
| 分支标识改动影响事务恢复 | 只换取值来源不换值；声明值一经确定不再变更；升级前先确认无未完成事务（运维检查） |
| 白名单改授权派生后“少一条授权即全线拒” | 声明里 `default_consumers` 覆盖现有调用方；上线前对账现有白名单（逐项比对） |
| 单仓校验放宽掩盖消费方拼写错误 | 仅「未装载任何产品清单」时降为告警，装载后仍判错；由 `04_02` 跨仓契约校验兜底 |
| 声明按装载视图过滤导致能力名拼错静默 | 单仓退化为调用期 `ParamError`；装载环境仍拒启；`04_02` 增跨仓对账 |
| 能力解析在装配期依赖装载顺序 | 解析入口在使用时惰性取视图；装配期不解析（避免启动顺序耦合） |
| 平台内部白名单未纳入导致“两套” | 明确范围外并登记开放项，避免被误认为遗漏 |
| `tenant_base` 新增字段改变清单结构 | 可选字段，缺省 false，不破坏既有清单 |
| 平台新增产品路由进入前端目录出口 | `03_02` 消费时按 `domain` 区分产品域；本任务只登记、不改前端 |
