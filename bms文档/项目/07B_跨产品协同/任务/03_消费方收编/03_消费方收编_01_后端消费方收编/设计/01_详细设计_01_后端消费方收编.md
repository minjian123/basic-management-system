# 后端消费方收编详细设计

> 跨产品协同 · 03 消费方收编 · 01 后端消费方收编 · 详细设计（开发核心文档）

[文档首页](../../../../../../文档首页.md) › [01 后端消费方收编](../03_消费方收编_01_后端消费方收编.md) › 设计

## 1. 目标与边界 <a id="scope"></a>

**目标**：把后端五类跨产品消费点从「写死对端标识与访问面」改为「按能力名取用」与「按授权派生白名单」，**行为等价**地去掉产品字面量。

**范围内**：

1. 权限解析器（读出口）；
2. 用户保存编排（内部写通道 + 事务分支动作名 + 分支标识）；
3. 角色保存编排（同构两组）；
4. 三处入站白名单中与产品相关的部分；
5. 基座「租户恒开通模块」清单中的产品标识。

**范围外**：平台内部服务间白名单（`identity` 等，属平台内部，不在本专项）；前端（`03_02`）；平台种子（`03_03`）；能力视图与授权机制的实现（`02_02` / `02_04`）。

## 3. 设计 <a id="design"></a>

### 3.1 权限解析器（读出口） <a id="resolver"></a>

| 项 | 改造前 | 改造后 |
| --- | --- | --- |
| 服务标识 | 常量 `MDM_SERVICE_KEY = "mdm"` | 删除；由 `resolve_capability("mdm.org.user-roles").target.service_key` 提供 |
| 路径 | 常量 `/api/v1/mdm/user-roles` | 删除；由 `resolve_capability(...).path` 提供 |
| 降级 | 异常一律降级为空集 | 按 `CapabilityUsage(name="mdm.org.user-roles", degrade="empty", reason=...)` 声明，且输出日志 + 指标 |
| 失败 | `ParamError` 被吞 | 未声明降级的能力失败即上抛（保持既有“严格模式”参数语义） |

**行为等价**：能力解析结果与既有常量一致（同一服务键、同一路径）；`strict` 模式与降级语义保持现状，仅把“无声明降级”改为“显式声明 + 可观测”。

### 3.2 用户保存编排（写 + 事务分支） <a id="user-assign"></a>

| 项 | 改造前 | 改造后 |
| --- | --- | --- |
| 库键派生 | `build_tenant_db_key(..., service=MDM_SERVICE)` | **直接取拓扑解析结果** `endpoint.target.db_keys`（不自行按服务键派生——库归属由部署单元决定） |
| 分支规格 | `BranchSpec(branch_id=BRANCH_ID_MDM, service=MDM_SERVICE, db_key=...)` | `branch_id=endpoint.branch_id`（见 §3.4）、`service=endpoint.target.service_key`、`db_key=endpoint.target.db_keys` |
| 顺序提交路径 | `path=MDM_INTERNAL_USER_POSTS_PATH.format(user_id=...)` | `path=endpoint.path.format(user_id=...)` |
| 分支动作名 | `ops.add((MDM_USER_POSTS_OP, ...))` | `ops.add((endpoint.branch_op, ...))` |
| 能力名 | — | `mdm.org.user-posts.assign` / `mdm.org.user-depts.assign` |
| 失败语义 | 失败即抛（现状已是 fail-closed） | 保持 fail-closed；**禁止**新增降级声明 |

**等价性**：路径模板与方法（全量覆盖 PATCH/PUT）均取自能力声明，与既有常量逐字一致；XM / 顺序提交两条路径的判定条件不变。

### 3.3 角色保存编排（同构） <a id="role-assign"></a>

改造方式与 §3.2 完全同构，能力名换为 `mdm.org.role-posts.assign` / `mdm.org.role-depts.assign`，库键、分支规格、动作名、内部通道路径同样取自已解析能力。

### 3.4 分支标识的派生（不再写死单字符） <a id="branch"></a>

现状 `BRANCH_ID_MDM = "m"` 是 XA 事务内的参与者标识。改造要点：

| 项 | 口径 |
| --- | --- |
| 派生规则 | `branch_id = 提供方业务域的稳定短标识`（随能力解析结果返回，见 `02_02` 的 `CapabilityEndpoint`） |
| 历史兼容 | 映射表保留历史值（`mdm → "m"`），使**升级前已进入 `txn_global_branch` 的事务**仍能按原 ID 恢复；新事务使用派生值 |
| 唯一性 | 同一事务内多参与者不得撞 ID；派生规则保证不同业务域不同值，撞车即装载期报错 |
| 稳定性 | 同一业务域的派生值**不得随版本变化**（否则历史事务无法恢复） |

> 该字段是事务账本的对外形态，改动须保守：**允许新增，不允许随版本漂移**。

### 3.5 三处入站白名单 <a id="inbound"></a>

| 落点 | 改造前 | 改造后 |
| --- | --- | --- |
| 用户只读出口（`internal_users.query_router`） | `require_service("mdm")` | `require_capability("platform.user.query")` |
| 权限失效入口（`permission.router`） | `require_service("mdm")` | `require_capability("platform.permission.invalidate")` |
| 系统参数内部读（`internal_config`） | `require_service("identity", "mdm")` | 产品侧走 `require_capability("platform.config.snapshot")`；平台内部侧保留 `require_service("identity")` |

**`require_capability` 语义**（依赖 `02_04` 的授权视图）：取调用方服务身份 `sub` → 查该能力的有效授权 → 未授权即拒（错误含 `capability` 与 `consumer`）→ 命中则放行。

**为什么能替掉白名单**：白名单本质是「谁被允许调我」，正是授权记录的表达；能力声明里 `default_consumers` 提供默认授权，装载后落库，运营期可调（`02_04`）。

**平台内部调用不动**：`identity` 等平台服务之间的白名单仍走 `require_service`——它们不是跨产品协同，纳入会扩大范围且无收益（登记为开放项待评估）。

### 3.6 租户恒开通模块清单 <a id="tenant-base"></a>

| 项 | 改造前 | 改造后 |
| --- | --- | --- |
| 常量 | `TENANT_BASE_MODULE_KEYS` 含 `"mdm"` | 常量移除 `"mdm"`，仅保留平台自身模块 |
| 来源 | 平台代码写死 | 产品在服务行声明 `tenant_base = true`（清单可选字段，`02_01` 扩展） |
| 取值 | 直接读常量 | `tenant_base_module_keys()` = 平台常量 + 已装载且 `tenant_base=true` 的模块键（**函数签名与返回类型不变**，调用方零改动） |
| 校验 | — | 声明了 `tenant_base` 的产品模块须为 `product` 分组且表前缀与模块键一致（沿用既有校验） |

**行为等价**：装载 mdm 清单后，恒开通集合与改造前一致（仍含 `mdm`）；未装载清单的环境（如纯平台部署）集合自然不含产品模块——这正是期望语义。

## 5. 行为等价与回归口径 <a id="equivalence"></a>

| 项 | 回归要求 |
| --- | --- |
| 权限结果 | 既有主体链并集 / 降级 / 严格模式用例全绿，结果与改造前逐条一致 |
| 分配写入 | 用户 / 角色保存的 XA 与顺序提交两条路径结果一致；失败无半写 |
| 白名单 | 未授权调用被拒（错误码与信息可定位能力名）；已授权放行 |
| 恒开通 | 装载 mdm 清单后集合与改造前一致；不装载时不含产品模块 |
| 事务账本 | 升级前未完成的事务按历史 `branch_id` 仍可恢复；新事务使用派生值 |

## 7. 风险与边界 <a id="risk"></a>

| 风险 | 处置 |
| --- | --- |
| 分支标识改动影响事务恢复 | 保留历史映射；派生值一经确定不再变更；升级前先确认无未完成事务（运维检查） |
| 白名单改授权派生后“少一条授权即全线拒” | 声明里 `default_consumers` 覆盖现有调用方；装载期校验非空；上线前对账现有白名单（逐项比对） |
| 能力解析在装配期依赖装载顺序 | 解析入口在首次使用时惰性取视图；装配期不解析（避免启动顺序耦合） |
| 平台内部白名单未纳入导致“两套” | 明确范围外并登记开放项，避免被误认为遗漏 |
| `tenant_base` 新增字段改变清单结构 | 可选字段，缺省 false，不破坏既有清单 |

## 8. 开放项 <a id="open"></a>

| # | 事项 | 归口 |
| --- | --- | --- |
| 1 | 平台内部服务间白名单是否也纳入能力授权 | 平台内部调用方增多、或出现平台服务跨域部署时评估 |
| 2 | `branch_id` 派生规则是否统一到部署单元维度 | 07C 拓扑落地后评估（届时参与者可能是部署单元而非业务域） |
