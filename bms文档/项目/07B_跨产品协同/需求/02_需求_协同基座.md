## 1. 业务域说明 <a id="intro"></a>

本业务域把架构语义落成机制：产品自持声明的格式与装载校验、消费方按能力名取访问面与失败语义、产品种子的声明与平台统一调度、能力分配（授权）记录与派生。四者为后续收编（业务域 03）提供唯一入口。

- **依据**：架构 38 节点 §4 ~ §8；《项目规划说明》「平台扩展接入流程」节。
- **性质**：后端基座机制改造（含跨仓清单切换）。

## 2. 需求 02-1：产品自持声明 toml 化与装载校验 <a id="r02-1"></a>

优先级：2（高）

**背景与动机**：现有产品登记清单为 json，无法写注释，字段语义只能靠旁路文档；更关键的是清单只承载注册要素（服务行 / 产品路由 / 数据源），没有「能力」这一段，跨产品协作因此无处声明。装载时也没有「能力是否与本产品契约一致」的校验，断链只能在运行期以降级形式出现。

**内容**：

1. **格式切换**：产品自持清单由 json 改为 toml（原生注释、标准库可读、与既有配置口径一致）；同一次切换保持注册要素字段语义不变。
2. **能力段与种子段**：能力作为产品自持声明的**第五类登记记录**（与产品档案 / 服务行 / 产品路由 / 数据源**同源、同装载入口、同合并视图族、同唯一性纪律**），清单新增能力声明段（能力名、访问面类别与位置、业务语义要素、前端命名空间、版本）与种子声明段（模块路径、入口、依赖顺序）。
3. **装载校验**：装载期校验能力名全局唯一、提供方与清单归属一致、访问面能在对端公开契约中定位、声明版本与提供方契约版本兼容、种子入口可解析；不满足**拒绝启动**。
4. **跨仓切换**：平台仓与产品仓同批次切换为 toml（直接切换，不做双格式过渡），切换后两仓校验全绿。
5. **单一权威**：能力声明的权威只在产品仓；平台侧仅装载、校验并形成运行期只读视图，不保存第二份手写源。

**完成标准**：产品清单为 toml 且含注册要素 / 能力 / 种子三段；能力记录与既有四类同源同通道（**不出现第二套注册表**）；装载校验对「缺能力 / 能力重名 / 提供方不符 / 访问面不在契约 / 版本不兼容 / 种子入口不可解析」分别有用例且均拒绝启动；合法声明的装载用例通过；两仓切换后各自校验与预检全绿。

**参考文档**：《[架构设计 · 跨产品协同](../../../设计/架构设计/38_架构设计_子系统_跨产品协同.md)》§4 ~ §6；《[跨产品协同登记清单](../../../跨产品协同登记清单.md)》§5、§6

## 3. 需求 02-2：能力寻址与三档失败语义 <a id="r02-2"></a>

优先级：2（高）

**背景与动机**：消费方当前把对端服务标识、路径、分支动作名、白名单字面量直接写在代码里。产品侧一旦改名或改路径，消费方必须逐个改；且读取侧异常一律降级为空集，断链不可见。

**内容**：

1. **运行期能力视图**：装载后形成只读能力视图，消费方以能力名取访问面（含服务标识、路径、分支动作名、业务语义要素），不持有对端字面量。
2. **装载期失败语义**：能力缺失 / 提供方未登记 / 访问面不在契约 / 版本不兼容 → **拒绝启动**（fail-fast）。
3. **运行期失败语义**：写与强一致路径 **fail-closed**（整体失败并报明确错误码，不得只写一半）；读与弱一致路径允许**逐能力显式声明**的有界降级（返回空集或旧副本），且必须记录日志并计入可观测指标。
4. **禁止无差别降级**：全局缺省不得为「降级」；未声明降级的能力在运行期失败即上抛。
5. **目录下发**：**扩展既有服务目录快照（不新开端点）**，能力与产品键一并下发，供服务启动对账、跨服务查询与前端取址**共用同一份**。

**完成标准**：消费方改按能力名取用（后端以业务域 03 收编为验证）；缺能力时启动即失败且错误信息可定位到能力名；写路径失败用例断言 fail-closed 且无半写；读路径降级仅在被声明的能力上发生，并有日志与指标断言；未声明降级的能力失败即上抛；既有快照端点扩展后契约与用例齐备（**无新增目录出口**）。

**参考文档**：《[架构设计 · 跨产品协同](../../../设计/架构设计/38_架构设计_子系统_跨产品协同.md)》§7；《[架构设计 · 服务间通信与一致性](../../../设计/架构设计/37_架构设计_子系统_服务间通信与一致性.md)》

## 4. 需求 02-3：产品种子声明与平台统一调度 <a id="r02-3"></a>

优先级：2（高）

**背景与动机**：平台种子当前直接写产品的业务码与权限码（如产品服务标识及其查询 / 新建 / 修改 / 删除权限码），既与「基座不写产品」的口径矛盾，也使新增产品必须改平台代码。而让产品各自连库播种，又会把幂等、冲突与失败回滚责任分散到各产品。

**内容**：

1. **产品声明**：产品在自持清单声明本产品所需默认数据种子的入口（模块路径 + 入口 + 依赖顺序），种子内容归产品仓。
2. **平台调度**：并入**既有平台种子编排入口**（`seed_platform`）——既有种子族视为「平台自身种子」，产品种子按声明追加后按序执行，统一处理幂等（重复执行结果一致）、冲突（已存在且异值即报错并给出差异，不静默覆盖）、事务边界（单产品种子失败不影响已成功产品，整体退出码非零并给出逐项报告）。
3. **平台种子去产品化**：平台种子清单移除产品业务码与权限码，仅保留平台自身数据。
4. **可审计**：每次执行输出逐项结果（跳过 / 新建 / 冲突），供运维与验收核对。

**完成标准**：平台种子清单不含任何产品标识与产品权限码；产品种子按声明执行后产品权限码仍正确入库；重复执行幂等；人为构造冲突时命令以非零退出并给出差异；逐项结果输出可核对。

**参考文档**：《[架构设计 · 跨产品协同](../../../设计/架构设计/38_架构设计_子系统_跨产品协同.md)》§5、§8；《[跨产品协同登记清单](../../../跨产品协同登记清单.md)》§6

## 5. 需求 02-4：能力分配与授权 <a id="r02-4"></a>

优先级：2（高）

**背景与动机**：能力目录只回答「谁能提供什么」，不回答「谁被允许用」。没有授权记录，产品间调用要么被一刀切禁止（平台被迫给每个组合包一层中转），要么靠代码常量与口头约定放行——后者既不可审计，也无法在事后回答「这次调用是谁授权的」。分配记录同时是白名单与出站 scope 的唯一来源，也是监控与审计的天然维度。

**内容**：

1. **两层分工**：产品自持声明写「默认允许谁消费本能力」（文件级、随产品发布）；平台装载后落**分配记录**（运营期数据）；运营期可在平台侧调整、撤销，变更留审计。
2. **粒度**：**能力级**（一个能力一组访问面）；数据范围仍由既有数据权限体系约束，不在分配里重复定义。
3. **派生**：① 入站校验（谁能调我）＝本能力的有效分配；② 出站授权（我能调谁）＝消费方维度的有效分配，落实为服务令牌 scope；③ 监控维度＝「调用方 × 能力」。
4. **合法性判定**：有有效分配即合法（**直连或经平台中转均可**）；无有效分配即越界——运行期拒绝并报明确错误，装载期无法解析的分配直接拒启。
5. **审计与监控**：分配、调整、撤销进审计链；调用侧按「调用方 × 能力」打点（调用量 / 失败率 / 越权尝试），面板随可观测性阶段落地。
6. **默认策略**：产品间**默认经平台中转**，直连须先有分配记录。

**完成标准**：分配记录可由产品声明默认值装载落库，并可在平台侧调整 / 撤销（变更进审计链）；入站白名单与出站 scope 均由分配记录派生，代码中不再有调用方字面量；无分配时运行期拒绝并报明确错误、装载期解析失败即拒启；指标按「调用方 × 能力」打点且有断言；默认策略（中转优先、直连需分配）有对应用例。

**参考文档**：《[架构设计 · 跨产品协同](../../../设计/架构设计/38_架构设计_子系统_跨产品协同.md)》「能力分配与授权」节、《[跨产品协同登记清单](../../../跨产品协同登记清单.md)》§4

## 6. 需求 02-5：产品错误码自持与装载 <a id="r02-5"></a>

优先级：2（高）

**背景与动机**：错误码**段位**已随服务行自持（清单 `errcode_segment`，且有唯一性校验），但**具体码**仍只存在于产品仓代码（如 mdm 的 `330051`），平台只知段、不知码。后果是：平台中间件无法按「码 → HTTP 状态 / 文案键」统一渲染，只能透传产品自塞的文案；产品误用平台段（1~9 万位）查不出来；契约里声明的错误响应码与代码定义之间可能漂移；对外错误码手册只能手抄。错误码是对外承诺，应与其他契约要素同源登记。

**内容**：

1. **第七类记录**：产品自持声明新增错误码段（码级），要素为 `code` / `domain` / `http_status` / `message_key` / `severity` / `description`；与能力、种子同一装载入口与视图纪律。
2. **合并视图**：平台自身 `ErrorCode` 枚举**保持代码常量不变**，装载后与产品声明合成同一 `code → 定义` 视图；中间件只走这一条渲染路径。
3. **统一渲染**：错误响应按视图取 `http_status` 与 `message_key`；文案本体仍在产品语言包，缺失时回退 `description` 并记警告日志（不静默返回空文案）。
4. **三类校验**：① 段位归属——码的前两位必须等于清单声明段，且段不得落入平台码区；② 全局唯一——跨产品、以及与平台码不撞；③ 契约反向——契约声明的错误响应码必须已登记，已登记的码若被契约引用须一致（双向）。
5. **手册导出**：按合并视图导出错误码表（供开放平台文档与前端映射），导出结果与视图逐项一致。
6. **边界**：错误码**不是**能力里的业务码 / 权限码（后者属 `kind = "codes"` 的业务语义要素），两者不共用段与命名空间。

**完成标准**：产品可在自持声明中登记错误码并被装载；合并视图同时包含平台码与产品码且无重复；错误响应按视图渲染 `http_status` 与文案键，文案缺失时回退并告警；段位越界、跨产品撞码、契约与登记不一致三类反例均被拒；手册导出与视图逐项一致。

**参考文档**：《[架构设计 · 跨产品协同](../../../设计/架构设计/38_架构设计_子系统_跨产品协同.md)》「协同契约要素」节、《[API 接口规范](../../../规范/API接口规范.md)》「错误码分段」节、《[跨产品协同登记清单](../../../跨产品协同登记清单.md)》§5

## 7. 需求 02-6：产品自注册通道与平台权威视图 <a id="r02-6"></a>

优先级：2（高）

**背景与动机**：现行「产品自持声明」靠**文件装载**——平台与各产品服务在装配期按配置路径读 `deploy/registry/*.toml`，装进各自进程的内存视图。这带来三个后果：① 平台要消费产品能力（如组织域的按用户取角色）就得在平台配置里挂产品仓清单路径，形成**跨仓文件依赖**（bms 单仓 CI 读不到、路径易漂、拼写与版本无从对账）；② 产品服务要知道对端能力，也得各自装载别家清单，等于每个进程各持一份「真相副本」；③ 没有「注册」语义——产品是否已登记、登记内容是否与平台一致，只能靠文件与装载日志推断。架构把平台定为协同登记的唯一权威源，却缺一条「产品→平台注册、谁需要就问平台要」的通道。

**内容**：

1. **注册上报**：产品服务启动时把自身四类声明（服务行 / 产品档案 / 能力 / 消费方使用声明）上报平台；平台幂等合并落库（同键同值幂等、异值拒收并回报差异）。
2. **落库与恢复**：能力声明与使用声明落 `sys_collaboration`（一表承载两类，键与来源分列）；服务行 / 产品档案沿用既有 `sys_module` / `sys_product` 并按其口径扩展；平台重启自库恢复权威视图，**不再依赖清单文件**。
3. **权威视图出口**：新增服务身份专用的完整能力视图出口（含访问面路径、分支标识与动作名、访问面类别、承载服务键），供消费方启动期拉取；面向浏览器的目录出口保持不含内部路径。
4. **消费方取数改源**：`resolve_capability` 的取数来源由「本进程装载视图」改为「平台权威视图」——平台进程本库直读、产品进程启动期拉取并缓存。
5. **口径重写**：`ops.check_modules`、网关配置生成、服务目录出口、装载校验一律改对注册表 / 权威视图校验；产品清单降为**注册输入**，不再是被各进程各自装载的「真相」。
6. **断链即拒启**：注册校验不过、拉取失败一律拒启（断链在启动期暴露，不留到运行期）。

**完成标准**：平台在零产品清单文件的情况下即可得到完整登记视图，且重启后仍成立；产品服务只上报自身声明、不再装载别家清单；改声明即改注册表、消费方取址与入站判定随之变化（有用例）；重复注册幂等、异值拒收并报差异；消费方拉取失败拒启且信息可定位；`ops.check_modules` 与网关配置改对注册表校验后全绿；四类声明的落库与视图一一对应（无第二套手写源）。
