# 消息平台端口适配需求

## 1. 业务域说明 <a id="intro"></a>

本业务域承载**协议能力归位**：把消息平台在 04-1 ~ 04-4 已交付的「帧协议 + RPC 客户端 + 错误语义 + 幂等重试」整条链上移为基座通用能力，使每个继承 `bms-core` 的产品仓**天生附带消息客户端**，无需额外部署或跨仓装配；随后在 `bms_core` 内落地 `BaseServiceClient` / `EventPublisher` 的适配实现与配置切换。

- **依据**：《[架构设计 · 跨产品协同](../../../设计/架构设计/38_架构设计_子系统_跨产品协同.md)》§8「依赖方向与红线」、《[架构设计 · 产品与服务划分](../../../设计/架构设计/39_架构设计_子系统_产品与服务划分.md)》、《[后端开发规范](../../../规范/后端开发规范.md)》「服务间调用必须走基座」节、《[AI开发规范](../../../规范/AI开发规范.md)》§3.1「补充需求流程」。
- **跨仓需求源**：`msg/msg文档/项目/08B_消息平台/需求/04_需求_远程调用.md#r04-5`（纯文本路径；本仓 CI 只克隆 bms，不写跨仓链接）。
- **性质**：跨产品接入性质的**能力归位 + 插件实现 + 装配切换**；不改 bms 端口契约，不做产品业务迁移。
- **立项触发**：07B 收口后，`msg` 侧 04-5 开工需要 bms 侧适配任务作为前置契约；核查发现若按既有分工在 bms 内直接引入 `bms_msg.client`，会形成「msg → bms-core」与「bms → msg」的仓级循环依赖，且 07B 架构 38 §8 明令禁止服务间直接引用彼此内部实现。故本域先定依赖方向，再定适配层。

## 2. 需求 06-1：协议链上移与消息平台端口适配 <a id="r06-1"></a>

优先级：2（高）

**背景与动机**：消息平台已造好协议库（RPC 一元 / 流式、五类错误分类、full jitter 退避与调用链预算、幂等键去重、熔断三态），bms 早已交付 `BaseServiceClient` / `EventPublisher` / `ServiceCallPolicy` 三个端口契约与 `provider` 插件选择机制，但两者之间缺一个适配实现。缺口不在「谁写适配层」，而在**依赖方向**：msg 仓本身以路径依赖 `bms-core`，若 bms 反向引用 `bms_msg.client`，将同时造成仓级循环、bms 单仓 CI 断链与「同一协议两处实现」的漂移。不先解决这一层，04-5 的「业务代码不改即可切换」无法成立，各产品仓还得各自部署一份客户端。

**内容**：

1. **依赖方向定稿**：把帧编解码、RPC 客户端、韧性策略、值对象与协议异常整条链上移到 `bms_core` 新增能力域 `msgclient/`；`bms_core` 不引用任何 `bms_msg` 符号，msg 仓删除本地副本并统一 `from bms_core.msgclient import …`。依赖图恒为「产品 → 基座」，协议实现**唯一**。
2. **上移清单按职责切分**：整体上移客户端 10 个文件、帧编解码与 payload、两个枚举与三个协议异常、`deadline` / `naming`、两个值对象与 RPC 常量段；`RpcRegistry`（服务端装配态）、25 个 msg 业务异常、`MsgErrorMapper`、数据面常量、`api/` / `broker/` / `schemas/` 全部留在 msg 仓。基座不得混入产品业务标识。
3. **产品字面量改通用语义名**：帧字节、码值与契约形状不变，仅把 `FRAME_MAGIC` / `x-msg-frame` / `msg:rpc` 一类符号改为通用命名；msg 作为首个接入产品在声明里给具体值。契约快照仍由 msg 仓导出，字段值改从 `bms_core.msgclient` 常量读取。
4. **适配层与切换**：在 `bms_core` 内实现 `BaseServiceClient` / `EventPublisher` 的 msg 版实现，接入既有 `resolve_plugin`；`[service_client].provider` / `[event].provider` 取 `msg` 即全局切换，取原值即回滚，**业务代码零改动**。缺插件时拒启并报明确错，不静默降级。
5. **错误与上下文映射**：按 04-4 的 `category` / `retryable` / `code` / `attempts` / `backoff_ms` 映射 bms 异常，保留原始码与 `retryable`；`trace_id` / `tenant_id` / 服务 JWT 透传，不新增认证协议。
6. **回滚窗口三态**：明确「在途请求 / 未确认事件 / 双写窗口」的处置口径与回滚演练步骤；事件侧不双写，先停旧后启新并保留 outbox 重投。
7. **退出条件**：替换一个真实 `HttpServiceClient` 调用、切回原实现后行为恢复、事件发布链路可切换；两仓契约测试与回归全绿。
8. **实施归口**：协议链上移作为本域任务的**第一个前置实施步骤**（另立子任务，代码归后续会话执行）；本域立项阶段只定稿设计，不落实现代码、不预占 Kiwi 编号（按《测试规范》在编码前回读最大号 +1 登记）。

**完成标准**：`bms_core/msgclient` 能力域落地且被 msg 仓与各产品仓直接引用，bms 代码零 `bms_msg` 引用、`bms` 单仓 CI 不依赖 msg 仓即可通过；`provider` 切换与回滚经真实调用验证、业务代码零改动；错误码 / 超时 / trace / 租户映射正确；两仓变更模块行 + 分支覆盖率 100%、静态与文档三项校验全绿；04-5 前置契约标为已交付。
