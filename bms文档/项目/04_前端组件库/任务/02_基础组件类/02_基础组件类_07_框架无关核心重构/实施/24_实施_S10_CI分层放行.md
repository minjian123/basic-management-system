## 2. 背景与问题 <a id="issue"></a>

- S9 波 1 推送（`34622a7d`，纯文档：`bms文档/规范/**` + 前端基类清单 + 项目/设计/任务文档）触发**全量流水线**（backend 组 + 双端 + core-check……），与「避免文档类小改动空耗 CI」的分层流水线口径（《开发部署规划》§7.2）相悖；
- 根因：原口径为「workflow 触发路径含基座文档（为让 `base-integrity` 跑）+ 各 job 仅 `exists` 守卫（`exists` 只判文件存在，不判改动）」→ 基座文档改动即全量；
- 旧注释「不得用 `changes` 区分文档/代码场景给 job 放行」源于 2026-08-22 教训（MR 场景漏跑）——该教训的规避口径限定在 **MR**，main 直推可按域放行。

## 3. 交付物 <a id="deliverables"></a>

| 块 | 内容 |
| --- | --- |
| workflow（流水线级） | 触发路径**保持并集**（代码 + 基座文档；纯业务文档仍不建流水线）；注释改为「双层口径」说明（并集建线 / job 级放行 / MR 全量） |
| job 级 `changes`（main 直推规则新增，MR 规则不动） | **后端组**（backend-lint / typecheck / plugins / modules / test、integration-plan、三库集成、backend-image、container-scanning、swagger-snapshot、allure-report）：`backend/**/*` + `deploy/**/*` + `.gitlab-ci.yml`；**前端组**（frontend-check / core-check / frontend-mobile-check / frontend-build / frontend-mobile-build、frontend-image）：`frontend/**/*` + 根清单（`package.json` / `package-lock.json` / `tsconfig.base.json` / `.npmrc`）+ `deploy/**/*` + `.gitlab-ci.yml`；**E2E**：后端 + 前端 + 根清单 + CI 配置；**ci-base-build**：三份锁文件 + 两份 Dockerfile + `build-base.sh` + CI 配置 |
| 无 `changes`（保持无条件） | `gate-smoke`（必跑冒烟）、`base-integrity`（基座四项校验，秒级） |
| 文档 | 《[开发部署规划](../../../../../../规划/开发部署规划.md)》§7.2「免跑 / 分层放行」条按新口径重写 |

## 4. 效果与验证 <a id="verify"></a>

| 推送类型 | 触发的 job |
| --- | --- |
| 纯业务文档（规划 / 项目 / 设计 / 资料） | 不建流水线（不变） |
| 纯基座文档（规范 / 资料 / 资源 / 清单） | **仅 `gate-smoke` + `base-integrity`**（原：全量） |
| 后端代码 | 后端组 + 镜像档（前端组跳过） |
| 前端代码 | 前端组 + `core-check` + 双端构建（后端组跳过） |
| 锁文件 / Dockerfile / CI 配置 | 对应域 + `ci-base-build` 重建判定 |
| MR | 全量门禁（不变） |

- YAML 语法校验通过（pyyaml 解析 24 job）；规则抽查：后端 / 前端 / 镜像 / E2E / 无条件的 `changes` 落位与预期一致；
- 本批推送（含 `.gitlab-ci.yml`，属代码路径）按预期触发**一次全量**（作为新配置的实跑验证）；其后纯基座文档推送将只跑秒级两 job。
