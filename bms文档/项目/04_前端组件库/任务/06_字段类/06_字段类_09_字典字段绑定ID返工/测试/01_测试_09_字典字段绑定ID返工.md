## 4. 真实接口联调（后端 `02-14`） <a id="integration"></a>

本地栈（本机 SQLite + 三服务）按 `本地全套.py up --reset-db` 重建后执行：

| 项 | 请求 | 结果 |
| --- | --- | --- |
| 取数 | `GET /api/v1/dicts/role` | 200 / `code=0` / 3 条；条目 `id` 为**字符串**（18 位，如 `807611076517560320`，超 JS 安全整数） |
| 按 id 回填 | `GET /api/v1/dicts/role?ids=<id1>,<id2>` | 200 / `code=0`；返回条目 id 与请求**逐一相等**（顺序一致） |
| 非法 ids | `GET /api/v1/dicts/role?ids=abc` | 200 / `code=10001`（统一口径） |
| 版本比对 | `GET /api/v1/dicts/role?version=<当前版本>` | 200 / `code=0` / `items=null`（复用本地缓存） |

- 结论：`ids` 参数、条目 id 字符串输出、非法值业务码与版本三态与后端 `02-14` 契约逐项一致；18 位 id 实证了「字符串保精度 + 提交裸字面量序列化」方案的必要性（`Number(id)` 会改数）。
- 前端侧线参数由 `buildDictTypeQuery` 单一构造，HTTP 数据源用例断言 `ids=1790000000000000001%2C2` 实际拼装。

## 5. 原型对照 <a id="prototype"></a>

**结论：不适用（纯逻辑改动）。** 本次仅组件内部取值口径（条目 `value → id`）、分发映射（`select → option` 等）、字段属性 `widget` 覆盖与提交序列化出口，无可见界面形态、布局与交互流程变更，故不做逐页截图对照。

**原型依据**：[《字典字段》可交互原型](../../../../../../设计/组件设计/06_字段类/01_组件设计_字典字段/01_原型设计_字典字段.html)（字典下拉 / 级联 / 标签回显语义）、[《组件设计 · 字典字段》](../../../../../../设计/组件设计/06_字段类/01_组件设计_字典字段/01_组件设计_字典字段.md)「字典下拉件语义」节、[《组件设计 · 开关与枚举字段》](../../../../../../设计/组件设计/06_字段类/08_组件设计_开关与枚举字段/08_组件设计_开关与枚举字段.md)「形态由字段属性决定」节。

**不适用理由**：改动落在取值与分发语义（数据契约）而非呈现；下拉 / 单复选 / 标签等形态在原型中已定案，本次仅让字段属性可选用既有形态（`dropdown` / `dropdown-multi`），未新增或改动任何页面形态与交互流程。
