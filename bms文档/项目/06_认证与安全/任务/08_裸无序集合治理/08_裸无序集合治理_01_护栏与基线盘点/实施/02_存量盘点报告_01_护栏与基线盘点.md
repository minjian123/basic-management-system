## 4. 分批整改建议 <a id="batching"></a>

按「契约影响面优先、随模块任务顺带整改（不独立大改）」原则分四批（各批数量为**基线快照条目近似值**，实际以整改时脚本报告为准）：

| 批次 | 范围 | 约数量 | 建议 |
| --- | --- | --- | --- |
| 1 | 直接继承 `BaseObject` 的类字段（对外数据契约 / 值对象） | 8 | **优先**：影响对外契约与序列化，且集中在 `events` / `outbox` / `idp` / `masking` 等基座契约类 |
| 2 | `bms_core` 其余类字段与签名 | ~297 | 随对应基座 / 能力域任务顺带整改（如契约类字段改基座只读抽象） |
| 3 | `services`（identity / org / ai 等） | ~80 | 随各服务后续任务顺带整改；Schema 字段优先 |
| 4 | `backend/ops` 与 `scripts/tools` | ~169 | **最后评估**：`scripts/tools` 多为构建期内部工具（结构不外流），整改收益低于基座；可评估「内部工具豁免」或在低峰期统一处理 |

**整改注意事项**：
1. **改声明不改行为**：以「换基座形态 / 只读抽象」为主（如 `dict[str, X]` → `Mapping[str, X]`、`list[X]` → `Sequence[X]`），避免顺带改逻辑；对外返回稳定序要求（分页 / 游标 / 导出）优先换 `SortedList` / `SortedDict` 或 `Sequence`。
2. **同步基线**：每批完成后跑 `--update-baseline` 递减基线，使护栏持续反映现状（**不得**直接删基线条目绕过）。
3. **与 04_02 的解耦**：04_02（脱敏接入）仅需按本域落定的口径实现（声明与公共纯函数使用基座集合/只读抽象），**不依赖存量整改完成**。

## 5. 基线与递减口径 <a id="baseline"></a>

- 快照路径：`deploy/boundaries/bare_collections_baseline.json`（`version` / `generated_at` / `entries`）。
- 条目形态：`{file, line（规范化行内容指纹，不含行号）, container, position, count}`。
- 判定：**新增即失败**；基线残留（已修复）仅提示「可递减」，由 `--update-baseline` 重写完成递减；基线条目**不得**手工删除绕过。
