## 1. 设计目标与范围 <a id="goal"></a>

在 `03_05` 已交付的 `sys_account_lock` 表 / 模型 / 迁移与 `inactive` 扫描服务（`bms_org/services/account_lock.py::AccountLockService.scan_inactive`）之上，落**账号锁定的三型写入口径与解锁治理**：

1. **三型锁定**——`fail_limit`（登录失败达阈值，org `apply_login_state` 同事务写锁，与 `[login]` 限流窗口协同）、`inactive`（既有 180 天扫描）、`manual`（管理员手动锁定，新增接口）。
2. **手动解锁**——解锁接口（`user:unlock` 权限码占位）恢复账号状态（清 `locked_until` / `failed_count`）并留痕；锁定列表 / 详情接口。
3. **登录联动**——被锁账号登录一律被拒（统一 `20003` ACCOUNT_LOCKED）；`fail_limit` 到期自动解锁、`inactive` / `manual` 保持直到手动解锁的口径成文。
4. **表结构补齐**——`sys_account_lock` 补 `expire_at`（锁定期限）/ `unlock_mode`（解锁方式）两列，使锁记录与账号状态一致、审计可辨。
5. **审计留痕**——锁定 / 解锁写操作接 `AuditCapturer` 占位 + 结构化日志。

- **本任务范围**：org 服务锁定管理接口（列表 / 详情 / 手动锁定 / 解锁）；`AccountLockService` 扩展（`lock_manual` / `unlock` / `list_locks` / `detail`）；`CredentialService.apply_login_state` 写 `fail_limit` 锁与到期自动闭锁；`sys_account_lock` 补两列（表文件 v2 + ORM + 迁移 `org:tenant 0004`）；仓储筛选查询；错误码 `30007`；`user:lock` 动作码登记；审计接入；契约 / 前端类型重生成；测试与登记回写。
- **不在本任务**：`inactive` 扫描（`03_05` 交付，本任务仅补 `expire_at=NULL` 口径）；Celery 定时调度（**阶段八**）；真实 RBAC 判定（`require_permission` 仍为 Null = RBAC 前平台超管口径，**阶段七**）；锁定列表 / 解锁 / 手动锁定**页面**（**阶段七 · 用户管理**，本任务只交接口与 E2E 证据）；操作日志真实落库（**阶段八**）；锁记录 90 天归档（**后续审计归档策略**）；解锁回调 identity 清 Redis 失败计数（**不在本期**，见 §7）。
- **接口兼容**：org 服务**只增**公开端点与 DTO；`sys_user` / `sys_account_lock` 仅增可空列；`CredentialService` 构造只增可选仓储；identity 侧**零改动**（登录被拒的 `20003` 语义由 `01_03` 既有实现承载）。
- **安全影响（SDL）**：账号锁定是防爆破处置与合规扫描手段——专项验收点：三型锁定均可产生且落库、被锁账号登录被拒（`20003`）、解锁恢复登录且留痕、解锁幂等 / 并发分支明确、锁记录与 `sys_user.locked_until` 状态一致、日志不落敏感值（本表无敏感字段）。

## 3. 接口 / 契约与边界 <a id="contract"></a>

### 3.1 管理端点清单（org 服务，`require_auth` + 权限码占位） <a id="endpoints"></a>

落 **org 服务**新增 `org_locks` 模块路由，内部前缀 `/api/v1/org/locks`（外部经网关 `/api/org/v1/org/locks`）；模块级依赖 `Depends(require_auth)`，各端点再挂 `Depends(require_permission(...))`（permission 基座当前 Null 恒定通过 = RBAC 前平台超管口径）。

| 方法 | 路径 | 权限码 | 说明 |
| --- | --- | --- | --- |
| GET | `/api/v1/org/locks` | `user:query` | 锁定记录列表（分页 + 筛选） |
| GET | `/api/v1/org/locks/{lock_id}` | `user:query` | 锁定记录详情（含已解锁） |
| POST | `/api/v1/org/locks` | `user:lock` | 手动锁定账号（写 `manual` 型；幂等） |
| PUT | `/api/v1/org/locks/{lock_id}/unlock` | `user:unlock` | 手动解锁（恢复账号状态 + 留痕） |

**列表查询参数**：`page` / `size` / `order_by` / `order`（经 `page_query` 统一绑定；排序白名单 `id` / `locked_at`）+ `user_id`（精确）+ `lock_type`（`fail_limit` / `inactive` / `manual`）+ `active`（三态：True=生效中、False=非生效、缺省=全部）+ `locked_from` / `locked_to`（`locked_at` 闭区间，UTC）。

**列表响应**：`{code, message, data: {list, total, page, size}}`，`LockItem` 字段：

```json
{ "id": 1800, "user_id": 1001, "lock_type": "fail_limit", "reason": "登录失败达阈值自动锁定",
  "locked_at": "2026-10-14T02:00:00", "locked_by": null, "expire_at": "2026-10-14T02:15:00",
  "unlock_at": null, "unlock_by": null, "unlock_mode": null }
```

**手动锁定请求**（`POST /api/v1/org/locks`）：`{"user_id": 1001, "reason": "违规处置"}`（`user_id` 必填；`reason` 可选，≤255）。响应 `data` 为 `LockItem`。

**解锁响应**：`data` 为 `LockItem`（`unlock_at` / `unlock_by` / `unlock_mode='manual'` 已回填）。

- **操作者**：从请求上下文 `current_user_id` 尽力取（记入 `locked_by` / `unlock_by` 与审计 `actor`；未取到记 `NULL`）。
- **租户**：`require_auth` 解析租户写请求态，`get_uow` 依租户库键取 org 租户库会话（与内部端点同口径）。
- **不 join 用户表**：列表 / 详情只返 `user_id` 与锁定字段，账号名由前端经 org `resolve-names` 批量回显（沿用 01_04 会话管理口径）。

### 3.2 三型锁定写入口径 <a id="lock-types"></a>

| 锁型 | 触发 | 写入落点 | `sys_user.locked_until` | `expire_at` | `locked_by` |
| --- | --- | --- | --- | --- | --- |
| `fail_limit` | 登录失败达 `[login].max_failures` 阈值 | `CredentialService.apply_login_state`（同事务） | `now + [login].lock_seconds` | `same` | `NULL`（系统） |
| `inactive` | 180 天未登录扫描 | `AccountLockService.scan_inactive`（既有） | 远期哨兵 `9999-12-31` | `NULL`（需手动） | `NULL`（系统） |
| `manual` | 管理员手动锁定 | `AccountLockService.lock_manual`（新增） | 远期哨兵 `9999-12-31` | `NULL`（需手动） | 操作人 |

- **`fail_limit` 写锁**（`CredentialService`，注入可选 `AccountLockRepository`）：
  - `apply_login_state(success=False, lock_seconds>0)` 命中阈值时，在**既有单事务内**写 `sys_account_lock`（`lock_type='fail_limit'`、`expire_at=now+lock_seconds`、`locked_at=now`）；
  - **幂等**：若该账号已存在活跃锁（`get_active_by_user` 非空）则**不重复新增**（并发双请求只有一处落记录），仅按既有逻辑更新 `locked_until` / `failed_count`；
  - 登录流程既有逻辑保证「锁定后不再累计失败」（`verified.locked` 直接拒），故阈值命中处天然单次。
- **`inactive`**：不改既有扫描语义，仅补 `expire_at=NULL` 口径（模型默认即可，扫描 `create` 不传该列）。
- **`manual`**（`AccountLockService.lock_manual(user_id, *, reason, actor, now=None)`）：
  1. `UserRepository.get_by_id` 未命中 → 抛 `NotFoundError`（`10002`，见 §7 开放项）；
  2. 已存在活跃锁 → **幂等返回既有锁**（`created=False`，不重复写、不改状态）；
  3. 否则置 `sys_user.locked_until=PERMANENT_LOCK_SENTINEL`（`9999-12-31`），写 `sys_account_lock`（`lock_type='manual'`、`expire_at=NULL`、`locked_by=actor`）；
  4. 审计 `capture` + 结构化日志。

### 3.3 解锁口径 <a id="unlock"></a>

`AccountLockService.unlock(lock_id, *, actor, now=None) -> SysAccountLock`（单事务）：

1. `AccountLockRepository.get(lock_id)` 未命中 **或** `unlock_at` 非空 → 抛 `AccountLockNotFoundError`（`30007`）；
2. `UserRepository.get_by_id(lock.user_id)` 命中则清 `locked_until=NULL`、`failed_count=0`（恢复登录）；
3. 更新锁记录：`unlock_at=now`、`unlock_by=actor`、`unlock_mode='manual'`；
4. 审计 `capture` + 结构化日志（动作 / 目标锁 / 账号 / 操作者 / 结果 / 租户）。

- **幂等 / 并发**：重复解锁（已解锁）→ `30007`（业务失败，HTTP 200）；两管理员并发解锁同一活跃锁 → 仓储乐观锁（`version`）冲突 → `ConcurrentConflictError`（`10004` / 409）。不引入 `Idempotency-Key`（幂等基座当前 Null）。
- **不回调 identity**：仅清 org 侧 `locked_until` / `failed_count`；identity 侧 Redis 失败计数随窗口（`[login].lock_seconds`）自然过期，解锁后正确口令登录即成功并在登录成功路径清零（见 §7 开放项）。

### 3.4 锁定期满口径 <a id="expire"></a>

- **`fail_limit` 到期自动解锁**：登录逻辑既有「`locked_until <= now` 即放行」；在 `apply_login_state(success=True)` 写回时，若存在 `lock_type='fail_limit'` 的活跃锁且 `expire_at <= now`，补写 `unlock_at=expire_at`、`unlock_by=NULL`、`unlock_mode='auto'`（自动解锁留痕，锁记录与账号状态一致）。
- **`inactive` / `manual` 保持**：`expire_at=NULL`，不自动解锁，**须手动解锁**（远期哨兵保证登录始终被拒）。
- **列表 `active` 判定**：`active=True` ⇒ `unlock_at IS NULL AND (expire_at IS NULL OR expire_at > now)`；`active=False` ⇒ `unlock_at IS NOT NULL OR (expire_at IS NOT NULL AND expire_at <= now)`。
- **被锁登录被拒**：`CredentialVerifyResult.locked`（= `locked_until IS NOT NULL AND locked_until > now`）触发 identity `AccountLockedError`（`20003` / 401）；三型统一该口径（需求 / 任务文档中 `20004` / `20005` 系 `01_03` 码位避让前旧口径，实施时回写）。

### 3.11 失败分支与错误语义 <a id="failures"></a>

| 场景 | 行为 |
| --- | --- |
| 手动锁定目标用户不存在 / 已软删 | `NotFoundError`（`10002` / 404） |
| 手动锁定目标已存在活跃锁 | 幂等返回既有锁（`created=False`，不重复写） |
| 解锁 / 详情锁记录不存在 | `AccountLockNotFoundError`（`30007`，HTTP 200） |
| 解锁已解锁记录（重复） | `30007`（HTTP 200，幂等） |
| 两管理员并发解锁同一活跃锁 | 乐观锁冲突 → `ConcurrentConflictError`（`10004` / 409） |
| `lock_type` 非法（列表筛选） | `ParamError`（`10001`） |
| 列表无命中 | 200，`list=[]`、`total=0` |
| 无 / 失效登录态 | `require_auth` → `AuthError` / `SessionAuthError`（401） |
| 无权限码（RBAC 就绪后） | `PermissionError`（`30001` / 403） |
| `fail_limit` 到期 | 登录放行；成功写回时自动闭锁（`unlock_mode='auto'`、`unlock_by=NULL`） |
| `inactive` / `manual` 锁定中 | 登录一律 `AccountLockedError`（`20003` / 401），须手动解锁 |

## 4. 兼容性与消费方影响 <a id="compat"></a>

## 7. 边界与开放项 <a id="boundary"></a>

- **页面**：锁定列表 / 详情 / 解锁 / 手动锁定页面 → **阶段七 · 用户管理**（本任务只交接口与 E2E 证据；计划 §7 第 5 项已归口）。
- **Celery 定时**：`inactive` 扫描定时触发 → **阶段八**（`03_05` 边界）。
- **操作日志真实落库**：本任务 `AuditCapturer` 占位 + 结构化日志 → 真实落库 **阶段八**。
- **真实 RBAC**：`user:query` / `user:lock` / `user:unlock` 真实判定与越权口径 → **阶段七**（当前 Null = 超管口径）。
- **解锁不回调 identity 清 Redis 失败计数**：解锁后窗口内再次失败可能重新达阈值锁（限流机制正常行为）；是否回调 identity 清计数 → **后续评估**。
- **锁记录归档**：解锁记录 90 天后随审计归档 → **后续审计归档策略**。
- **`30001 用户不存在` 冲突**：概要 03 §7 的 `30001` 与平台 `PERMISSION=30001` 冲突属既有问题，本任务手动锁定目标不存在改用通用 `10002`，不回写概要该表。
- **`fail_limit` 到期未登录时的记录状态**：登录写回时才自动闭锁；期间列表以 `expire_at` 判定为非生效（不误显活跃）。
- **手动锁定期限**：`manual` 为无限期（`expire_at=NULL`），仅手动解锁；如需带期限再评估。
- Kiwi 用例编号 → 测试实施时登记回填。
