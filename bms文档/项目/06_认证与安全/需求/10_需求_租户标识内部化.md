## 1. 域说明 <a id="intro"></a>

当前系统在**内部链路**（库键 / 库名、JWT claim、事件信封、发件箱、身份映射表、请求态、缓存 / 限流键）里到处传**租户编码 `code`**；而租户的**主键是雪花 `id`**（`sys_tenant.id`，全系统唯一且不可变）。这带来根本缺陷：

- **稳定性**：`code` 是人为业务编码，**可变更**（录入错误 / 改名）、**软删后可复用**——拿它作内部键，一次改名即全系统断链、一次复用即串号；
- **效率**：租户维度列 `VARCHAR(64)`（code）比 `BIGINT`（id）索引更大、比较更慢（雪花 id 本身即为“快而准”而选）；
- **成本可控**：边界（子域名 / `X-Tenant-ID` / 登录请求）天然只有 `code`，入口做一次 `code → id` 解析（可缓存）即可，成本可忽略。

- **本域范围**：把**内部租户标识**由 `code` 改为雪花 `id`——边界仍用 `code`（对外接口以 code 表达，本系统 id 在外部无意义），内部（解析链之后）一律以 `tenant_id` 为准；含库键 / 库名、令牌 claim、事件信封、发件箱、身份映射表、请求态键、缓存 / 限流键的评估与改造，以及列类型迁移与兼容窗口。
- **不重复建设**：租户解析链（子域名 → 请求头 → token）、`TenantContext`（已同时携带 `code` 与 `tenant_id`）、`TenantSnapshot`、租户源与缓存（`TenantSource` / `TenantSnapshot`）已交付，本域在其上**换内部标识**，不重写解析与取数语义。
- **已定口径**（2026-09-28 拍板）：
  1. **对外仍用 code**：跨系统/跨服务的**对外接口**（子域名、`X-Tenant-ID`、登录请求体、SSO 回调等外部输入）保持 `code`（本系统 id 在其他系统无意义）；
  2. **内部以雪花 id 为准**：请求上下文（解析后）、令牌 claim、事件信封 / 发件箱、身份映射表、请求态键、缓存 / 限流键统一携带 `tenant_id`；
  3. **边界一次映射**：入口做一次 `code → id` 解析（经租户源 / 缓存），失败即拒绝；内部链路零回查；
  4. **命名按值**：装雪花主键的字段叫 `tenant_id`；装租户业务编码的字段叫 `tenant_code`（见《[后端开发规范](../../../规范/后端开发规范.md)》命名节）；
  5. **迁移与兼容**：`code` 列（VARCHAR）改 `tenant_id`（BIGINT）需 Alembic 迁移与**兼容窗口**；令牌 claim 切换需旧令牌兼容；
  6. **库键 / 库名落点**（`tenant_{…}` / `bms_{service}_{…}` 用 id 还是 code）由**详细设计**评估后定（涉及运维可读性与建库脚本）。
- **依据**：《[架构设计 · 多租户路由](../../../设计/架构设计/12_架构设计_子系统_多租户路由.md)》、《[架构设计 · 认证与会话](../../../设计/架构设计/14_架构设计_子系统_认证与会话.md)》、《[架构设计 · 事件总线](../../../设计/架构设计/16_架构设计_子系统_事件总线.md)》、《[架构设计 · 服务间通信与分布式一致性](../../../设计/架构设计/37_架构设计_子系统_服务间通信与一致性.md)》、《[后端开发规范](../../../规范/后端开发规范.md)》命名节、《[后端基类清单](../../../后端基类清单.md)》、需求 [09-2](09_需求_类体系根治理.md#r09-2)。

## 2. 需求 10-1：租户标识内部化（内部以雪花 id 为租户键） <a id="r10-1"></a>

优先级：3（中）

**背景与动机**：租户主键是雪花 `id`（`sys_tenant.id`，全系统唯一且不可变），`code` 只是可控人为编码（可改、软删后可复用）。当前内部链路以 code 作键，导致「改 code = 全链断链」「code 复用 = 串号」的隐患，且 `VARCHAR` 租户列索引效率低于 `BIGINT`。把内部标识换成雪花 id，可从根本上消除该隐患并提升租户维度查询效率；对外仍以 code 表达，边界做一次可缓存的 `code → id` 解析即可。

**内容**：

1. **边界（对外，仍用 code）**：子域名 / `X-Tenant-ID` / 登录请求体 / SSO 回调等外部输入保持 `code`；入口（中间件 / 依赖）做一次 `code → id` 解析（经租户源与缓存），解析失败按现有语义拒绝。
2. **内部标识（改 id）**：请求上下文（`TenantContext` 已带 `tenant_id`）、用户 / 服务 JWT 租户 claim、事件信封与发件箱、`sys_user_identity` 映射表、请求态键、缓存 / 限流键的租户位统一为雪花 `tenant_id`。
3. **库键 / 库名**：评估 `tenant_{…}` / `bms_{service}_{…}` 是否改用 id（详细设计定；若不改，需说明内部另有 id 与库键并存的口径）。
4. **迁移与兼容**：`code`（VARCHAR）列改 `tenant_id`（BIGINT）经 Alembic 迁移（三库 + 兼容窗口），存量行按 `code → id` 回填；令牌 claim 切换需旧令牌兼容读。
5. **命名**：按值命名——`tenant_id`（雪花主键）/ `tenant_code`（租户业务编码）；相关字段随改造对齐。

**完成标准**：内部链路（请求上下文 / 令牌 / 事件 / 发件箱 / 映射表 / 请求态 / 缓存与限流键）租户标识统一为雪花 `tenant_id`，对外仍以 `code` 表达且边界一次解析；`code` 变更 / 复用不再导致内部断链或串号；迁移与兼容窗口就位（`check-backend-base` 迁移链、契约快照、旧令牌兼容读数）；命名与《后端开发规范》一致；受影响定向 `pytest`、`ruff`、`pyright`、基座校验与 `preflight --fast` 全绿。
