## 1. 域说明 <a id="intro"></a>

架构铁律要求「公共字段与方法只在所属基类维护」「能力即继承链上的层」；但实测后端 **171 个类直接继承 `BaseObject`**（不可变值对象 110 / 可变数据类 3 / 框架类 58），`BaseObject` 事实上被当成**上帝基类**——任何类都往根系上挂，各体系基类形同虚设：「公共配置单点维护」落空、体系语义无从表达、护栏也只能检查「登记与否」而不能检查「继承是否合法」。

- **本域范围**：**严禁上帝基类**强制口径；三个体系基类（不可变值对象 / 可变数据契约 / 框架对象）；继承链固定四段；体系根白名单与**继承链护栏**（扩展 `check-backend-base`）；存量归位清单与分批；前后端对称（前端同步加框架对象层）；未登记直继承类补登。
- **不重复建设**：根系 `BaseObject`、集合体系（`BaseSorted` 等）、模块基类（`BaseRepository` / `BaseService` / `BaseModel` / `BaseSchema`）、中间层基类（`BaseCapability` / `BasePluggable` / `BasePlaceholder` / `BaseAsyncResource`）已交付；本域只做**体系分层、归位与护栏收口**，不重写既有基类语义。
- **已定口径**（2026-09-28 拍板）：
  1. **严禁上帝基类**：`BaseObject` 仅为根系（只承载所有类共有的最小语义）；**除体系根外，禁止直接继承 `BaseObject`**；体系根**必须承载本体系公共语义**（禁止空壳标记层）。
  2. **体系根白名单**＝现有 11 个（`BaseSchema` / `BaseModel` / `BaseRepository` / `BaseService` / `BaseSorted` / `BaseCapability` / `BaseAsyncResource` / `BasePlaceholder` / `BaseLogger` / `BaseRouter` / `UnitOfWork`，其中部分随体系重构改挂）+ 新增 3 个（`BaseValueObject` / `BaseDataContract` / `BaseFrameworkObject`）；**其余 160 个全部归位**。
  3. **继承链固定四段**：`BaseObject`（根系）→ `BaseFrameworkObject`（框架对象层）→ 能力域基类 → 插件基类；`BaseFrameworkObject` **接管**既有框架类基类（`BaseCapability` / `BaseAsyncResource` / `BasePlaceholder` / `BaseLogger` / `BaseRouter` 等）。
  4. **三个体系基类语义**：`BaseValueObject` ＝ `@dataclass(frozen=True)` 不可变值对象基类；`BaseDataContract` ＝ `@dataclass` 可变数据契约基类；`BaseFrameworkObject` ＝ 框架对象（非数据对象约定：不参与值语义与序列化输出 + `object_kind` 统一标识 + 可选 `aclose` 生命周期钩子位）。
  5. **落点**：`bms_core/core/objects.py`（新模块，与 `core/base.py` 根系、`core/collections.py` 集合体系同构）；**09_03 起改为包** `bms_core/core/objects/`——体系根在 `roots.py`、值对象角色链层一链一模块，对外仍从 `bms_core.core.objects` 导入。
  6. **护栏与豁免**：扩展 `check-backend-base`（继承链合法性：直继承仅允许体系根）；存量以基线快照 `deploy/boundaries/direct_base_object_baseline.json` 豁免并**递减**；**验收目标＝除体系根外零直继承**。
  7. **首轮交付**：体系基类 + 护栏 + 基线 + 分类盘点报告 + 规范 / 架构回写；**160 处存量归位按模块分批另立任务**。
  8. **前后端对称**：前端同步加框架对象层（组件链变四段）并回写《前端基类清单》；架构铁律由「固定前三段」改为「固定四段」。
- **依据**：《[架构设计 · 后端基础类体系](../../../设计/架构设计/04_架构设计_后端基础类体系.md)》、《[后端开发规范](../../../规范/后端开发规范.md)》「后端基座体系（强制）」节、《[后端基类清单](../../../后端基类清单.md)》、《[前端基类清单](../../../前端基类清单.md)》、《[AI开发规范](../../../规范/AI开发规范.md)》「架构铁律」节。
- **用例口径**：本域用例入 Kiwi TCMS，自动化用例标注用例编号（随任务实施登记）。

## 2. 需求 09-1：禁止上帝基类与体系根治理 <a id="r09-1"></a>

优先级：2（高）

**背景与动机**：基类是「公共语义的唯一落点」这一架构价值的载体；当 `BaseObject` 成为所有类的直接父类时，它既承担不了各体系的差异语义，也让「公共字段与方法只在链上基类维护」失去着力点——**基类体系形同虚设**。实测 171 个直继承类覆盖三个互不相干的语义域（不可变值对象 / 可变数据契约 / 框架对象），却共用同一父类，正是「上帝基类」的典型表现。若不治理，后续新增仍会继续挂根系，体系只会进一步虚化。

**内容**：

1. **强制口径**：`BaseObject` 仅作根系、禁止直继承（除体系根）；体系根必须承载本体系公共语义；口径写入《[后端开发规范](../../../规范/后端开发规范.md)》「后端基座体系（强制）」节与《[架构设计 · 后端基础类体系](../../../设计/架构设计/04_架构设计_后端基础类体系.md)》。
2. **体系基类交付**：`core/objects.py` 新增 `BaseValueObject`（`@dataclass(frozen=True)`）/ `BaseDataContract`（`@dataclass`）/ `BaseFrameworkObject`（非数据对象约定 + `object_kind` + 可选 `aclose` 钩子位），并登记《[后端基类清单](../../../后端基类清单.md)》。
3. **继承链四段落地（基座侧）**：`BaseFrameworkObject` 接管既有框架类基类（`BaseCapability` / `BaseAsyncResource` / `BasePlaceholder` / `BaseLogger` / `BaseRouter` 等）；`BaseSchema`（Pydantic 混入）与 `BaseModel`（ORM 混入）归数据契约体系；同步回写架构 04 的「固定四段」与清单继承链。
4. **护栏**：扩展 `check-backend-base`——**直继承 `BaseObject` 仅允许体系根**（白名单来自《后端基类清单》登记）；存量以 `deploy/boundaries/direct_base_object_baseline.json` 豁免并递减；新增直继承**即失败**；目标为零直继承。
5. **存量归位与盘点**：160 个直继承类按体系分类成文（区域 × 体系 × 位置 + 分批建议），另立分批任务推进归位。
6. **未登记补齐**：8 个未登记直继承类（含 `ops/` 4 个）本轮补登，并明确其归位体系。
7. **前后端对称**：前端加框架对象层（组件链：组件根 → 框架对象层 → 能力基类 → 组件基类），《[前端基类清单](../../../前端基类清单.md)》与架构铁律同步回写；前端契约用例同步。

**完成标准**：三个体系基类就位并登记；`check-backend-base` 对「新增直继承」失败、对「体系根」放行（自测用例证明）；基线快照生成且零漂移；160 处归位清单与分批建议成文；《后端开发规范》/《架构设计 · 后端基础类体系》/《后端基类清单》/《前端基类清单》四处口径一致（四段）；前端组件链加层落地且契约用例通过；`pytest`、`pyright`、`ruff`、基座校验通过。

**参考文档**：《[架构设计 · 后端基础类体系](../../../设计/架构设计/04_架构设计_后端基础类体系.md)》、《[后端开发规范](../../../规范/后端开发规范.md)》、《[后端基类清单](../../../后端基类清单.md)》、《[前端基类清单](../../../前端基类清单.md)》

## 3. 需求 09-2：租户编码命名统一与契约键隔离 <a id="r09-2"></a>

优先级：3（中）

**背景与动机**：价值对象归位与角色链分层（09_03）实测到**同语义字段名分叉**：同一「租户代码」在 `TenantContext.tenant_code` 与 `TenantSnapshot.code` 两处不同名；进一步全仓普查发现租户编码被叫成 `tenant_code` / `tenant_id` / `tenant` / `code` 等多种名字，散落在值对象、JWT claim、事件信封、缓存 / 会话载荷、请求态键、API 协议与 DB 列中。分叉的直接代价：租户链层公共段无法覆盖该字段（公共段必须在**全部**成员上同名成立），层只能以 `CODE_FIELD` 映射表达、调用方每处都要回查字段名；跨面命名不一也让“租户编码”在契约层难以一眼识别。因此确立**可判定的编码命名规则**并全域统一。

**内容**：

1. **命名规则（写入《[后端开发规范](../../../规范/后端开发规范.md)》）**：**泛指**——实体（基础数据）**自身**的业务编码字段统一叫 `code`；**专指**——其他数据里**引用**某业务编码的字段用限定名 `<业务>_code`（引用租户 → `tenant_code`）。判据：字段值是“本实体自己的编码” → `code`；是“指向别的实体的编码” → `<业务>_code`；真 ID 仍用 `<实体>_id`。
2. **租户视图对象用 `code`**：`TenantContext.tenant_code` → `code`（`TenantSnapshot.code` / `TenantSummary.code` / `SysTenant.code` 保持）。
3. **引用一律 `tenant_code`**：现名 `tenant_id`（存编码）/ `tenant` / 引用型 `code` 全部改为 `tenant_code`——覆盖值对象 / 数据契约、参数 / 局部变量 / 辅助函数名、JWT claim、事件信封与发件箱键、缓存 / 会话载荷键、请求态键、API 协议与 query 参数、DB 列（含 Alembic 迁移）。
4. **契约键隔离**：字段是 Python 属性，契约键（事件负载键、缓存载荷键、DB 列、JWT claim、API 协议）与外层逐处显式映射 / 改名；事件**信封**租户字段统一为 `tenant_code`（保留键），租户事件**负载**键为租户自身编码 `code`（信封键不得被载荷占用），事件侧以 `TENANT_EVENT_CODE_KEY` 常量单一来源。
5. **映射退场与护栏**：租户链层公共段纳入 `code`，`CODE_FIELD` 映射退场；受害者测试随改随更；新增命名护栏用例（视图对象自身编码为 `code`、引用型一律 `tenant_code`、层公共段、契约键一致、迁移链零漂移）。
6. **兼容口径**：**硬切不兼容**（用户拍板）——破坏面不设新旧并存窗口，由同一次发版同步切换。

**完成标准**：命名规则写入《后端开发规范》；`TenantContext.code` 落地；全域「引用租户编码」字段统一为 `tenant_code`（含 JWT claim / 事件信封 / API 协议 / DB 列与迁移），无引用型 `tenant_id` / `tenant` / `code` 残留（`grep` 白名单 + `pyright` 严格模式 + 用例共同保证，白名单见 09_04 详细设计 §3.4）；`CODE_FIELD` 退场；事件负载键与缓存载荷键隔离有断言；受影响定向 `pytest`、`ruff`、`pyright`、基座校验（迁移链）、契约快照与 `preflight --fast` 全绿。
