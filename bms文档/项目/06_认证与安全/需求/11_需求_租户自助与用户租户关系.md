## 1. 域说明 <a id="intro"></a>

本域把[《架构设计 · 多租户路由》](../../../设计/架构设计/12_架构设计_子系统_多租户路由.md)已交付**契约与占位**、但**真实取数一直缺位**的「租户自助」能力补成真：补上其数据承载——**用户↔租户关系**，并把「我加入的租户 / 切换租户」从 Null 占位换成真实实现。

- **本域范围**：用户↔租户关系表（平台库）与写入 / 读路径；`my_tenants`（我加入的租户）与 `switch`（切换租户）真实化；与登录链路、用户建号链路、租户开通链路的接线。
- **承接口径**：关系表落 **tenant 服务平台库 `bms_tenant`**（与 `sys_tenant` 同库）；「用户」的跨租户标识为**组合键 `(租户 code, 用户 code)`**——`username` / 用户编码**仅租户内唯一**，跨租户**不假设同名同人**（2026-10-04 拍板）。
- **明确不做**：**不以关系表支撑「登录前按账号反查租户」**——《[安全开发规范](../../../规范/安全开发规范.md)》§3「免认证链路不得查询业务数据」已把「登录前按账号查询租户归属 / 账号存在性」列为禁止项；登录页的租户标识口径见[需求 05-6](05_需求_登录前端.md#r05-6)。
- **端范围**：**仅后端 + 契约**（本域不出页面；租户切换的界面载体归前端全页面阶段）。
- **依据**：《[架构设计 · 多租户路由](../../../设计/架构设计/12_架构设计_子系统_多租户路由.md)》（「租户自助」节：「真实取数随 RBAC 阶段、品牌来源与平台超管租户管理随租户管理阶段回补（契约与占位已交付，2026-09-20）」）、《[架构设计 · 数据架构](../../../设计/架构设计/07_架构设计_数据架构.md)》（三库拓扑）、《[架构设计 · 认证与会话](../../../设计/架构设计/14_架构设计_子系统_认证与会话.md)》、《[概要设计 · 用户管理](../../../设计/概要设计/03_概要设计_用户管理.md)》、《[概要设计 · 租户管理](../../../设计/概要设计/26_概要设计_身份认证SSO.md)》、《[数据库开发规范](../../../规范/数据库开发规范.md)》。

## 2. 需求 11-1：用户↔租户关系与租户自助真实化 <a id="r11-1"></a>

优先级：2（高）｜**补充需求**（2026-10-04 立项）

**背景与动机**：架构 12 已给出「租户自助」契约（`BaseTenantSelfService` 的 `my_tenants` / `switch` / `brand`，REST 端点 `GET /api/v1/tenants/mine`、`POST /api/v1/tenants/switch`），但实现是 **Null 占位**（`NullTenantSelfService` 固定返回单租户、`multi_tenant=false`、不落库），数据模型里也**没有任何表**承载「用户在哪些租户中」——`sys_user` 落在 org 服务**每租户一份**的库中（`bms_org_{code}`），`username` 唯一仅为 `(username, deleted_at)` **租户内**唯一，平台库唯一全局的身份表 `sys_user_identity` 只映射 **SSO 外部身份 →（租户, 用户）**。

后果：**一切跨租户功能都缺公共前置**——「我加入的租户」列不出、「切换租户」无从校验、「邀请加入 / 跨租户协作」无法落地。本需求把关系与自助能力一次做真。

**内容**：

1. **关系模型（平台库 `bms_tenant`）**：新增用户↔租户关系表，记录「**某个租户内的某个用户**（`用户 code` + 所属 `租户 code`）**可访问的租户集合**」；租户位按「租户标识内部化」存**雪花 `tenant_id`**，对外契约仍用 `code`；唯一约束覆盖 `(所属租户, 用户 code, 目标租户, deleted_at)`；带 `source`（写入来源）与 `status`（有效 / 停用）及审计字段；软删除可回收。
2. **跨租户标识口径**：**组合键 `(租户 code, 用户 code)`**——`username` / 用户编码**仅租户内唯一**，跨租户**不假设同名同人**；「同一自然人」在系统内**没有**统一标识（本条不引入平台级账号 ID）。
3. **写入路径全量覆盖**：租户开通建超管、管理员建号（org 用户创建）、批量导入、SSO **JIT 建号**、**自助注册**、用户**停用 / 删除**（关系回收）——全部同步维护关系；写入方与一致性口径（同事务 / 事件驱动）在详细设计定稿，**禁止**出现「有用户无关系」的长期漂移。
4. **读路径真实化**：`my_tenants` 返回「当前用户可访问的租户」列表 + `current_code`（由调用方传入，仍以解析链为唯一权威）+ **`multi_tenant`**（租户数 > 1）；`switch` 校验「目标租户 ∈ 当前用户可访问租户」并按既有语义返回生效方式（是否需重发令牌）——**解析链优先级不变**。
5. **数据边界**：关系表**只承载「用户 ↔ 租户」可达性**，承载角色 / 权限的归属（RBAC）不在本条范围；关系表**不落**口令、邮箱、手机号等 PII。
6. **不服务登录前判定**：关系表**不得**用于免认证链路的账号反查（安全口径见域说明）；登录页的 `20007` 语义见[需求 05-6](05_需求_登录前端.md#r05-6)。
7. **契约与门禁**：`/tenants/mine`、`/tenants/switch` 的响应字段与新表进公开契约快照与 `@bms/api-types` 生成类型（零漂移由既有门禁保证）；表结构按《数据库开发规范》先改表文件 → 模型 → 迁移 → 登记状态两处回写。
8. **用例与核对**：覆盖「单/多租户 `my_tenants`」「`switch` 命中 / 未命中（越权）」「各写入路径建立关系」「停用删除回收关系」「关系表不参与免认证链路」；新增模块覆盖率达标。

**完成标准**：多租户用户的 `my_tenants` 能列出其可访问租户且 `multi_tenant=true`；`switch` 仅对可访问租户生效、越权目标被拒；六条写入路径均能建立 / 回收关系且无长期漂移；登录前链路**无任何**账号反查请求；契约四道门禁与数据库一致性校验全绿；后端 `pytest`、覆盖率门禁与 `preflight --fast` 全通过。
