## 1. 适用与边界 <a id="scope"></a>

- 本清单只覆盖「等外部条件」的四项；设计 §9 的**评估型开放项**（出现某种形态时再评估，如 DTO 自动投影、图标键形态、ORM 运行期检测）不在本清单，以各设计 §9 为准。
- 全部步骤假定：已按目标环境配好 `backend/config*.toml`（库连接串、`[app].unit`、`[topology].units`），且 `ops.migrate_topology` 可从 `backend/` 目录运行。
- 演练与生产走**同一套命令**，差异只在 `--from-url` / `--to-url` 指向的库与 `--notice` 的告知留痕；演练环境建议先用 SQLite 文件库把 S1 / S3 两条路径各跑一遍，再上真库。

## 2. W1 真库与真部署演练（S1 合并 / S3 换库） <a id="w1"></a>

对应计划 §7 第 5 项。已达成部分：S2 拆分方向五阶段端到端（复制 / 四类对账 / 切换 / 清理）在 SQLite 上可复现；本项补齐 **S1 合并方向**与 **S3 换库（拓扑版本不变）**，并把三条路径在 MySQL / PostgreSQL / DM8 上各跑一遍。

**前置**

1. 目标单元已在服务目录登记（租户库键 `tenant_{unit}_{db_basis}` 的服务段靠登记识别）；未登记时用 `--to-url` 显式给连接串。
2. 已取得备份凭据（`cleanup` 步强制要求 `--backup-ref`）。
3. 已告知相关方停机窗口（`stop` 档必须给 `--notice`；`dual` 档不停写，可不给）。

**步骤**

```bash
# 0) 计划（不建连、不建库）：核对源单元 / 目标单元 / 搬表清单 / 停机预估
uv run python -m ops.migrate_topology --tenant demo --domain role --to-unit identity --dry-run

# 1) S2 拆分（真库复验）：p1 预检 → p2 建表 → p3 搬数 → p4 对账 → p5 切换
uv run python -m ops.migrate_topology --tenant demo --domain role --to-unit identity \
    --notice "已告知：2026-11-xx 20:00-21:00 role 域迁移"

# 2) S1 合并（反向）：把域搬回原单元，验证「合并方向」同样可复现
uv run python -m ops.migrate_topology --tenant demo --domain role --from-unit identity \
    --to-unit platform --notice "已告知：回合并演练"

# 3) S3 换库（拓扑版本不变）：单元不变，只换库；--skip-release 保持拓扑不动
uv run python -m ops.migrate_topology --tenant demo --domain role --to-unit platform \
    --from-url "$OLD_DB_URL" --to-url "$NEW_DB_URL" --skip-release --notice "已告知：换库演练"

# 4) 观察期后清理旧库（必须有备份凭据）
uv run python -m ops.migrate_topology --tenant demo --domain role --to-unit identity \
    --step cleanup --backup-ref bkp-202611xx
```

**验收**

- 三条路径（S2 / S1 / S3）P4 对账均 `passed`：行数一致、主键覆盖无缺失、抽样逐列无差异、业务断言通过。
- 迁移期间能力取址不中断：迁移窗口内调用带能力声明的端点返回正常（非 403 / 非 `not_loaded`）。
- 三种真库方言（MySQL / PostgreSQL / DM8）各跑通一次；达梦走同步连接适配层，需显式 `--schema` 或缺省取连接串 `database` 段。
- 切换后 `sys_tenant_topology` 的新版本行与发布清单同版本，`apisix.yaml` 的上游指向新单元。

**回退**

- P4 未通过：不切换，目标库保持可弃；修数据后 `--resume` 从断点续跑。
- P5 已切换但需回退：把拓扑行整批改回上一版本（新行写入，不改原行），并按 §3 处理旧库数据差异。

## 3. W2 切换后数据补偿 <a id="w2"></a>

对应计划 §7 第 11 项（`04_02` 遗留 4）。当前实现只**量化**差异（P4 `extra` 计数），不搬回、不丢弃。

**步骤**

1. 取 P4 报告的 `extra` 明细：切换后旧库新增 / 变更的主键集合。
2. 按租户等级二选一，并在迁移记录里写明选择与依据：
   - **搬回**：按主键把 `extra` 行回写目标库（`DELETE+INSERT` 幂等，主键冲突以目标库为准），再跑一次 `--verify-only` 确认对账转绿；
   - **丢弃**：书面记录丢弃行数与业务影响，由租户负责人签字确认。
3. 回写 `04_02` 实施记录「遗留 4」与计划 §7 第 11 项。

**验收**：回退后的 `--verify-only` 通过，或存在签字的丢弃记录。

## 4. W3 跨仓调用方升级（`domains` claim） <a id="w3"></a>

对应计划 §7 第 16 项（`04_03` 设计 §9 开放项 8）。07C `04_03` 起，入站带能力声明的端点先判**域归属**：调用方服务令牌必须带 `domains` claim，否则按 fail-closed 拒绝（403「缺少业务域声明」）。

**步骤**

1. 在 mdm 等外仓把 `bms_core` 升级到含 `domains` claim 的版本（`ServiceTokenSpec.domains` + `instance_domains()` 出站注入）。
2. 外仓若使用自定义签发点，改为走 `bms_core` 的出站客户端，或在 `ServiceTokenSpec` 里显式带域。
3. 联调验证：外仓调用带 `require_capability` 的端点返回 2xx；日志出现 `capability_domain_attributed` 且 `domain` 非 `unknown`。

**回退**：外仓 `bms_core` 版本回退 + 该端点在外仓侧停用（不建议长期停用，等于放弃域归属判定）。

**验收**：mdm 全链路调用无 403；平台侧日志能按域过滤出该调用。
