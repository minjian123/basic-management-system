## 2. 实施过程 <a id="process"></a>

### 2.1 批 A：模型、表归属与域布局 <a id="batch-a"></a>

- `bms_core/models/platform/release_manifest.py`：`SysReleaseManifest`（一次发布一行）+ `SysReleaseManifestDomain`（一域一行），
  状态常量（`released` / `rolled_back` / `failed`）与 `GLOBAL_TENANT_SCOPE = 0` 同文件声明；
- `TABLE_OWNERSHIP` 增两条：`platform` / `platform_registry` / `Datasource.PLATFORM`（与拓扑表同域同库）；
- `MODEL_MODULES` 增该模块；`deploy/registry/platform.toml` 的 `platform_registry` `[[domains]].paths` 补该模型文件，
  再经 `ops.check_modules --render-domain-layout` 重渲染 `deploy/boundaries/domain_layout.json`（生成物不手改）；
- 表集断言（`test_table_registry.py`）随之补两行——`series_tables("platform_registry", PLATFORM)` 是清单表集的唯一断言点。

### 2.2 批 B：出口形态（DTO + 端口 + 仓储） <a id="batch-b"></a>

| 文件 | 内容 |
| --- | --- |
| `domains/platform_registry/dto.py` | `ReleaseDomainEntry` / `ReleaseCheckItem` / `ReleasePrecheckResult` / `ReleaseManifestSnapshot` / `RollbackStep` / `RollbackPlan`；结论与计划是**计算产物**（不落库） |
| `domains/platform_registry/ports.py` | `ReleaseRevisionPort`（域 → 结构 revision）与 `ContractBreachReader`（服务 → 破坏性变更摘要） |
| `repositories/release_manifest.py` | 主表：`max_version` / `latest` / `find_version` / `list_recent` / `page_rows` / `create_manifest`；明细：`list_by_manifest` / `append_entries`（只追加不改历史） |

### 2.3 批 C：发布服务（校验 / 写入 / 回滚） <a id="batch-c"></a>

`services/release.py::ReleaseService` 按设计 §3.3 / §3.4 / §3.5 落地：

- **六条校验**逐项出结论（`unit_complete` / `version_consistent` / `topology_current` / `structure_ready` /
  `contract_compatible` / `manifest_version_monotonic`），任一不过即整体失败；
- **明细派生只取实际值**：服务版本与契约版本取服务目录登记值、`schema_revision` 取记录表当前值；
  声明值（`--declare`）只用于与实值比对，不参与落盘；
- **写入**：主表 + 明细同事务；失败行（`record_failure`）只写主表；
- **回滚**：`plan_rollback` 生成逐域步骤（from / to revision）+ 阻断原因；`rollback` 追加一行 `rolled_back`、
  `rolled_back_from` 指向被回滚清单，原行不变；有域 revision 变化即要求 `confirmed`。

### 2.4 批 D：只读端点与运维入口 <a id="batch-d"></a>

- `api/releases.py`：`GET /api/v1/releases`（分页）/ `/releases/recent`（按单元最近 N 次）/ `/releases/{id}`，
  鉴权 `release-manifest:query`；**不放写端点**——发布与回滚只经 `ops.release`；
- `ops/release.py`：`precheck` / `record` / `fail` / `plan` / `rollback` / `list` 六子命令，
  经平台应用工厂进入生命周期复用同一个服务（命令行与进程内行为一致）；
  `DatabaseRevisions` 实现 revision 读面：按域清单所属数据源连库，`platform` → `tenant` 取首个已初始化值；
- 生成物重生成：`ops.contract_snapshot export`（`deploy/contracts/platform.json` +420 行）与
  `frontend/packages/api_types` 的 `pnpm gen`（仅 `platform.ts` 变化；其余服务快照只是行尾差异，已还原避免噪声）。

### 2.5 批 E：用例与文档 <a id="batch-e"></a>

- `services/platform/tests/release/test_release_service.py`：13 条（六条校验的正反例、写入、失败行、回滚确认与阻断、只读端点）；
- `libs/bms_core/tests/ops/test_release_cli.py`：3 条（参数解析、声明条目解析、跨库 revision 选链）；
- 设计 §8 对齐记录 10 条；本记录与测试记录；计划表进度回写。

## 4. 覆盖率 <a id="coverage"></a>

新增实现全部落在 `bms_platform.domains.platform_registry`（服务 / 仓储 / DTO / 端口 / schemas / api）与 `ops.release`：

- `ReleaseService` 的六条校验、明细派生、写入、失败行、回滚计划与回滚写入均有用例直击；
- `DatabaseRevisions.current` 的「首个已初始化」与「无连接串跳过」两条路径有用例；
- 覆盖率门禁（推送前）要求改动模块**行 + 分支 100%**：`services/release.py`（211 语句 / 70 分支）、
`repositories/release_manifest.py`（64 / 14）、`dto.py`、`api/releases.py` 均达 100%（首轮缺 24 行 16 分支，
补 8 条用例——契约读面空结论、回退目标越界、上一发布缺域、审计留痕、空明细追加、默认作用范围、无筛选分页、`_major` 空版本——后补齐）。

## 7. 偏差与遗留 <a id="leftover"></a>

1. **Kiwi 用例未登记**（编号未取得）：用例本体已入库，下一轮平台窗口补编号并回填 `@pytest.mark.kiwi_id`；
2. **契约兼容判定口径**：不内联 oasdiff，改为「消费结论 / 主版本兜底 + 显式放行」（设计 §8 第 2 条）；
3. **「待执行清单非空」未在发布路径判定**：只校验记录表已初始化，脚本视图归 `ops.migrate_tenants`（设计 §8 第 3 条）；
4. **能力级定位依赖注入结论**：未注入契约读面时只能定位到「业务域 + 契约版本」，定位到具体能力需由
   `ContractBreachReader` 提供 oasdiff 的服务级破坏性变更摘要（设计 §8 第 2 条）；
5. **部署流水线未切换为按单元发布**（设计 §4 影响面「修改部署流水线」）：本任务交付「清单 + 校验 + 回滚」能力与
   `ops.release` 入口，流水线改造随部署窗口进行——期间流水线仍按服务发布，发布清单需人工触发 `record`；
6. **发布锁未另做**：并发保护由唯一键 `(unit_key, tenant_scope, manifest_version, deleted_at)` 兜底
   （同版本并发必有一方失败），跨单元并行发布的分布式锁留部署窗口与 `04_02`；
7. **`ops.check_modules` 的「清单与库中发布记录一致」可选校验未做**（设计 §4 标注为可选）；
8. **真库与多单元并行未验证**：MySQL / PostgreSQL / DM8 上的建表与并发行为随 CI 集成档复验；
9. **按租户专属单元（`tenant_scope != 0`）未单独用例**：实现按「租户无拓扑回退默认拓扑」处理，用例只覆盖默认范围。
