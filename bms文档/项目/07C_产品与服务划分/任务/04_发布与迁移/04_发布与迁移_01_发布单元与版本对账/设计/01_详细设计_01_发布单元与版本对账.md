# 发布单元与版本对账详细设计

> 产品与服务划分 · 04 发布与迁移 · 01 发布单元与版本对账 · 详细设计（开发核心文档）

[文档首页](../../../../../../文档首页.md) › [01 发布单元与版本对账](../04_发布与迁移_01_发布单元与版本对账.md) › 设计

## 1. 目标与边界 <a id="scope"></a>

**目标**：合并部署时一次发布含多个业务域——必须能给出「**这次发布了哪些域、各自到哪个版本**」的原子快照，据此做前置对账与整体回滚，避免同单元内版本错配。

**范围内**：

1. 发布单元的定义（= 部署单元）；
2. 发布清单的数据载体（主表 + 域明细）与写入时机；
3. 发布前置校验（三方版本一致、拓扑一致、清单完整、契约兼容）；
4. 发布执行顺序与各步失败语义；
5. **批次回滚**（按清单整体回退）；
6. 观测与审计。

**范围外**：表结构变更清单本身（`03_02`，含执行期冲突校验）、拓扑记录与解析（`02_xx`）、拓扑迁移（`04_02`）、网关与身份（`04_03`）。

## 2. 现状 <a id="current"></a>

| 项 | 事实 |
| --- | --- |
| 发布单位 | 按**服务**发布（每个服务一条子流水线）；无「一次发布含哪些域」的记录 |
| 版本对账 | 靠人工比对：服务包 `CONTRACT_VERSION` ↔ 清单登记（`check_modules` 已有）、表结构 revision ↔ 库（无工具） |
| 契约门禁 | 已有（快照 + oasdiff 破坏性变更判定），但只针对**服务契约**，不覆盖“多域合并发布”的组合 |
| 回滚 | 按服务回滚；合并部署后“只回滚一个服务”等于回滚多个域，无原子单位 |
| 记录 | 无。发布后“这个单元跑的是哪一版”只能查部署系统 |

## 3. 设计 <a id="design"></a>

### 3.1 发布单元 = 部署单元 <a id="unit"></a>

| 项 | 口径 |
| --- | --- |
| 定义 | 一次发布的最小原子单位 = **一个部署单元**（可能含 1~N 个业务域） |
| 依据 | 单元内多域同库、同进程，版本必须整体一致；跨单元可独立发布 |
| 与租户的关系 | `tenant_scope = 0` 表示全局（默认拓扑）；非 0 为该租户专属单元（按租户分实例的形态） |
| 与拓扑的关系 | 每次发布绑定一个**拓扑版本**；拓扑不变时版本不变，拓扑变更即一次发布（与 `04_02` 联动） |

### 3.2 发布清单 <a id="manifest"></a>

两张表（结构以数据库设计表文件为准）：[sys_release_manifest](../../../../../../设计/数据库设计/数据表设计/sys_release_manifest.md)（主）与 [sys_release_manifest_domain](../../../../../../设计/数据库设计/数据表设计/sys_release_manifest_domain.md)（明细）。

| 要素 | 来源 | 用途 |
| --- | --- | --- |
| `unit_key` / `tenant_scope` | 拓扑记录 | 定位发布对象 |
| `manifest_version` | 单元内递增 | 发布序号；回滚定位上一版 |
| `topology_version` | `sys_tenant_topology` | 证明本次发布对应的拓扑 |
| 明细：`domain_key` | 单元所含域 | 逐域登记 |
| 明细：`schema_revision` | 该域「表结构变更记录表」当前值 | 结构版本快照 |
| 明细：`service_version` | 服务包版本 | 代码版本快照 |
| 明细：`contract_version` | 服务契约版本（能力契约随其） | 契约版本快照 |

**写入时机**：所有变更成功后，**主表 + 明细同事务写入**；失败写 `status=failed` 的主表行（不写明细），便于排查。

### 3.3 发布前置校验 <a id="precheck"></a>

| # | 校验 | 判定 | 失败 |
| --- | --- | --- | --- |
| 1 | 单元完整 | 单元所含域 = 拓扑记录中该单元全部域（不多不少） | 拒绝发布 |
| 2 | 三方一致 | 每域：代码声明的 `service_version` / `contract_version` = 清单登记值；`schema_revision` = 该域记录表当前值 | 拒绝发布，逐域列出 |
| 3 | 拓扑一致 | 本次发布携带的 `topology_version` = 库中当前版本 | 拒绝 |
| 4 | 结构就绪 | 该域待执行的表结构变更清单为空（已在发布前执行完毕） | 拒绝（提示先执行清单） |
| 5 | 契约兼容 | 与上一版契约做破坏性变更判定（复用既有 oasdiff 口径） | **拒绝**；确需破坏性变更时走主版本升级流程 |
| 6 | 清单版本 | `manifest_version` > 当前最大值 | 拒绝（不允许回退或重复） |

**输出**：逐项「校验 / 结果 / 详情」，任一不过即整体失败且不改变任何状态（先校验后执行）。

### 3.4 发布执行顺序 <a id="order"></a>

```
1 校验（§3.3）
2 拓扑生效（若本次含拓扑变更：整批替换拓扑记录，版本 +1）
3 逐域执行表结构变更清单（含 03_02 的执行期冲突校验；按域清单顺序）
4 执行种子（平台自身 + 产品声明，幂等 + 冲突报告）
5 启动 / 切换服务实例（按单元）
6 写入发布清单（主 + 明细）
7 输出发布结果（域清单与版本）
```

| 步 | 失败语义 |
| --- | --- |
| 1 | 不产生任何变更 |
| 2 | 拓扑版本回滚到原值（同事务） |
| 3 | 已成功的域不回滚（各自事务）；整体标记失败，发布清单记 `failed`；**由批次回滚处理** |
| 4 | 同 3（种子自带幂等，重跑安全） |
| 5 | 实例启动失败 → 整体失败；已切换实例按发布流程回切 |

**为什么结构变更先于服务启动**：新版本代码可能依赖新列；反向顺序会出现“代码已上、列还没加”。

### 3.5 批次回滚 <a id="rollback"></a>

| 项 | 口径 |
| --- | --- |
| 单位 | **一次发布**（按清单回退），不是单域、不是单服务 |
| 目标 | 取同单元同范围上一次成功的清单，逐域回退到其 `schema_revision` 与版本 |
| 顺序 | 与发布相反：先回切实例 → 回退种子（不自动删数据）→ 逐域回退结构清单（自后向前）→ 回退拓扑（如本次改过拓扑，走 `04_02` 的反向迁移） |
| 记录 | 新增一行清单（`status=rolled_back`，`rolled_back_from` 指向被回滚清单），**不修改原行** |
| 不可逆保护 | 结构回退若涉及删列（原升级是加列的反向），默认**拒绝自动执行**，需人工确认后单独处理——数据丢失不可召回 |
| 部分回滚 | 不支持（会留下域间版本错配）；确有单域问题走“修复合入 + 再次发布” |

### 3.6 与相邻机制的分工 <a id="boundary"></a>

| 机制 | 管什么 | 本任务关系 |
| --- | --- | --- |
| `03_02` 执行期冲突校验 | 执行结构清单时的表集相交 / 记录表污染 / 结构漂移 / 并发 | 发布流程第 3 步调用它 |
| `02_01` 拓扑记录 | 域 → 单元与库 | 发布第 2 步整批替换 |
| `02_03` 种子编排 | 幂等 / 冲突 / 失败隔离 | 发布第 4 步调用 |
| `04_02` 拓扑迁移 | 拓扑变更的数据搬迁 | 发布第 2 步涉及拓扑时由其提供步骤 |
| `04_03` 网关与身份 | 对外路径与令牌 | 发布第 5 步后校验对外路径一致 |

### 3.7 观测与审计 <a id="observe"></a>

| 项 | 要求 |
| --- | --- |
| 审计 | 发布、回滚各记一条审计（单元、范围、清单版本、域数与各域版本） |
| 指标 | `release_total{unit, status}`、`release_duration_seconds{unit}`（分段：结构 / 种子 / 启动） |
| 日志 | 逐域输出「域 / 结构 revision / 服务版本 / 契约版本」 |
| 查询 | 管理面只读端点：按单元查最近 N 次发布与明细；供运维回答“这个单元跑的是哪一版” |

## 4. 影响面 <a id="impact"></a>

| 类别 | 对象 | 变更 |
| --- | --- | --- |
| 新增 | 模型 `bms_core/models/platform/release_manifest.py`（两表） | 表模型 |
| 新增 | 表归属登记 | 两表归 `platform` 域、`platform:platform` 清单 |
| 新增 | `services/platform` repository / service / api | 清单写入、查最近发布、只读端点 |
| 新增 | 发布编排命令（`ops.release` 或等价） | 执行 §3.4 序列，含前置校验 |
| 修改 | 部署流水线 | 按单元发布（替代按服务发布） |
| 修改 | `ops.check_modules` | 增加“清单与库中发布记录一致”校验（可选） |
| 不改 | 表结构变更清单机制 | 本任务只调用 |

## 5. 测试设计 <a id="test"></a>

| # | 用例 | 断言 |
| --- | --- | --- |
| 1 | 单域单元发布 | 主表 + 1 条明细，版本正确 |
| 2 | 多域单元发布 | 明细行数 = 域数，各域版本快照正确 |
| 3 | 单元域集与拓扑不符 | 拒绝发布并列出差异 |
| 4 | 三方版本不一致 | 拒绝并逐域列出（代码 / 清单 / 记录表） |
| 5 | 拓扑版本过期 | 拒绝 |
| 6 | 待执行清单非空 | 拒绝并提示先执行 |
| 7 | 契约破坏性变更 | 拒绝；主版本升级路径可通过 |
| 8 | 清单版本回退 | 拒绝 |
| 9 | 执行中某域结构失败 | 整体失败、清单记 `failed`、已成功域不回滚 |
| 10 | 批次回滚 | 逐域回到上一清单版本；新增 `rolled_back` 行，原行不变 |
| 11 | 回滚涉及删列 | 默认拒绝，需显式确认 |
| 12 | 部分回滚请求 | 拒绝（不支持） |
| 13 | 按租户范围 | `tenant_scope != 0` 的单元独立发布互不影响 |
| 14 | 查询最近发布 | 端点返回主表 + 明细 |
| 15 | 与执行期校验联动 | 结构清单执行失败时发布流程终止且状态一致 |

## 6. 风险与边界 <a id="risk"></a>

| 风险 | 处置 |
| --- | --- |
| 清单与实际部署不一致（记录说 A、实跑 B） | 发布编排按清单生成部署；启动后回采实际版本比对，不一致标 `failed` |
| 回滚不可逆（删列/删表） | 默认拒绝自动回滚；要求“向前修复”优先 |
| 多单元并行发布互相影响 | 发布锁按单元粒度；跨单元共享库的场景禁止（架构上不鼓励） |
| 发布清单成为第二份事实源 | 清单只记录“发布结果快照”，版本事实仍在代码与记录表；对账失败即失败，不双向同步 |
| 失败行堆积 | `failed` 行保留（排查依据），按时间清理策略另定 |

## 7. 开放项 <a id="open"></a>

| # | 事项 | 归口 |
| --- | --- | --- |
| 1 | 是否要求“灰度/分批”发布（同单元多实例分批切换） | 多实例形态明确后评估 |
| 2 | 发布清单是否对外暴露给租户可见（“你的系统当前版本”） | 运营需求出现时评估 |
| 3 | 失败行与明细的保留期 | 数据量增长后定 |
| 4 | 契约兼容判定是否细化到能力级（而非服务级） | 能力契约单独演进时评估 |

## 8. 对齐记录 <a id="alignment"></a>

实施（2026-10-30）与本文设计的差异，按「设计 → 实现」逐条记录原因；设计未改口径的部分不重复。

| # | 设计 | 实现 | 原因 |
| --- | --- | --- | --- |
| 1 | §3.3 #2 / #4：`schema_revision` 取「该域记录表当前值」 | 经 `ReleaseRevisionPort` 注入读面；`ops.release` 的实现按域清单所属数据源连库（`platform` → `tenant` 取首个已初始化值） | 域服务只持平台库会话；读别的库要连接串与方言，域内不应知道库拓扑（与 `03_04` 的「注入工厂」同形态） |
| 2 | §3.3 #5：与上一版契约做破坏性变更判定（复用 oasdiff） | 可选 `ContractBreachReader` 端口消费结论；未注入时按**声明版本主版本**口径判定，`--allow-breaking` 显式放行 | oasdiff 要 docker 与外部二进制，不能进发布路径的同步校验；CI 的 `ops.contract_gate` 仍是破坏性变更的权威判定 |
| 3 | §3.3 #4：待执行清单为空 | 只校验「版本记录表已初始化」；「待执行脚本非空 / 未知 revision / 版本分叉」由 `ops.migrate_tenants` 的版本单调与清单一致校验拦截 | 脚本视图只有迁移侧持有（`alembic` 目录）；发布流程重跑一遍脚本发现等于把迁移逻辑复制一份 |
| 4 | §3.2：明细记录三方版本快照 | 明细落**实际值**（服务目录登记值 + 记录表当前值）；声明值只在校验 2 里与实际值比对 | 实现初版让声明值覆盖明细，导致「声明什么就记什么」、校验 2 恒过——已由「声明服务版本 9.9.9」用例抓出并改正 |
| 5 | §3.7：管理面只读端点 | 只做 `GET`（分页 / 最近 / 单条）；发布与回滚仅经 `ops.release` | 不暴露「网页点一下发布」的写入口，避免绕过校验链；写路径必须带结构 revision 读面（跨库），HTTP 进程里拿不到 |
| 6 | §3.2：失败写 `status=failed` 主表行 | `record_failure` 只写主表、不写明细；**校验阶段失败不写任何行** | 与 §3.4 第 1 步「不产生任何变更」一致；失败行只用于执行阶段（第 3~5 步）留痕 |
| 7 | §3.5：结构回退默认拒绝自动执行 | 「需人工确认」按**是否有域 revision 变化**判定：纯代码回退（revision 全相同）不要求确认，有变化即要求 `--confirm` | 保守口径：无法从 revision 串判断是否含删列，故「有结构回退就要求人工确认」 |
| 8 | §3.1：`tenant_scope != 0` 为租户专属单元 | 该租户无自身拓扑时回退默认拓扑，并在「单元完整」结论里注明 | 与 `TenantTopologyService.export` 同口径，避免自举前无法发布 |
| 9 | §4 影响面：新增两表 + 域登记 | 模型 `release_manifest.py` 进 `deploy/registry/platform.toml` 的 `[[domains]]`；`deploy/boundaries/domain_layout.json` 由 `ops.check_modules --render-domain-layout` 重渲染 | 域布局已是「清单第九类声明 + 生成物」口径（`03_01` 修订），生成物不手改 |
| 10 | §4 影响面：新增 api | 3 个只读端点 → `deploy/contracts/platform.json` +420 行、`frontend/packages/api_types/src/platform.ts` 由 `pnpm gen` 重生成 | 契约快照与前端类型都是生成物；其余服务快照仅行尾差异，已还原避免噪声 |
