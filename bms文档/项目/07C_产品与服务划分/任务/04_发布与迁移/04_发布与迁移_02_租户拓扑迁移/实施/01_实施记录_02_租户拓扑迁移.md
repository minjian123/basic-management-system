## 2. 实施过程 <a id="process"></a>

### 2.1 勘察：设计与代码先行对照 <a id="survey"></a>

| 设计假设 | 代码现状 | 结论 |
| --- | --- | --- |
| `db/admin.py` 已有建 / 删 / 存在性 / 执行语句 | 四者齐备，另有 `resolve_target` / `admin_url_for` / `fetch_rows` | 直接复用（P2 建库、清理删库） |
| `ops.init_schema` 能按「目标单元的域表集」建表 | 域表集由**单元**反推（`unit_domains` → 域布局），不接受显式域清单 | **不符**：拆分到新单元时取不到目标域表 → 补 `domains_metadata` / `apply_domains_schema` |
| `ops.migrate_tenants` 需改为按清单维度 | `03_02` 已交付：`unit_series` 按域清单执行、逐清单一张版本记录表 | **无需改动** |
| 跨库搬数据 / 双写 / 对账「无」 | 确认无 | 新建内核 |
| 拓扑记录读面可用 | `TenantTopologyService` 依赖平台应用生命周期 | **不符**（P1 需在不起应用时跑）→ 源单元判定改为只读 SQL |
| 租户可解析为主键 + 库名基 | `TenantRef` 只有 `code` / `db_basis`，无主键 | **不符** → 补 `tenant_id` |
| 目标单元库键可派生 | `parse_db_key` 只对**已登记服务**识别 `tenant_{service}_{code}` 的服务段 | **不符**（新单元未登记即不可派生）→ 计划阶段显式报错，允许 `--to-url` |

### 2.2 批 A：搬运与对账内核 <a id="batch-a"></a>

`libs/bms_core/src/bms_core/db/topology_migration.py`（新增，358 语句 / 62 分支）：

| 能力 | 实现要点 |
| --- | --- |
| 表集 | `table_targets(metadata)` 按外键依赖序（父表在前）；无主键即 `ConfigError`（无法按主键幂等写） |
| 复制 | 单列主键游标分页（`pk > 上一批末值`），每批 `DELETE`（按主键 `IN`）+ `INSERT`，一批一事务；复合主键直接拒绝（按首列游标会跨批漏行） |
| 断点 | `MigrationProgress`（JSON：表 → `{cursor, done}`）；游标不可 JSON 表示时丢弃该表游标（下次从头重跑，幂等） |
| 限速 | 每批之间 `asyncio.sleep(rate_limit_seconds)` |
| 对账 | 行数 / 主键覆盖（源−目标、目标−源）/ 抽样逐列比对 / 业务断言（数值按差额、其余按文本） |
| 连接 | `AsyncTableGateway`（`AsyncConnection.run_sync`）与 `SyncTableGateway`（达梦等仅同步方言，线程池内跑独立事件循环）；SQL 逻辑只有一份 `_*_sync` |

### 2.3 批 B：按域建表与租户引用 <a id="batch-b"></a>

- `db/bootstrap.py`：新增 `domains_metadata(domains, datasource, *, include_infrastructure)` 与 `apply_domains_schema(...)`；
  `unit_metadata` / `apply_unit_schema` 改为委托（「域集由单元反推」成为特例，表集派生仍单一来源 `unit_tables` / `series_tables`）；
  `include_infrastructure=False` 供 P3 使用——发件箱等基础设施表每库一份，搬过去会造成重复投递；
- `tenant/registry.py`：`TenantRef` 增 `tenant_id`（`sys_tenant.id`），查询语句补该列；拓扑写入按主键进行。

### 2.4 批 C：五阶段运维入口 <a id="batch-c"></a>

`ops/migrate_topology.py`（新增，377 语句 / 86 分支；`RUN_IMAGE = platform`——P5 复用平台服务层）：

| 阶段 | 行为 | 失败处置 |
| --- | --- | --- |
| P1 预检 | 七条结论：租户与库名基 / 域已登记 / 搬迁表集 / 目标单元合法 / 目标库可取 / 数据量与停机预估（含依赖方）/ 停机告知留痕；`--dry-run` 不建连 | 任一条不过即停，不产生任何变更 |
| P2 建库建表 | 目标库不存在则建；按显式域清单幂等建表；域清单有脚本则执行到 head | 目标库可整库删除回退 |
| P3 搬数 | 内核复制（幂等 + 断点 + 限速） | 单表失败即截断，目标库可重来 |
| P4 对账 | 内核四类对账 | 不全绿不切换 |
| P5 切换 | `TenantTopologyService.replace`（整批替换 + 版本 +1）与 `ReleaseService.record` **同一事务**；未在本轮跑 P4 时须 `--confirm` | 发布校验不过 → 整体回滚，拓扑不生效 |
| cleanup | 观察期后删旧库，必须给 `--backup-ref` | 缺备份凭据即拒绝（退出码 1） |

其他：`--strategy dual` 反复「回填 + 对账」直至连续 `--converge-rounds` 轮全绿；审计留痕追加一行 JSON
（谁 / 何时 / 哪些域 / 策略 / 库 / 结果 / 告知）到 `<state-dir>/audit.jsonl`；依赖方清单读 `sys_capability_grant`
（`capability_name LIKE '%.{domain}.%'`），授权表不可用只记「不可用」不阻断。

## 5. 问题与处置 <a id="issues"></a>

| # | 问题 | 处置 |
| --- | --- | --- |
| 1 | 平台库读面用同步 `create_engine` 打开 `sqlite+aiosqlite` 连接串 → `MissingGreenlet`（此前异常被「表不存在」吞掉，真库才暴露） | 抽出 `_query_platform`：按方言选异步连接（`create_async_engine`）或同步连接（线程池），拓扑与授权两处共用 |
| 2 | `tenant_{unit}_{code}` 的服务段只对**已登记服务**可识别：`grpops` 被解析成 `code` 前缀 → 库名变成 `bms_platform_grpops_demo` | 计划阶段校验「解析出的服务段 == 目标单元」，否则报「未在服务目录登记」并要求登记或 `--to-url`；用例改用已登记单元 `identity` |
| 3 | `TenantRef` 无主键，拓扑写入无法定位租户 | 补 `tenant_id` 并更新查询语句；`_ref` 签名变更连带修既有用例 |
| 4 | 目标库为异步驱动时同步复制代码不可用（MySQL 侧无同步驱动） | 内核走 `AsyncConnection.run_sync`（SQL 仍是同步函数），仅达梦等同步方言走线程池 + 同步连接 |
| 5 | 复合 / 无主键表按首列游标会跨批漏行或无法幂等写 | 一律 `ConfigError` 拒绝并提示「补单列主键或人工迁移」（本项目登记表均为单列 `id` 主键） |
| 6 | `except ConfigError: raise` 成为不可达分支 | 删除，统一 `except Exception` 包装（异常类型写入消息），保留可诊断性 |
| 7 | 集合声明护栏拦测试辅助函数的 `list[...]` / `dict[...]` / `locals` 声明 | 断言辅助改用 `ConcurrentStableFrozenList` / `ConcurrentStableDict`，与全仓口径一致 |
| 8 | 覆盖率采集留下 `backend/.coverage` 触发工作区卫生 | `check_workspace_hygiene.py --clean` 隔离到 `tmp/_quarantine/` 后复跑开发环 |

## 7. 偏差与遗留 <a id="leftover"></a>

1. **Kiwi 用例未登记**（编号未取得）：用例本体已入库（39 条），下一轮平台窗口补编号并回填 `@pytest.mark.kiwi_id`；
2. **B 档双写未接线**：`--strategy dual` 只做到「回填 + 反复对账追平 + 切换前连续全绿」，应用侧同一次写落两库的开关属运行期写路径改造（设计 §9 开放项 5）；
3. **真库未验证**：MySQL / PostgreSQL / DM8 上的复制与对账只在 SQLite 上跑通；同步方言路径以「同步连接串 + 方言替身」锁适配层，真库随 CI 集成档与部署窗口复验；
4. **回滚的数据补偿未实现**：切换后旧库已停写且新库有新数据时，`extra` 只量化差异，「补偿搬回」或「书面丢弃」由租户等级决定，仍靠人工执行（设计 §3.5 已约定须在预检时书面确认）；
5. **S1 / S3 未做端到端演练**：S2（拆分）走通全程用例；S1（合并）以「同单元多域表集派生」部分覆盖，S3（换库）以「显式 URL 通道」部分覆盖，整单元搬迁随设计 §7 开放项 3 评估；
6. **迁移进度与审计为文件形态**：跨机续跑与查询需落库（设计 §7 开放项 2 / §9 开放项 6）；
7. **观察期与停机窗口靠人工纪律**：`--notice` / `--backup-ref` 只做留痕与闸门，无法验证「观察期是否真的等够」；
8. **依赖方清单口径较粗**：按能力名 `%.{domain}.%` 反查 `sys_capability_grant`，能力名不合该形态（历史遗留命名）时查不到，只记「未查到」不阻断。
9. **未回写表文件的「归属库」行**（`03_02` 遗留 3 指向本窗口）：库名派生已随部署单元（默认单元＝服务，既有库名零变化），但 56 份表文件的「归属服务 / 库」行仍写「服务 · 库名」形态；批改属文档收口，归 `05_01` 统一处理，本任务不改（避免把字段级口径变更混进迁移实现）。
