# 租户拓扑迁移详细设计

> 产品与服务划分 · 04 发布与迁移 · 02 租户拓扑迁移 · 详细设计（开发核心文档）

## 1. 目标与边界 <a id="scope"></a>

**目标**：让「同一租户的拓扑」可以从一种形态迁到另一种（单体 ⇄ 分组 ⇄ 独立），迁移过程**数据不丢、可校验、可回退**，并复用既有的建库建表、结构变更清单与发布清单机制。

**范围内**：

1. 三类迁移场景与适用策略；
2. 五阶段流程（预检 → 建库建表 → 搬数 → 校验 → 切换与清理）；
3. 数据搬迁的三档策略（停机窗口 / 双写回填 / 预留 CDC）；
4. 校验与对账（行数 / 主键覆盖 / 校验和 / 关键业务断言）；
5. 切换与回滚（含回填期新数据的补偿口径）；
6. 工具命令与演练要求。

**范围外**：拓扑记录本身（`02_01`）、发布清单（`04_01`）、结构变更清单的执行（`03_02`）、跨机房/跨云迁移。

## 2. 现状（可复用的与缺的） <a id="current"></a>

| 能力 | 现状 | 可用性 |
| --- | --- | --- |
| 建库 / 删库 / 存在性 | `db/admin.py`：`create_database` / `drop_database` / `database_exists` / `run_statements` | **可直接复用** |
| 建表 | `ops.init_schema` 按表集幂等建表；`ops.init_tenant` 建库 + 建表 + 种子 | **可直接复用** |
| 按服务 × 数据源 × 租户执行迁移 | `ops.migrate_tenants`（逐库 `upgrade head`、幂等、失败不中断、`--dry-run`） | 需改为按**清单**维度（`03_02`） |
| 归档搬迁契约 | `archive` 契约（`BaseArchivePolicy`），当前为 `null` 空实现 | 概念可借鉴，**不能直接用**（按时间归档，非拓扑搬迁） |
| **跨库全量搬数据** | **无** | 需新建 |
| **双写 / 增量回填** | **无** | 需新建或走停机策略 |
| **迁移对账工具** | **无** | 需新建 |

**结论**：建库、建表、执行清单已齐备；缺口集中在**搬数据**与**对账**两块。

## 3. 设计 <a id="design"></a>

### 3.1 三类场景 <a id="scenario"></a>

| 编码 | 场景 | 数据流向 | 典型 |
| --- | --- | --- | --- |
| S1 | **合并**：独立单元并入大单元 | 源库（单域）→ 目标库（多域共享） | 租户业务萎缩，从独立回退到分组 |
| S2 | **拆分**：大单元中某域独立出去 | 源库（多域共享）→ 新库（单域） | 采购变重，从分组升到采购独立 |
| S3 | **换库**：拓扑不变、库变更 | 旧库 → 新库（同名不同实例/前缀） | 库名规范化、实例迁移 |

三者共用同一套流程，差异只在「搬迁的表集」与「目标库是否已存在」。

### 3.2 五阶段流程 <a id="flow"></a>

```
P1 预检 → P2 建库建表 → P3 搬数 → P4 校验 → P5 切换与清理
```

| 阶段 | 内容 | 失败处置 |
| --- | --- | --- |
| **P1 预检** | 目标拓扑合法（域 → 单元唯一、单元非空）；目标库可取（能建/已存在）；**搬迁表集**（该域登记的表）列全；数据量与容量评估；依赖方清单（谁在读该域）；**停机窗口与影响范围确认，涉及停机的按租户等级提前告知**（告知渠道与提前量由运营约定，记录留痕） | 不产生任何变更 |
| **P2 建库建表** | 目标库不存在则建；按目标单元的域表集幂等建表（`init_schema`）；执行该域结构变更清单到 head | 目标库可整库删除回退（无业务数据） |
| **P3 搬数** | 按「表 → 主键区间分批」复制；大表分页、限速、可断点续传（记录已完成区间） | 目标库重来（幂等：按主键 upsert） |
| **P4 校验** | 四类对账（§3.4）；不通过则停在 P3 修复 | 不切换 |
| **P5 切换与清理** | 拓扑记录整批替换（版本 +1）→ 按 `04_01` 发布 → 观察期（旧库保留只读）→ 清理 | 回滚见 §3.5 |

**顺序约束**：P4 全绿才允许 P5；P5 的拓扑替换与发布是**同一次发布动作**（不拆两次）。

### 3.3 数据搬迁三档策略 <a id="strategy"></a>

| 档 | 做法 | 停机 | 适用 |
| --- | --- | --- | --- |
| **A 停机窗口** | 停写 → 全量搬 → 校验 → 切 → 恢复 | 有（分钟级到小时级，取决于数据量） | 中小租户、可约窗口 |
| **B 双写回填** | 开启双写（旧库为准）→ 全量回填历史 → 追平增量 → 切读 → 停旧写 → 校验 | 接近零（切换瞬间秒级） | 大租户、不可停业务 |
| **C CDC / 逻辑复制** | 依赖数据库复制能力 | 零 | **当前不具备**，列为开放项 |

**本期实现 A**，B 作为同一流程的可选分支（双写开关是迁移工具的一部分），C 只保留接口位置。

**A 档细节**：

1. 停写范围 = 该域（不是整租户）——同租户其它域不受影响；
2. 全量复制按表分批（主键游标），每批提交 + 记录进度，中断可续；
3. 复制期间目标库不对外服务（避免半量数据被读到）。

**B 档细节**：

1. 双写窗口内**旧库为权威**（写入以旧库成功为准，新库失败记差异并告警，不阻塞业务）；
2. 回填完成后按主键比对差异，追平后再切读；
3. 切换后旧库转只读，作为回滚兜底。

### 3.4 校验与对账 <a id="verify"></a>

| # | 校验 | 方法 | 通过标准 |
| --- | --- | --- | --- |
| 1 | 行数一致 | 逐表 `count(*)` | 完全相等（双写窗口内允许差额，但须在追平后相等） |
| 2 | 主键覆盖 | 源库主键集合 − 目标库主键集合 | 差集为空 |
| 3 | 内容校验和 | 按主键区间抽样，比对关键列拼接的哈希 | 抽样一致率 100%；差异须逐条解释 |
| 4 | 关键业务断言 | 业务聚合（如订单数、库存总量、用户数）源目标对比 | 相等（或差异在允许口径内且书面说明） |

**校验报告**：逐表一行（表 / 源行数 / 目标行数 / 差集 / 抽样结果），失败即列出差异主键。

### 3.5 切换与回滚 <a id="switch"></a>

| 项 | 口径 |
| --- | --- |
| 切换 | 拓扑记录整批替换（与 `02_01` 一致）→ 走 `04_01` 发布（含结构就绪、契约兼容、清单写入） |
| 观察期 | 旧库保留**只读**至少一个约定窗口；读路径不再指向旧库 |
| 回滚触发 | 切换后业务异常且指向迁移（数据缺失、查询报错） |
| 回滚方式 | 拓扑记录改回原单元（新版本）→ 重新发布；**旧库仍是权威则数据无丢失** |
| 回滚的数据补偿 | 若切换后旧库已停写而新库写入了数据，回滚需把新库**增量搬回**旧库（按切换点时间戳/主键区间），或接受丢弃并记录——**由租户等级决定，须在预检时约定** |
| 清理 | 观察期结束、校验通过后删旧库；删除前备份（按备份策略） |

**禁止**：把“删旧库”放在切换同一步——失去回滚兜底。

### 3.6 与相邻机制的接口 <a id="interface"></a>

| 机制 | 本任务如何使用 |
| --- | --- |
| `02_01` 拓扑记录 | 读当前拓扑（源）、写目标拓扑（整批替换 + 版本递增） |
| `03_02` 表结构变更清单 | P2 阶段把目标库的结构清单执行到 head；执行期冲突校验同时生效 |
| `04_01` 发布清单 | P5 的切换即一次发布；清单记录迁移前后各域版本 |
| `db/admin.py` | 建库、存在性判断、执行语句 |
| `ops.init_schema` | 按目标单元域表集建表 |
| `archive` 契约 | 不适用（按时间归档，非拓扑搬迁） |

### 3.7 工具与命令 <a id="tool"></a>

新增 `ops.migrate_topology`（薄命令，实现在基座）：

| 参数 | 语义 |
| --- | --- |
| `--tenant <code>` | 目标租户（必填） |
| `--domain <key>`（可重复） | 迁移的业务域（S1/S3 可多个） |
| `--to-unit <unit_key>` | 目标部署单元 |
| `--strategy stop|dual` | 搬迁策略（缺省 `stop`） |
| `--dry-run` | 只输出计划（表集、数据量、依赖方、预计停机），不建连 |
| `--step p1..p5` | 分步执行（可单独重跑某步，各步幂等） |
| `--verify-only` | 只跑 P4 对账 |
| `--resume` | P3 断点续传 |

**演练要求**：任何正式迁移前，先在**同规格副本**上完整跑一遍（含 P4 全绿与回滚演练），演练记录进迁移方案。

### 3.8 风险控制 <a id="risk-control"></a>

| 项 | 要求 |
| --- | --- |
| 幂等 | P2 建表、P3 复制（主键 upsert）、P5 拓扑替换均可重跑 |
| 限速 | P3 支持并发与速率上限，避免压垮源库 |
| 断点 | P3 记录已完成的主键区间，中断可续 |
| 观测 | 指标：复制行数 / 速率 / 失败批次；日志：逐表进度 |
| 变更留痕 | 迁移全过程记审计（谁、何时、哪些域、策略、结果） |

## 5. 测试设计 <a id="test"></a>

| # | 用例 | 断言 |
| --- | --- | --- |
| 1 | S2 拆分（停机） | 目标库表集正确、数据行数一致、切换后业务查询正常 |
| 2 | S1 合并（停机） | 两域并入同库、表名不冲突、切换成功 |
| 3 | S3 换库 | 拓扑版本不变前提下完成库切换（或按方案升版本） |
| 4 | P1 预检失败（域/单元非法） | 不产生变更 |
| 5 | P2 重复执行 | 幂等（不重复建表、不报错） |
| 6 | P3 断点续传 | 中断后续跑，结果与一次跑完一致 |
| 7 | P3 单批失败 | 记录进度，重跑该批成功 |

| 9 | P4 抽样差异 | 列出差异主键与列 |
| 10 | 切换后回滚（旧库未停写） | 拓扑回退，数据无丢失 |
| 11 | 切换后回滚（旧库已停写 + 新库有新数据） | 按约定补偿或明确丢弃并留痕 |
| 12 | 观察期后清理 | 旧库删除前有备份 |
| 13 | 双写策略（B 档） | 旧库权威、新库差异告警、追平后校验通过 |
| 14 | 迁移中结构清单冲突 | 执行期校验拦截（`03_02` §3.8） |
| 15 | 发布清单记录 | 迁移前后版本正确落库（`04_01`） |

## 6. 风险与边界 <a id="risk"></a>

| 风险 | 处置 |
| --- | --- |
| 数据丢失（最严重） | 旧库只读保留至观察期结束；删库前备份；P4 四类对账全绿才切换 |
| 停机超预期 | P1 给出数据量与预计停机；超限改走双写；分批按租户 |
| 双写期差异累积 | 差异告警 + 追平校验；不得在差异未清零时切换读 |
| 回滚后数据不一致 | 预检时书面约定“丢弃或补偿”，并在回滚记录中留痕 |
| 迁移期间并发写冲突 | 停机档位直接停写；双写档位旧库权威、目标库 upsert |
| 跨域共享库中的表混搬 | 搬迁表集严格按该域登记表清单（`03_01` 的 `domain` 字段） |

## 8. 对齐记录 <a id="alignment"></a>

实施（2026-10-30）与本文设计的差异，按「设计 → 实现」逐条记录原因；设计已按现状描述、实现与之一致的部分不重复。

| # | 设计 | 实现 | 原因 |
| --- | --- | --- | --- |
| 1 | §2 / §4：`ops.migrate_tenants`「需改为按清单维度（`03_02`）」 | **未改动**：`03_02` 已交付为「单元 → 域清单」（`unit_series` 按域派生、逐清单一张版本记录表） | 设计撰写时 `03_02` 尚未落地；再改一次等于重复造轮子 |
| 2 | §2：`ops.init_schema` 按目标单元域表集建表 | 新增基座 `db/bootstrap.py::domains_metadata` / `apply_domains_schema`（**显式域清单**）；`init_schema` 维持「由单元反推域集」不动 | 拆分到新单元时，静态域布局还不认这些域是该单元的，按单元反推取不到要搬的表 |
| 3 | §3.7：8 个参数（`--tenant` / `--domain` / `--to-unit` / `--strategy` / `--dry-run` / `--step` / `--verify-only` / `--resume`） | 全部落地，另加 `--from-unit` / `--tenant-id` / `--db-basis` / `--from-url` / `--to-url` / `--schema` / `--batch-size` / `--sample-size` / `--rate-limit` / `--max-rounds` / `--converge-rounds` / `--assert` / `--notice` / `--state-dir` / `--skip-release` / `--backup-ref` / `--confirm` | 演练与真库要能给显式连接串、达梦要切模式、对账要业务断言、告知与备份要留痕参数；均属设计已要求能力的操作面 |
| 4 | §3.7：`--step p1..p5` | 增 `cleanup` 取值（删旧库独立成步） | §3.5 明令「禁止把删旧库放在切换同一步」，必须可单独执行、可单独审计 |
| 5 | §3.3：B 档「双写回填」，双写开关是迁移工具的一部分 | `--strategy dual` 实现为「反复（回填 + 对账）直至连续 `--converge-rounds` 轮全绿」；**应用侧双写开关未接线** | 真实双写要改运行期写路径（同一次写落两库），属 ORM 级改造，超出本任务边界；见 §9 开放项 5 |
| 6 | §3.4 第 3 类：按主键区间抽样，比对关键列拼接的**哈希** | 改为**逐列文本比对**（抽样行两侧取整行，按列取值文本比较，`None` 记 `<null>`） | 哈希要先定算法与跨方言编码口径，逐列比对等价且差异能定位到具体行；报告口径不变 |
| 7 | §3.4 第 4 类：关键业务断言（订单数 / 库存总量等） | 以 `--assert 名称=SQL` 显式给出（两侧各取一个标量，数值按 `--tolerance` 差额、其余按文本）；缺省不跑 | 业务聚合口径因域而异，平台侧无法内置；显式给还能把断言内容写进审计记录 |
| 8 | §3.6：`02_01` 拓扑记录「读当前拓扑（源）」 | P1 的源单元判定改为**直连 `sys_tenant_topology` 只读查询**（`--from-unit` 可覆盖）；P5 写入仍走 `TenantTopologyService.replace` | P1 必须在「不起平台应用」的场景也能跑（演练 / 变更评审阶段）；读走 SQL 不产生第二套写逻辑 |
| 9 | §3.2：P5「拓扑替换与发布是同一次发布动作」 | 同一会话同一事务：发布清单校验不过 → 拓扑替换**一并回滚**（拓扑不生效）；另留 `--skip-release`（仅演练） | 避免「拓扑已切、清单没写」的半完成态；atomic 化比设计更强 |
| 10 | §3.5：清理「观察期结束、校验通过后删旧库；删除前备份」 | 独立步骤 `--step cleanup`，**必须给 `--backup-ref`** 才执行删库 | 把「删除前必须有备份」做成硬闸门，而不是文档约定 |
| 11 | §4 影响面：`db/admin.py` 增加批量子集复制所需的最小能力（或由复制器直连） | 选「复制器直连」：新模块 `db/topology_migration.py`（`AsyncConnection.run_sync` + 仅同步方言的线程池），`admin.py` 未改 | `admin.py` 职责是建删库与语句执行；批量行复制属迁移内核。两种连接共用同一套 `_*_sync` SQL 函数，不写两套逻辑 |
| 12 | （设计未载）目标单元的可解析性 | **目标单元须已在服务目录登记**：否则租户库键 `tenant_{unit}_{db_basis}` 的服务段不可识别（`parse_db_key` 只对已登记服务识别），计划阶段即报错并要求登记或给 `--to-url` | 既有键体系按登记识别服务段，本任务不改键体系；把限制前移到计划阶段，避免搬到一半才发现库不可达 |
| 13 | 需求完成标准「迁移后表归属校验通过」 | P4 的搬迁表集**即**该域的登记表集（`series_tables`），并校验目标库中逐表存在；「库内表 vs 登记」的全量对账仍由 `ops.check_tables` 负责 | 迁移只对自己搬的域负责；全库归属对账是既有单点职责，不在此重复 |
