## 2. 实施过程 <a id="process"></a>

### 2.1 勘察：设计与代码先行对照 <a id="survey"></a>

| 设计假设 | 代码现状 | 结论 |
| --- | --- | --- |
| 外部路径已按域（`/api/{product}/v1/{domain}`） | 产品级路由确已按域；平台服务仍按服务（`/api/{service}/v1`） | **一致**，只改上游映射 |
| 上游由服务键决定（`upstream_node(service_key)`） | `render_product_routes` 的 `upstream_id` 取 `record.service_key` | **不符** → 改为取拓扑单元；上游段补单元条目 |
| 令牌只有 `aud` + scope，无域维度 | `ServiceTokenSpec` 无 `domains`；`VerifiedToken` 无域字段 | **不符** → 令牌契约与签发 / 校验两侧都补 |
| 入站只有能力分配一道 | `require_capability` 直接 `check_capability_access` | **不符** → 前置域归属判定（第一道） |
| 日志 / 指标按服务与请求打标 | `RequestLoggingMiddleware` 只有 `method / path / status / duration_ms` | **不符** → 注入 `domain_key` / `unit_key` 与指标标签 |
| 配置只有 `[app].service` | `[app].unit`（`03_02`）+ `[topology].units`（`02_02`）已存在 | **部分不符**：单元已可声明，缺「声明域即拒」的护栏 |
| 拓扑记录是唯一来源 | 平台库 `sys_tenant_topology` 有默认拓扑；域登记面（域布局）可派生同一映射 | **一致**（两档取数，见 §2.4） |
| 能力目录可按能力取提供方域 | `collaboration/grant.py::capability_domain` 已提供 | 直接复用（不按能力名前缀猜域） |

### 2.2 批 A：域归属内核与令牌域声明 <a id="batch-a"></a>

`libs/bms_core/src/bms_core/collaboration/domain_scope.py`（新增，76 语句 / 24 分支）：

| 能力 | 实现要点 |
| --- | --- |
| 域段解析 | `domain_of_path(path)`：内部路径 `/api/v1/{域段}/...` → 域标识；非登记域段 / 非内部路径 → `unknown`（登记面取 `domain_service_view()`，不另建清单） |
| 本实例承载域 | `instance_domains()` = 默认拓扑启用域 ∩ `instance_units()`（`[topology].units`）；`enabled_domains()` 供边缘（网关票据）用，拓扑未装载时回落域登记面 |
| 令牌域声明 | `claimed_domains(claim)` 解析空格分隔串 / 序列（去重保序）；常量与 `oauth/token.py` 同源（`SERVICE_DOMAIN_CLAIM` / `SERVICE_DOMAIN_SEPARATOR`） |
| 入站归属判定 | `check_domain_attribution(capability, claimed, consumer=...)`：能力域取 `capability_domain`；三道拒法（本实例未启用 / 未声明 / 声明不符）均给明确错误并留痕 |
| 审计域标注 | `domain_of_table(table)`：表 → 归属域（读表归属登记），未登记回落 `unknown` |

令牌链路（四处，单一口径）：

- `oauth/token.py`：`ServiceTokenSpec.domains` + 常量 `SERVICE_DOMAIN_CLAIM` / `SERVICE_DOMAIN_SEPARATOR`；
- `oauth/jwt.py`：签发时非空才写 claim（缺失可被入站识别）；
- `oauth/verify.py`：`VerifiedToken.domains` 由 claim 回填；
- `servicecall/http.py`：出站令牌带 `instance_domains()`（惰性导入，避免 `collaboration → servicecall.base → servicecall.http` 环）；
- `services/identity/.../auth/api/auth.py`：网关代发票据带 `enabled_domains()`（边缘承载全部启用域）。

### 2.3 批 B：入站两道判定与观测标注 <a id="batch-b"></a>

- `api/capability.py`：`require_capability` / `require_capability_or_service` 在能力分配判定**之前**调 `_check_domain`（第一道），
  白名单分支（平台内部服务）不判域；拒绝一律 403 并给出域 / 能力 / 消费方；
- `api/middleware.py`：`RequestLoggingMiddleware` 的访问日志增 `domain_key` / `unit_key`，请求指标
  （`bms_request_total` / `bms_request_duration_seconds`）加 `domain` / `unit` 标签；`domain=unknown` 且路径以
  `/api/v1/` 开头时另发一条 `request_domain_unknown` 告警（样本不丢）；
- `audit/base.py` + `audit/null.py`：捕获契约要求 `payload["domain_key"]`，占位实现按表归属写入（真实实现归阶段六）。

### 2.4 批 C：网关路由按部署单元 <a id="batch-c"></a>

`services/gateway_catalog.py`：

| 能力 | 实现要点 |
| --- | --- |
| 路由拓扑 | `RouteTarget(unit_key, status)` + `default_route_topology()`（域登记面派生）+ `route_targets_from_rows()`（平台库行投影） |
| 生成前校验 | `validate_route_topology()`：域须在拓扑有行、单元非空、产品域路径不得与 `/api/{service}/v1` 重叠；不过即 `CatalogError` |
| 产品级路由 | 上游取 `unit_key`；`disabled` 域**不生成**；对外路径不变（`/api/{product}/v1/{domain}`） |
| 上游段 | 启用服务（服务级路由）+ 产品路由的部署单元（同单元去重） |
| 兼容 | 默认拓扑下单元＝承载服务 → 生成物与改造前**逐字一致**（`deploy/gateway/apisix.yaml` 未变、`check` 零漂移） |

`ops/gateway_config.py`：

- `load_topology_from_db(url)`：读默认租户（`tenant_id = 0`）当前版本拓扑行 → 路由拓扑；同时比对其它租户当前版本行，
  把「域落在不同单元」的租户列为**告警**（边缘路由全局，按租户分流属开放项 5）；
- 两档取数：清单模式用默认拓扑（零依赖），注册表模式用平台库拓扑；默认拓扑为空时告警并退回域登记面；
- `render` / `check` 均透传拓扑，`check` 的零漂移与请求体上限口径不变。

### 2.5 批 D：配置护栏与用例 <a id="batch-d"></a>

- `core/config.py`：`TopologySettings.domains` 字段 + `model_validator` —— **声明即拒启**（`ConfigError`，错误给出
  「只声明 `[topology].units`，承载域＝默认拓扑启用域 ∩ 本实例承载单元」）；
- 新增用例：`tests/collaboration/test_domain_scope.py`（12 条）、`tests/api/test_request_domain_labels.py`（6 条）；
  扩展：`test_require_capability.py`（+4）、`test_gateway_catalog.py`（+8）、`tests/ops/test_gateway_config.py`（+5）、
  `tests/core/test_config.py`（+2）、`tests/audit/test_hashchain.py`（+2）、`services/identity` 令牌两处（+2）；
  跟随修正：`test_capability_dependency.py`、平台三处（`test_internal_query` / `test_internal_permission` / `test_capability_cleanup`）。

## 5. 问题与处置 <a id="issues"></a>

| # | 问题 | 处置 |
| --- | --- | --- |
| 1 | 顶层导入成环：`servicecall.http → collaboration.domain_scope → grant → servicecall.base`（`servicecall.__init__` 又导入 `http`） | 出站令牌处**惰性导入** `instance_domains`，其余保持顶层（环只在 `http` 这一侧） |
| 2 | 域声明常量两处写（令牌契约 / 域内核） | 集中在 `oauth/token.py`（`SERVICE_DOMAIN_CLAIM` / `SERVICE_DOMAIN_SEPARATOR`），域内核引用之（单一来源） |
| 3 | 存量平台用例的令牌替身无 `domains` → 带能力声明的端点 403 | 按设计 fail-closed 保留硬拒；替身补域声明（`user` / `permission_meta`），并新增「缺声明 / 声明不符 / 域未启用」三条拒法用例 |
| 4 | 网关生成器改上游后可能漂移 `apisix.yaml` | 默认拓扑＝域登记面派生，生成物与改造前逐字一致；`check` 验证零漂移，测试台账记「路径不变、上游随拓扑」 |
| 5 | 边缘路由全局 vs 租户级拓扑：不同租户把同域放不同单元时路由说不清 | 只用默认拓扑生成 + 对其它租户偏离**告警**；按租户路由记开放项 5 |
| 6 | `tests/ops/` 目录与 `ops` 包同名：仓库根跑 pyright 时 `from ops import gateway_config` 解析到测试目录（`unknown import symbol`） | 改用 `import ops.gateway_config as gateway_config`（与 `tests/ops` 既有写法一致），解析稳定 |
| 7 | `ops/gateway_config.py` 的「APISIX 上限不可解析」分支不可达（正则已限定数字 + 单位），覆盖率卡在 99% | 去掉不可达分支（不做死代码），改为 `parse_size(...) or 0` + 注释说明不变式；文件回到 100% |
| 8 | `04_02` 交付的 `MigrationProgress` 未继承基类（`test_base_inheritance` 全量跑才暴露，开发环按改动文件选测没选中） | 基类改 `BaseFrameworkObject`（可变状态 + IO 行为的框架对象），修后基座全量 2819 passed |

## 7. 偏差与遗留 <a id="leftover"></a>

1. **Kiwi 用例未登记**（编号未取得）：用例本体已入库（本轮新增 39 条），下一轮平台窗口补编号并回填 `@pytest.mark.kiwi_id`；
2. **按租户路由未做**：边缘只用默认拓扑生成，其它租户的域级落点差异只告警（设计 §9 开放项 5）；
3. **域级条件装配未做**：未启用域不装配处理器这一层没落地，现靠「不生成路由 + 入站拒绝」两层保证
   （设计 §9 开放项 6；动态装配与「同镜像多单元」冲突）；
4. **审计真实实现未接入**：只把 `domain_key` 写进捕获契约与占位实现，真实审计捕获归阶段六；
5. **指标面板未做**：指标已带 `domain` / `unit` 标签，按域下钻的面板归可观测性阶段；
6. **跨仓调用方未升级**：外仓（mdm 等）服务令牌不带 `domains` 时调用带能力声明的端点会被拒（403），
   须随其依赖升级一起上线（设计 §9 开放项 8）；
7. **真机未验证**：网关侧只做生成物与零漂移校验，`apisix.yaml` 未在真机重载验证（默认拓扑下生成物未变，风险低）；
8. **按域限流 / 按域灰度**未做（设计 §7 开放项 1 / 2，保持原状）。
