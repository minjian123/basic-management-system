## 2. 实施过程 <a id="process"></a>

### 2.1 交付内容 <a id="deliver"></a>

| 交付物 | 落点（设计节） | 要点 |
| --- | --- | --- |
| 术语与三层模型 | §2 | 业务域 / 部署单元 / 数据单元 / 基座能力域四者对照；业务域回答「这是什么业务」（稳定），部署单元回答「跑在哪个进程与库」（可变） |
| 判据（可操作化） | §3 | 拆域四条（数据所有权 / 业务语义 / 扩缩 / 变更节奏）满足两条及以上；开产品四条（仓库 / 发版 / 团队 / 定价）满足两条及以上；反例清单与复核触发条件 |

| 三处待复核结论 | §5.3 | 认证与身份联邦拆两域；验证码并入认证；租户管理面与 `tenant` 合并；平台参数与目录拆两域；`sys_account_lock` 归用户域（2026-10-24 修订） |
| 现状差距与阶段对应 | §6 | 7 项缺口逐条给阶段 / 任务（无「无归口」项） |
| 交付物验收映射 | §7 | 5 项验收要点逐条对应任务完成标准 |

### 2.2 与代码现实一致性核对 <a id="consistency"></a>

| 核对项 | 事实 | 结论 |
| --- | --- | --- |
| 平台侧 16 域清单 ↔ 域布局 | `deploy/boundaries/domain_layout.json` **16 域**，`domain_key` 与 §5.1 平台侧 16 域逐一对应（`org` 不在 bms 布局，随 mdm 仓自建） | 一致 |
| 每域表所有权 / 表前缀 ↔ 表归属登记 | `bms_core/services/table_registry.py::TABLE_OWNERSHIP` 的 `domain` 字段值与 §5.1 逐表对应（`sys_business(+_i18n)` / `sys_permission` → `permission_meta`；`sys_icon(+_i18n)` → `permission_meta`；`sys_account_lock` → `user` 等） | 一致 |
| 清单被后续任务直接引用 | ① `03_01` 域布局；② `03_02` 清单名 `{domain}:{datasource}` 与版本记录表；③ `03_03` 域子包目录名、`public_api`、逐域模型模块；④ 后端开发规范「业务域级断言」 | 已被直接引用 |
| 代码载体 | `03_03` 已把九服务分包到 `domains/<域>/`，模型按域一文件一模块；§4/§6 的「无代码载体」缺口闭合 | 一致（时点说明见 §2.3） |

### 2.3 设计与现状的时点说明（回写） <a id="rewrite"></a>

- §4「现状盘点」与 §6「现状差距」是 **2026-10-24 的盘点时点**（当时服务内扁平、模型混域）；其后 `03_02` / `03_03` 已落地清单按域与代码分包，故在设计 §6 补一条时点说明，指向 `03_02` / `03_03`，避免后续读者把「现状」误读为当前事实（清单本身未变，属**目标**口径）。
- `org` 域维持在 mdm 仓（设计开放项 4），bms 布局不登记产品域，与 `03_01` 对齐记录一致。
