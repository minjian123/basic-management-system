## 1. 目标与边界 <a id="scope"></a>

**目标**：把「业务域」从概念变成可执行判据与可核对清单——给出划分判据（可判、可复核）、术语对照（与现有服务 / 模块 / 产品路由 domain 段 / 基座能力域区分）、**目标业务域清单**（现有全部服务与产品的业务域归属 + 数据所有权 + 表前缀），并给出**现状差距评估**（现有实现能否支撑、缺什么），作为后续阶段一的输入。

**范围内**：

1. 术语与三层模型（业务域 / 部署单元 / 数据单元）的正式定义与对照；
2. 域划分判据的可操作化（含反例清单与复核触发条件）；
3. 现状盘点：现有 9 个平台服务 + 产品服务（mdm）的实际业务域归属；
4. 目标业务域清单（骨架 + 首批域 + 待定项）；
5. 现状差距评估（可复用 / 需调整 / 必须补齐），四阶段对应关系；
6. 交付物与验收映射。

**范围外**：实际代码分包与表归属改造（归 `03_01` / `03_02`）、拓扑机制（归 `02_01`）、迁移与发布（归 `04_xx`）。

## 2. 术语与三层模型 <a id="terms"></a>

| 术语 | 定义 | 与现有概念的关系 |
| --- | --- | --- |
| **业务域**（domain，限界上下文） | 代码、表、事务、对外能力的共同归属单位 | **不等于服务**（一服务可含多业务域）；**不等于模块**（模块是运营面登记项，模块按服务/产品）；**不等于产品路由的 domain 段**（那只是 URL 段） |
| **部署单元** | 一个或多个业务域的运行时集合，对应一个服务进程与一套库 | 现状 `service_key` 就是这个概念（`platform` / `identity` / `mdm`…） |
| **数据单元** | 部署单元拥有的库集合（平台库 / 租户库 / 归档库） | 库名派生沿用现有"前缀 + 服务段 + 库名基"规则，服务段改为部署单元标识 |
| **基座能力域** | `bms_core` 下的技术横切分层（core / db / permission / tenant / servicecall…） | **与本专项的业务域无关**，不得混称 |

**判据一句话**：业务域回答「这是什么业务」（稳定），部署单元回答「跑在哪个进程与库」（可变），两者正交。

## 3. 域划分判据（可操作化） <a id="criteria"></a>

拆出一个业务域须满足下列**至少两条**，且每条都能用事实回答：

| # | 判据 | 可验证问法 |
| --- | --- | --- |
| 1 | 数据所有权独立 | 这批表是否只被本域写？是否有其他域直接读写它们？所属聚合的生命周期是否独立？ |
| 2 | 业务语义独立 | 是否有独立的业务规则与外部承诺？能否被单独授权（能力分配）或单独开通？ |
| 3 | 扩缩需求独立 | 读写量级 / 峰值是否与其他域显著不同（差一个数量级以上）？合并是否会形成瓶颈？ |
| 4 | 变更节奏独立 | 演进频率与发布窗口是否明显不同？是否常因他域改动而被迫一起发版？ |

**不新开域**（在既有业务域内加聚合）的情形：与既有业务域共享所有权与事务边界，且无独立扩缩需求。

**开产品**（而不是在平台内加业务域）须满足下列至少两条：独立仓库、独立发版节奏、独立团队、独立商业定价。

**反例清单**（不构成拆域理由）：表数量多、代码行数多、目录看着像另一个业务、某人觉得“应该分开”。

**复核触发**：出现下列任一情形时按判据复核该业务域：单业务域表数或代码量翻倍、出现两个及以上消费方要求独立扩缩、发布窗口冲突频率上升、跨业务域直接读表被护栏拦下的次数增多。

## 4. 现状盘点 <a id="inventory"></a>

**服务与业务域的实际归属（核查自代码与表归属登记）**：

| 现有服务 | 承载的业务域（按实现语义） | 备注 |
| --- | --- | --- |
| `platform` | 用户、角色、权限元数据（业务码 / 动作码 / 权限码 / 图标）、菜单与表单挂接、租户（管理面）、平台参数、产品登记与目录、数据源登记、表单标识 | **典型多业务域同服务**，是拆分候选池的主要来源 |
| `identity` | 认证与会话、令牌与凭证、SSO / 身份联邦、验证码与账号治理 | 语义相对集中，域粒度较清 |
| `tenant` | 租户开通与配额、租户模块开关、租户库与迁移编排 | 与 platform 的"租户管理面"相邻，需在清单里明确边界 |
| `file` / `notification` / `search` / `ai` / `report` / `txn` | 各一个业务域 | 语义单一，暂不需拆 |
| `mdm`（产品） | 组织（部门 / 岗位 / 分配）、参考数据 | **单服务多业务域**，是"产品内多域"的样本 |

**关键现状事实（决定差距）**：

| 事实 | 影响 |
| --- | --- |
| 表归属记录的归属字段是**服务标识** | 无法表达"这张表属于哪个业务域"，合并部署时无法判越界 |
| 库键解析按服务拒绝跨服务访问 | 多业务域同库时会被自身校验挡住 |
| 迁移链按服务组织（每条链一个服务） | 拆分业务域要切迁移历史 |
| 服务间调用只有 HTTP 与占位两种实现 | 同部署单元内业务域互调会绕网络自我调用 |
| 边界护栏按服务包断言 | 合并部署后同进程内一切可达，护栏失效 |
| 平台服务内为扁平实现文件 | 没有业务域子包，护栏无着力点 |
| 平台种子代写产品业务码与权限码 | 与"基座不写产品"口径相抵（07B 已列，另有专项处理） |

## 5. 目标业务域清单（定稿） <a id="target"></a>

**盘点事实（2026-10-24，扫描基座与各服务 `__tablename__`）**：平台 44 张表**全部定义在基座** `bms_core/models/` 下，已按目录分为 `identity/`（4 张）、`platform/`（29 张）、`tenant/`（5 张）与根目录（4 张横切）；服务侧仅 `ai` / `notification` / `txn` 有自有表（1 / 1 / 3 张），`file` / `search` / `report` 无自有表。

**结论**：业务域雏形在**模型层已存在（按目录分）**，但 `platform/` 一个目录里混了 6 个业务域，且服务侧无业务域载体——这两点是阶段一的改造对象。

### 5.1 业务域清单 <a id="list"></a>

| 业务域 | 数据所有权（表） | 现有承载服务 | 表前缀 | 判据结论 |
| --- | --- | --- | --- | --- |
| 认证与会话 | `sys_session`、`sys_account_lock`（验证码无表，缓存实现） | identity | `sys_` | 拆（验证码并入；`sys_account_lock` 由 platform 目录划入） |
| 身份联邦 | `sys_client`、`sys_identity_provider`、`sys_user_identity` | identity | `sys_` | 拆 |
| 用户 | `sys_user`、`sys_user_extension`、`sys_user_preference` | platform | `sys_` | 保留 |
| 角色与授权 | `sys_role`、`sys_role_permission`、`sys_role_field`、`sys_data_scope`、`sys_user_role` | platform | `sys_` | 保留（用户-角色绑定归本域，用户保存时经编排写本域表） |
| 权限元数据 | `sys_business(+_i18n)`、`sys_action(+_i18n)`、`sys_permission`、`sys_icon(+_i18n)` | platform | `sys_` | 保留（**拆域候选首位**，达阈值先拆） |
| 菜单与表单 | `sys_menu(+_i18n)`、`sys_menu_form`、`sys_form`、`sys_field(+_i18n)`、`sys_button` | platform | `sys_` | 保留（拆域候选） |
| 租户与开通 | `sys_tenant`、`sys_tenant_database`、`sys_tenant_module`、`sys_tenant_quota`、`sys_user_tenant` | tenant | `sys_` | 合（平台侧为只读消费方，无独立所有权） |
| 平台参数 | `sys_config` | platform | `sys_` | 拆（与注册目录分离） |
| 平台注册与目录 | `sys_product`、`sys_module(+_i18n)`、`sys_table_ownership` | platform | `sys_` | 拆 |
| 任务调度 | `sys_task`、`sys_task_log` | platform | `sys_` | 保留 |
| 组织 | `mdm_dept`、`mdm_post`、`mdm_user_post`、`mdm_user_dept`、`mdm_role_post`、`mdm_role_dept` | mdm | `mdm_` | 保留（角色-组织绑定并入本域） |
| 通知 | `sys_notification` | notification | `sys_` | 保留 |
| AI 辅助 | `ai_chat_log` | ai | `ai_` | 保留 |
| 事务协调 | `txn_global`、`txn_global_branch`、`txn_global_recovery` | txn | `txn_` | 保留 |
| 文件 | 无自有表（对象存储 + 元数据引用） | file | — | 无表业务域（仅登记边界与能力） |
| 检索 | 无自有表（索引） | search | — | 无表业务域 |
| 报表 | 无自有表（读侧聚合） | report | — | 无表业务域 |

**待接入产品**：biz（采购 / 仓储 / 销售）、cw 的业务域在其接入时按同一判据补录，表前缀各自 `biz_` / `cw_`。

### 5.2 不登记为业务域 <a id="excluded"></a>

| 对象 | 归属 | 理由 |
| --- | --- | --- |
| `sys_outbox`、`sys_event_consumed`、`sys_event_dead_letter` | 基座横切设施（架构 37 可靠事件） | 不承载业务语义、无独立消费方承诺；按基座能力域管理 |
| `demo` | 测试遗留（删除候选） | 非业务数据，实施时清理 |

### 5.3 三处待复核项的结论 <a id="review"></a>

| 项 | 结论 | 判据依据 |
| --- | --- | --- |
| 认证与会话 vs 身份联邦 | **拆两个业务域** | 数据所有权分两组（会话短生命周期高频写 / 联邦配置低频写）；扩缩需求独立——满足 2 条 |
| 验证码 | **并入认证与会话** | 无自有表、无独立语义与生命周期——0 条 |
| 平台“租户管理面” vs `tenant` 服务 | **合为一个业务域** | 5 张表全部归 tenant，平台侧仅读消费，无独立数据所有权——不满足第 1 条 |
| 平台参数 vs 目录登记 | **拆两个业务域** | 业务语义独立（运营配置 vs 部署期元数据）+ 变更节奏独立——满足 2 条 |
| `sys_account_lock` 目录归属 | **划入认证与会话** | 登录安全机制随认证链路写入；留在用户域将造成跨域写 |

## 7. 交付物与验收映射 <a id="deliver"></a>

| 交付物 | 验收要点（需求 01-1 完成标准） |
| --- | --- |
| 术语对照表 | 业务域 / 部署单元 / 数据单元 / 基座能力域 四者无混淆；与现有服务、模块、产品路由 domain 段的关系写清 |
