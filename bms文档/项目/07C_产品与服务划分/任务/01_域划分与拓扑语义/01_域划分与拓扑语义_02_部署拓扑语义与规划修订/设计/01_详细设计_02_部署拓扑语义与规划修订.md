## 1. 目标与边界 <a id="scope"></a>

**目标**：把架构节点 39 的拓扑语义收敛成**可实现的形式**——标识规则、库派生规则、拓扑记录形态、参照拓扑划分——作为 `02_01`（拓扑记录与解析）与 `03_02`（库与迁移按业务域）的直接输入；同时确认规划侧的修订落点。

**范围内**：

1. 标识规则（业务域标识、部署单元标识）；
2. 库派生规则（平台库 / 租户库 / 归档库，服务段换为部署单元）；
3. 拓扑记录的语义形态与版本、生效方式；
4. 三类**参照拓扑**（单体 / 分组 / 独立）与 17 个业务域在其下的划分；
5. 架构节点 39 与《微服务演进规划》的补充/确认清单（哪些进节点、哪些只进设计）。

**范围外**：拓扑记录的存储与解析实现（`02_01`）、能力寻址第二段的实现（`02_02`）、库与迁移改造（`03_02`）、发布与迁移操作（`04_01` / `04_02`）。

## 3. 语义细化 <a id="semantics"></a>

### 3.1 标识规则 <a id="ids"></a>

| 标识 | 形态 | 命名约束 | 稳定性 |
| --- | --- | --- | --- |
| 业务域标识 `domain_key` | 小写字母 / 数字 / 连字符，如 `auth`、`identity-federation`、`org`、`refdata` | 遵循《[命名规范](../../../../../../规范/命名规范.md)》；与模块键、表前缀解耦（可同名但非同一概念） | **稳定**（一经发布不改） |
| 部署单元标识 `unit_key` | 同上，如 `core`、`grp-purchase`、`dom-org` | 同一租户内唯一；不得与业务域标识混用（命名空间不同） | 可变（拓扑重建时可换） |

**为什么分开命名空间**：`domain_key` 是契约（能力声明引用它）；`unit_key` 是运营标识（部署时生成）。混用会让“改部署”看起来像“改契约”。

**约束**：

1. 一个 `domain_key` 在**同一租户**内只映射到一个 `unit_key`（禁止长期双活）；
2. 一个 `unit_key` 可承载多个 `domain_key`；
3. `unit_key` 与 `domain_key` 不同名时可读性更好（`core` vs `user`），同名不禁止但不推荐。

### 3.2 库派生规则 <a id="db"></a>

沿用既有函数签名，**把“服务段”换为“部署单元段”**：

| 库类别 | 既有形态 | 拓扑后 |
| --- | --- | --- |
| 平台库 | `platform` / `platform_{service}` | `platform` / `platform_{unit}` |
| 租户库 | `tenant_{code}` / `tenant_{service}_{code}` | `tenant_{code}` / `tenant_{unit}_{code}` |
| 归档库 | `{prefix}_archive` | 不变（归档库不按单元拆） |

**库名**：`{prefix}_{unit}`（平台库）/ `{prefix}_{unit}_{db_basis}`（租户库）；`prefix == unit` 时去重（避免 `core_core`），与既有规则同构。

**关键不变式**：

| 不变式 | 说明 |
| --- | --- |
| 表名不随拓扑变化 | 表前缀体现业务域（`sys_` / `mdm_` / `biz_`），与部署单元无关 |
| 库结构 = 所含业务域表的并集 | 任一拓扑下成立（由 `03_02` 的变更序列按域聚合保证） |
| 库键归属校验按单元 | 既有 `resolve_db_key(service=...)` 的“服务段”改为“单元段”，跨单元访问仍拒绝 |

### 3.3 拓扑记录的语义形态 <a id="record"></a>

一条记录 = **租户 × 业务域 → 部署单元（及其库）**：

| 维度 | 语义 |
| --- | --- |
| 租户 | 拓扑按租户；平台级（不区分租户）的拓扑可视为“默认拓扑” |
| 业务域 | 引用 `domain_key`（必须已登记） |
| 部署单元 | 引用 `unit_key`（同一租户内唯一） |
| 库 | 由单元派生（`{prefix}_{unit}` / `{prefix}_{unit}_{db_basis}`），记录中只存单元，不重复存库名 |
| 版本 | 每次变更递增**拓扑版本**；发布时生效，运行期解析按版本取快照 |
| 状态 | `enabled` / `disabled`；停用的域视为“本租户未启用该业务域” |

**生效语义**：拓扑变更 = 一次发布动作；运行期解析读**当前版本快照**，不逐请求查库（`02_01` 实现缓存与失效）。

### 3.4 三类参照拓扑 <a id="reference"></a>

以 17 个业务域为输入，给出三档参照划分（模板基线，非强制）：

| 参照 | 单元划分 | 适用 |
| --- | --- | --- |
| **单体型** | `core`（全部 17 个域） | 小微 / 试用 / 开发测试 |
| **分组型** | `core`（平台 13 域）+ `biz-purchase`（采购）+ `biz-ops`（仓储 + 销售） | 业务重心明显的租户 |
| **独立型** | 每域一个单元（`dom-*`） | 大型企业 / 强隔离 |

**分组型的判据依据**：采购与仓储/销售的读写峰值与变更节奏差异最大（判据 3 + 4），故先拆采购；仓储与销售共享库位与订单主体，暂合。

**模板不是契约**：模板只减少配置量，租户可在模板基础上调整；判断依据仍是 `01_01` 的四条判据。

### 3.5 与能力声明的关系 <a id="capability"></a>

| 层 | 表达 |
| --- | --- |
| 能力声明（产品自持） | 能力绑 `domain_key`（不绑 `unit_key`） |
| 拓扑记录 | `domain_key` → `unit_key` |
| 运行期解析 | 能力 → 域（`02_02` 第一段）→ 单元与库（本任务定义的语义，`02_01` 实现） |

**因此**：产品改名、服务拆分、租户重新分组，**都不改能力声明**——这正是三段设计的目的。

## 7. 风险与边界 <a id="risk"></a>

| 风险 | 处置 |
| --- | --- |
| 标识规则被下游各自解释 | 规则只写在架构节点一处，下游引用；`02_01` 实现时按此校验 |
