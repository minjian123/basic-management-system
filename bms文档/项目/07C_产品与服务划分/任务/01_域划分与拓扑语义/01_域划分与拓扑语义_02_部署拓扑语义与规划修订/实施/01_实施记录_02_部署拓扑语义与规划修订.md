### 2.2 与代码现实一致性核对 <a id="consistency"></a>

设计 §3.2 的派生式是否与既有实现冲突，逐项对代码核对（库键与库名派生全部在 `backend/libs/bms_core/src/bms_core/db/keys.py`）：

| 核对项 | 代码事实 | 结论 |
| --- | --- | --- |
| 平台库派生 | `build_platform_db_key()`（L135）→ `platform` / `platform_{service}`；`platform_database_name()`（L219）→ `{prefix}_{service}` | 与 §3.2 同构，「服务段」即拓扑后的「单元段」 |
| 租户库派生 | `build_tenant_db_key()`（L147）→ `tenant_{db_basis}` / `tenant_{service}_{db_basis}`；`tenant_database_name()`（L235）→ `{prefix}_{service}_{db_basis}` | 一致；`db_basis` 为创建时冻结的租户编码，语义不变 |
| 前缀去重 | `_service_segment()`（L206）：`prefix == service` 时去重为单段（避免 `core_core`） | 与 §3.2「`prefix == unit` 时去重」一致 |
| 相对键补单元段 | `database_name(key, *, unit, service, prefix)`（L266）：`effective = key.service or unit or service`，缺省则抛 `ConfigError` 要求配置单元标识 | 不变式 3 的落点已在位 |
| 归属校验按单元 | `resolve_db_key(db_key, *, unit, service, allow_cross_service)`（L294）：单元未登记抛 `ConfigError`；非当前单元且未豁免抛 `DataOwnershipError`（10008） | 与 §3.2「跨单元访问仍拒绝」一致 |
| 归档库例外 | `archive_database_name()`（L254）→ `{prefix}_archive`，不接单元段 | 与 §3.2 例外项一致 |
| 单元标识来源 | `AppSettings.unit`（`core/config.py` L91）：「空则回落 `service`」，即 `[app].unit` 未设时既有库名不变 | 语义迁移**零改动**可用 |

**结论**：设计 §3.2 不是新规则，而是把 `03_02` 已落地的「服务段 → 单元段」语义**显式化**——同一组函数签名不变，`service` 作为过渡期别名保留（`unit` 优先）。因此本任务确无代码变更，`02_01` / `04_01` 可直接按此语义实现与对账。

### 2.4 本任务对详细设计的修订（回写） <a id="rewrite"></a>

| # | 修订 | 缘由 |
| --- | --- | --- |
| 1 | §3.4 分组型由「`core`（已登记的全部 17 域）+ `biz-purchase` + `biz-ops`」改为「`core`（平台 16 域 + 组织）+ `biz-purchase` + `biz-ops`」，并新增**两类时点区分表**（当前已登记 17 域 / `biz`·`cw` 接入后） | 原表述把「已登记的 17 域」与两个 `biz-*` 单元并列，读者易误读为同一域被映射到两个单元（违反 §3.1 约束 ①） |
| 2 | §3.4 新增「模板只引用已登记业务域」段 | `02_01` 的校验口径是「引用未登记业务域即拒」；若把 `biz-*` 写成模板中的空壳单元，实现的校验会两难（放行未登记域，或模板自身不可用）。定为「接入时新增单元」后模板恒可校验 |

修订只涉及参照拓扑的**表述与时点**，不改变 §3.1~§3.3 / §3.5 的任何规则，下游 `02_01` / `04_01` 的输入语义不变。
