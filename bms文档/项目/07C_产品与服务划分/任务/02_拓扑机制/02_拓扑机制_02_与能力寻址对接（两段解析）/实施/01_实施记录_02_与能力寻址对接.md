## 2. 实施过程 <a id="process"></a>

### 2.1 交付清单 <a id="deliver"></a>

| 交付物 | 落点 | 要点 |
| --- | --- | --- |
| 配置分区 | `bms_core/core/config.py` | `TopologySettings`（`[topology]`）：`distribute`（分发开关，缺省 true）、`units`（承载单元集合，`None` = 默认拓扑全单元） |
| 三态判定 | `bms_core/collaboration/topology.py` | `register_instance_context()` / `instance_units()` / `reset_instance_context()` / `_mode_for()`：承载服务 == 本服务 → `local`；单元 ∈ 集合 → `colocated`；否则 `remote` |
| 单元校验 | 同上 | 集合内单元须在默认拓扑登记，违反即 `CatalogError`（`data.reason=unit_not_registered`，拒启级） |
| 快照解析 | 同上 | `snapshots_from_payload()`：内部出口响应 → 快照清单；结构非法即 `CatalogError`，脏数字取缺省 |
| 进程释放 | 同上 | `TopologyResolverResource` 从平台服务下沉基座（解析器 + 快照 + 实例身份一并复位），平台与分发引导共用 |
| 分发引导 | `bms_core/collaboration/bootstrap.py` | `bootstrap_remote_topologies()`：开关 → 平台跳过 → 拉取 → 登记 → 装载 → 校验 → 释放器；失败降级打 `topology_degraded` |
| 装配点 | `bms_core/application.py` | `service_lifespan` 在 `bootstrap_declarations` 之后调用（域登记视图与承载服务映射已就绪） |
| 地址生效 | `bms_core/servicecall/base.py` | `ServiceRequest.base_url` + `validate_service_request` 前缀校验 + `build_service_url` 显式基址优先（尾斜杠归一） |
| 地址取值 | `bms_core/collaboration/request.py` | `build_capability_request` 用 `endpoint.target.base_url` 填 `base_url` |
| 平台内部出口 | `services/platform/.../api/internal_tenant_topologies.py` | `GET /api/v1/platform/internal/tenant-topologies`：双模鉴权，服务身份读全量，只回解析三列 |
| 响应模型 | `services/platform/.../schemas/tenant_topology.py` | `TopologySnapshotRow` / `TopologySnapshotItem` / `TopologySnapshotResponse` |
| 平台装配 | `services/platform/.../services/tenant_topology_bootstrap.py` | 装载快照后 `register_instance_context`（平台进程本库权威），释放器改从基座导入 |
| 测试配置 | `bms/backend/config.test.toml`、`mdm/backend/config.test.toml` | `[topology] distribute = false`（单测不发网络请求） |
| 契约 | `deploy/contracts/platform.json` | 新端点随 `ops.contract_snapshot export` 刷新（+72 行，仅平台；其余服务零内容差异） |

### 2.2 四项拍板的落地点 <a id="decisions"></a>

| # | 结论 | 落地 |
| --- | --- | --- |
| 1 | 内部出口 + 装配层统一拉取 | 平台端点 + `application.py` 装配期调用；平台进程按 `PLATFORM_SERVICE_KEY` 内部跳过，bms 九服务与 mdm 自动生效，无需逐服务改 `main.py` |
| 2 | 按承载集合判三态 | `_mode_for()`：承载服务先行（`local`）、单元集合次之（`colocated`）、否则 `remote`；集合未配置取默认拓扑全单元 → 阶段 A 得「自域 local + 他域 colocated」 |
| 3 | 本轮不做直调 | `mode=local` 仅给语义（本进程承载、不该走网络）；同服务跨域仍经域 `public.py`，无走寻址的本地消费点；直调传输登记开放项 |
| 4 | `target.base_url` 覆盖 | `ServiceRequest.base_url` → `build_service_url` 优先；阶段 A 单元 = 承载服务键，地址与改造前**同值**（回归按字符串比对） |

### 2.3 与现有机制的一致性核对 <a id="consistency"></a>

| 核对项 | 事实 | 结论 |
| --- | --- | --- |
| 协议签名 | 07B `TopologyResolver.resolve(domain)` 未改；`resolve_capability(name)` 未改 | 消费方（`user_assignments` / `role_assignments` / `permission_subject`）零改动 |
| 降级口径 | 与 07B 授权视图一致：装配缺客户端拒启、来源不可达降级 + 标记 | 产品进程不因平台重启被拖下水 |
| 服务身份与地址 | `service` 仍为承载服务键（出站 JWT / 限流 / 熔断 / 目录校验都按它），仅地址改取 `base_url` | 拆分拓扑下不必改服务目录登记 |
| 表与边界 | 未新增表；新端点属 `platform_registry` 域、只读 `TenantTopologyService.snapshot()` | `check_service_boundaries` 通过（域未归属 0 / 跨域 import 0 / 表引用 0） |
| 契约 | 新端点属「只加不删」，基线无需变更 | `tests/ops/test_contract_snapshot.py` 与契约门禁用例通过 |

## 4. 问题与处置 <a id="issues"></a>

| # | 问题 | 处置 |
| --- | --- | --- |
| 1 | 旧设计「协议升版 v2、`tenant_id` 必填」与 `02_01` 已交付的「签名不变 + 上下文」冲突 | 按 `02_01` 口径改写（设计 §9-1），不升版；显式租户仍走 `resolve_for` |
| 2 | 旧设计 §3 与 §4.2 对阶段 A 的 `mode` 自相矛盾（`colocated` vs `local`） | 统一为按承载服务判定（设计 §9-2） |
| 3 | `target.base_url` 未进调用链（装饰字段），拆分拓扑取址测不出来 | `ServiceRequest` 增显式基址（设计 §9-4），阶段 A 等价性由用例 10 / 17 守住 |
| 4 | 承载集合校验若放在 `instance_units()` 之后取值，会拿声明值自比（永远通过） | 抽 `_default_units()` 单独取默认拓扑全单元，校验与生效分离 |
| 5 | `02_01` 用例 `test_tenant_without_snapshot_falls_back_to_default` 断言 `mode=remote` | 三态判定生效后该场景为 `colocated`，按新语义更新断言并在 docstring 说明来源（不是放宽断言） |
| 6 | 平台内部出口把 `tenant_id` 序列化成字符串（`BaseSchema` 的 id 字符串化口径） | 基座解析用 `_int_field()` 容错取整，用例按字符串比对；MQ / 第三方解析同样安全 |
| 7 | 每个进程装配期多一次跨服务调用 | 开关 `[topology].distribute` 单测关闭；一次拉取、无轮询；失败降级不拒启 |
| 8 | 契约导出顺带把 8 个无内容差异的服务快照改成 CRLF | `git checkout --` 还原，只提交 `platform.json` |
