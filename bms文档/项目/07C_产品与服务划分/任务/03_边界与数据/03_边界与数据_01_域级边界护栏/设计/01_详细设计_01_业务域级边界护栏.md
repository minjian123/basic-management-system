# 业务域级边界护栏详细设计

> 产品与服务划分 · 03 边界与数据 · 01 业务域级边界护栏 · 详细设计（开发核心文档）

[文档首页](../../../../../../文档首页.md) › [01 业务域级边界护栏](../03_边界与数据_01_域级边界护栏.md) › 设计

## 1. 目标与边界 <a id="scope"></a>

**目标**：把边界断言的维度从「服务包」下沉到「业务域」——使多域合并部署到同一进程时，跨域访问仍被静态与运行期双轨拦截（“合并的是部署，不是边界”）。

**范围内**：

1. 业务域 ↔ 代码路径的映射（未分包阶段可用）；
2. 新增域级断言（跨域 import、跨域表引用、跨域事务边界）；
3. 表归属维度从「服务」迁到「业务域」（与既有登记兼容）；
4. 基线与例外机制扩展（按域维度）；
5. 按业务域分包的分批迁移口径（护栏先行，迁移随后）。

**范围外**：实际分包改造（按域分批的代码移动）、库与迁移（`03_02`）、拓扑与解析（`02_xx`）。

## 2. 现状 <a id="current"></a>

**既有护栏已相当完整**（`check-service-boundaries`，十项）：

| # | 既有断言 | 与本任务的关系 |
| --- | --- | --- |
| 1 / 2 | 共享库不依赖服务、服务不互相依赖 | 保留（服务维） |
| 3 | 分层依赖单向（`api → services → repositories → models`） | 保留（包维） |
| 4 | 跨包不引用私有实现（下划线前缀） | 保留，扩展为域级 |
| 5 | 表名 / 表前缀跨服务唯一 + 表归属已登记 | **归属维度需从服务改为业务域** |
| 6 | 跨服务库访问（声明越权 + 引用越界） | **需增加“跨域”判定** |
| 7 | 读侧出口例外白名单（`deploy/boundaries/data_ownership_exceptions.json`） | **复用并扩展域维度** |
| 8 ~ 10 | ops 运行镜像与导入闭包、运行期不依赖运维通道 | 保留（无关） |

**缺口**：

| 缺口 | 后果 |
| --- | --- |
| 归属维度是服务键 | `platform` 内 6 个业务域互访不受约束；合并部署后“跨域调用”与“同域调用”无法区分 |
| 无域 ↔ 代码路径映射 | 无法断言“这段代码属于哪个域”，护栏无从下手 |
| 代码未按域分包 | `platform` 内仍是扁平的 `services/`、`api/`、`repositories/` 目录，域边界只存在于文档 |

## 3. 设计 <a id="design"></a>

### 3.1 业务域 ↔ 代码路径映射 <a id="mapping"></a>

新增**域布局声明**（`deploy/boundaries/domain_layout.json` 或等价配置），一条 = 一个业务域 + 其代码归属：

| 字段 | 语义 |
| --- | --- |
| `domain_key` | 业务域标识（与 `01_01` 清单一致） |
| `service_key` | 当前承载服务（分包前为服务包；分包后为该服务内的域子包） |
| `paths` | 该域的代码路径集合（目录或文件 glob）；**必须覆盖该域全部实现** |
| `status` | `placement`（已分包到域子包）/ `legacy`（仍在服务扁平目录，逐文件声明）/ `planned`（未落地） |
| `public_api` | 域内公共出口模块名（≤1 个；D2 放行的唯一跨域引用面；分包前为空） |
| `shared_paths`（顶层） | 域外路径：装配面（`main` / `asgi` / `router` / 包入口）、基座横切面、基础设施与不归域文件 |

**规则**：

1. 同一路径不得归属两个域（重复即失败）；
2. `legacy` 域的文件集合须显式列出（不允许整目录兜底，否则“域”退化为“服务”）；
3. 新增业务域必须登记布局，否则护栏报“未登记域的实现”；
4. 分包完成一个域，把其 `legacy` 条目改为 `placement`，基线相应递减。

**为什么用文件级声明兜底**：`platform` 内暂未分包，若只按目录映射，user 与 role 的实现同在 `services/user.py` / `services/role.py` 尚可，但 `api/`、`repositories/` 是混合目录——只能按文件归属。文件集合显式化虽然啰嗦，但它是“域边界真实存在”的唯一证据。

### 3.2 新增域级断言 <a id="rules"></a>

| # | 断言 | 判定 |
| --- | --- | --- |
| D1 | **跨域 import 禁止** | 域 A 的实现文件 import 域 B 的实现模块（`services.*` / `repositories.*` / `models.*` 具体域内模块）即失败；**同服务内不同域同样适用** |
| D2 | 跨域只经公共面 | 跨域引用仅允许：能力契约调用、事件、域内声明的公共 API 模块（≤1 个出口文件） |
| D3 | 跨域表引用禁止 | 原始 SQL / `ForeignKey` / 字符串表名 token 指向他域归属的表即失败（复用既有第 6 项判定，归属换成域） |
| D4 | 跨域事务禁止 | 域内方法不得在自身事务内直接写他域表（AST 断言：写操作目标的表归属不得跨域） |
| D5 | 观测标注 | 日志 / 指标打点须带 `domain_key`（缺失计入软提示，逐步转硬） |

**与既有断言的关系**：D1 ~ D4 是既有 1 ~ 6 的**细化维度**，不替代——服务维断言继续生效（服务间仍不得互相 import）。

### 3.3 归属维度迁移（服务 → 域） <a id="owner"></a>

| 对象 | 现状 | 目标 | 兼容策略 |
| --- | --- | --- | --- |
| 表归属登记 `owner` | 服务键 | 业务域键 | 登记记录增加 `domain` 字段；`owner` 保留服务键一个过渡期，两字段并存校验一致 |
| `assess_table()` 判定 | 按服务 | 按域（同域放行、跨域拒绝） | 同服务内不同域：过渡期先“告警 + 计数”，分包完成后转拒绝 |
| `resolve_db_key()` | 按服务拒绝跨服务库 | 按**部署单元**归属（`02_01` 语义） | 与 `03_02` 联动，本任务只改判定入参来源 |
| 表文件「归属库 / 归属服务」 | 写服务 | 写业务域 + 部署单元 | 表文件补「业务域」字段（`03_02` 批量回写，本任务定格式） |

**为什么两字段并存**：一次改到底会让既有登记、表文件、护栏三处同时红；并存期由护栏断言“两字段一致”，迁移完成后删 `owner`。

### 3.4 基线与例外 <a id="baseline"></a>

| 机制 | 用法 |
| --- | --- |
| 基线文件（新增，域级） | `deploy/boundaries/domain_boundary_baseline.json`：记录存量跨域引用（源域 + 目标域 + 文件 + **行指纹**）；`kind` 区分 `import` / `table_ref` / `table_declare`；只报新增；分包迁移时逐项删除 |
| 既有例外白名单 | 复用 `data_ownership_exceptions.json` 结构，增加 `domain` 维度与理由；命中计数，未登记仍失败 |
| 豁免标记 | 行内标记 + **理由必填**（与 `04_01` 同一套风格） |
| 基线只减不增 | 新增即失败；`--update-baseline` 需人工执行并审阅 |

### 3.5 分包迁移口径 <a id="migration"></a>

| 步骤 | 内容 | 护栏状态 |
| --- | --- | --- |
| 1 | 建域布局声明（`legacy` + 文件集合） | D1 ~ D4 以基线方式生效（存量放行） |
| 2 | 每域一次迁移：文件移入 `domains/<domain>/`，补公共 API 出口 | 该域条目转 `placement`，基线删除对应项 |
| 3 | 迁移完成的域：跨域 import 即失败 | 硬门禁 |
| 4 | 全部完成：删除 `legacy` 条目与基线文件 | 全域硬门禁 |

**顺序建议**：先迁“被依赖少”的域（如 AI / 报表），最后迁“互相引用密集”的（用户 / 角色 / 权限元数据），每步可独立回滚。

### 3.6 运行期校验 <a id="runtime"></a>

| 点 | 变更 |
| --- | --- |
| 表归属校验（`DataOwnershipError`） | 判定依据由“服务”改为“域 ∈ 当前部署单元”（与 `02_01` 一致） |
| 跨域调用 | 只经能力契约（07B），运行期由入站授权校验（`02_04`）兜底 |
| 观测 | 中间件按 `domain_key` 打标签（D5） |

## 6. 风险与边界 <a id="risk"></a>

| 风险 | 处置 |
| --- | --- |
| `legacy` 文件集合演进后过期（新增文件未登记） | 护栏报“未登记的域实现”，强制补登记 |
| 域边界靠文件清单维持，易退化 | 分包迁移逐步把 `legacy` 清零；清单条目数作为治理指标 |
| 双字段并存期口径漂移 | 护栏强制一致性校验；迁移完成后删 `owner` |
| 大规模基线导致“红灯变绿灯” | 基线只减不增 + 计数可见 + 每域迁移后强制递减 |
| 迁移期频繁冲突 | 按域逐个迁移，单域一次改动，减少并行冲突 |

## 7. 开放项 <a id="open"></a>

| # | 事项 | 归口 |
| --- | --- | --- |
| 1 | 域内公共 API 出口是否允许每域多个（如 commands / queries 分离） | 首个域迁移时按实际情况定 |
| 2 | `domain_layout.json` 是否由域清单自动生成 | 域数量增加后评估（当前手工维护 + 护栏校验） |
| 3 | D5 观测标注何时转硬门禁 | 中间件改造完成后 |
| 4 | 产品仓（mdm / biz）是否也建域布局 | 其内部多域拆分需求出现时 |

## 8. 对齐记录（2026-10-24 实施回写） <a id="alignment"></a>

| # | 事项 | 结论与理由 |
| --- | --- | --- |
| 1 | **单文件混多域**（设计假定「一文件一域」不成立） | 实测 `bms_core/models/platform/{menu,system,user}.py` 等同一声明多个域的表，platform 6 域在文件级切不开。处置：布局维持「一条目 = 一域 + 文件清单」，混域文件按**主域**登记；其对他域的表声明 / 引用进基线（`kind = table_declare` / `table_ref`），只减不增。**规则 1（同一路径不得归属两个域）不变** |
| 2 | D1 判定范围 | 只判**同服务内跨域** import（跨服务 import 已由规则 1 / 2 拦截，不重复计） |
| 3 | D2 放行面 | 命中**目标域**的 `public_api` 模块即放行（域内出口属目标域），非源域 |
| 4 | 布局缺省行为 | `domain_layout.json` 缺失或为空（产品仓 / 临时工程）时**域级断言停用**，服务维 1~10 照常——避免「无布局即全红」 |
| 5 | 未归属文件 | 域外路径显式登记（`shared_paths`）；未登记文件只计入软指标 `domain_files_unregistered`（不阻断），但**声明了已登记表的文件必须落在其域 paths**（否则 `[域实现未登记]` 硬拦） |
| 6 | `sys_account_lock` 归域 | 改归 `user` 域（与 `sys_user` 同库同域）；原「划入 auth」作废，理由与处置见 `01_01` §5.3 修订行 |
| 7 | 表归属双字段 | `TableRecord` 增 `domain`（空串 = 不归域，仅基础设施表与测试遗留表 `demo`）；`sys_table_ownership` 增列落库；一致性判定 = 「域在布局中登记」+「域承载服务 == `owner`」，由护栏与 `ops.check_tables`（离线）共用同一校验函数 |
| 8 | 运行期接入点 | 本任务提供 `assess_table(domain=…)` / 守卫 `domain=` 入参与 `domain` / `owner_domain` 观测标签；「当前域由部署单元决定」的装配点归 `03_02` / `02_01` / `04_03` |
