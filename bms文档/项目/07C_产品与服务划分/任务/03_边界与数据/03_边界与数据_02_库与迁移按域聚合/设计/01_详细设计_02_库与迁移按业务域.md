# 库与迁移按业务域详细设计

> 产品与服务划分 · 03 边界与数据 · 02 库与迁移按业务域 · 详细设计（开发核心文档）

[文档首页](../../../../../../文档首页.md) › [02 库与迁移按业务域](../03_边界与数据_02_库与迁移按域聚合.md) › 设计

## 1. 目标与边界 <a id="scope"></a>

**目标**：让「库」跟着部署单元走、「表结构变更清单」跟着业务域走——同一套域模型在单体与独立两种拓扑下都能建表与演进，且**拆 / 合不切迁移历史**。

**范围内**：

1. 表结构变更清单标识与目录改为业务域维度；
2. **每清单独立一张记录表**（多域同库的核心前提）；
3. 目标表集与模型导入按域；
4. 部署单元执行多清单的顺序与失败语义；
5. 库键的服务段换为部署单元段；
6. 存量库切换与回滚。

**范围外**：拓扑记录（`02_01`）、域布局声明与护栏（`03_01`）、发布对账（`04_01`）、迁移操作流程（`04_02`）。

## 2. 现状 <a id="current"></a>

| 项 | 事实 |
| --- | --- |
| 清单目录 | `alembic/versions/{service}/`（9 个：ai / file / identity / notification / platform / report / search / tenant / txn） |
| 清单标识 | `{service}:{datasource}`（`build_chain_name` / `parse_chain_name`）；一个服务一条表结构变更清单 |
| 表结构变更记录表 | **全库一张 `alembic_version`**（读取用 `SELECT version_num FROM alembic_version`；`env.py` 只设了 schema，未设表名） |
| 建表方式 | 结构以**模型为唯一事实源**：启动期按服务表集自动建表、运维 / CI 经 `ops.init_schema` 幂等建表；历史迁移脚本已清空 |
| 表归属 | `owner` = 服务键；`chain_tables(service, datasource)` 按其派生目标表集 |
| 库键 | `{prefix}_{service}` / `{prefix}_{service}_{db_basis}`，服务段 = 服务标识 |

**两个直接冲突**：

1. **多域同库 + 单表结构变更记录表**：合并部署后多个域清单同库共写一张 `alembic_version`，后跑的把先跑的记录覆盖，等于互相破坏版本状态；
2. **链按服务**：`platform` 一条表结构变更清单含 6 个域的表，拆域时要切历史（multi-head），风险高。

## 3. 设计 <a id="design"></a>

### 3.0 术语与定义（固定） <a id="terms"></a>

> **表结构变更清单**：一个业务域的**全部数据库结构变更脚本**，按时间顺序线性排列，**独立记录执行进度**；域内线性、域间互不引用。
> **表结构变更记录表**：某条表结构变更清单的执行进度记录（每清单一张），回答「该域已执行到哪一步」。

四条边界——任何一条不成立就不是表结构变更清单：

| # | 边界 |
| --- | --- |
| 1 | 只属于**一个业务域**（跨域即两条清单） |
| 2 | 清单内脚本**线性相接**（有前驱后继），不留分支 |
| 3 | **独立记录进度**（自己的表结构变更记录表，不被其他清单覆盖） |
| 4 | **不随部署拓扑变化**（拆 / 合部署单元时清单不动，只是“跑哪些清单”变了） |

三条推论（下文直接引用）：

- 同一库有 N 个业务域 → N 条清单、N 张表结构变更记录表，互不干扰；
- 判断「某域到哪一步」只看它自己的表结构变更记录表；
- 库结构 = 该库所含业务域各清单执行结果之和。

**与旧称的对应**：原「迁移链 / 链」即表结构变更清单，原「版本表」即表结构变更记录表；代码标识同步改名（`MigrationChain` → `MigrationSeries`，`build_chain_name` → `build_series_name` 等，见 §4）。

### 3.1 清单标识与目录改为域维度 <a id="chain"></a>

| 项 | 改造前 | 改造后 |
| --- | --- | --- |
| 清单标识 | `{service}:{datasource}` | `{domain_key}:{datasource}`（如 `user:tenant`、`org:tenant`） |
| 目录 | `alembic/versions/{service}/` | `alembic/versions/{domain_key}/` |
| 解析 | `service_chains(service)` | `domain_series(domain_key)`；`series_names()` 返回全部清单名 |
| 兼容 | — | 解析器同时接受旧 `{service}:…` 形态一个过渡期，按**服务 → 主域映射表**解析（表随清单维护，如 `platform` → `platform-registry`、`identity` → `auth`）；**无映射即拒绝**并提示先补映射，不猜 |

**迁移脚本分配**：现有脚本按操作对象表的归属域**机械拆分**（表归属已在 `03_01` 建立 `domain` 字段），脚本内容不变、只换目录与清单标识；`down_revision` 按域内线性重连，域间互不引用。

### 3.2 每清单独立一张记录表（核心） <a id="version-table"></a>

| 项 | 口径 |
| --- | --- |
| 表名 | `alembic_version_{domain_key}`（同一库内多清单各一张） |
| 设置点 | `env.py` 显式设置 `version_table`（当前只设了 schema） |
| 读取 | 读取当前版本的函数改为按清单名拼表名；**表不存在视为未迁移**（沿用现有异常处理） |
| 归档清单 | `alembic_version_archive` 一张（归档库单清单，不按域拆） |
| 冲突 | 同名域在不同库各自独立（表在库内），不跨库冲突 |

**为什么必须每清单一张**：表结构变更记录表是“这条表结构变更清单跑到哪”的唯一记录；多清单共用一张时，A 链写入的 head 会被 B 链覆盖，回滚与增量判断全部失真。

### 3.3 目标表集与模型导入按域 <a id="tables"></a>

| 项 | 改造前 | 改造后 |
| --- | --- | --- |
| 目标表集 | `chain_tables(service, datasource)`：该服务全部表 + 基础设施表 | `chain_tables(domain_key, datasource)`：该域的表 + 基础设施表（仅 `platform` / `tenant` 库类别） |
| 模型导入 | `service_model_modules(service)` → 导入该服务 `models` 包 | `domain_model_modules(domain_key)` → 导入该域的模型模块（按 `03_01` 的域布局声明定位） |
| 建表 | 按服务表集自动建表 | 按**部署单元所含域**的表集并集自动建表（单元内多域合并） |
| 表归属校验 | 表名须在 `TABLE_OWNERSHIP` 登记 | 增加“表的 `domain` ∈ 当前单元所含域”校验 |

**关键不变式**（与 `01_02` 对齐）：任一拓扑下，库结构 = 所含业务域各链的并集；表名不随拓扑变化。

### 3.4 部署单元执行多清单 <a id="execute"></a>

```
for domain_key in unit.domains (按固定顺序):
    upgrade 该域清单到 head（表结构变更记录表 alembic_version_{domain_key}）
```

| 项 | 口径 |
| --- | --- |
| 顺序 | 按域清单序（稳定、可复现）；**不按域间依赖**（域间无 DDL 依赖，物理外键已禁） |
| 幂等 | 已到 head 的链直接跳过（读表结构变更记录表） |
| 失败语义 | 任一链失败 → 整体失败并指出域与脚本；**不回滚已成功链**（各自事务，与种子口径一致） |
| 并发 | 同一库的链执行加库级锁（或依赖部署串行），避免两实例同时 upgrade |
| 空单元 | 无域 → 跳过（但 `02_01` 已禁止空单元） |

### 3.5 库键：服务段换部署单元段 <a id="dbkey"></a>

| 项 | 改造前 | 改造后 |
| --- | --- | --- |
| 平台库键 | `platform` / `platform_{service}` | `platform` / `platform_{unit}` |
| 租户库键 | `tenant_{code}` / `tenant_{service}_{code}` | `tenant_{code}` / `tenant_{unit}_{code}` |
| 解析函数 | `resolve_db_key(db_key, service=…)` | `resolve_db_key(db_key, unit=…)`（保留 `service=` 别名一个过渡期，语义等同） |
| 归属校验 | 跨服务即拒 | 跨单元即拒（`03_01` 的域判定在其内层） |
| 库名派生 | `{prefix}_{service}` / `{prefix}_{service}_{db_basis}` | `{prefix}_{unit}` / `{prefix}_{unit}_{db_basis}`；`prefix == unit` 时去重 |

**兼容**：既有部署的库名不变（单元标识取当前服务名即可，如 `unit=platform`），切换拓扑时才改库名——**这意味着首次引入单元时，默认拓扑的单元标识应与现有服务名一致**（`single` 模板的 `core` 需配置别名或首批沿用旧名）。

### 3.6 存量库切换 <a id="switch"></a>

| 步骤 | 内容 |
| --- | --- |
| 1 | 旧清单（按服务）**冻结**：保留文件与 `alembic_version` 记录，不再新增脚本 |
| 2 | 域清单从 `0001` 起（按表归属拆分脚本）；首次执行前做**结构对账**（模型 vs 库） |
| 3 | 对账通过 → 直接写入该域表结构变更记录表基线（标记 `baseline`），不执行 DDL；对账不通过 → 正常执行链（补差异） |
| 4 | 全部域清单写入基线后，旧 `alembic_version` 表标记为只读（保留一版，后续清理） |
| 5 | 回滚：回滚代码 + 恢复旧清单读取路径（旧表仍在），域表结构变更记录表可保留或清理 |

**为什么不切历史**：切历史（multi-head / branch）会让“同一库表结构”出现多条并行的版本线，回滚与对账都变复杂；而项目当前结构以模型为事实源、脚本已清空，**拆目录 + 基线写入**成本最低且无损。

### 3.7 例外 <a id="exception"></a>

| 对象 | 处置 |
| --- | --- |
| 基础设施表（发件箱三表） | 每库一份，不按域拆；进入 `platform` / `tenant` 清单，归档清单不含（沿用现状） |
| 归档库 | 单清单 `archive`，不按域拆（`01_02` 已定） |
| 共享模型子包（`bms_core/models/<来源>/`） | 按“定义来源”归域，声明场景只校验已登记、不判越权（沿用既有例外） |

### 3.8 执行期冲突校验（不只靠护栏） <a id="exec-check"></a>

**为什么不能只靠护栏**：护栏是静态的（查代码里“不该写什么”），而冲突取决于**执行当时的库现状与清单全集**——两个域的清单各自看都没问题，合到同一库才撞表；记录表里出现别的库带过来的版本号，也只有执行时才知道。所以**平台作为执行方必须自带校验**，护栏只是第一道。

| # | 校验 | 时机 | 判定 | 失败处置 |
| --- | --- | --- | --- | --- |
| 1 | 脚本目标表归属 | 执行前 | 逐个解析脚本操作（建表 / 加列 / 改索引 / 删表…）的目标表，必须**全部归本清单的业务域** | 拒绝执行，指出域与表 |
| 2 | 清单间表集不相交 | 执行前 | 同一库内**各清单的目标表集不得有交集**（域间不得操作彼此的表） | 拒绝执行，指出相撞的两域与表 |
| 3 | 记录表与清单一致 | 执行前 | 记录表中的 revision 必须存在于本清单；**未知 revision 即拒**（防别的库 / 别的域带入） | 拒绝执行，输出未知 revision |
| 4 | 结构对账 | 执行前 | 「模型声明」与「库现状」比对；差异必须为空，或已被本次待执行脚本覆盖 | 拒绝执行，输出差异清单 |
| 5 | 版本单调 | 执行前 | 待执行 revision 必须**大于**记录表当前值；不允许回退、不允许分叉（多 head 即拒） | 拒绝执行 |
| 6 | 破坏性操作 | 执行前 | `drop table` / `drop column` 等须脚本显式标记破坏性 + 调用方显式确认参数 | **默认拒绝**，需显式放行 |
| 7 | 库级互斥 | 执行中 | 获取库级锁；拿不到即拒（**不排队等待**，避免两实例同时改结构） | 拒绝并提示并发 |

**输出与退出码**：逐项给出「校验项 / 结果 / 详情」；任一不过即非零退出，且**不执行任何脚本**（先全量预检、再执行，不留半改状态）。

**与护栏的分工**：

| 层 | 管什么 | 落点 |
| --- | --- | --- |
| 静态护栏 | 代码与脚本里“不该出现什么”（跨域 import、跨域表引用、表归属登记完整性） | `03_01` 与 `check-*` 脚本 |
| 执行期校验 | 这次执行“会不会破坏别人”（表集相交、记录表污染、结构漂移、并发） | 本节，属平台执行器职责 |

> 一句话：**护栏防“写错”，执行器防“撞上”**——两者缺一，冲突仍会漏到线上。

## 6. 风险与边界 <a id="risk"></a>

| 风险 | 处置 |
| --- | --- |
| 存量库基线判断错误（以为结构一致实际不一致） | 对账必须逐表逐列（复用既有模型比对），不一致则走正常链 |
| 多清单并发执行 | 库级锁或部署串行；CI 单实例不受影响 |
| 脚本拆分错域 | 依据表归属 `domain` 机械拆分 + 人工复核；拆分后跑三库集成 |
| 单元标识与旧服务名不一致导致库名变化 | 首次引入单元沿用现有服务名；改名需一次性迁移（`04_02`） |
| 表结构变更记录表增多（每库多张） | 数量 = 该库所含域数，可接受；运维脚本按前缀列出 |
| 旧 `alembic_version` 残留 | 只读保留一版，后续清理；不影响新清单 |

## 7. 开放项 <a id="open"></a>

| # | 事项 | 归口 |
| --- | --- | --- |
| 1 | 链顺序是否改为按域间“表依赖”推导 | 当前物理外键已禁，域间无 DDL 依赖，暂不需要 |
| 2 | 表结构变更记录表是否统一加前缀（如 `alembic_version_domain_*`） | 现命名为 `alembic_version_{domain}`，出现同名冲突再调整 |
| 3 | 存量脚本拆分是否保留旧目录只读副本 | 切换完成后评估（保留会增加目录噪音） |
| 4 | 多单元共库（两个单元读写同一库）是否允许 | 架构上不鼓励；出现时评估（当前一库一单元） |
