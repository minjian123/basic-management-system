## 2. 实施过程 <a id="process"></a>

### 2.1 设计核对与拍板结论 <a id="review"></a>

动手前核对了 6 处「设计与现状」冲突，逐项经用户拍板（2026-10-25）：

| # | 冲突 | 结论 |
| --- | --- | --- |
| 1 | 域标识含连字符，`alembic_version_identity-federation` 在 MySQL 需引号 | **域标识统一 snake_case**（`identity_federation` 等 5 个复合域改名），表名直接拼接 |
| 2 | 设计写目录 `versions/{domain}/`，但清单标识含数据源段 | 取**两层** `versions/{domain}/{datasource}/` |
| 3 | 02_01 拓扑记录未实施，`unit.domains` 无事实源 | `[app].unit` 可选、缺省回落 service；域集由布局按承载服务反推 |
| 4 | 设计写「基础设施表进 platform/tenant 清单」，与「清单表集不相交」冲突 | **不进域清单**，由单元级 `unit_tables` 追加 |
| 5 | 设计要旧 `{service}:` 形态过渡期映射 | **不兼容**，直接拒绝并提示改用域清单名 |
| 6 | 设计要 `domain_model_modules` 按域导入，但模型文件文件级混域 | 导入承载服务全量模型 + 公共模块，建表集按域过滤（设计 §8-3） |

### 2.2 域标识改 snake_case <a id="domain-rename"></a>

`identity-federation` / `permission-meta` / `menu-form` / `platform-config` / `platform-registry` → 下划线形态；同步域布局、域级基线（30 条）、表归属登记 52 行 `domain`、两处域标识正则、01_01 设计与数据表文件。校验：`check_service_boundaries`（域布局 140 / 基线 30 条全命中）、`ops.check_tables --offline` 通过。

### 2.3 迁移清单按业务域（核心） <a id="series"></a>

`db/migration.py` 重写：

| 对象 | 口径 |
| --- | --- |
| `MigrationSeries` | `name`（`{domain}:{datasource}`）/ `domain` / `datasource` / `tables` / `scope`；`version_table` = `alembic_version_{domain}`；`version_location` = `versions/{domain}/{datasource}` |
| 命名与解析 | `build_series_name` / `parse_series_name`（旧 `{service}:` 命中服务标识即报错） |
| 目录与清单全集 | `series_names()`（域 × 平台/租户 + 归档 `archive:archive`）、`domain_series(domain)` |
| 表集 | `series_tables(domain, datasource)`（只含本域表） |
| 单元 | `unit_key()` / `unit_domains()`（承载服务反推；拆分形态以「单元 = 域」表达）/ `unit_series()`（域名稳定排序） |
| 模型导入 | `domain_model_modules(domain)` = 承载服务模型 + 公共模块；`import_service_models(service)` 供离线清点 |
| 连接串 | `series_url()` 平台库取**承载单元**的 `platform_{unit}`；归档库固定 `archive` |
| 版本读取 | `current_revision(url, version_table=…)` 按清单表名读，未迁移返回 None |

`alembic/env.py`：按清单设置 `version_table`（离线 / 在线 / 达梦模式分支同源）；`alembic.ini` 只留缺省段 `[alembic]` → `platform_registry:tenant`，其余清单按需补段；版本目录重建为 `platform_registry/{platform,tenant}`，旧 9 个服务目录删除，根目录新增 README 说明规则。

### 2.4 库键单元段 <a id="dbkey"></a>

`db/keys.py`：`resolve_db_key(unit=…, service=别名)`、`database_name(unit=…)`——归属判定改「跨单元即拒」；`[app].unit` 新增（空则回落 `[app].service`），既有部署库名不变。

### 2.5 单元建表与 ops 四入口 <a id="ops"></a>

| 对象 | 变更 |
| --- | --- |
| `db/bootstrap.py` | `unit_metadata`（域并集 + 基础设施表）、`apply_unit_schema`、`ensure_unit_schema`（按单元三库类别） |
| `ops/migrate_tenants` | 任务改为「单元 × 数据源 × 库」，携带该库清单序列；执行前 `MigrationGuard.preflight()`、执行中库级锁 + 逐清单版本校验；失败即该库整体失败且不回滚已成功清单 |
| `ops/init_schema` | 改用 `apply_unit_schema`（同一派生点） |
| `ops/init_tenant` / `tenant/provisioning` / `ops/provision_tenant` / `ops/test_db` | 全部改单元口径（去掉服务链解析） |
| `ops/baseline_series`（新增） | 存量库切换：结构对账 → 只写 `alembic_version_{domain}` 基线行、不执行 DDL（`--dry-run` 只对账；旧 `alembic_version` 只读保留） |

### 2.6 执行期校验（§3.8） <a id="guard"></a>

新增 `db/migration_guard.py`：校验 1（脚本目标表归属）、2（清单表集不相交）、3（版本记录表与清单一致）、5（版本单调 / 禁止分叉）、6（破坏性操作须显式放行）、7（库级互斥：PG 咨询锁 / MySQL 命名锁，其余方言按部署串行）；结构对账复用 `ops.check_tables`（不新增第二套实现）。

### 2.8 域布局改由清单渲染（2026-10-29 补注） <a id="domains-manifest"></a>

07B `04_02` 重开后，域布局的**权威来源**由各仓 `deploy/boundaries/domain_layout.json` 文件改为清单第九类 `[[domains]]` 声明，文件降为**生成物**（`ops.check_modules --render-domain-layout` 渲染、`--check-domain-layout` 漂移比对，已挂入两仓预检）。本任务口径**不变**：

| # | 项 | 现状 |
| --- | --- | --- |
| 1 | 清单表集 / 版本记录表 / 单元聚合 | 与布局来源无关，零改动 |
| 2 | `domain_model_modules` 与 `check_tables` 的「有布局派生」 | 仍读**本仓生成物**；生成物是清单的确定性函数，渲染结果与迁移前文件逐字段一致；「无布局回退全量」分支保留（容器内未携带 `deploy/`） |
| 3 | §2.1 冲突 3「域集由布局按承载服务反推」 | 跨进程场景改由**注册表快照**重建（`domain_service_view()` / `_project_domains()`），平台不读产品仓文件 |
| 4 | 产品域（mdm `org`） | 由产品仓自己的清单声明，经注册通道写入平台 `sys_domain`；不再需要「产品仓自建布局文件」 |
