## 7. 复盘与经验教训 <a id="retro"></a>

**根因**：平台侧长期缺「业务域」这一层——服务既是代码包又是部署单元又是数据归属单位，导致三件事互相绑架：合并部署就怕丢边界、拆服务就得改代码路径、库名跟着服务名走。本专项的解法是**把域抽成第一等公民、让单元成为可变参数**，并用四道机器护栏替代「靠约定」：域级 import / 表读写护栏、出口 DTO 护栏、拓扑与路由生成校验、令牌域声明与入站两道判定。

**机制收益**（可复验）：

- 同一套域模型在单进程单库到一租户一域一库间是**连续谱**，切换成本落在拓扑记录与迁移工具，而不落在业务代码；
- 默认拓扑（单元 = 服务）下**生成物逐字不变**（`apisix.yaml` / 库名 / 表集），改造对既有部署零扰动——这是「先加后切」能成立的前提；
- 边界不再依赖进程隔离：合进一个进程后跨域 import 与直接读表仍被拦，合并因此是**部署选择**而不是**架构让步**。

**踩坑与教训**（本轮真实付出）：

1. **开发环查不到全仓问题**：`pyright` 按改动文件查通过，推送环查全仓才暴露 2 处私有导入；`check_backend_base` 也不在开发环里。教训——新增基座类 / 改公开面后，**至少手动跑一次全仓 `pyright` 与基座校验**，不要等推送环。
2. **「补基类」要连语义一起补**：`04_03` 为消除「未继承基类」告警给 `MigrationProgress` 加了 `BaseFrameworkObject`，却保留了 `@dataclass`，被「框架对象不得 dataclass」二次打回——框架对象是**可变状态载体**，字段应写在 `__init__`。
3. **选测规则要跟着目录组织走**：`03_03` 按域分包后，测试目录（`tests/auth/`）与源码层级（`domains/auth/api/`）不同构，只按导入闭包推导仅命中 13/51 用例，覆盖率门禁据此判缺行；正解是在仓根 `engkit.toml` 声明「改该域 ⇒ 并入该域的测试目录」，而不是放宽门禁。
4. **覆盖率门禁是按模块而非按变更行**：改一行 docstring 也会把整模块拉进 100% 要求，于是「文档级改动」也会暴露真实缺口（`get_audit_capturer` 从无用例）——这不是噪音，是**顺带补齐的机会**。
5. **文档与机制漂移是缺陷而非笔误**：库键服务段改成部署单元后，56 份表文件仍写「归属服务」；虽然默认拓扑下库名没变，但读者会按旧机制理解。收口时逐份批改 + 在数据规范补口径注，才谈得上「文档是事实源」。
