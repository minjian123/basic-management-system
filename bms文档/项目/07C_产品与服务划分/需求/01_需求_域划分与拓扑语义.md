## 1. 业务域说明 <a id="intro"></a>

本业务域定语义层：业务域怎么划（判据）、业务域与部署单元与库怎么分层、同一套业务域模型如何从单体到一租户一业务域一服务。后续机制与收编以其为准。

- **依据**：《[架构设计 · 产品与服务划分](../../../设计/架构设计/39_架构设计_子系统_产品与服务划分.md)》「三层模型」「业务域划分判据」节；《[微服务演进规划](../../../规划/微服务演进规划.md)》「业务域、部署单元与租户拓扑」节。

## 2. 需求 01-1：业务域划分判据与目标业务域清单 <a id="r01-1"></a>

优先级：2（高）

**背景与动机**：顶层的「产品 / 服务」两个词混用已久：产品指独立仓库与发版单元，服务指部署单元，而领域边界从未单独表达。结果是「什么时候该拆服务」只能靠规模与直觉，平台侧出现巨型服务（单服务容纳用户、角色、租户、菜单、权限元数据、参数、图标等多个业务语义），产品侧则出现单服务多业务域（组织与参考数据同进程）。缺乏判据会导致每次讨论都从头争论。

**内容**：

1. **判据**：拆业务域四条（数据所有权独立 / 业务语义独立 / 扩缩需求独立 / 变更节奏独立），满足两条及以上即拆；不满足则在既有业务域内加聚合。
2. **开产品判据**：独立仓库、独立发版节奏、独立团队或独立商业定价中至少两项。
3. **反例清单**：表多、代码多、命名上“像另一个业务”不构成拆业务域理由。
4. **目标业务域清单**：以现有服务与产品为输入，逐个标注业务域归属（含平台业务域与产品业务域），输出「业务域 → 现有服务 / 表前缀」对照。
5. **复核机制**：业务域清单定期复核（合并同类、拆分过载），判定沿用上述判据。

**完成标准**：判据与反例成文；目标业务域清单覆盖现有全部服务与产品的业务域归属，每业务域给出数据所有权与表前缀；清单可被后续任务直接引用（能力目录、表归属、拓扑均以业务域为键）。

**参考文档**：《[架构设计 · 产品与服务划分](../../../设计/架构设计/39_架构设计_子系统_产品与服务划分.md)》「业务域划分判据」节

## 3. 需求 01-2：部署拓扑语义与规划修订 <a id="r01-2"></a>

优先级：2（高）

**背景与动机**：业务域边界定完，还需要回答「业务域怎么组合成部署单元与库」。若不定语义，每个租户的部署方式都会变成一次临时决策，运维无法复用，能力寻址也无法落地第二段解析。

**内容**：

1. **三层模型**：能力（最稳定）→ 业务域（稳定）→ 部署单元（可变：一个或多个业务域的集合，一个服务进程 + 一套库）。
2. **连续谱**：最小一个进程承载全部业务域（含平台业务域）+ 一库；极端一租户一业务域一服务一库；中间按业务重心分组。
3. **库随部署单元、表归属随业务域**：拓扑变更不改变表名，只改变表所在库；表结构变更清单按部署单元聚合。
4. **规划修订**：《微服务演进规划》补「业务域、部署单元与租户拓扑」节，说明服务清单是**默认拓扑**、租户可调组合。

**完成标准**：架构节点「产品与服务划分」定稿（只写语义）；《微服务演进规划》补节并与架构节点互链；连续谱两端与中间形态均有文字定义；「库随部署单元、表归属随业务域」写入且有反例说明。

**参考文档**：《[微服务演进规划](../../../规划/微服务演进规划.md)》「业务域、部署单元与租户拓扑」节
