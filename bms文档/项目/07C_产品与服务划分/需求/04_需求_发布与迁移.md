# 发布与迁移需求

## 1. 业务域说明 <a id="intro"></a>

本业务域处理拓扑带来的两个运营问题：合并部署时怎么发版与对账、租户拓扑变更怎么迁。

- **依据**：《[架构设计 · 产品与服务划分](../../../设计/架构设计/39_架构设计_子系统_产品与服务划分.md)》「发布与版本」「拓扑迁移」节。

## 2. 需求 04-1：发布单元与版本对账 <a id="r04-1"></a>

优先级：2（高）

**背景与动机**：当前按服务发版；同一部署单元内合并多业务域后，会出现「三个业务域同时发布、契约版本互相不兼容」的情形——这在按服务发版时不会出现，因为各服务独立。

**内容**：

1. **发布单元 = 部署单元**：一次发布包含其内全部业务域的当次版本；业务域版本是部署单元版本的组成部分。
2. **契约版本对账**：合并部署前校验业务域间契约版本兼容（沿用协同节点的版本口径），不兼容即拒绝发布。
3. **产品版本解耦**：产品按自身节奏发版，只声明依赖的能力（业务域）与契约版本。
4. **回滚**：按部署单元整体回滚，避免同单元内版本错配。

**完成标准**：合并部署能给出业务域版本清单与契约兼容结论；不兼容时拒绝发布并定位到业务域与能力；回滚以部署单元为单位且有对应用例；产品版本与服务版本解耦的说明写入规划。

**参考文档**：《[架构设计 · 产品与服务划分](../../../设计/架构设计/39_架构设计_子系统_产品与服务划分.md)》「发布与版本」节、《[部署发布规范](../../../规范/部署发布规范.md)》

## 3. 需求 04-2：租户拓扑迁移 <a id="r04-2"></a>

优先级：2（高）

**背景与动机**：拓扑一旦可配，就一定会有「从单库单服务迁到分组」或「从分组迁回合并」的需求。这类动作涉及数据搬迁与流量切换，若无统一套路，每次都是高风险手工操作。

**内容**：

1. **先加后切**：新部署单元先上线并就绪，再切流量，最后下线旧单元。
2. **数据先行**：按业务域搬迁（表归属按业务域），搬迁期双写或停机窗口按租户等级选择。
3. **能力地址不变**：消费方按业务域寻址，拓扑切换对其透明；切换期允许短暂双活，但同一能力不得长期由两处提供。
4. **可回滚**：切换前保留旧单元与数据快照，回滚窗口内可整体退回。
5. **审计与告知**：变更留审计；涉及停机窗口须提前告知租户。

**完成标准**：从合并到拆分、从拆分到合并各有一条可复现的迁移步骤与回滚步骤；迁移期间能力取址不中断（夹具或演练验证）；迁移后数据完整性与表归属校验通过；变更留审计。

## 4. 需求 04-3：网关、身份与观测按业务域 <a id="r04-3"></a>

优先级：2（高）

**背景与动机**：对外路径当前按服务键生成（`/api/{service_key}/v1`），服务令牌主体也是服务标识，日志与指标同样按服务标注。业务域与部署解耦后，同一对外路径背后的服务可能随租户变化、同一进程内也可能承载多个业务域——若这三处仍按服务表达，对外契约会随拓扑漂移，审计与排障也无法按业务域归因。

**内容**：

1. **对外路径按业务域**：外部路由由「业务域 → 部署单元 → 上游」生成，对外路径保持按业务域稳定，不因拓扑变化而变。
2. **调用身份带业务域**：服务令牌声明其承载的业务域，与能力分配记录（按业务域授权）对账；对不上即拒绝。
3. **观测按业务域**：日志、指标、审计按业务域标注，合并部署后仍可区分归属与归因。
4. **配置按部署单元**：配置能表达「本部署单元启用哪些业务域」，未启用的业务域不装配、不暴露。

**完成标准**：同一业务域在合并与拆分两种拓扑下对外路径一致（夹具验证）；令牌携带业务域且与分配记录对账，不一致时拒绝；指标与日志可按业务域过滤；配置能声明部署单元启用的业务域，未启用业务域的路由不生成且调用被拒。
