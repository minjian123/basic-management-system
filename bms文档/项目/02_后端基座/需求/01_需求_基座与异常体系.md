## 1. 域说明 <a id="intro"></a>

本域对应阶段二「基座与异常体系」（WBS 01），承载两件事：

- **异常体系与统一响应**（原阶段一 02-3 迁入）：统一异常基类 `BizError` + 全局异常处理器 + 统一响应 `{code, message, data}` + 错误码登记，替换阶段一的 `NotFoundError` 过渡实现。
- **core 基座补齐与登记**：补齐安全基座（配置基座由阶段一 02-1 交付，本域只做登记与统一入口确认）；把阶段一已交付的 core 基座（`BaseObject` / 有序集合 / 并发集合 / Redis 封装）与三套基类（`BaseRepository` / `BaseService` / `BaseSchema`）在《架构设计 · 后端基础类体系》与本域回写登记。

**依据**：《[架构设计 · 后端基础类体系](../../../设计/架构设计/33_架构设计_后端基础类体系.md)》「core 横切基座」节、《[后端开发规范](../../../规范/后端开发规范.md)》「后端基座体系」节「异常与错误码」节、《[API接口规范](../../../规范/API接口规范.md)》、《[架构设计 · 接口与集成](../../../设计/架构设计/06_架构设计_接口与集成.md)》。
**目标**：全部后端模块可统一抛业务异常并经全局处理器转统一响应；core 基座与基类清单在架构登记齐备。

## 2. 需求 01-1：异常体系与统一响应 <a id="r01-1"></a>

优先级：2（高）　|　状态：未开始　|　完成日期：—

**背景与动机**：阶段一以 `NotFoundError` + 临时处理器过渡（body 结构与统一响应不一致）；若不在基座阶段统一，认证/RBAC/通用能力各模块将各自定义异常与错误响应，错误码口径必然发散。

**内容**（《后端开发规范》「异常与错误码」节、《API接口规范》）：

1. `app/core/exceptions.py`：统一异常基类 `BizError`（携带错误码与参数）+ 常用子类（参数异常 / 认证失效 / 权限不足 / 资源不存在 / 冲突等）；`NotFoundError` 过渡实现改为继承 `BizError`。
2. 全局异常处理器：`BizError` → 统一响应 `{code, message, data}`（HTTP 状态码与业务错误码分离）；未捕获异常 → 500 且不暴露堆栈（开发环境可含 trace_id）。
3. 统一响应模型 `ApiResponse`（Pydantic），成功 `code=0`；错误码平台段 `1xxxx`~`9xxxx` 登记于《架构设计 · 接口与集成》「错误码」节，本阶段建立骨架段位。
4. 业务异常在 services 层抛出、api 层不 catch；`main.py` 注销阶段一临时 404 处理器。
5. 测试：先登记 Kiwi 用例，再写自动化（异常分支 + 统一响应结构断言）；替换阶段一 demo 的过渡断言。

**完成标准**：`BizError` 及各子类可用；业务异常经全局处理器转统一响应结构；未捕获异常返回 500 且不泄露堆栈；错误码段位登记；阶段一临时处理器移除；`pytest`、`ruff`、`pyright` 全绿。

**参考文档**：《后端开发规范》「异常与错误码」节、《API接口规范》「统一响应与错误码」节、《架构设计 · 接口与集成》「错误码」节

## 3. 需求 01-2：core 基座补齐与登记 <a id="r01-2"></a>

优先级：2（高）　|　状态：未开始　|　完成日期：—

**背景与动机**：阶段一已交付 core 基座与三套基类，但**未在架构登记**（设计目录零提及），后续模块不知继承什么、公共能力加在哪；安全原语也缺统一落点，认证等阶段会各自实现。

**内容**（《架构设计 · 后端基础类体系》「基座分层」节「core 横切基座」节、《后端开发规范》「后端基座体系」节）：

1. 配置基座沿用与登记：`app/core/config.py`（config.toml 分区 + `BMS_` 环境变量覆盖 + 启动校验）由**阶段一 02-1 配置管理交付**，本域只做基座登记与统一入口确认，不重复实现。
2. 安全基座：`app/core/security.py`（密码哈希、令牌与会话安全原语），供阶段四认证与会话复用。
3. 基座登记回写：将 `BaseObject` / `BaseCollection`（有序集合）/ `ConcurrentSorted*` / Redis 有序封装 / `BaseRepository` / `BaseService` / `BaseSchema` 的职责、继承关系与代码位置在《架构设计 · 后端基础类体系》与《后端开发规范》保持同源一致（架构节点已建，本需求负责代码侧对齐与差异补齐）。
4. 继承约定校验：新增/改造类必须继承对应基类，禁止重复定义公共字段/方法（CI lint 或评审条款）。

**完成标准**：配置基座沿用阶段一 02-1 交付件并完成登记、安全基座就位并被后续阶段引用；《架构设计 · 后端基础类体系》基类清单与代码实现一致；继承约定纳入规范并有人可核对；`pytest`、`ruff`、`pyright` 全绿。

**参考文档**：《架构设计 · 后端基础类体系》「基座分层」节「core 横切基座」节、《后端开发规范》「后端基座体系」节、《命名规范》
