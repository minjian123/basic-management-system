## 2. 任务内容 <a id="content"></a>

> **口径修订（2026-11-04 复核）**：原第 5 条「编码变更约束」**删除**——该约束已完整落地：`后端开发规范` 第 170 条（租户编码可变更、不得作内部稳定键，库键 / 令牌 / 事件 / 存储一律以 `tenant_id` 为准）+ 架构 12 §8（库名基冻结于 `sys_tenant_database`，code 变更只改注册表编码与缓存失效、不重命名库）+ 表已落地（`models/tenant/tenant_database.py`）+ 接口层 `TenantUpdateRequest` 不含 `code`（不可改）。本任务只保留注销生命周期。

1. **注销语义缺失**：当前只有「停用 / 启用」，没有「注销」；产品侧因此不敢做数据清理，长期占用磁盘且无法真正退租。
2. **注销流程定义**：停用 → 数据归档（可选，复用归档管理既定能力）→ 产品侧清理 → 注册表标记 → 保留期后物理清理；每一步的状态与可回退边界明确。
3. **不可逆与确认**：注销与物理清理必须二次确认并留审计；保留期内可恢复，保留期后不可逆。
4. **产品侧清理契约**：产品如何感知注销、清理什么、失败如何重试；与 `04-04` 的初始化契约**对称**（经事件或既有契约，不新造机制）。
5. **事件补充**：如需新增 `tenant.deleted` 契约，按事件契约流程登记版本与字段（现有 `tenant.created/suspended/activated` 为契约 v2.0.0）。
6. **与已交付契约对账（2026-11-08 复核，2026-11-08 定案）**：07D `01-4` 已把 `tenant.deleted` 纳入租户事件 v2.1.0（载荷 `tenant_id` / `db_key` / `status` / 可选 `version`，无 `purge_at` / `reason`），msg `05-5` 已按该契约消费。**定案**：`tenant.deleted` 留租户事件族、只增可选 `purge_at` / `reason`（升 `2.2.0`）；`tenant.purged` 独立 `1.0.0`；msg `05-5` **同批双仓**改为「`deleted` 只停写 + `purged` 触发清理」（见设计 §4.5 / §4.8）。
7. **管理面只读放行（07 §7 第 58 项，纳入本任务）**：停用 / 注销后数据面拒绝，但管理面（主题、用量、清理进度）需可只读查；判据与实现形态见设计 §4.11（`readonly_routes` 白名单 + `require(readonly=True)`，缺省空即全拒）。`#59` TCP / h2 强关不在本任务。

## 3. 完成标准 <a id="accept"></a>

- 注销流程有状态机与文档，明确每个状态的进入 / 退出条件与可回退性。
- 物理清理有保留期与二次确认，操作留审计。
- 产品侧清理契约有明确接口或事件约定，msg 有落地示例（停用保留、注销清理）。
- 新增事件（若有）已登记契约与版本。
- 归档环节引用既有归档管理能力，不重复实现归档执行器（执行器缺失由审计合规模块补齐）。
- 契约口径与已交付代码一致：`tenant.deleted` 留租户事件族且只增可选字段，`tenant.purged` 独立 `1.0.0`，契约快照零漂移。
- 停用 / 注销后管理面只读可查、数据面与写操作仍拒（放行判据见设计 §4.11）。
