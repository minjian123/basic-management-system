## 3. 关键实现口径 <a id="impl"></a>

1. **扫描与提交分离**：`tenant.purge.scan` 只回填保留期并提交 `tenant.purge`，不内联删库；单租户一个作业，失败互不影响，重试粒度是「一个租户」而不是「一整轮」。
2. **作业落平台链**（`tenant_id = None`）：`sys_job` 写本服务平台库。若写进租户库，删完库会连带删掉作业记录——失败重试依据与执行留痕同时丢失。
3. **作业步骤固定顺序**：取注册行 → 复核 `deleted` 且 `purge_at` 非空且已到期 → 逐服务删库（单库失败不中断、记失败服务名）→ 全部成功才删对照行与注册行 → 同事务落 `tenant.purged` 与审计 → 提交。
4. **删库执行器统一入口**：`_resolve_drop()` 注入优先、否则按配置解析连接串走运维通道 `drop_database`。**解析必须 `allow_cross_service=True`**——要删的是各服务的租户库（platform / identity / file / report …），用默认工厂会被归属校验拒（`DataOwnershipError`），实测踩到并在设计风险表登记。
5. **幂等三处**：注册行已不存在 → `skipped`；状态被恢复改回 `active` → `skipped`；删库本身幂等（库不存在视为成功）。重复执行不重复发事件。
6. **失败不丢重试依据**：任一库删除失败即**不删注册行**，作业置失败并带失败服务清单，交框架重试；超限进死信 + 告警。
7. **回填从当下起算**：只处理 `purge_at IS NULL` 的注销行，且回填 `now + 保留期`——不会缩短已有时点，也不会把「归档刚就绪」的历史租户立刻清掉。
8. **提交幂等键带「租户 + 版本 + 日期」**：同日扫描重跑不重复提交；次日可再提交（死信后仍有机会收敛）。不含版本会让「恢复后再注销」被旧键挡住。
9. **清理留痕三处、不新增表**：作业执行记录（结果摘要含 `status` / `dropped_services` / `failed_services` / `db_key`）+ `tenant.purged` 事件 + 审计 `sys.operation.logged`（`actor=system`，扩展位含 `db_basis` / 两个计数 / 耗时）。

## 4. 问题与偏差 <a id="issues"></a>

| # | 问题 | 处置 |
| --- | --- | --- |
| 1 | **设计写的是 `BaseTask` + `services/.../tasks.py`**，但 `BaseTask` 插件位自 01_02 起明确「不再扩容」，周期任务的实际机制是「`sys_task` 内置任务 → 提交作业」（见 `bms_core/tasks/builtin.py` 头部口径） | 改按既有机制落地：内置任务 `purge_deleted_tenants` + 两个作业 + 独立 worker；设计 §2 / §4 同步改口径，历史写法不保留 |
| 2 | **跨服务删库被归属校验拒**：`EngineFactory(settings)` 默认只解析本服务库，`drop_database` 前的连接串解析直接 `DataOwnershipError`（首轮测试即红） | `_resolve_drop` 用 `allow_cross_service=True`（只解析地址、不建业务引擎），与开通编排 `_resolve_urls` 同口径；设计 §6 新增该风险行 |
| 3 | 设计要求仓储 `purge_backfill` 一个方法同时「查待回填 + 回填」，实际拆成 `purge_pending`（查）与 `backfill_purge_at`（写） | 拆开后回填逻辑在服务层可注入 `now` 与保留期，且与「查询不带写」一致；设计落点清单同步 |
| 4 | 保留期解析原只有 `TenantAdminService._retention_days` 私有实现，清理侧需要同一口径 | 抽 `parse_retention_days` 公开函数，两处共用（缺失 / 非整数 / 非正数 → 回落 30 + WARNING） |
| 5 | 删库时其他进程可能仍持有该租户库连接（MySQL 元数据锁 / PG 活动连接） | 属部署窗口事项：作业只负责「删」，连接先断由 API 侧停用 / 注销时的引擎回收承担；真删库验证与备份核对在部署窗口做（设计 §6 第 3 项开放项不变） |
