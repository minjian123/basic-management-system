## 1. 概述 <a id="overview"></a>

- **目标**：把租户生命周期从「开通 / 停用 / 启用」补成**含注销与物理清理的完整闭环**——注销即不可用、保留期内可恢复、到期由作业逐库清理，每一步的状态、可回退性与留痕都明确。

  1. **状态机**：`active | suspended` →（注销，二次确认）→ `deleted` →（保留期到期，作业）→ 注册行删除。`deleted` 期间**不软删**（`deleted_at` 保持 NULL），保留期内详情 / 列表 / 恢复全部走现有查询，不新增「含软删」分支。
  2. **可恢复边界**：保留期内（`purge_at` 未到或为空）可恢复为 `active`；物理清理后不可逆。过期未清理期间**不可恢复**（防「已过期又恢复」两头不一致）。
  3. **两步产品契约**：`tenant.deleted`（注销，产品停写、**不删数据**）+ `tenant.purged`（清理完成，产品才删数据），避免保留期内恢复时数据已被产品销毁。前者**留在租户事件族**（`2.2.0` 内只增可选 `purge_at` / `reason`），后者独立 `1.0.0`——已交付的 07D `01-4` 与 msg `05-5` 订阅声明零破坏。
  4. **归档不阻塞**：归档执行器未就绪时**不置 `purge_at`**（保留期不计时、清理作业不认），注销照常可用；就绪后统一回填时点，数据不会在未归档时被销毁。
  5. **清理执行**：定时任务每日扫描到期租户 → 逐租户提交清理作业 → 按「服务目录已启用服务 × 租户」逐库删除 → 删注册行 → 落 `tenant.purged`。单库失败不中断、可重试、可观测。
  6. **管理面只读放行**：停用 / 注销后数据面一律拒，**管理面只读**（主题、用量、清理进度）经白名单放行——判据在基座守卫（`readonly_routes` + `readonly=True`），产品只登记路径、不自建旁路（§4.11）。

- **依据**：任务 [04-03](../04_租户与平台超管_03_租户注销生命周期.md) 第 2、3 节；需求 [07-7](../../../../需求/04_需求_租户与平台超管.md#r07-7) 第 3、10 条；《[架构设计 · 多租户路由](../../../../../../设计/架构设计/12_架构设计_子系统_多租户路由.md)》§4 / §8；《[概要设计 · 租户管理](../../../../../../设计/概要设计/25_概要设计_租户管理.md)》§2.2 / §5.3 / §7；《[概要设计 · 归档管理](../../../../../../设计/概要设计/30_概要设计_归档管理.md)》§2.2 / §3.2；《[架构设计 · 事件总线](../../../../../../设计/架构设计/16_架构设计_子系统_事件总线.md)》§2 / §6。
- **范围**：租户服务（`bms_tenant`）的注册表字段、状态机、两个端点、两条事件契约、保留期参数、清理作业与定时扫描；`sys_tenant` 表文件与总览登记；概要 25 与架构 12 的口径回写。
- **不含（归口见 §9）**：归档执行器本体（审计合规模块，计划 §7 第 32 项）；TCP / h2 连接应用层强关（07 §7 第 59 项，部署基座）；mdm / biz 的 `tenant.purged` 订阅声明（暂无清理实现）；备份保留策略（部署与运维）。msg `05-5` 的消费口径改造属**同批双仓**范围（不在本仓代码内，但同窗口交付）。

## 4. 契约设计 <a id="contract"></a>

### 4.1 状态机与可回退边界 <a id="state-machine"></a>

```text
provisioning ──开通成功──▶ active
active       ──停用──────▶ suspended ──启用──▶ active
active / suspended ──注销（确认码 + reason）──▶ deleted
deleted      ──恢复（保留期内）──▶ active
deleted      ──保留期到（作业）──▶ 注册行物理删除（终态，不可回退）
```

| 状态 | 进入条件 | 退出条件 | 可回退 |
| --- | --- | --- | --- |
| `provisioning` | 开通中 | 开通成功 → `active`；开通失败清理注册行 | 不适用（**不允许注销**，82003） |
| `active` | 开通成功 / 启用 / 恢复 | 停用 / 注销 | 是 |
| `suspended` | 停用 | 启用 / 注销 | 是 |
| `deleted` | 注销（`confirm_code` 校验通过） | 恢复（`purge_at` 为空或未到）→ `active`；保留期到 → 物理清理 | **有条件**：`purge_at` 非空且已过 → 不可恢复（82010） |
| 物理清理后 | 清理作业成功 | — | **不可逆**（注册行与各服务库均已删） |

- **平台租户（`kind = platform`）不得注销**：它是平台超管的承载，注销等于自锁（82003）。
- **注销不清 `expire_at`、不改 `code` / `domain`**：保留期内 `code` / `domain` 仍占用唯一约束（`uq_sys_tenant_code_deleted_at` 等），新租户不能用同一编码；物理清理后自然释放。这是**有意的**——避免「旧租户保留期内、新租户复用同码」导致产品侧按 code 派生的键串号。

### 4.2 表字段变更（两列 + 一个索引） <a id="schema"></a>

| 变更 | 列 / 索引 | 类型 | 语义 |
| --- | --- | --- | --- |
| 加列 | `deletion_requested_at` | `DATETIME` 可空 | 注销申请时刻（UTC）；恢复时清空。审计与「保留期从哪天起算」的可见依据 |
| 加列 | `purge_at` | `DATETIME` 可空 | 保留期截止（UTC）；**为空 = 尚未进入清理倒计时**（归档未就绪 / 归档失败 / 待回填），清理作业只认非空且已到期 |
| 改枚举 | `status` | `VARCHAR(16)` | 取值增 `deleted`（`provisioning` / `active` / `suspended` / `deleted`） |
| 加索引 | `idx_sys_tenant_purge_at` | `(status, purge_at)` | 清理扫描（`status = deleted AND purge_at <= now`）与回填扫描（`status = deleted AND purge_at IS NULL`）共用 |

- `deleted_at` **不参与注销**：保持 NULL，直到物理清理。这样 `by_id` / 列表 / 详情 / 恢复全部沿用现有「过滤软删」的查询，不需要为注销新增第二套读取路径（这是本设计相对「注销即软删」的关键取舍）。
- 字段唯一事实源在表文件《[sys_tenant](../../../../../../设计/数据库设计/数据表设计/sys_tenant.md)》，本设计不复制字段清单；实施时按「表文件（含变更记录 v9）→ ORM 模型 → 建表落地 → 总览登记」顺序推进。

### 4.3 注销端点 <a id="api-delete"></a>

`POST /api/v1/tenants/{id}/delete`　权限码 `tenant:manage`

请求体 `TenantDeleteRequest`：

| 字段 | 类型 | 必填 | 约束 |
| --- | --- | --- | --- |
| `confirm_code` | `str` | 是 | 必须**等于**该租户 `code`（二次确认）；不做大小写宽松匹配 |
| `reason` | `str \| None` | 否 | 最长 200 字；进审计载荷与事件，便于事后追溯 |

响应 `ApiResponse[TenantDetail]`（`status = "deleted"`，含两字段）。

处理顺序（**先校验形态与状态，再落状态机**）：

1. 取注册行（未软删）→ 不存在 `82002` / 404；
2. `kind == platform` → `82003` / 409；
3. `status` 不为 `active` / `suspended`（含 `provisioning`、已是 `deleted`）→ `82003` / 409；
4. `confirm_code != code` → `82009` / 400（**不泄露**「租户存在但码不对」以外信息）；
5. 归档判定（§4.6）→ 决定 `purge_at`；
6. 落状态：`status = deleted`、`deletion_requested_at = now`、`purge_at = now + retention` 或 NULL；
7. 同一事务内 `enqueue_event(row, "tenant.deleted", extra={purge_at, reason})`；
8. 审计：`AuditCapturer.capture(table="sys_tenant", model_id, changes=[status, deletion_requested_at, purge_at])`；
9. 事务提交后：回收该租户引擎（逐 `enabled_tenant_services()`）、`_revoke_sessions(code)`、租户源缓存失效——**与停用同一段编排，抽成公共函数**，失败只告警不回滚（与停用现状一致）。

> 注销**即时生效**：在线会话立即失效、登录被拒；产品侧随后收 `tenant.deleted` 做停写准备（§4.7）。

### 4.4 恢复端点 <a id="api-restore"></a>

`POST /api/v1/tenants/{id}/restore`　权限码 `tenant:manage`

无请求体（或可选 `reason` 同注销）。响应 `ApiResponse[TenantDetail]`（`status = "active"`，两字段为空）。

| 分支 | 判定 | 结果 |
| --- | --- | --- |
| 不存在 | 注册行缺失 / 已软删 | `82002` / 404 |
| 非 `deleted` | `status != deleted` | `82003` / 409 |
| 保留期已过 | `purge_at` 非空且 `<= now` | `82010` / 409（已进入待清理，不可恢复；如需保留须运维介入并留审计） |
| 正常 | `purge_at` 为空或 `> now` | 置 `active`、清两列、`enqueue_event("tenant.activated")`、审计、缓存失效 |

- 恢复**不需要**撤销会话（本来已全撤）、不需要预热引擎（懒加载）。
- 恢复后产品侧收 `tenant.activated`（既有契约），自行恢复写入。

### 4.5 事件契约 <a id="events"></a>

**口径（2026-11-08 定案，交付前须先按本节回写代码与文档）**：`tenant.deleted` **留在租户事件族**，不另立 `1.0.0`。理由：该事件已由 07D `01-4` 随租户事件 `2.1.0` 登记并交付、msg `05-5` 已按其消费（Kiwi 2453），另立 `1.0.0` 等于把已发布契约**版本回退**（硬校验直接拒：契约版本不得回退），且订阅方要同时升两个版本、已交付代码返工。本次在族内追加**可选** `purge_at` / `reason`，按「契约字段变更至少升次版本」升 `2.2.0`；`tenant.purged` 是**新事件**，独立 `1.0.0`。

| 事件 | 版本 | 触发 | 载荷（`payload`） |
| --- | --- | --- | --- |
| `tenant.deleted` | `2.2.0`（租户事件族；`2.1.0` 起已登记） | 注销事务内（Outbox） | `tenant_id`（必填，雪花 id 字符串）、`db_key`（必填，库名基）、`status`（必填，固定 `"deleted"`）、`version`（可选，乐观锁版本戳）、**`purge_at`（可选，ISO8601 UTC 字符串；归档未就绪时不写入）**、**`reason`（可选）** |
| `tenant.purged` | `1.0.0` | 清理成功、删注册行同事务 | `tenant_id`（必填）、`db_key`（必填）、`status`（必填，固定 `"purged"`）、`dropped_services`（可选，整数，删成功的服务数）、`failed_services`（可选，整数） |

- **版本影响面**：`_TENANT_EVENT_VERSION` 为四条租户事件共用 → `tenant.created` / `suspended` / `activated` 同标 `2.2.0`（载荷不变，属族版本抬升）。订阅方按**主版本**兼容（`EventSubscription.supported_majors` 含 `2`），**订阅声明无需改动**；契约快照 `deploy/events/contracts.json` 按工程命令重生成，零漂移校验通过。
- **注册表描述同步改写**：`tenant.deleted` 现描述「产品按保留期归档或清理资源」与新语义（**只停写、不授权删数据**）冲突，改为「租户注销（产品停写、保留数据；清理授权见 `tenant.purged`）」。
- 信封：`tenant_id` 与载荷同名同值；`aggregate_key = code`（与既有租户事件一致），审计链按租户有序。
- **为什么不合成一条**：保留期内恢复时产品不能已删数据，`tenant.deleted` 只表达「停写 + 待清理」；只有 `tenant.purged` 才授权删数据。合成一条会让产品在恢复窗口内毁数据。
- `purge_at` 用字符串而非时间类型：跨语言契约稳定，且与既有事件载荷风格一致（载荷只放标量）。
- Webhook 可订阅：是（与既有 `tenant.*` 同口径）。
- **订阅范围**：`tenant.purged` **仅 msg** 声明消费组（`msg-tenant-lifecycle` 已有实现基础）；mdm / biz 当前无租户数据清理实现，提前声明只会得到空转订阅，待出现真实清理需求再声明，基座不预置。

### 4.6 保留期与「归档未就绪」 <a id="retention"></a>

| 项 | 口径 |
| --- | --- |
| 参数键 | `tenant.deletion.retention_days`（`sys_config`，平台默认项，缺省值 `30`） |
| 读取 | `BaseConfigSource.get("tenant.deletion.retention_days", "30")`；非正整数 / 解析失败 → 回落 30 并 `warning`（不阻断注销） |
| 生效 | 改参数即时生效（`sys_config` 自带版本失效），无需重启 |
| 计算 | `purge_at = deletion_requested_at + retention_days`（UTC naive，与库内时间口径一致） |

**归档判定**（`get_archive_policy()` 解析结果）：

| 判定 | 处置 |
| --- | --- |
| provider 为 `null`（`NullArchivePolicy`，当前状态） | **跳过归档，`purge_at` 留空**；注销照常成功；事件不带 `purge_at` |
| provider 非 `null`，有可归档数据且归档成功 | 置 `purge_at` |
| provider 非 `null`，归档失败 | 注销仍成功，`purge_at` 留空 + `error` 日志与告警；不把归档失败变成「注销不可用」 |

**回填**（避免 `purge_at` 长期为空导致永不清理）：

- 定时任务在同一轮里扫 `status = deleted AND purge_at IS NULL`；
- 若此刻归档**已就绪**，回填 `purge_at = now + retention_days`（从现在起算，给足新的保留期），审计留痕；
- 归档仍未就绪则跳过（不置时点，继续等待）。

> 这条回填设计是本任务与「归档执行器未就绪」的官方衔接点：注销先可用，清理倒计时等归档能力就绪后才开始。

### 4.7 物理清理 <a id="purge"></a>

**触发**：定时任务 `tenant.purge.scan`（`BaseTask`，每日一次，`ops/task_scheduler.py --beat` 驱动）

```text
扫描 status = deleted AND purge_at <= now（分批，批大小配置项，缺省 50）
  └─ 逐租户提交作业 tenant.purge（job 参数：tenant_id）
```

**作业** `TenantPurgeJob`（`BaseJobHandler`，`job_type = "tenant.purge"`）：

1. 取注册行；不存在 → `skipped`（幂等：重复执行不重复发事件）；
2. 复核 `status == deleted` 且 `purge_at` 非空且已到 → 不满足则 `skipped`（防止与恢复并发）；
3. 遍历 `enabled_tenant_services()`，逐服务 `drop_database(resolve_target(...))`：库不存在视为成功（`drop_database` 本身幂等）；**单库失败不中断**，记失败服务名继续；
4. 全部成功 → 删除 `sys_tenant_database` 对照行与 `sys_tenant` 注册行（复用 `delete_provisioning` 的删法），同事务 `enqueue_event("tenant.purged")`，提交；
5. 有失败 → **不删注册行**（否则丢掉重试依据），作业置失败并带失败服务清单，交作业框架重试；超限进死信并告警；
6. 审计：`sys.operation.logged`（actor = 触发者；系统触发记 `system`），载荷含 `tenant_id`、`dropped_services`、`failed_services`、耗时。

**并发与安全**：

- 与「恢复」互斥：作业在步骤 2 复核状态，恢复会把 `status` 改回 `active` 并清 `purge_at`，作业随即 `skipped`；数据库层以乐观锁版本（`SysTenant.version`）兜底，冲突即重试。
- 与「注销」互斥：重复注销在状态校验处即 82003。
- 作业**不跨服务写库**：删的是各服务的租户库（运维通道语义），走 `drop_database` 而非业务仓储；平台库内的注册行删除只在 tenant 服务自己的平台库。
- 清理结果**不新增表**：落作业执行记录（`jobs` 框架已有 job 记录与进度）+ `tenant.purged` 事件 + 审计日志。任务书要求「留痕可查」，这三处已够，避免再开一张 `sys_tenant_purge_log`。

### 4.8 产品侧清理契约 <a id="product"></a>

| 事件 | 产品应做 | 产品**不得**做 |
| --- | --- | --- |
| `tenant.deleted` | 停写（拒收新消息 / 拒绝写接口）、保留全部数据、可置只读；记下 `purge_at`（若有） | 删除任何租户数据、删除租户库 |
| `tenant.activated`（恢复） | 恢复写入 | — |
| `tenant.purged` | 删除该租户数据（按 `tenant_id` 定位；可删表数据或整库），幂等 | 依赖平台再次通知（只发一次，靠消费重试保证） |

- 消费组由产品自持声明（`event_consumer_records()`），订阅 `tenant.deleted` / `tenant.purged`，强有序（按 `tenant_id` 分区）。
- **基座端口随本任务扩展**：`TENANT_LIFECYCLE_EVENT_TYPES` 增 `tenant.purged → purged`；`BaseTenantResourceHandler` 增 `on_purged(context)`（**缺省 no-op + WARNING**，与 `null` 端口同口径——未实现的产品不会因新事件直接崩，但会留下可发现的告警）。否则产品侧无法经统一分发器消费 `purged`，只能各自绕过基座。
- 失败重试：消费框架指数退避 → 死信落库 + 告警；产品侧删除实现须幂等（重复消费不报错）。
- **msg 同批改造**：消费组 `msg-tenant-lifecycle`；`tenant.deleted` → 置租户为「已注销」、拒收拒发、清易失资源（**不排定数据清理**）；`tenant.purged` → 删该租户主题 / 分区 / 消息存储数据。与 `04_03` 同窗口提交，并补跨仓契约用例（msg `05-5` 设计 §4 / §6 / §15 同步改口径）。

### 4.11 管理面只读放行口（07 §7 第 58 项，本任务纳入） <a id="readonly"></a>

**问题**：租户守卫对 `suspended` 一律抛 `TenantSuspendedError`（`tenant/guard.py:146`），`deleted` 之后同样拒；产品管理面（主题列表 / 用量 / 清理进度）在保留期内取不到任何数据，「保留期可恢复」在产品侧不可用，msg `05-5` 只能按缺口登记、不敢硬绕守卫。

**判据（三条件同时成立才放行，缺一即拒）**：

| # | 条件 | 说明 |
| --- | --- | --- |
| 1 | 请求方法 ∈ `{GET, HEAD}` | 写方法永不进只读通道；不按业务语义判断「是不是查询」 |
| 2 | 路径命中本服务登记的只读前缀 | `[tenant_guard].readonly_routes`（形如 `"msg:/api/v1/msg/admin/"`，`服务键:路径前缀`；**缺省空列表 = 一条不放行**，fail-closed） |
| 3 | 租户状态 ∈ `{suspended, deleted}` 且注册行仍在 | 物理清理后注册行不存在 → 走既有「未知租户」（`80001` / 404），不放行 |

**实现形态（基座，产品零改判定逻辑）**：

- `BaseTenantGuard.require()` / `per_round()` / `batch()` 增关键字参数 `readonly: bool = False`；`readonly=True` 时 `resolve()` 对 `suspended` / `deleted` 不抛错，改为**返回上下文**（`TenantContext.status` 已是现有字段，透出 `suspended` / `deleted` 供产品判定展示口径），`verify()` 仍照常调用（产品扩展校验不跳过）。
- HTTP 侧由租户中间件按上表三条件置 `readonly=True`；未命中白名单的请求保持现状（`80002` / 403）。
- 只读不放宽鉴权：仍走权限码判定与租户上下文解析，**只是跳过「停用 / 注销即拒」**这一条。
- 放行命中记 `tenant_readonly_access` 结构化日志（`tenant`、`path`、`status`），便于事后核对「谁在只读窗口里看了什么」；不写操作审计（与普通 GET 同口径）。

**边界**：`#59`（TCP / h2 连接应用层强关）**不在本任务**，维持归部署 / 基座另立；本任务只解「读得到」，不解「连着的长连接怎么断」。

7. 接口层（两个端点；停用编排抽公共函数复用）；
8. 只读放行口（§4.11）：`TenantGuardSettings.readonly_routes` + `require(readonly=True)` + 中间件置位；
9. 清理：`tenant_purge.py` 编排 + `TenantPurgeJob` + `TenantPurgeScanTask`；
10. 前端（**先补原型**，再实现 §4.10）；
11. 登记回写（概要 25、架构 12、09 事件清单、计划表）→ 实施 / 测试记录 → 提交。

**前置与阻塞**：

- 归档执行器（审计合规模块，计划 §7 第 32 项）未就绪 → **不阻塞**本任务（§4.6 已定「跳过 + 回填」），但「注销前归档」要到它就绪后才真正生效。
- 前端原型未补 → 阻塞步骤 10（不阻塞 1~9）。
- 用例编号先登记后编码（Kiwi），按子任务分配：`-01` 用例 1~12、18~23（含只读放行 21~23）；`-02` 用例 13~17；`-03` 前端交互沿用 19 的契约断言、不新增后端用例。

## 10. 决策确认 <a id="decisions"></a>

| # | 待决项 | 结论 |
| --- | --- | --- |
| 1 | 交付范围 | 设计 + 实施，拆 3 个子任务（`-01` 契约与端点、`-02` 清理作业、`-03` 前端）；前端先补原型（前置见 §8） |

| 4 | 物理清理触发 | 定时任务每日扫描 + 逐租户清理作业（自动） |

| 8 | 归档未就绪 | 允许注销、**不置 `purge_at`**；就绪后回填 |
| 9 | 事件版本 | `tenant.deleted` **留租户事件族**（`2.1.0` 已登记，只增可选 `purge_at` / `reason` → 升 `2.2.0`）；`tenant.purged` 独立 `1.0.0`（2026-11-08 取代「两条独立 1.0.0」） |

| 11 | 注销即时性 | 即时生效（引擎回收 + 会话撤销 + 登录拦截），与停用同口径 |

| 13 | 清理失败处置 | 不删注册行、作业重试、告警；不新增清理日志表 |
| 14 | 进度回写 | 只在计划表回写；设计完成不等于任务完成，按子任务逐个回写 |
| 15 | 契约口径冲突处置 | 沿用已交付的租户事件族，不重立 `1.0.0`：另立会造成版本回退（硬校验直接拒）与订阅方双升；追加字段保持**可选**（2026-11-08） |

| 18 | 任务拆分 | 3 个子任务：`-01` 契约统一与注销 / 恢复端点（含只读放行）、`-02` 清理作业与定时扫描、`-03` 前端注销与恢复（先补原型）（2026-11-08） |
