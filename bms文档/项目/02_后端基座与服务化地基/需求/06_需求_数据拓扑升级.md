## 1. 域说明 <a id="intro"></a>

本域对应阶段二「数据拓扑升级」：把数据拓扑由「平台库 + 租户库」升级为**每服务独立库 × 每租户**（database-per-service），并落地多服务多库的建库 / 迁移编排与按服务的连接预算。**域内顺序**：先由 06-3 定平台层表归属并解开共享基座库对平台库的直读（前置），再由 06-1 落每服务每租户建库与路由，最后 06-2 落多服务多库迁移编排与按服务连接预算。

**依据**：《微服务演进规划》「设计原则」「服务化地基要求与门禁」（S1 / S2）；《架构设计 · 数据架构》「数据分布」「数据规范」「迁移策略」节；《架构设计 · 多租户路由》「引擎注册表与生命周期」「三库命名与建库标准」节。**目标**：平台层表归属唯一且可校验；每服务每租户一库可建、可路由、可迁移；连接预算按服务分别核算；租户解析链对主机名与来源值形态健壮（不因请求侧脏值产出非法库名或 5xx）。

**域内追加（2026-09-24）**：06-4 由 09_03 契约冒烟命中另立（GitLab Issue #47），收口租户解析链的形态健壮性（IP 字面量主机名不入子域名解析、来源值形态校验与兜底不冒泡 5xx）；同时在其任务内把 `contract-smoke-<服务>` 由非阻断改为阻断，使接口正确性门禁真正生效。

## 2. 需求 06-1：每服务每租户建库与路由 <a id="r06-1"></a>

优先级：2（高）

**背景与动机**：database-per-service 是微服务的硬定义与数据所有权根基；阶段一「一租户一库」需升级为「每服务每租户一库」，且每服务只路由到自身库。

**内容**（《架构设计 · 数据架构》「数据分布」节、《架构设计 · 多租户路由》「引擎注册表与生命周期」节）：

1. 库命名：平台服务库 `bms_{service}`、服务租户库 `bms_{service}_{tenant}`、归档库沿用；建库字符集口径沿用（MySQL utf8mb4 / PG UTF8 / 达梦 UTF8）。
2. 建库流程：租户开通按服务建库（每服务一库）；平台服务库与服务租户库分别管理。
3. 路由：每个服务只持自身库引擎（平台服务库 + 该服务租户库）；租户上下文经解析链传入数据访问层。
4. 数据边界：禁止访问他服务数据库；跨服务读经契约 / 事件或只读投影。

**完成标准**：按服务建库成功且命名合规；每服务只路由到自身库（越界被拒）；租户隔离用例通过；`pytest` / `ruff` / `pyright` 全绿。

**参考文档**：《架构设计 · 数据架构》「数据分布」节；《架构设计 · 多租户路由》「三库命名与建库标准」节

## 3. 需求 06-2：多服务多库迁移编排与连接预算按服务 <a id="r06-2"></a>

优先级：2（高）

**背景与动机**：库数量随「服务 × 租户」乘法增长，手工迁移不可行；连接数也需按服务核算，避免单库连接被打满。

**内容**（《架构设计 · 数据架构》「迁移策略」节、《架构设计 · 性能与安全》「部署规模与连接规划」节）：

1. 迁移编排：Alembic 按**服务 × 数据源**维护迁移；批量迁移遍历「服务 × 租户」逐库幂等执行；新服务 / 新租户开通自动执行对应迁移。
2. 幂等与演练：重复执行结果一致；演练按方言建库 → 迁移 → 校验 → 清理。
3. 连接预算：按服务分别核算（该服务 worker × (pool_size + max_overflow) ≤ 该服务库 max_connections 的 70%）；活跃租户懒加载与闲置回收。
4. 库数量治理：记录并监控库数量增长，必要时评估分库策略（不锁死）。

**完成标准**：多服务多库批量迁移幂等且可演练；连接预算按服务生效；库数量可观测；`pytest` / `ruff` / `pyright` 全绿。

**参考文档**：《架构设计 · 数据架构》「迁移策略」节；《架构设计 · 性能与安全》「部署规模与连接规划」节

## 4. 需求 06-3：平台层表归属与按服务拆分 <a id="r06-3"></a>

优先级：2（高）

**背景与动机**：`sys_` 前缀自阶段一起按「共享前缀」放行，平台层表的**服务归属始终未定案**，形成三次顺延：02_01 列为开放项 → 02_03 归 03_01 → 03_01 归本需求域 → 05_02 归独立任务。后果是「每服务独立库 × 每租户」在平台库维度无法落地：平台库一旦按服务拆分，非租户服务读不到 `sys_tenant`（租户解析失效）、非 platform 服务启动期读不到 `sys_module`（接库校验失效）；共享基座库 `bms_core` 内有 5 处运行时实现正按「固定平台库」直读（租户源 / 服务目录仓储与启动校验 / 发件箱投递器 / 健康探针 / 启动期自动建表）。本需求先把归属与实现落定，使 06-1 的库拆分不再受阻。

**内容**（《架构设计 · 数据架构》「数据分布」「数据规范」节、《架构设计 · 多租户路由》「三库命名与建库标准」节、《微服务演进规划》「服务化地基要求与门禁」S1 / S2）：

1. 表归属定案：平台层表（`sys_*`）逐表登记**唯一服务归属**（含尚未建设服务的占位归属），服务目录、数据库设计总览与表文件三处一致；静态硬校验的「共享前缀」由前缀级放行收窄为**表级归属**（未登记或跨服务引用即拒）。
2. 实现迁出：`sys_tenant`（租户注册）与 `sys_module` / `sys_module_i18n`（服务目录）的模型与落库实现在共享基座库 `bms_core` 内不再直读，按归属迁至所属服务。
3. 跨服务读出口：服务不直读他服务的平台层数据——租户上下文以**网关注入身份头为主 + 服务侧缓存 + 版本键失效**；缓存未命中或需权威数据时经服务契约取数（超时与降级口径与同步调用一致）。
4. 迁移链按服务分链：Alembic 链由「数据源」扩为「**服务 × 数据源**」，各服务平台服务库与服务租户库分别取链、可独立迁移。

**完成标准**：平台层每张表有唯一服务归属且校验生效（未登记 / 跨服务引用被拒）；`bms_core` 内无平台层表直读；租户解析与停用 / 改名失效即时生效（不再直读平台库）；迁移链按「服务 × 数据源」可取、可分链执行；`pytest` / `ruff` / `pyright` 全绿。

**参考文档**：《架构设计 · 数据架构》「数据分布」「数据规范」节；《架构设计 · 多租户路由》「三库命名与建库标准」节；《微服务演进规划》「服务化地基要求与门禁」节

> 本需求为阶段二 06_03 专项（2026-09-23 决策确认）：因平台库共享问题已三次顺延，经专项讨论定案「表归属 → 逐表迁出 → 拆库」路线，本需求承担前两步与迁移链分链，平台服务库的最终拆分由需求 06-1 承接（06_01 真实拆库）。

## 5. 需求 06-4：租户解析与库键派生健壮性 <a id="r06-4"></a>

优先级：2（高）

**背景与动机**：09_03 契约冒烟（`contract-smoke-<服务>`）在 `BMS_ENV=dev`/SQLite 下实测命中 **7 处 5xx**（platform：`GET /api/v1/dicts/{dict_type}`、`/api/v1/dicts/{dict_type}/attrs`、`/api/v1/outbox/dead-letters`、`/api/v1/outbox/dead-letters/{dead_letter_id}`、`/api/v1/query-schemes`、`/api/v1/query-schemes/default`、`/api/v1/query-schemes/{scheme_id}`），错误文案一律为 `库名形态非法：bms_platform_127.0.0.1`。根因与「dev 未迁移表 / 无 Redis 依赖」无关：租户解析链把 **IP 字面量主机名**（`Host: 127.0.0.1:8000`，恰好四段）当成「带子域名的租户域名」，进而在租户注册契约不可达时把该值**原样当作租户编码**构造兜底上下文，派生库名 `bms_platform_127.0.0.1` 形态非法 → `ConfigError` 冒泡为 500。后果有二：① 本地 / CI / Compose 直连（IP 或 `localhost`）一律污染租户解析，dev 环境接口可用性失真；② 契约冒烟因噪声 5xx 只能保持**非阻断**，「破坏性变更拦截」之外的接口正确性门禁形同虚设。

**内容**（《架构设计 · 多租户路由》「租户解析链」「三库命名与建库标准」节、《架构设计 · 数据架构》「数据分布」节）：

1. 主机名判定：带端口 / IPv6 方括号归一后识别 **IP 字面量**（IPv4 / IPv6）与 `localhost`，均**不进入**子域名解析；其余按「≥ 三段且各标签形态合法」判定，形态非法同样不进入解析。
2. 来源值形态校验：`X-Tenant-ID`、token 租户位与子域名映射值先过**编码形态**（`^[A-Za-z][A-Za-z0-9_]{0,63}$`，与 `sys_tenant.code` 字段口径一致）与**域名形态**校验；形态非法视为**未命中**（等同未提供来源），不送入租户源取数。
3. 兜底收口：租户源兜底仅在「来源值可作租户编码」时构造上下文；不可用的兜底值视为未命中并按 **4xx**（`TenantNotFoundError` → 404 / 80001）返回，**不得由请求侧脏值触发 5xx**。
4. 既有口径不变：无来源仍按 `[tenant].allow_demo_fallback` 回落演示租户（dev / test）/ 拒绝（prod）；契约不可达的降级口径（503）不变；库名与库键派生规则（`tenant_{service}_{code}` → `bms_{service}_{code}`）不变。
5. 门禁转阻断：dev 环境契约冒烟零 5xx 后，`contract-smoke-<服务>` 由 `allow_failure: true` 改为**阻断**。

**完成标准**：IP 字面量 / `localhost` 主机名不进入租户解析；形态非法的来源值不触发 5xx（dev / test 回落演示租户、prod 返 4xx）；dev 环境 platform 公开契约全 GET 端点零 5xx（**真实流水线 `contract-smoke-platform` 实证**），其余启用服务以同一基座能力与本地同口径抽验通过；`contract-smoke-<服务>` 为阻断 job（护栏用例断言 `allow_failure` 不出现）；`pytest` / `ruff` / `pyright` 全绿。

**参考文档**：《架构设计 · 多租户路由》「租户解析链」「三库命名与建库标准」节；《架构设计 · 数据架构》「数据分布」节；《契约门禁与契约测试使用说明》；《后端基类清单》「数据访问与多租户基座」节
