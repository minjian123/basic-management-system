## 2. 需求 05-1：服务契约与同步调用规范 <a id="r05-1"></a>

优先级：2（高）

**背景与动机**：服务间同步调用若无统一契约与韧性控制，调用链会放大延迟与故障；契约若不可追踪，破坏性变更会静默打断消费方。

**内容**（《架构设计 · 服务间通信与分布式一致性》「服务边界与契约」「同步调用」节）：

1. 公开契约：每服务维护唯一公开契约（OpenAPI），作为服务间唯一访问面；禁止跨服务访问内部实现。
2. 同步调用韧性：服务间调用封装统一设显式超时 / 重试 / 熔断降级 / 限流（复用基座）；服务间调用不经网关。
3. 契约快照：契约快照入 CI（与 [09_需求_多服务CI-CD与契约门禁](09_需求_多服务CI-CD与契约门禁.md) 衔接）。
4. 调用规范：只经公开契约调用、不直读他库；跨服务读经契约返回 DTO 或本地只读投影。

**完成标准**：服务间调用经公开契约且超时 / 重试 / 熔断可证；契约快照可导出；禁止内部实现访问可校验；`pytest` / `ruff` / `pyright` 全绿。

**参考文档**：《架构设计 · 服务间通信与分布式一致性》「服务边界与契约」「同步调用」节；《架构设计 · 接口与集成》「服务间通信与契约」节

## 3. 需求 05-2：数据所有权与读侧出口 + 服务边界硬校验 <a id="r05-2"></a>

优先级：2（高）

**背景与动机**：数据所有权靠纪律无法持久，须把边界变成构建失败；否则跨服务直写 / 跨库 JOIN 会退化为分布式单体。

**内容**（《架构设计 · 数据架构》「数据规范」节、《架构设计 · 服务间通信与分布式一致性》「服务边界与契约」节）：

1. 数据所有权：每份数据的写方唯一归属某服务；跨服务读经契约 / 事件或**只读投影**，禁止跨服务直写、共享 ORM 关系与跨库 JOIN。
2. 边界硬校验：CI 检查禁止跨服务 import 内部实现、禁止跨服务库访问（越界即失败）。
3. 读侧出口：跨服务报表 / 聚合经只读投影或数据查询提供者，不直接读他库；例外登记。
4. 度量：服务边界越界数、跨库访问数纳入阶段度量（与 [09_需求_多服务CI-CD与契约门禁](09_需求_多服务CI-CD与契约门禁.md) 衔接）。

**完成标准**：边界硬校验可拦截跨服务 import 与跨库访问（越界即 CI 失败）；读侧出口用例通过；所有权纪律可度量；`pytest` / `ruff` / `pyright` 全绿。

**参考文档**：《架构设计 · 数据架构》「数据规范」节；《后端开发规范》「模块边界与数据所有权」节

## 4. 需求 05-3：事务性 Outbox 与幂等消费 <a id="r05-3"></a>

优先级：2（高）

**背景与动机**：「本地事务提交」与「事件发布」无法原子是跨服务不一致的根因；需以事务性发件箱保证库↔事件原子，并以幂等消费收敛至少一次投递。

**内容**（《架构设计 · 事件总线》「生产一致性」节、《架构设计 · 服务间通信与分布式一致性》「事务性 Outbox」「幂等与重放」节）：

1. `sys_outbox` 表与投递器：业务事务内同库同事务写事件；投递器（轮询）转发到 RocketMQ 并标记已投递（后续可切 CDC）。
2. 幂等消费：消费者维护「已处理事件」（consumer + event_id 唯一），与业务副作用同事务写入，命中唯一键即跳过。
3. 顺序与重放：同聚合按序投递（顺序消息）；Outbox 作为事件账本可重放；死信进看板人工处理。
4. 业务幂等：写接口支持幂等键（Redis SETNX 前置 + 唯一约束兜底）。

**完成标准**：库↔事件原子用例通过（事务回滚不发事件）；投递器转发与标记正确；消费幂等去重用例通过；重放安全；`pytest` / `ruff` / `pyright` 全绿。

**参考文档**：《架构设计 · 事件总线》「生产一致性」「幂等与重试」节；《架构设计 · 服务间通信与分布式一致性》「事务性 Outbox」节

## 5. 需求 05-4：事件契约版本与 Saga / 补偿基座 <a id="r05-4"></a>

优先级：3（中）

**背景与动机**：事件是长期契约，字段变更须可控；跨服务流程在部分完成不可接受时需补偿机制，但强一致场景有限，按需建设即可。

**内容**（《架构设计 · 事件总线》「幂等与重试」节、《架构设计 · 服务间通信与分布式一致性》「跨服务一致性（Saga / 补偿）」节）：

1. 事件契约版本：字段只增不删、新增可选、破坏性变更升版本；消费方按订阅做新旧兼容。
2. Saga / 补偿基座：提供事件驱动协同与补偿的基座语义（本地事务 + 事件 + 补偿动作，补偿幂等）；编排式运行时（Temporal）按判据再引入，不在本阶段强制接入。
3. 强一致场景口径：审计哈希链按 `(service, tenant)` 分条、服务内本地强一致；财务类收敛到单一账务服务；**排除 2PC / XA**。

**完成标准**：事件契约版本规则落地（兼容用例可证）；Saga / 补偿基座语义就位并可被消费方使用；强一致场景口径成文并与实现一致；`pytest` / `ruff` / `pyright` 全绿。

**参考文档**：《架构设计 · 服务间通信与分布式一致性》「跨服务一致性（Saga / 补偿）」「强一致场景处理」节；知识档案《[微服务 · 09 渐进式演进](../../../资料/知识档案/微服务/09_微服务_渐进式演进.md)》

## 6. 需求 05-5：分布式事务能力（达梦 XA 方言 / 三库 2PC / 跨服务 TM） <a id="r05-5"></a>

优先级：2（高）

**背景与动机**：部分跨库写要求「要么全成功要么全失败」（如结构化权限的「角色 + 用户/岗位/部门分配 + 权限项」），而平台基线「本地事务 + Outbox + 幂等」只保证最终一致、无法跨库原子。2026-10-06 真库实测澄清：三库**服务器**均支持 XA（达梦 `DBMS_XA` 包、MySQL `XA`、PostgreSQL `PREPARE TRANSACTION`），受限在**应用驱动层**——达梦 `dmSQLAlchemy` 同步方言未接 `DBMS_XA`、MySQL / PostgreSQL 的 SQLAlchemy 异步 API 不暴露 `begin_twophase`。本需求为达梦补齐 XA 驱动能力，并评估三库 2PC 与跨服务协调（TM）的完整方案。

**内容**：

1. **达梦 XA 自定义方言**：纯 Python 方言（继承 `dmSQLAlchemy` 同步方言），将 `do_begin / prepare / commit / rollback / recover_twophase` 接服务器端 `DBMS_XA` 包；经 SQLAlchemy 方言注册表登记（**不改编译驱动 `dmPython`**）；`Connection.begin_twophase()` 可用（需 `XA_COMPATIBLE_MODE≠2`）。
2. **三库 2PC 可行性**：同步引擎下单进程跨库 2PC（MySQL × PostgreSQL 已实测通过、达梦补方言后可用）；明确 PostgreSQL 需 `max_prepared_transactions>0`；异步 API 限制与规避（2PC 走同步引擎）。
3. **跨服务协调（TM）评估**：面向「结构化权限保存原子」场景，评估外部 TM + 各服务 XA / 单进程多库 / 权限数据单库三条路线，产出结论与推荐。
4. **口径登记**：据实测回写《[数据库设计 · 方言特性](../../../设计/数据库设计/方言特性/03_DM8.md)》「事务与连接」节与《[架构设计 · 服务间通信与分布式一致性](../../../设计/架构设计/37_架构设计_子系统_服务间通信与一致性.md)》《[后端开发规范](../../../规范/后端开发规范.md)》的 2PC 口径。

**完成标准**：达梦 XA 方言落地（`begin_twophase` 提交 / 回滚用例通过、方言注册与文档登记）；三库 2PC 可行性实测结论成文；跨服务 TM 评估结论与推荐成文；`pytest` / `ruff` / `pyright` 全绿。

**参考文档**：需求 [05-4](#r05-4)；《架构设计 · 服务间通信与分布式一致性》「事务性 Outbox」「跨服务一致性」节；《数据库设计 · 方言特性》三库「事务与连接」节；达梦《DBMS_XA 包》《DM XA 编程指南》
