## 1. 域说明 <a id="intro"></a>

本域对应阶段二「平台模型下沉基座」：把**跨服务共用**的 ORM 模型（菜单 / 角色 / 用户）从平台服务 `bms_platform.models` 下沉到共享基座 `bms_core`，消除「非平台服务为读共享表而依赖平台服务源码」的隐式耦合。

**依据**：《[平台可扩展性规划](../../../规划/平台可扩展性规划.md)》三层分层模型（基座只提供机制、平台不自营业务）；《[后端开发规范](../../../规范/后端开发规范.md)》分层依赖口径；《[数据库开发规范](../../../规范/数据库开发规范.md)》「与数据库设计的关联与事实源」节。

**问题来源（实测）**：流水线 1188 的 `contract-smoke-tenant` 失败——tenant 服务镜像启动即 `ModuleNotFoundError: No module named 'bms_platform'`。导入链为：

```text
bms_tenant/services/provisioning.py:25  →  ops.tenant_provisioning
ops/tenant_provisioning.py              →  ops.seed_platform / seed_rbac / seed_user
ops/seed_platform.py:30                 →  bms_platform.models.{menu,role,user}
```

而服务镜像按设计只装目标服务源码（`backend/Dockerfile` 仅 COPY `libs/bms_core/src` 与 `services/${SERVICE}/src`），不含其他服务源码。**该缺陷此前被 CVE 门禁失败掩盖**（镜像从未跑到冒烟阶段），门禁转绿后暴露。

**耦合面实测**：`ops/` 下共 7 个文件导入 `bms_platform`（`check_modules` / `check_plugins` / `seed_menu` / `seed_module` / `seed_platform` / `seed_rbac` / `seed_user`）；全仓 `bms_platform.models.{menu,role,user}` 引用 **58 个文件 / 80 处**。

**可行性实测**：`models/menu.py`、`role.py`、`user.py` 三个模型文件**只依赖 `bms_core`，无任何 `bms_platform` 内部导入**，下沉在技术上成立。

**目标**：服务镜像不再因共享表模型而依赖其他服务源码；`ops` 种子与编排模块只依赖基座；表归属、契约快照、迁移链在迁移后零漂移。

## 2. 需求 14-1：共享模型下沉基座 <a id="r14-1"></a>

优先级：2（高）

**背景与动机**：菜单 / 角色 / 用户三张表是**平台库共享表**，被 platform 服务自身、`ops` 运维脚本（建库种子 / 租户开通编排）以及其他服务的开通链路共同读写。当前这些模型物理位于 `services/platform/src/bms_platform/models/`，导致任何要读写共享表的模块都必须依赖平台服务源码，与「服务独立构建、镜像只装本服务源码」的部署口径直接冲突。

**内容**：

1. **模型迁移**：`models/menu.py`、`models/role.py`、`models/user.py` 迁至 `backend/libs/bms_core/src/bms_core/models/`（命名遵循《命名规范》），模型定义与表名 / 表前缀 / 字段**保持不变**，仅改变导入路径。
2. **导入路径同步**：全仓 58 个文件 / 80 处引用改为新路径；`bms_platform.models` 保留转发模块（re-export）以免存量引用一次性断裂，转发层标注为过渡、并在后续清理。
3. **`ops` 依赖收口**：`ops/` 下 7 个文件的 `bms_platform` 导入改为基座路径；`check_plugins.py` 对 `bms_platform.main` 的依赖属**校验职责**（需实例化平台应用），保留并显式声明为例外。
4. **服务依赖声明**：`bms_core` 的 `pyproject.toml` 补齐模型所需依赖；各服务 `pyproject.toml` 不新增服务间源码依赖。

**完成标准**：tenant 等服务镜像启动无 `ModuleNotFoundError`；`ops` 下除 `check_plugins`（显式例外）外无 `bms_platform` 导入；全仓 `bms_platform.models.{menu,role,user}` 直接引用归零（经转发层过渡者计入待清理清单）；`uv sync --frozen` 与全量测试通过。

**参考文档**：《[平台可扩展性规划](../../../规划/平台可扩展性规划.md)》「总体模型：基座 + 平台 + 多产品三层分层」节；《[后端开发规范](../../../规范/后端开发规范.md)》分层依赖节

## 3. 需求 14-2：表归属与契约登记同步 <a id="r14-2"></a>

优先级：2（高）

**背景与动机**：模型下沉改变了 ORM 类的**所属 Python 包**，而表登记（表文件 / 总览状态）、契约快照（OpenAPI / 事件契约）、迁移链（Alembic 自动建表按服务模型包发现）均以包路径为发现依据。若不同步，表现为「表归属校验失败」「契约快照漂移」「启动期自动建表漏表」。

**内容**：

1. **表登记同步**：核对三张表的表文件「归属服务 / 模块」字段，下沉后归属标注为基座共享，并同步总览登记状态（两处一致）。
2. **自动建表发现口径**：核对 `bms_core.db.migration` 与 `ops.init_schema` 的模型包发现逻辑，确保基座 `bms_core.models` 被纳入扫描，不因迁包而漏表。
3. **契约与快照**：`ops.contract_snapshot check`、`ops.event_contracts check`、`ops.check_contracts`、`ops.check_tables` 全部零漂移；必要时按规范重新导出归档。
4. **迁移链**：确认 Alembic 建表链路在迁包后仍可完整建出三张表（历史迁移脚本已清空、机制保留，按新基线重建时走迁移路径）。

**完成标准**：`check_tables` / `contract_snapshot check` / `event_contracts check` / `check_contracts` 全部通过且零漂移；启动期自动建表与 `ops.init_schema` 均能建出三张表；表登记两处一致。

**参考文档**：《[数据库开发规范](../../../规范/数据库开发规范.md)》「与数据库设计的关联与事实源」节；《[API接口规范](../../../规范/API接口规范.md)》

## 4. 需求 14-3：门禁固化与服务镜像边界校验 <a id="r14-3"></a>

优先级：3（中）

**背景与动机**：本次缺陷的根因是**导入链跨服务**，但既有护栏没有在任何早期环节拦住它——静态检查、单元测试、镜像构建都通过，只有容器真正启动才暴露。同类问题会在下一个服务上重演。

**内容**：

1. **导入边界断言**：新增护栏用例，断言「非平台服务的运行期代码（`services/*/src`）不得导入 `bms_platform`」，并断言 `ops` 的导入闭包不引入非基座服务源码；例外清单显式登记并注明理由。
2. **镜像启动自检**：服务镜像构建后增加「`python -c "import <服务入口模块>"`」式冒烟（或在 `service-build` 阶段加一步导入检查），把「镜像缺模块」从运行时前移到构建期。
3. **冒烟门禁说明**：`contract-smoke` 的失败语义与镜像边界的关系写入《[部署发布规范](../../../规范/部署发布规范.md)》，明确「冒烟失败先看容器启动诊断」。

**完成标准**：护栏用例可复现本次缺陷（在修复前版本上失败、修复后通过）；`service-build` 具备导入自检；规范文档补入对应小节；护栏自身有 `--self-test`。

**参考文档**：《[测试规范](../../../规范/测试规范.md)》；《[部署发布规范](../../../规范/部署发布规范.md)》；《[代码评审规范](../../../规范/代码评审规范.md)》
