## 1. 域说明 <a id="intro"></a>

本域对应阶段二「平台模型下沉基座」：把**跨服务共用**的 ORM 模型从各服务（`bms_platform.models` / `bms_identity.models` / `bms_tenant.models`）整包下沉到共享基座 `bms_core.models`，并把被运行期代码依赖的**租户开通编排内核**同步下沉，消除「非本服务代码为读写共享表而依赖其他服务源码」的隐式耦合。

**依据**：《[平台可扩展性规划](../../../规划/平台可扩展性规划.md)》三层分层模型（基座只提供机制、平台不自营业务）；《[后端开发规范](../../../规范/后端开发规范.md)》分层依赖口径；《[数据库开发规范](../../../规范/数据库开发规范.md)》「与数据库设计的关联与事实源」节。

**问题来源（实测）**：流水线 1188 的 `contract-smoke-tenant` 失败——tenant 服务镜像启动即 `ModuleNotFoundError: No module named 'bms_platform'`。导入链为：

```text
bms_tenant/main.py:11              → services/platform_tenant
services/platform_tenant.py:23     → ops.tenant_provisioning
ops/tenant_provisioning.py:37-40   → ops.seed_platform / seed_rbac / seed_sso / seed_user
ops/seed_platform.py:30            → bms_platform.models.{menu,role,user}
ops/seed_sso.py:34-35              → bms_identity.models.{identity_provider,user_identity}
```

而服务镜像按设计只装目标服务源码（`backend/Dockerfile:51-52` 仅 COPY `libs/bms_core/src` 与 `services/${SERVICE}/src`，另加 `alembic` 与 `ops`），不含其他服务源码。**该缺陷此前被 CVE 门禁失败掩盖**（镜像从未跑到冒烟阶段），门禁转绿后暴露。

**耦合面实测（2026-10-22 全仓扫描）**：

- `services/*/src` 之间**零跨服务 Python 导入**（跨服务协作已全部走 `bms_core.servicecall`），`bms_core` 对服务包**零静态导入**（仅 `db/migration.py` 的 `importlib` 动态发现）——边界只有两处不干净；
- **`ops/` 下 13 个脚本跨包导入服务源码**：`seed_platform` / `seed_rbac` / `seed_menu` / `seed_user` / `seed_module`（`bms_platform.models`）、`seed_sso` / `seed_oidc_client`（`bms_identity.models`）、`seed_tenant` / `migrate_tenants`（`bms_tenant.models`，惰性）、`bootstrap_platform`（`bms_tenant.services`×4）、`check_modules`（`bms_platform.repositories`×2）、`check_plugins`（`bms_platform.main`）、`txn_recovery`（`bms_txn.repositories` / `services`）；
- **反向依赖**：`services/tenant/src` 3 处 import `ops.tenant_provisioning`（`platform_tenant.py:23`、`provisioning.py:25` 为模块级，`api/tenant_admin.py:459` 为函数内惰性）——运维包被运行期代码依赖，是本次镜像崩溃的直接根因；
- 部署侧已用「挑镜像」变通：`scripts/tools/deploy/release.py:684` 注释「种子按『服务包 / 表归属』选运行镜像：seed_module 需 bms_platform；seed_tenant 需 bms_tenant」——隐式耦合未登记、无门禁。

**可行性实测**：`platform.models`（6 文件 / 29 表）、`identity.models`（4 文件 / 4 表）、`tenant.models`（5 文件 / 5 表）共 **17 个模型文件 / 38 张表**，**全部只依赖 sqlalchemy + `bms_core.models.base`，零服务内交叉依赖**（模块级常量如 `ROLE_TYPE_PLATFORM_ADMIN` / `TENANT_KIND_PLATFORM` 随文件迁移），下沉在技术上成立。

**范围界定（判据 = 「是否被非本服务镜像内的代码导入」）**：

- **纳入**：上述三个模型的**整包**（不做逐文件挑拣，避免长期「一半在基座、一半在服务」的混合态）；被运行期代码依赖的开通编排内核与四个种子模块；
- **不纳入**：`txn.models.ledger`（`txn_global*` 为 TM 私有账本，独立库 `bms_txn`，无任何跨包 models 引用，`ops.txn_recovery` 按「声明仅 txn 镜像运行」处理）；`bms_core` 下阶段三 / 四的能力域空目录（按《[AI开发规范](../../../规范/AI开发规范.md)》3.1「明确属后续阶段内部实现的不立项」）；服务内能力单元实现（基类在基座、实现在服务的正常继承形态）。

**目标**：服务镜像不再因共享表模型或开通编排而依赖其他服务源码；`ops` 的跨包依赖显式登记运行镜像并纳入门禁；表归属、契约快照、迁移链在迁移后零漂移。

## 2. 需求 14-1：共享模型整包下沉基座 <a id="r14-1"></a>

优先级：2（高）

**背景与动机**：platform / identity / tenant 三个服务的 `models` 包承载的是**平台库与租户库的共享表模型**（用户 / 角色 / 菜单 / 表单 / 字段 / 服务目录 / 产品 / 租户注册 / 租户库对照 / 租户模块 / 租户配额 / 用户-租户 / 外部身份 / 会话 / 客户端 / 定时任务 / 图标等），被 platform 服务自身、`ops` 运维脚本（建库种子 / 租户开通编排）以及其他服务的开通链路共同读写。这些模型物理位于各服务源码内，导致任何要读写共享表的模块都必须依赖对应服务源码，与「服务独立构建、镜像只装本服务源码」的部署口径直接冲突；且本次 tenant 镜像崩溃只补 3 个平台模型仍修不掉（`ops.seed_sso` 还需 `bms_identity.models`），逐文件挑拣必然反复返工。

**内容**：

1. **整包搬迁**（模型定义、表名、表前缀、字段与模块级常量**保持不变**，仅改变导入路径）：
   - `services/platform/src/bms_platform/models/{menu,role,user,catalog,system,demo}.py` → `backend/libs/bms_core/src/bms_core/models/platform/`（6 文件 / 29 表）；
   - `services/identity/src/bms_identity/models/{client,identity_provider,session,user_identity}.py` → `bms_core/models/identity/`（4 文件 / 4 表）；
   - `services/tenant/src/bms_tenant/models/{tenant,tenant_database,tenant_module,tenant_quota,user_tenant}.py` → `bms_core/models/tenant/`（5 文件 / 5 表）。
   - 目录口径：按**源服务分子包**（`models/{platform,identity,tenant}/`），与基座能力域目录（`permission/` / `tenant/` 等机制域）区分；后续产品服务模型可并行 `models/<product>/`，与需求 12-4「服务包模型名前缀参数化」同构。
2. **引用同步（不保留转发层）**：全仓 **131 处**引用（`bms_platform.models` 80 处 / `bms_identity.models` 29 处 / `bms_tenant.models` 22 处，含服务内 src、`tests_support` 与各服务测试）一次性改到基座新路径；`bms_platform.models` / `bms_identity.models` / `bms_tenant.models` **不保留 re-export 转发模块**（转发层会让「不得导入服务包」的断言失去可验证性）。
3. **模型包登记同步**（两处，漏改即故障）：
   - 源服务 `models` 包**整包删除**（不留空壳、不留转发层）——漏删会双注册同名表，触发 `InvalidRequestError: Table already defined`；随之 `require_service_model_modules()` 的缺失判定**下沉到服务包层级**（服务包在、`models` 子包不在 = 该服务无私有模型，返回空清单；仅服务包缺失才报错）；
   - 基座 `bms_core/db/migration.py` 的 `COMMON_MODEL_MODULES` **加入已搬模块**（由三子包 `MODEL_MODULES` 组合，基座不重复录清单）——漏加则该表进不了任何迁移链，`chain_metadata` 取不到模型、建表静默为 0 表。
4. **`ops` 模型层依赖收口**：`seed_platform` / `seed_rbac` / `seed_menu` / `seed_user` / `seed_module` / `seed_sso` / `seed_oidc_client` / `seed_tenant` / `migrate_tenants` 的模型导入改为基座路径；`check_plugins` 对 `bms_platform.main` 的依赖属**校验职责**（需实例化平台应用），保留并按需求 14-3 显式登记运行镜像为例外。
5. **服务依赖声明**：`bms_core` 的 `pyproject.toml` 补齐模型所需依赖；各服务 `pyproject.toml` 不新增服务间源码依赖。

**完成标准**：三个服务侧 `models` 包**整包删除**（无残留模块、无转发层；服务私有模型才建包，`models` 子包缺失不视为故障）；全仓 **0 处** `from bms_platform.models.*` / `from bms_identity.models.*` / `from bms_tenant.models.*`；`ops` 的**模型层**跨包导入归零（非模型跨包按 14-3 登记运行镜像例外）；`models/{platform,identity,tenant}/` 与 `COMMON_MODEL_MODULES` 一致且能建出 38 张表；tenant 服务镜像启动无 `ModuleNotFoundError`；`uv sync --frozen` 与全量测试通过。

**参考文档**：《[平台可扩展性规划](../../../规划/平台可扩展性规划.md)》「总体模型：基座 + 平台 + 多产品三层分层」节；《[后端开发规范](../../../规范/后端开发规范.md)》分层依赖节；《[后端基类清单](../../../后端基类清单.md)》「共享模型与表归属」相关条目

## 3. 需求 14-2：表归属与契约登记同步 <a id="r14-2"></a>

优先级：2（高）

**背景与动机**：模型下沉改变了 ORM 类的**所属 Python 包**，而表登记（表文件 / 总览状态）、契约快照（OpenAPI / 事件契约）、迁移链（启动期自动建表与 Alembic 按服务模型包发现）均以包路径为发现依据。若不同步，表现为「表归属校验失败」「契约快照漂移」「启动期自动建表漏表」「迁移链缺表」。

**内容**：

1. **表登记同步**：38 张已搬表的表文件「ORM 模型」列改基座共享路径（标注下沉事实）、**表归属（`owner`）与库类别（`datasource`）保持不变**（链归属由 `owner` 派生，改 `owner` 会让表跑到别的链）；同步《数据库设计总览》登记状态（两处一致）。
2. **自动建表发现口径**：核对 `bms_core/db/migration.py` 的 `COMMON_MODEL_MODULES` / `service_model_modules()` 与 `db/bootstrap.py::ensure_service_schema`、`ops/init_schema.py` 的模型包发现逻辑，确保基座 `bms_core.models.{platform,identity,tenant}` 被纳入扫描、`chain_metadata` 交集非空。
3. **契约与快照**：`ops.contract_snapshot check`、`ops.event_contracts check`、`ops.check_contracts`、`ops.check_tables` 全部零漂移；必要时按规范重新导出归档。
4. **迁移链**：确认启动期自动建表、`ops.init_schema` 与 Alembic 建表链路在迁包后均能完整建出 34 张 enabled 共享表（`planned` 不进链；历史迁移脚本已清空、机制保留，按新基线重建时走迁移路径）。

**完成标准**：`check_tables` / `contract_snapshot check` / `event_contracts check` / `check_contracts` 全部通过且零漂移；启动期自动建表与 `ops.init_schema` 均能建出 **34 张 enabled 共享表**（38 张共享表中 4 张为 `planned`，不进链）；表文件、总览登记、目录一致性校验通过且两处状态一致。

**参考文档**：《[数据库开发规范](../../../规范/数据库开发规范.md)》「与数据库设计的关联与事实源」节；《[API接口规范](../../../规范/API接口规范.md)》；`bms_core/services/table_registry.py`（`TABLE_OWNERSHIP` 单一来源）

## 4. 需求 14-3：门禁固化与镜像边界校验 <a id="r14-3"></a>

优先级：3（中）

**背景与动机**：本次缺陷的根因是**导入链跨服务**，但既有护栏没有在任何早期环节拦住它——静态检查、单元测试、镜像构建都通过，只有容器真正启动才暴露。现有 `scripts/tools/base-check/check-service-boundaries.py` 的规则 2 只校验「服务之间不得互相 import」，**全文不检查 `ops/`**（规则不覆盖 `ops`，也不覆盖服务反向依赖 `ops`），因此 identity / tenant / txn 的跨包引用都在门禁之外。同类问题会在下一个服务上重演。

**内容**：

1. **运行镜像声明（机器可读）**：每个 `ops` 脚本在 docstring 与机器可读常量（如 `RUN_IMAGE = "platform" | "tenant" | "txn" | "ci"`）中显式声明「可在哪些镜像 / 环境运行」；未声明的跨包脚本一律失败。当前需登记的例外：`bootstrap_platform`（tenant 镜像）、`check_modules` / `check_plugins`（CI / 开发机全量工作区，无镜像边界）、`txn_recovery`（txn 镜像 / 运维机）、`seed_sso` / `seed_oidc_client`（platform 镜像，模型下沉后不再跨包）。
2. **导入闭包断言**：护栏按「脚本声明的运行镜像所含包 ⊇ 脚本导入闭包所需的服务包」校验（镜像所含包 = `bms_core` + 本服务 + `ops`）；同时断言「非 platform 服务的运行期代码（`services/*/src`）不得导入 `bms_platform`」，且「`services/*/src` 不得导入 `ops`」（本次反向依赖的正面拦截）。
3. **镜像启动自检**：服务镜像构建后增加「`python -c "import <服务入口模块>"`」式冒烟（或在 `service-build` 阶段加一步导入检查），把「镜像缺模块」从运行时前移到构建期。
4. **冒烟门禁说明**：`contract-smoke` 的失败语义与镜像边界的关系写入《[部署发布规范](../../../规范/部署发布规范.md)》，明确「冒烟失败先看容器启动诊断」。
5. **部署侧口径清理**：`scripts/tools/deploy/release.py` 中「按服务包挑镜像」的注释与分支随镜像声明登记改为显式依据，不再靠注释解释。

**完成标准**：护栏用例可复现本次缺陷（在修复前版本上失败、修复后通过）；每个跨包 `ops` 脚本都有机器可读运行镜像声明且断言通过；`services/*/src` 导入 `ops` 的反向依赖归零并有断言；`service-build` 具备导入自检；规范文档补入对应小节；护栏自身有 `--self-test`。

**参考文档**：《[测试规范](../../../规范/测试规范.md)》；《[部署发布规范](../../../规范/部署发布规范.md)》；《[代码评审规范](../../../规范/代码评审规范.md)》；`scripts/tools/base-check/check-service-boundaries.py`（现存七项规则）

## 5. 需求 14-4：开通编排内核下沉基座 <a id="r14-4"></a>

优先级：2（高）

**背景与动机**：tenant 服务在**启动链**上 import 运维包 `ops.tenant_provisioning`（`services/platform_tenant.py:23`、`services/provisioning.py:25` 模块级，`api/tenant_admin.py:459` 函数内惰性），而该内核又模块级导入四个种子脚本、种子脚本再导入 platform / identity 的模型——这是本次镜像崩溃的**直接根因**。运维包（`ops/`）属运维通道，被运行期代码依赖会使「服务独立构建」失效，且靠「挑镜像」与「惰性导入」都只是治标。模型整包下沉后，该内核只依赖 `bms_core`，「开通编排」可成为基座机制供任何服务 / 产品复用。

**内容**：

1. **内核下沉**：`ops/tenant_provisioning.py` → `backend/libs/bms_core/src/bms_core/tenant/provisioning.py`，公开接口（`ProvisionOutcome` / `provision_infrastructure` / `enabled_tenant_services`）与签名**不变**，行为（建库 → 逐链幂等建表 → 批量种子 → 失败逆序清理）不变；落点为**租户能力域**（`bms_core/tenant/` 已有 `base` / `membership` / `source` 等机制），不放 `db/`（`db` 域只放数据库机制，种子含平台内置数据）。
2. **种子下沉**：`ops/seed_platform.py` / `seed_rbac.py` / `seed_sso.py` / `seed_user.py` → `bms_core/tenant/seed/{platform,rbac,sso,user}.py`；种子数据（内置管理员角色与互斥预授、菜单 / 权限码 / 表单、初始系统管理员、默认 IdP 占位、系统参数）内容不变。
3. **调用方切换与 CLI 薄壳**：tenant 三处 import 改基座路径；`ops/` 保留同名 CLI 薄壳（`python -m ops.seed_platform` 等命令、参数与退出码不变），`scripts/tools/deploy/release.py` 的部署命令**零改动**。
4. **依赖方向**：`bms_core/tenant/` 只依赖 `bms_core`（模型整包下沉后成立）；禁止 `bms_core` 反向导入 `ops` 或任何服务包。
5. **口径回写**：《[平台可扩展性规划](../../../规划/平台可扩展性规划.md)》三层模型节补边界——基座可承载「开通所需的默认数据种子」，但**不得承载业务运营逻辑**；《[后端开发规范](../../../规范/后端开发规范.md)》分层依赖节补对应一句。

**完成标准**：tenant 服务镜像启动零跨包（`python -c "import bms_tenant.main"` 通过）；`services/*/src` 对 `ops` 的导入归零；四个 `ops` 种子脚本成为薄壳（仅参数解析 + 调用基座）；`python -m ops.<script>` 与部署脚本行为不回退；`bms_core/tenant/` 无 `ops` / 服务包导入；规划与规范已回写；全量测试与覆盖率门禁通过。

**参考文档**：《[平台可扩展性规划](../../../规划/平台可扩展性规划.md)》「总体模型：基座 + 平台 + 多产品三层分层」节；《[后端开发规范](../../../规范/后端开发规范.md)》「依赖方向」节；《[部署发布规范](../../../规范/部署发布规范.md)》「建表先行与种子」节
