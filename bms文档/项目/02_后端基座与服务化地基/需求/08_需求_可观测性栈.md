## 1. 域说明 <a id="intro"></a>

本域对应阶段二「可观测性栈」：接入 OpenTelemetry 采集与 Tempo（Trace）+ Prometheus / Grafana（指标）+ Loki（日志）标准栈，并按**服务**归因（service.name / version），跨服务问题可定位（服务化地基 S6 / S7）。

**依据**：《微服务演进规划》「服务化地基要求与门禁」（S6 / S7）；《架构设计 · 可观测性》全节；知识档案《[微服务 · 12 选型对比（BMS）](../../../资料/知识档案/微服务/12_微服务_选型对比.md)》。**目标**：Trace / 指标 / 日志三支柱按服务可见；健康检查与就绪就位。

## 2. 需求 08-1：可观测性栈接入 <a id="r08-1"></a>

优先级：2（高）

**背景与动机**：微服务跨服务问题若无全链路追踪与按服务指标即黑盒；阶段一只有单体日志与健康检查，需接入标准可观测栈。

**内容**（《架构设计 · 可观测性》「结构化日志」「指标采集」「链路追踪」节）：

1. 采集：OpenTelemetry SDK + otel-collector，各服务自动埋点（FastAPI / SQLAlchemy / Redis / Celery 等）。
2. Trace 存储：Tempo（OTLP 接入，配置保留期 / TTL）。
3. 指标：Prometheus 采集每服务 `/metrics`；Grafana 统一展示（指标 + 日志 + Trace 数据源）。
4. 日志：Loki（结构化 JSON stdout 采集，携带 trace_id / request_id / service）。
5. 部署：可观测组件随 `deploy` 编排一体（Tempo / Loki / Prometheus / Grafana / otel-collector）。

**完成标准**：服务 Trace 可在 Tempo 查询、指标可在 Grafana 查询、日志可按服务检索；保留期配置就位；本地一键拉起含可观测栈；校验通过。

**参考文档**：《架构设计 · 可观测性》「指标采集」「链路追踪」节；《架构设计 · 部署与运维》「基础设施编排」节

## 3. 需求 08-2：按服务归因与健康就绪 <a id="r08-2"></a>

优先级：2（高）

**背景与动机**：多服务下需按服务定位问题；每服务须暴露健康与就绪供编排与网关探活。

**内容**（《架构设计 · 可观测性》「链路追踪」「健康检查与优雅停机」节）：

1. 按服务归因：span / 指标 / 日志带 `service.name` 与 `service.version` 资源标签；跨服务调用链可定位。
2. 核心链路 SLO：作为告警阈值锚点（性能目标按服务化分档，见《[微服务演进规划](../../../规划/微服务演进规划.md)》）。
3. 健康就绪：每服务 `/healthz` `/readyz`，聚合依赖并豁免统一响应包裹（与 [02_需求_多服务骨架与仓库](02_需求_多服务骨架与仓库.md) 衔接）。
4. 度量与门禁：服务独立发布成功率、契约破坏数、边界越界数等纳入阶段度量（与 [09_需求_多服务CI-CD与契约门禁](09_需求_多服务CI-CD与契约门禁.md) 衔接）。

**完成标准**：跨服务调用链可按服务定位（Trace 贯通）；每服务探针可用；关键度量可采集；校验通过。

**参考文档**：《架构设计 · 可观测性》「链路追踪」「健康检查与优雅停机」节；《架构设计 · 性能与安全》「可用性目标与 SLO」节
