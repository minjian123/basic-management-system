## 1. 域说明 <a id="intro"></a>

本域对应阶段二「API 网关与边缘」：以 Apache APISIX 建立边缘统一入口（路由 / 边缘认证 / 限流 / 灰度 / 边缘观测），standalone 声明式配置入 Git；服务间寻址走 DNS（以服务目录为依据）。

**依据**：《微服务演进规划》「技术选型」「服务化地基要求与门禁」（S4）节；《架构设计 · API 网关与边缘》全节；知识档案《[微服务 · 12 选型对比（BMS）](../../../资料/知识档案/微服务/12_微服务_选型对比.md)》。**目标**：外部流量经网关进入并按服务目录路由；边缘完成认证与请求净化；限流与服务发现可用；前端按服务段寻址接入；网关请求体边界与文件策略一致。

## 2. 需求 04-1：API 网关接入与声明式配置入 Git <a id="r04-1"></a>

优先级：2（高）

**背景与动机**：微服务起步必须有边缘统一入口；网关配置若靠手工控制台维护则不可追溯、不可回归，需声明式入 Git 随流水线热加载。

**内容**（《架构设计 · API 网关与边缘》「部署形态与演进」「边缘功能」节）：

1. APISIX 接入：以 standalone 声明式模式运行（容器化），与 `deploy` 编排一体，本地一键拉起含网关。
2. 声明式配置入 Git：路由 / 上游 / 认证 / 限流规则以声明式配置入仓库，随流水线校验并热加载。
3. 路由以服务目录为依据：网关上游指向各服务（按服务目录登记的服务清单），静态资源由 nginx 托管、与 API 流量分流。
4. 演进预留：配置模型保持可平移至 K8s Ingress / Gateway API（迁 K8s 时不换选型）。

**完成标准**：网关容器随本地一键拉起就位；外部请求经网关按服务路由到目标服务；声明式配置入 Git 且改动经流水线生效；`deploy` 编排含网关；校验通过。

**参考文档**：《架构设计 · API 网关与边缘》「部署形态与演进」节；《微服务演进规划》「技术选型」节；《部署发布规范》

## 3. 需求 04-2：边缘认证与请求净化 <a id="r04-2"></a>

优先级：2（高）

**背景与动机**：网关是唯一外部入口，须在边缘完成认证校验并**剥离客户端伪造的身份头**、注入网关验证过的身份，后端只做授权；否则存在身份伪造与网关旁路风险。

**内容**（《架构设计 · API 网关与边缘》「边缘功能」「安全边界」节）：

1. 边缘认证：校验用户 JWT（签名 / 过期 / issuer / **audience**），拒绝未认证请求；认证细节归 [07_需求_认证与服务身份](07_需求_认证与服务身份.md)。
2. 请求净化：剥掉客户端伪造的身份头（X-User-Id / X-Service-Identity 等），注入网关验证过的身份信息后透传后端。
3. 网关旁路防护：内部服务只接受带服务身份的流量（服务 JWT），非同网段裸暴露。
4. 授权下沉：后端只做 scope / 权限码授权，不重复认证；外部 access token 不透传内部。

**完成标准**：未认证请求被网关拒绝；伪造身份头被剥离、注入身份正确；后端仅信任网关 / 服务身份流量；用例覆盖；校验通过。

**参考文档**：《架构设计 · API 网关与边缘》「安全边界」节；《架构设计 · 认证与会话》「服务身份与服务间认证」节；《架构设计 · 性能与安全》「服务间安全」节

## 4. 需求 04-3：限流与服务发现 <a id="r04-3"></a>

优先级：2（高）

**背景与动机**：多副本下边缘限流须共享计数；服务实例以容器运行、地址动态，调用方需按名寻址而非硬编码 IP。

**内容**（《架构设计 · API 网关与边缘》「边缘功能」节、《架构设计 · 部署与运维》「集群设计要点」节）：

1. 边缘限流：按用户 / 客户端 / 租户 / IP 限流，基于共享 Redis 实现多副本一致计数；登录限流优先。
2. 服务发现：服务间按稳定主机名寻址（Compose 内置 DNS → 迁 K8s 原生 Service），地址收敛进配置层，禁止硬编码 IP / 端口。
3. 边缘观测：访问日志与指标经现有 RocketMQ / ES / 可观测栈出口（与 [08_需求_可观测性栈](08_需求_可观测性栈.md) 衔接）。
4. 灰度预留：支持按版本 / 权重灰度路由（规则声明式入 Git）。

**完成标准**：共享限流计数在多副本一致生效；服务间按名寻址用例通过、无硬编码 IP；边缘访问日志 / 指标可见；校验通过。

**参考文档**：《架构设计 · API 网关与边缘》「边缘功能」节；《架构设计 · 部署与运维》「集群设计要点」节；《架构设计 · 可观测性》「指标采集」节

## 5. 需求 04-4：前端网关接入改造 <a id="r04-4"></a>

优先级：2（高）

**背景与动机**：网关外部路径前缀由 `/api/v1` 变更为 `/api/{service_key}/v1`（网关重写为服务内 `/api/v1`，见 [04-1](04_需求_API网关与边缘.md#r04-1)），前端原按单一 `/api/v1` 组装请求的方式失效；需前端按服务段寻址改造，否则登录与各能力源请求全部不可用。微服务对前端影响评估（2026-09-25）将其登记为遗留。

**内容**（《架构设计 · 前端架构》「多服务寻址」节、《架构设计 · API 网关与边缘》「边缘功能」节）：

1. 请求层集中维护「域 → 服务前缀」映射（单一来源），按 `/api/{service_key}/v1/...` 组装；禁止各模块 / 页面自拼服务前缀。
2. 请求适配器装配与 baseURL 收敛；能力源（字典 / 组织 / 验证码 / 文件 / 检索等）按服务注入 `endpoint`。
3. 9 份服务契约的前端类型生成（`openapi-typescript` → `@bms/api-types`），以 `deploy/contracts/` 快照为唯一事实源，禁止手写漂移。
4. 登录页 / 路由守卫 / 401 刷新按服务段寻址联通（与认证阶段衔接）。

**完成标准**：前端请求一律经「域 → 服务前缀」映射按服务段寻址；能力源按服务分流；类型由契约快照生成、无手写漂移；登录与各能力源请求联通；用例覆盖、校验通过。

**参考文档**：《架构设计 · 前端架构》「多服务寻址」节；《架构设计 · API 网关与边缘》「边缘功能」节；《前端开发规范》

## 6. 需求 04-5：网关请求体大小限制 <a id="r04-5"></a>

优先级：3（中）

**背景与动机**：网关 nginx `client_max_body_size` 未配置（默认 1m），与文件上传 20MB / 分片策略潜在冲突；APISIX 侧亦无请求体限制。微服务对前端影响评估（2026-09-25）登记为遗留。

**内容**（《架构设计 · API 网关与边缘》「边缘功能」节）：

1. 明确请求体大小与分片的边界口径：网关 nginx `client_max_body_size` 与 APISIX 请求体限制配置值，与文件上传 20MB / 分片策略对齐。
2. 配置声明式入 Git（随网关配置热加载）。
3. 实测：超限请求被拒且返回口径一致；分片上传不受影响。

**完成标准**：网关与 APISIX 请求体限制配置就位且与文件策略一致；超限拒绝口径一致；分片上传实测通过；校验通过。

**参考文档**：《架构设计 · API 网关与边缘》「边缘功能」节；文件管理阶段联调口径
