## 1. 目标与边界 <a id="scope"></a>

**目标**：14_01 已把 17 个模型文件 / 38 张共享表整包下沉到 `bms_core.models.{platform,identity,tenant}`，但「表登记（表文件 / 总览）」「模型发现（`chain_metadata`）」「契约快照」「迁移链」四处都以**包路径 / 表归属**为发现依据。本任务把这四处与迁包结果对齐并留证：表文件的模型落点改到基座共享路径、落库状态与实际一致、四道 check 零漂移、两条建表入口实测可建出全部 enabled 共享表，并把「建表核对」固化为可回归用例。

**范围内**：

1. **表文件同步（36 份）**：38 张共享表中 36 张有表文件，「ORM 模型」列一律改基座共享路径并标注「基座共享模型（14_01 下沉）」，逐表追加一条变更记录。
2. **落库状态同步**：`sys_user_tenant` 由 `待落库` 改 `已落库`（表文件 + 《数据库设计总览》两处）。
3. **通用约定同步**：《数据库设计 · 数据规范》里 `app/models/base.py::BaseModel` 改为 `bms_core/models/base.py::BaseModel`。
4. **四道 check 核对**：`ops.check_tables --offline`、`ops.contract_snapshot check`、`ops.event_contracts check`、`ops.check_contracts` 全部零漂移（不重新导出快照）。
5. **建表链核对**：启动期自动建表（`ensure_service_schema`）、`ops.init_schema`、Alembic 建表链（脚本已清空，机制保留）三路核对，确认 enabled 共享表全部建出、`planned` 表不进链。
6. **建表核对用例**：新增 1 个自动化用例（临时 SQLite 真实建表 + 表集断言），Kiwi 编号先登记后回填。
7. **登记回写**：需求 14-2 / 任务 14_02 / 阶段计划 / 本任务三份记录。

**范围外**（归口见 §8）：

- `TABLE_OWNERSHIP` 的 `owner` / `datasource`：**本任务零改动**（链归属由其派生，改 `owner` 会让表跑到别的链）；
- 表结构本身（字段 / 索引 / 约束）：零改动，只是模型代码位置变了；
- `sys_user_preference` / `demo` 两张 `planned` 表的表文件：不补（未定稿，随所属阶段）；
- 「表文件 ORM 模型列」的机器门禁：本次不加（避免扩大门禁面），登记缺口归口；
- `ops` 运行镜像声明与导入闭包断言 → `14_03`；开通编排内核与四种子下沉 → `14_04`。

## 2. 现状与核对结论 <a id="current"></a>

### 2.2 表登记缺口

- **表文件「ORM 模型」列全部写的是迁包前路径**：33 份写已删除的服务包（如 `bms_platform/models/user.py::SysUser`），3 份写更早的 `app/` 目录（`app/models/system.py::SysTask` / `SysTaskLog`、`app/models/platform.py::SysModuleI18n`）。
- 38 张表中有 **2 张没有表文件**：`sys_user_preference`（planned，05-用户喜好）、`demo`（planned，五层示例表）。
- `sys_user_tenant` 状态仍是 `待落库`：该值写于 2026-10-04（迁移脚本已生成、真库执行待部署窗口），而 06_05 起表结构由幂等建表落地、该表 `status = enabled`，本次实测已被建出。
- 《数据库设计总览》「已设计数据表登记」**不含 ORM 列**，其表文件 ↔ 总览 ↔ 目录三处一致性由 `check_base.py` 断言，当前通过。

### 2.3 模型发现链（单一派生点）

```text
chain_metadata(chain)
  ├── chain.tables        ← chain_tables(service, datasource)（TABLE_OWNERSHIP 派生，仅 status = enabled）
  └── Base.metadata       ← import_models(service) = COMMON_MODEL_MODULES + 服务 MODEL_MODULES
                              └── COMMON_MODEL_MODULES = 基座 4 模块 + models/{platform,identity,tenant}::MODEL_MODULES
```

四个消费方**都经这同一派生点**，没有任何一处另立表集：启动期建表（`db/bootstrap.py::ensure_service_schema`）、运维建表（`ops/init_schema.py`）、迁移（`alembic/env.py` 的 `target_metadata`）、表归属校验（`ops/check_tables.py`）。因此「基座三个新子包被纳入扫描」不需要改代码——14_01 已把它们组合进 `COMMON_MODEL_MODULES`。

### 4.2 变更记录追加 <a id="revlog"></a>

每份表文件在「变更记录」末尾追加一行（版本号 = 该文件现有末位版本 +1）：

```text
| 2026-10-22 | v<N> | ORM 模型落点迁基座共享 `bms_core/models/<来源服务>/<模块>.py`（14_01 整包下沉；表名 / 字段 / 索引 / 归属不变） | minjian |
```

- 与 `sys_user.md` v4「归属库迁移」先例同构：**非结构变更但有解释价值的位置迁移也留痕**；
- 版本号按文件逐个读取现有末位（如 `sys_tenant` v6 → v7、`sys_user` v5 → v6、`sys_task` v1 → v2），**不统一按 v2 覆盖**；
- 若某文件末位已是 `v1` 且同日有两条（如 `sys_user` 有两条 v1），仍按「末位数字 +1」推进。

## 6. 兼容与回滚 <a id="rollback"></a>

- **兼容**：表结构、表归属、契约、事件契约、建表入口、部署命令零变化；仅文档登记与一个测试文件。
- **回滚**：`git revert` 本任务提交即可；无运行时影响。
- **风险与兜底**：
  - **批量改漏 / 改错表文件**（如版本号写成同一个）→ 逐文件读末位版本；改完用 `rg` 断旧路径 0 处 + `check_base.py` 校验结构；
