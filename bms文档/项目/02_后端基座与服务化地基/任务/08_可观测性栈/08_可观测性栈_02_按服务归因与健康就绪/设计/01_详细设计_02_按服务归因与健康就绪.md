## 1. 概述 <a id="overview"></a>

- **目标**：在 08_01 已交付的可观测栈之上补齐「按服务归因与健康就绪」——复核并验收三类信号（span / 指标 / 日志）的 `service.name` / `service.version` 归因与**跨服务调用链贯通**；落**核心链路 SLO 告警阈值锚点**（Alertmanager + Prometheus 规则 + blackbox 探针 + 告警通道骨架）；落**阶段度量采集通道**（Pushgateway + 越界数复用 + Grafana 面板），使 S6「跨服务问题可定位」与 S7「度量挂门禁」两项目标可验收。
- **依据**：《[架构设计 · 可观测性](../../../../../../设计/架构设计/27_架构设计_子系统_可观测性.md)》「链路追踪」「告警」「健康检查与优雅停机」节；《[架构设计 · 性能与安全](../../../../../../设计/架构设计/31_架构设计_性能与安全.md)》「可用性目标与 SLO」节；《[架构设计 · 部署与运维](../../../../../../设计/架构设计/33_架构设计_部署与运维.md)》「容量规划」节；《[微服务演进规划](../../../../../../规划/微服务演进规划.md)》「服务化地基 S6 / S7」；《[部署发布规范](../../../../../../规范/部署发布规范.md)》「可观测性栈编排与采集口径」节；需求 [08-2](../../../../需求/08_需求_可观测性栈.md#r08-2)；前置契约 08_01（可观测栈真实实现 / 端点 / 数据源）、02_02（探针 / 服务身份 / 摘流）、05_02（越界度量）、06_01（`catalog` 健康项与 `catalog_degraded` 状态，指标化 / 告警联动明确归口本任务）。
- **范围（本任务）**：
  1. **按服务归因复核与跨服务链路**：三类信号归因逐项复核（复核表）；新增跨服务链路用例（httpx 出站自动注入 W3C `traceparent` → 服务端 span 同 trace）；mjbk 双服务真实冒烟（`identity` 的 `catalog` 健康项经 `service_client` 调 `platform` 快照，同一 trace 含两服务 span）；Grafana 加 `service` / `version` 变量，落地「按服务与版本归因」展示。
  2. **SLO 告警阈值锚点**：`deploy/observability/rules/bms-slo.yml` 基座规则（探针 / 依赖 / 错误率 / P99 / catalog 降级 / 发件箱积压）+ 业务链路锚点留位登记；Alertmanager（9093）纳入编排；告警通道渲染（邮件 SMTP + 企业微信 / 钉钉 webhook 骨架，凭据经 `.env` 外部化、缺失即禁用）。
  3. **探针可用性观测**：blackbox_exporter 周期探测每服务 `/healthz` `/readyz`（`probe_success` / `probe_duration`），并借此使 `bms_dependency_up` 持续刷新（解决「仅在 `/readyz` 被调用时记录」的被动无数据）。
  4. **catalog 降级指标化**：新增 `bms_catalog_degraded` gauge（`/readyz` 聚合按 `catalog` 检查项结果刷新）+ 警告级规则，落实计划 §7 第 16 项归口。
  5. **阶段度量采集通道**：Pushgateway（9092）纳入编排；发布成功率 / 契约破坏数 / 越界数指标口径与命名登记；Grafana「阶段度量」面板；本任务只建通道与口径，CI 推送归 09。
- **不含（明确归口，见第 8 节）**：CI 侧推送发布 / 契约度量（**09_01 / 09_02 / 09_03**）；服务容器化后抓取与探针目标切 Compose DNS（**09_需求**）；告警内部接口格式转换（企业微信 / 钉钉经 BMS 内部接口）与短信通道（**通知阶段**）；业务链路 SLO 规则实体（登录 / 审批 / Socket.IO / 备份，端点未实现，本任务只留位登记）；容量水位监控（node-exporter / cadvisor，运维阶段）。

## 4. 领域设计 <a id="design"></a>

### 4.1 按服务归因复核与跨服务链路贯通 <a id="attribution"></a>

**复核口径**（08_01 已交付，本任务逐项验收，不重复接入）：

| 信号 | 归因字段 | 来源 / 落点 | 验收方式 |
| --- | --- | --- | --- |
| span | `service.name` / `service.version`（资源标签） | `tracing/setup.py` 全局 provider（身份取 `app.state.service_identity`） | Tempo 按 `service.name` 查询命中；双服务同 trace |
| 指标 | `service`（实现统一注入；`version` 不进标签） | `PrometheusMetrics` | `/metrics` 与 Prometheus 查询带 `service` 标签 |
| 日志 | `service` / `service_version`（进程级绑定） | `core/service.py` `bind_service_identity` | Loki `{service="…"}` 检索命中 |

**跨服务链路语义**（不新增接入，只补证据）：出站 `httpx` 经 `HTTPXClientInstrumentor` 自动注入 W3C `traceparent`；入站 `FastAPIInstrumentor` 以 `traceparent` 为父创建服务端 span；`TraceIdMiddleware` 取 OTel 事实源写入日志 `trace_id` 与响应头 `X-Trace-Id`——同一 trace 跨服务一致（OTel 为唯一事实源，08_01 口径）。

**验证一：自动化用例** `libs/bms_core/tests/tracing/test_cross_service_trace.py`：

- 独立 `TracerProvider` + `InMemorySpanExporter`（显式传 `tracer_provider` 给 instrumentor，**不设全局 provider**，保证测试隔离）；
- 构造最小服务端应用（`FastAPI` + `FastAPIInstrumentor.instrument_app(tracer_provider=…)`），客户端用 `httpx.AsyncClient(transport=ASGITransport(app=…))` 发起请求（`HTTPXClientInstrumentor().instrument(tracer_provider=…)`，`try/finally` 复原）；
- 断言：exporter 收到客户端 span 与服务端 span、两者 `trace_id` 一致、服务端 span 的父 span id == 客户端 span id（传播链完整）；服务端处理期 `resolve_trace_id()` 与 span 上下文一致（日志一致性）。

**验证二：mjbk 真实冒烟（双服务）**：

- `platform` 宿主直跑（8000）；`identity` 宿主直跑（`BMS_SERVER__PORT=8001`），并开 `BMS_SERVICE_CLIENT__PROVIDER=http` + `BMS_SERVICE_CLIENT__OPTIONS={"base_url_template":"http://localhost:8000"}`（`identity` 为非目录权威服务，其 `catalog` 健康项经 `service_client` 调 `platform` 的 `GET /api/v1/modules/snapshot`）；
- 触发：`curl localhost:8001/readyz`（catalog 检查跨服务调用）→ Tempo 查该 trace，断言**同一 trace 含 `identity` 与 `platform` 两个服务**的 span（`identity` 客户端 span + 服务端 span、`platform` 服务端 span）；
- 留痕：Tempo 查询结果与 trace id 记入测试记录。

**版本归因展示**（Grafana，不使指标时间线随版本漂移）：总览面板加 `service` / `version` 变量——`service` 取 Prometheus `label_values(bms_request_total, service)`；`version` 取 Tempo 数据源 `label_values(service.version)`（实施时实测该变量查询；Tempo 不支持则退化为文本框变量并在部署说明登记）。

### 4.2 SLO 告警阈值锚点与规则 <a id="slo-rules"></a>

`deploy/observability/rules/bms-slo.yml`（Prometheus 规则；`promtool check rules` 校验）：

| 告警 | 表达式要点 | 阈值 | 分级 | `for` | 依据 |
| --- | --- | --- | --- | --- | --- |
| `BmsServiceMetricsDown` | `up{job="bms-services"} == 0` | — | 严重 | 1m | `/metrics` 可达性（服务宕机 / 网络） |
| `BmsProbeFailing` | `probe_success{job="bms-probe"} == 0` | — | 严重 | 2m | 每服务 `/healthz` `/readyz` 探针 |
| `BmsDependencyNotReady` | `bms_dependency_up == 0` | — | 严重 | 2m | 架构 27「依赖就绪」 |
| `BmsCatalogDegraded` | `bms_catalog_degraded == 1` | — | 警告 | 5m | 06_01 归口（catalog 降级可见） |
| `BmsHighErrorRate` | 按服务 5xx 率（`rate` 5m 比） | > 0.1% | 警告 | 5m | 架构 31（成功率 ≥ 99.9% → 错误预算 0.1%） |
| `BmsCriticalErrorRate` | 同上 | > 5% | 严重 | 2m | 架构 31「错误率突增」 |
| `BmsSlowRequestsP99` | 按服务 P99（`histogram_quantile` 5m） | > 0.8s | 警告 | 5m | 架构 31 举例（P99 连续 5 分钟超 800ms） |
| `BmsOutboxBacklog` | `bms_outbox_backlog` | > 100 | 警告 | 10m | 架构 27「消费积压」；M10 前无真实投递，锚点随量复核（开放项） |

- **分级与抑制**：`severity` ∈ `warning` / `critical`；`critical` 抑制同 `alertname` + `service` 的 `warning`（`inhibit_rules`，Alertmanager 侧）。
- **注解口径**：`summary` / `description` 中文可读、含服务与实例；`runbook` 指向《可观测性栈部署使用说明》排障节；`error` 不泄露连接串（沿用既有口径）。
- **业务链路锚点留位**（规则实体不落，注释 + 文档登记）：登录成功率 ≥ 99.9%（阶段六）、审批提交成功率 ≥ 99.95%（工作流阶段）、Socket.IO 待办推送延迟 P95 ≤ 2s（实时推送阶段）、备份任务每日成功（运维阶段）——业务端点未实现，阈值随阶段十四压测复核。
- **无数据口径**：规则仅在有数据时判定（不配 `absent()` 类规则，避免服务未启用时误报）；服务启用后随目标登记自动生效。
- **挂载**：`prometheus.yml` 增 `rule_files: ["/etc/prometheus/rules/*.yml"]`；compose 挂载 `../observability/rules:/etc/prometheus/rules:ro`。

### 4.3 Alertmanager 编排与告警通道 <a id="alertmanager"></a>

**编排**（`deploy/compose/observability.yml` 增组件，固定 tag；实施时以 mjbk 实拉可用版本回写）：

| 服务 | 镜像（候选 tag） | 宿主端口 | 数据 | 说明 |
| --- | --- | --- | --- | --- |
| `alertmanager` | `prom/alertmanager:v0.33.1` | `9093` | 命名卷 | 告警路由 / 抑制 / 通道；配置为渲染产物 |
| `blackbox-exporter` | `prom/blackbox-exporter:v0.28.0` | `9115` | — | 探针主动探测（见 4.4） |
| `pushgateway` | `prom/pushgateway:v1.11.3` | `9092`（容器 9091） | 命名卷 | 阶段度量推送（见 4.6） |

`prometheus.yml` 增 `alerting.alertmanagers`（`alertmanager:9093`）。

**配置渲染（凭据外部化）**：Alertmanager 配置文件**不支持环境变量替换**，且 SMTP 主机 / 收件人 / webhook URL 属本地资源（公开文档红线）——采用「模板入 Git + 脚本渲染」：

- 模板 `deploy/observability/alertmanager.yml.tmpl`（入 Git）：`route`（默认 `default`；`severity="critical"` → `critical`；`group_by: [alertname, service]`；`group_wait: 30s` / `group_interval: 5m` / `repeat_interval` 警告 12h / 严重 1h）、`receivers` 骨架、`inhibit_rules`；
- 渲染脚本 `scripts/tools/observability/render_alertmanager.py`（Python，只读 `.env` 不改动它）：读 `deploy/.env`（或 `--env-file`）→ 生成 `deploy/observability/rendered/alertmanager.yml`（**gitignore**）；条件分支——
  - 有 `ALERTMANAGER_SMTP_SMARTHOST` → `default` / `critical` receiver 附 `email_configs`（`to` / `from` / `smarthost` / 可选 `auth_username` + `auth_password`）；无 → receiver 仅声明名称（no-op，告警仅 Alertmanager UI 可见）；
  - 有 `ALERTMANAGER_WECOM_WEBHOOK_URL` / `ALERTMANAGER_DINGTALK_WEBHOOK_URL` → `critical` receiver 附对应 `webhook_configs`（`send_resolved: true`）；无 → 不附（骨架保留在模板与文档中，启用只需补 `.env` 后重渲染）；
  - 幂等：同输入同输出；`--check` 校验已渲染产物是否为最新（部署说明用）；
- 部署步骤（写入《可观测性栈部署使用说明》）：首次 / 变更凭据后 `python3 scripts/tools/observability/render_alertmanager.py --env-file deploy/.env` → `docker compose -f compose/bms.yml --env-file .env up -d`；`rendered/.gitkeep` 保证目录存在，未渲染时 Alertmanager 启动报配置缺失（日志明确，可回退）。
- **K8s 平移**：Alertmanager → Helm / StatefulSet，渲染产物改 Secret 挂载，路由语义不变；webhook → BMS 内部接口格式转换归通知阶段（届时在 webhook receiver 侧加 `http_config` 或改内部地址）。

### 4.4 探针可用性观测（blackbox_exporter） <a id="blackbox"></a>

- **配置** `deploy/observability/blackbox.yml`：模块 `http_2xx`（`prober: http`；`http.preferred_ip_protocol: ip4`；`timeout: 5s`；有效状态码 200——`/readyz` 未就绪即 503，探测失败即告警信号，不把 503 视为成功）。
- **抓取**（`prometheus.yml` 增 job `bms-probe`）：`metrics_path: /probe`、`params.module: [http_2xx]`；目标按启用服务登记（当前 `http://host.docker.internal:8000/healthz`、`/readyz`，与 `bms-services` 同口径；容器化后切 `{service_key}:8000`）；`relabel_configs`——`__address__` → `__param_target`、`__param_target` → `instance`、`__address__` → `blackbox-exporter:9115`、从目标路径提取 `probe` 标签（`healthz` / `readyz`）。
- **联动**：blackbox 周期（15s）探测 `/readyz` → 应用聚合健康检查并记录 `bms_dependency_up`——**解决「无人调用 `/readyz` 时依赖指标无数据」**；`bms_catalog_degraded` 同点刷新（见 4.5）。
- **规则**：`BmsProbeFailing`（`probe_success == 0` 严重）；`probe_duration_seconds` 供面板展示。
- **可达性**：blackbox 容器需 `extra_hosts: host.docker.internal:host-gateway`（探测宿主直跑服务，与 Prometheus 同口径）。

### 4.5 catalog 降级指标化 <a id="catalog-metric"></a>

- **指标**：`bms_catalog_degraded`（gauge；`1` = 服务目录快照不可达 / 降级，`0` = 可达；`service` 标签实现统一注入）。
- **记录点**：`api/health.py` 的 `/readyz` 聚合后——`catalog` 检查项成功记 `0`、失败记 `1`（与 `bms_dependency_up` 同点、同「写入失败静默」口径）；启动期降级（`app.state.catalog_degraded`）在首次 `/readyz` 探测即反映（快照恢复后归 `0`，语义为「当前可达」）。
- **登记**：`METRIC_NAMES` 增 `bms_catalog_degraded`；`METRIC_DOCS` 增 HELP 文案；《后端基类清单》指标登记补一行。
- **规则**：`BmsCatalogDegraded`（`== 1`，警告 5m）——使非必需健康项失败（不产生 503）**可告警可见**，落实 06_01 归口。
- **不改**：`catalog` 检查项 `required=False` 语义、`/readyz` 响应结构、`app.state.catalog_degraded` 置位逻辑。

### 4.6 阶段度量采集通道（Pushgateway） <a id="stage-metrics"></a>

**指标口径与命名**（`bms_` 前缀；S7「服务独立发布成功率 / 契约破坏数 / 越界数」）：

| 度量 | 指标 | 类型 | 标签 | 采集来源 | 推送方 |
| --- | --- | --- | --- | --- | --- |
| 服务独立发布成功率 | `bms_release_total` | counter | `service` / `result`（success / failure） | CI 发布结果 | CI（09_01 / 09_02）→ Pushgateway |
| 契约破坏数 | `bms_contract_breaking_total` | gauge | `service` | oasdiff 破坏性变更数 | CI（09_03）→ Pushgateway |
| 边界越界数（运行期） | `bms_boundary_cross_access_total` | counter | `service` / `prefix` / `owner` / `operation` | 应用 `/metrics`（05_02 已交付；标签以实现为准，实施核对回写） | 应用（已有） |
| 边界越界数（静态） | —（门禁；非零即 CI 失败） | — | — | `check-service-boundaries`（05_02 已交付） | —（不重复推送，见开放项） |

- **命名登记**：`bms_release_total` / `bms_contract_breaking_total` 入 `METRIC_NAMES`（注释注明「由 CI 推送 Pushgateway、应用侧不记录」）；HELP 入 `METRIC_DOCS`。
- **通道**：Pushgateway 组件（4.3）+ `prometheus.yml` job `pushgateway`（`honor_labels: true`，保留推送侧标签）；CI 侧推送命令（09 接入，命令模板入部署说明）：`curl --data-binary @metrics.txt http://<pushgateway>:9091/metrics/job/bms-ci/<service>`（文本格式，指标与标签随推送）。
- **面板**：`bms-stage-metrics.json`——发布成功率（`sum(rate(bms_release_total{result="success"}[7d])) / sum(rate(bms_release_total[7d]))` 或按窗口累计）、发布次数（按服务 / 结果）、契约破坏数、运行期越界数（`increase` 按日 / 周）。
- **边界**：本任务交付**通道 + 口径 + 面板 + 规则消费位**；真实数据由 09 推送（本任务不侵入 CI）；冒烟以手工推送样例验证通道可达、可抓、可展示。

### 4.7 Grafana 面板与 provisioning <a id="dashboards"></a>

- **面板加载**：沿用目录 provisioning（`/var/lib/grafana/dashboards` 目录加载，新增 JSON 自动生效），不新增 loader。
- **`bms-slo.json`（SLO 与告警）**：告警状态（`ALERTS{alertstate="firing"}` 按 `alertname` / `severity` / `service`）、5xx 错误率（按服务）、P99 / P95 延迟（按服务）、依赖就绪（`bms_dependency_up`）、探针成功率（`probe_success`）、catalog 降级（`bms_catalog_degraded`）、发件箱积压（`bms_outbox_backlog`）。

## 5. 失败分支与边界 <a id="failures"></a>

| 场景 | 处理 |
| --- | --- |
| Alertmanager 未渲染配置 | 容器启动报配置缺失（日志明确）；部署说明要求先跑渲染脚本（幂等，重跑安全） |
| 无 SMTP / webhook 凭据 | 渲染为 no-op receiver，告警仅 Alertmanager UI 可见；补凭据后重渲染 + `docker compose up -d` 生效，不阻断其余组件 |
| SMTP 不可达 / 认证失败 | Alertmanager 重试并记 `alertmanager_notifications_failed_total`；告警不丢（UI 可见）；排障入部署说明 |
| Alertmanager 自身宕机 | 规则仍在 Prometheus 评估（`ALERTS` 可见）；`up{job="alertmanager"} == 0` 规则可选（本任务加 job 抓取，不加自监控规则） |
| blackbox 探测失败 | `probe_success=0` 即告警信号（预期行为）；服务未启用时目标不登记（不误报） |
| `/readyz` 503 | blackbox 探测按失败处理（`http_2xx` 仅 200 成功）；`bms_dependency_up` / `bms_catalog_degraded` 随之刷新 |
| 规则表达式无数据 | 不触发（不配 `absent()`）；服务启用后随目标登记生效 |
| Pushgateway 无数据 | 面板空；不告警（`push_time_seconds` 陈旧检测登记开放项） |
| Grafana `version` 变量不支持 | 退化文本框 / 常量并在部署说明登记（不影响其余面板） |
| 渲染产物误入 Git | `.gitignore` 忽略 `deploy/observability/rendered/alertmanager.yml`；预检 / 公开文档红线核对（凭据不入库） |
| 镜像拉取 | 国内加速 + 固定 tag；实施时以 mjbk 实拉可用版本回写（沿用 08_01 经验） |
| 告警噪声（dev 频繁重启） | 阈值与 `for` 按生产口径；dev 需要时用 Alertmanager silence，不另造 dev 阈值 |
| 阶段度量真实数据缺位 | 面板空态可读（标注「待 09 接入」）；冒烟以样例数据验证通道 |

## 8. 边界与开放项 <a id="boundary"></a>

- **归 09_需求**：CI 推送发布 / 契约度量（本任务只建通道与口径）；服务容器化后 Prometheus 抓取与 blackbox 探针目标切 `{service_key}:8000`（Compose DNS）。
- **归通知阶段**：告警内部接口格式转换（企业微信 / 钉钉经 BMS 内部接口）、短信通道（`sys_sms_template`）、邮件模板。
- **归后续阶段**：业务链路 SLO 规则实体（登录：阶段六；审批：工作流阶段；Socket.IO：实时推送阶段；备份：运维阶段）；阈值随阶段十四压测复核。
- **开放项（容量水位）**：node-exporter / cadvisor 采集磁盘与内存水位告警（架构 33 容量规划）随部署 / 运维阶段评估。
- **开放项（静态越界推送）**：`boundary_metrics.py` 静态越界数推送 Pushgateway（当前静态门禁非零即 CI 失败，不重复推送）。
- **开放项（Pushgateway 陈旧）**：`push_time_seconds` 陈旧告警随 09 推送落地后评估。
- **开放项（告警自监控）**：Alertmanager 自身指标已抓取，`up{job="alertmanager"}` 自监控规则按需加。
- **开放项（version 变量）**：Tempo `label_values(service.version)` 实测不支持时退化文本框（部署说明登记）。
- **不改**：指标 / 链路能力域契约签名、探针响应结构与豁免口径、08_01 已交付配置语义（保留期 / 数据源 / 一键聚合）、既有 Kiwi 用例号。
