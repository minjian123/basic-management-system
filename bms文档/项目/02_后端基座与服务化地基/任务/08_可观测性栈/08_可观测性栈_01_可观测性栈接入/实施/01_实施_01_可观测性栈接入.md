## 3. 实施过程 <a id="process"></a>

1. **依赖引入**：`bms_core` 增 `prometheus-client`、`opentelemetry-sdk` / `-exporter-otlp-proto-http` 与 `-instrumentation-fastapi/-sqlalchemy/-redis/-httpx/-celery`（版本对齐 OTel SDK 1.44 / instrumentation 0.65b0）；`uv sync` 落地。
2. **指标真实实现**：`metrics/prometheus.py` 的 `PrometheusMetrics`（独立 `CollectorRegistry`，三入口按 `(kind, name, labelnames)` 缓存指标、统一注入 `service` 标签、同名冲突早失败）；`BaseMetrics.render()` 新增具体方法（占位返回 None）。
3. **采集端点**：`api/metrics.py` 的 `/metrics`（`BaseRouter`，`include_in_schema=False`，免统一响应 / 租户 / 鉴权 / 访问日志）；`/metrics` 纳入租户与边缘缺省豁免集、中间件排除清单；`application.py` 随探针统一挂载。
4. **请求 / 依赖指标**：`RequestLoggingMiddleware` 记 `bms_request_total` / `bms_request_duration_seconds`（`route` 取匹配路由模板 `scope["route"].path`，实测 FastAPI 已写回外层 scope）；`/readyz` 聚合后记 `bms_dependency_up`。
5. **链路真实实现**：`tracing/otel.py` 的 `OtelTracer`（span 落全局 provider、id 即 OTel 32/16 位 hex、attach/detach 上下文、无有效 provider 退回本地占位 id）；`tracing/setup.py` 配置全局 `TracerProvider`（资源标签、采样、OTLP/HTTP、W3C 传播）与程序化自动埋点（每项降级）；`application.py` 末尾调用 `setup_observability`（OTel ASGI 中间件位于最外层）。
6. **链路事实源**：`tracing/base.py` 新增 `resolve_trace_id` / `otel_trace_id` / `resolve_span_id`；`TraceIdMiddleware` 取 OTel 事实源（`otel_trace_id() or 入站头 or request_id or 新生成`），日志 `trace_id` 与 Tempo 一致。
7. **SQLAlchemy 埋点接线**：`db/engine.py` 改用**延迟绑定**（`sqlalchemy.create_engine` / `sqlalchemy.ext.asyncio.create_async_engine` 模块属性调用），使全局补丁对惰性创建的异步引擎生效（原 `from ... import create_async_engine` 在导入期绑定、补丁不可达）。
8. **配置**：`core/config.py` 新增 `TracerSettings`（`otlp_endpoint` / `sampler` / `sampler_ratio` / `export_timeout_ms` / `insecure`）；`config.toml` 增 `[metrics] provider=prometheus` 与 `[tracer] provider=otel`，`config.prod.toml` 下调 `sampler_ratio=0.1`；豁免集补 `/metrics`。
9. **测试隔离**：各服务与基座 `conftest.py` 的 `isolate_settings` 追加 `BMS_METRICS__PROVIDER=""` / `BMS_TRACER__PROVIDER=""`（防全局 provider / 后台导出线程与网络噪声）；契约套件会话级快照构建显式关闭真实 provider。
10. **部署资产**：`deploy/compose/observability.yml`（6 组件）+ `deploy/compose/bms.yml`（`include` 聚合）；`deploy/observability/`（collector / prometheus / tempo / loki / alloy / grafana provisioning + 总览面板）；`.env.example` 补可观测端口与 Grafana 口令。
11. **用例与门禁**：新增 4 个用例文件（指标 / 链路 / 端点 / 编排配置，Kiwi 2182）；全量 `pytest` / `ruff` / `pyright` / 基座校验 / 本地预检全绿。
12. **mjbk 真实冒烟**：同步 `deploy/observability` 与编排 → 一键拉起可观测栈 → platform 服务宿主直跑（日志落 `observability/logs/`）→ 逐项验证（见 §5）→ 清理。

## 4. 问题与处置 <a id="issues"></a>

| 问题 | 现象 | 处置 |
| --- | --- | --- |
| SQLAlchemy 埋点补丁不可达（关键） | `db/engine.py` 以 `from sqlalchemy.ext.asyncio import create_async_engine` 在导入期绑定函数，otel 的全局补丁只改模块属性，惰性租户引擎不被埋点 | 改**延迟绑定**（调用 `sqlalchemy.ext.asyncio.create_async_engine(...)` / `sqlalchemy.create_engine(...)` 模块属性），并同步修正 `tests/db/test_pool_config.py` 的 monkeypatch 目标 |
| 契约套件会话级快照触发全局 OTel | `tests/contracts/conftest.py` 的 session 级 `build_snapshot()` 先于函数级配置隔离运行，读到 `config.toml` 的真实 provider → 起全局 TracerProvider + 后台导出线程 | `build_snapshot()` 内用 `pytest.MonkeyPatch.context()` 显式关闭 `BMS_TRACER__PROVIDER` / `BMS_METRICS__PROVIDER` 再建应用 |
| 中间件误取环境链路 id | `TraceIdMiddleware` 初版用 `resolve_trace_id()`（含上下文回退），会取到用例预置的 `current_trace_id`，破坏「未开启 OTel 时回退入站头 / request_id / 新生成」语义 | 新增 `otel_trace_id()`（**仅** OTel 当前 span），中间件改用之；`resolve_trace_id()` 仍供日志用（OTel 优先、上下文回退） |
| NoOp provider 下父链丢失 | 用 `NoOpTracer` 且传入父上下文时，`start_span` 返回透传父上下文的 `NonRecordingSpan`（有效 id），既非本地产物又无父信息 | `start_span` 判定 `NonRecordingSpan` 即退回本地占位 id（保持父子链与上下文贯穿） |
| `opentelemetry-instrumentation-celery` 不可导入 | 该包顶层 `from billiard import VERSION`，而当前未引入 Celery 运行时（`billiard` 缺失） | 埋点统一 `try/except` 降级；Celery 埋点随任务调度阶段引入 Celery 后生效（设计 §4.5、开放项） |
| 镜像源限速 | 默认加速器（daocloud）对 `otel-contrib` 拉取停滞；显式 `docker.1ms.run/<image>` 前缀拉取后重打 tag 可用 | 实施期以显式镜像前缀拉取并 `docker tag` 回标准名（文档 §7 排障已记） |
| 镜像损坏（关键） | `otel/opentelemetry-collector-contrib:0.116.0` 拉下后容器 `exec /otelcol-contrib: no such file or directory`；`docker export` 见根fs 仅二进制、缺 `/lib64` 加载器（动态链接），core 版 `0.116.0` 同样 | 判定为加速器缓存的**坏副本**；改拉 `0.115.1`（可运行、组件齐全）并回写编排 / 清单 / 部署说明；经验补入《DockerEngine 部署使用说明》「大镜像拉取与断点续传」节（containerd 断点续传 + 批量拉取工具） |
| 日志可检索但需 JSON | 平台服务 dev 默认 `[log].format = console`，Alloy `stage.json` 解析不出 `service` | 冒烟以 `BMS_LOG__FORMAT=json` 运行（test/prod 本就 JSON）；日志按服务检索验证通过 |
| 静态 `service` 标签冲突 | Prometheus 抓取目标设静态 `service` 标签、与指标自带 `service` 同名 → 指标标签被重命名为 `exported_service` | 去掉抓取目标静态 `service` 标签（指标自带归因）；`prometheus.yml` 已回写 |
| dev 日志 `DEBUG` 级别噪声 | `config.dev.toml` 为 DEBUG，服务日志量大 | 冒烟日志按需过滤；不影响功能 |
