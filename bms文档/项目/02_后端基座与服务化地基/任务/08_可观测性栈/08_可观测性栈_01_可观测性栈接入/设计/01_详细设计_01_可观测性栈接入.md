## 1. 概述 <a id="overview"></a>

- **目标**：把阶段一交付的**占位**指标 / 链路能力域回补为**真实实现**，并接入标准可观测栈——`BaseMetrics` 落 Prometheus 真实实现 + 每服务 `/metrics` 采集端点 + 请求 / 依赖指标埋点；`BaseTracer` 落 OpenTelemetry 真实实现 + 程序化自动埋点（FastAPI / SQLAlchemy / Redis / httpx / Celery）+ otel-collector；`deploy` 编排一体（otel-collector / Tempo / Prometheus / Grafana / Loki / Alloy）并含保留期 / TTL 配置与 Grafana 数据源 / 面板 provisioning；边缘（APISIX）指标与访问日志并入展示。**Trace 可查、指标可查、日志可按服务检索**。
- **依据**：《[架构设计 · 可观测性](../../../../../../设计/架构设计/27_架构设计_子系统_可观测性.md)》「结构化日志」「指标采集」「链路追踪」节；《[架构设计 · 部署与运维](../../../../../../设计/架构设计/33_架构设计_部署与运维.md)》「基础设施编排」「容量规划（可观测性栈保留期）」节；《[架构设计 · API 网关与边缘](../../../../../../设计/架构设计/36_架构设计_子系统_API网关与边缘.md)》「边缘观测」节；《[微服务演进规划](../../../../../../规划/微服务演进规划.md)》「服务化地基 S6」；需求 [08-1](../../../../需求/08_需求_可观测性栈.md#r08-1)；前置契约 02_01（共享库 + 服务工程）、02_02（服务身份 / 探针 / 摘流）、04_03（边缘指标端点 / 访问日志出口）、02-3-11（指标 / 链路占位契约，回补出处）。
- **范围（本任务）**：
  1. **指标真实实现**：`bms_core/metrics/prometheus.py` 的 `PrometheusMetrics`（`prometheus-client` 支撑 `counter` / `gauge` / `histogram`），provider `prometheus`；既有 `BaseMetrics` 调用面（库数量 / 边界 / 发件箱等）零改动即变真实。
  2. **`/metrics` 采集端点**：每服务根路径 `/metrics`（与探针同级，免鉴权 / 免租户 / 免访问日志），渲染 Prometheus 文本格式；`provider` 非真实实现时端点返回 404。
  3. **请求 / 依赖指标**：`RequestLoggingMiddleware` 记 `bms_request_total` / `bms_request_duration_seconds`（标签 `service` / `method` / `route` 模板 / `status`）；`/readyz` 聚合后记 `bms_dependency_up`（标签 `service` / `dependency`）。
  4. **链路真实实现**：`bms_core/tracing/otel.py` 的 `OtelTracer`（provider `otel`，`opentelemetry-sdk`），`bms_core/tracing/setup.py` 配置全局 `TracerProvider`（资源标签 `service.name` / `service.version`、采样、OTLP/HTTP 导出、W3C 传播）与程序化自动埋点；**OTel 为链路 id 唯一事实源**，`X-Trace-Id` / `traceparent` 双兼容入站。
  5. **可观测栈编排**：`deploy/compose/observability.yml`（otel-collector / Tempo / Prometheus / Grafana / Loki / Alloy）+ 聚合 `deploy/compose/bms.yml`（`include` base / gateway / observability，一键拉起）；配置入 `deploy/observability/`（含保留期 / TTL：Prometheus 15d、Loki 30d、Tempo 72h）。
  6. **Grafana provisioning**：三数据源（Prometheus / Loki / Tempo）+ 一张总览面板（请求量 / 延迟 / 错误率 / 依赖状态 / 日志 / Trace），开箱即用、声明式入 Git。
  7. **日志采集**：Grafana Alloy 采集容器（APISIX 及后续服务容器）与宿主日志文件，JSON 解析后写 Loki——`service` / `level` 作标签、`trace_id` / `request_id` 作**结构化元数据**（Loki 3.x，避免高基数）。
  8. **边缘接入**：Prometheus 抓 APISIX `:9091/apisix/prometheus/metrics`（前缀 `apisix_`）；Alloy 采 APISIX 访问日志入 Loki。
- **不含（明确归口，见第 8 节）**：Alertmanager 与告警规则 / SLO 阈值锚点、阶段度量（发布成功率 / 契约破坏数 / 越界数）、探针细化与按服务归因的验收 → **08_02**；服务容器化与按服务镜像发布 → **09_需求**；slowapi 真实 Redis 限流后端 → 性能与安全阶段；真实 Celery 运行时埋点实测 → 任务调度阶段（依赖与钩子就位）。

## 4. 领域设计 <a id="design"></a>

### 4.1 指标真实实现（Prometheus） <a id="metrics-real"></a>

`bms_core/metrics/prometheus.py`：`PrometheusMetrics(BaseMetrics)`，`plugin_name = "prometheus"`，**不继承 `BaseNullObject`**（真实实现）。

| 成员 | 形态 | 说明 |
| --- | --- | --- |
| `PrometheusMetrics(service, registry=None)` | 构造 | `service` 为服务身份（`settings.app.service`）；`registry` 缺省新建独立 `CollectorRegistry`（隔离全局默认注册表，便于多服务同进程测试） |
| `counter(name, *, value=1.0, labels=None)` | 覆写 async | 惰性建 `Counter`（标签名首次调用固定），`labels(**merged).inc(value)` |
| `gauge(name, *, value, labels=None)` | 覆写 async | 惰性建 `Gauge`，`labels(**merged).set(value)` |
| `histogram(name, *, value, labels=None)` | 覆写 async | 惰性建 `Histogram`（默认桶 `DEFAULT_BUCKETS`：5ms~10s 覆盖请求延迟），`labels(**merged).observe(value)` |
| `render() -> tuple[bytes, str] \| None` | 覆写 | `generate_latest(self._registry)` + `CONTENT_TYPE_LATEST` |
| `_merged(labels)` | 私有 | 自动注入 `service` 标签（调用方若已传同值则等价；重复键以本实现注入值为准） |
| `_metric(name, kind, labelnames)` | 私有 | `(name, kind, tuple(sorted(labelnames))) → 指标对象` 缓存；同名跨 kind / 跨标签集冲突即抛 `ValueError`（早失败） |

**口径**：

| 情形 | 处置 |
| --- | --- |
| 标签基数 | 调用方负责有界；HTTP 指标 `route` 用**路由模板**（非原始 path），`status` 用数字码，杜绝 id 类高基数 |
| `service` 标签 | 实现**统一注入**（架构「按服务与版本打标签归因」）；`version` 不进指标标签（由 Prometheus 抓取目标外部标签 / Grafana 变量归因，避免每次发布换时间线） |
| 存储 | 进程内 `CollectorRegistry`，`workers=1`（一服务一容器）下无多进程聚合问题；多 worker 时按进程各自暴露（后续按需切 `multiprocess` 模式，登记开放项） |
| 与调用面 | 既有 `bms_db_count` / `bms_boundary_cross_access_total` / 发件箱调用零改动即真实落点 |

`BaseMetrics` 增**具体方法** `render() -> tuple[bytes, str] | None`（默认 `None` = 不支持暴露），`NullMetrics` 沿用默认；不破坏契约（新增具体方法、向后兼容，`contract_version` 不变）。`METRIC_NAMES` 增补 `bms_request_total` / `bms_request_duration_seconds` 已存在，无需变更。

### 4.2 `/metrics` 采集端点 <a id="metrics-endpoint"></a>

`bms_core/api/metrics.py`：`BaseRouter(key="metrics", default_responses=False)`（与探针同款豁免统一前缀 / 统一响应）。

- `GET /metrics`：取 `request.app.state.metrics`；`render()` 为 `None`（null 实现）→ `404`；否则 `Response(content=body, media_type=content_type)`。
- **豁免**（免租户解析 / 免鉴权 / 免访问日志）：加入 `TenantSettings.exempt_paths` 与 `DEFAULT_EXEMPT_PATHS`、`EdgeSettings` 缺省豁免集、`middleware._EXCLUDED_PATHS`；路由由 `application.py` 随探针统一挂载（`app.include_router(metrics.router)`）。
- **仅内网可达**：不入网关（网关只放行 `/api/{service_key}/...` 前缀）；生产由 ufw / 网络策略限制来源。端点内容不含敏感数据。

### 4.3 请求 / 依赖指标埋点 <a id="metrics-instrument"></a>

- **请求指标**（`RequestLoggingMiddleware`，请求结束统一记）：`bms_request_total{service,method,route,status}`（counter）、`bms_request_duration_seconds{service,method,route}`（histogram，单位秒）。`route` 取 `scope["route"].path`（FastAPI 已把匹配路由写回外层 scope，经实测确认），未匹配回退 `scope["path"]`；探针与 `/metrics` 排除（沿用排除清单，不记请求指标）。指标实例经 `scope["app"].state.metrics` 获取，缺失（未装配）静默跳过。
- **依赖指标**（`api/health.py` 的 `/readyz`）：聚合报告后对每项检查记 `bms_dependency_up{service,dependency}`（就绪 1 / 未就绪 0）；labels `dependency` 取 `DEPENDENCIES` 口径。
- **散点指标**：库数量等由既有调用面（`_record_db_inventory` / 引擎注册表）在启动与变更时写入，本任务无需新增调用点。

### 4.4 链路真实实现（OpenTelemetry） <a id="tracing-real"></a>

`bms_core/tracing/otel.py`：`OtelTracer(BaseTracer)`，`plugin_name = "otel"`（真实实现）。

| 成员 | 形态 | 说明 |
| --- | --- | --- |
| `OtelTracer(tracer_name="bms")` | 构造 | 持有 `opentelemetry.trace.get_tracer(name)`（用**全局 provider**，provider 生命周期归 `setup.py`） |
| `start_span(name, *, attributes, parent)` | 覆写 async | 取当前 OTel 上下文为父；生成 OTel span → `context.attach(set_span_in_context(span))`（令牌按本域 span id 暂存）→ 返回 `SpanContext`（id 即 OTel 的 32/16 位 hex，日志与 Trace 一致） |
| `end_span(span)` | 覆写 async | 按 span id 取回 OTel span 与令牌：`span.end()` → `context.detach(token)` |
| 父链 | — | 优先 OTel 活动上下文（跨进程经 W3C 传播）；显式 `parent` 且无活动上下文时用其 id 构造远端父 |

`bms_core/tracing/base.py` 增 `resolve_trace_id()` / `resolve_span_id()`：优先读 OTel 当前 span 上下文（`format(trace_id, "032x")`），无有效 span 回退 `core/context.py` 的上下文变量。**OTel 为唯一事实源**：`TraceIdMiddleware` 改为先 `resolve_trace_id()`，为空再回退入站 `X-Trace-Id` / 新生成 uuid4；响应回写 `X-Trace-Id`。这样日志的 `trace_id` == Tempo 的 trace id。

### 4.5 自动埋点与传播 <a id="tracing-instrument"></a>

`bms_core/tracing/setup.py`：

| 函数 | 行为 |
| --- | --- |
| `configure_tracing(settings, identity)` | `provider == "otel"` 时：构造 `TracerProvider(Resource({service.name, service.version}), sampler)` + `BatchSpanProcessor(OTLPSpanExporter(endpoint, timeout))`；`trace.set_tracer_provider`（**幂等**，已配置则复用）+ 全局 `TraceContextTextMapPropagator`；导出失败只记 SDK 日志、不抛业务 |
| `instrument_observability(app, settings)` | 依次程序化埋点：`FastAPIInstrumentor.instrument_app`（排除 `/healthz` `/readyz` `/metrics`）、`SQLAlchemyInstrumentor().instrument()`（全局补丁，覆盖惰性创建的租户引擎）、`RedisInstrumentor().instrument()`、`HTTPXClientInstrumentor().instrument()`（出站自动注入 `traceparent`，跨服务贯通）、`CeleryInstrumentor().instrument()`（当前无运行时，接入即生效）；每项 `try/except` 降级（缺插件不阻断启动） |
| 采样 | `sampler` 取配置：dev `parentbased_traceidratio` + ratio `1.0`；prod 可下调。`sampler` / `ratio` 经 `[tracer]` 配置与环境变量可调 |

**装配位置**：`BaseServiceApplicationFactory.create()` 中，`attach_service` 之后、**中间件全部注册之后**调用 `configure_tracing` + `instrument_observability`，使 OTel 的 ASGI 中间件位于最外层（进入我方中间件时服务端 span 已激活，`resolve_trace_id()` 可取到真实 id）。`SQLAlchemyInstrumentor` 等全局补丁进程内只生效一次（幂等守卫）。

### 4.6 配置分区 <a id="config"></a>

`config.py` 新增 `TracerSettings(PluginSelection)`（`tracer` 字段类型替换；`assemble_plugins` 只读 `provider`，兼容）：

| 字段 | 默认 | 说明 |
| --- | --- | --- |
| `provider` | `otel` | `metrics` 的 `provider` 缺省 `prometheus` |
| `otlp_endpoint` | `http://localhost:4318` | OTLP/HTTP 端点；容器化后经 `BMS_TRACER__OTLP_ENDPOINT` 覆盖为 `http://otel-collector:4318` |
| `sampler` | `parentbased_traceidratio` | 采样器名（白名单校验） |
| `sampler_ratio` | `1.0` | 比例采样率（0~1） |
| `export_timeout_ms` | `10000` | 导出超时（毫秒） |
| `insecure` | `true` | OTLP/HTTP 明文（内网；生产可关） |

配置文件：`config.toml` 增 `[metrics]`（`provider = "prometheus"`）与 `[tracer]`（`provider = "otel"` + 缺省字段）；`config.prod.toml` 可下调 `sampler_ratio`。密钥 / 端点环境差异一律经 `BMS_` 环境变量注入。

**测试隔离（强制）**：单元测试运行于 dev 配置，为避免真实 provider 引入全局 TracerProvider / 后台导出线程与网络噪声，各套件 `conftest.py` 的 `isolate_settings` 追加 `BMS_METRICS__PROVIDER=""` / `BMS_TRACER__PROVIDER=""`；真实实现用例显式开启（monkeypatch 覆盖 provider 与端点 / 用 in-memory exporter）。

## 5. 失败分支与边界 <a id="failures"></a>

| 场景 | 处理 |
| --- | --- |
| otel-collector 未部署 / 不可达 | `BatchSpanProcessor` 导出失败只记 SDK 日志，业务不受影响（启动不阻断、请求不失败） |
| `prometheus-client` / `opentelemetry-*` 未安装 | 依赖为 `bms_core` 必装；实现模块顶部导入，缺失即装配期报错（拒启并指出依赖） |
| TracerProvider 重复配置 | `configure_tracing` 幂等守卫（已配置复用）；多服务同进程测试只配置一次 |
| 请求无匹配路由（404） | `route` 回退 `scope["path"]`（仍记指标；生产关注主要业务路由） |
| 指标标签跨调用不一致 | `_metric` 缓存以 `(name, kind, labelnames)` 为键；同名冲突早失败（`ValueError`），防静默串指标 |
| `render()` 未实现（null provider） | `/metrics` 返回 404，不影响探针与业务 |
| 多 worker（后续） | 现按单 worker；`multiprocess` 模式登记开放项（避免重复指标） |
| Loki 高基数 | `trace_id` / `request_id` **不作标签**，作结构化元数据；标签仅 `service` / `level` / `job` 等低基数 |
| 宿主服务日志采集 | dev 服务直跑（非容器）时经 Alloy `local.file_match` 采集 `logs/*.log`；容器化后自动切 docker 发现 |
| 保留期资源占用 | 单机资源吃紧时按《部署与运维》风险项下调保留期（Prom 15d / Loki 30d / Tempo 72h 均为可配） |
| 镜像拉取 | 走 daocloud / 国内加速器；固定 tag，不以 `latest` 浮动 |
| 环境变量端点差异 | `BMS_TRACER__OTLP_ENDPOINT` 外部化（宿主 `localhost:4318` / 容器 `otel-collector:4318`）；禁硬编码 IP |
