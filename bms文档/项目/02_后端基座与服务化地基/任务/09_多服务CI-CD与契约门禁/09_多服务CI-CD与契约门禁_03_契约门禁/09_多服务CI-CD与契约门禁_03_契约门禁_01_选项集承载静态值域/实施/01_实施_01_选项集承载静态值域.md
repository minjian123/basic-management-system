## 2. 关键实现点 <a id="impl"></a>

1. **派生时机**：包 `app.openapi()` 而不是改每个 `model_json_schema`，保证「导出契约 = 运行时 OpenAPI」同源，`contract_snapshot export/check` 无需额外参数。
2. **标记键不落契约**：`optionSetKey` 是内部标记，派生时**先剔除**再写值域；未登记的 key 只剔除不改写，避免契约导出因缺登记失败（登记缺失由启动期注册表校验负责）。
3. **命名组件**：有 `contract_name` 时字段变 `$ref`，字段描述与 `title` 保留；这样 oasdiff 能按组件名报「加值」而不是散落在多个响应里。
4. **极简环境**：`valid_kinds=None` 只在「未装载任何清单」时出现（`test_assembly_tolerates_empty_product_manifests`），业务路径始终有值域。
5. **前端未知值**：`tenantStatusLabel` 未知返回 `未知状态（value）`，标签色取 `danger`；工具函数 `optionLabelOf` 不做兜底。

## 4. 附带收口（测试基座） <a id="infra"></a>

预检选测时 `services/tenant` 与 `platform/i18n` 同批运行会触发等锁超时（单次 10 分钟级），根因两条：

1. **陈旧锁清理在 Windows 上冒错**：持锁进程仍打开锁文件时 `Path.unlink` 抛 `PermissionError`，而清理点只 `suppress(FileNotFoundError)`，导致等锁方 setup 直接失败。处置：陈旧清理与放锁都容忍 `PermissionError`（清理失败只意味着「暂不可抢」，残锁仍由陈旧判据兜底），并去掉清理失败后的忙等（走 50ms 轮询 + 超时判定）。
2. **i18n 种子逐条查写**：单次种子要发 `2 × len(MESSAGE_SEEDS)` 条 SELECT（约 900 条），持锁时间秒级，多个 worker 在 i18n 串行锁上排队时等锁时长逼近上限。处置：`seed_i18n_in_session` 改为**一次预取 + 内存比对**，稳态不发写操作（实测 39ms → 12ms，且无脏对象）。

两条均属测试基础设施，不改业务语义；`locks.py` / `i18n/seed.py` 的对应用例同批补充。

> **存量问题（单列，不属本次修复）**：全闭包选测（一个 pytest 会话里混跑 `services/tenant` / `libs/bms_core` / platform 各域）仍可能被 `shared-db-write` 锁卡住约 600s 并报若干条等锁超时——持锁用例的「先取文件锁 / 先开写事务」顺序与其它 worker 相反，形成跨进程等待链，只能靠锁文件陈旧判据解开（Windows 无法按进程存活探测）。**CI 按服务独立跑不受影响**；本地影响面为 import_export / file / report / jobs 四个套件。处置方向：统一「先取锁、后开写事务」的夹具顺序，或把共享库写串行下沉为单入口。已登记为后续测试基座任务，不在本次范围。
