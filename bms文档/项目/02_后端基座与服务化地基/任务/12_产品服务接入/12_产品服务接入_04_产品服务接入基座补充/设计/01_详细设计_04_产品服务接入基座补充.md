## 1. 设计目标与范围 <a id="goal"></a>

承接需求 12-4：补齐**产品服务落表**暴露的三处基座缺口，使产品（首例 mdm，消费方为 mdm 需求 `01-2`）能自持登记表归属、按配置解析服务包模型、并登记产品权限码：

1. **表归属产品注入与合并视图**：`TABLE_OWNERSHIP` 由「平台侧常量」升为「注册表 + 产品注入合并」——新增注册 / 合并入口，平台侧登记行与产品自报注入行按「**同 `table_name` 同值去重、异值即拒**」处理；`chain_tables` / `chain_metadata` / 开发库自动建表 / 归属校验**一律取合并视图**。产品侧经**应用装配钩子**与 **ops / alembic 装载入口**在装载时注册本产品表记录（机制与 12_03 服务目录注入同构）。
2. **服务包模型名前缀参数化**：链的服务模型包名前缀由配置 `[app].package_prefix` 派生（平台默认 `bms`，产品配自有前缀）；新增**严格入口**——「服务已启用但服务包缺失」即 `ConfigError`（免静默空清单导致迁移与自动建表不建表）。
3. **产品业务码 / 动作码种子**：产品管理面权限码按产品域登记（业务码 + 域级 / 专属动作码），经平台种子写入 `sys_business` / `sys_action`；首例登记 mdm 组织域 `org` 业务码与 `org:query` / `org:create` / `org:update` / `org:delete` / `org:move`。
4. **规范与清单回写**：关联表主键口径（实现侧一律雪花 `id`）、服务包模型模块声明口径（`{包前缀}_{service}`）、表归属登记与服务应用装配基座登记同步回写。

**范围内**：`bms_core` 的 `services/table_registry.py` / `application.py` / `db/migration.py` / `core/config.py`；`ops/check_tables.py`；`ops/seed_menu.py`；四处文档回写。

**范围外**：产品侧（mdm 仓）的 `backend/services/table_registry.py` 声明与装载调用（归 mdm 需求 `01-2`，本任务只提供通道）；菜单 / 表单 / 字段 / 按钮种子（归 mdm 需求 `01-4`）；bms 现役关联表的主键形态收口（经 2026-10-07 拍板不做）；产品公开契约基线与 oasdiff 门禁（随 mdm 需求 `01-3`）。

### 1.1 现状与缺口 <a id="gap"></a>

| # | 现状 | 缺口 |
| --- | --- | --- |
| 1 | `TABLE_OWNERSHIP`（`services/table_registry.py`）为**平台侧代码常量**，`chain_tables` / `table_names` / `TableOwnershipRegistry` / `ops.check_tables` / 启动期归属校验均直接读该常量 | 产品表无法登记 → 产品迁移链、开发库自动建表、归属校验取不到产品表 |
| 2 | `db/migration.py::service_model_modules()` 硬编码 `package = f"bms_{service}.models"` | 产品服务包名（如 `mdm_org`）取不到模型清单 → `import_models` 得空、`chain_metadata` 为空、迁移与自动建表不建表（且**静默**） |
| 3 | `ops/seed_menu.py` 的 `BUSINESS_SEEDS` / `ACTION_SEEDS` 只登记平台业务码（`menu` / `user` / `post` / `dept` / `role` / `dict` 等） | 产品管理面权限码无登记入口 → 产品接口声明的权限码无法按码授权 |
| 4 | 《数据库开发规范》§3 与《数据库设计 · 数据规范》「公共字段」写明「关联表**联合主键、不设 `id`**」 | 基座仅 `BaseModel`（雪花 `id` 主键），bms 现役「关联表」全用 `BaseModel` —— **规范文字与基座 + 全部现役实现矛盾**（从未按文字实现过） |

> 缺口 4 的处置经 2026-10-07 拍板：**规范文字向实现收口**（关联表同样用雪花 `id` 主键 + 业务列复合唯一），不新增关联表 ORM 基类、不收口 bms 现役关联表。

## 3. 表归属注入与合并视图 <a id="ownership"></a>

### 3.1 注册与合并 <a id="ownership-merge"></a>

镜像 12_03 的服务目录 R 架构，`services/table_registry.py` 新增：

- `merge_table_records(platform_records, injected_records) -> ConcurrentStableList[TableRecord]`：
  - 平台侧在前、注入侧在后；
  - 同 `table_name` **逐字段同值** → 去重（保留平台侧一条）；
  - 同 `table_name` **任一字段不同** → 两条并存（随后被 `TableOwnershipRegistry.validate()` 以「表名重复登记」拒绝，fail-closed，不静默取一侧）。
- 进程级注册入口（与 `events.contracts` 的注册表同模式）：
  - `register_table_records(records) -> None`：登记产品注入记录（**同值重复登记无操作**，幂等）；
  - `injected_table_records() -> ConcurrentStableList[TableRecord]`：取已注入记录（插入序）；
  - `reset_table_records() -> None`：清空注入记录（**测试隔离用**）。
- `table_ownership_view() -> ConcurrentStableList[TableRecord]`：合并视图（`merge_table_records(TABLE_OWNERSHIP, injected_table_records())`）。

**为何用进程级注册表**（与服务目录的「构造入参」不同）：表归属的派生发生在**装载与迁移路径**（`db/bootstrap.py` 开发库自动建表、`alembic/env.py`、`ops` 脚本），这些路径没有应用实例可传参；进程级注册与事件契约注册表同模式，且「装载即注册、后继查询可见」正是需求口径。装配期注册发生在应用工厂 `create()`（lifespan 之前），故启动期自动建表已可见注入记录。

### 3.2 派生函数改读合并视图 <a id="ownership-derive"></a>

下列助手由「直接读 `TABLE_OWNERSHIP` 常量」改为「读 `table_ownership_view()`」（签名与语义不变，平台部署下注入记录为空 → 行为与改前**逐字等价**）：

| 函数 | 用途 |
| --- | --- |
| `table_owner` / `table_record` / `table_names` | 表名归属查询 |
| `owned_tables_for` / `infrastructure_tables` / `registered_services` | 归属集合查询 |
| `chain_tables(service, datasource)` | **迁移链与自动建表表集派生**（核心消费点） |
| `TableOwnershipRegistry.__init__` 缺省入参 | 离线校验默认清单 |

`known_service_keys()` / `service_table_prefixes()` 仍取自 `SERVICE_CATALOG`（服务目录已含产品行，`org` 行随 11_01 易主后即在此）；`_SHARED_TABLE_PREFIX` / `RESERVED_SERVICE_KEYS` 口径不变。

### 3.3 装配钩子与装载期注册 <a id="ownership-hook"></a>

`application.py`：

- `BaseServiceApplicationFactory` 新增钩子 `table_records() -> tuple[TableRecord, ...]`（缺省空元组），语义与 `service_records()` 对齐：**产品服务**在其中返回本产品表归属清单（跨仓直接 `import` 自身清单）；平台服务不覆写。
- `create()` 内（与 `service_records()` 同一处）：`register_table_records(ConcurrentStableList(self.table_records()))`，并落 `app.state.table_ownership = TableOwnershipRegistry(table_ownership_view())`；`app.state.table_injected_records` 供诊断。
- `_validate_table_ownership()`：离线校验改取合并视图；**接库对账仍只对 `platform` 服务执行**（`sys_table_ownership` 归 `platform` 平台服务库，非其归属库不跨服务直读）——平台部署视图 = 合并视图（注入为空），行为不变；产品服务只做离线自校验，不新增跨服务读。

### 3.4 离线校验与 ops <a id="ownership-ops"></a>

- `ops/check_tables.py`：`check_offline()` 的清单自校验与「enabled 表必入链」「脚本表集不越界」一律取**合并视图**；`check_table_db()` 双向对账同样取合并视图（`platform` 侧运行）。产品侧若自建同类校验，须先 `register_table_records()` 再调用（通道已具备，落点归产品仓）。
- `ops/seed_tables.py`：种子单一来源改为合并视图（bms 平台部署无注入 → 种子行数与内容不变；产品部署如自建则随之带上产品行）。

## 4. 服务包模型名前缀参数化 <a id="package"></a>

### 4.1 配置项 <a id="package-config"></a>

`core/config.py::AppSettings` 新增：

```toml
[app]
# 服务包名前缀：链的服务模型模块按 {package_prefix}_{service}.models 解析（平台默认 bms；产品配自有前缀，如 mdm）
package_prefix = "bms"
```

- 校验：非空且匹配 `^[a-z][a-z0-9_]*$`（非法即启动即报错，指明键名）；
- 环境覆盖：`BMS_APP__PACKAGE_PREFIX`（与其他 `[app]` 项同口径）；
- 平台部署不配 → 默认 `bms`，与改前逐字等价。

### 4.2 解析与严格入口 <a id="package-resolve"></a>

`db/migration.py`：

- `service_model_modules(service, *, settings=None)`：`package = f"{settings.app.package_prefix}_{service}.models"`；**包不存在仍返回空元组**（跨仓产品 / 预留服务的既有语义不变），`settings` 缺省取 `get_settings()`（本模块已依赖 `core.config`，无新增依赖方向）。
- 新增 `require_service_model_modules(service, *, settings=None) -> tuple[str, ...]`：**服务包不存在即 `ConfigError`**（含包名与配置键提示）。用于「服务已启用但服务包缺失」的快速失败：
  - bms `ops/check_tables.py::imported_model_tables()`：对每个 `enabled_service_keys()` 服务先 `require_service_model_modules()` 再导入（enabled 服务必有服务包；缺失即 CI / 本地预检失败）；
  - mdm 侧（消费方）：应用装配钩子与 ops / alembic 装载入口对本服务调用该入口（落点归 mdm 需求 `01-2`）。
- `import_models` / `chain_metadata` 保持经 `service_model_modules()` 取清单（不改变「无模型服务声明空元组」的成链语义）。

> **口径说明**：不把严格校验放进 `import_models`——`chain_metadata` 会被「预留 / 未建设服务」的链名触发（`known_service_keys()` 含 `permission`），统一严格化会误伤既有语义；改为「由消费方在**本服务 / 已启用服务**处显式调用严格入口」，既不静默又不误伤。

## 5. 产品业务码 / 动作码种子 <a id="seed"></a>

`ops/seed_menu.py`：

- `BUSINESS_SEEDS` 追加首例产品业务码：`("org", "组织主数据", "Organization master data")`；

## 7. 失败分支与边界 <a id="edge"></a>

| 场景 | 处置 |
| --- | --- |
| 注入记录与平台侧同 `table_name` 但字段不同 | 两条并存 → `TableOwnershipRegistry.validate()` 报「表名重复登记」→ 离线校验拒（`CatalogError`，fail-closed，不静默取一侧） |
| 注入记录与平台侧同值 | 去重，保留平台侧一条（视图条目数与平台清单一致） |
| 重复装载 / 多次装配 | `register_table_records()` 同值重复登记无操作（幂等）；测试用 `reset_table_records()` 隔离 |
| 注入记录前缀与归属服务登记不符 | `_validate_prefix` 拒绝（沿用既有规则：`sys_` 共享前缀与无前缀表跳过） |
| 服务包前缀配错（如 `[app].package_prefix` 漏配） | 严格入口 `require_service_model_modules()` 抛 `ConfigError`（含包名与配置键）；不再静默空清单 |
| 产品服务包确实未建（跨仓 / 预留） | `service_model_modules()` 返回空元组（既有语义）；严格入口只在「本服务 / 已启用服务」处调用，不误伤 |
| 平台部署（无任何注入） | 合并视图 = `TABLE_OWNERSHIP`、包前缀 = `bms` → 装配 / 校验 / 迁移 / 自动建表 / 种子行为与改前**逐字等价** |
| 关联表主键口径变更的影响面 | 仅 mdm 三张关联表（`org_user_post` / `org_role_post` / `org_role_dept`）按新口径落地并回写表文件；bms 现役关联表**不动**（本已为 `id` 形态） |
