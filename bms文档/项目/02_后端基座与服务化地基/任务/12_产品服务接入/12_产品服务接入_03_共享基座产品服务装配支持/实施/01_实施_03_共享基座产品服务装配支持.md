## 3. 实施过程 <a id="process"></a>

1. **上下文与决策（第 1~2 步）**：按《AI开发规范》读规范 → 详设 → 需求 → 任务 → 计划 → 架构 04 / 11 → 《后端开发规范》「目录与分层职责」「服务应用装配」节 → 12_01 / 12_02 详设与实施 / 测试记录 → mdm 01_01 详设（消费方），并核现状口径：`_validate_service_catalog` **硬编码 `SERVICE_CATALOG`**、`create()` 以 `ModuleRegistry()` 平台默认清单落 `app.state`、`_validate_event_contracts()` 经 `known_event_domains()` 同源引用平台清单、`ModuleRegistry` 构造已为 `modules` / `products` / `routes` 三参（12_02 改）、`ops/check_modules.py::resolve_service_contracts` 按 `backend/services/` 扫描。**12 项待拍板事项**分三组 question 逐项确认（全部取推荐项）。
2. **详设回写（设计为准）**：12 项结论与机制 / 失败分支 / 测试设计与验收映射 / 决策记录（14 行）/ 对齐记录回写详设，随后提交 `docs(12_03)`。
3. **Kiwi 先登记后编码**：登记输入 `test/scripts/kiwi/cases/2026-10-07_阶段二12-03_共享基座产品服务装配支持.json`（经 `register_cases.py` 走容器 Django shell），平台回读编号 **2251**；用例代码以 `@pytest.mark.kiwi_id(2251)` 标注。
4. **服务目录视图入口**（`bms_core/services/module_registry.py`）：增 `ModuleRegistry.catalog_records()`（全量清单）与 `ModuleRegistry.event_domains()`（事件域集合）——启动校验取清单与事件域的**单一入口**；增公开校验函数 `validate_product_service_records()`（四项 fail-closed 断言：注入记录非空 / 均为产品分组 / 产品归属与声明一致 / 含运行服务登记行）；模块级 `known_event_domains()` 保留为**平台清单视图**（CI 快照 CLI 消费），文档标注应用装配期改取实例方法。
5. **应用工厂装配**（`bms_core/application.py`）：`BaseServiceApplicationFactory` 增类属性 `product_key` 与可覆写钩子 `service_records()`（缺省空元组）；`create()` 以「`SERVICE_CATALOG` + 注入记录」构造 `app.state.module_registry`，并把 `product_key` 与注入记录分别落 `app.state.service_product_key` / `app.state.service_injected_records`（构造入参合并，未改常量、未引入进程级注册表）。
6. **启动校验改造**：`service_lifespan` 离线阶段在 `registry.validate()` 之后追加产品维度校验（仅声明 `product_key` 时）；`_validate_event_contracts(app)` 事件域改取 `registry.event_domains()`；`_validate_service_catalog` 对账清单改取 `registry.catalog_records()`（接库对账因此覆盖产品行 + 运行服务项）。
7. **用例**：新增 `libs/bms_core/tests/core/test_product_service_assembly.py`（8 例，Kiwi 2251；含装配启动与探针、注入合并视图、产品维度四项断言、合并冲突拒启、接库对账缺行 / 字段漂移、事件域按视图判定、平台服务视图不变）；同步适配 `libs/bms_core/tests/saga/test_saga.py` 的 `_validate_event_contracts(app)` 调用口径。
8. **验证**：见 §5（静态、类型、定向与全量用例、覆盖率、零漂移、基座与文档校验、推送前预检、状态一致性）。
9. **登记回写与记录**：见 §6 / §7。

## 4. 问题与处置 <a id="issues"></a>

| 问题 | 现象 | 处置 |
| --- | --- | --- |
| 产品维度校验入参口径 | 首版以**应用级合并清单**作入参 → 平台行（`product_key = None` / 非产品分组）被按产品记录误判，启动必失败 | 入参改为**注入记录**（`app.state.service_injected_records`，即 `service_records()` 产物）；合并清单仅用于离线清单校验 / 接库对账 / 事件域判定；已回写详设 §3.2 / §3.3 与对齐记录 5 |
| 登记要素形态 | 首版用例以 `mdm_org` 作 `module_key`、`mdm_org_` 作表前缀 → `module_key 非法` / `table_prefix 非法`（格式为 `^[a-z][a-z0-9]*$` 与 `{module_key}_`） | 用例改用 `mdorg` / `mdorg_`；把形态结论回写详设对齐记录 6（产品服务清单须按此形态登记） |
| 就绪探针口径 | 测试环境无 Redis，本地健康注册表 `redis` 检查项失败 → `/readyz` 503 | 假产品服务工厂覆写 `prepare_settings()` 置空健康注册表 provider（与脚手架「最小服务」同口径）；用例断言 `/readyz` 200 |
| 私有函数调用面 | `_validate_event_contracts` 由零参改为一参（取应用实例视图） | 同步适配既有用例 `tests/saga/test_saga.py`（构造应用后调用），保持断言不变 |
| 覆盖率口径 | `bms_core/application.py` 未达 100% | 未覆盖行均为**存量路径**（表归属接库降级 / 指标未装配 / 连接预算告警分支）；本次新增行全覆盖，实测结论如实登记（详设对齐记录 7） |

## 7. 偏差与遗留 <a id="deviations"></a>

- **实施偏差（已回写详设 §10 对齐记录 5~7）**：① 产品维度校验入参取**注入记录**而非应用级合并清单（合并清单含平台行，按产品维度判定会把平台行误判为产品记录）；② 登记要素形态核对结论（`module_key` 不含下划线、表前缀为 `{module_key}_`），用例以合法形态示范；③ Kiwi 编号回填 **2251**；④ 覆盖率实测口径如实登记（`application.py` 剩余未覆盖为存量路径）。
- **遗留（归口）**：① 产品档案与产品级路由映射的**产品侧注入不做**（平台侧登记职责，避免双事实源）→ 后续如需再评估；② 库数量指标 `kind=platform` 与 `ops.check_modules` 契约声明扫描口径**维持平台侧** → 产品可观测（阶段八）/ 产品侧自校验；③ 真实 git 源依赖安装与产品服务端到端启动实测 → **mdm 01_01**（跨仓消费方）；④ 模块级注销态建模与产品服务生命周期治理（下线 / 停用运行期处置）→ 后续数据库与治理阶段。
- **开放项**：产品服务清单的真实登记要素（服务键 / 模块键 / 表前缀 / 错误码段 / 事件域）随产品接入与 bms `org` 服务退役释放标识后定稿。
