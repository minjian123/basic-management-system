# 10 测试状态前提与常驻装配 · 详细设计

> 后端基座与服务化地基 · 13_测试执行粒度与工程效能 · 子任务 10

## 1. 背景与目标 <a id="goal"></a>

本任务要改的是**测试的前提假设**，不是测试的执行速度。

真实运行形态只有一种：进程长驻、库长期存在、数据由多方累积写入、多实例并发。测试若把「库为空」「库只被我使用」当作断言前提，那么它验证的行为在生产里不存在——绿也不代表对。业主口径（2026-11-23）：**在共享库上跑不通，说明用例写错了，改用例**；不得用独占库把「库里有别人数据」这一真实条件排除掉。

三条目标：

| # | 目标 | 判定 |
| --- | --- | --- |
| G1 | 断言只针对本次写入的数据 | 共享库**单轮**内断言不受库里既有数据影响（不靠「再跑一轮」兜底，见 §7.2） |
| G2 | 独占库只在「库是被测产物」时使用 | 白名单逐条可复核，其余全部回共享库 |
| G3 | 装配一次常驻 | 装配次数等于 worker 数；启动副作用（拓扑分发 / 能力登记 / 声明装载）每 worker 一次 |

### 2.3 现有夹具与判定 <a id="status-fixtures"></a>

- `service_app`（`backend/services/platform/tests/conftest.py`）：函数级 `ApplicationFactory().create(None)` + `lifespan_context`，每例执行一次；`clear_tenant_cache(app)` 在启动前清进程级租户缓存。

- 事件循环：`asyncio_mode = "auto"`、pytest-asyncio 1.4.0，未设默认 loop scope（即函数级）。

### 2.4 为什么「独占库」不是解法 <a id="status-why"></a>

独占库解决了「别人写的数据干扰我」，同时也把「别人写的数据存在」这一真实条件删掉了。它带来的绿是条件性的：

1. 数据形态不同——空库下的查询计划、唯一约束、分页、排序、缓存命中都与累积库不同；
2. 并发形态不同——独占库里永远只有一个写者，测不到并发写下的可见性与锁行为；
3. 装配副作用不同——独占库上每次装配都是首次装配，测不到「重复装配 / 已存在」的路径。

因此 G2 的判定不是「有没有用独占库」，而是「独占是不是被测对象本身」。

## 3. 决策与不动清单 <a id="decide"></a>

| # | 决策 | 结论 |
| --- | --- | --- |
| D1 | 运行形态 | 只有共享库一种；共享库跑不通即改用例 |
| D2 | 独占库范围 | 仅「建库 / 迁移 / DDL 即被测」，且不得用于规避库内既有数据 |
| D3 | 装配粒度 | 先文件级（module），再 worker 级（session）；两步都不得降低清理强度 |

| D5 | 验证方式 | 共享库上**全量单轮**通过即达判据；不以「再跑一轮才绿」兜底（2026-11-24 取消连跑两轮的门禁，2026-11-26 收敛 T7 判据） |

**不动清单**：0.1 秒忙等、一份库零复制、覆盖率门限 100%、`-n auto` 并行档、`[preflight.budget]` 数值与 600s 硬上限、《测试规范》《AI开发规范》既有条文。

## 4. 反模式定义与检测口径 <a id="patterns"></a>

四类反模式，都要可静态或半静态判定，并允许**带理由的显式豁免**（与 13_09 的 `session.info` 豁免同一思路：例外必须写在代码里）。

### 4.1 A1 空库前提断言 <a id="pattern-a1"></a>

判定形态（AST，**只拦高置信的两类**，2026-11-24 拍板）：

1. 聚合字段与零比较：断言 `<表达式>[<字面键>] == 0`，键属于 `total` / `count`；
2. 列表字段与空值全等：断言 `<表达式>[<字面键>] == []` / `{}` / `()` / `set()`，键属于 `list` / `items` / `rows`。

不计入：`len(...) == 0`（无法判断集合来自全表还是本次写入）、任意非空列表全等、`!=` / `<` 等非等值比较、裸属性、非字面键。为什么收窄：宽口径实测误报过高（`len(...) == 0` 204 处、任意列表全等 2123 处），拦不住新增反而逼人加豁免。

豁免：命中行或所属函数头部注 `# premise: own-data <说明>`，说明须能复核「这条断言只看本用例自己写的行」；说明为空视为未豁免。

### 4.2 A2 逐例重装 <a id="pattern-a2"></a>

判定：`service_app` 或同类「建应用 + 走 lifespan」夹具的 scope 为默认（function）。终态允许 `module` / `session` / `package`：

- 先做 B1（module），取得同文件复用样本；
- B2（session，xdist 下即 worker 级）需先做 3 文件探针；
- 两者都不得降低每例的状态复位强度。

豁免：夹具头部注 `# premise: per-case <说明>`，写明为什么这条装配不能常驻（如「该用例验证装配失败路径」）。

### 4.3 A3 独占库滥用 <a id="pattern-a3"></a>

判定：`pytest.mark.own_db("理由", scope="…")` 缺 `scope`，或 `scope` 不在六类合法取值内：

| `scope` | 含义 | 机器条件 |
| --- | --- | --- |
| `ddl` | 建表 / 迁移 / DDL / 表结构差异本身即被测 | — |
| `create` | 建库 / 建 schema 本身即被测 | — |
| `seed` | 种子装载 / 初始化数据派生本身即被测 | — |
| `topology` | 租户拓扑 / 分片 / 库路由派生本身即被测 | — |
| `memory` | 内存库（不落文件、不产生跨用例状态） | — |
| `external` | 真外部服务联调 | 同作用域必须带 `integration` 标记 |
| `destructive` | 破坏性全局操作本身即被测（按租户批量撤销全部会话、整表清场等） | — |

**不设**「全库口径 / 全局状态即被测」类别——那正是「靠库里只有我的数据」的写法，与业主口径冲突。存量 98 处先入基线，改造时逐批补 `scope` 并递减。

### 4.4 A4 全局状态独占锁 <a id="pattern-a4"></a>

判定：`file_lock("platform-global-state")` 出现即计入存量。终态：使用面清零（装配常驻后不再需要整段独占）——**已于 2026-11-25 清零**，替代手法见 §7.3。

## 5. 装配常驻设计 <a id="boot"></a>

### 5.1 三阶段模型 <a id="boot-phases"></a>

装配不是某个测试模块 / 会话的私事，而是**系统启动的一个独立阶段**：初始化完成后，整套系统装配一次，之后才对外（并发）使用。测试必须复刻这个顺序：

| 阶段 | 内容 | 发生次数 | 测试侧载体 |
| --- | --- | --- | --- |
| ① 初始化 | 建库 / 播种 / 配置就位 | 每进程一次，先于装配 | 现有测试插件入口（`bms_testing_plugin`） |
| ② 全系统装配 | 创建并启动**本仓全部后端服务**的应用（全部 lifespan），登记为「已装配系统」 | 每进程一次 | 会话首个用例之前执行的装配组件（`AssembledSystem`） |
| ③ 并发使用 | 用例作为用户访问已装配系统 | 每用例任意次 | `client` 从已装配系统取对应服务实例，不再自行创建 |

**为什么不是函数级 / module 级 / 会话级“按服务”装配**：

- 函数级：隐含「每个用例都是冷启动」，与进程长驻不符；
- module 级：隐含「同一文件的用例独占一个 app」，且 xdist `--dist=loadgroup` 下同一模块可能被多个 worker 各装配一次，「每模块一次」并不成立；
- 只装配被测服务：隐含「其他功能没有在跑」，与「库是干净的」同属错误前提——真实运行是所有服务一起启动、一起对外。

**次数口径**：装配次数 = 进程数（xdist 下 worker 数；串行 1 次）。进程之间无法共享实例，生产也是每个实例各自启动一次，故「每进程一次」是与调度方式无关的终态。

**落地形态（2026-11-24 拍板）**：本模型直接作为终态落地，**不保留 module 级 / 函数级中间态**。通知 / 文件 / 报表 / 检索 / AI / 租户 / 身份七个服务的 module 级实现已完成验证（「隔离可提级」与「每例复位」成立），结论作为实现依据保留，代码侧一次性切到全系统装配；`service_app` **一刀切为「只取装配实例」**，自建路径删除，仅 `own_db` / `destructive` 用例保留自带 app。落地节奏为**一次改完再跑完整会话**，不按服务分批验收。

### 5.2 事件循环与装配时序 <a id="boot-loop"></a>

装配组件是**异步**的（要进入每个服务的 lifespan），且应用实例必须与其事件循环同生共死：

- **已拍板（2026-11-24）**：全局设 `asyncio_default_test_loop_scope = "session"`，装配与全部用例在同一会话循环内运行；**不采用**「只给依赖装配的用例加 session loop」的双语义方案。
- 影响面：约 72 个自建 loop / `asyncio.run(` 的文件逐个判断是否触碰装配系统——触碰者改为会话循环内执行，不触碰者保持原样；改动后由**全量单轮**兜底。
- 装配在**初始化完成之后**执行：装配夹具依赖共享库的会话级夹具，确保「建库 / 播种 → 装配 → 用例」顺序固定，不依赖收集顺序。

### 5.3 每例必须清理的进程内状态 <a id="boot-clean"></a>

装配常驻后，以下状态跨用例存活，必须每例复位（复位点放在夹具 teardown，不放进用例）。**同时禁止用例自身改 app 状态**（`dependency_overrides` / `app.state` / 全局 Settings，规则 P5）：那是「假设只有我在用这个进程」，与干净库前提同类。

| 状态 | 位置 | 复位方式 |
| --- | --- | --- |
| 租户源缓存 | `app.state.tenant_source.cache` | 现成 `clear_tenant_cache(app)` |
| 插件实例缓存 | `PluginRegistry._instances` | 装配期已清；常驻后需在每例前后各清一次或提供 `reset_instances()` |
| 审计捕获开关 / 表清单 | `bms.audit` 模块级 | 现成 `reset_audited_tables()` |
| 审计事件暂存区 | `bms_core.audit.staging`（ContextVar） | 现成 `reset_staged()`；由 `bms_core.testing.plugin._reset_audit_staging` **单列夹具**承担，不在 `_reset_assembled_per_test` 内（暂存区是 ContextVar，与「已装配系统缓存」不是一类状态，混在一处会让两件事的复位时机互相牵制） |
| 事件订阅 | 进程级消费者表 | 装配一次后不变；用例不得增删 |
| 消费方能力使用声明 | `bms_core.collaboration.usage._CONSUMER_USAGES` | 装配期由注册表投影登记一次；**用例不得复位**——`load_product_manifests` 只登记八类记录、不含使用声明，复位后补不回来。每例重建视图族时按清单**补登记**（同值幂等）；丢声明的后果是 `call_capability` 找不到降级策略、把取用失败原样上抛（能力取用 `40003` 变成 500） |
| 依赖覆盖 | `app.dependency_overrides` | 每例 teardown 清空——仅作 P5 基线的过渡兜底，收敛方向是请求级注入 / 装配期声明 |
| Settings 缓存 | `get_settings` | 现状每例 `cache_clear()`；常驻后只在显式配置用例里清 |

### 5.4 失败隔离 <a id="boot-fail"></a>

全系统装配后，风险是「一个用例把系统弄成不可用，后续全红」。约束：

1. 用例不得修改 app / 服务 / 全局单例（P5），只能通过 API 行为观察；
2. 装配失败**即会话失败**（fail fast），不允许「跳过某个服务继续跑」——生产不会带病启动；
3. 确需验证「装配失败 / 启动路径」的用例改为服务层直连或纯逻辑断言，**不建 app**——自建 app 等于第二次装配，与本模型冲突；
4. 某个用例把数据改坏不构成系统不可用：数据由命名空间隔离，用例自己清理。

### 5.5 装配组件（`AssembledSystem`） <a id="boot-component"></a>

| 项 | 设计 |
| --- | --- |
| 落点 | `backend/libs/bms_core/src/bms_core/testing/system.py`（新增；测试基座内，产品仓可复用） |
| 服务清单 | **单一来源** `SERVICE_CATALOG`（`services/module_registry.py`）；工厂按服务键取各自 `ApplicationFactory`，不另写清单 |
| 装配载体 | 根 `conftest.py` 的 `assembled_system` 改为 **autouse session 级**异步夹具：会话首个用例前、初始化完成之后执行；退出时逆序 `aclose` |
| 开关 | **默认开启**；`BMS_TEST_ASSEMBLED=0` 反向关闭（仅用于切换期排障，不作日常口径） |
| 在册登记 | 进程级单例 `get_assembled_system()`；`service_client` 的地址表由它提供 |
| 取用 | `system_client(service_key)` 返回 `AsyncClient(ASGITransport(app=apps[key]))`；各服务 `service_app` **一刀切**为 `get_assembled_system().app(<服务键>)`，不再创建 app；`xxx_module_env` 仅保留给自带 app 用例 |
| 跨服务直连 | `BaseServiceClient` 的 provider 换成进程内实现：按 `base_url` 里的服务键路由到 `apps[key]`，走真实路由与鉴权；失败 / 超时语义与生产一致 |
| CI 对端 | **装配不装载对端声明**（总体架构是「[产品自持、装载注册](../../../../../../设计/架构设计/03_架构设计_总体架构.md#principle)」：平台不写产品声明、不读产品仓）。CI 只 clone bms 与本地工作区因此跑同一套装配；需要跨产品前置的用例自己造（能力声明 + 拓扑快照，按模块夹具登记、用完复位）；**本仓不保留任何对端声明副本**（装配夹具与平台用例夹具都已清空） |
| 取证 | 组件内计数器（装配次数 / 装配完成时刻）；护栏用例断言「一轮会话恰好 1 次，且早于首个用例」 |
| 每例复位 | 对全部已装配 app 清租户缓存与 `dependency_overrides`；复位请求上下文、审计捕获、权限缓存；**不重建 app** |
| 事件循环 | 全局 `asyncio_default_test_loop_scope = "session"`；装配与用例同循环 |
| 独立 app | **不设例外（2026-11-24 拍板）**：任何用例都不得自建 app。`own_db` 分两类处理——库已存在、装配前可入库路由表的（`destructive` / 特殊数据形态）走共享装配；库初始状态 / 启动路径本身即被测的（拓扑自举 / 建库 / DDL）改为服务层直连或纯逻辑断言，执行段由初始化阶段真实跑一次 |

**组件级验证（已完成，2026-11-24）**：装配组件单测 5 条全绿；进程内直连、调用方服务身份与对端声明装载在受控开关下验证通过（`identity → tenant` 真实内部契约调用返回 200）；`BMS_TEST_ASSEMBLED=1` 下装配一次、用例并发使用不串状态。

**用例级验证**：终态切换后由「全量单轮」统一承担，不再单设探针阶段——探针要证的三件事（装配次数 / 直连 / 状态复位）已由组件级验证与护栏用例覆盖。

## 6. 用例改造口径 <a id="case"></a>

### 6.1 唯一命名空间 <a id="case-ns"></a>

沿用基座 `Namespace` 夹具（`ns.prefix`），所有业务键、手机号、产品键、模块键带前缀；断言只按前缀过滤。

### 6.2 只断言自己写入的数据 <a id="case-own"></a>

改造前 → 改造后：

| 改造前 | 改造后 |
| --- | --- |
| `assert resp.json()["data"]["total"] == 0` | `assert all(item["key"].startswith(ns.prefix) for item in ...)`，或断言按前缀过滤后的条数 |
| `assert [x["key"] for x in data] == expected` | `assert set(expected) <= {x["key"] for x in data}` |
| `assert row.version == 1` | `first = ...; assert first >= 1`，再断言第二次严格递增 |
| `assert product["frontend_package_source"] == ...`（取首页 20 条） | 索引取全量（`size=200`）或按 `product_key` 单查 |

### 6.3 前置显式构造 <a id="case-pre"></a>

需要「某条数据存在」时，由用例自己写入（带唯一前缀），不依赖库里既有行；写入后立刻断言「写成功」，再断言被测行为。

## 7. 独占库退场 <a id="own-db"></a>

### 7.1 保留范围 <a id="own-keep"></a>

**2026-11-25 收紧为一条**：除「真外部服务联调」外**一律不保留**。开发、生产、测试中都不存在「分给某个用例一个库」的形态，凡使用平台共享库与租户共享库之外的库即为错误。

| 类别 | 原形态 | 改造后 |
| --- | --- | --- |
| 建库 / 引擎 / 库名派生 | 临时库验证建库、引擎构造、库键派生 | **纯逻辑断言**库名 / 连接串 / 库键的派生结果；真实建库由初始化阶段跑一次 |
| 建表 / 迁移 / DDL / 表结构差异 | 自带库建表、跑迁移、造缺表 / 多表 / 列漂移 | **断言生成段内容**（SQL / 目标清单 / 差异报告）；执行段由初始化阶段真实跑一次（已确认结论 10） |
| 播种 / 种子 CLI | 私有库上跑播种编排 | 在共享库上跑（按清单幂等 upsert），断言「跑完再跑结果不变」与清单内行 |
| 多租户拓扑（一租户一库） | 真派生多个租户库文件 | **纯逻辑断言**库名与连接串派生；真实派生由初始化阶段承担 |
| 内存库 / 临时单文件库 | `:memory:` / `tmp_path` 建库 | 共享库 + 唯一命名空间 |
| 破坏性数据形态（如损坏 JSON 行） | 放进独立库避免波及他人启动读取 | 事务内构造 + 回滚（不落共享库），或改为纯逻辑断言解析失败 |
| 破坏性全局操作（按租户批量撤销全部会话） | 专用租户库 | 该实现是**整库撤销**（`list_active_all`），共享库上必波及其他用例。处置：用例改为断言「撤销集合包含本次播种的会话」并只对本次会话断言活跃数；实现若无法按租户隔离，缺陷登记到该服务任务，**不在测试侧用独占库兜住** |

**唯一保留**：真外部服务联调（真 Redis / 真 MySQL / 真达梦）。它们连部署环境的真实服务，连接串来自配置、缺配即跳过，**不建库、不落测试文件**；跨库 2PC 与达梦 XA 验的就是两阶段提交本身，替身无法替代。

### 7.2 退场路径 <a id="own-exit"></a>

按域推进，每域一批：`platform` → `bms_core` 运维与工具类 → 播种类 → 其余服务；文件锁（`platform-global-state`）随对应域一并退场。每批的退出条件：

- 该域内 `own_db`、`isolated_*`、`:memory:`、`tmp_path` 建库**清零**（真外部联调不计）；
- 该域在共享库上**全量单轮**失败 0（不要求再跑一轮：单轮不成立即为用例写错，见 D5）；
- 覆盖率门禁仍 100%（改造后用例覆盖的行不能少）。

### 7.3 文件锁删除 <a id="own-lock"></a>

设计计 10 处 `platform-global-state`，其中 `registry/test_tenant_topology_bootstrap.py` 一处随平台域首批独占库退场（2026-11-25），**剩余 9 处**随装配常驻逐条删除并已清零（2026-11-25）。删除顺序：先删「只读类」（装配一次后无可变全局状态）→ 再删「写入类」（用例自带唯一前缀，互不干扰）。

**替代口径**：跨进程互斥改为「**同组用例不分发到不同 worker**」——这 9 个文件统一打 `pytestmark = pytest.mark.xdist_group("platform-global-state")`（每个文件只允许一个分组标记，多标记会被 xdist 拼成新组名而失去互斥），落在同一 worker 上组内串行；互斥集合与删除前的文件锁完全一致，只是不再跨进程等锁。**P4 口径不变**：`file_lock("<全局状态锁名>")` 出现即违规，禁用面清零。

## 8. 护栏 <a id="guard"></a>

### 8.1 落点 <a id="guard-place"></a>

判定实现**只落 engkit**（跨仓单一实现），bms 侧只留薄包装：

| 层 | 位置 | 职责 |
| --- | --- | --- |
| 判定实现 | `engkit` 包内 `base/test_premises.py` | AST 扫描、基线读写、内置自测 |
| 命令行 | `engkit base test-premises` | `--self-test` / `--files-from` / `--list-own-db` / `--update-baseline` |
| 规则数据 | 仓根 `engkit.toml` 的 `[rules.test_premises]` | 扫描根 / 字段名 / scope 枚举 / 锁名 / 基线路径 |
| 仓内入口 | `scripts/tools/base_check/check_test_premises.py` | 参数转发与退出码透传，不含推导 |

不并入既有 `check_test_db_isolation.py`：口径不同（状态前提 vs 库隔离），混在一起会让豁免逻辑互相牵制。

### 8.2 规则与豁免 <a id="guard-rules"></a>

| 规则 | 判定 | 豁免 |
| --- | --- | --- |
| P1 | A1 两类高置信形态 | `# premise: own-data <说明>` |
| P2 | A2 函数级装配夹具 | 夹具头部 `# premise: per-case <说明>` |
| P3 | A3 缺 `scope` / 越界 / `external` 无 `integration` | 无（补齐分类即可） |
| P4 | A4 `platform-global-state` 使用 | 无（存量清零） |
| P5 | 用例改 app 状态：`dependency_overrides` / `app.state` / 全局 Settings 写入 | 无（改用请求级注入或自带 app） |

存量用基线文件（`deploy/boundaries/test_premises_baseline.json`）承接，按「文件 + 规则码」计数，只减不增，与 pragma 理由基线同一套路；行号变动不失效。

### 8.3 自测 <a id="guard-selftest"></a>

- 每条规则给正例 / 反例各一组，断言「命中 / 不命中」，并覆盖豁免注释、空说明、`external` 的 `integration` 机器条件与模块级标记；
- P5 覆盖四类写法（`dependency_overrides` 赋值 / 容器方法、`app.state` 属性赋值 / 整体替换、`get_settings()` 与 `settings` 变量属性写入、`setattr` / `delattr` 反射写）与「只读访问 / 局部变量 / 其它对象不误判」；
- 判定向量由 `--self-test` 唯一覆盖（现 33 条，P5 已并入），pytest 用例只补 `self_test` 够不到的分支（文件枚举、增量清单、基线读写与只减不增），避免同一向量抄两遍。

### 8.4 P5 判定细则 <a id="guard-p5"></a>

| 形态 | 判定 |
| --- | --- |
| 依赖覆盖 | 对 `*dependency_overrides[...]` 赋值、整体赋值，或 `.update` / `.clear` / `.pop` / `.setdefault` 被调用 |
| app 状态 | 对 `*.state.<属性>` 赋值、`state` 整体替换，或 `setattr` / `delattr` 指向 `*.state` |
| 全局配置 | 对 `get_settings()` 返回值属性赋值（如 `.session.max_active =`），或对 `settings` 变量属性赋值（含 `settings = get_settings()` 后再写） |
| 反射写 | `setattr` / `delattr` 第一个参数命中上述任一容器 |

不命中：只读访问（`dependency_overrides.get` / `app.state.x` 读取）、普通字典与局部变量写入、其它对象的 `setattr`。

豁免：**不设行内豁免**（2026-11-24 拍板）。静态判据无法区分共享装配与自带 app，自带 app 内的写入同样进基线；收敛方向是请求级注入或装配期声明。存量进基线，只减不增。

## 10. 验收判据 <a id="accept"></a>

1. 全量在同一份共享库上**单轮**跑通：失败 0、`database is locked` = 0、无「等待测试锁超时」。**不判「两轮」**：连跑两轮的门禁已于 2026-11-24 取消（用例必须在共享库上单轮成立），2026-11-26 同步收敛本判据。
2. `own_db` 与 `isolated_*` 只剩 DDL 类，逐条理由可复核；`platform-global-state` 使用面清零。
3. 装配次数等于进程数（xdist worker 数）；同一进程内用例不重复触发装配。
4. 静态护栏 P1~P5 全部生效，基线只减不增，自测覆盖正反例。
5. 覆盖率门禁 100%，选中文件数与改造前一致（无漏测）。
6. `service_app` 无自建路径：各服务 conftest 不再出现 `ApplicationFactory().create`，取到的实例均来自已装配系统。
7. CI（只 clone bms、产品仓缺席）与本地跑同一套装配：装配不装载对端声明，跨产品前置由用例自造（本仓不保留任何对端声明副本）。
8. 测试目录无自建 app：`ApplicationFactory()` 在 `tests/` 下为 0 处；`own_db` 用例均走服务层直连或纯逻辑断言。

## 11. 实施步骤 <a id="steps"></a>

> 口径注（2026-11-26）：下面步骤 3 / 4 / 5 / 8 里出现的「两轮」是 2026-11-24 之前的执行记录（当时按两轮判定）；**现行判据为单轮**（D5 与 §10 第 1 条），历史痕迹保留以便回溯。

1. **盘点**：逐文件标注 `own_db` / `isolated_*` / `service_app` / 空库前提断言，产出「保留 / 改造」清单（T1，已完成）。
2. **护栏**：先落 P1~P4 与基线，锁住新增（T3，已完成）；P5（改 app 状态）已落（532 项存量进基线，见实施记录 §12）。
3. **样本**：选 1 个文件做「共享库只断言自己写入」的改造样本，两轮复用验证（T5 试点，已完成）。
4. **全系统装配（T4，本轮）**：终态一次落地——组件计数器 → `assembled_system` 改 autouse 且默认开启 → 全局 session loop → 9 个服务 conftest 切「只取装配实例」→ 用例适配（P5 过渡清理）→ CI 内置对端替身；**一次改完再跑全量两轮**，不按服务分批验收。
5. **按域清存量**：platform → bms_core → 其余服务；每域两轮复用验证（T5）。
6. **文件锁退场**：随装配常驻逐条删除（T6）。
7. **P5 存量收敛**：把 `dependency_overrides` / `app.state` / Settings 写入逐批改为请求级注入或自带 app，基线递减。
8. **验收与回写**：全量两轮、覆盖率、装配次数取证、口径回写（T7 / T8）。
