### 0.1 阶段模型

每一轮测试**固定三个阶段，顺序不可颠倒**：

| 阶段 | 做什么 | 次数 |
| --- | --- | --- |
| 1 初始化 | 建库 / 建表 / 播种（种子租户、系统参数、表归属、服务目录、产品档案）+ 执行本次变更产生的迁移脚本 | **每轮一次** |
| 2 装配 | **一次装配阶段**内把**全部后端服务**（platform / identity / tenant / txn / ai / file / notification / report / search）装配完毕（每个服务各一个实例，同属这一次装配），形成已装配系统 | **全系统只装配一次**，不随用例数增长 |
| 3 跑用例 | 用例只作为用户发请求 / 断言，**并发执行**；跨服务调用直接打已装配对端 | 全部用例 |

**装配范围 = 全部服务，不是「只装配被测服务」**。跨服务路径（权限来源、缓存、限流、内部契约调用）本身就是检测目标；预设「只有一个服务在跑」与「库是干净的」同属错误前提。

**装配的启动形态未定**：真实进程与端口、或同进程应用对象，属设计决策，业主未选择；未定前不得按其中一种写死实现。

由此引出的实现要求：**进程级单值必须按应用隔离**。多个服务同时运行时，权限数据来源、缓存区域、限流器、权限快照仓等若仍是「进程级最后登记生效」，A 服务的请求会走到 B 服务的实现——这是必须修的缺陷，不是可以绕过的障碍。

### 0.2 推论（必须遵守）

1. **装配不得发生在用例执行期**。用例、用例级夹具都不得调用 `ApplicationFactory().create()`；`service_app` / `client` 一律从第 2 阶段的已装配系统取实例。
2. **全系统只装配一次**：装配阶段执行一遍，把所有服务装配完；此后整个用例阶段不再有任何装配动作（不重建、不补装、不按需装配）。
3. **用例只消费，不承担装配**。用例文件不需要为「拿到应用」写任何东西；某个服务固化「一次装配」由该服务的 `conftest.py` 负责。
4. **不重写用例、不逐文件迁移**。用例的断言与数据准备是既有资产，保持不动；迁移动的是装配阶段与夹具。
5. **不做「分层重构」**。不把接口用例降成组件级、不引入「最小应用 + 替身」的第三条路；真实装配是既定前提（本任务的核心就是让测试前提与真实运行一致）。
6. **初始化与装配是显式阶段**，不靠「第一个用例顺手触发」。取证标准：装配发生在第一个用例之前，一轮只装配一次。
7. 「每个用例都建一次应用」是**缺陷**，不是基线；存量按此口径逐个服务铲除，不设「渐进保留」开关。

### 0.3 判定「改好了」的取证

- 装配入口计数（`ApplicationFactory().create` / lifespan 进入次数）：一轮只装配一次，且发生在第一个用例之前；
- 用例数 N 增加时，装配次数**不变**；
- 单文件耗时随用例数线性增长的部分只剩「造数 + 请求」，不再有固定装配开销。

## 4. 检测口径（T2） <a id="rules"></a>

口径落点：本节为权威表述，护栏实现见 §5；《测试规范》§2.1 / §4 摘录本条并指回本文件。

### 4.1 P1 空库前提断言 <a id="rule-p1"></a>

只拦**高置信、无歧义**的两类形态（避免宽口径误报把正常断言也拦掉）：

| 形态 | 判定 | 示例 |
| --- | --- | --- |
| 聚合字段与零比较 | 断言 `<表达式>[<字面键>] == 0`，键属于 `total` / `count` | `assert body["data"]["total"] == 0` |
| 列表字段与空值全等 | 断言 `<表达式>[<字面键>] == []` / `{}` / `()` / `set()`，键属于 `list` / `items` / `rows` | `assert body["items"] == []` |

不计入：`len(...) == 0`（无法判断集合来自全表还是本次写入）、任意非空列表全等、`!=` / `<` 等非等值比较、裸属性（`body.total`）、非字面键（`body[key]`）。

**豁免**：命中行或所属函数头部注 `# premise: own-data <说明>`；说明必须非空且能复核「这条断言只看本用例自己写的行」。豁免只对单条断言生效，不因文件头注释整片放行。

### 4.2 P2 逐例重装 <a id="rule-p2"></a>

判定：装配夹具（`service_app` 一类「建应用 + 走 lifespan」）的 `scope` 不是 `module` / `session` / `package`。

**豁免**：夹具头部注 `# premise: per-case <说明>`，须写明「为什么这条装配不能常驻」（例如该用例验证装配失败路径，自带独立 app）。豁免写在夹具定义处，不写在用例里。

### 4.3 P3 独占库分类 <a id="rule-p3"></a>

`@pytest.mark.own_db("理由", scope="…")` 必须带 `scope`，取值限六类；**新增不带即拦**：

| `scope` | 含义 | 机器条件 |
| --- | --- | --- |
| `ddl` | 建表 / 迁移 / DDL / 表结构差异本身即被测 | — |
| `create` | 建库 / 建 schema 本身即被测 | — |
| `seed` | 种子装载 / 初始化数据派生本身即被测 | — |
| `topology` | 租户拓扑 / 分片 / 库路由派生本身即被测 | — |
| `memory` | 内存库（不落文件、不产生跨用例状态） | — |
| `external` | 真外部服务联调（如真机 Keycloak） | **同一作用域必须带 `@pytest.mark.integration`**（模块级 `pytestmark` 或逐用例标记） |
| `destructive` | 破坏性全局操作本身即被测（按租户批量撤销全部会话、整表清场等） | — |

不设「全库口径 / 全局状态即被测」类别：那正是「靠库里只有我的数据」的写法，与业主口径冲突。

### 4.4 P4 全局状态独占锁 <a id="rule-p4"></a>

判定：`file_lock("platform-global-state")` 调用即命中；终态要求使用面清零。新增没有豁免——真实系统里不存在「整段全局状态只有我一个写者」的窗口。

### 4.5 豁免与存量承接 <a id="rule-baseline"></a>

- 豁免必须写在代码里（`# premise: <类别> <说明>`），说明为空视为未豁免。
- 存量承接：`deploy/boundaries/test_premises_baseline.json`，按「文件 + 规则码」计数，**只减不增**；治理后跑 `--update-baseline` 递减。
- 基线不按行号记账：行号变动不失效，新增同类命中才会判失败。

## 5. 护栏实现（T3） <a id="impl"></a>

### 5.1 落点与数据 <a id="impl-place"></a>

| 层 | 位置 | 职责 |
| --- | --- | --- |
| 判定实现 | `engkit/src/engkit/base/test_premises.py` | AST 扫描、基线读写、内置自测 |
| 命令行 | `engkit base test-premises` | `--self-test` / `--files-from` / `--list-own-db` / `--update-baseline` |
| 规则数据 | `bms/engkit.toml` 的 `[rules.test_premises]` | 扫描根、字段名、scope 枚举、锁名、基线路径 |
| 仓内入口 | `bms/scripts/tools/base_check/check_test_premises.py` | 只做参数转发与退出码透传（薄包装） |
| 预检接线 | `bms/engkit.toml` 的 `[[preflight.steps]]` | 全量档固定跑，新增命中超基线即失败 |

为什么落 engkit：判定逻辑跨仓复用（mdm 同款），bms 侧只留包装，避免「一处改动维护两套判定」。

### 5.2 判定实现要点 <a id="impl-ast"></a>

| 要点 | 做法 | 理由 |
| --- | --- | --- |
| 用 AST 不用正则 | 断言、装饰器、`pytestmark` 都按节点解析 | 注释 / 字符串里的同形文本不误判 |
| 空字面量按节点判 | `[]` / `{}` / `()` / `set()` 都是容器或调用节点，不是 `Constant` | 按 `Constant` 判会整类漏掉「列表全等空」 |
| 模块级标记两种形态 | `pytestmark = [pytest.mark.own_db(...)]` 与 `pytestmark = pytest.mark.integration` 同判 | 整份文件打标是主流写法 |
| 豁免说明必须非空 | `# premise: own-data` 后必须有文字 | 空说明等于没有前提，必须拦 |
| 注释判定要求真注释 | `premise:` 前必须出现 `#` | 字符串里的同形文本不算 |
| 双向外置 | `total == 0` 与 `[] == items` 都判 | 断言写法不该改变判定结果 |
| 扫 `conftest.py` | 扫描范围同时收 `test_*.py` 与 `conftest.py` | P2 判的是装配夹具，只扫用例文件会整片漏掉 |

### 5.4 自测与用例 <a id="impl-test"></a>

## 10. T4-B1 装配常驻（通知服务） <a id="b1"></a>

### 10.1 试改暴露的结构性阻塞 <a id="b1-blocker"></a>

首次只改 `service_app` 的 scope 与 loop scope（19 个用例），14 个 setup error。根因：

- pytest **先建高作用域夹具**，模块级 `service_app` 会早于函数级 `isolate_settings` / `fake_tenant_source` 执行；

## 11. 装配模型修正（业主口径，2026-11-24） <a id="model-revision"></a>

### 11.1 修正内容 <a id="revise-content"></a>

业主指正：装配不应落在会话级 / 模块级——那等于预设「只装配了本次要测的那部分功能」；真实运行是**全系统在初始化之后装配一次，之后才并发对外**。只装配被测服务、或让每个模块各装配一次，都与「库是干净的」同属错误前提。

据此确认四项：

| 项 | 结论 |
| --- | --- |
| 装配范围 | 本仓全部后端服务（platform / identity / tenant / txn / ai / file / notification / report / search） |
| 跨服务调用 | 进程内直连已装配服务（真实路由与鉴权链路） |
| 用例约束 | 新增 P5：不得改 `dependency_overrides` / `app.state` / 全局 Settings |
| 验证方式 | 3 文件探针先行；完整两轮只在合入时跑一次，不再用全量两轮做内层循环 |

| platform 237 条失败 | 不再逐文件适配；按 P5 反模式清单收敛（改 app 状态 → 基线只减不增） |

## 14. 装配常驻的实测经验（2026-11-24，装配落地同轮） <a id="assembly-lessons"></a>

装配从「每例建 app」切成「会话级常驻」后，**用例的前提假设整体变了**：原先「每个用例独占一个刚建好的 app」时期写下的隔离手法，很多在常驻形态下会静默破坏装配态。以下四条都是本轮实测踩到的，配置 / 装配侧已修，记在此处供后续改造对照。

### 14.1 配置串味：`[app].service` 回写与装配后未复位 <a id="lesson-config"></a>

同进程装配九个服务时，`Settings` 是单例形态，`[app].service` 会被**最后装配的那个服务**回写，表现为：平台请求的日志里 `service=txn`、按服务键取配置取到别家的值。

处置（已落）：

- `get_settings` 改为按服务键分槽（ContextVar + 按服务键缓存），装配期用 `before_create` 切键；
- 装配结束**必须复位为空**（`reset_current_service`），否则非装配路径（自建 app / 后台任务 / 声明校验）会一直读最后一个服务的配置；
- 请求期由 `ServiceContextMiddleware` 按 `scope["app"]` 的服务身份切键与复位，保证「一个请求 = 一个服务身份」。

用例侧推论：**请求之外拿到的 `get_settings()` 是默认单例，不是应用读的那个实例**。要在用例里改配置（如临时换帮助包根目录），必须取该服务槽的实例——`bms_core.testing.fixtures.service_settings(<服务键>)`；改默认单例会得到「配置改了但端点行为没变」。

### 14.2 声明重复装载 <a id="lesson-declare"></a>

对端（产品仓）清单**只能在装配前装载一次**。逐应用重复装载会重复注册，且后装的清单顶掉先前注册的记录（同键异值直接抛 `CatalogError`），表现为装配期随机拒启。处置：`peer_manifest_paths()` 的结果在 `assemble()` 之前装载一次，各应用只装**本仓**清单。

> **2026-11-25 更正（该做法已撤销）**：按总体架构「[产品自持、装载注册](../../../../../../设计/架构设计/03_架构设计_总体架构.md#principle)」，平台**不读产品仓**——`peer_manifest_paths()` 扫描工作区读兄弟仓清单会让本地与 CI 跑成两套装配，已删除；装配不再装载任何对端声明。需要跨产品前置的用例自造（能力声明 + 拓扑快照，按模块夹具登记、用完复位），**本仓不保留任何对端声明副本**（平台用例夹具里那处 `_MDM_PEER_CAPABILITIES` 也已删除）。本条只留「重复装载会撞键」这一事实，处置以详设 §5.5「CI 对端」为准。

### 14.3 审计事件暂存区 <a id="lesson-staging"></a>

`bms_core.audit.staging` 的暂存区是 ContextVar，装配常驻后会在用例之间存活：上一例 stage 的事件会在下一例请求收尾被一并 drain，表现为「本用例多出不属于它的事件」。处置：每例前后 `reset_staged()`，由 `bms_core.testing.plugin._reset_audit_staging` **单列夹具**承担（不与「已装配系统缓存」复位混写，详见详设 §5.3 对应行）。

### 14.4 用例 monkeypatch 模块级类 / 函数会被常驻系统吃到 <a id="lesson-monkeypatch"></a>

「用 `monkeypatch.setattr(<模块>, "<函数>", 替身)` 改行为」在每例建 app 的时代是可用的；常驻后**被改的是整个进程共用的模块对象**，装配好的应用下次请求就会走到替身上，且改动力度往往远超用例本意（例如让平台主体链的降级声明凭空消失）。

处置方向：**改成构造参数注入**——`OperationAuditMiddleware(emitter=...)` 就是样板（把替换点从模块属性改成构造入参）；需要临时换掉某个协作者时，优先走装配期声明（provider 配置）或构造注入，不要再改模块级名字。

### 14.5 装配期登记的进程级声明不能被每例复位 <a id="lesson-declarations"></a>

消费方能力使用声明（`platform.toml` 的 `[[usages]]`）由注册表投影在**应用启动时**登记一次；`load_product_manifests` 只登记八类记录、不含使用声明。平台侧原先的每例「复位视图族 + 重载清单」把使用声明一并清掉，装配常驻后没有第二次登记机会，于是 `call_capability` 找不到声明、按「未声明降级」把取用失败原样上抛：平台主体链解析 `mdm` 角色时能力取用失败（`40003`）直接变 500，帮助域整片用例变红（详见 §15.1）。

处置：每例重建视图族时**按清单补登记使用声明**（同值幂等），清单重载与声明登记保持同源。

### 14.6 依赖提供者重新解析 vs 装配实例 <a id="lesson-wiring-instance"></a>

装配常驻后，服务持有的是**装配期**实例（`app.state.<能力>`，如 `DbTranslatorFactory` 取 `app.state.i18n_cache_region`）；而 `get_cache_region` / `get_i18n_cache_region` / `get_i18n_invalidator` 原先每次请求 `resolve_plugin(...)` 现取。每例复位插件注册表后，请求侧解析出的是**第二个实例**：写路径在新实例上删缓存 / 递增版本，翻译器在装配期实例上命中旧缓存，表现为「保存成功、下发不生效」（`i18n/test_messages_dispatch.py` 两例 `KeyError`；菜单元数据版本同理）。

处置：三个依赖提供者改为**优先取 `request.app.state.<能力>`**，未设置（单测自建 app）才回退 `resolve_plugin`。口径：依赖提供者返回的是「应用装配的实例」，不是「按配置再解析一次」。

### 14.7 未部署产品的使用声明不得拒启 <a id="lesson-usage-deployed"></a>

`platform.toml` 的 `[[usages]]` 声明了 mdm 能力，而 bms 单仓 / cws 工作区没有 mdm。原先启动校验「声明了未登记的能力」直接拒启，连带新建 app 的用例（如 `api/test_role_api.py` 的 `role_client`）14 例全 ERROR；此前靠 conftest 全局塞 mdm 声明掩盖。

处置：`inspect_capability_usages` 按**已部署产品**收敛——能力名第一段不在已登记产品集合即跳过并告警；产品在场仍 fail-fast（口径见[《38 跨产品协同》](../../../../../../设计/架构设计/38_架构设计_子系统_跨产品协同.md#resolve)）。bms 单仓 / cws 工作区可正常启动。
