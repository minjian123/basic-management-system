### 2.7 读门口径修正（S9，实施期发现的偏差） <a id="process-readgate"></a>

**现象**：`test_role_api.py` 14 条、`test_config_admin_api.py` 10 条全红，报
`RuntimeError: 门 tenant 已以 read 模式持有：禁止原地升级`。

**根因链**（两处）：

1. `shared_platform_engine` / `shared_tenant_engine` 在夹具生命周期内持读门 = **整条用例持读门**，与设计决策 2「不采用整条用例持读门」直接矛盾；凡「夹具持读门 + 用例内写库」必撞。
2. FastAPI 的 `Depends` yield 依赖生命周期**延伸到响应结束**：写端点里注入 `get_read_db`（role 域操作人护栏），读门覆盖整个写请求，端点再取写门即撞。同理 `i18n` 取语言包用默认写门，在错误响应路径上撞读门。

**处置**（已回写设计决策 11 / 12 与《测试规范》§2.1 第 9 条）：

- `shared_*_engine` 只给引擎、**不取门**；直连引擎的裸读与写门并发时靠 SQLite 快照 + `busy_timeout` 兜底；
- `platform_db_write` / `tenant_db_write` 改为**直接取写门**（不再「升级」）；其作用域是**整条用例**（夹具 setup 到 teardown），属决策 13 的豁免，**不是**「一次写操作」——此措辞在 2026-11-19 复核时纠正，见 §2.10；
- role 域 `_require_role_operator` 改为依赖内 `session_scope(read_only=True)` 即开即关；
- `i18n` 语言包取数标 `read_only=True`。

### 2.8 回滚夹具进写门（S10） <a id="process-rollback"></a>

`rollback_session` 原本只做 SQLite 的 `BEGIN IMMEDIATE`（整条用例持库写锁），与读写门是**两套互斥**：不取门时其它 worker 的写会话会在 SQLite 层盲等 `busy_timeout`（30s，无任何诊断）。

按设计 §7 改为「整段回滚区间在对应库写门内执行」：新增 `gate_for_engine()` 按引擎库文件名推断门名（只认共享 `platform` / `tenant`，临时库与内存库不取门），写门等门有 10s 告警 / 180s 超时。该夹具仍标注**待淘汰**，新用例用命名空间隔离。

platform 23 个文件 75 处、notification 85 处、libs 34 处的「改命名空间」按服务分批推进，见 §5。

### 2.12 覆盖率放大倍数与回滚用例改造（S14，2026-11-19） <a id="process-cost"></a>

**覆盖率采集放大倍数实测**（同组 62 条，开 / 关采集对比）：

| 执行方式 | 不带采集 | 带采集 | 倍数 |
| --- | --- | --- | --- |
| 单进程 `-n 0` | 46.24s | 48.27s | **1.04×** |
| 四路 `-n 4` | 26.35s | 28.46s | **1.08×** |

结论：采集不是 300s 目标的大头（历史「采集翻倍」的假设不成立）。全量耗时的主要构成仍是用例本体与串行点。

**门缺陷修复（改造中暴露）**：`release(write=True)` 归零时把读计数一并清零——写门内「借用」的读份额在**写门先释放、读门后释放**时会报
`RuntimeError: 门 platform 释放模式不匹配：当前 None，请求释放 read`，把正常请求打成 500。真实触发路径是 FastAPI 的 yield 依赖把只读会话生命周期拉到响应结束。
修法：借用份额单独计 `_borrowed_reads`，`release(read)` 先销账、不碰内核锁；`mode` / `depth` / `close` 同步口径。

**回滚夹具实测**：持门区间 = 用例体（`call`）——这些夹具都依赖 `service_app` 先完成装配再开事务，装配期不在门内。

| 文件 | setup（门外） | call（门内） |
| --- | --- | --- |
| `api/test_scope_resource_types.py` | 2.81s | 0.11~0.30s |
| `help/test_help_package_loader.py` | 0.07~1.50s | 0.02~0.15s |
| `jobs/test_job_monitor.py` | 0.09~0.13s | 0.01~0.05s |
| permission 三件套 / crosscut / type_mapping | — | ≤0.04s |

**改造（批次 1，2 个文件）**：`test_scope_resource_types.py` / `test_internal_declarations.py` 去掉回滚夹具，写入经 `session_scope` 自带门。

### 2.16 读写门按业主方案重做（S18，2026-11-19） <a id="process-gateredo"></a>

**原实现的三处偏差**（实测暴露，非推测）：

1. **两条加锁路径**：读操作直接 `read_gate`、写操作直接 `write_gate`，写之前没有「先持读锁」这一步；
2. **等门走线程池**：`asyncio.to_thread(_wait_and_lock)` 在调用方被取消后线程仍继续轮询，拿到锁却无人释放——锁永久泄漏，后续请求全部阻塞；
3. **读份额按进程记账**：`_read_depth` 是一个整数，同一进程内多个并发会话共用一个计数器，一个会话升级写门会把别人的读份额一起放掉；对方的 SQLite 读事务还开着，写者提交被挡、读者又在等门，互等到 `busy_timeout`（表现为成片的「等待门 10s」与整轮停滞）。

**重做后的模型**（业主口径）：所有数据库操作**一律先取读锁**；读操作持读锁执行并释放；写操作先让出**自己这份**读份额，再排队取写门，写完放写门、恢复自己的读份额，最后放读锁。

- 取门只留 `gates.gate_scope(name, read_only=...)` **一个入口**，删除裸写门 `write_gate`；会话入口、测试基座 `write_session` / `rollback_session`、`write_window`、两个夹具、`tests_support` 全部走它；
- **删除 `begin_write`（`BEGIN IMMEDIATE`）与 `needs_explicit_begin`**：互斥只由门提供，不再有「单独写锁」；`rollback_session` 的 savepoint 分支只保留一条普通 `BEGIN`（不取写锁，只为让 `SAVEPOINT` 不退化成最外层事务）；
- 读份额改 **token 记账 + 任务归属**：释放只放自己那份、升级只让出本任务那份，其它任务仍持读时直接报错（禁止原地升级）；写门内取的读门是借用份额，写门释放后转「已退役」，稍后释放只销账不报错（FastAPI 的 yield 依赖会把只读会话拖到响应结束）；
- 等门改事件循环内 `await asyncio.sleep()` 异步轮询，**不再用线程池**；
- 新增诊断工具 `bms_core/testing/diagnostics.py`：`BMS_TEST_STACK_DUMP=1` 时告警 / 超时把本进程所有 asyncio 任务栈与线程栈落 `.cache/test/gate-stacks-<pid>.log`，`BMS_TEST_STACK_DUMP_EVERY` 控节流（默认 10s），默认关闭零开销。

**豁免收窄（试过，已回退）**：曾把 `test_config_admin_api.py` 的整条用例持门收窄为「只在复位段持门」，并把两个清理作业文件改成只给扫描类用例挂门。实测在 `-n 4` 下立刻出现竞态：`test_dependency_both_directions` 期望 `40505`（依赖未满足）却拿到 `40502`（键重复）、清理作业断言到他人行。根因是**收窄把用例体移到了门外**——这些用例读写的是共享库里的全局默认键，必须整条用例独占。已恢复设计决策 13 的 4 处登记，收窄不作为方向。

**验证**：测试基座（门 / 事务 / 诊断）**181 条通过**；受影响的 14 个平台文件 **128 条通过**（27.9s）。

**遗留**：`services/platform/tests/api` 单进程跑到第 144 条（56%）卡住，卡点为 `test_internal_tenant_topologies.py`；该文件单独跑 4 条全过、卡点用例单跑 2.9s 通过——**累积性问题**，与门无关，待查。

### 2.17 启动期长会话治理与三段采样（S19，2026-11-19） <a id="process-startup"></a>

**采样口径修正（先纠正读数，否则方向全错）**：`gate_scope` 的计时从 `acquire_read()` **之前**起算，日志里的「持有时长」是门区间全长（含等读锁 + 等写门），不是真持有。全量 2944 条区间 / 2072.9s 中，写区间中位数只有 0.021s，不足 1s 的 2215 条合计 249.3s——门内没有慢活，成本在门口排队。据此把采样改成三段：日志列依次为「总时长 / 模式 / 门名 / 用例 / 等读 / 等写 / 实占」，`实占 = 总时长 − 等读 − 等写`。

**头部来源（≥1s，337 条 / 1269.6s）**：`service_lifespan` 占 1093.9s（86%）——声明注册 343.8s、作业类型同步 271.5s、表归属对账 240.5s、i18n 清单 106.2s、授权视图加载 86.7s。每个用例的 `client` 夹具都跑一遍完整启动引导，各做十余次写库；多 worker 并发时这些写全部串行排队。按入口分布看，「长会话跨 HTTP 持有」不是本轮主因。

**改动**：

- 声明注册拆出 `plan()`（只读校验 + 对账，与 `register()` 共用同一段实现，不复制逻辑）；启动钩子在**同一次写门**内先比对，无差异则不写库（日志 `declaration_register_skipped`），只按现状重建进程内视图；
- 启动期三处整段作业（声明注册 / 作业类型同步 / 能力授权同步）传 `GATE_CRITICAL_WAIT`（180s）：首次全量写实测 5s+，用单次写的 5s 短上限会直接把正常首启判成超时拒启；
- `session_scope` 增 `gate_wait` 透传，用于表达「整段临界区」；`db/gate.py` 新增 `GATE_CRITICAL_WAIT` 作为该口径的单一来源；
- 三段采样落地：`note_hold` / `note_slow_hold` 增三段参数，慢区间阈值仍按总时长判定（排队也是被堵的成本）。

**试过并回退的五条路（均有实测数据，勿重走）**：

1. **纯读改读门**（`session_scope(gate_read_only=True)`）——给表归属对账、授权视图加载、i18n 清单、声明预检改用读锁。结果注册目录 53 通过 → 48 通过 / 5 条门超时。根因：测试库是 SQLite rollback journal，**读写互斥**；读门共享让多个读者同时等写，每个读者又持读份额挡住写门，形成「读者等写、写者等读者」。已全部回退（含参数本身，避免死代码）。
2. **建表 DDL 走门**（`ensure_unit_schema` 每库取写门）——注册目录 48 → 50，但拓扑文件 22s → 44s、错误 6~8 条。根因：建表是**每 worker 每次启动都跑一遍**的重复检查（0.45s），串行化后被放大。已回退。
3. **测试库启用 WAL**（建库后 `PRAGMA journal_mode=WAL`）——拓扑三次 1 / 0 / 5 条错误、36s，慢于未启用时的 22s。已回退。
4. **门重入判据改为「同任务才重入」**（`acquire_write` 同时校验 `_write_owner == 当前任务`）——门自身单测 18 条通过、拓扑 1~4 条错误无改善，但注册目录**挂住 2m34s** 后异常退出。根因：写门内嵌套取写门的用法是既有代码依赖的（以前靠「跨任务也放行」跑通），改成排队即互锁。已回退；要修必须连「写门内嵌套写」的调用形态一起梳理，属门模型重构。
5. **测试环境关闭启动建表**（`BMS_DATABASE__AUTO_CREATE=false`，表由共享库夹具建）——拓扑 2 / 1 条错误、26s，与未关闭时的 1~3 条 / 22s 无实质差别。已回退：瓶颈不在建表检查本身。

### 2.18 按任务记持门者并补齐启动期整段上限（S20，2026-11-19） <a id="process-holder"></a>

**采样增强（只加记录，不动锁结构）**：写门与读门都改成**按任务**记账——`acquire_write` / `acquire_read` 成功时把「进程号 + 任务身份 + 用例名 + 取门时刻 + 重入深度」记进进程内登记表，并按进程整体重写 `.cache/test/db-gate-<name>.taskholds-<pid>`（一行一个持有任务）；等门超时时按任务点名，不再只给进程。配套两处纠偏：

- **死进程记录一律过滤**：holder 目录残留 117 份历史记录，原先只要文本里有 `hold=1` 就参与点名，会把早已退出的进程当持有者。改按文件名末段取 pid 判存活（Windows 走 `OpenProcess` + `GetExitCodeProcess`，不能用 `os.kill(pid, 0)`——那会直接杀进程）。
- **任务级记录是权威口径**：进程级那行只在没有任务级记录时才采信，避免同一次持有被点名两次。

**日志列扩展**（旧列不变，新列追加在后）：`gate-hold.log` 增加第 8 列「重入」（进入写门前本进程已有其它任务持写门，说明取门不排队）；`gate-hold-slow.log` 在调用栈之后追加「重入」与「进入前持有者」。

**数据推翻上一轮的假设**：五轮采样 2144 条区间里「重入=1」只有 4 条（全是声明注册用例内的小嵌套，0.03~0.12s），而 5s 级区间**全部**是「重入=0、进入前无人持有」。也就是说：不是「同进程另一协程也进了写门」，写者拿到门时门是干净的。

**真正的根因**：5s 级区间的分段数据缺列——`实占` 是**外层区间**吞掉内层写门超时后的读数。异常路径下体内计时点不执行，外层只见「实占≈5s」。把体内计时点前移到 `finally` 后，完整分段显示：`取写` 最长 8.41s、`体内` 最长 0.32s。即**门内没有慢活，慢在门口排队**，排队超过单次写的 5s 短上限就抛 `等待数据库门超时（5.0s）`，启动引导随即拒启。

排队来源是启动期仍有会话走默认短上限。上一轮只给三处整段作业传了 `GATE_CRITICAL_WAIT`，漏了三处：

- 表归属登记播种（`_seed_dev_table_ownership`）；
- 表归属登记对账（`_validate_table_ownership`）——报错文案「表归属登记库不可读」即出自这里；
- 授权视图来源加载（`CapabilityGrantBootstrap.load`）——报错文案「授权视图预热失败」即出自这里。

全并行起 24 个 worker 时，每个 worker 每次启动要做十余次写门作业，单次 0.3~0.4s，队列长度自然到 5~8s；短上限因此把正常排队判成「有人长期占用」。三处统一补 `gate_wait=GATE_CRITICAL_WAIT`（与既有三处同口径），不改门模型、不改重入判据。

**改动清单**：`rwlock.py`（任务级读写持有登记、快照落盘、死进程过滤、按任务点名）、`gates.py`（进门前采样持有者、透传重入标记）、`diagnostics.py`（两处采样新增列）、`application.py` 与 `capability_grant_bootstrap.py`（三处补整段上限）；用例侧同步更新持有者断言并补 5 条（读份额点名、死进程过滤、任务级优先、Windows 存活分支、嵌套写标记）。

**实测（本机 24 核，`-n auto`）**：

| 项 | 结果 |
| --- | --- |
| 拓扑文件连跑三次 | 22 通过 / 22.12s、22 通过 / 22.26s、22 通过 / 22.35s（0 错误） |
| 注册目录连跑两次 | 53 通过 / 16.41s、53 通过 / 16.25s |

**结论**：上一轮遗留的 1~3 条 `等待数据库门超时（5.0s）` 已消——不是锁模型问题，而是三处启动会话用了单次写的短上限。写门排队仍是启动耗时的主要成分（等写合计 492.2s），但它随 worker 数线性放大、不再产生尾部超时。

### 2.19 启动期写门合并（S21，2026-11-19） <a id="startup-gate-merge"></a>

**先量再改**：给 `gate-hold.log` 临时追加一列调用栈（仅采样开关下计算，出表后即回退，日志仍是八列），单用例串行跑一次即得单次启动的完整写门清单——**25 段**，其中 18 段是同一件事：

| 次序 | 取门位置 | 作用 | 串行实占 |
| --- | --- | --- | --- |
| 1 | `bootstrap_platform_declarations` | 比对并注册平台八类声明 | 0.275s |
| 2 | `_seed_dev_table_ownership` | dev 表归属播种 | 0.006s |
| 3 | `_validate_table_ownership` | 表归属接库对账 | 0.007s |
| 4 | `i18n/registry_sql._session` | 语言清单回源（租户库） | 0.011s |
| 5 | `bootstrap_job_types` | 作业类型目录同步 | 0.076s |
| 6 | `bootstrap_capability_grants` | 授权声明同步 | 0.032s |
| 7~24 | `PlatformCapabilityGrantSource.load`（经 `ensure_grant_view`） | **逐域预热授权视图：17 个承载域 + 自身消费方维，各开一次会话、各取一次写门** | 0.001~0.007s/次 |
| 25 | `bootstrap_tenant_topologies` | 默认拓扑自举 | 0.035s |

串行实占合计仅 0.47s，但并发启动时「等写 ≈ 段数 × 队列深度 × 单段持有」——段数是可压缩的公因数。

**四处改动**：

1. **授权预热改一次装载**：`CapabilityGrantSource` 协议加 `load_all`，返回「视图键 → 该维度记录」的分组结果；平台源一次查询取全量启用行后在进程内按能力目录切分，远端源按承载域逐项 HTTP 拉取后分组（产品进程走 HTTP、不涉本地写门，不改内部出口契约）。新增 `prime_grant_views`（批量投影）与 `warm_grant_views`（TTL 内已新鲜的维度不重拉），逐维 `ensure_grant_view` 的运行期惰性刷新路径不变。18 段压成 1 段。
2. **表归属播种与对账合并为一次会话**：`_bootstrap_table_ownership` 在同一个临界区内完成「探测 → 播种 → 提交 → 读回 → 对账」，既省一次取门，也消掉两段之间被别的 worker 清库插队的窗口；离线清单校验仍先于接库，三档失败文案（库不可读 / 登记为空 / 接库不一致）逐条保留。
3. **声明注册的比对移出写门**：读门内算一次对账计划（读门共享、可并发），计划为空直接重建进程内视图并返回，**完全不取写门**；有差异才取写门，并在门内以现状为准重算（并发启动收敛，不会「门外判有差异、进门发现已被写」而重写一遍）。
4. **采样栈列回退**：临时列撤销后重跑门用例 66 条全绿，确认无残留探针。

**为什么第 3 条不违「读写两段会互等」**：已回退的第 1 条路是「读门内等写门（持读份额升级）」；本处读门内不做升级、不等待写门，算完即释放，写者只需等这一小段读结束，不会与读者互等。
