## 2. 实施过程 <a id="process"></a>

### 2.1 前置测量（S1） <a id="process-measure"></a>

| 项 | 结果 |
| --- | --- |
| 共享锁取放（Windows `LockFileEx`） | 平均 **0.0031ms**、p95 0.0032ms（500 次） |
| 独占锁取放 | 平均 **0.0030ms**、p95 0.0031ms（500 次） |
| 3 个读者各持共享锁 20ms | 总耗时 **21.2ms** → 真并发 |
| 读者持续请求时写者取独占锁 | 等待 **3.3ms** → 写者不被饿死 |
| 写者持锁 20ms 时读者等待 | **20.55ms** → 阻塞语义准确，无轮询延迟 |
| 对照：现有文件锁 | 取放 0.30ms、50ms 轮询、进程被杀留残锁 |

读写区分采样：API 请求由中间件按 HTTP 方法自动设置只读标记（`api/middleware.py`）；服务层 189 处 `session_scope` 调用中仅 10 处显式 `read_only=True`，其余按写门处理（决策 6）。

### 2.2 锁实现（S2） <a id="process-lock"></a>

| 文件 | 内容 |
| --- | --- |
| `bms_core/testing/rwlock.py`（新增） | `DbGate`：读 / 写深度分开计数、同模式重入、写门内取读放行、禁止持读升级；平台后端 `_WindowsLock`（`LockFileEx`）/ `_PosixLock`（`fcntl.lockf`）；非阻塞 + 退避重试（0.5ms → 5ms）；等门 10s 告警、180s 超时；锁文件 `.cache/test/db-gate-<name>.lock` |
| `bms_core/testing/gates.py`（新增） | 门名单例、`read_gate` / `write_gate` / `upgrade_to_write`（让读 → 取写 → 放写 → 取读）、`close_gates` / `reset_gates` |
| `bms_core/db/gate.py`（新增） | 生产侧空钩子：`set_gate_hook` / `current_gate_hook` / `db_access_gate`（未注入时直通） |

## 3. 问题与处置 <a id="issues"></a>

| 问题 | 根因 | 处置 |
| --- | --- | --- |
| 平台用例报「门 platform 已以 write 模式持有」 | 用例持写门后，应用内部只读会话请求读门被当成原地升级 | 写门包含读能力：写门内取读放行、只加读计数；持读取写仍报错 |
| `shared_*_engine` 与写门声明互相冲突 | 两个夹具独立解析，先读后升、先升后读都会撞 | 引擎夹具检测「已持门」即跳过读门 |
| `pytest_unconfigure` 三行未被覆盖率采集 | 会话结束后才执行，覆盖率报告已生成 | 加用例直接调用 `pytest_unconfigure` |
| 达梦同步分支改动行未覆盖 | 选测不选 `test_sync_facade.py` | 在**同构**文件 `tests/db/test_session_scope.py` 补同步方言用例（`session_scope` 与 `get_db` 两条入口） |
| 提交环三次才过 | ①`ruff format` ②裸 `list` 集合声明 ③覆盖率分支 | 分别修复后提交通过 |
