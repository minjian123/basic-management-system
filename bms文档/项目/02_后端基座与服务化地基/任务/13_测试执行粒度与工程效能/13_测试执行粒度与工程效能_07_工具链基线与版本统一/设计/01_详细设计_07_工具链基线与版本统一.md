## 1. 背景与目标 <a id="goal"></a>

`13_05` 把护栏与开发脚本收进跨仓工具包 engkit 之后，「**各仓只放配置、实现单一来源**」这条原则已在文档校验、预检、选测、覆盖率门禁上落地。但**工具链本身的配置与版本**没有收口，仍在各仓各写一份：

- **规则段逐字复制**：bms / mdm / engkit 三仓 `[tool.ruff]` 的 `line-length = 120`、`select = ["E","F","W","I","B","UP","SIM","RUF"]`、`ignore = ["RUF001","RUF002","RUF003"]` 三行完全一致，改一处要改三处，漏改即口径分叉；
- **版本已经漂移**（实测各仓 `uv.lock`）：ruff 为 **bms 0.16.6 / mdm 0.16.10 / engkit 0.17.1** 三个版本并存，pyright 为 **bms 1.1.411 / mdm 与 engkit 1.1.414**；
- **配置无法共享已逼出绕法**：bms 的 `tooling-lint` job 注释写明「从 `backend/` 运行以取用 `backend/pyproject.toml` 的 ruff 配置」——脚本区没有自己的 ruff 配置，只能靠切工作目录借。

同一份代码在不同仓可能得出不同的 ruff 诊断与格式化结果，这正是「口径分叉」的典型形态，与 `13_05` 已确立的原则不一致。

**目标**：

1. **ruff 规则单一来源**：基线文件放 engkit，各仓只 `extend`，不再复制规则段；
2. **版本单一来源**：ruff / pyright 版本由 engkit 的可选依赖组锁定，各仓经 git 源依赖取得，升级只改 rev 一处；
3. **缺依赖即失败**：基线或工具缺失时明确报错并给出指引，不静默回落到旧规则；
4. **行为零回退**：升级与改造后各仓 lint / format / typecheck 结论与改造前一致。

**边界（不在本任务）**：

- **前端工具链**（pnpm / eslint / vitest）不在范围：engkit 是 Python 包，前端配置基线需另发 JS 共享包，属独立事项（§14 开放项 1）；
- **pyright 配置基线不做**：三仓 pyright 配置除 `typeCheckingMode = "strict"` 外全部不同（`include` / `extraPaths` / `pythonVersion` / `reportMissingTypeStubs` 各仓各异），共享一个字段收益有限；本次只统一其**版本**（§3 决策 4）；
- **新增统一入口子命令不做**：版本收敛后 `uv run ruff` 已是同形命令，再包一层收益有限，且会膨胀 engkit 对外 API（§3 决策 5）；
- **uv 本身不可收进 engkit**：uv 是包管理器命令，engkit 只能规定「怎么调、调哪个版本」，不能提供它（§2 现状实测）。

## 2. 现状实测 <a id="status"></a>

### 2.1 版本与配置漂移

| 项 | bms | mdm | engkit |
| --- | --- | --- | --- |
| ruff（`uv.lock` 锁定） | 0.16.6 | 0.16.10 | 0.17.1 |
| pyright（`uv.lock` 锁定） | 1.1.411 | 1.1.414 | 1.1.414 |
| ruff 配置所在 | `backend/pyproject.toml` | `backend/pyproject.toml` | `pyproject.toml` |
| `line-length` | 120 | 120 | 120 |
| `select` | E/F/W/I/B/UP/SIM/RUF | 同左 | 同左 |
| `ignore` | RUF001/002/003 | 同左 | 同左 |
| `target-version` | py314 | py314 | **py311**（包声明 `>=3.11`） |
| `known-first-party` | 13 项（`bms_*` 包 + `ops`/`scripts`/`tests_support`） | 4 项 | 无 |
| pyright `include` | `libs`/`services`/`ops` | `services` | `src` |
| pyright `extraPaths` | 13 项 | 1 项 | `src` |

`target-version` 与 `known-first-party` 属**本仓专属**，不属可共享部分——这决定了基线只能收「三行规则 + 行宽」，不能整段照搬。

### 2.2 ruff 配置机制实测

用临时仓实测（探针已清理，不落工作区）：

| 项 | 实测结论 | 对设计的影响 |
| --- | --- | --- |
| `extend` 相对路径基准 | **相对声明它的配置文件所在目录**，非 cwd | 各仓 `pyproject.toml` 用 `extend = "../engkit/toolchain/ruff-base.toml"` 可跨仓引用 |
| `extend` 目标缺失 | **直接报错退出码 2**，错误信息含两个路径 | 满足「缺依赖即失败」，不会静默用旧规则 |
| `extend` 是否支持环境变量 | **不支持**，`${ENGKIT_TOOLCHAIN}` 被当字面路径 | 不能用环境变量做间接寻址，必须写相对路径 |
| 子段覆盖 | `extend` 后本文件再写 `[tool.ruff.lint.isort]` 等**子段可覆盖/补充**基线 | 各仓专属项可继续写在 `pyproject.toml` |
| `--config` 外部文件 | **整体替代**仓内配置：实测仓内 `select` 全套被外部 `select = ["E501"]` 覆盖后，`E401`/`F401`/`I001` 全部不再报 | 排除「用 `--config` 传基线」方案（会让仓专属段失效） |
| 多个 `--config` | **不允许**，报「You cannot specify more than one configuration file」 | 排除「基线 + 仓内配置双传」方案 |
| 配置发现顺序 | 按**被检查文件所在目录向上查找**，找不到才兜底 cwd | 决定 `tooling-lint` 写法（见 §6.3） |
| 缓存目录 | 版本升级后旧 `.ruff_cache` 可能拒绝访问 | 预检/CI 用 `--no-cache` 或 `RUFF_CACHE_DIR`（§6.5） |

配置发现顺序的实测证据：`backend/pyproject.toml` 声明 `line-length = 20`，从工作区根跑 `ruff check backend` 报 E501（吃到 backend 配置），跑 `ruff check scripts/tools` 不报（脚本区无配置、向上找不到）。

### 2.3 升级到统一版本的影响实测

拟统一到 ruff 0.17.1 / pyright 1.1.414（engkit 现版本，即最新）：

| 仓 | `ruff check` | `ruff format --check` |
| --- | --- | --- |
| bms | 通过（1364 个文件） | 通过（1364 个文件已格式化） |
| mdm | 通过（108 个文件） | 通过（108 个文件已格式化） |
| engkit | 通过 | 通过 |

**结论：升级不引入任何新增诊断或格式差异**，改造风险集中在配置接线与依赖声明，不在代码适配。

### 2.4 pyright 配置继承实测

`[tool.pyright]` 的 `extends` **可用**（相对项目根解析），strict 模式生效。但基线缺失时**只打印一行 `Config file ... could not be read`，退出码 3 而诊断数为 0**——比 ruff 的硬失败隐蔽，容易被误读成「检查通过」。这是本次不做 pyright 基线的原因之一（§3 决策 4）。

### 2.5 uv 可选依赖组与 git 源实测

| 项 | 实测结论 |
| --- | --- |
| `[project.optional-dependencies]` + `[dependency-groups] dev = ["自包[extras]"]` | 可解析（`uv lock` 成功） |
| git 源依赖带 extras（`fakekit[devtools]` + `[tool.uv.sources]` 指 git） | 可解析，extras 内的 ruff 正确进入解析结果 |
| bms 现状 | 平级克隆 + `ENGKIT_HOME` 路径探测，**未安装 engkit 包**，依赖组下不到它 |
| mdm 现状 | 已以 git 源依赖锁 rev 引 `engkit`，`uv run engkit --version` 可用 |

### 2.6 bms CI 现状

| job | 是否已有 engkit 克隆 | 改造后是否必须 |
| --- | --- | --- |
| `base-integrity` | 有（`ENGKIT_REV` + 克隆 + `ENGKIT_HOME`） | 必须 |
| `backend-test` | 有 | 必须 |
| `.test-selection`（前端选测片段） | 有 | 必须 |
| `backend-lint` | **无** | **必须**（基线外置后 ruff 要读 engkit） |
| `tooling-lint` | **无** | **必须** |
| `backend-typecheck` | **无** | **必须**（pyright 由 engkit 提供版本） |

克隆步目前在三处各写一遍（`base-integrity` / `backend-test` / `.test-selection`），再加三个 job 就是六份重复——这是 §3 决策 8「抽公共片段」的直接动因。

## 3. 决策确认 <a id="decide"></a>

| # | 事项 | 决策 |
| --- | --- | --- |
| 1 | 收哪些 | **ruff + pyright 的共用配置基线**（长期看单一来源最省；仓专属项仍留本仓） |
| 2 | 怎么引用 | **各仓 `pyproject.toml` 用 `extend` 指向平级 engkit 克隆**（真正单一来源；代价是本地与 CI 都必须有克隆） |
| 3 | 版本统一 | **版本随 engkit 可选依赖组下发**（升级只改 engkit rev 一处，全仓自动收敛） |
| 4 | pyright 基线 | **只做 ruff 基线，pyright 只统一版本**（pyright 实际只有 `typeCheckingMode` 一项可共享，且基线缺失不阻断门禁） |
| 5 | 统一入口 | **不加新子命令**，各仓仍用原生 `uv run ruff` / `uv run pyright` |
| 6 | 缺克隆兜底 | **直接失败并给出克隆指引**（与「engkit 为工作区必选仓」口径一致，不静默回落） |
| 7 | 前端范围 | **本次只做后端 Python 工具链**；前端需另发 JS 共享包，登记为开放项 |
| 8 | bms 版本下发 | **bms 也改为 git 源依赖安装 engkit**（与 mdm 同构，升级只改一处 rev；路径探测保留为兜底） |
| 9 | 基线落点 | **engkit 仓根 `toolchain/` 目录**（工具链资产不是包代码；路径稳定，与路径探测口径一致） |
| 10 | CI 克隆步 | **抽公共片段，相关 job 统一引用**（一处维护、升级只改一个变量） |
| 11 | 文档与归属 | **挂 bms 13 域新子任务 13_07**（跨三仓改动需需求基线与验收标准） |
| 12 | 推进方式 | **先出详细设计，再实施**（符合「先设计后编码」口径） |

## 5. 基线文件设计 <a id="baseline"></a>

### 5.1 文件内容与边界 <a id="baseline-content"></a>

`engkit/toolchain/ruff-base.toml` 只放**三仓完全一致**的部分：

```toml
# ruff 规则基线（跨仓单一来源；口径见 engkit 文档《工程化工具包说明》「工具链基线」节）
# 各仓 pyproject.toml 以 `extend = "<相对路径>/toolchain/ruff-base.toml"` 引用；
# 本仓专属项（target-version / known-first-party / include / extraPaths）留在各仓，不写在这里。
line-length = 120

[lint]
select = ["E", "F", "W", "I", "B", "UP", "SIM", "RUF"]
# 中文标点为文档与注释的有意用法，关闭歧义字符检查
ignore = ["RUF001", "RUF002", "RUF003"]
```

**明确不进基线的内容**：

| 项 | 原因 |
| --- | --- |
| `target-version` | engkit 是 `>=3.11` 的库（py311），bms / mdm 是 py314 应用——本仓属性 |
| `known-first-party` | 各仓自有包名清单，本质是本仓结构 |
| `src` / `extend-exclude` / `per-file-ignores` | 均为目录结构相关，本仓属性 |
| `[format]` 段 | 三仓均用 ruff 默认格式（实测 `format --check` 全通过），无差异化需求；将来若有再加 |

### 5.2 各仓引用写法 <a id="baseline-usage"></a>

bms（`bms/backend/pyproject.toml`，基线在平级 `engkit/`）：

```toml
[tool.ruff]
extend = "../../engkit/toolchain/ruff-base.toml"
target-version = "py314"

[tool.ruff.lint.isort]
known-first-party = ["bms_core", "bms_txn", ...]
```

mdm（`mdm/backend/pyproject.toml`）：

```toml
[tool.ruff]
extend = "../../engkit/toolchain/ruff-base.toml"
target-version = "py314"

[tool.ruff.lint.isort]
known-first-party = ["mdm", "services", "ops", "tests_support"]
```

engkit（`engkit/pyproject.toml`，基线在自身仓内）：

```toml
[tool.ruff]
extend = "toolchain/ruff-base.toml"
target-version = "py311"
```

> 相对路径基准是**声明它的配置文件所在目录**（§2.2 实测）。bms / mdm 的配置文件在 `<仓>/backend/`，基线在 `<工作区>/engkit/toolchain/`，故为 `../../engkit/toolchain/ruff-base.toml`。

## 6. 版本统一下发设计 <a id="version"></a>

### 6.1 engkit 可选依赖组 <a id="version-extras"></a>

```toml
[project.optional-dependencies]
# 工具链版本基线：各接入仓以 `engkit[devtools]` 取得，版本只在本处升级
devtools = ["ruff==0.17.2", "pyright==1.1.414"]
```

- 版本口径用 **`==` 严格同版**（实施期修订，见 §14 对齐记录第 1 条）：原设计用 `>=` 下限 + 各仓锁文件固化，实测各仓按各自解析时机落到**不同补丁版**（bms / mdm 新锁落 0.17.2、engkit 仍 0.17.1），与「三仓版本一致」的完成标准不符；改 `==` 后同版成为结构性事实；
- 代价：任何一次 ruff 补丁升级都要改 engkit 的 `devtools` 并推一次 rev（两仓各改一处 `rev`）——正是「升级只改一处」的目标形态，不再靠人盯锁文件。

### 6.2 各仓依赖声明 <a id="version-deps"></a>

> **变更注（2026-10-27）**：`engkit` 由「git 源 + 锁提交 SHA」改为**路径依赖**（`path = "../../engkit"`，editable），bms 与 mdm 两仓同批——工作区内跨仓依赖统一为源码链接（改工具包代码即时生效，不再需要「推送 + 改 rev」）。`ENGKIT_REV` 仅保留给 CI 侧克隆（`scripts/tools/ci/engkit_setup.sh`）锁 ref；§6.3 升级流程相应简化为「改 CI 变量锁的那一个 ref」。下方为原 git 源形态，历史留档。

bms（新增 `[tool.uv.sources]`，与 mdm 同构）：

```toml
[dependency-groups]
dev = [
    # ... 既有项
    "engkit[devtools]",
]

[tool.uv.sources]
engkit = { git = "<GitLab>/bms/engkit.git", rev = "<SHA>" }   # 2026-10-27 起改为 path
```

mdm（既有 `engkit` 依赖加 extra）：

```toml
[dependency-groups]
dev = ["...", "engkit[devtools]"]

[tool.uv.sources]
engkit = { git = "http://<GitLab>/bms/engkit.git", rev = "<SHA>" }   # 2026-10-27 起改为 path
```

> bms 改为 git 源依赖后，`backend/.venv` 内将同时有 engkit 包（ruff / pyright 由它带入）。既有 `engkit_boot.py` 的路径探测逻辑保留：`import engkit` 成功即返回，探测只在未安装时兜底——**bms 侧包装入口与 CI 命令原文均不变**。

### 6.3 升级流程 <a id="version-upgrade"></a>

1. engkit 改 `devtools` 版本 → 提交 → 打 tag / 记 SHA；
2. bms 与 mdm 各自改 `[tool.uv.sources].engkit.rev`（以及 CI 的 `ENGKIT_REV`）→ `uv lock` → 本地跑 ruff / pyright 确认零差异；
3. 推送（`-o ci.skip`），按需手动触发一次流水线复核。

**升级触点收敛为 2 处**：各仓 `pyproject.toml` 的 `rev` + bms CI 的 `ENGKIT_REV` 变量（抽公共片段后只有一处）。相比现状「三仓各自改 ruff / pyright 版本声明」，触点数量与漏改概率都下降。

## 7. CI 接线设计 <a id="ci"></a>

### 7.1 公共片段 <a id="ci-fragment"></a>

**实施期修订（见 §14 对齐记录第 2 条）**：原设计在 `.gitlab-ci.yml` 抽 YAML 锚点（`.engkit-setup: &engkit-setup`），但前端选测片段自身有 `before_script`，锚点插入会形成**嵌套数组**（依赖 GitLab 扁平化行为，本地无法预验）；改抽 **shell 脚本** `scripts/tools/ci/engkit_setup.sh`，各 job 一行 `. scripts/tools/ci/engkit_setup.sh`（**source**，以便导出 `ENGKIT_HOME`）：

```sh
# 脚本内含：ENGKIT_REV 缺省值、克隆地址口径（用 CI_SERVER_URL，含端口）、已有克隆只 checkout、导出 ENGKIT_HOME
ENGKIT_REPO_ROOT="${CI_PROJECT_DIR:-$(cd "$(dirname "$0")/../../.." && pwd)}"
ENGKIT_CLONE_DIR="${ENGKIT_REPO_ROOT}/../engkit"
ENGKIT_REF="${ENGKIT_REV:-<锁定 SHA>}"
test -d "${ENGKIT_CLONE_DIR}/.git" || git clone --quiet --no-checkout "${ENGKIT_REPO_URL:-…}" "${ENGKIT_CLONE_DIR}"
git -C "${ENGKIT_CLONE_DIR}" checkout --quiet "${ENGKIT_REF}"
ENGKIT_HOME="${ENGKIT_CLONE_DIR}"; export ENGKIT_HOME
```

一处维护（脚本内 `ENGKIT_REV` 缺省值）、本地可直接验、不受 YAML 特性版本影响；mdm 侧同口径自备一份（各仓 CI 样板，非工具包逻辑）。

### 7.2 各 job 接法 <a id="ci-jobs"></a>

| job | 改动 |
| --- | --- |
| `backend-lint` | `script` 前置 `*engkit-setup`（ruff 需读 `../../engkit/toolchain/ruff-base.toml`） |
| `tooling-lint` | 同上；**命令原文不变**（仍 `cd backend` 后跑 `ruff check ../scripts/tools`） |
| `backend-typecheck` | 同上；`uv run pyright` 由 engkit 提供的版本执行 |
| `base-integrity` | 三行内联克隆改引用片段 |
| `backend-test` | 同上 |
| `.test-selection` | 同上 |

### 7.3 为什么 `tooling-lint` 命令不用改 <a id="ci-tooling"></a>

`tooling-lint` 跑的是 `cd backend && uv run ruff check ../scripts/tools`。按 §2.2 实测的配置发现顺序，被检查文件（`scripts/tools/*.py`）自身向上找不到 ruff 配置，才兜底 cwd（`backend/`）——**现状能生效正是靠这个兜底**。

基线外置后这条兜底链变为：`backend/pyproject.toml` 的 `extend` → `../../engkit/toolchain/ruff-base.toml`。因此：

- 命令**不需要改**，但 `backend/pyproject.toml` 必须能被找到，且 engkit 克隆必须存在；
- 若将来给 `scripts/tools/` 加独立 ruff 配置，兜底链会断（配置从脚本区向上找、不回落到 `backend/`），届时须在该配置里也 `extend` 基线——**这一点写进 engkit 接入说明，避免后人踩坑**。

### 7.4 uv 与克隆的关系 <a id="ci-uv"></a>

bms 改 git 源依赖后，`uv sync` 会**自己**按 rev 拉 engkit（走 GitLab 凭据），这与 `../engkit` 平级克隆是两条独立路径：

- **uv 侧**：提供 engkit 包（含 ruff / pyright）与 `engkit` 命令，落在 `.venv`；
- **克隆侧**：提供 `toolchain/ruff-base.toml`（ruff 的 `extend` 读的是文件路径，读不了包内路径——`.venv` 外置符号链接下包内路径不稳定）。

两条都要有，`ENGKIT_HOME` 仍用于包装入口定位。CI 中 `uv sync --frozen` 已存在，只需补克隆片段。

## 8. 失败与兜底 <a id="failure"></a>

| 场景 | 行为 | 是否满足决策 6 |
| --- | --- | --- |
| 本地无 engkit 克隆 | ruff 报错退出 2，信息含缺失路径 | 是（明确失败） |
| CI job 未接克隆片段 | ruff 报错退出 2，job 失败 | 是 |
| engkit 已安装但无克隆 | 同上（`extend` 读文件路径，与包无关） | 是 |
| 基线文件被改名 / 移走 | 同上 | 是 |
| pyright 未装（版本组缺失） | `uv run pyright` 报命令不存在，job 失败 | 是 |

**用户侧提示**：`extend` 的报错信息由 ruff 自己产出（含「哪个配置 extends 哪个文件」与「Failed to read 哪个路径」），已经足够定位。我们在 engkit 接入说明与 `scripts/tools/preflight/README.md` 补一句「ruff 报 Failed to load extended configuration 即说明 engkit 克隆缺失，按接入说明克隆」。

> **不做仓内副本兜底**：留副本等于双份实现，违背 engkit「单一来源」红线，副本迟早与基线不一致（决策 6）。

### 9.1 engkit 侧新增用例
