## 2. 任务内容 <a id="content"></a>

### 2.1 触发与实测 <a id="trigger"></a>

第五次推送预检（2026-11-23，645 个测试文件选面）的分批实测：

| 批 | 目标数 | 耗时 | 结果 |
| --- | --- | --- | --- |
| 1 | 150 | 240.15s | 4067 通过 / 0 失败 |
| 2 | 117 | 54.40s | 1269 通过 / 0 失败 |
| 3 | 60 | **139.36s** | 464 通过 / **11 失败 + 12 错误**（全 `database is locked`） |

- 整轮 564.3s / 上限 600s（静态与护栏段 103.0s，测试段 452.0s）；唯一失败项即后端定向测试。
- 645 个文件经目录聚合为 327 个目标。折叠条件是「目录内测试文件全被选中且不超过 20 个」（`[guard].dir_test_threshold = 20`），因此 `services/platform/tests/api`（35 个测试文件）永远不折叠。
- 第 3 批正是折叠不了的**残余文件**：`platform/tests/api`、`notification` 的 mail / notice / notification、`file`、`identity/auth`——写最密集的一批。
- 每用例耗时：批 1 **0.059s**、批 2 **0.043s**、批 3 **0.29s**（5~7 倍），指向等门而不是用例本身慢。
- 失败栈全部落在 teardown 清理（`DELETE FROM sys_notice_read` / `sys_notice_i18n ... WHERE title LIKE`），且已持写门（`write_session` + `GATE_CRITICAL_WAIT`）；持门写入仍然 locked ⇒ 冲突方在门外。
- 对照：同四域 7 个文件在 `-n 0` / `-n 24` 下均 56 通过、locked = 0（13_08 实施记录 §2.30）。

**另需登记的事实**：第五次预检失败后，13_08 的 14 个提交于 2026-11-23 06:53 以**裸 `git push`** 直推（远程引用更新记录为 `update by push`，`.cache/preflight/audit.jsonl` 无对应条目——推送环未参与）。因此本任务的触发点是「同一份代码在推送环上的成功率不稳」，不是「提交被卡住」。

### 2.2 目标与边界 <a id="scope"></a>

**目标**：让定向档在「一次跑五六百个测试文件」的形态下可重复通过——同一提交集连续 3 次：失败 0、`database is locked` = 0、测试段 ≤440s；任一批失败时一次给全所有批次的失败清单。

**不动清单（本次硬边界，2026-11-23 拍板）**：

1. `[preflight.budget]` 数值（定向档单步 300s / 总 420s）与 `PUSH_MAX_TOTAL_SECONDS = 600` 硬上限；
2. 强制并行（`--jobs off` / `-n 0` 继续被推送入口拒绝）、单次 `engkit push`；
3. 0.1 秒忙等、一份库零复制、覆盖率门限 100%；
4. 《测试规范》《AI开发规范》与 engkit 文档的既有条文（不改写、不新增、不回写口径）。

**可动范围**：engkit 内部分批装箱实现（目标集合等价、字符预算不变、批数不增——碎片化时最多 +1 且须在批级摘要说明）、失败汇总行为、bms 用例侧（按取证结论逐条改）。

## 3. 完成标准 <a id="accept"></a>

- 同一提交集连续 3 次定向档：失败 0、`database is locked` = 0、测试段 ≤440s。
- 选中文件数与跳过数与改造前一致（无漏测），覆盖率门禁仍 100%。
- 末批每用例耗时 ≤0.10s/条（与其它批同量级）。
- 任一批失败时，失败清单包含全部已跑批次结果与未跑批次说明。
- 装箱自测覆盖：按服务轮转、单批字符不越界、目标集合无重无漏、批数不增（最多 +1 且有摘要说明）、空输入与单文件超预算边界。
- 不动清单四条逐条复核（复核命令与结论写进测试记录）。
