## 2. 实施过程 <a id="process"></a>

### 2.1 S1 判别实验 E1：末批原样独立跑 3 轮 <a id="process-e1"></a>

把第五次推送预检第 3 批的 60 个目标**原样**（不打散、不改代码）独立跑三轮，`-n 24`、忙等缺省、不开覆盖率采集：

| 轮 | 耗时 | 通过 | 失败 | `database is locked` | 失败项 |
| --- | --- | --- | --- | --- | --- |
| 1 | 133s | 482 | 1 | **0** | `test_help_coverage_api::test_coverage_filters_and_determinism` |
| 2 | 121s | 482 | 1 | **0** | `test_capability_grants::test_declared_sync_create_disable_restore_with_audit[asyncio]` |
| 3 | 119s | 483 | 0 | **0** | — |

**结论一**：末批构成自身**不需要**「645 文件选面」就能复现失败 → 至少这两条属**用例自身**，与执行形态无关（H1 成立）。

**结论二**：三轮 `database is locked` 全为 **0**，与推送环该批的 119 次形成鲜明对照 → 锁冲突族**不是**末批构成单独导致的，需要完整三步上下文（或覆盖率采集）才出现。

两条失败都不是锁冲突，而是**断言全局口径**：

| 失败 | 断言 | 实际 | 原因 |
| --- | --- | --- | --- |
| `test_declared_sync_create_disable_restore_with_audit` | `('enabled', '产品声明默认消费方')` | `('disabled', '声明移除')` | `sync_declared()` 把「库内有、当前声明没有」的行判为声明移除；别的 worker 的启动装配用真实目录（不含本用例的 `demo.mdm.user-roles`），把本用例的行改成 disabled |
| `test_coverage_filters_and_determinism` | 两次调用 `summary` 相等 | `action_fallback.declared` 4 → 5、`total` 5 → 7 | `summary.reference`（表单 / 字段 / 动作码兜底）是**全平台**口径，不随 `module_key` 收敛；两次调用之间别的 worker 新增锚点即变 |

### 2.5 复核：F1 的独占库被否定，改服务层单测 <a id="process-f1-redo"></a>

业主判定「又用独占库是偷懒」，要求回退重做。复核结论：**这条用例病根在「断言库的全局终态」，而库被所有 worker 并发写**，与「本用例的库是否干净」是两件事；但给它单独一份库也确实是把问题推给环境。

重做取服务层单测（仓储替身，不连共享库），三段语义与审计序列完整保留：

| 项 | 做法 |
| --- | --- |
| 仓储 | `_MemoryGrantRepo`：内存行表 + 自增主键，只实现 `sync_declared()` 用到的 `pair_where` / `insert_if_absent` / `update_where` / `get_by_pair` / `list_all` |
| 会话与工作单元 | `_NullSession`（`rollback` 空实现）、`_NullUow`（`begin()` 只提供上下文），都不连库 |
| 注入方式 | `monkeypatch.setattr(CapabilityGrantService, "_repo", property(...))`，**产品代码一行未改** |
| 断言 | `GrantSyncReport` 的 `created` / `revoked` / `restored` 逐段精确比对 + 审计变更序列全等（替身下完全确定） |

真库装配路径仍由同文件既有的 `test_bootstrap_registers_source_and_warms_views`（`own_db`，13_08 已确立）覆盖，不重复占库。

### 2.6 F2 收口：进程级状态隔离 <a id="process-f2"></a>

F2 的 403 与数据库无关，先证伪了三个假设：

| 假设 | 核查 | 结论 |
| --- | --- | --- |
| 共享库默认拓扑残缺 | 直查 `.cache/test/platform.db` 的 `sys_tenant_topology`：默认租户当前版本 25 行、全部 `enabled`、含 `permission_meta` | 不成立 |
| 启动钩子没装载快照 | `bootstrap_tenant_topologies` 在启动钩子清单里无条件执行，每例装配都从库装载 | 不成立 |
| `ensure_default()` 写出缺域版本 | 有版本时只补不缺域（`merged` = 现有行 + 新域），只会多不会少 | 不成立 |

真实成因有两条，都在**进程级全局**：

1. **拓扑快照与实例上下文无隔离**：`instance_domains()` 读 `_SNAPSHOTS` / `_CURRENT_VERSIONS` / `_instance_units`，任何用例改写后不恢复就泄漏给同 worker 后继用例；
2. **域映射的「保存-恢复」把残值当基线**：`isolate_catalog_records` 原来在用例前存 `domain_service_view()`、用例后恢复它。本目录 `_isolate_grant_state` 每例把映射设成只有 `mdm` / `platform_registry` 两项且自身不复位，于是下一例存下的基线就是残值，逐例传播——一旦拓扑快照恰为空，`instance_domains()` 回退到这份残映射，就报「业务域未在本实例启用」。

处置：

| 改动 | 位置 | 说明 |
| --- | --- | --- |
| 新增 `TopologyState` / `topology_state()` / `restore_topology_state()` | `libs/bms_core/src/bms_core/collaboration/topology.py` | 整份留存与还原（全部快照 + 各租户当前版本 + 实例上下文两种形态）；与既有 `reset_topology_snapshots()` 同属测试隔离支撑 |
| 新增 `isolated_topology` 夹具 | `libs/bms_core/src/bms_core/testing/fixtures.py` | 每例保存-恢复；经 `bms_core.testing.plugin` 注册，各服务套件可直接用 |
| `isolate_catalog_records` 接入并改口径 | `services/platform/tests/conftest.py` | 依赖 `isolated_topology`（保证在装配前留存）；域映射由「恢复上一例值」改为「复位 + 按会话级清单重载」，与其余八类同口径 |

复现与验证（末批 35 个 `platform/tests/api` 文件、`-n 8`）：

| 阶段 | 结果 |
| --- | --- |
| 夹具只补拓扑、域映射仍「保存-恢复」 | 1 轮 1 失败：`test_metadata_endpoint_requires_identity_capability` 仍 403 → 证明域映射基线才是主因 |
| 域映射改「复位 + 按清单重载」 | 3 轮 × 259 用例全绿，403 **0 次** |
| F1 改服务层单测后 | 3 轮 × 259 用例全绿 |

### 2.7 F3 复现与收口：建租户库取错门 <a id="process-f3"></a>

**复现门槛是完整三批形态**。末批单独跑共 11 轮（8 轮无采集 + 3 轮补采集）`database is locked` 全为 0，逐项对齐后只剩「批 1、批 2 先跑」这一个差异：

| 项 | 末批单独跑 | 推送环 | 核查结论 |
| --- | --- | --- | --- |
| 共享库状态 | 每会话删库重建（`reset_shared_databases`） | 同 | 批序不影响库内容 |
| 并行档 | `-n 24` | `-n auto`（本机 24） | 同 |
| 批次目标 | 60 目标 / 484 用例 | 同 | 同 |
| 覆盖率采集 | 已补（`BMS_COVERAGE_DATA` + `-p bms_testing_plugin`） | 有 | 仍 0 次，**不是**采集开销 |

三批连跑两轮：第 1 轮批 3 命中 **107 次** locked（13 失败 + 24 错误，117s），第 2 轮批 3 为 0 —— 复现率约一半，与推送环「同一份代码成功率不稳」一致。

三条互相印证的证据（都取自命中轮）：

| # | 证据 | 读法 |
| --- | --- | --- |
| 1 | 20 处锁异常的等待时长 **159~170ms** | 只比 0.1 秒忙等上限多一点：是**等锁**，不是语句本身慢 |
| 2 | 全部集中在 **5 秒窗口**内（09:44:59.96~09:45:04.96），位于会话起始 | 一次性事件，不是全程争用 |
| 3 | 失败语句**全部落在租户库表**（`sys_notice` / `sys_notice_read` / `sys_file` / `sys_session` / `sys_notification`） | 只有租户库被同时写，平台库表一条没有 |

探针（`BMS_TEST_LOCK_PROBE=1`：46615 段门区间、75 个进程）直接点出位置：

| 观测 | 值 |
| --- | --- |
| `rebuild platform` | 2158ms，位于 `platform rw` 内，其它进程门区间 0 段（worker 都在等就绪） |
| `rebuild tenant` | 1749ms，**整段落在 `platform rw` 内**，租户门在这 1.7 秒里完全为空 |
| 长持门分布 | `platform rw` 共 23748 段、p95 = 6.7ms、最长 2157ms（即建库那段） |

成因：`_build_shared_db_under_gate()` 对**任何**库都取 `PLATFORM_GATE`（硬编码），与「按库一把门、门粒度是实际库文件」的口径相悖。于是建租户库 / 播种期间，租户门是空的——首批用例的租户库写直接落到 SQLite 层，0.1 秒忙等一到就成片报 `database is locked`。

处置：

| 改动 | 位置 | 说明 |
| --- | --- | --- |
| 建库按库取门 | `libs/bms_core/src/bms_core/testing/fixtures.py` | `gate_name = TENANT_GATE if name == TENANT_GATE else PLATFORM_GATE`；只换门名，不改等待上限、不改库模型 |
| 新增用例 | `libs/bms_core/tests/testing/test_shared_db_edges.py`（Kiwi **2548**） | 断言两次建库依次取 `PLATFORM_GATE` / `TENANT_GATE`；修复前为红（`['platform', 'platform']`） |

验收：修复后完整三批连跑 **3 轮 × 3 批共 9 个会话全绿、locked = 0**；改完措辞（去裸字典常量）后再跑 1 轮，locked 仍为 0。

### 2.8 删库口径纠正与用例隔离自检门 <a id="process-isolation"></a>

业主指出实现侧把「删库重建」曲解成了「每个 pytest 会话都删」。原话已逐字写入《测试规范》§4，纠正为：**一次测试运行开始、数据初始化之前删库重建一次；同一次运行的各 pytest 会话叠加复用，不得再删**；除初始化外**禁止动库结构、禁止动别人的用例数据**（开发期表单设计功能除外），凡违反的用例**全部算错、全部要改**。

| 项 | 改前（曲解） | 改后（原话口径） |
| --- | --- | --- |
| 删库时机 | 每个 pytest 会话开始都删 | 一次运行只在**首次会话**删一次 |
| 判定依据 | 无（`_prepare_test_dir` 无条件调 `reset_shared_databases`） | `BMS_TEST_RUN_ID` 与 `.cache/test/run.id` 一致即同一次运行（复用），否则删库并记新标识 |
| 运行标识来源 | — | `推送.py` / `提交前预检.py` 入口各写一次（整轮共用）；未设时每次 pytest 调用自成一次运行 |
| 用例数据 | 靠删库掩盖「依赖空库 / 固定键 / 整表口径」 | 一律按违规处理，改用例；新增强制自检门（见下） |

两处必须先修的地基（否则复用第二轮当场撞唯一键，实测 `UNIQUE constraint failed: sys_session.id`）：

| 地基 | 改动 | 说明 |
| --- | --- | --- |
| 命名空间前缀 | `namespace.py`：`sha1(nodeid)[:4] ^ 会话随机盐` | 原前缀「同用例跨会话一致」，复用时会与自己上一轮的行相撞；异或是双射，会话内「不同用例必不同」不变 |
| 自造行幂等 | `session_helpers.seed_session` 先删同键行再插；`form_design/helpers.seed_business` 按 code 已存在则复用 | 只动本用例键 / 固定业务码（`role` 不能命名空间化）；不删不改他人行 |

**隔离自检门（强制）**：新增 `scripts/tools/preflight/check_isolation_reuse.py`——同一批文件、**同一运行标识**连跑两轮（第 1 轮删库建库、第 2 轮叠加复用），**第 2 轮出现任何失败即判用例违规**。已接入提交前预检：本次改动含 `test_*.py` 时自动追加该步骤（只跑改动用例，覆盖率不参与）。《测试规范》§4 同步写入这条强制要求，并明确**不得**用加忙等 / 加删库 / 加独占库绕过。

实测（60 个末批目标文件、两轮同运行）：

| 阶段 | 第二轮结果 |
| --- | --- |
| 改造前 | **12 条失败**（identity 固定会话主键、icon 固定业务码、modules 全表清单等） |
| 补命名空间盐 + 两处幂等 | 7 文件子集降到 **1 条**（`test_role_business_grant_rejected_for_custom_role`） |
| 清掉库里 3 条重复的固定业务行（`sys_business.code='role'`，NULL 唯一约束下可重复） | 待复核后归零 |

新增用例 Kiwi **2549**（`test_gates.py`：新运行删库建库 / 同运行复用两态）。
