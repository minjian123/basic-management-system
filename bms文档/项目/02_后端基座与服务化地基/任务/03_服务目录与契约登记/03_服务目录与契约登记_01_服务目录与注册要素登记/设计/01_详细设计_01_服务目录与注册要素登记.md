## 1. 概述 <a id="overview"></a>

- **目标**：把阶段一交付的业务模块注册表 `sys_module` **升格为服务目录与契约登记**——同一张表承载「服务」与「模块」两类登记行，扩展服务维度（服务标识 / 归属分组 / 建设批次 / 产品归属）、契约版本（服务版本 / 契约版本）与业务权限码字段；按《[微服务演进规划](../../../../../../规划/微服务演进规划.md)》分组分批登记服务清单与注册要素（表前缀 / 业务码 / 错误码段 / 事件域），以平台种子方式幂等落库，并提供只读仓储支持按分组查询。
- **依据**：《[架构设计 · 模块注册](../../../../../../设计/架构设计/11_架构设计_子系统_模块注册.md)》「注册表结构与数据」「服务目录与契约登记」节；《[微服务演进规划](../../../../../../规划/微服务演进规划.md)》「目标架构与服务清单」节；《[平台可扩展性规划](../../../../../../规划/平台可扩展性规划.md)》「产品扩展接入形态」节；《[命名规范](../../../../../../规范/命名规范.md)》「数据库命名」「API 命名」节、《[数据库开发规范](../../../../../../规范/数据库开发规范.md)》「变更传导」「迁移与建表口径」节；需求 [03-1](../../../../需求/03_需求_服务目录与契约登记.md#r03-1)。
- **范围（本任务）**：
  1. **表结构升格**：`sys_module` 新增 `service_key` / `business_code` / `service_group` / `build_batch` / `service_version` / `contract_version` / `product_key`；`errcode_segment` 改为可空并移除其 DB 复合唯一约束（唯一性交启动 / CI 校验）。
  2. **登记清单单一来源**：`bms_core/services/module_registry.py` 扩展为 `SERVICE_CATALOG`（16 行）+ `ModuleRecord` 扩展字段 + `ServiceGroup` / 枚举与校验规则；`PLATFORM_MODULES` 收敛为清单视图。
  3. **种子落库**：`ops/seed_module.py` 由「新增平台域 4 行」升级为**按 `module_key` 幂等 upsert 全量清单**（既有 4 行补齐新字段）。
  4. **只读仓储**：新增 `ModuleRepository`（`BaseDbRepository[SysModule]`），支持按分组 / 状态 / 服务维度查询。
  5. **命名口径**：服务行沿用微服务工程名作登记标识与表前缀（如 `identity` / `identity_`），业务模块沿用《英文简称规范》既有简称；**不改动既有模块简称与表前缀**。
  6. **迁移与模型**：先改表文件 → 改 ORM 模型 → 新增平台链 `0002` revision（零漂移）。
- **不含（明确归口，见第 8 节）**：启动 / CI 接库唯一性与契约版本兼容校验（03_02）；只读 HTTP 接口 `GET /api/v1/modules`（03_03）；产品服务实际建表与每服务独立库拓扑（06_需求 / 各所属阶段）；RBAC 业务码表 `sys_business` 落地与 `business_code` 校验（RBAC 阶段）；`sys_` 前缀表的服务归属迁移。

## 4. 领域设计 <a id="design"></a>

### 4.1 登记模型（单表双用） <a id="model"></a>

`sys_module` 一行 = 一个**登记单元**，同一行可同时承载「服务」与「模块」两个维度：

- `module_key`：**行登记标识**（NOT NULL、唯一）——模块行取模块简称，服务行取服务标识（微服务工程名）；**服务与模块同源登记**。
- `service_key`：**服务维度标识**（可空、应用 / CI 层唯一）——服务行填微服务工程名（如 `identity`），模块行可留空（产品模块经 `product_key` 归属产品）。
- `business_code`：**业务权限码**（可空）——对齐将来 `sys_business.code`（RBAC）；模块行默认取 `module_key`，服务行留空。
- 既有平台域 `sys` / `wf` / `rpt` / `ai` 并入对应服务行（`platform` / `workflow` / `report` / `ai`），其 `01~04` 段位属**模块维度**、按既有契约保留。

字段一览（新增列以 **★** 标注）：

| 字段 | 类型 | 可空 | 约束 / 默认 | 说明 |
| --- | --- | --- | --- | --- |
| `id` | BIGINT | 否 | 主键，雪花 ID | 主键（`BaseModel` 公共字段） |
| `module_key` | VARCHAR(32) | 否 | 与 `deleted_at` 复合唯一 | 行登记标识（模块简称 / 服务简称） |
| **★** `service_key` | VARCHAR(32) | 是 | 应用 / CI 层唯一 | 服务维度标识（微服务工程名） |
| `name` | VARCHAR(128) | 否 | — | 名称（默认文案；多语言见 `sys_module_i18n`） |
| `table_prefix` | VARCHAR(32) | 否 | 与 `deleted_at` 复合唯一 | 表前缀（形如 `{简称}_`，**强制合法**） |
| **★** `business_code` | VARCHAR(64) | 是 | — | 业务权限码（`sys_business.code`；模块行默认取简称） |
| `errcode_segment` | VARCHAR(8) | 是（原否） | **去复合唯一** | 错误码段号（产品模块 `10` 起；平台域 `01~04`；纯服务空） |
| `event_domain` | VARCHAR(64) | 否 | 与 `deleted_at` 复合唯一 | 事件域（全小写，默认与 `module_key` 一致） |
| **★** `service_group` | VARCHAR(16) | 否 | 默认 `foundation` | 归属分组（`foundation` / `capability` / `product`） |
| **★** `build_batch` | INT | 否 | 默认 `0` | 建设批次（`0`~`3`，对齐演进规划） |
| **★** `service_version` | VARCHAR(16) | 否 | 默认 `0.1.0` | 服务版本（semver） |
| **★** `contract_version` | VARCHAR(16) | 否 | 默认 `0.1.0` | 公开契约（OpenAPI）版本（semver） |
| **★** `product_key` | VARCHAR(32) | 是 | — | 产品标识（`biz` / `cw`；空 = 平台） |
| `status` | VARCHAR(16) | 否 | 默认 `enabled` | 状态（`enabled` / `disabled` / `planned`） |
| `created_at` / `created_by` / `updated_at` / `updated_by` / `deleted_at` / `version` | — | — | `BaseModel` 公共字段 | 审计 / 软删除 / 乐观锁 |

**约束口径（关键）**：

- DB 级复合唯一仅保留 **NOT NULL 列**：`module_key` / `table_prefix` / `event_domain`（`(列, deleted_at)`）。
- **`errcode_segment` 与 `service_key` 不建 DB 唯一**（均可空）——达梦视复合唯一中的 NULL 相等（01_05 实测、计划「后续阶段待办 #1」归口信创阶段），多个空值行无法在达梦共存；其唯一性由启动 / CI 校验承担（03_02）。
- `table_prefix` 强制合法（`^[a-z][a-z0-9]*_$`）且全局唯一，**每个服务 / 模块分配独立前缀**；无合法前缀的登记不被接受。

### 4.3 服务标识与表前缀 <a id="shortname"></a>

- **服务标识**：服务行 `module_key` 取微服务工程名（`platform` 服务沿用既有平台域简称 `sys`）；10 个服务为 `sys` / `identity` / `tenant` / `org` / `file` / `notification` / `search` / `ai` / `rpt` / `wf`。`service_key` 固定取工程名（`platform` / `identity` / …），仅 `platform→sys`、`workflow→wf`、`report→rpt` 与 `module_key` 不同名。
- **表前缀**：按服务 / 模块分配独立前缀（`sys_` / `identity_` / `tenant_` / `org_` / `file_` / `notification_` / `search_` / `ai_` / `rpt_` / `wf_`），形如 `{module_key}_`；业务模块沿用既有前缀（`pur_` / `pay_` / … / `cw_`）。
- **不改动既有模块简称**：业务模块沿用《[英文简称规范](../../../../../../规范/英文简称规范.md)》§4 既有简称，本任务不整改其超长项（表前缀与标识符长度均在四库上限内：PostgreSQL 63 字节最紧、MySQL 64 字符，达梦更宽）。

### 4.4 校验规则 <a id="validate"></a>

`ModuleRegistry.validate()`（离线，种子 / 启动 / CI 共用）逐项产出冲突与非法明细：

| # | 规则 | 说明 |
| --- | --- | --- |
| 1 | `module_key` 唯一且合法 | 匹配 `^[a-z][a-z0-9]*$` |
| 2 | `service_key` 唯一（非空） | 匹配 `^[a-z][a-z0-9_-]*$`；服务行必填 |
| 3 | `table_prefix` 唯一且合法 | 匹配 `^[a-z][a-z0-9]*_$`，且首段 = `module_key` |
| 4 | `errcode_segment` 唯一（非空） | 两位数字（产品 `10` 起；平台域 `01`~`04`）；纯服务留空 |
| 5 | `event_domain` 唯一且合法 | 匹配 `^[a-z][a-z0-9_]*$` |
| 6 | `service_group` 合法 | ∈ {`foundation`,`capability`,`product`} |
| 7 | `build_batch` 合法 | 整数 `0`~`3` |
| 8 | 版本合法 | `service_version` / `contract_version` 匹配 semver `^\d+\.\d+\.\d+$` |
| 9 | 产品维度一致 | `service_group=product` ⇔ `product_key` 非空；`product_key` 取 `biz`/`cw` |
| 10 | 服务维度一致 | 服务行（`service_key` 非空）`business_code` 可空；模块行 `business_code` 默认取 `module_key` |

- 接库查重（读 `sys_module` 与清单比对、冲突即拒）归 03_02；本任务只做清单离线校验与仓储查询。

### 4.5 模型与迁移 <a id="migration"></a>

**变更顺序（强制，见《[数据库开发规范](../../../../../../规范/数据库开发规范.md)》「变更传导」节）**：

1. 改表文件 `设计/数据库设计/数据表设计/sys_module.md`（字段 / 索引约束 / 变更记录）；
2. 改 ORM 模型 `bms_core/models/platform.py::SysModule`；
3. 新增平台链迁移 `alembic/versions/platform/0002_sys_module_catalog.py`（`0001` 不动，遵循「新增变更 = 一个 revision」）；
4. 回写《数据库设计总览》登记状态（保持 `已落库`）与表文件状态。

迁移 `0002` 动作（四库通用、禁方言 SQL；SQLite 经 `batch_alter_table` 兼容）：

- 新增列：`service_key` / `business_code` / `service_group` / `build_batch` / `service_version` / `contract_version` / `product_key`（NOT NULL 列带 `server_default` 以便既有行平滑升级）；
- `errcode_segment` 改可空；
- 删除唯一约束 `uq_sys_module_segment_deleted_at`。

- 零漂移由 `test_alembic_drift.py`（既有 Kiwi 1078）覆盖；`PLATFORM_TABLES` 表集不变。

### 4.6 单一来源与种子 <a id="seed"></a>

- **单一来源**：`SERVICE_CATALOG` 是种子、启动校验、CI 校验与只读接口的共同来源；`PLATFORM_MODULES` 收敛为「平台域模块」视图（`service_group=foundation` 且 `errcode_segment` 非空），保持既有引用兼容。
- **种子脚本** `ops/seed_module.py`（`--url` > `BMS_MIGRATION_URL` > 配置 `database.platform.url`；`--dry-run` 打印清单）：
  - 对 `SERVICE_CATALOG` 逐行按 `module_key`（未软删）判存；
  - 不存在 → 插入；存在 → **更新**本任务新增字段（`service_key` / `business_code` / `service_group` / `build_batch` / `service_version` / `contract_version` / `product_key` / `errcode_segment` / `status`）；
  - 幂等：重复执行新增 0 行、更新 0 行；输出 `[seed_module] 新增 N / 更新 M 行`。
- **CI 离线校验** `ops/check_modules.py`：复用 `ModuleRegistry.validate()`，冲突 / 非法退出码 1。

### 4.7 只读仓储 <a id="repository"></a>

`bms_core/repositories/module_repository.py` 新增：

```text
ModuleRepository(BaseDbRepository[SysModule])
├── model = SysModule
├── list_catalog(*, group=None, status=None, service_only=False) -> list[SysModule]
│     # 作用域内 SELECT + 可选 WHERE（service_group / status / service_key IS NOT NULL）+ id 升序
└── get_by_key(module_key) -> SysModule | None
```

- 会话经构造注入（`get_db` / `get_write_db` / `get_uow` 同一请求同会话），只读、不提交；平台表非租户作用域。
- 仅提供读方法，**不提供写接口**（注册运行时只读边界，架构 11 §3.3）；写路径仅种子脚本（开发期）。
- 消费：03_03 只读接口经依赖注入取用；03_02 启动 / CI 校验读库比对。

### 4.8 装配与调用面 <a id="assembly"></a>

- `schemas/module.py::ModuleResponse` 增 `service_key` / `business_code` / `service_group` / `build_batch` / `service_version` / `contract_version` / `product_key`，供 03_03 只读接口直接序列化（本任务不改路由）。
- 既有 `bms_platform/api/modules.py` 仍返回内存清单（`ModuleRegistry`），其改读库与字段透出归 03_03；本任务保持接口可用不回退。
- 实施后开发平台库执行 `uv run python -m ops.seed_module` 落 16 行（幂等）。

## 5. 失败分支与边界 <a id="failures"></a>

| 场景 | 处理 |
| --- | --- |
| 清单内 `module_key` / `service_key` / `table_prefix` / `event_domain` 重复 | `validate()` 产出冲突明细，CI 退出码 1 |
| `table_prefix` 不含法形态（无下划线 / 大写 / 数字起首） | `validate()` 判非法；种子不落库 |
| `table_prefix` 首段与 `module_key` 不一致 | 校验判非法（登记标识与前缀一一对应） |
| 服务行缺 `service_key` 或多行同 `service_key` | 校验判非法 / 重复 |
| `service_group` 非枚举值、`build_batch` 越界、版本非 semver | 校验判非法 |
| `service_group=product` 但 `product_key` 为空 / 反之 | 校验判产品维度不一致 |
| 种子目标库已有同 `module_key` 行（含既有 4 行） | 走 upsert 更新新字段，不重复插入 |
| 种子目标库已有未软删行但字段与清单冲突且不属本任务字段 | 不覆盖（仅更新本任务新增字段），遗留交 03_02 接库校验 |
| 迁移在既有库升级（已有 4 行） | NOT NULL 新列带 `server_default`，既有行平滑填充 |
| 达梦下 `errcode_segment` / `service_key` 多空值 | 二者不建 DB 唯一，规避达梦 NULL 相等差异；唯一性交启动 / CI |
| 仓储查询未知分组 / 状态 | 返回空列表（不做校验，查询语义） |
| 运行时调用写接口 | 仓储不提供写方法，接口层不暴露（只读边界） |

## 8. 边界与开放项 <a id="boundary"></a>

- **归 03_02**：启动读服务目录校验（四要素唯一与格式、契约版本主版本兼容）；CI 按清单与迁移后查重；运行时只读边界的强约束。
- **归 03_03**：`GET /api/v1/modules` 与 `/{service_key}` 只读接口、统一响应与 404、鉴权随认证 / RBAC。
- **归 06_需求**：每服务独立配置与迁移链（database-per-service）；`sys_` 平台基础表的服务归属迁移（本任务只登记服务前缀命名空间，不动既有 `sys_` 表）。
- **归 RBAC 阶段**：`sys_business` 表落地与 `business_code` 唯一性 / 有效性校验。
- **开放项**：平台服务行 `errcode_segment` 留空、其错误码沿用平台 `1xxxx~9xxxx` 五位段（如需模块段位另行定案）；服务版本 / 契约版本的自动回写（CI 取 OpenAPI 版本）归 09_需求契约门禁。
- **不改**：既有平台域 `sys/wf/rpt/ai` 的注册值（段位 / 前缀 / 事件域）；`sys_module` 表名与平台链归属；既有路由前缀与响应体。
