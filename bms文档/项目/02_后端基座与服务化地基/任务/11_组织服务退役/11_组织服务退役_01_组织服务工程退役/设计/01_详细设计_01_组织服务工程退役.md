## 1. 设计目标与范围 <a id="goal"></a>

承接需求 11-1：**一步到位退役 bms `org` 服务**——删除服务工程，清理服务目录 / 网关 / 契约快照 / api-types / 迁移链 / 部署脚本 / CI 与校验脚本中的 org 登记；组织主数据职责归 mdm。

1. **工程删除**：`backend/services/org/` 整目录。
2. **登记清理与置位**：`SERVICE_CATALOG` 的 `org` 条目**易主**（平台能力服务 → mdm 产品服务，见下「协同改动 1」）、网关 upstream/route、契约快照与 baseline、api-types、`Dockerfile` COPY、`ops/dev_run.py`、相关测试与校验脚本引用。
3. **迁移链与库**：删除 `alembic/versions/org/` 与 `org:platform`；清理已存在的 `bms_org_{code}` 租户库。
4. **服务规模**：平台服务由 **9 → 8** 个平台服务工程（`org` 退出平台服务计数，计入产品服务）。

**执行顺序（跨任务，强制；2026-10-07 修订）**：本任务**提前执行**——**先退役释放 `org` 标识，mdm 随后以 `org` 承接**。原「先切出口（11_02 前段）→ 后删服务（本任务）→ 再移除基座契约（11_02 后段）」的次序随之修订为：本任务（退役与置位）→ mdm 需求 01-1 / 01-2 / 01-3 交付 → 11_02 前段（前端 / 调用方切 mdm 出口）→ 11_02 后段（`bms_core/org` 契约与装配移除）。

**为什么可以提前**：bms `org` 服务已空壳——`MODEL_MODULES` 空元组、无归属表（`sys_user` / `sys_account_lock` 已迁 platform）、仅 4 个占位路由（`/org/users` `/org/posts` `/org/dept-tree` `/org/resolve-names`）走 `bms_core/org` Null 实现；前端组织选择字段族当前仅开发校验页 `frontend/apps/desktop/src/dev/OrgCheck.vue` 与组件库测试引用、**无业务页消费**——退役不造成业务断档。而 mdm 组织域**必须先取得 `org` 标识**（注册要素一经登记即对外契约、不回收改派）才能立项工程，故次序调整为「先释放、后承接」。

**协同改动（2026-10-07 追加确认，同批次交付）**：

1. **`org` 行易主（不删除）**：`SERVICE_CATALOG` 的 `org` 行由**平台能力服务**改为**mdm 产品服务**——`service_group: capability → product`、`product_key: None → mdm`、`errcode_segment: None → "33"`、`build_batch: 2 → 3`、`name → mdm 组织主数据服务`、`contract_version → 0.1.0`（服务版本随 mdm 服务包）。保证 `known_service_keys()` 与网关 upstream **不出现空窗**：mdm 服务键 / 迁移链名 `org:tenant` / 库键派生（`platform_org` / `tenant_org_{code}`）立即可用。
2. **mdm 产品登记**：`PRODUCT_ROUTES` 增 `mdm/org → org` 映射（产品命名空间 `/api/mdm/v1/org/...`）；`PRODUCT_CATALOG` 的 `mdm` 状态 `planned → enabled`。
3. **网关服务级路由分组**：`render_upstreams()` 保持**全量 enabled 服务**（产品级路由需要 `org` upstream `org:8000`）；`render_routes()`（服务级路由 `/api/{service_key}/v1`）**只取非产品分组**——产品服务仅经 `/api/{product_key}/v1/{domain}` 暴露，避免 `/api/org/v1` 服务级命名空间泄露。
4. **库名前缀参数化**：基座库名派生前缀由硬编码 `bms_` 改为 `[database].name_prefix`（默认 `bms`），供 mdm 配 `mdm`（`mdm_org` / `mdm_org_demo` / `mdm_archive`）；本仓默认值不变，现有部署零影响。
5. **产品服务合并同值去重**（12_03 机制微调）：应用级服务目录视图（平台清单 + 产品服务注入记录）按「同 `module_key` **同值去重、异值即拒**」合并，使平台侧登记行与产品侧自报注入行**并存而不冲突**（保留 12_03 的产品自持清单意图，同时让平台侧登记服务于网关 / 迁移链 / 库键 / 表归属派生）。

**不在本期**：`bms_core/org` 契约与装配移除、前端 adapter 切换（归 11_02）；门禁回归与阶段收口（归 11_03）；`bms_org_{code}` 租户库 DROP（运维，见 §8 开放项）。

## 4. 失败分支与边界 <a id="edge"></a>

| 场景 | 处置 |
| --- | --- |
| 服务目录 `org` 行易主后启动校验 | 对账「8 个平台服务 + `org`（产品行）」通过；运行库登记行随 `ops.seed_module` 幂等 upsert 更新为产品归属（`service_group` / `product_key` / `errcode_segment` 变化由接库对账检出） |
| 契约快照残留 org | `contract_snapshot check` 报漂移 → 删除 `org.json` 与 baseline 后按 8 服务零漂移 |
| api-types 与契约不一致 | 前端类型零漂移门禁失败 → 重新生成 |
| 迁移链删除后真库残留 | `bms_org_{code}` 库由运维清理（DROP）；旧链记录清理（不参与新迁移） |
| 网关残留服务级 org 路由 | 网关配置校验（`gateway_config check`）失败 → 重生成后仅剩产品级 `route-mdm-org` |
| 前端仍调用 bms org 出口 | 组织选择字段族无业务页消费（仅开发校验页 `frontend/apps/desktop/src/dev/OrgCheck.vue` 与组件库测试），该页在 mdm 出口就绪前不可用属已知空窗，随 11_02 前段切换恢复 |
| 库名前缀参数化影响现有部署 | 默认值仍为 `bms`（`config.toml`），本仓生成库名与既有部署完全一致；`check-*` 与库键用例按默认值断言不变 |
| 合并同值去重弱化错误检出 | 仅对「完全相同记录」去重；任何字段差异（含 `status` / `contract_version` / `build_batch`）仍判冲突拒启（与 12_03 fail-closed 口径一致） |

## 6. 实施要点 <a id="impl"></a>

- **顺序内嵌（2026-10-07 修订）**：本任务**提前执行**，不再等 11_02 前段——先退役释放 `org` 标识，mdm（需求 01-1 / 01-2 / 01-3）随后以 `org` 承接；本任务完成后再做 11_02 前段（前端 adapter 切 mdm 出口）与后段（`bms_core/org` 移除）。
- **协同改动顺序**：① 基座能力（`name_prefix` 参数化 → 合并同值去重 → 网关服务级路由分组）→ ② 服务工程删除与登记引用清理 → ③ `org` 行易主 + 产品级路由 + 产品状态 → ④ 生成件重生成（网关 / 契约快照 / api-types）。
- **重生成**：契约快照、api-types、网关 `apisix.yaml` 以工具重新生成（非手改），保证与实现一致。
- **不动既有语义**：平台其余 8 服务行为与库名（默认 `bms` 前缀）不受影响；共享基座 `bms_core` 除本任务列明点位（`module_registry` / `gateway_catalog` / `application` / `db/keys` / `db/engine` / `core/config`）外不改动（`bms_core/org` 移除归 11_02）。
