## 2. 背景与动机 <a id="why"></a>

01_04 已在真栈闭环「发布 → 消费 → 审计分片落库 → 链校验」，但 180 条突发下端到端 P95 为 **15.8~16.1 秒**（约 9.5 条/秒），高于 5 秒目标（15_01 报告 §5.3、§8-2）。已定位的构成有三条：

1. **有序组全组串行**：`audit-chain` 声明 `ordered=True`，键级执行器道数固定 1，3 租户 × 3 日志类型的全部消息挤在同一条道上；
2. **批内逐条 ack**：拉取到的消息处理完一条就发一次 ack 请求，每条一次 HTTP 往返 + msg 侧一次位点提交；
3. **一条一事务**：每条记录独立开会话、独立事务，链尾查询与插入各一次（`writer.py` / `jobs.py`）。

同时存在两项每消息固定开销：Redis 去重「判读 + 标记」两跳、逐条指标上报。测得每条约 105ms，明显高于「一次提交 + 一次 ack」的理论值，说明还有未定位开销，需先测量再优化。

本任务按「链的真实粒度」（租户 × 日志类型）拆分并行度，并把事务、去重、指标从「每条一次」降到「每批一次」，在**不改变哈希链语义**的前提下把端到端 P95 压到 5 秒以内。

## 3. 任务内容 <a id="content"></a>

1. **分段计时基线**：在消费链路加入可关闭的分段计时（拉取 / 解码 / 去重 / 分派 / 事务 / ack），用同一复跑脚本采一轮构成数据。
2. **有序组按链键分道**：键级执行器支持「按链键动态建道」——每个（租户 × 日志类型）一条道，同链严格串行、跨链并行；道数上限与空闲回收可配。
3. **批量消费契约**：`EventConsumer` 增加可选 `consume_batch`，返回与入参等长的逐条结果；缺省实现逐条调用既有 `consume`，既有处理器零改动。
4. **批量事务与链计算**：审计链写入按批分组，批内每链只查一次链尾、在内存里逐条衔接哈希，一批一次事务提交；失败整批回滚并交回逐条重试。
5. **ack 并发化**：同分区按序 ack、跨单元并发；位点语义与失败处理保持现状（未 ack 的消息由 broker 重投）。
6. **去重与指标降开销**：Redis 去重改 pipeline 批量判读 / 批量标记，事务内按 `event_id IN (...)` 批量查重；计数逐条、耗时按批上报新计数器。
7. **验收复跑**：沿用 `tmp/e2e_audit_latency.py` 同一口径复跑 180 条，并追加 600 条线性度场景；结果回写 15_01 报告与测试记录。

## 4. 完成标准 <a id="accept"></a>

- 180 条突发（3 租户 × 3 类 × 20）端到端 P95 **≤ 5 秒**，P50 / P99 / 最大与排空总耗时同表登记；与 15.8~16.1 秒基线可比（同脚本、同口径、同清理步骤）。
- 600 条场景（每租户每类约 67 条）排空耗时相对 180 条的增长显著低于线性 3.3 倍，证明并行度与批量确实生效。
- 三类审计分片链校验全量通过（`prev_hash` / `record_hash` 重算一致），批内、跨批、跨月链头均正确；跨月切换仍有自动化用例覆盖。
- 失败与边界：单条毒消息不连坐整批；批事务失败整批回滚且可重试；未 ack 的消息在可见性超时后重投且只生效一次；停机时批要么已提交要么未处理。
- 既有行为回归：有序组顺序语义按新口径（同链串行、跨链并行）通过用例；非有序组、作业投影组、通知组行为不变；现有 01_04 用例全绿。
- 新增与改动模块覆盖率达标（口径见《[AI开发规范](../../../../../规范/AI开发规范.md)#coverage》「覆盖率要求」节），静态检查与装配冒烟全绿。
- Kiwi 用例编号取自平台回读；实施记录、测试记录、计划与 15_01 报告回写齐备。
