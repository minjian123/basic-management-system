## 2. 过程 <a id="process"></a>

### 2.1 批 1：配置与常量收敛

- `[dict]` 新增 7 个参数（`type_ttl_seconds` / `empty_ttl_seconds` / `lock_ttl_seconds` / `lock_wait_seconds` / `l1_max_items` / `probe_limit` / `invalidate_on_write`），配套 `DictSettings`。
- 字段名取 `dict_options` + `validation_alias="dict"`：直接叫 `dict` 会遮蔽 `BaseSettings.dict()`（实测 pydantic 告警），且 `Settings` 为 `extra="forbid"`——配置节与字段必须同批落地，否则启动即失败。
- 基线 `config.toml` 补 `[data_source]`（routed）/ `[dict_translator]`（routed）/ `[dict_cache_region]`（memory）：**修掉 test / prod 落 null 实现（字典恒空）** 的现状；`config.dev.toml` / `config.prod.toml` 覆盖为 `redis`，`config.test.toml` 压短 TTL。
- 新增 `datasource/keys.py::DataSourceKey`（12 个平台 key 的 StrEnum）+ `platform_data_source_keys()`；`DATA_SOURCE_CATALOG` 与 `FORM_CATALOG` 的 `data_source_key` 全部改用枚举值（24 处字面量收敛）。
- `DictCacheRegion.lock_cache_key()` + `adrop_id_subset()`；Redis 缓存域互斥锁键由 `lock:bms:...` 改为 `bms:{tenant}:dict:lock:{locale}:{type}`（命名规范口径）。

### 2.2 批 2：出口与表源

- `DictOptions`（值对象，`[dict]` 的唯一运行期形态，`from_settings()` 构造）；`RoutedDataSource` 注入 options。
- 出口四处改造：空结果走 `empty_ttl_seconds`、带过滤条件不缓存、互斥锁 TTL / 等待可配、`batch` 尊重入参 `locale`（缺省值视为未指定，沿用 `Accept-Language`）。
- 翻译复用缓存：先读 `aid_subset` → 只对缺失 id 回源 → 回填（原实现每次全量 `load`）。
- 提供者异常边界：`_load_rows()` 只包 `provider.load`，异常记 `warning` 并返回空结果、**不写缓存**。
- `DictTableDataSource` 扩展：`db_scope`（platform / tenant）+ `DictI18nSpec`（i18n 附表 LEFT JOIN + `COALESCE` 回退）+ `sort` 列可缺省（按 `id` 排序）。
- 新增 `DictInvalidator`（DEL 各语言类型键 + id 子集键 → `INCR` 版本键；失败只告警）+ `get_dict_invalidator` 依赖。

### 2.3 批 3：平台规格与失效接入

- 新增 `dict_specs.py`：12 个 key 一行规格（库域 / 表 / 列映射 / i18n / 排序 / `mode`），平台库 5 + 租户库 7；`role` 保留 `mode=port` 走 `RoleReferencePort`，其余 `mode=table` 走表源。
- `PlatformDictDataSource` 改为按规格分派（表源实例按 key 缓存），**新增字典不再改本文件**。
- 角色域三个写端点（`POST /roles`、`PUT /roles/{id}`、`DELETE /roles/{id}`）在服务层提交后调 `invalidate(("role",))`——顺序为「先提交、后失效」。

### 2.4 批 4：启动校验与护栏

- `application.service_lifespan` 前置 `_validate_data_sources()`：清单自校验（复用 `DataSourceRegistry.validate()`）+ 覆盖校验（仅 `provider=routed` **且本进程已登记提供者**时，避免非平台服务启动即失败）。
- `ops/check_tables.py` 的 `check_offline` 追加数据源登记校验（运维 / CI 离线复跑同一规则）。
- 护栏用例两份：基座 `tests/datasource/test_registry_guard.py`（枚举 ↔ 清单、无 `sys_dict*` 表、声明表外无 `data_source_key` 字面量）、服务侧 `tests/dict/test_dict_registry_guard.py`（规格 ↔ 清单 ↔ 模型列 ↔ 库域 ↔ i18n 关联列）。

## 附录 A：依赖环境跨平台事故与处置（2026-10-31） <a id="appendix-deps"></a>

> 本节记录本段实施期间发生的**本机依赖环境**事故、恢复过程与结构性加固，供后续同类环境问题对照；属实施细节，不进 `AGENTS.md`（那边的操作规则不因此改变）。

### A.1 现象与根因

| 项 | 内容 |
| --- | --- |
| 现象 | `backend/.venv/Scripts/python.exe` 消失；`D:\dev-deps\bms\backend-venv` 只剩 `lib64 -> lib` 与 `pyvenv.cfg`（`home = /usr/local/bin`、`uv = 0.12.7`），即 Windows venv 被替换成 Linux venv |
| 直接原因 | 执行「全量 pyright」时把命令套进 `bash -lc "cd backend && uv run pyright"`：Windows 上 `bash` 解析到 WSL 的 `bash.exe`（输出里出现 `/mnt/d/Develop/...` 即为证据），随之运行的是 **WSL 侧 uv**，它把依赖仓当成自己的项目环境重建 |
| 为何原守卫没拦住 | `deps_common.py` 的跨平台判定只在**脚本**里跑（`还原/外置/重装`）；直接调 `uv` 绕过脚本，不受任何校验 |

### A.2 恢复步骤（实测可用，约 3 分钟）

1. 留证不删：`mv backend-venv backend-venv.broken-20261031`。
2. 用 Windows 结构备份换回：`mv backend-venv.bak-20261019 backend-venv`（其 `pyvenv.cfg` 的 `home` 为 `C:\...`、`Scripts/python.exe` 可用）。
3. `python scripts/tools/deps/重装依赖.py --backend-only`（还原 → `uv sync --frozen` → 再外置）。
4. 验证：`backend/.venv/Scripts/python.exe -m pytest libs/bms_core/tests/dict -q -n0` → **98 passed**。

### A.3 结构性加固（已提交 `d8718c23b`）

- **依赖仓按平台分目录**：`resolve_deps_dir()` 返回 `<依赖根>/<windows|linux>`，两平台的 `backend-venv` / `node_modules` / `frontend` 落在不同子目录，共用同一 `DEPS_DIR` 也不互相覆盖。
- **平台标识校验**：每个平台目录落 `.platform`（内容为平台标签），三个 deps 脚本启动即 `ensure_platform_marker()` 校验，不匹配直接 `exit 2`；与既有 `pyvenv.cfg` 平台判定形成双重校验。
- **老布局自动迁移**：`migrate_legacy_layout()` 把根下 `backend-venv` / `node_modules` / `frontend` 一次性搬进平台目录（目标已有则跳过、跨平台 venv 不搬）。
- **修掉一处自伤**：`重装依赖.py` 原先把解析结果导出为 `DEPS_DIR` 给子脚本，平台分目录后会叠成 `<根>/windows/windows`；改为导出**依赖仓根**。
- 切换平台只需跑一次 deps 脚本：两边数据都在，**不需要重新安装**。

### A.4 操作要点（本机环境，仅供排障对照）

- `uv` / `pnpm` / `pip` 只经 `scripts/tools/deps/` 三个脚本调用；脚本外的安装器不受校验保护。
- 不要把命令套进 `bash -lc` / `bash -c`：切目录直接 `cd <dir> && <cmd>`（同一 shell），需要 shell 语义用 `cmd /c`。
- 调用前验身份：`uv --version` 含 `windows` 才是本机 uv；`python -c "import sys;print(sys.executable)"` 应为 `C:\...`。
- 自检：`.venv/Scripts/python.exe` 不存在且 `pyvenv.cfg` 的 `home` 为 POSIX 路径 → 被 WSL 侧污染，跑一次 `重装依赖.py --backend-only` 即回到本平台目录。
- **残余暴露面**：绕过脚本在 WSL 里直接 `uv sync` 仍会顺着 `backend/.venv` 链接写坏 `windows` 那份；但 `linux` 那份完好，恢复只需再跑一次 Windows 侧脚本，无需重装依赖。
