## 1. 概述 <a id="overview"></a>

- **目标**：把需求 11-1 的四个数字（主链路 P99 差异 ≤5%、审计链消费 P95 ≤5s、单租户写入 ≥500 条/秒、分片表当月 25 日前就绪）落成**可采集的指标 + 可触发的告警 + 可复现的压测方法与报告**，而不是只写一份结论。
  1. **指标**：按现有指标基座（`BaseMetrics` / `METRIC_NAMES` / `METRIC_DOCS`）扩展 7 个指标名 + 给既有 `bms_outbox_backlog` 补 `db_key` 维度，模块内不自研平行指标。
  2. **告警**：5 条规则（Outbox 1 万/租户、审计链 P95 超 5s、审计链断裂、次月分片 25 日后未就绪、死信超 24 小时未处置），配 `promtool` 规则单测真跑表达式。
  3. **面板**：新增「容量口径」Grafana 面板（四组），随既有 provisioning 目录自动加载。
  4. **压测**：固定数据集（单租户 5 万条）+ 固定并发（32）+ 三档配置（副作用全关 / 仅操作日志 / 全开）跑主链路；写入侧基准直接驱动真实 `AuditLogWriter`，测吞吐、分位与积压排空。
  5. **报告**：测试记录 + 独立压测报告，写明环境规格与「限定达标」差距归口。
- **依据**：需求 [11-1](../../../../需求/11_需求_容量与延迟.md#r11-1)；《[架构设计 · 事件总线](../../../../../../设计/架构设计/16_架构设计_子系统_事件总线.md)》§4 / §5 / §6；《[架构设计 · 任务调度](../../../../../../设计/架构设计/17_架构设计_子系统_任务调度.md)》§5；《[架构设计 · 审计哈希链](../../../../../../设计/架构设计/19_架构设计_子系统_审计哈希链.md)》§3 / §4 / §5；《[架构设计 · 可观测性](../../../../../../设计/架构设计/27_架构设计_子系统_可观测性.md)》「指标采集」；《[测试规范](../../../../../../规范/测试规范.md)》§2 / §6 / §14；《[部署发布规范](../../../../../../规范/部署发布规范.md)》§11。
- **范围**：指标基座扩展与发射点接线、告警规则与规则单测、容量面板、写入侧基准、HTTP 压测场景（测试资产仓）、压测报告与测试记录、计划与需求回写。
- **不含（归口见 §12）**：msg 消费组运行时实现（01_01 遗留，阻塞端到端消费延迟实测）、`audit-chain` 多实例扩容实现（依赖上一条）、真三库与真 broker 环境压测（部署窗口 / 阶段十四验收压测）、前端容量页面（无此需求）。

## 4. 指标设计 <a id="metrics"></a>

> 全部指标名登记进基座 `METRIC_NAMES` 与 `METRIC_DOCS`；实现侧常量集中在 `bms_core/audit/observability.py`，业务模块不写字面量。

### 4.1 指标清单 <a id="metric-list"></a>

| 指标名 | 类型 | 标签 | 语义 | 发射点 | 基数 |
| --- | --- | --- | --- | --- | --- |
| `bms_audit_consume_lag_seconds` | 直方图（秒） | `log_type` | 事件 `occurred_at` → 审计分片落库完成的时延 | `AuditLogWriter._append`（写入成功后） | 3 |
| `bms_audit_write_total` | 计数器 | `log_type` / `tenant` | 审计日志写入条数（`rate()` = 单租户吞吐） | 同上 | 3 × 租户数 |
| `bms_audit_chain_valid` | 瞬时值 | `log_type` | 最近一次链校验结果（1 完整 / 0 断裂） | 内部校验端点、`/audit/chain/verify` | 3 |
| `bms_audit_chain_broken_total` | 计数器 | `log_type` | 累计检出断裂次数 | 同上（仅 `valid=false` 时 +1） | 3 |
| `bms_audit_shard_next_month_ready` | 瞬时值 | `log_type` | 次月分片是否已就绪（1 / 0） | `ensure_audit_shards`（启动预热 + 预创建端点） | 3 |
| `bms_event_dead_letter_pending` | 瞬时值 | `source` / `db_key` | 待处置死信条数（`status=pending`） | `PollOutboxDispatcher.dispatch_once` 的指标上报段 | 2 × 库键数 |
| `bms_event_dead_letter_age_seconds` | 瞬时值（秒） | `source` / `db_key` | 最老待处置死信距今时长（无待处置为 0） | 同上 | 2 × 库键数 |
| `bms_outbox_backlog`（扩展） | 瞬时值 | `db_key`（新增） | 该库待投递条数 | 同上 | 库键数 |

**基数口径**：`tenant` 取租户主键十进制字符串（与 `sys_outbox.tenant_id` 同源），无租户时取 `global`；`db_key` 为数据源键（平台库 `platform`、租户库 `tenant_{code}` / `tenant_{unit}_{code}`），基数随租户数线性增长、有界。`log_type` 取 `operation` / `login` / `data_audit`。

### 4.2 发射函数（单一落点） <a id="metric-record"></a>

`bms_core/audit/observability.py`：

```text
METRIC_AUDIT_LAG = "bms_audit_consume_lag_seconds"
METRIC_AUDIT_WRITE = "bms_audit_write_total"
METRIC_CHAIN_VALID = "bms_audit_chain_valid"
METRIC_CHAIN_BROKEN = "bms_audit_chain_broken_total"
METRIC_SHARD_NEXT_MONTH_READY = "bms_audit_shard_next_month_ready"

async def record_audit_write(metrics, *, log_type, tenant, lag_seconds) -> None   # 记直方图 + 计数
async def record_chain_verify(metrics, *, log_type, valid) -> None               # 记 valid + 断裂计数
async def record_shard_readiness(metrics, *, log_type, ready) -> None            # 记次月就绪
```

- 三个函数 `metrics is None` 时**空操作**（消费处理器 / 无指标环境的测试不必构造替身）。
- `lag_seconds` 取 `max(0.0, written_at - occurred_at)`：事件缺 `occurred_at` 时按写入时刻计（时延 0）。
- 不在模块内另写指标名或标签拼装（改口径只改这一处）。

### 4.3 死信统计契约 <a id="dead-letter-stats"></a>

`bms_core/outbox/base.py` 增值对象与端口方法：

```text
DeadLetterStat(BaseValueObject, frozen dataclass)
├── source: str                 # outbox / consumer
├── pending: int                # status=pending 的条数
└── oldest_occurred_at: datetime | None   # 最老待处置事件的发生时间
```

`BaseOutboxStore.dead_letter_stats(session)` → `ConcurrentStableList[DeadLetterStat]`：

- 实现（`store.py`）：`SELECT source, COUNT(*), MIN(occurred_at) FROM sys_event_dead_letter WHERE status='pending' GROUP BY source`；
- `null.py`：返回空清单（占位实现不改语义）；
- 已处置（`replayed` / `ignored`）不计入 —— 只统计「待处置」。
- 探针 / 测试对表内他人数据不清理，按来源断言相对增量（《测试规范》§4）。

## 5. 告警设计 <a id="alerts"></a>

### 5.1 规则清单 <a id="alert-list"></a>

`deploy/observability/rules/bms-slo.yml` 新增 `bms-capacity` 组（并调整 `bms-outbox` 组的旧阈值）：

| 告警名 | 表达式（要点） | 分级 | 说明 |
| --- | --- | --- | --- |
| `BmsOutboxBacklogPerTenant` | `bms_outbox_backlog{db_key=~"tenant_.*"} > 10000` for 10m | warning | 单租户库待投递超 1 万条；`db_key` 出明细 |
| `BmsOutboxBacklogPlatform` | `bms_outbox_backlog{db_key="platform"} > 10000` for 10m | warning | 平台库同阈值（替换旧 `> 100` 锚点口径） |
| `BmsAuditConsumeLagHigh` | `histogram_quantile(0.95, sum by (le, log_type) (rate(bms_audit_consume_lag_seconds_bucket[5m]))) > 5` for 5m | warning | 审计链消费 P95 超 5 秒 |
| `BmsAuditChainBroken` | `bms_audit_chain_valid == 0` for 1m | critical | 链断裂（合规风险，立即处置） |
| `BmsAuditShardNextMonthMissing` | `(bms_audit_shard_next_month_ready == 0) and on() (day_of_month() >= 25)` 持续 1 小时 | critical | 当月 25 日后次月分片仍未就绪，跨月写入将失败 |
| `BmsDeadLetterPendingTimeout` | `bms_event_dead_letter_age_seconds > 86400` for 5m | warning | 死信超过 24 小时未处置 |

> **阈值单一来源**：阈值只落规则文件（应用只出原始值），1 万 / 5 秒 / 24 小时 / 25 日四个数字与需求 11-1 逐字对应；改阈值不改代码、不重启服务。

### 5.2 可触发的验证方式 <a id="alert-verify"></a>

两层证据，均不依赖线上真实积压：

1. **规则单测**（`deploy/observability/rules/tests/bms-capacity.test.yml`，`promtool test rules`）：
   - 每条规则给两组输入序列——**阈值外**（不触发）与**阈值内**（触发），断言 `exp_alerts` 精确匹配告警名、标签与注解；
   - 分片规则用 `eval_time` 落在 25 日前后各一次，断言「25 日前不就绪不报警、25 日后不就绪必报警」；
   - 死信规则用 `age = 86399`（不触发）/ `86401`（触发）卡边界。
2. **指标发射用例**（pytest）：断言真实调用路径把指标写进 `PrometheusMetrics` 注册表（`render()` 文本可见），避免「规则对、指标没发」。

**执行**（开发机无 Docker，规则单测在开发服务器上用**最新版 promtool 3.16.0** 的临时容器跑，只读挂载临时目录、不改共享规则与镜像）：


| 1 | 主链路 P99（按路由） | `histogram_quantile(0.99, sum by (le, route) (rate(bms_request_duration_seconds_bucket{route=~"$route"}[5m])))` | 主链路不被阻塞 |
| 2 | 审计链消费 P95 与写入吞吐 | `histogram_quantile(0.95, … bms_audit_consume_lag_seconds_bucket …)` / `sum by (tenant) (rate(bms_audit_write_total[1m]))` | 消费 P95 / 单租户吞吐 |

## 7. 压测设计 <a id="load-test"></a>

### 7.1 环境与固定口径 <a id="env"></a>

| 项 | 口径 |
| --- | --- |
| 执行环境 | 本机（mjpc，Windows）裸跑全套：`scripts/tools/dev/本地全套.py up`（platform / tenant / identity）；本地 SQLite（`database/bms/*.db`）+ 内存缓存；Redis 用开发服务器隔离库 |

| 固定数据集 | **单租户 5 万条**审计事件（写入侧基准）；HTTP 压测每档固定请求数 |

### 7.2 主链路三档对比 <a id="main-path"></a>

同一端点、同一请求体、同一并发与请求数，只改配置（两次重启切换）：

| 档 | 配置 | 作用 |
| --- | --- | --- |
| A 全关 | `BMS_AUDIT_LOG__ENABLED=false` + `BMS_AUDIT_CAPTURE__ENABLED=false` | 基线（无审计副作用） |
| B 仅操作日志 | `audit_log.enabled=true` + `audit_capture.enabled=false` | 只测异步副作用（响应后写发件箱） |
| C 全开 | 两者 `true`（默认） | 含字段级审计同事务捕获 |

判据：`P99(C) / P99(A) - 1 ≤ 5%`。B 档用于说明「操作日志写发件箱在响应后执行，不进客户端时延」；C 档与 A 的差额单列为**字段级审计同事务成本**（06_02 明确取舍：宁可拒绝写、不可无审计），不计入「异步副作用」结论。

> 说明：操作日志事件在中间件 `finally` 里发射（响应体已发送），客户端测得的时延天然不含该段；这正是需求「响应不等待异步副作用」的实现口径，报告须写明测量边界。

**实施期调整（环境阻塞）**：本机起 platform / tenant / identity 时，服务间回连在启动钩子阶段被拒（换回环别名与 `127.0.0.1 + 不同端口` 均复现；同一调用从独立进程可通，端口 / 代理 / 端点映射已逐一排除），HTTP 客户端口径无法闭环。改用**应用层 A/B**（`benchmarks/bench_main_link.py`）：真实 `SysRole` 写入 + 真实 ORM 字段级捕获 + 同事务 / 响应后段发件箱，三档 `off` / `field` / `oplog`；HTTP 段标「限定达标（环境阻塞）」，归口部署窗口复测（§12-10）。

### 7.3 审计链写入与积压排空 <a id="write-bench"></a>

`backend/benchmarks/bench_audit_chain.py`（真实 `AuditLogWriter` + 本地 SQLite + `PrometheusMetrics`）：

1. **稳态吞吐**：逐条构造事件并**立即**写入（无积压），跑 `--rows 50000`，输出条/秒与 P50 / P95 / P99 写入时延；目标 ≥500 条/秒。
2. **积压排空**：先构造 `--rows` 条事件（`occurred_at` = 入队时刻）放入内存队列，再逐条写入（**一条一事务**，与 `audit-chain` 消费处理器同口径），输出端到端（入队 → 落库）P50 / P95 / P99 与排空总耗时；目标 P95 ≤5s。
3. **指标渲染**：跑完 `metrics.render()`，把 `bms_audit_write_total` / `bms_audit_consume_lag_seconds` 的实际样本值打印并写入报告，证明指标发射点真实生效。
4. **提交成本分离（补充口径）**：`--batch N` 把 N 条并入一个事务（仅用于区分「链计算成本」与「每事务 fsync 成本」，不改变官方口径）；官方值恒为 `--batch 1`。

**测量边界（必写进报告）**：
- 环境无 broker，第 2 项**不含** msg 传输、可见性超时与消费组拉取段，属「消费侧处理段」；端到端标「限定达标」，差距 = broker 传输 + 拉取排队，归口 01_01 补口任务。
- `audit-chain` 为单道串行（`ordered=True`），积压排空时延随积压量线性增长；本报告给出 5 万积压下的实测值，作为「消费扩容」决策依据（归口 §12-2）。

### 7.4 分片提前量与跨月 <a id="shard"></a>

- **提前量**：预创建任务（`ensure_audit_shards`，`months_ahead=1`）在注入时钟为「当月 26 日」时执行 → 次月台账与物理表存在，`bms_audit_shard_next_month_ready=1`；
- **跨月 0 失败**：时钟推进到次月 1 日，写入三类日志各一条 → 直接成功，次月首条 `prev_hash` = 上月同租户末条 `record_hash`（首月为创世哈希），校验器通过；
- 均为注入时钟的自动化用例（不等待真实跨月），报告引用用例编号与断言结果。

| 场景 | 行为 | 依据 |
