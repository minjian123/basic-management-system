## 4. 主链路三档明细 <a id="main-path"></a>

### 4.1 测量边界 <a id="main-boundary"></a>

- 操作日志事件在 ASGI `finally`（响应体已发送）发射，**客户端时延天然不含该段**；这正是「响应不等待异步副作用」的实现口径。
- C 档与 A 档差额单列为**字段级审计同事务成本**（06_02 取舍：宁可拒绝写、不可无审计），不计入「异步副作用」结论。
- HTTP 客户端三档因本机服务间回连在启动钩子被拒（换回环别名、`127.0.0.1 + 不同端口` 均复现；同一调用从独立进程可通）未能闭环；改用 `benchmarks/bench_main_link.py` 的**应用层 A/B**（真实 `SysRole` 写入 + 真实 ORM 捕获 + 同事务 / 响应后段发件箱）。

### 4.2 四轮结果 <a id="main-rounds"></a>

| 轮次 | 数据集 | P99 差异（C 对 A） | P95 差异 | 备注 |
| --- | --- | --- | --- | --- |
| 1 | 2000 | −3.2% | 记录未留存 | — |
| 2 | 3000 | +98% | 记录未留存 | 离群：SQLite 提交尖峰（同轮 `oplog` 变体最长 298 ms） |
| 3 | 2000 | +2.0% | +4.0% | — |
| 4 | 3000 | −2.9% | +7.9% | — |
| 中位 | — | **+5.0%** | **+4.0% / +7.9%** | 不取单轮最优值 |

- 结论：中位 P99 差异 **+5.0%**，处判据临界；单轮最大值由 SQLite 提交尖峰主导，不能据此判定链路退化。
- P50 / P95 / P99 的绝对值在实施记录中未逐项留存（仅保留差异百分比）；复跑时按 §9 重新采集完整分位。

## 5. 审计链写入段明细 <a id="write"></a>

### 5.1 稳态与排空 <a id="write-run"></a>

| 模式 | 行数 | 批大小 | 结果 |
| --- | --- | --- | --- |
| 稳态（逐条立即写） | 50000 | 1 | **62.7 条/秒** |
| 积压排空（先入队再逐条写） | 50000 | 1 | **87.6 条/秒**；端到端 **P95 = 546.0 秒** |
| 提交成本分离 | 5000 | 100 | **169.4 条/秒** |
| 提交成本分离 | 5000 | 1000 | **187.4 条/秒** |

- 分位：仅 P95 有留存（546.0 秒）；P50 / P99 与排空总耗时未逐项记录。
- 解读：批提交把每事务 fsync 成本摊薄后吞吐提升约 2~3 倍，但仍远低于 500 条/秒；**链计算 + 单道串行**是主要瓶颈，SQLite 每事务 fsync 是次要瓶颈。
- 测量边界：第 2 项**不含** msg 传输、可见性超时与消费组拉取段，属「消费侧处理段」；端到端消费延迟归 04 补口后在真栈复跑。

### 5.2 指标样本 <a id="write-metrics"></a>

- `bench_audit_chain.py` 跑完调用 `metrics.render()`，`bms_audit_write_total` 与 `bms_audit_consume_lag_seconds` 的样本实际渲染成功（实施记录 §5）。
- 具体样本值未留存；复跑时按 §9 打印并回填。

### 5.3 消费端到端（04 补口后回填） <a id="consume-e2e"></a>

> 本节在 04 任务真栈验收完成后回填：发布 → msg → 消费组 → 审计分片落库的端到端 P95（按组 / 日志类型），与本节 5.1 的「消费侧处理段」对比，差值即 msg 传输 + 拉取排队成本。

## 6. 分片提前量与跨月 <a id="shard"></a>

| 项 | 方法与结果 |
| --- | --- |
| 提前量 | `ensure_audit_shards(months_ahead=1)` 在注入时钟「当月 26 日」执行 → 次月台账与物理表存在，`bms_audit_shard_next_month_ready=1` |

## 9. 复跑步骤（命令级） <a id="rerun"></a>

### 9.1 环境准备 <a id="rerun-env"></a>

```bash
# 在 bms 仓根执行；解释器只认仓内 venv（Windows 示例）
backend/.venv/Scripts/python.exe -V        # 3.14.x
# 独立 SQLite 目录，不动开发库
set BMS_DATABASE__SQLITE_DIR=database/bms-perf-15-01
set BMS_LOG__LEVEL=WARNING
```

> Linux 用 `export` 与 `backend/.venv/bin/python`；`database/` 已忽略，不入库。

### 9.2 写入侧基准 <a id="rerun-write"></a>

```bash
# 稳态 + 积压排空（官方口径：一条一事务）
backend/.venv/Scripts/python.exe benchmarks/bench_audit_chain.py --rows 50000 --mode both --batch 1

# 提交成本分离（不作为官方值）
backend/.venv/Scripts/python.exe benchmarks/bench_audit_chain.py --rows 5000 --mode both --batch 100
backend/.venv/Scripts/python.exe benchmarks/bench_audit_chain.py --rows 5000 --mode both --batch 1000
```

记录：条/秒、P50 / P95 / P99、排空总耗时、`metrics.render()` 中的 `bms_audit_write_total` 与 `bms_audit_consume_lag_seconds` 样本值。

### 9.3 主链路应用层 A/B <a id="rerun-main"></a>

```bash
backend/.venv/Scripts/python.exe benchmarks/bench_main_link.py --rows 2000 --mode all
backend/.venv/Scripts/python.exe benchmarks/bench_main_link.py --rows 3000 --mode all
```

记录：`off` / `field` / `oplog` 三档 P50 / P95 / P99；至少四轮，取中位数，单轮离群单独标注。

### 9.4 规则与面板 <a id="rerun-rules"></a>

```bash
# 需 promtool >= 3.9（日期门控）；用临时容器或本机 promtool
promtool check rules deploy/observability/rules/bms-slo.yml
promtool test rules deploy/observability/rules/tests/bms-capacity.test.yml
```

### 9.5 消费端到端（04 补口后） <a id="rerun-consume"></a>

```bash
# 1) 起 msg 与 bms 栈（开发服务器，平台网络内）
# 2) 幂等建主题（审计三主题 4 分区，其余 1 分区）
backend/.venv/Scripts/python.exe -m ops.event_topics --ensure
backend/.venv/Scripts/python.exe -m ops.event_topics --check

# 3) 打开事件发布与消费（dev）：[event].provider=msg、[event_consumer].provider=msg、enabled=true
# 4) 单轮自检
backend/.venv/Scripts/python.exe -m ops.event_consumer --service platform --groups
backend/.venv/Scripts/python.exe -m ops.event_consumer --service platform --once

# 5) 持续消费（worker 宿主）
backend/.venv/Scripts/python.exe -m ops.event_consumer --service platform --worker

# 6) 制造事件：写一批审计事件（或 ops.outbox 重放），记录 occurred_at
# 7) 取端到端 P95（Prometheus）
#    histogram_quantile(0.95, sum by (le, log_type) (rate(bms_audit_consume_lag_seconds_bucket[5m])))
```

记录：三组消费日志、`sys_outbox.status`、审计分片行数与链校验结果、端到端 P95（按日志类型）、死信与积压指标。两进程验证另起一个同组 worker，记录两边 `join` 分配的分区与同租户处理顺序。

## 10. 结论 <a id="conclusion"></a>

- 指标、告警、面板与写入侧基准已具备可复现口径；分片提前量与跨月达标。
- 主链路 P99 中位差异 +5.0%（临界），HTTP 客户端口径未测，属限定达标。
- 审计链消费 P95 546 秒、写入吞吐 62.7~87.6 条/秒，属 SQLite + 无 broker 的限定环境结论，未达标；端到端消费延迟待 04 补口后复跑。
- 本报告不把限定环境结论当作生产结论；生产库与真栈复测归部署窗口与阶段验收。
