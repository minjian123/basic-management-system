## 1. 业务域说明 <a id="intro"></a>

本域只定**「故障」与「争用」的边界**：主库只读降级是故障开关，一旦置位，本进程后续所有写请求都会被拒（`10006` / 503）。现有实现把所有 `OperationalError` 一律当主库不可用，于是**锁等待 / 死锁**这种「并发争用」也会把整个进程打成只读——一条瞬时冲突就能让后续几十个无关请求排队失败。

本域先解决这一条（`13-1`），后续限流、熔断、重试、幂等等韧性议题沿用本域归口。

- **依据**：《架构设计 · 数据访问》降级与只读态口径；《[后端开发规范](../../../规范/后端开发规范.md)》异常分层；《[测试规范](../../../规范/测试规范.md)》异常路径覆盖。
- **前置**：`03-3`（异步作业中心，批量写路径是首个真实争用来源）、`05-1`（日志落库）。

## 2. 需求 13-1：锁冲突不得触发只读降级 <a id="r13-1"></a>

优先级：2（高）

**背景与动机**：只读降级是「主库真的坏了」时的止损手段，代价是全进程写不可用。而「行锁等待超时」「死锁回滚」「SQLite 写锁冲突」都是**并发争用**，重试即可恢复，与主库存活无关。把两者混为一谈的后果是把一次 50 毫秒的锁冲突放大成整段只读窗口；在生产 MySQL 的高峰期，`Lock wait timeout` 与 `Deadlock found` 都会命中这条错判路径。

**内容**：

1. **判定分离**：锁等待（`Lock wait timeout exceeded` / SQLite `database is locked`）、死锁（`Deadlock found` / PG `deadlock detected`）、锁不可得（PG `could not obtain lock`）**不属于**主库故障，**不得**置降级标记、不得阻断后续写请求。
2. **响应语义不变**：仍返回 HTTP `503` + 业务码 `10006`，body 结构（`code` / `message` / `data`）不变，**不新增**字段；另附 `Retry-After: 1`（秒）作为标准可重试标记。
3. **文案精确**：锁冲突分支文案为「数据库繁忙，请稍后重试」，**不得**出现「已降级为只读模式」这类与实际状态不符的描述。
4. **真故障口径不变**：连接失败、驱动错误、库不可达等仍按原逻辑置降级并返回 `10006`，行为不回退。
5. **可观测**：锁冲突记日志事件 `database_contention`（含路径、方法、异常类型）并计指标 `bms_db_lock_contention_total`，与真故障的 `database_unavailable` 分开，便于告警区分。
6. **覆盖方言**：SQLite / MySQL / PostgreSQL 三类标记纳入识别；达梦（DM8）暂无对应抛错形态，登记为待补，不阻塞本条。

**完成标准**：

- 锁冲突用例：`503` + `code=10006` + `Retry-After` 头存在；降级标记仍为 `false`；**同一进程后续写请求正常**（不被拒）。
- 真故障用例：降级标记为 `true`、响应无 `Retry-After`，与改动前一致。
- 各方言标记（SQLite / MySQL 1205 / MySQL 1213 / PG 死锁 / PG 锁不可得）识别为真，普通连接类错误识别为假（含 SQLAlchemy `orig` 包装）。
- 指标与日志事件可查到，且事件名与真故障事件不混。
