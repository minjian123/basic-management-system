## 1. 业务域说明 <a id="intro"></a>

本业务域管**数据的下半场**：热表放不下时怎么冷化（归档）、误删的数据怎么找回（回收站）。两条能力共用一套调度（`03-2`）与一条纪律：**审计类数据先校验哈希链完整，再允许归档**。

- **依据**：《[概要设计 · 归档管理](../../../设计/概要设计/30_概要设计_归档管理.md)》《[概要设计 · 回收站](../../../设计/概要设计/32_概要设计_回收站.md)》《[架构设计 · 数据架构](../../../设计/架构设计/07_架构设计_数据架构.md)》。
- **前置**：需求 `03-2`（任务调度）、`05-1` / `05-2`（审计链）、阶段二对象存储契约、四库（平台 / 租户 / 归档）。

## 2. 需求 07-1：归档管理 <a id="r07-1"></a>

优先级：2（高）

**背景与动机**：操作日志、登录日志、审计日志按月分表后仍会无限增长，租户库的流水表同理；没有归档策略，两三年后单库体积会让备份与查询都不可用。归档还必须可查（合规要能翻旧账），不能归档即失联。

**内容**（《概要设计 · 归档管理》§2.1 / §2.2）：

1. **归档策略配置**：全表可配——时间字段 / 阈值天数 / 保留期 / 目标 / 批次大小 / 启停（业务码 `archive`）。
2. **两段式归档**：热表超阈值 → 迁入归档库（可在线只读查询）；超过保留期 → 冷化到 MinIO；由 Celery 调度执行。
3. **执行记录**：批次、数量、目标、状态、耗时逐次记录（含物理清理记录）。
4. **归档数据查询**：归档库只读查询（带 `tenant_id` 与原库表标识），审计类数据查询沿用 `log` 业务码。
5. **物理清理与合规销毁**：过期归档文件与软删除残留由 Celery 物理清理，销毁记录日志备查。
6. **审计链前置校验**：审计类数据归档前必须通过链完整性校验，链不完整则中止并告警（不允许把断链数据归档成「看起来完整」的冷数据）。

**完成标准**：配置策略后到期数据自动迁入归档库并从热表消失；归档库只读可查且带租户标识；超过保留期的归档数据冷化到对象存储并可取回；审计类数据链不完整时归档任务中止并告警；每次执行有记录（数量 / 状态 / 耗时）；重复执行同批次不产生重复归档。

**参考文档**：《概要设计 · 归档管理》§2「功能分解与业务流程」、§5「接口设计」；《架构设计 · 数据架构》「归档库与冷化」节。

## 3. 需求 07-2：回收站 <a id="r07-2"></a>

优先级：3（中）

**背景与动机**：软删除避免了误删即丢，但如果没有回收站，恢复只能靠运维改库；而「唯一字段删了之后无法再建同名记录」是软删除最常见的坑（`deleted_at` 参与唯一索引才能解决）。

**内容**（《概要设计 · 回收站》§2.1 / §2.2）：

1. **软删除数据查看**：查询各业务表 `deleted_at` 非空数据，按模块 / 表筛选（业务码 `recycle`）。
2. **恢复**：清空 `deleted_at` 恢复数据，恢复动作落操作日志与字段级审计。
3. **过期物理清理**：Celery 定时物理清理超期软删除残留，与归档清理任务衔接（同一调度，避免两套清理逻辑打架）。
4. **唯一约束保障**：`(唯一字段, deleted_at)` 复合唯一索引——删除释放唯一键、恢复回填；由数据规范层统一要求，不由各表自由发挥。

**完成标准**：删除的数据出现在回收站且可按表筛选；恢复后数据回到业务列表且唯一键冲突按预期处理（同名记录存在时恢复被拒并提示）；恢复动作可在操作日志与字段级审计中查到时序；超过保留期的软删除数据被物理清理且记录在案；复合唯一索引在所有带唯一字段的业务表上生效（规范校验可查）。

**参考文档**：《概要设计 · 回收站》§2「功能分解与业务流程」、§4「数据模型与表设计」；《[数据库设计 · 数据规范](../../../设计/数据库设计/02_数据库设计_数据规范.md)》「软删除与唯一约束」节。
