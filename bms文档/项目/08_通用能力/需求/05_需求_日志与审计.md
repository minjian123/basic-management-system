## 1. 业务域说明 <a id="intro"></a>

本业务域承担**可追溯性**：操作日志回答「谁在什么时候对什么做了什么」，登录日志回答「谁从哪来、失败几次」，字段级变更审计回答「这个字段从什么值变成了什么值，且没被改过」。三者一律**异步落库 + 哈希链串联**，热表保留 90 天，超期先校验链完整再归档。

- **依据**：《[概要设计 · 操作日志](../../../设计/概要设计/11_概要设计_操作日志.md)》《[概要设计 · 登录日志](../../../设计/概要设计/12_概要设计_登录日志.md)》《[概要设计 · 审计合规](../../../设计/概要设计/28_概要设计_审计合规.md)》《[架构设计 · 审计哈希链](../../../设计/架构设计/19_架构设计_子系统_审计哈希链.md)》。
- **前置**：需求 `03-1`（事件总线，审计链组分区有序）、阶段二审计捕获器契约、需求 `07-1`（归档）。

## 2. 需求 05-1：操作日志与登录日志 <a id="r05-1"></a>

优先级：2（高）

**背景与动机**：安全事件排查时最常问的三个问题是「谁改的」「从哪个 IP 来的」「失败了几次」——没有操作与登录日志，这三个问题只能靠猜。日志还必须能证明没被篡改，否则审计价值为零。

**内容**（《概要设计 · 操作日志》§2.1 / §2.2、《概要设计 · 登录日志》§2.1 / §2.2）：

1. **操作日志捕获**：请求中间件收集上下文（`user_id` / 模块 / 动作 / 方法 / 路径 / 参数 / `ip` / `user_agent` / 耗时 / 状态 / 错误信息）；敏感字段（密码 / token / 密钥）**脱敏后记录**，不落原始值。
2. **登录日志捕获**：认证域在登录成功 / 失败时记录（`username` / `ip` / `user_agent` / 状态 / 失败原因）；失败信息作为账号锁定（`fail_limit` 类型）的判定依据。
3. **异步链式落库**：两类日志经 RocketMQ 审计链组**分区有序**消费（分区键 = 租户），逐条哈希串联后写入按月分片表（`sys_operation_log_yyyyMM` 等）。
4. **查询**：操作日志按用户 / 模块 / 动作 / 状态 / 时间范围；登录日志按用户名 / 状态 / 时间范围；均支持分页与详情（权限码 `log:query`）。
5. **链完整性校验**：校验工具逐条重算比对，定期巡检（内置任务）+ 归档前强制校验；校验失败进系统监控告警。
6. **归档衔接**：热表保留 90 天，超期按归档策略两段式归档（见 `07-1`）。

**完成标准**：一次写操作产生一条操作日志且参数中密码类字段为脱敏值；登录失败在日志中可查且失败次数累计与账号锁定判定一致；并发写入下同租户日志链顺序正确、链校验通过；篡改任一条记录后校验工具能定位到该条；查询按时间范围与模块筛选结果准确；90 天前的数据在归档任务后从热表消失且归档库可查。

**参考文档**：《概要设计 · 操作日志》§2、§5；《概要设计 · 登录日志》§2、§5；《架构设计 · 审计哈希链》「链构造与校验」节。

## 3. 需求 05-2：字段级变更审计与哈希链 <a id="r05-2"></a>

优先级：1（紧急）

**背景与动机**：操作日志只记「调了哪个接口」，回答不了「这条记录的金额从 1000 改成了 800」。合规与纠纷场景要求字段级旧值 / 新值可查、且能证明未被事后修改——这是审计链在业务侧最硬的落点。

**内容**（《概要设计 · 审计合规》§2.1 / §2.2）：

1. **字段级捕获**：关键表通过 ORM 事件自动记录字段旧值 / 新值，落 `sys_data_audit_log`（按月分表）；捕获由契约 `AuditCapturer` 实现，业务代码不手写审计。
2. **哈希链构造**：`record_hash = SHA256(prev_hash + 规范化记录内容)`，经 RocketMQ 审计链组分区有序消费保证链序；记录含 `domain_key`（业务域归属，07C `04_03` 口径）。
3. **链校验与巡检**：校验工具逐条重算比对，内置任务定期巡检，结果接入系统监控告警。
4. **三权分立**：系统管理员 / 安全管理员 / 审计管理员三类角色互斥、同一用户不得兼任；审计管理员只读全部日志与审计数据。
5. **合规留存与销毁**：90 天热表 + 归档冷存储，哈希链随归档导出；合规销毁留销毁日志备查。
6. **查询**：数据变更审计列表（含按月分片检索与归档库只读查询）。

**完成标准**：任一关键表的一条记录被更新后，审计表出现含旧值 / 新值 / 操作人 / `domain_key` 的记录；未经 ORM 的直连 SQL 修改不产生审计（口径在文档中显式声明，不假装覆盖）；链校验对人为篡改能精确定位到记录；三类管理员角色不可由同一用户同时持有（授权被拒）；归档后审计数据仍可按链校验通过。

**参考文档**：《概要设计 · 审计合规》§2「功能分解与业务流程」、§6「权限与配置」；《架构设计 · 审计哈希链》；07C `04_03` 设计「审计记录须带业务域」。
