## 1. 域说明 <a id="intro"></a>

本域对应阶段三「能力域改造」：把平台既有 40 个能力域契约定型为可替换插件——基类改继承 `BasePluggable`（继承轨）、提供者改经 `resolve_plugin` 解析（消费面收口）、目录结构按「契约 / 缺省实现 / 内建实现」对齐（`base.py` / `null.py` / `<impl>.py`）。域一提供机制，本域完成**改造面**；两者共同构成 M3 门禁主体。

**依据**：《架构设计 · 扩展点与插件化》「阶段三交付与验收（M3 口径）」节交付物 #2/#3/#4、《架构设计 · 后端基础类体系》「基类候选」节、《后端基类清单》「能力域基类清单」与「改造面」标注、《后端开发规范》「后端基座体系（强制）」节。**目标**：40 基类继承链就位；35 个提供者经 `resolve_plugin`（配置驱动装配）；`null.py` 迁移后导入路径与测试全绿；全量 `pytest` / `ruff` / `pyright` 通过。

## 2. 需求 02-1：能力域基类改继承 BasePluggable（40 个） <a id="r02-1"></a>

优先级：2（高）　|　状态：已完成　|　完成日期：2026-09-15

**背景与动机**：阶段一交付的 40 个能力域基类（`BaseConfigCenter`、`BaseStorage`、`BaseNotification`、`BaseSms` 等）目前继承 `BaseCapability, ABC`——只有能力 `key` 标识，无插件键 / 实现名 / 契约版本 / 生命周期，无法被插件注册表识别；M3 要求「继承与组合双轨注册可用」，继承轨的前提就是能力域基类挂在 `BasePluggable` 之下。

**内容**（《架构设计 · 扩展点与插件化》「基类承载与双轨」节）：

1. 40 个 `BaseXxx(BaseCapability, ABC)` 改为继承 `BasePluggable`（**业务方法签名不变**，仅替换继承与补字段）。
2. 各基类补类属性：`plugin_key`（与能力 `key` 一致）、`plugin_name`（平台内建默认实现名，如 `core` / `snowflake` / `null` 之外的平台实现）、`contract_version`（自 `0.1.0` 起）。
3. 继承链核对：`BasePluggable → BaseCapability → BaseObject`（L0）；抽象端口不因「可实例化判定」误登记（与 01-1 §3 配套）。
4. 登记回写：架构 04「基类候选」、基类清单、后端开发规范与相关设计文档同步。

**完成标准**：40 个基类继承链一致且业务方法未变；抽象端口不误登记、`Null` 缺省实现登记为 `null`；应用可正常启动；全量 `pytest` / `ruff` / `pyright` 全绿；架构 04 与基类清单登记同步（无遗漏、无多余）。

**参考文档**：《架构设计 · 扩展点与插件化》「基类承载与双轨」节；《架构设计 · 后端基础类体系》「基类候选」节；《后端基类清单》「能力域基类清单」节

## 3. 需求 02-2：提供者改经 resolve_plugin（35 个） <a id="r02-2"></a>

优先级：2（高）　|　状态：已完成　|　完成日期：2026-09-15

**背景与动机**：M3 要求「**配置切换 provider 生效且业务代码零改动**」。现状各模块暴露 `get_xxx(request)` 提供者函数（35 个）直连具体实现（或 Null），「换实现」要改代码；阶段三把提供者收口为薄封装——业务只依赖 `get_xxx`，实现由配置经 `resolve_plugin` 解析。

**内容**（《架构设计 · 扩展点与插件化》「配置驱动装配」节）：

1. 35 个 `get_xxx(request)` 改为薄封装：`return resolve_plugin(plugin_key, settings.<domain>.provider)`；请求期只取缓存实例（**不得**在请求内实例化 / 导入实现）。
2. `settings` 各能力分区补齐（与 01-2 配置驱动装配配套）；未配置能力维持解析到 `null`。
3. 调用面保持稳定：业务模块与既有测试不改调用签名；仅提供者内部解析路径变化。
4. 解析路径唯一性核查：不再存在绕过注册表直连具体实现的路径（含既有 `config` 开关分支）。

**完成标准**：切换 provider 后消费方零改动（测试或示例可证）；35 个提供者全部经 `resolve_plugin`；无绕过注册表的直连实现；全量 `pytest` / `ruff` / `pyright` 全绿。

**参考文档**：《架构设计 · 扩展点与插件化》「配置驱动装配」节；《后端基类清单》「改造面」列；《后端开发规范》「后端基座体系（强制）」节

## 4. 需求 02-3：代码结构对齐（null.py 拆分迁移） <a id="r02-3"></a>

优先级：2（高）　|　状态：已完成　|　完成日期：2026-09-15

**背景与动机**：现状 38 个 `NullXxx`（缺省实现）与端口契约同落在各域 `base.py`，文件职责混杂；《架构设计 · 扩展点与插件化》「代码结构（目标）」节定口径为「`base.py`（契约）/ `null.py`（默认实现）/ `<domain>/<impl>.py`（平台内建实现）」，并把本次迁移列为**阶段三前置**（该节「结构迁移」注记、《阶段三需求提出清单》第 7 行 P0 配套）。

**内容**（《架构设计 · 扩展点与插件化》「代码结构（目标）」节）：

1. 38 个 `NullXxx` 由 `backend/app/<domain>/base.py` 迁至同域 `null.py`；`base.py` 只保留端口契约 / 数据契约 / 常量。
2. 平台内建实现落点 `<domain>/<impl>.py`（如 `storage/local.py`、`storage/minio.py`，随 04-1 落地）；`app/plugins/` 集中区暂不启用（需要时再迁）。
3. 导入路径全量调整：模块内引用、跨模块引用、测试与脚本引用同步；`__init__` 导出（如有）按新结构组织。
4. 登记回写：架构 10「代码结构」节、基类清单「代码位置」列同步。

**完成标准**：38 个 `NullXxx` 迁移完成且 `base.py` 不再含实现类；导入路径与测试引用全部更新、无残留旧路径；全量 `pytest` / `ruff` / `pyright` 与基座自检（`check-base`）通过；文档登记同步。

**参考文档**：《架构设计 · 扩展点与插件化》「代码结构（目标）」节；《阶段三需求提出清单》第 7 行；《文档生成规范》「图形与示意图」节（目录树形态）
