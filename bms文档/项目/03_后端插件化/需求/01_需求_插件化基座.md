## 1. 域说明 <a id="intro"></a>

本域对应阶段三「插件化基座」：落地 `app/core/plugin.py`（`BasePluggable` + 插件注册表 + `resolve_plugin`，**机制唯一落点**），打通「配置选实现 → 启动装配校验 → 运行期解析」链路，并提供平台超管只读插件清单接口；与 02 域（能力域改造）配合完成 M3 门禁。

**依据**：《架构设计 · 扩展点与插件化》「基类承载与双轨」「注册表与三阶段发现」「配置驱动装配」「阶段三交付与验收（M3 口径）」节；《架构设计 · 后端基础类体系》「基类候选」节；《后端基类清单》；《后端开发规范》「后端基座体系（强制）」节。**目标**：`BasePluggable` 与插件注册表可用；配置切换 provider 生效且业务代码零改动；非法 provider / 重名 / 契约版本不符启动被拒（含 CI 离线校验）；插件清单只读可查且不含密钥。

## 2. 需求 01-1：插件化中间层 BasePluggable 与插件注册表 <a id="r01-1"></a>

优先级：2（高）　|　状态：已完成　|　完成日期：2026-09-15

**背景与动机**：纵向能力替换缺「实现可替换」的装配语义——能力域基类目前只继承 `BaseCapability`（仅 `key` 标识），没有插件键 / 实现名 / 契约版本 / 生命周期与注册解析机制；`core/plugin.py` 在架构与《后端基类清单》中登记为**待交付**，且《后端开发规范》明确「未交付前不得自行实现临时替换框架、基座未就位不得开工」。它是阶段三所有能力域改造（02 域）的前置。

**内容**（《架构设计 · 扩展点与插件化》「基类承载与双轨」与「注册表与三阶段发现」节）：

1. `BasePluggable(BaseCapability)`：字段 `plugin_key` / `plugin_name` / `contract_version`，生命周期 `setup()` / `aclose()`（默认空实现，`aclose` 经 `ResourceManager` 统一回收），`describe()` 元信息（供插件清单与排障）。
2. 插件注册表：进程内两级映射 `plugin_key → {plugin_name → 实现}`，启动期构建、运行期只读；`(plugin_key, plugin_name)` 冲突即拒（不静默覆盖）。
3. 双轨注册：继承自动登记（`__init_subclass__` 仅对**可实例化子类**生效，抽象端口 / 中间层不登记）与显式 `register_plugin(plugin_key, plugin_name, impl)`（面向组合路径：虚拟子类 / `Protocol` 结构化）汇入同一注册表。
4. 缺省实现：`NullXxx` 自动登记为 `plugin_name = "null"`；`config.toml` 未配置 provider 时解析到 `null`（占位可跑）。
5. `resolve_plugin(plugin_key, provider)`：按配置解析实现；**同 provider 复用唯一实例**（解析结果缓存，请求期只取引用）；未注册实现抛错（启动期即失败）。
6. 契约版本：装配时按 `contract_version` 主版本兼容校验，不匹配拒启并告警。

**完成标准**：`BasePluggable` 就位（字段 / 生命周期 / `describe` 齐备）；继承自动登记（仅可实例化子类）与显式注册双轨均可用且汇入同一注册表；重名注册启动期即拒；未配 provider 时解析到 `null`；`resolve_plugin` 同 provider 返回同一实例、未注册抛错；`pytest` / `ruff` / `pyright` 全绿；注册表语义纳入契约测试（与 03-1 一致）。

**参考文档**：《架构设计 · 扩展点与插件化》「基类承载与双轨」节；《后端基类清单》「中间层基类」节；《后端开发规范》「后端基座体系（强制）」节

## 3. 需求 01-2：配置驱动装配与启动 / CI 校验 <a id="r01-2"></a>

优先级：2（高）　|　状态：已完成　|　完成日期：2026-09-15

**背景与动机**：M3 要求「**配置切换 provider 生效且业务代码零改动**」「非法 provider / 重名 / 契约版本不符**启动被拒**」；若缺校验，错误配置会到请求期才暴露，且实现依赖（如 MinIO 客户端）可能在缺依赖时才炸。需要把「选实现」下沉到配置，并把校验前移到启动与 CI。

**内容**（《架构设计 · 扩展点与插件化》「配置驱动装配」节）：

1. `config.toml` 各能力分区补 `provider` / `options` 字段（仅被替换域，按需添加）。
2. 启动装配（应用 lifespan）：读取各能力 provider → 校验**存在性 / 契约版本 / 依赖可用性** → 实例化并缓存 → 调 `setup()`；失败以统一错误类型拒启（非零退出，不静默回退 `null`）。
3. 实现延迟导入：注册表登记实现类（或工厂），实例化时才导入具体模块——未选中的实现不被导入（不为它背依赖）。
4. CI 离线校验（与 `check_modules` 同构）：运行现有注册表，校验各能力 provider 引用合法性 / 重名 / 契约版本；挂冒烟层。
5. 启动日志：打印各能力当前 provider（不含 options 密钥），供排障核对。

**完成标准**：切换某能力 provider 后消费方代码零改动且行为随实现生效；非法 provider / 重名 / 契约版本不符启动被拒（退出码非 0、错误信息可读）；CI 离线校验能拦截非法配置且随冒烟层执行；未选中实现不被导入（依赖隔离可证）；启动日志可核对各能力 provider；`pytest` / `ruff` / `pyright` 全绿。

**参考文档**：《架构设计 · 扩展点与插件化》「配置驱动装配」节；《后端基础能力需求》03-1（配置管理，`config.toml` 分区先例）；《测试规范》「流水线分层与自动触发」节

## 4. 需求 01-3：插件清单接口 <a id="r01-3"></a>

优先级：2（高）　|　状态：未开始　|　完成日期：—

**背景与动机**：《项目规划说明》要求「插件清单」（平台超管可见每个能力域当前 provider）；《架构设计 · 扩展点与插件化》「阶段三交付与验收（M3 口径）」节列为交付物 #6——运维与平台管理需要只读入口核对「当前平台各能力实际用的是哪个实现」，且**不得暴露密钥**。

**内容**（《架构设计 · 扩展点与插件化》「插件清单接口」节）：

1. `GET /api/v1/plugins`：按能力分组返回各 `plugin_key` 的注册实现与当前 provider（`plugin_key` / `plugin_name` / `contract_version` / 当前 provider / 状态）。
2. `GET /api/v1/plugins/{plugin_key}`：单能力明细（注册实现列表 + 当前选中 + 版本）。
3. 只读接口，不提供启停 / 切换操作；**返回不含 options 密钥**。
4. 未登记能力返回 404（统一错误码口径）；鉴权按 `platform:manage` 口径随认证 / RBAC 阶段接入，当前与既有平台接口一致（暂不鉴权，口径见架构 10 §4）。

**完成标准**：双接口可查且字段与架构一致；不含任何密钥 / 敏感 options；未登记能力 404 与统一响应体一致；自动化用例覆盖（随测试阶段入 Kiwi）；`pytest` / `ruff` / `pyright` 全绿。
