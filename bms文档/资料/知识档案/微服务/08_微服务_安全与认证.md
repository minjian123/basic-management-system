## 1. 技术概述 <a id="overview"></a>

单体只有**一个安全边界**：守住入口即可。拆成微服务后：

- 网络里出现大量东西向（服务间）流量，每个服务都是潜在入口；
- 「内网 = 可信」的假设失效——任何被攻破的服务都可能横向移动；
- 多租户上下文要在更多进程间传递，泄漏面更大。

因此微服务安全的原则是**零信任**（NIST SP 800-207 / SP 800-204A）：**不因网络位置而信任，
每次请求都要认证与授权**。本页把安全拆成四层：入口、服务间身份、授权、多租户。

## 2. 入口层：API 网关 <a id="gateway"></a>

| 职责 | 说明 |
| --- | --- |
| 认证 | 校验 OAuth2 / JWT（签名、过期、issuer、**audience**），拒绝未认证请求 |
| 限流 | 按用户 / 客户端 / 租户限流（令牌桶），防刷与 DoS |
| 路由与协议转换 | 外 → 内协议归一，隐藏内部拓扑 |
| 请求净化 | **剥掉**客户端伪造的身份头（`X-User-Id`、`X-Service-Identity` 等），注入网关验证过的身份 |
| 灰度与 WAF | 版本路由、SQL 注入 / XSS 基础防护（按需） |

**网关旁路风险**：网关鉴权后，内部服务若直接可达（同网段、调试端口），攻击者可绕过网关。
对策：内部服务只接受带服务身份的流量（mTLS / 服务令牌），或仅网格内可达。

## 3. 服务间认证：证明「我是谁」 <a id="service-auth"></a>

| 手段 | 层级 | 说明 | 取舍 |
| --- | --- | --- | --- |
| **mTLS** | 传输层 | 双方各持证书，互相验证；证书由内部 CA / 网格签发 | 身份强、可防冒充；证书轮换与信任引导有成本（网格可免代码实现） |
| 服务令牌（Client Credentials） | 应用层 | 服务用自身 ID + secret 换 token，携带 scope 调用下游 | 简单；secret 分发与轮换要治理 |
| 工作负载身份（SPIFFE/SPIRE） | 平台层 | 平台签发短期身份（SVID），免静态 secret | 平台能力要求高；适合 K8s 等多服务环境 |

**JWT 的正确用法**（若用 token 承载身份 / 权限）：

- 签名用 **RS256 / ES256**（非对称，公钥经 JWKS 分发）；不要用 HS256 共享密钥到处分发；
- 必须校验 `exp`、`iss`、**`aud`**（防止「A 服务签发的 token 被 B 服务接受」的混淆代理问题）；
- **不要把外部 access token 直接透传给内部服务**（泄漏面扩大）；网关应换成内部身份凭证；
- 短时效 + 刷新轮换；撤销场景配黑名单。

## 4. 授权：粗粒度在网关，细粒度在服务 <a id="authorization"></a>

OWASP 微服务安全清单的建议：

1. **网关做粗粒度**（是否登录、基础 scope），**服务做细粒度**（业务权限、对象级权限、租户边界）——两层防御；
2. 策略不硬编码：用策略引擎（OPA 等）或统一权限组件表达（本项目用 `BasePermissionChecker` + `require_permission` 依赖工厂）；
3. 服务间调用同样要鉴权：**内部调用不默认可信**，按 scope / 权限码校验；
4. 日志与审计：拒绝路径、权限变更、敏感操作全部留痕（本项目有审计链与操作日志）。

## 5. 多租户安全 <a id="tenant"></a>

| 原则 | 说明 |
| --- | --- |
| 租户身份来自**已验证凭证** | 从签名 token / 会话推导 `tenant_id`，绝不信任请求参数或头 |
| 全链路传播 | 请求 → 服务 → 异步任务 → 消息消费 → 缓存 key，任一处丢失即泄漏风险 |
| 双重防御 | 应用层过滤 + 数据库层 RLS / 独立库隔离兜底 |
| 缓存与队列 | 缓存 key 带租户前缀；任务载荷显式携带租户，worker 拒绝无租户任务 |
| 审计 | 跨租户访问尝试必须告警（这是安全事件，不是普通错误） |

> 与《[06 数据架构与多租户](06_微服务_数据架构与多租户.md)》§4 同源：**隔离模型决定风险面，工程纪律决定是否踩坑**。

## 6. 密钥与证书管理 <a id="secrets"></a>

- Secret 不入库、不入镜像、不进 git；统一走 Secret 管理（本项目：`deploy/.env` 本地 + CI/CD masked 变量 + 运行时注入）；
- 证书自动化：cert-manager（K8s）或网格内置轮换；CA 切换要有重叠窗口；
- 最小权限：每个服务只拿到它需要的凭据与 scope；
- 轮换演练：密钥/证书轮换要有流程与验证（本项目备份恢复与凭据文档已有对应条目）。

## 7. 在本项目中的用途 <a id="usage"></a>

| 安全能力 | 本项目现状 | 拆分后的变化 |
| --- | --- | --- |
| 认证 | 双 token（access/refresh）、图形验证码、密码策略、会话标记（阶段六） | 认证中心不变；但**每服务都要能验签**（JWKS/公钥分发） |
| 授权 | RBAC 主体链 + `data:plain` 权限 + 字段权限 + 数据范围（阶段七） | 权限判定要么每服务接同一权限源，要么网关统一携带判定结果 |
| 多租户 | token 内 tenant_id + 租户解析链 + 独立库隔离 | 横切逻辑需在每个服务复制，泄漏面扩大 |
| 开放接口 | OAuth2 Server + scope + 签名 + 防重放 + IP 白名单 + 按 client 限流（阶段十） | 网关/服务间需再叠服务身份（mTLS / 服务令牌） |
| 密钥 | Secret 不入库不入镜像；CI 变量 masked | 证书/服务凭据管理成为新增运维面 |
| 审计 | 操作日志 + 审计哈希链 | 分区有序消费跨服务后需重新设计顺序保证 |

**结论**：本项目安全体系是**集中式**的（认证中心 + 统一权限 + 统一租户路由），
这正是单体在安全上的优势；微服务化会把「安全横切」复制到每个服务，并新增 mTLS / 服务身份 / 证书治理的运维面——
评估时应作为明确成本项（见《[10 项目评估](10_微服务_项目评估.md)》）。
