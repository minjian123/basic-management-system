## 1. 技术概述 <a id="overview"></a>

微服务的收益（独立部署、独立伸缩、故障隔离）**全部由运维基础设施兑现**；
基础设施不到位，微服务就只剩复杂度。Fowler 的「Microservice Prerequisites」给出最低门槛：

| 前提 | 含义 | 本项目现状 |
| --- | --- | --- |
| 快速供给（Rapid Provisioning） | 新环境/新实例小时级可用，且趋于自动化 | 单机 Compose 可快速起；按需扩容未自动化 |
| 基础监控（Basic Monitoring） | 错误、可用性、业务指标可见，能快速回滚 | 阶段十三引入 Prometheus/Loki/Grafana；阶段一已有 `/healthz` `/readyz` 与结构化日志 |
| 快速部署（Rapid Deployment） | 构建到生产小时级、可重复、可回滚 | GitLab CI 冒烟层已激活；重验证层分档开启中 |

> 一句话：**微服务把「上线」从一次动作变成一种能力**；没有这条能力，拆分只会让发版更痛苦。

## 2. 容器与编排：K8s 不是默认答案 <a id="orchestration"></a>

| 方案 | 运维负担 | 适合场景 |
| --- | --- | --- |
| 单机 Docker Compose | 低 | 单体 + 少量 worker、内网系统（本项目 MVP 形态） |
| 托管容器（ECS / Cloud Run 等） | 中低 | 少量服务、无集群团队 |
| Nomad / Swarm | 中 | 需要编排但不想背 K8s 复杂度 |
| **Kubernetes** | 高（自建更高） | 10+ 服务、多团队、需调度/自动扩缩容、有平台团队 |

行业估算（小团队 3~10 个服务的真实口径）：K8s 的**总持有成本**（控制面 + 节点 + 网关 + NAT + 监控 + 分摊的运维人力 + 学习成本）
可达 **每月上万美元量级**，而多数小团队的问题「单机 + 托管数据库」就能解；
决策阈值经验值：**服务数 > 10、团队 > 5~10 且有专职运维/平台角色** 才值得上 K8s。

> 结论：本项目当前「Compose 一键部署」是合理形态；K8s 化已在《总体项目规划》演进路线中按需触发。

## 3. 流量入口与治理 <a id="traffic"></a>

| 组件 | 解决什么 | 是否必需 |
| --- | --- | --- |
| API 网关 | 统一入口：鉴权、限流、路由、协议转换、灰度 | 有外部流量与多服务时**推荐**（单体也可有薄网关/反向代理） |
| 服务发现 | 调用方找到实例（K8s Service / DNS / 注册中心） | 动态调度场景必需；固定地址场景可省 |
| 配置中心 | 多环境/多服务配置集中管理 + 动态刷新 | 服务多了才需要；本项目用 `config.toml` + 环境变量已够 |
| 服务网格（Istio/Linkerd） | mTLS、流量治理、遥测下沉到 sidecar/节点，无需改应用代码 | **服务少时属过度工程**；≥ 10 服务且需要统一 mTLS/灰度时评估 |

服务网格的收益（零代码 mTLS、可视化、流量拆分）真实，代价也真实：
sidecar 资源与延迟、控制面运维、排障链路变长。行业共识是**先有网关，再按需上网格**。

## 4. 可观测性：三支柱 + SLO <a id="observability"></a>

| 支柱 | 内容 | 工具（本项目已规划） |
| --- | --- | --- |
| 日志 | 结构化、带 trace_id / 租户 / 请求上下文 | structlog + Loki（阶段十三） |
| 指标 | 请求量、错误率、延迟分位、资源、队列积压 | Prometheus + Grafana（阶段十三；`/metrics` 待接） |
| 追踪 | 跨服务调用链（span 父子关系） | OpenTelemetry + Jaeger（阶段十三） |
| 告警 | 基于 SLO 的 Burn Rate 告警 | Alertmanager（阶段十三） |

微服务场景的额外要求：

- **必须**有分布式追踪——否则一次跨服务问题是「黑盒」；
- **必须**有消费者延迟 / Outbox 积压 / 端到端新鲜度指标（见《[05 通信与分布式一致性](05_微服务_通信与分布式一致性.md)》§5）；
- 指标标签基数会随「服务 × 租户 × 实例」爆炸，需要治理（只保留必要维度）。

## 5. CI/CD：服务数量 = 流水线数量 <a id="cicd"></a>

| 单体 | 微服务 |
| --- | --- |
| 一条主流水线，全量构建测试 | 每服务独立流水线（构建/测试/镜像/发布/回滚） |
| 一次发布原子生效 | 需处理**契约兼容**与**发布顺序** |
| 回滚一次即可 | 回滚可能需要多服务协调 |
| 端到端测试一套 | 端到端测试需编排服务与环境，成本上升 |

配套能力：契约测试（消费者驱动）、数据库迁移与回滚策略、灰度/金丝雀、渐进交付。

> DORA 2024 的提醒：平台工程整体有益，但**引入平台本身也可能短期降低吞吐与变更稳定性**——
> 基础设施升级要小步验证，不要一次性引入。

## 6. 成本核算（把账算清再决定） <a id="cost"></a>

| 成本项 | 单体现状 | 微服务后 |
| --- | --- | --- |
| 计算资源 | 1 台应用 + 1 套依赖服务 | 服务数 ×（实例 + 健康检查 + 网关/网格开销） |
| 基础设施组件 | 已 8+（库 ×3 / Redis / MQ / ES / MinIO / CI 等） | 再叠加编排、服务发现、配置、追踪、网关/网格 |
| 人力 | 发布/排障一次动作 | 每服务维护、升级、告警、证书轮换；需专职或半专职平台角色 |
| 学习成本 | 低 | K8s/网格/追踪的团队上手成本（周级） |
| **隐性成本** | — | 产品迭代时间被基础设施占用（小团队最贵的资源） |

## 7. 在本项目中的用途 <a id="usage"></a>

- **现状合理**：Docker Compose 一键部署（M19 验收项）+ GitLab CI（冒烟层已全绿、重验证层分档开启）符合「少量部署单元」阶段的最佳实践；
- **建设方向与微服务前提同向**：阶段十三的监控/追踪/备份/分片建设，同时是「未来若要拆」的三项前提；
- **触发条件**：只有当服务数、团队规模或隔离需求触发（见《[10 项目评估](10_微服务_项目评估.md)》§重评触发条件），才评估容器编排与网关/网格；
- **不建议**：在没有运维专职与多服务需求时提前引入 K8s / 服务网格——「为未来买单」的成本会直接吃掉产品迭代时间。
