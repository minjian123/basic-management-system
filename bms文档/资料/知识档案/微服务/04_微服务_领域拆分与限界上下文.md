## 1. 技术概述 <a id="overview"></a>

微服务拆分的第一原则是：**按业务领域拆，不按技术分层拆**。判据来自领域驱动设计（DDD）的**限界上下文**（Bounded Context）——
「同一个词在不同上下文里含义不同」的边界，就是业务边界：

- 「商品」在**采购**语境是进货对象、在**销售**语境是售卖对象、在**库存**语境是物料——各上下文应各自建模；
- 「用户」在**认证**语境是账号与凭证、在**组织**语境是员工与部门——不强行共用一个万能模型。

同时要区分**子域类型**，避免过度投入：

| 子域类型 | 含义 | 投入策略 | 本项目示例 |
| --- | --- | --- | --- |
| 核心子域 | 业务差异化所在 | 自研、精细建模 | 表单定制、工作流接入、扩展机制 |
| 支撑子域 | 业务必需但不差异 | 可自建、可采购 | 租户管理、报表、通知 |
| 通用子域 | 行业通用 | 优先成熟组件 / 采购 | 认证协议、对象存储、检索、LLM |

## 2. 拆分粒度与依据 <a id="granularity"></a>

| 依据 | 说明 |
| --- | --- |
| 业务能力 | 一次业务操作所需的最小能力集合（订单处理、库存扣减） |
| 数据生命周期 | 数据的产生、变更、归档节奏是否一致（审计链与业务表往往不同） |
| 变化频率 | 高频迭代的模块与年更模块分开，变更互不牵制 |
| 发布节奏 | 需要独立发布的模块才有拆服务的必要性 |
| 团队边界 | 一个模块能落给一个团队全权负责（见 §3） |

**粒度教训**：

- 太细（一个实体一个服务）→ 一个业务操作跨 4~6 个服务同步调用，延迟叠加、故障级联，得到**分布式单体**；
- 太粗（拆了又什么都共享）→ 服务间靠共享库 / 共享库表同步，等于换个地方耦合；
- 经验值：业界多以 **2~5 个开发能长期维护一个服务** 为健康区间；「团队 > 服务数」通常意味着拆过头。

**边界自检法**（来自 CD 实践）：把一次典型业务操作画出来，数它**跨几个服务**：

- ≤ 2：边界合理；
- 3~4：可疑，检查是否切错了维度；
- ≥ 5：基本可以判定为分布式单体（见《[11 常见误区](11_微服务_常见误区.md)》）。

## 3. 康威定律与组织设计 <a id="conway"></a>

> **康威定律**：系统的架构会长成构建它的组织的沟通结构。
> 想得到什么样的架构，就先设计对应的组织——即**逆康威机动**（Inverse Conway Maneuver）。

| 概念 | 内容 | 与拆分的关系 |
| --- | --- | --- |
| 逆康威机动 | 先按目标架构调整团队，再等架构自然长成 | 微服务本质上是**组织解耦工具**（Fowler） |
| 两披萨团队 | 一个团队应小到能用两块披萨喂饱（Amazon） | 服务规模应与团队规模匹配，不追求服务数量 |
| Team Topologies | 四类团队（流水线对齐 / 平台 / 赋能 / 复杂子系统）+ 三种交互（协作 / X 即服务 / 赋能） | 给「谁维护哪个服务、怎么协作」提供词汇 |
| 认知负载 | 一个团队能同时理解与维护的系统复杂度有上限 | 拆分的真正目标：降低单团队认知负载 |

> 本项目现状：**单人兼职**。按康威定律，当前组织只需一个模块化单体；
> 拆分的组织前提是「出现多个需要独立交付的团队」——这正是《[10 项目评估](10_微服务_项目评估.md)》的重评触发项之一。

## 4. 常见拆分反模式 <a id="antipatterns"></a>

| 反模式 | 表现 | 后果 |
| --- | --- | --- |
| 按技术层拆 | `api-service`、`data-service`、`ui-service` | 每个业务操作都要跨全部层，延迟与耦合最大 |
| 按实体/名词拆 | `user-service`、`order-service` 但共享模型 | 边界随业务变化立刻失效 |
| 按 UI 页面拆 | 一个页面一个后端服务 | 页面重组时服务重组，联动成本高 |
| 公共模块黑洞 | 什么都放 `common` / `shared` | 全员依赖，改一处牵动所有服务 |
| 拆完仍共享数据库 | 服务各自 repo 但连同一个库 | 分布式单体，独立部署成空话（见《[06 数据与多租户](06_微服务_数据架构与多租户.md)》） |
| 为拆而拆 | 无组织或性能收益，纯技术追求 | 只收获了分布式复杂度（《[02 取舍](02_微服务_单体与微服务取舍.md)》§3） |

## 5. 在本项目中的用途 <a id="usage"></a>

- **业务域地图已有**：平台域（认证 / 权限 / 通用能力 / 工作流 / 系统集成…）与产品域（biz 采购 / 收付款 / 供应商 / 销售 / 仓储；cw）在《平台可扩展性规划》与 biz 规划中已按业务能力划分——这套划分本身就是**限界上下文级别的边界**，无论最终是否拆服务都成立。
- **注册要素即边界声明**：模块简称 / 表前缀 / 业务码 / 错误码段 / 事件域，是「一个模块一个域」的机器可校验表达；跨域调用走服务层或事件（《后端开发规范》分层职责）。
- **横切关注点不拆**：权限、多租户、审计、日志属于**平台横切**，在微服务里同样会横切所有服务（这正是现行评估里「权限体系与多租户路由横切全局难以拆分」的技术依据）。
- **事件域设计**：命名 `{域}.{对象}.{动作}`（如 `pur.order.created`）已在事件总线契约中体现，天然为未来跨进程事件流做准备（见《[05 通信与分布式一致性](05_微服务_通信与分布式一致性.md)》）。
