## 1. 技术概述 <a id="overview"></a>

**单体**把全部功能放在一个部署单元里：一次构建、一次发布、一个进程；模块之间是进程内调用，共享数据库事务。
**微服务**把应用拆成一组可独立部署的服务，服务间经网络通信，各自管理自己的数据。

两者的差别不只在「拆不拆」，而在**把什么放到了网络边界之外**：

- 单体：模块边界靠纪律与工具（编译期、架构测试）维持；修改一处需要整体构建部署；
- 微服务：边界由网络与部署单元天然强制；但每次调用都可能失败、变慢、不一致。

因此业界把它称为**取舍**（trade-off）而非升级：微服务用**分布式复杂度**换**独立性与边界强制性**。
Fowler 明确提醒：**大多数软件系统应当做单体**，「先把系统保持简单到不需要微服务；如果需要，再演进」。

## 2. 收益清单（微服务换来了什么） <a id="benefits"></a>

| 收益 | 说明 | 成立前提 |
| --- | --- | --- |
| 强模块边界 | 网络边界让「绕开接口直接调内部」变得困难，模块化被强制执行 | 切分对齐限界上下文，否则变成分布式单体 |
| 独立部署 | 小服务可单独测试、发布、回滚，改坏一个不拖垮全网 | 有成熟的 CD 流水线与契约兼容策略 |
| 独立伸缩 | 热点服务单独扩容，资源画像不同的模块不再互相迁就 | 无状态设计 + 编排能力 |
| 故障隔离 | 一个服务故障可降级，不必然全站不可用 | 有帮助降级设计与超时/熔断 |
| 技术异构 | 不同服务可用不同语言 / 存储，适配不同问题 | 有治理能力，否则运维面爆炸 |
| 团队自治 | 一个服务对应一个团队，减少跨团队排队与协调 | 团队达到「两披萨」规模且边界清晰（康威定律，见《[04 领域拆分](04_微服务_领域拆分与限界上下文.md)》） |

## 3. 代价清单（微服务引入了什么） <a id="costs"></a>

Fowler 的代价清单在本项目语境下逐条翻译：

| 代价 | 具体表现 | 本项目对照 |
| --- | --- | --- |
| 分布式编程 | 远程调用慢且必定会失败，要处理超时 / 重试 / 幂等 | 单体进程内调用无此成本；异步走事件总线 |
| 最终一致 | 跨服务无法用一个事务，需要 Saga / Outbox 等模式 | 审计哈希链、软删除复合唯一、乐观锁等强一致场景多 |
| 运维复杂度 | 服务数量 ×（部署 + 监控 + 日志 + 告警 + 升级） | 现有基础设施已 8+ 组件（库/缓存/MQ/对象存储/CI…） |
| 性能损耗 | 一组远程调用链的延迟显著高于进程内调用 | 目标 P99 ≤ 1s、500 并发（《项目规划说明》性能指标） |
| 调试与追溯 | 跨服务问题定位成本高（需要分布式追踪） | 现有 trace_id 透传在进程内成本低 |
| 数据拆分 | 共享库拆成每服务一库，迁移与跨域查询复杂 | 多租户独立库模型下，拆分即租户库 × 服务数 |
| 测试成本 | 端到端测试要编排多服务，测试环境复杂化 | 单体 + SQLite/真库 CI 已覆盖 |
| 初始成本溢价 | 初始开发成本更高、ROI 回本慢 | 见 §4 实证数据：+20~30%，2~3 年回本 |

> 一句话：**分布式是复杂度放大器**。在单体里「改一个方法签名」的事，在微服务里变成「改契约 + 双端升级 + 兼容期」。

## 4. 实证数据（学界与行业调查） <a id="evidence"></a>

| 来源 | 结论 | 参考 |
| --- | --- | --- |
| Taibi 等（IEEE Cloud Computing，2017）| 76% 受访者报告微服务初始开发成本高出 **20%~30%**；ROI 回本 2 年（33%）或 3 年（66%）；迁移主因是**可维护性与可扩展性**，最大问题是**从单体解耦困难、数据迁移、服务间通信** | [论文](https://doi.org/10.1109/mcc.2017.4250931) |
| 后续工业调研（VU，18 位从业者）| 迁移最大挑战是**既有系统高耦合（9/18）**，其次是**服务边界识别（7/18）** 与解耦（6/18） | [研究](https://research.vu.nl/ws/files/277169551/Migrating_Towards_Microservice_Architectures.pdf) |
| DORA / Accelerate（多年）| 「松耦合架构」是交付绩效的强预测因子；但 DORA 明确**松耦合不等于微服务**——它衡量的是「改一处不影响他人」的能力，单体也能做到 | [DORA](https://dora.dev/) ·《[03 模块化单体](03_微服务_模块化单体.md)》 |
| Fowler（Thoughtworks 观察）| 「几乎所有成功的微服务故事，都是从变得过大的单体里长出来的；几乎每个一开始就用微服务构建的系统，最终都遇到严重麻烦」 | [MonolithFirst](https://martinfowler.com/bliki/MonolithFirst.html) |

## 5. 行业案例（正反两面） <a id="cases"></a>

### 5.1 从微服务回到单体

| 案例 | 背景 | 做法与结果 | 关键教训 |
| --- | --- | --- | --- |
| **Amazon Prime Video（2023）** | 视频质量监测（VQA）用 Step Functions + Lambda + S3 的分布式无服务器管线 | 合并进单个 ECS 进程（内存内传数据），**基础设施成本降约 90%**，突破此前约 **5% 负载**的扩展瓶颈 | 团队自述「微服务/无服务器是高规模工具，用不用要按场景判断」；AWS 的 Cockcroft 补充：这更像「Step Functions → 微服务」，广播成「Amazon 弃用微服务」是过度解读——**结论要限定在具体工作负载** |
| **Segment / Twilio（2018）** | 数百个目的地各一个服务与队列，共享库版本发散，团队 3 人全职救火 | 合并为单一服务（Centrifuge + 单体），**部署一次改变过去需部署 140+ 服务**；共享库改进从一年 32 次提升到 46 次 | 明确列出代价：故障隔离变难、进程内缓存命中下降、依赖升级牵动全局——**回到单体也要接受新代价** |
| **Stack Overflow（长期）** | 全球高流量问答站，约 50 名工程师 | **9 台 Web 服务器**跑单体 .NET 多租户应用（约 5~10% 容量水位）；自述「不拆是为避开我们没遇到的问题」 | 「快速部署从来不是我们的问题」，拆分的理由是**组织扩张与新人上手**，不是技术时尚 |
| **Shopify（2017 起）** | 千人协作、超大 Rails 代码库 | 选择**模块化单体**（组件化 + Packwerk 边界检查），明确否决微服务作为目标架构 | 「我们喜欢单体的部分正是它在一个地方；问题只是缺少边界」 |
| **Basecamp / 37signals（DHH）** | 约 12 名程序员支撑全平台 | 公开倡导「Majestic Monolith」；2023 年发文《How to recover from microservices》给出回退清单 | 「微服务用得好通常依赖：大而复杂的系统已从小系统演化而来 + 明确的强边界模块 + 有性能或组织上的硬收益」 |

### 5.2 微服务的合理主场

| 案例 | 背景 | 为什么适合微服务 |
| --- | --- | --- |
| Netflix / Amazon（早期）| 数百团队并行、全球规模、独立交付诉求极强 | 组织规模与业务复杂度远超单体认知边界；微服务是**组织解耦工具** |
| GitHub / Etsy / Facebook | 单体 + 极强 CD 能力 | 说明「单体不能快速交付」是伪命题，**交付能力来自工程系统而非架构风格** |

**共性结论**：拆分的选择与**团队规模、领域复杂度、运维能力**强相关；与「技术先进性」无关。
从微服务回退的案例，问题大多出在**边界切错 + 运维溢价**，而不是「微服务本身错」。

## 6. 决策因子 <a id="factors"></a>

| 因子 | 偏单体 | 偏微服务 |
| --- | --- | --- |
| 团队规模 | 1~5 人、单团队 | 多团队、需独立交付节奏 |
| 系统认知 | 一个人能装进脑子 | 已超出单团队认知边界 |
| 领域稳定性 | 边界仍在探索 | 限界上下文稳定且被验证过 |
| 一致性要求 | 跨模块强一致事务多 | 可接受最终一致 + 补偿 |
| 性能目标 | 跨模块调用密集、延迟敏感 | 调用链短、可缓存/异步 |
| 运维能力 | 无专职平台/运维 | 有 CD、监控、编排、平台团队 |
| 技术栈 | 单一栈足够 | 确有异构或独立伸缩需求 |
| 迁移成本 | 边界不清、数据耦合深 | 模块边界清晰、有防腐层 |

> Fowler 的判据一句话版：**「系统是否已经复杂到单体管不动」**——而不是「以后可能会复杂」。
> 如果只是「想更好」，先把单体做模块化（见《[03 模块化单体](03_微服务_模块化单体.md)》）。

## 7. 在本项目中的用途 <a id="usage"></a>

> **口径更新（2026-09-22）**：本项目已改定**以微服务为目标架构**（从一开始就分布式构建），原「不引入微服务」口径作废；本页收益/代价清单转为服务化演进须管理的风险项，目标架构与路线见平台《微服务演进规划》。

- **原口径的行业依据**：原《项目规划说明》「不引入微服务」的理由（分布式事务难、跨服务延迟威胁 P99、权限/多租户横切难拆、基础设施已多、团队小）与上述案例和实证**高度一致**；本页为当时的讨论提供证据基座。
- **收益的替代实现**：本项目把微服务收益中的「能力可替换」「边界强制」「独立伸缩」分别用**插件化**、**模块注册与 CI 校验**、**无状态 + 独立 worker** 承载；剩「独立部署与故障隔离」见《[10 项目评估](10_微服务_项目评估.md)》逐条核对。
- **讨论用反例**：如果把「向微服务演进」作为预案，必须先满足 Fowler 的**前置条件**（可观测性、CD、领域边界稳定）——这恰好也是现行计划中的建设方向（可观测性 / 运维阶段）。

## 8. 常见误区 <a id="pitfalls"></a>

- **「微服务 = 高性能」**：微服务通常**增加**延迟（网络 + 序列化 + 多跳），性能靠的是缓存、异步、水平扩展，不是拆分。
- **「单体不能快速交付」**：Facebook / Etsy / Stack Overflow 反例充分；交付能力取决于 CD 与测试体系。
- **「大厂都微服务，所以我们也该」**：大厂拆分的动因是**组织规模**（数百团队并行），不是流量本身。
- **「先拆了再说，反正迟早要拆」**：边界没稳定就拆，大概率收获一个**分布式单体**（见《[11 常见误区](11_微服务_常见误区.md)》）。
- **「回退单体是失败」**：Prime Video / Segment 的回退是**按数据与成本做的工程决策**；架构本应随认知演进。
