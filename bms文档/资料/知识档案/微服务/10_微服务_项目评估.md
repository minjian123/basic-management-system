## 1. 评估目的与口径 <a id="purpose"></a>

本页把《[02 取舍](02_微服务_单体与微服务取舍.md)》的收益/代价清单**逐条代入 BMS 的实际约束**，
产出一张可讨论的决策矩阵与一份可执行的重评触发条件。口径：

- 只验证**前提是否满足、收益是否真实、代价能否承受**，不以「先进/落后」评判架构；
- **决策已重开（2026-09-22）**：本项目**以微服务为目标架构**（从一开始就分布式构建），见平台《微服务演进规划》。本页收益/代价核对转为服务化演进**须管理的风险清单**；触发条件（原 T1~T8）改写为「何时升级运行与治理能力」（E1~E5，见 §6 / §7）。
- 评估随时间变化：本页升级触发条件是「什么时候执行 E1~E5」的清单。

## 3. 收益核对（微服务能给的，本项目现在要不要） <a id="benefits-check"></a>

| 收益 | 本项目现状替代 | 现在是否需要 | 触发条件（见 §6） |
| --- | --- | --- | --- |
| 强模块边界 | 模块注册 + CI 唯一性校验 + 分层职责 + 基类体系；可再补架构测试 | 部分（可低成本补强） | 模块越界成为实际痛点 |
| 独立部署 | 无（单体一次发布） | **暂否** | 发布频率/风险成为瓶颈，且有多团队并行 |
| 独立伸缩 | 无状态应用 + Celery worker 横向复制；热点模块可拆 worker | **暂否**（计算层已可伸缩） | 单模块资源画像极端且影响全局 |
| 故障隔离 | 进程内熔断/降级/限流基座 + 就绪检查 | **部分满足**（进程内隔离） | 出现模块级故障拖垮全局的实例 |
| 技术异构 | 插件化端口可换实现（进程内）；确需异构走「独立服务」形态 | **已有出口** | 出现必须异构/强隔离的模块 |
| 团队自治 | 单人团队无此诉求 | **暂否** | 多团队独立交付诉求出现 |

> **决策重开后**：本表收益转为「目标架构下各服务的实现方式」；原「现在是否需要」列不再作为「是否拆分」的依据。

## 4. 代价核对（本项目要付多少） <a id="costs-check"></a>

| 代价 | 本项目具体化 | 量级判断 |
| --- | --- | --- |
| 分布式事务 | 审计哈希链等 C5 场景需 Saga/补偿重建，正确性风险高 | 高 |
| 跨服务延迟 | C6 的 P99 ≤ 1s 对多跳同步链敏感；调用链越深越危险 | 高 |
| 运维复杂度 | C8 已 8+ 组件；再叠加编排/网关/网格/追踪，单机与单人不可持续 | 高 |
| 数据拆分 | C4 租户独立库 × 服务数 = 库数量乘法；迁移/备份/监控 fan-out | 高 |
| 安全横切 | C7 权限/租户/审计在每服务重复实现；新增 mTLS/服务身份/证书治理 | 高 |
| 测试与调试 | 端到端需多服务编排；分布式问题定位依赖追踪体系 | 中高 |
| 初始成本溢价 | 实证 +20%~30% 初始成本，2~3 年回本（Taibi 2017） | 与 C1 单人兼职冲突 |
| 认知负载 | 单人维护的服务数量与基础设施面扩大 | 高 |

## 5. 决策矩阵 <a id="matrix"></a>

| 维度 | 当前取值 | 偏向 | 说明 |
| --- | --- | --- | --- |
| 团队规模 | 1 人兼职 | **单体** | 康威定律：组织不需要多服务 |
| 系统认知 | 阶段一已交付、基线可控 | **单体** | 尚未出现「单体管不动」 |
| 领域稳定性 | 业务域地图已定，产品/平台边界清晰 | 中性 | 边界质量有利于未来拆分，但不构成现在拆的理由 |
| 一致性要求 | 强一致场景多（C5） | **单体** | 本地事务零成本 |
| 性能目标 | P99 ≤ 1s / 500 并发（C6） | **单体** | 避免多跳延迟 |
| 运维能力 | 无专职运维，Compose 单机（C1/C3） | **单体** | 不满足 Fowler 三项前提的规模化要求 |
| 技术异构 | 插件化 + 独立服务出口（C9/C11） | 中性 | 已有替代路径 |
| 独立伸缩 | worker 层已可伸缩 | 中性 | 尚未触达单模块极端画像 |
| 交付风险 | 单体发布风险由测试/门禁/回滚覆盖 | **单体** | CD 能力可弥补 |
| **综合** | — | **以微服务为目标演进（分布式起步）**；上表代价转为服务化演进须管理的风险清单 | 见 §6 / §7 与平台《微服务演进规划》 |

## 6. 演进路线（E1~E5） <a id="options"></a>

原「维持现状 / 强化模块化 / 独立服务出口 / 按需抽取」四选项（A~D）随**以微服务为目标架构**的决策作废；演进路线改写为「**何时升级运行与治理能力**」，与服务化地基共同构成演进路径（详见平台《微服务演进规划》「演进路线」节）：

| # | 触发条件（任一成立即执行） | 动作 |
| --- | --- | --- |
| E1 | 单机多容器资源触顶 | 迁多主机 |
| E2 | 容器编排复杂度超 Compose | 引入 k3s / 服务网格 |
| E3 | 服务数量与团队规模上升 | 引入配置中心 / 服务发现 / 契约注册的托管方案 |
| E4 | 跨服务一致性问题频发 | 引入编排式 Saga（Temporal） |
| E5 | 合规 / 隔离要求 | 物理隔离部署 |

## 7. 升级触发条件（原 T1~T8 → E1~E5） <a id="triggers"></a>

原「是否从单体拆」的重评触发条件（T1~T8）随分布式起步失效，改写为「**何时升级运行与治理能力**」的 E1~E5（动作见 §6），量化口径建议：

| # | 触发条件（任一成立即执行） | 量化口径（建议） |
| --- | --- | --- |
| E1 | 单机资源触顶 | 单机多容器持续逼近资源上限 |
| E2 | 编排复杂度超 Compose | 自愈 / 滚动升级 / 多节点调度成为刚需 |
| E3 | 服务与团队规模上升 | 服务数持续增长、需独立交付节奏的团队 ≥ 2 |
| E4 | 一致性问题频发 | 手写状态机 + 补偿开始失控，或跨服务流程步骤 ≥ 4~5 且含人工节点 |
| E5 | 合规 / 隔离 | 客户或合规要求物理隔离（数据驻留、专有部署） |

> 复审节奏：每阶段末复盘时对照本表一次（`review_stage.py` 第 9 项原打印 T1~T8 与微前端 F1~F8，随本文修订更新为 E1~E5）；E1~E5 全部不成立则维持当前单机多容器形态。
> **联动口径**：瓶颈在哪端先动哪端；前后端触发同时成立时**后端优先**（后端一致性与运维代价结构更重）。

## 8. 待讨论问题 <a id="discussion"></a>

原 5 项待讨论问题已随决策重开闭环：① 独立服务出口 → 产品默认独立服务接入（见 §6 / §7）；② 模块边界 CI 硬校验 → 服务化地基 S1 / S2 门禁；③ 事件契约与 Outbox → 服务化地基 S3 与自研 Outbox；④ 前端微前端口径 → 另行讨论；⑤ 重评触发引用 → 见 §6 / §7 的 E1~E5。后续开放问题登记于平台《微服务演进规划》「风险与待实测」节。
