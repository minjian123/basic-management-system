## 1. 评估目的与口径 <a id="purpose"></a>

本页把《[02 取舍](02_微服务_单体与微服务取舍.md)》的收益/代价清单**逐条代入 BMS 的实际约束**，
产出一张可讨论的决策矩阵与一份可执行的重评触发条件。口径：

- 只验证**前提是否满足、收益是否真实、代价能否承受**，不以「先进/落后」评判架构；
- 结论**不改变现行决策本身**——是否修订《项目规划说明》「不引入微服务」条目，由讨论与评审拍板；
- 评估随时间变化：本页的重评触发条件是「什么时候必须重新开这个会」的清单。

## 3. 收益核对（微服务能给的，本项目现在要不要） <a id="benefits-check"></a>

| 收益 | 本项目现状替代 | 现在是否需要 | 触发条件（见 §6） |
| --- | --- | --- | --- |
| 强模块边界 | 模块注册 + CI 唯一性校验 + 分层职责 + 基类体系；可再补架构测试 | 部分（可低成本补强） | 模块越界成为实际痛点 |
| 独立部署 | 无（单体一次发布） | **暂否** | 发布频率/风险成为瓶颈，且有多团队并行 |
| 独立伸缩 | 无状态应用 + Celery worker 横向复制；热点模块可拆 worker | **暂否**（计算层已可伸缩） | 单模块资源画像极端且影响全局 |
| 故障隔离 | 进程内熔断/降级/限流基座 + 就绪检查 | **部分满足**（进程内隔离） | 出现模块级故障拖垮全局的实例 |
| 技术异构 | 插件化端口可换实现（进程内）；确需异构走「独立服务」形态 | **已有出口** | 出现必须异构/强隔离的模块 |
| 团队自治 | 单人团队无此诉求 | **暂否** | 多团队独立交付诉求出现 |

## 4. 代价核对（本项目要付多少） <a id="costs-check"></a>

| 代价 | 本项目具体化 | 量级判断 |
| --- | --- | --- |
| 分布式事务 | 审计哈希链等 C5 场景需 Saga/补偿重建，正确性风险高 | 高 |
| 跨服务延迟 | C6 的 P99 ≤ 1s 对多跳同步链敏感；调用链越深越危险 | 高 |
| 运维复杂度 | C8 已 8+ 组件；再叠加编排/网关/网格/追踪，单机与单人不可持续 | 高 |
| 数据拆分 | C4 租户独立库 × 服务数 = 库数量乘法；迁移/备份/监控 fan-out | 高 |
| 安全横切 | C7 权限/租户/审计在每服务重复实现；新增 mTLS/服务身份/证书治理 | 高 |
| 测试与调试 | 端到端需多服务编排；分布式问题定位依赖追踪体系 | 中高 |
| 初始成本溢价 | 实证 +20%~30% 初始成本，2~3 年回本（Taibi 2017） | 与 C1 单人兼职冲突 |
| 认知负载 | 单人维护的服务数量与基础设施面扩大 | 高 |

## 5. 决策矩阵 <a id="matrix"></a>

| 维度 | 当前取值 | 偏向 | 说明 |
| --- | --- | --- | --- |
| 团队规模 | 1 人兼职 | **单体** | 康威定律：组织不需要多服务 |
| 系统认知 | 阶段一已交付、基线可控 | **单体** | 尚未出现「单体管不动」 |
| 领域稳定性 | 业务域地图已定，产品/平台边界清晰 | 中性 | 边界质量有利于未来拆分，但不构成现在拆的理由 |
| 一致性要求 | 强一致场景多（C5） | **单体** | 本地事务零成本 |
| 性能目标 | P99 ≤ 1s / 500 并发（C6） | **单体** | 避免多跳延迟 |
| 运维能力 | 无专职运维，Compose 单机（C1/C3） | **单体** | 不满足 Fowler 三项前提的规模化要求 |
| 技术异构 | 插件化 + 独立服务出口（C9/C11） | 中性 | 已有替代路径 |
| 独立伸缩 | worker 层已可伸缩 | 中性 | 尚未触达单模块极端画像 |
| 交付风险 | 单体发布风险由测试/门禁/回滚覆盖 | **单体** | CD 能力可弥补 |
| **综合** | — | **维持「单体 + 模块化 + 插件化 + 独立 worker」**；把「可拆分性」作为长期设计原则保留 | 见 §6/§7 |

## 6. 演进选项（如果将来要动，按什么顺序） <a id="options"></a>

| 选项 | 内容 | 触发/适用 | 主要代价 |
| --- | --- | --- | --- |
| **A 维持现状** | 单体 + 模块化 + 插件化 + 独立 worker；继续补边界与契约 | 当前 | 无新增 |
| **B 强化模块化**（低成本，推荐持续做） | 架构测试/依赖检查补强、数据所有权纪律、事件契约与 Outbox 思想预埋、可观测性按阶段落地 | 任何阶段 | 少量工程投入，回报是可维护性与可拆分性 |
| **C 独立服务出口** | 确需异构/强隔离的模块走「独立服务」形态（OIDC + 开放接口 + 事件），不并入主进程 | 出现异构/隔离诉求时 | 该模块自身的运维成本 |
| **D 按需抽取微服务** | 在 B 的基础上用 Strangler Fig 抽取 1~2 个边缘/热点模块 | 仅当 §7 触发条件成立 | 分布式成本（见 §4），需先满足前提 |

## 7. 重评触发条件（什么时候必须重新讨论） <a id="triggers"></a>

| # | 触发条件（任一成立即开评） | 量化口径（建议） |
| --- | --- | --- |
| T1 | 团队规模 | 稳定 **≥ 5~8 人** 且存在多个需要独立交付节奏的团队 |
| T2 | 领域边界稳定 | 同一模块边界在 **≥ 2~3 个大阶段**迭代中未发生调整 |
| T3 | 发布瓶颈 | 单体发布风险/频率成为瓶颈：重大故障与回滚显著增加，或需多团队协调发布 |
| T4 | 资源画像 | 某模块（报表/检索/AI/批处理）资源画像极端，独立伸缩收益可量化（如成本或稳定性） |
| T5 | 故障隔离 | 出现「模块级故障拖垮全局」且进程内隔离（熔断/降级/限流/配额）无法覆盖 |
| T6 | 隔离/合规 | 客户或合规要求物理隔离（数据驻留、专有部署），且「独立服务」出口无法满足 |
| T7 | 运维能力 | 出现/引入专职平台或运维角色，CD、可观测性、编排能力达到 Fowler 前提 |
| T8 | 性能证据 | 压测/生产数据显示单体瓶颈在**非可拆模块内部**（而非缓存/索引/连接池等） |

> 复审节奏：每阶段末复盘时对照本表一次（`review_stage.py` 第 9 项已打印 T1~T8 与微前端 F1~F8）；T1~T8 全部不成立则维持选项 A。
> **联动口径**：瓶颈在哪端先动哪端；前后端触发同时成立时**后端优先**（后端一致性与运维代价结构更重，且平台已备「独立服务」出口）。

## 8. 待讨论问题（留给讨论会） <a id="discussion"></a>

1. 「独立服务出口」是否需要更明确的能力边界与最小骨架（便于将来 C 选项落地）？
2. 模块边界纪律要不要升级为 CI 硬校验（架构测试 / 依赖检查），投入与收益如何？
3. 事件契约与 Outbox 思想是否在阶段二/通用能力阶段预埋，作为「可拆分性」的一部分？
4. 前端是否维持「不引入微前端」口径（与后端评估解耦）？
5. 是否需要在《项目规划说明》「不引入微服务」条目中补充**重评触发条件**的引用（本页 §7）？
