## 1. 技术概述 <a id="overview"></a>

拆分微服务时，**数据是最难拆的部分**：代码可以逐步重构，数据的权威归属、事务边界与迁移路径一旦定错，代价极高。
微服务的标准原则是 **Database per Service**：每个服务拥有自己的数据存储，别的服务只能经 API 或事件访问——
「拥有」的含义包括：只有它写、只有它定 schema、只有它决定生命周期。

> 与《[03 模块化单体](03_微服务_模块化单体.md)》的「数据所有权」是同一个概念，只是微服务把物理隔离也加上了。

## 2. 共享数据库反模式 <a id="shared-db"></a>

**现象**：服务拆了，但两个服务仍直接读写同一批表。**后果**：

- schema 变更变成跨团队协调：一个服务加字段，另一个服务的查询/导入任务可能失败；
- 独立部署成为空话：两边必须一起发布（→ 分布式单体）；
- 数据损坏难追责：无法判断是 API 缺陷、批处理还是手工 SQL 改坏的；
- 跨租户 / 跨模块的隐性访问无法用权限约束（绕过服务层校验）。

**典型演化路径**：先共享几张表 → 再共享字典表 → 为了性能跨 schema JOIN → 写「方便视图」→
最后某个服务直接读另一个服务的状态，理由是「API 太慢」。数据模型变成了真正的集成层，API 成了装饰。

**修复路径**（渐进）：

1. 用服务边界**包住**共享 schema：新代码一律经该服务 API，切断新增直连；
2. 相关域建**独立库**，新业务状态写新库；历史数据经 ETL / CDC 同步过渡；
3. 用**领域事件**发布变更，其他服务建本地投影（读模型），不再直读对方的表；
4. 逐个下线旧表访问，最后归档/退役旧 schema。

> 注意：跨服务 JOIN 的报表需求应走**只读从库 / 数据查询提供者 / 数仓**，不做在线跨库事务。

## 3. 跨服务数据访问的四种合法姿势 <a id="access"></a>

| 姿势 | 适用 | 代价 |
| --- | --- | --- |
| 同步 API 查询 | 需要强一致读的少量场景 | 运行时耦合（延迟/可用性） |
| 事件 + 本地投影 | 大部分读场景（订单状态、用户资料副本） | 最终一致、投影维护与补偿 |
| CDC 同步 | 过渡期或分析侧（Debezium 等） | 额外组件、schema 漂移风险 |
| 批量数据交换 | 报表 / BI / 归档 | 时效性差，适合离线 |

**读己之写**（用户刚提交就刷新要看得到）需要专门设计：命令响应携带版本号、读侧等待或前端乐观更新（见《[05 通信与分布式一致性](05_微服务_通信与分布式一致性.md)》§4.4）。

## 4. 多租户：三种隔离模型 <a id="multitenancy"></a>

SaaS 平台绕不开的问题：**多个租户的数据怎么放**。业界归纳为三档（外加混合的桥接形态）：

| 模型 | 隔离强度 | 成本 | 迁移/运维复杂度 | 典型适用 |
| --- | --- | --- | --- | --- |
| 共享库共享表（行级 + `tenant_id`） | 最弱（应用保证） | 最低 | 最低（一次迁移） | 大量小租户、消费级 |
| 每租户独立 schema | 中（逻辑隔离） | 中 | 中（迁移 ×schema 数） | 中型 B2B |
| **每租户独立库**（silo） | 最强（物理隔离） | 高 | 高（迁移 ×租户数、备份/监控 ×N） | 企业 / 合规 / 数据驻留 |
| 混合（桥接） | 按租户分层 | 按需 | 双路径 | 大客户单独，长尾共享 |

> 行业建议：**不要先共享再迁移**——从共享库迁到独立库的迁移成本随租户数剧增；
> 隔离模型属于「写完第一行业务逻辑前就要定」的决策。

**独立库模型在微服务下的双重乘法**（本项目的关键讨论点）：

- 单体 × 租户独立库 = 每租户一个库，连接池 = 租户数 × 池大小（如 500 租户 × 10 连接 = 5000 连接，远超单库上限）；
  业界做法：分层池化 + 事务级连接池（如 PgBouncer）、按租户等级分配专用/共享池、连接预算与 LRU 回收；
- 微服务 × 租户独立库 = **服务数 × 租户数** 个物理库：迁移要 fan-out、备份/监控数量翻倍、
  每服务都要实现租户路由与上下文传播；
- **横切成本**：租户上下文必须在请求、异步任务、消息消费、缓存 key、后台脚本全链路一致传播，否则就是跨租户数据泄漏——
  这是本项目评估中「多租户路由横切全局难以拆分」的含义（见《[10 项目评估](10_微服务_项目评估.md)》）。

**多租户的常见事故点**（与架构风格无关，拆分后风险面更大）：

- 漏加租户过滤条件（一条 SQL 泄漏全部租户）；RLS 是兜底而不是替代；
- 缓存 key 未带租户前缀；
- 异步任务丢失租户上下文；后台脚本直连库绕过程序校验；
- 连接池被单租户打满（noisy neighbor）。

## 5. 在本项目中的用途 <a id="usage"></a>

| 维度 | 本项目现状 | 与微服务模式对照 |
| --- | --- | --- |
| 租户拓扑 | **租户独立库**（silo）+ 平台库；`db/tenant.py` 解析链、`EngineRegistry` 引擎注册表（LRU / 连接预算，阶段二真实实现） | 已是微服务业界眼中最贵的隔离档，拆分会让「库数量 × 服务数」 |
| 迁移 | Alembic + `ops` 批量迁移 / 新租户初始化（阶段二落地） | 拆分后需要按租户 × 按服务 fan-out |
| 数据范围 | `DataScope` 契约 + `_apply_data_scope` 钩子（RBAC 阶段注入规则） | 数据权限横切，拆服务后每个服务都要重复实现 |
| 报表 / 查询 | `BaseQueryProvider`（只读从库 + 白名单，报表阶段落地） | 已按「读侧不碰写库」的思想预留 |
| 事件投影 | 事件总线契约 + 审计哈希链（分区有序消费） | 未来跨进程读模型的传输层已定 |
| 平台库 | `sys_module` 等平台表登记跨租户元数据 | 拆分时需要界定哪些表属「平台域」共享 |

**结论**：本项目在多租户上属于「最强隔离、最高成本」的一档；不拆服务时，这套成本只付一次
（一套租户路由 + 一套迁移工具 + 一套数据权限）；一旦微服务化，这些**横切能力要在每个服务重复一遍**，
这是现行「不引入微服务」评估的重要技术理由。
