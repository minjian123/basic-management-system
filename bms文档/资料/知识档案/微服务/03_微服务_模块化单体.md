## 1. 技术概述 <a id="overview"></a>

**模块化单体**（Modular Monolith）是：**一个部署单元，但内部按业务能力划出强边界**——
模块之间只能通过公开契约通信，各自拥有自己的数据与实现，边界由工具在构建 / CI 期强制。

```mermaid
flowchart LR
    subgraph 部署单元（一个进程 / 一份构建）
        direction TB
        M1[模块 A<br/>公开契约 + 私有实现 + 自有数据]:::m
        M2[模块 B<br/>公开契约 + 私有实现 + 自有数据]:::m
        M3[模块 C<br/>公开契约 + 私有实现 + 自有数据]:::m
        M1 -->|"契约调用 / 进程内事件"| M2
        M3 -->|"契约调用 / 进程内事件"| M1
    end
    X[外部请求] --> M1
    classDef m fill:#e8f4e8,stroke:#3a7,color:#111
```

它的定位来自一个业界共识：**微服务的好处里，有一大半与「分布」无关**——
强模块边界、契约纪律、可独立测试的单元，在单进程里同样能做到；
而微服务的代价（网络、一致性、运维）却全部来自分布。

> Shopify：「我们喜欢单体的部分正是它在一个地方；我们遇到的问题，是不同功能之间缺少边界。」
> DORA：松耦合架构衡量的是「改一处是否影响他人」，**与是否微服务无关**。
> 因此本页是讨论的前提：**先把单体模块化做好，再谈要不要拆**——如果模块化都没做到，拆分只会
> 把耦合原封不动搬进网络（分布式单体，见《[11 常见误区](11_微服务_常见误区.md)》）。

## 2. 边界的四个要素 <a id="elements"></a>

一个「真模块」需要同时满足四条，缺一条就会退化为「一个文件夹」：

| 要素 | 含义 | 违反的表现 |
| --- | --- | --- |
| 公开契约 | 模块对外只暴露一个稳定入口（接口 / DTO / 事件） | 别的模块直接 import 内部类、复用内部模型 |
| 私有实现 | 内部类默认不可见（`internal` / 下划线 / 包私有） | 内外无差别，随便取用 |
| 数据所有权 | 模块的数据只有一个权威归属，他人经契约 / 事件访问 | 跨模块直接 JOIN、共享 ORM 关系、互相改表 |
| 依赖单向 | 模块依赖图无环、方向明确（按层 / 按域） | 循环依赖、互相 import |

## 3. 工程化强制手段 <a id="enforcement"></a>

「靠自觉」的模块化在压力下必然腐化，主流做法是把边界变成**构建失败**：

| 手段 | 代表实现 | 作用 |
| --- | --- | --- |
| 语言可见性 | Java package-private、C# `internal`、Python `_private` + 包组织 | 编译/约定期阻止内部类型外泄 |
| 架构测试 | Java: [ArchUnit](https://www.archunit.org/) / .NET: ArchUnitNET / 自研 AST 脚本 | 在 CI 中断言依赖方向、禁止跨模块引用 |
| 静态边界检查 | Shopify [Packwerk](https://shopify.engineering/shopify-monolith)（Ruby）、Sorbet 类型契约 | 对超大代码库做常量引用级检查，PR 期拒绝越界 |
| 框架支持 | [Spring Modulith](https://docs.spring.io/spring-modulith/reference/) | 模块结构验证、模块级集成测试、文档生成、运行时观测 |
| 契约与注册 | 模块注册表 + 唯一性校验（表前缀 / 错误码段 / 事件域） | 新模块登记冲突即拒（本项目已有，见 §4） |
| 独立测试 | 每模块可单独跑测试；变更只触发相关测试 | 把「模块化」转化为交付速度收益 |

> 判断标准：**把边界检查从代码评审挪进流水线**——人可能心软，CI 不会。

## 4. 与本项目的对应 <a id="project"></a>

本项目当前的架构形态就是**模块化单体 + 插件化**：

| 模块化单体要素 | 本项目对应机制 | 现状 |
| --- | --- | --- |
| 分层与职责 | backend 分层目录（api / services / repositories / models / schemas）+ 基类体系 | 已交付（阶段一） |
| 模块登记与唯一性 | `sys_module` 注册表：表前缀 / 业务码 / 错误码段 / 事件域，启动与 CI 校验冲突即拒 | 结构与离线校验已交付；落库随阶段二 |
| 能力边界（纵向） | 插件化端口 / 适配器 + `BasePluggable` + 注册表 + `Null` 默认实现 | 骨架与占位已交付（阶段一），真实实现随各能力阶段 |
| 业务边界（横向） | 产品扩展接入流程：独立业务模块按分层挂接、注册要素登记、构建期合并 | 机制已定（《平台可扩展性规划》） |
| 事件解耦 | 事件总线（RocketMQ）统一发布 / 订阅，跨域调用走事件 | 契约骨架已交付（阶段一） |
| 异步与独立伸缩 | 无状态应用 + Celery worker（可独立扩容进程） | 任务基座占位已交付 |
| 契约校验 | OpenAPI 契约快照（CI）、模块清单校验、基座自检 | 已交付并挂 CI |

**换言之**：微服务收益里的「边界强制」「能力可替换」「独立伸缩（计算层）」已有承载；
剩下的是「独立部署单元」「故障隔离边界」两项——它们才是下一步讨论的真正议题。

## 5. 可拆分性：为「以后可能要拆」预留什么 <a id="extractability"></a>

> **口径更新（2026-09-22）**：本项目已改定**以微服务为目标架构、从一开始就分布式构建**；下文的「可拆分性」（保留拆分选项）对应目标架构下的**服务化地基**要求（见平台《微服务演进规划》），其工程纪律仍具参考价值。

模块化单体不是「永远不拆」的承诺，而是**保留拆分选项**的工程纪律。要保住的四个接口：

1. **契约即服务接口**：模块公开契约（接口 + DTO）设计得像未来的服务 API（无进程内假设、传值不传引用、显式幂等）；
2. **数据所有权**：模块只写自己的表；跨模块读经契约或事件，不共享 ORM 关系与事务；
3. **进程内事件与异步习惯**：跨模块的副作用尽量走事件（本地事件表 / Outbox 同构），未来换成消息总线只是换传输层（见《[05 通信与分布式一致性](05_微服务_通信与分布式一致性.md)》）；
4. **无状态与外部化**：会话 / 缓存 / 文件 / 定时任务已外部化（Redis / MinIO / Celery），进程可横向复制——这是独立伸缩与独立部署的物理前提。

> 达到这四条后，从单体里「抽出」一个模块，主要工作量是**数据搬迁与调用方切换**，
> 而不是先花半年解耦——这正是《[09 渐进式演进](09_微服务_渐进式演进.md)》的前提。

## 6. 反例与注意事项 <a id="pitfalls"></a>

- **只有文件夹的模块化**：目录分了，代码随便 import、表随便 JOIN，等于没分；
- **共享「实体模型」**：多个模块共用一个领域模型与 ORM 关系，是最常见的隐性耦合（数据所有权失效）；
- **跨模块 JOIN 做报表**：读侧可以用只读视图 / 数据查询提供者 / 数仓，写侧禁止跨模块直连（本项目已设「数据查询提供者」基座）；
- **契约过宽**：公开契约暴露内部状态，等于把实现当接口用；
- **为拆而拆**：模块化单体的目标是**可维护 + 可拆分**，不是制造拆分借口——拆分与否只看收益（见《[02 取舍](02_微服务_单体与微服务取舍.md)》§6）。
