## 1. 场景：结构化权限保存必须原子 <a id="scenario"></a>

触发点：结构化权限保存（「角色 + 用户 / 岗位 / 部门分配 + 权限项」）要求**要么全成功要么全失败**。

数据分布（2026-10-06 组件设计口径）：

| 数据 | 归属 | 是否跨服务 |
| --- | --- | --- |
| 角色、角色权限项、字段 / 数据权限 | 权限域（bms） | 否 |
| 角色-用户分配 `sys_user_role` | 权限域（bms） | 否 |
| 角色-岗位 `org_role_post` / 角色-部门 `org_role_dept` | mdm 组织域 | **是**（插件独立即时提交） |

## 2. 三路线对比 <a id="compare"></a>

| 维度 | ③ 单库收敛（**推荐**） | ② 单进程多库 2PC | ① 外部 TM + 各服务 XA |
| --- | --- | --- | --- |
| 一致性 | **强（本地事务原子）** | 强（同进程多库原子） | 强（跨服务原子） |
| 实现 | 把权限主数据收进权限服务单库 | 同进程同步引擎驱动多库 2PC | 自研 / 引入 TM + 全局账本 + 服务侧参与端点 |
| 代价 | 几乎为零 | 中（握锁、需同步引擎、PG 参数） | **最高**（TM 基础设施 + 恢复 + 对账） |
| 可用性 | 高 | 中（阻塞协议） | 低（任一参与方慢即全局阻塞） |
| 运维面 | 无新增 | 无新增组件 | 新增 TM + 全局事务库 + 恢复器 |
| 是否适用本场景 | **是** | 否（服务分进程，非单进程） | 是（但代价过高、当前无必要） |

> 实测依据：三库服务器均支持 XA、单进程多库 2PC 可用（含达梦 `dmxa`）、异步 API 不暴露两阶段——见《[02 两阶段提交与 XA](02_分布式事务_两阶段提交与XA.md)》与《数据库设计 · 方言特性》三库「事务与连接」。

## 3. 推荐 <a id="recommend"></a>

**推荐路线 ③「单库收敛」+ 现有最终一致 + 一致性屏障**：

1. **原子部分收敛单库**：角色 + 用户分配 + 权限项收敛权限服务单库，保存为**本地事务**——天然原子，零分布式代价。
2. **跨服务部分最终一致**：mdm 岗位 / 部门分配本就已拆、插件独立即时提交，经**事件 + Outbox + 幂等**收敛；执行前经**一致性屏障**等待收敛（见《[04 一致性屏障](04_分布式事务_一致性屏障.md)》）。
3. **2PC / 外部 TM 不引入**：作为**技术储备**保留（见《[03 跨服务 TM 方案](03_分布式事务_跨服务TM方案.md)》），仅在触发条件成立时经插件化替换启用。

**为什么不是 2PC / TM**：本场景的原子部分**可以**收敛单库，2PC / TM 唯一多给的「跨库写入瞬间原子」在此**用不上**，却要付出阻塞、可用性、运维与正确性工程的代价。能用本地事务解决，就不引入分布式事务。

## 4. 强一致作为技术储备的触发条件 <a id="trigger"></a>

引入强一致方案（自研 TM + 各服务 XA）**须三条同时成立**：

1. 客户对「跨服务中间态」**零容忍**（较真客户 / 强合规场景）；
2. 要求原子的数据**无法收敛到单一服务库**；
3. **无法**用「最终一致 + 屏障」满足（即屏障等待时间 / 报错率不可接受）。

任一不成立，仍走默认方案。引入时按「能力基类 + 插件注册表 + 配置选择 + 提供者」替换（**默认关闭、改配置启用、业务调用面不变**）。
