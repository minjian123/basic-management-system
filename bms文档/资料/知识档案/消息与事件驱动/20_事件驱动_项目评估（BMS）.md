## 1. 现状 <a id="status"></a>

| 项 | 现状 |
| --- | --- |
| 事件总线 | 01_01 已交付：事务性发件箱 + 轮询投递器 + 消费幂等 + 死信看板 + 指标 |
| 表结构 | `sys_outbox` / `sys_event_consumed` / `sys_event_dead_letter`，表名写死 |
| 使用方 | 06_01 操作 / 登录审计经 `audit-chain` 有序组消费；06_02 字段级审计计划复用 |
| 同步调用 | `HttpServiceClient`（httpx + JSON，OpenAPI 契约），性能不足 |
| 事务消息 | `EventPublisher.publish_transactional()` 已留接口，当前委托普通发送（备选，未启用） |
| 账本能力 | `replay()` 按事件 / 类型 / 聚合 / 时间重放；死信可重投 / 忽略 |
| 已知短板 | 多实例投递无行锁 / 租约；基础设施表名写死导致共库撞名；事件与 RPC 两套机制 |
| 决策状态 | 自研 L3 已立项（msg 产品 / 08B）；06_02 暂停等 8B 结论 |

## 2. 约束 <a id="constraints"></a>

| 约束 | 对方案的影响 |
| --- | --- |
| 单人兼职 + AI 辅助，无专职运维 | 不能照搬「多组件集群」架构；管理台与指标必须先于功能 |
| 后端单一 Python / FastAPI | 自研 broker 要接受 Python 的性能上限；必要时热点用 C 扩展或 Rust 辅助 |
| 三库：MySQL 8 / PostgreSQL 16 / 达梦 DM8 | CDC 路线基本排除（达梦无 Debezium）；自研存储要与业务库解耦 |
| 本地开发 SQLite | 平台侧不得依赖数据库特性；开发态要能跑单机 broker |
| Windows 开发机 | 文件 IO、fsync、网络行为与 Linux 有差异，需双端验证 |
| 01_01 已上线、06_01 已依赖 | 迁移必须保留回滚路径，不能一次性删除 outbox |
| 审计合规要求 | 操作 / 登录 / 字段审计不能丢事件；这是「至少一次 + 幂等」的硬底线 |
| 已有产品仓形态（mdm） | msg 必须按产品声明接入，不能反过来改 bms 基座业务 |

## 3. 方案评估 <a id="evaluation"></a>

评分口径：★ 越多越契合当前约束（★ = 差，★★★★★ = 好）。**评分只用于对照，不用于推翻已定决策**。

| 方案 | 契合度 | 长期收益 | 主要风险 | 说明 |
| --- | --- | --- | --- | --- |
| **F 自研 L3（已选）** | ★★★☆ | ★★★★★ | 高（可靠性 / 工作量 / 运维） | 与平台深度集成、统一事件与 RPC、摆脱表名绑死 |
| A 维持 Outbox + 修隔离 | ★★★★★ | ★★ | 低 | 最小改动；但 RPC 性能与统一运维问题未解 |
| B 事务消息替代业务事件 | ★★★ | ★★★ | 中 | 绑 broker、无账本；操作 / 登录审计仍要暂存表 |
| D CDC | ★★ | ★★★ | 高 | 达梦缺口 + 单人运维不可行 |
| 开源自建（Kafka / Pulsar / RocketMQ 升级） | ★★★ | ★★★ | 中 | 集成适配层长期存在；版本升级与调优仍需专人 |

**为什么自研的契合度只有三星半**：技术收益高，但与「单人兼职 + 三库 + 无专职运维」的现实约束冲突。这也是为什么路线是「**先设计 + PoC，再分阶段，随时可刹车**」，而不是一次性替换。

## 4. L3 阶段路线 <a id="roadmap"></a>

```mermaid
flowchart LR
    A["8B_00<br/>立项与总体设计"] --> B["8B_01<br/>传输与协议 PoC"]
    B --> C["8B_02<br/>消息模型与存储"]
    C --> D["8B_03<br/>RPC"]
    D --> E["8B_04<br/>可靠性与事务"]
    E --> F["8B_05<br/>高可用与复制"]
    F --> G["8B_06<br/>管理台与运维"]
    G --> H["8B_07<br/>多租户与安全"]
    H --> I["8B_08<br/>bms 迁移"]
    I --> J["8B_09<br/>验收与压测"]
```

| 阶段 | 目标 | 关键退出条件 | 对应知识篇 |
| --- | --- | --- | --- |
| 8B_00 | 需求 / 总体设计 / 选型 | 六块设计无开放 blocker | 全篇 |
| 8B_01 | HTTP/2 + 二进制 PoC | 收发 / ack / 重试 / 死信 / 重启恢复 + 基准达标 | 03 / 05 / 06 / 07 / 08 |
| 8B_02 | 消息模型与存储 | 多分区、位点、分段、崩溃恢复 | 02 / 03 / 05 |
| 8B_03 | RPC | 可替换一个 `HttpServiceClient` 试点 | 07 / 09 |
| 8B_04 | 可靠性与事务 | 至少一次 + 幂等 + outbox 适配 | 14 / 15 / 16 |
| 8B_05 | 高可用与复制 | 单节点故障可恢复 | 04 / 12 |
| 8B_06 | 管理台与运维 | 积压 / 死信 / 重放可操作 | 10 / 11 |
| 8B_07 | 多租户与安全 | 租户隔离与配额生效 | 11 |
| 8B_08 | bms 迁移 | 一条事件链 + 一个 RPC 切换成功，可回滚 | 18 / 20 |
| 8B_09 | 验收与压测 | 性能 / 稳定性 / 故障演练通过 | 12 / 13 |

**阶段之间的硬依赖**：

- **8B_01 是 go/no-go 点**：基准不达标就退回「只换 RPC」的局部方案。
- **8B_02 决定 8B_04 能否成立**：没有可靠存储与位点，可靠性无从谈起。
- **8B_05 必须在 8B_08 之前**：没有复制就迁移生产事件，等于把单点故障放大到全平台。
- **8B_06 必须先于或同步于 8B_08**：没有管理台就迁移，出问题只能重启。

## 5. 迁移路径 <a id="migration"></a>

```mermaid
flowchart LR
    P0["0 适配层<br/>EventPublisher / BaseServiceClient"] --> P1["1 试点<br/>一条低风险事件 + 一个只读 RPC"]
    P1 --> P2["2 审计事件<br/>06_01 / 06_02"]
    P2 --> P3["3 业务事件<br/>逐域迁移"]
    P3 --> P4["4 收敛<br/>旧链路无流量，保留回滚开关"]
    P4 --> P5["5 收尾<br/>删旧代码 / 表 / 文档"]
```

| 阶段 | 内容 | 退出条件 | 回滚方式 |
| --- | --- | --- | --- |
| 0 适配层 | 实现 bms 端口的 msg 版本（业务代码不改） | 适配层单测 + 双实现可切换 | 配置切回原实现 |
| 1 试点 | 一条低风险事件（如非关键通知）+ 一个只读 RPC | 事件不丢、RPC 超时与错误码正确 | 切回 RocketMQ / HTTP |
| 2 审计事件 | 06_01 操作 / 登录审计接入 | 审计不丢、链校验通过 | 切回 outbox |
| 3 业务事件 | 逐域迁移（按服务 / 按事件类型） | 每域可独立回滚 | 按域切回 |
| 4 收敛 | 旧链路无流量 | 回滚演练通过 | 保留一个版本 |
| 5 收尾 | 删除旧代码 / 表 / 文档，更新架构口径 | 文档与实现一致 | 依赖备份 |

**迁移的三条铁律**：

1. **适配层先行**：业务代码只依赖 `EventPublisher` / `BaseServiceClient` 端口，换实现不改业务。
2. **分域而不是分阶段**：一次只切一个域，出问题影响面可控。
3. **回滚开关必须演练**：不是「写了开关」，而是「真的切回去过一次」。

## 6. 风险 <a id="risks"></a>

| # | 风险 | 影响 | 缓解 |
| --- | --- | --- | --- |
| 1 | 自研存储 / 复制的 bug 导致数据丢失 | **最高**（审计合规） | 先单机 + CRC + 恢复演练；HA 前不承载唯一副本 |
| 2 | Python 性能上限 | 吞吐 / 延迟不达标 | PoC 先测；热点用 C 扩展或异步批处理 |
| 3 | 工作量远超预期（L3 是数月级） | 项目长期半成品 | 分阶段 + 每阶段可独立验收；8B_01 可刹车 |
| 4 | 单人运维无以为继 | 出问题无人定位 | 管理台 / 指标 / 告警先于功能 |
| 5 | 与 bms 迁移耦合 | 生产事故 | 适配层 + 分域切换 + 回滚演练 |
| 6 | 多租户与配额设计滞后 | 无法承载产品 | 8B_07 与 bms 租户体系同步设计 |
| 7 | 协议演进破坏老客户端 | 升级即断 | 「只增字段、未知忽略、版本可见」三铁律 |
| 8 | 达梦 / Windows 行为差异 | 本地通过、生产失败 | 双端验证；关键路径在 Linux 开发服务器复测 |

## 7. 建议 <a id="recommend"></a>

1. **8B_01 严格按「可刹车」设计**：PoC 只验证「HTTP/2 + 二进制 + 单机 broker」是否显著优于现状；不达标就退回局部方案，不硬推。
2. **存储格式预留复制字段**：即使 8B_05 才做复制，8B_02 定格式时就要留 term / 副本位点 / 校验，避免推倒重来。
3. **管理台与指标提前**：把「能看到积压、延迟、死信」作为 8B_02 的验收项之一，而不是等到 8B_06。
4. **outbox 适配优先于事务消息**：平台化后账本与重放已由日志承担，事务消息的边际收益低。
5. **06_02 继续暂停**：恢复时直接基于 msg 的 outbox 适配层，不做「先接 RocketMQ 再迁移」的二次改造。
6. **保留开源自建作为备份方案**：适配层就是为「万一自研失败」准备的，不要把它当成临时脚手架。
