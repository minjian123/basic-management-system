> **定位**：本篇把前面各篇的结论落到 BMS 的具体场景。**2026-11 已拍板「自研消息平台 L3（msg 产品）」，本篇不再讨论「要不要自研」**，而是把决策讲清、把「什么情况下应该推翻」写清，避免后续反复。

## 1. 选型分三层，不要混在一起谈 <a id="layers"></a>

很多争论之所以吵不清，是因为把三个不同层次的问题混成一句「要不要换消息队列」：

| 层 | 问题 | 选项 | BMS 结论 |
| --- | --- | --- | --- |
| **第一层：平台形态** | 消息能力从哪来？ | 自研 / 开源自建 / 云服务 | **自研 L3**（msg 产品） |
| **第二层：传输与存储** | 用什么协议、消息存哪？ | HTTP/2+二进制 / 自定义 TCP / gRPC；文件日志 / DB / 外部存储 | **HTTP/2(h2c)+MessagePack + 追加日志** |
| **第三层：可靠性原语** | 业务提交与投递怎么对齐？ | Outbox / 事务消息 / CDC / 直接发布 | **outbox 适配优先，事务消息后置** |

**顺序不能倒**：先定平台形态，才谈传输；先有传输，才谈原语落在哪。反过来先纠结 outbox 表怎么改，会得出「改表名就够了」这种局部最优、全局次优的结论。

## 2. 第一层：平台形态 <a id="form"></a>

| 维度 | 自研 L3 | 开源自建（Kafka / Pulsar / RocketMQ） | 云消息服务 |
| --- | --- | --- | --- |
| 初始投入 | **高**（broker + 存储 + 复制 + 运维，数月级） | 低（部署 + 调参） | 最低（开通即用） |
| 与 bms 集成 | **原生**（租户 / 权限 / 审计 / 事件契约同一套） | 需适配层（认证、租户、契约映射） | 需适配层 + 网络打通 |
| 可控性 | **完全**（协议、存储、调度都可改） | 受社区版本约束 | 受厂商能力约束 |
| 运维 | 自己写管理台与指标 | 社区工具成熟，但仍要专人 | 厂商负责 |
| 长期成本 | 中（自主演化，无版本追车） | 中（版本升级、集群调优） | 高（按量计费，规模大后昂贵） |
| 主要风险 | **自研 bug 与可靠性**（丢消息、脑裂、数据损坏） | 运维复杂度、与平台集成摩擦 | 供应商锁定、成本失控、数据出境 |

**为什么选自研**（决策依据，非推荐）：

1. **集成成本**：bms 有多租户、RBAC、审计、事件契约、服务目录一整套；任何开源 broker 都要再写一层适配，且适配层本身会长期存在。
2. **统一事件与 RPC**：现有同步调用（`HttpServiceClient` + FastAPI 服务端）性能不足是独立痛点——开销来自 FastAPI 框架栈（路由 / 依赖注入 / Pydantic 校验 / JSON 序列化）与 httpx 连接，**与 OpenAPI 契约无关**；自研传输可一次解决「事件 + RPC」两条链路。
3. **摆脱表名绑死**：outbox 表名写死的根因是「基础设施表由业务库承载」；平台化后位点、账本、死信都在 msg 侧，业务库不再需要套一层表。
4. **可控演进**：签约、配额、灰度、审计等需求常年变化，自研不必等社区排期。

**必须承认的代价**：

- 至少要 6~9 个月才能达到「可承载生产事件」的成熟度（8B_00~09 合计约 200h+，且只是单人兼职下的乐观估计）。
- 复制、选举、崩溃恢复这类「看起来简单、实际极难」的部件，任何 bug 都是数据丢失级别。
- 运维面从「用别人造的」变成「自己造的」，管理台与指标必须先于功能上线。

## 3. 第二层：传输与存储 <a id="transport"></a>

### 3.1 传输

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| **HTTP/2（h2c）+ 二进制** | 多路复用、流控、复用现有网关与生态 | 头部有固定开销；订阅长流要自己设计 | **选用** |
| 自定义 TCP | 极致精简、开销最低 | 连接管理、TLS、调试工具全自研 | 后置（性能不够时再评估） |
| gRPC | 强契约、多语言、流式完整 | 引入 protoc 与 proto 契约，形成「三轨契约」 | 暂不选（跨语言需求出现再说） |
| WebSocket | 双向、浏览器友好 | 需自建重连与背压 | 不选（与服务端 HTTP 栈边界模糊） |

### 3.2 存储

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| **追加日志（文件）** | 顺序写、零拷贝、整段删除、恢复成本低 | 需自研索引、分段、CRC、恢复 | **选用**（8B_02） |
| 数据库表 | 实现快、事务与查询现成 | 写放大、保留期清理难、吞吐受限 | 仅 PoC 对照，不作目标 |
| 外部 KV（RocksDB） | 成熟、支持 compaction | 引入 C++ 依赖与运维复杂度 | 后置（需要 compaction 时评估） |
| 对象存储（分层） | 长保留成本低 | 延迟高、需要本地缓存层 | 8B_05 之后 |

## 4. 第三层：可靠性原语对比 <a id="matrix"></a>

| 维度 | 本地 Outbox | 事务消息 | CDC / 日志尾随 | 直接发布 |
| --- | --- | --- | --- | --- |
| 原子性（库↔MQ） | 强（同库同事务） | 强（半消息 + 回查） | 强（读事务日志） | **无**（dual-write） |
| 事件账本 | **有** | 无 | 有（broker retention） | 无 |
| 重放 | **有** | 依赖 broker 保留期 | 有（位点重放） | 无 |
| 死信看板 | **有** | 依赖 broker / 消费方 | 依赖消费方 | 无 |
| Broker 绑定 | 不绑 | **绑具体 broker** | 绑数据库方言 | 不绑 |
| 额外组件 | outbox 表 + relay | 无表 / 无 relay | Debezium / 自研连接器 | 无 |
| 三库兼容 | 好（纯 SQLAlchemy） | 与库无关 | **差**（达梦无 Debezium） | 与库无关 |
| 本地开发（SQLite） | 可验证 | 需真 broker | **不可验证** | 可验证 |
| 审计适用性 | **好** | 业务 / 字段好；操作登录需暂存 | 需转换层 | **不可** |
| 在 L3 中的角色 | **业务侧可靠入账**（保留） | 可选替代形态（后置） | outbox connector（后置） | 显式 best-effort 选项 |

## 5. 场景映射 <a id="scenario"></a>

| 场景 | 首要目标 | 原语 | 在 L3 中的落点 |
| --- | --- | --- | --- |
| 业务事件（订单 / 用户 / 角色变更） | 不丢、可重放 | **Outbox** | 业务库 outbox → msg relay |
| 字段级审计（业务事务内捕获） | 不丢、可查 | **Outbox** | 同上 |
| 操作日志（请求后发射） | 不丢、可查 | **Outbox** | 同上 |
| 登录日志（认证后发射） | 不丢、可查 | **Outbox** | 同上 |
| 跨服务写（权限保存等） | 强一致 | **TM + XA** | 不经消息 |
| 通知 / 指标 / 缓存失效 | 尽力而为 | **直接发布** | msg `acks=0` |
| 搜索索引同步 | 最终一致、可重建 | 直接发布 / CDC | msg 订阅 + 重建 |

> 关键区分：**跨服务写**不是事件投递问题，不能用 outbox 或事务消息替代 TM + XA；**事件投递**也不该用 XA 硬扛（MQ 不参加 XA）。

## 6. 原语层路线（保留以供回滚判断） <a id="options"></a>

| 路线 | 做法 | 现状 |
| --- | --- | --- |
| A 保留 Outbox，修隔离 | 表名参数化 / 加 `producer` 列 + 补行锁租约 | **已作为 L3 过渡形态保留** |
| B 事务消息替代业务事件 | 走 broker 半消息 + 回查 | 后置（8B_04 评估） |
| C 全量事务消息（含操作 / 登录审计） | 三类事件全走事务消息 | **不建议**：本质是 outbox 换名，还重排审计链路 |
| D CDC | Debezium / 自研连接器尾随 | 后置（仅 outbox connector 形态） |
| E 直接发布 | dual-write + 重试 | 仅 best-effort 场景 |
| **F 自研消息平台 L3** | msg 产品承载事件 + RPC + 运维 | **已选**（08B） |

## 7. 已定结论与推翻条件 <a id="decision"></a>

### 7.1 已定结论（2026-11）

1. 平台形态：**自研 L3**，新建 `msg` 产品仓与独立 08B 阶段。
2. 传输：**HTTP/2（h2c）+ MessagePack**，先 PoC 验证再全量。
3. 部署：**单服务多域**（broker / rpc / console / admin），后续按需拆。
4. 可靠性：**至少一次 + 消费端幂等**为默认；outbox 适配优先，事务消息后置。
5. 06_02（字段级审计）：**暂停**，等 8B 结论后恢复，避免在即将替换的链路上加码。

### 7.2 什么情况下应该推翻

| 触发条件 | 说明 | 应对 |
| --- | --- | --- |
| 8B_01 PoC 未达基准 | 吞吐 / 延迟没有明显优于 HTTP/1.1+JSON | 回到「只换 RPC、保留 RocketMQ」的局部方案 |
| 自研可靠性无法保证 | 崩溃恢复、复制反复出数据丢失 | 退回开源自建（RocketMQ / Kafka），保留适配层 |
| 运维成本失控 | 单人无法维护 | 云服务或托管版；适配层保证可切换 |
| 业务规模远低于预期 | 消息量小，自研性价比低 | 冻结 8B，保留现有 outbox |
| 团队扩充、引入专职中间件 | 有能力做 L3 全量 | 继续，但需补复制与多租户设计评审 |

**推翻不等于失败**：适配层（`EventPublisher` / `BaseServiceClient`）的存在就是为了让「换实现」不牵连业务代码。这也是为什么选型时先把端口定好，再选实现。

## 8. 与既有架构口径的衔接 <a id="alignment"></a>

| 既有口径 | 本专题的关系 |
| --- | --- |
| 平台《架构设计 · 服务间通信与一致性》：本地事务 + Outbox + 幂等为**事件基线** | 基线不变；L3 只是把「投递实现」从 RocketMQ 换成 msg，**基线语义不动** |
| 平台《架构设计 · 事件总线》：事件契约、分区有序、消费组、死信 | msg 需对齐这套契约与语义，不另造一套命名 |
| 平台《微服务演进规划》：产品服务经产品声明接入 | msg 按同一机制接入（`deploy/registry/msg.toml`） |
| 平台《分布式事务 · 选型对比》：跨服务写走 TM + XA | 与本专题不冲突：写走 XA，事件走 msg |
| 平台《01_01 事件总线》：outbox 多实例无行锁为开放项 | L3 过渡期仍需补行锁 / 租约；平台化后由 msg 位点取代 |
