> **定位**：本页把「消息与事件驱动」讨论中最容易被说错、传错的结论集中核对。分两段：**原语层**（Outbox / 事务消息 / CDC / XA 的混淆）与**平台层**（自研 broker 相关的低估与误判）。用途是**在讨论中被反驳时能落到事实**。

## 1. 原语层误区 <a id="myths"></a>

| # | 流行说法 | 事实 | 依据 |
| --- | --- | --- | --- |
| 1 | 「Outbox 要求一库一服务」 | **错**。只要求 outbox 表与业务表**同库、同一本地事务**；多服务共库可用「每服务表名」或 `producer` 列隔离 | microservices.io / Debezium 原文均无此要求 |
| 2 | 「事务消息 = 恰好一次」 | **错**。仍是至少一次；只是「本地事务 + 消息可见性」原子，消费端仍需幂等 | RocketMQ 事务消息文档 |
| 3 | 「CDC 万能，什么库都能接」 | **错**。达梦无官方 Debezium connector；三库日志格式差异大；SQLite 无 CDC | 《[微服务 · 12 选型对比](../微服务/12_微服务_选型对比.md)》待实测 |
| 4 | 「上了 XA，事件就可靠了」 | **错**。XA 覆盖数据库之间；MQ 通常不参加 XA。库↔MQ 仍需 outbox 或事务消息 | [17 直接发布与补偿](17_事件驱动_直接发布与补偿.md) §5 |
| 5 | 「共库就不能用 Outbox」 | **错**。共库只需给每个服务独立表名或加 `producer` 列 | [14 事务性发件箱](14_事件驱动_事务性发件箱.md) §2.2 |
| 6 | 「Outbox 就是多一张表」 | **错**。表只是账本；还需 relay、幂等消费、死信、重放、积压监控 | 01_01 实现包含投递器 / 幂等 / 死信 / 指标 |
| 7 | 「直接发 MQ + 重试就够了」 | **错**。重试解决不了「提交后崩溃」与「发送超时语义不明」 | [17 直接发布与补偿](17_事件驱动_直接发布与补偿.md) §3 |
| 8 | 「事务消息不需要本地结果」 | **错**。回查必须能查到持久化的本地事务结果 | [15 事务消息](15_事件驱动_事务消息.md) §4 |
| 9 | 「Outbox 保证全局有序」 | **错**。只保证**同聚合**有序（`aggregate_key`） | 表结构 `(aggregate_key, id)` 索引 |
| 10 | 「MQ 有事务消息了，Outbox 就过时了」 | **不准确**。事务消息省表 / relay，但绑 broker、无账本；Outbox 可移植、可重放、可取证 | [18 选型对比](18_事件驱动_选型对比（BMS）.md) |
| 11 | 「事务消息不需要消费端幂等」 | **错**。至少一次投递不变 | RocketMQ 文档；消费幂等表 |
| 12 | 「CDC 不侵入业务，所以没有成本」 | **错**。成本在连接器、位点、schema 演进、三库差异与运维 | [16 CDC 与日志尾随](16_事件驱动_CDC与日志尾随.md) §7 |
| 13 | 「共库就是分布式单体，所以什么都不能做」 | **半对**。共库损害独立部署与数据所有权，但 Outbox 模式本身不因共库失效 | 本篇 #1 / #5 |
| 14 | 「事务消息可以替代跨服务写的一致性」 | **错**。它只保证「本地事务 ↔ 消息可见」；跨服务写仍要 TM + XA | 《[分布式事务 · 总览](../分布式事务/01_分布式事务_总览.md)》 |

## 2. 平台层误区 <a id="platform"></a>

自研 broker 最常见的失误是**低估工作量与故障面**。以下十条几乎每个自研项目都会踩：

| # | 流行说法 | 事实 | 后果 |
| --- | --- | --- | --- |
| 1 | 「broker 就是个队列，几千行就够」 | **错**。可用的 broker = 存储 + 索引 + 分段 + 恢复 + 消费组 + 位点 + 背压 + 复制 + 指标，每个部件都有独立的故障模式 | 做出「demo 能跑、生产不敢用」的半成品 |
| 2 | 「先不做持久化，内存队列够用」 | **错**。没有持久化就没有「不丢」；重启即丢全部积压 | 一旦崩溃，业务方永久失去信任 |
| 3 | 「HTTP/2 一定比 HTTP/1.1 快」 | **不一定**。多路复用与 HPACK 在**长连接、多并发**下才显著；单连接小消息场景可能因分帧开销更慢 | 基准结论与预期相反，方案被质疑 |
| 4 | 「加了压缩就一定省带宽」 | **错**。单条小消息压缩后常常更大；压缩要按批 | 吞吐下降、CPU 上升 |
| 5 | 「分区越多吞吐越高」 | **错**。分区多会增加文件句柄、复制开销、再均衡耗时与元数据压力；且分区只能增不能减 | 扩容后性能反而下降 |
| 6 | 「消费组再均衡是无感的」 | **错**。eager 再均衡会让整组停摆数秒到数分钟；处理慢还会引发「被踢 → 再均衡 → 更慢」的风暴 | 高峰期消费停摆 |
| 7 | 「fsync 每条最安全」 | **半对**。只保证落到本机磁盘；磁盘坏、机器挂照样丢。持久性 = fsync + 副本确认 | 误以为已持久，未做副本 |
| 8 | 「至少一次 + 幂等就是恰好一次」 | **对，但要写对幂等键**。用 `message_id` 做幂等键，重放时会重复处理；应用业务唯一键 | 重放导致重复副作用 |
| 9 | 「自研就不用管运维」 | **错**。自研意味着管理台、指标、告警、重放工具全要自己做，且必须**先于功能**上线 | 出问题无从定位，只能重启 |
| 10 | 「复制和高可用最后再加就行」 | **部分对**。功能可以先单机，但**存储格式与协议要预留复制所需字段**（term / offset / 校验），否则后期要重做格式 | 8B_05 阶段推倒重来 |

## 3. 术语混淆速查 <a id="terms"></a>

### 3.1 可靠性

| 名词 | 一句话 | 容易混淆的点 |
| --- | --- | --- |
| Outbox | 业务库里的待发事件账本 + relay | 不是「消息队列」，也不是「可靠投递的全部」 |
| Inbox | 消费端的已处理事件账本（幂等表） | 与 Outbox 对称；BMS 用 `sys_event_consumed` |
| 事务消息 | 「半消息 + 本地事务 + 回查」 | 不是 XA；不覆盖跨服务写 |
| XA / 2PC | 数据库之间的两阶段提交 | MQ 通常不参加；不能替代事件可靠性 |
| CDC | 读数据库事务日志捕获变更 | 常用来替代 outbox 的 **relay**，不是替代表 |
| 至少一次 | 可能重复、不会丢 | 不等于「恰好一次」 |
| 效果一次 | 至少一次 + 幂等去重 | 业务效果一次，不是协议保证 |
| 事件账本 | 可查、可重放、可取证的事件记录 | 事务消息默认没有；Outbox 有 |

### 3.2 平台机制

| 名词 | 一句话 | 容易混淆的点 |
| --- | --- | --- |
| LEO | Log End Offset，日志末尾位置 | 不是「已提交位点」；未复制的部分不算已提交 |
| HW | High Watermark，已提交位点 | 消费者只能读到 HW 之前；HW ≤ LEO |
| ISR | 与 leader 保持同步的副本集合 | 不是「所有副本」；落后太多的会被踢出 ISR |
| Leader Epoch / Term | 领导者任期号 | 用于拒绝旧 leader 的过期写入，不是「版本号」 |
| Rebalance | 消费组内分区重新分配 | 不区分 eager / cooperative 会说错停摆范围 |
| Compaction | 按 key 保留最新值 | 不是「压缩」（compression），两者完全不同 |
| Backpressure | 下游处理不过来时向上游传导减速 | 不是「限流」的同义词；限流是主动拒绝，背压是传导 |
| 分段（Segment） | 追加日志按大小 / 时间切分的文件 | 不是「分片（shard）」；分段是单机内文件单位 |

## 4. 自研消息平台立项自检 12 问 <a id="checklist"></a>

1. **目标是什么**：替换 RocketMQ？解决 RPC 性能？摆脱 outbox 表名？还是三者都要？
2. **能接受多长周期**？L3 成熟至少 6~9 个月，期间旧链路不能停。
3. **可靠性谁背书**？丢一条审计事件，能否接受？谁能定位根因？
4. **复制与故障切换怎么做**？单机先行的同时，存储格式是否预留了 term / 副本位点？
5. **消费组与位点**：位点存哪、怎么恢复、重放怎么限流？
6. **背压加在哪几层**？内存、磁盘、连接、消费端是否都有阈值？
7. **协议怎么演进**？老客户端遇到新字段会不会崩？
8. **运维面**：指标、日志、追踪、管理台、死信重放，谁做、先做哪个？
9. **多租户与配额**：租户隔离是逻辑还是物理？超限怎么拒绝？
10. **迁移与回滚**：能否按域切换？出问题几分钟能切回？
11. **基准怎么做**？与谁比、比什么、达到多少算通过？
12. **谁来维护**？单人兼职下，运维窗口与响应时间是否可接受？

> 12 问里若有 4 个以上答不上来，先做 [20 项目评估](20_事件驱动_项目评估（BMS）.md) 与 8B_01 PoC，不要直接替换生产链路。

## 5. 一句话总结 <a id="summary"></a>

> **原语层的问题往往不是「模式错了」，而是「实现假设没被参数化」；平台层的问题往往不是「技术不可行」，而是「工作量与故障面被低估」。** 前者改实现，后者先做 PoC 与运维设计。
