> **定位**：本页把「事件可靠性」讨论中最容易被说错、传错的结论集中核对。用途是**在讨论中被反驳时能落到事实**，以及避免把 outbox / 事务消息 / CDC / XA 混为一谈。

## 1. 认知误区核对 <a id="myths"></a>

| # | 流行说法 | 事实 | 后果 / 依据 |
| --- | --- | --- | --- |
| 1 | 「Outbox 要求一库一服务」 | **错**。只要求 outbox 表与业务表**同库、同一本地事务**；多服务共库可用「每服务表名」或 `producer` 列隔离 | microservices.io / Debezium 原文均无「一库一服务」要求 |
| 2 | 「事务消息 = 恰好一次」 | **错**。仍是至少一次；只是「本地事务 + 消息可见性」原子，消费端仍需幂等 | RocketMQ 事务消息文档；消费幂等是前提 |
| 3 | 「CDC 万能，什么库都能接」 | **错**。达梦无官方 Debezium connector；三库日志格式差异大；SQLite 无 CDC | 《[微服务 · 12 选型对比](../微服务/12_微服务_选型对比.md)》待实测 #5 |
| 4 | 「上了 XA，事件就可靠了」 | **错**。XA 覆盖数据库之间；MQ 通常不参加 XA。库↔MQ 仍需 outbox 或事务消息 | [05 直接发布与补偿](05_事件驱动_直接发布与补偿.md) §5 |
| 5 | 「共库就不能用 Outbox」 | **错**。共库只需给每个服务独立 outbox 表名或加 `producer` 列；模式本身不禁止共库 | [02 事务性发件箱](02_事件驱动_事务性发件箱.md) §2.2 |
| 6 | 「Outbox 就是多一张表」 | **错**。表只是账本；还需要 relay、幂等消费、死信、重放、积压监控 | 01_01 实现包含投递器 / 幂等 / 死信 / 指标 |
| 7 | 「直接发 MQ + 重试就够了」 | **错**。重试解决不了「提交后崩溃」与「发送超时语义不明」；没有账本无法对账 | [05 直接发布与补偿](05_事件驱动_直接发布与补偿.md) §3 |
| 8 | 「事务消息不需要本地结果」 | **错**。回查必须能查到持久化的本地事务结果；否则 broker 无法判定提交/回滚 | [03 事务消息](03_事件驱动_事务消息.md) §4 |
| 9 | 「Outbox 保证全局有序」 | **错**。只保证**同聚合**有序（`aggregate_key`）；跨聚合不承诺 | 表结构 `(aggregate_key, id)` 索引 |
| 10 | 「MQ 有事务消息了，Outbox 就过时了」 | **不准确**。两者取舍不同：事务消息省表/relay，但绑 broker、无账本；Outbox 可移植、可重放、可取证 | [06 选型对比](06_事件驱动_选型对比（BMS）.md) |
| 11 | 「事务消息不需要消费端幂等」 | **错**。至少一次投递不变；重复消息仍会发生 | RocketMQ 文档；消费幂等表 |
| 12 | 「CDC 不侵入业务，所以没有成本」 | **错**。成本在连接器、位点、schema 演进、三库差异与运维 | [04 CDC 与日志尾随](04_事件驱动_CDC与日志尾随.md) §4 |
| 13 | 「共库就是分布式单体，所以什么都不能做」 | **半对**。共库确实损害独立部署与数据所有权，但 Outbox 模式本身不因共库失效；应解决隔离，而不是否定模式 | 微服务数据所有权口径；本篇 #1 / #5 |
| 14 | 「事务消息可以替代跨服务写的一致性」 | **错**。事务消息只保证「本地事务 ↔ 消息可见」；跨服务写仍要 TM + XA 或单库收敛 | 《[分布式事务 · 总览](../分布式事务/01_分布式事务_总览.md)》 |

## 2. 术语混淆速查 <a id="terms"></a>

| 名词 | 一句话 | 容易混淆的点 |
| --- | --- | --- |
| Outbox | 业务库里的待发事件账本 + relay | 不是「消息队列」，也不是「可靠投递的全部」 |
| Inbox | 消费端的已处理事件账本（幂等表） | 与 Outbox 对称；BMS 用 `sys_event_consumed` |
| 事务消息 | MQ 原生的「半消息 + 本地事务 + 回查」 | 不是 XA；不覆盖跨服务写 |
| XA / 2PC | 数据库之间的两阶段提交 | MQ 通常不参加；不能替代事件可靠性 |
| CDC | 读数据库事务日志捕获变更 | 常用来替代 outbox 的 **relay**，不是替代 outbox 表 |
| 至少一次 | 可能重复、不会丢 | 不等于「恰好一次」 |
| 效果一次 | 至少一次 + 幂等去重 | 业务效果一次，不是协议保证 |
| 事件账本 | 可查、可重放、可取证的事件记录 | 事务消息默认没有；Outbox 有 |

## 3. 废除 Outbox 前的自检 10 问 <a id="checklist"></a>

1. **目标是什么**：去表？去 relay？去 broker 绑定？还是解决共库撞名？
2. **能接受绑定 RocketMQ 吗**？未来是否可能换 Kafka / 其他 broker？
3. **还需要事件账本 / 重放 / 取证吗**？谁在用 `replay` / 死信看板？
4. **操作 / 登录审计怎么保证不丢**？它们没有业务行可回查。
5. **事务回查依据是什么**？按什么键能查到「本地事务已提交」？
6. **多实例 / 多租户 / 多库**怎么处理？事务消息 producer 与回查是否按库隔离？
7. **迁移期怎么回滚**？能否用配置切回 outbox？
8. **真机 PoC 做了吗**？提交 / 回滚 / 崩溃回查 / 重复投递四条路径。
9. **运维谁负责**？半消息堆积、回查失败、事务超时谁看？
10. **收益能量化吗**？省下的表 / relay 成本，是否大于迁移 + 运维 + 失去账本的成本？

> 10 问里若有 3 个以上答不上来，先做 [08 项目评估](08_事件驱动_项目评估（BMS）.md) 与 PoC，不要直接动 01_01 / 06_01 的生产链路。

## 4. 一句话总结 <a id="summary"></a>

> **Outbox 的问题往往不是「模式错了」，而是「实现假设没被参数化」。** 在决定废除它之前，先确认你要解决的是「模式缺陷」还是「实现缺陷」；前者才需要换机制，后者只需要改实现。
