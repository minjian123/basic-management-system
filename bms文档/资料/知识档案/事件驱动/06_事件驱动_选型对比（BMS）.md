## 1. 对比矩阵 <a id="matrix"></a>

| 维度 | 本地 Outbox | RocketMQ 事务消息 | CDC / 日志尾随 | 直接发布 |
| --- | --- | --- | --- | --- |
| 原子性（库↔MQ） | 强（同库同事务） | 强（半消息 + 回查） | 强（读事务日志） | **无**（dual-write） |
| 事件账本 | **有** | 无 | 有（Kafka retention） | 无 |
| 重放 | **有**（`replay`） | 依赖 MQ 保留期 | 有（位点重放） | 无 |
| 死信看板 | **有**（`sys_event_dead_letter`） | 依赖 MQ / 消费方 | 依赖消费方 | 无 |
| Broker 绑定 | 不绑 | **绑 RocketMQ** | 绑数据库方言 | 不绑 |
| 额外组件 | outbox 表 + relay | 无表 / 无 relay | Debezium / Kafka Connect 或自研 | 无 |
| 三库兼容 | 好（纯 SQLAlchemy） | 与库无关（MQ 侧） | **差**（达梦无 Debezium） | 与库无关 |
| 本地开发（SQLite） | 可验证 | 需真 broker | **不可验证** | 可验证 |
| 运维面 | 表积压、relay 延迟、死信 | 半消息堆积、回查失败 | 连接器、位点、schema 演进 | 无（但会丢） |
| 改造面 | 已落地（01_01） | 中（实现 + 回查 + 迁移） | 大（新基础设施） | 小 |
| 审计适用性 | **好**（操作 / 登录 / 字段全适用） | 业务 / 字段好；操作登录需暂存 | 需转换层 | **不可** |
| 长期成本 | 低（可控） | 中（绑 broker、无账本） | 高（单人运维） | 低（但业务风险高） |

## 2. 场景映射 <a id="scenario"></a>

| 场景 | 首要目标 | 推荐 | 备选 |
| --- | --- | --- | --- |
| 业务事件（订单 / 用户 / 角色变更） | 不丢、可重放 | **Outbox** 或 **事务消息** | CDC（已有 Kafka 时） |
| 字段级审计（业务事务内捕获） | 不丢、可查 | **Outbox** 或 **事务消息** | — |
| 操作日志（请求后发射） | 不丢、可查 | **Outbox** | 极简审计暂存 + 事务消息 |
| 登录日志（认证后发射） | 不丢、可查 | **Outbox** | 极简审计暂存 + 事务消息 |
| 跨服务写（权限保存等） | 强一致 | **TM + XA** | 单库收敛 |
| 通知 / 指标 / 缓存失效 | 尽力而为 | **直接发布 + 重试** | Outbox（若要求不丢） |
| 搜索索引同步 | 最终一致、可重建 | 直接发布 / CDC | Outbox |

> 关键区分：**跨服务写**不是事件投递问题，不能用 outbox 或事务消息替代 TM + XA；**事件投递**也不该用 XA 硬扛（MQ 不参加 XA）。

## 3. 三条候选路线 <a id="options"></a>

### 3.1 路线 A：保留 Outbox，修隔离

- 做法：保留 `sys_outbox` + relay；把基础设施表名参数化（`platform_outbox` / `audit_outbox`）或加 `producer` 列；补齐多实例行锁 / 租约。
- 优点：改动最小；保留账本、重放、死信、broker 可移植；操作 / 登录审计无需改链路。
- 缺点：没有「废除 outbox」；表与 relay 仍在。
- 适用：重视账本 / 重放 / 多 broker 可移植；不想大改事件基座。

### 3.2 路线 B：事务消息替代业务 + 字段审计，操作 / 登录审计保留极简暂存

- 做法：业务事件与字段级审计改走 RocketMQ 事务消息（业务行 / 版本号作为回查依据）；操作 / 登录审计保留一张**只服务审计**的暂存表 + 极简投递（不再作为通用 outbox）。
- 优点：通用事件真正去 outbox 表 / relay；审计不丢；绑定 RocketMQ 可接受。
- 缺点：仍保留一张审计专用表；需实现事务消息 + 回查；需真机验证。
- 适用：目标明确是「废除通用 outbox」，且能接受 RocketMQ 绑定。

### 3.3 路线 C：全量事务消息（含操作 / 登录审计）

- 做法：三类事件全走事务消息；操作 / 登录审计改为「先落审计库 → 本地事务提交 → 提交消息」。
- 优点：表面上去掉所有 outbox 表。
- 缺点：审计库表本身成为回查依据，本质仍是 outbox 换名；06_01 的「响应后发射」要重排；链路风险最高。
- 适用：不建议在本阶段采用。

### 3.4 路线 D：CDC

- 做法：Debezium / Kafka Connect 尾随 outbox 或业务表。
- 优点：近实时、可重放、业务无侵入。
- 缺点：达梦无 connector、三库差异、运维重、schema 耦合。
- 适用：已有 Kafka / Debezium 基础设施、多语言团队；**不适合当前单人兼职 + 三库 + SQLite 开发**。

### 3.5 路线 E：直接发布

- 只适用于指标、缓存失效、非关键通知等 best-effort 场景。
- 审计与业务事件**不可用**。

## 4. 推荐（待确认） <a id="recommend"></a>

> 以下为**知识档案层面的建议**，不是架构定案；最终以专项设计与用户拍板为准。

1. **若目标是「修掉共用库撞表 / 通用机制绑死表名」**：选 **路线 A**。Outbox 模式本身没有错，错的是表名写死；参数化即可，代价远低于换机制。
2. **若目标是「废除通用 outbox 表与 relay」**：选 **路线 B**，并接受：
   - 绑定 RocketMQ；
   - 失去事件账本 / 重放（或另建只读归档）；
   - 操作 / 登录审计保留一张极简暂存表（否则会丢审计）。
3. **不建议路线 C**：它只是把 outbox 换个名字，还重排了审计链路。
4. **不建议路线 D / E**：当前基础设施与团队规模不匹配；E 不能用于审计。
5. **无论选哪条，先做 PoC**：真机验证事务消息的提交 / 回滚 / 崩溃回查，再决定是否迁移。

## 5. 触发条件 <a id="trigger"></a>

### 5.1 从 Outbox 切到事务消息的触发条件（须同时成立）

1. 明确接受绑定 RocketMQ，不再要求多 broker 可移植；
2. 不再需要「事件账本 / 按条件重放 / 死信看板」（或已另建替代）；
3. 操作 / 登录审计已有暂存方案，或接受 best-effort；
4. 真机 PoC 通过（提交 / 回滚 / 回查 / 重复投递）；
5. 迁移期有回滚开关（配置切回 outbox）。

### 5.2 保留 Outbox 的触发条件（任一成立）

1. 需要事件账本 / 重放 / 取证；
2. 需要多 broker 可移植（Kafka / RocketMQ 切换）；
3. 操作 / 登录审计必须不丢且不想改链路；
4. 不想承担事务消息回查与 broker 绑定的运维成本。
