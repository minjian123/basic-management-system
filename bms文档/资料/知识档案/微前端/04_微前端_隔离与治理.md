## 1. 技术概述 <a id="overview"></a>

微前端把「一个应用」变成「多个构建产物共享一个浏览器运行时」，于是出现四类必须治理的问题：

| 治理面 | 问题 | 关键手段 |
| --- | --- | --- |
| 运行时隔离 | 全局变量、原型链、定时器、事件互相污染 | JS 沙箱 / iframe 原生隔离 |
| 样式隔离 | CSS 选择器互相命中、弹窗样式丢失 | 命名前缀 / Scoped / Shadow DOM / 选择器改写 |
| 依赖治理 | 运行时库重复打包、版本偏斜 | `shared` 声明、singleton、严格的 CI 双端验证 |
| 交付治理 | 独立发版后的兼容、灰度、回退与可观测 | 版本清单、契约兼容、灰度 / 蓝绿、按模块监控 |

> 行业共识：**微前端失败多因治理缺失，而非框架选错**（「微前端无政府状态」）。
> 本页按上述四层给出做法与坑。

## 2. JS 隔离 <a id="js"></a>

| 方式 | 原理 | 优点 | 局限 |
| --- | --- | --- | --- |
| Proxy 沙箱（qiankun 默认） | 为子应用创建 `fakeWindow`，拦截全局读写 | 多实例安全、性能较好 | 依赖 Proxy；部分隐式全局访问仍可能泄漏 |
| 快照沙箱（qiankun 降级） | 激活时快照 `window`、卸载时回滚 | 兼容老浏览器 | 仅支持单实例；切换有开销 |
| with + 作用域隔离（micro-app 等） | 包装执行作用域 | 实现简单 | 对动态代码与全局副作用防护有限 |
| **iframe 原生隔离**（wujie） | 子应用 JS 在独立 iframe 上下文执行，DOM 操作被代理到主文档 | 隔离最彻底、无额外沙箱成本 | 通信与调试链路更长；代理层有实现复杂度 |

**必须遵守**：
- 不依赖「子应用会清理全局」的假设——定时器、事件监听、样式注入都要随卸载清理（或由沙箱强制）；
- 对 `window` 上的隐式全局（第三方库的 `window.xxx`）做白名单与监控；
- 若做微前端，**优先让每个模块成为独立路由级应用**（生命周期明确），少做同页多模块。

## 3. 样式隔离 <a id="css"></a>

| 策略 | 做法 | 效果与风险 |
| --- | --- | --- |
| 命名前缀 / BEM | 团队前缀 + 约定（micro-frontends.org 的「Team Prefixes」） | 简单、零成本；靠纪律，易被绕过 |
| CSS Modules / `<style scoped>` | 编译期生成唯一类名 | 推荐默认（Vue/React 生态均支持） |
| 选择器改写（qiankun `experimentalStyleIsolation`） | 运行时给规则加 `[data-qiankun-app]` 前缀 | 基本隔离；动态插入样式可能漏改 |
| Shadow DOM（qiankun `strictStyleIsolation`、micro-app 类 Shadow DOM） | 模块包进 shadow root，样式与 DOM 封装 | 隔离强；**弹窗/下拉挂到 body 会丢样式**，可继承属性（字体、颜色变量）穿透，部分 UI 库不兼容 |
| iframe（wujie/原生） | 文档级隔离 | 最彻底；弹窗只能在模块内打开 |

**工程建议**：**前缀 + Scoped 为默认**；只在需要对抗不可控样式（嵌入式第三方）时局部使用 Shadow DOM；
设计令牌（CSS 变量）走「可继承」通道，保证视觉一致（与《[插件化架构 · 14 前端插件化](../插件化架构/14_插件化架构_前端插件化.md)》的本项目机制一致）。

## 4. 依赖共享与版本偏斜 <a id="deps"></a>

**核心事实**：版本相同≠只有一份。只有当**双方都声明 shared**（且命中同一 share scope）时，运行时才会协商复用；
否则各自打包一份。对系统级状态的状态型依赖（React、Vue、Router、样式运行时）出现两份会导致：

- React hooks dispatcher 为空 / Context 跨实例不可见 / 路由历史各持一份 / 样式重复或缺失注入。

**治理清单**：

1. 状态类依赖一律 `singleton: true`，`requiredVersion` 从 `package.json` 读取而非手写；
2. 非生产环境开启 `strictVersion`，把版本不兼容从「运行时警告」升级为「CI 失败」；
3. 子路径导入（`react-dom/client` 等）必须显式声明，否则绕过共享作用域；
4. 传递依赖（第三方组件引入的 peer）也参与协商——升级主版本属**团队间契约**，需协调发布；
5. 开发态（Vite dev 非打包）与生产构建行为不同，**共享结论必须用构建产物验证**；
6. 版本范围重叠「纸上成立、实际无解」的情况（`^18.3` vs `~18.2`）要在 CI 用双端组合测试兜底。

> 原则与后端「契约兼容」一致：**框架大版本是跨团队契约**，升级需要计划而非独立行动。

## 5. 路由与通信 <a id="routing"></a>

| 主题 | 建议 |
| --- | --- |
| 路由归属 | 宿主负责顶层路由与加载（薄壳）；模块内部路由自管，避免双路由状态 |
| 路由同步 | 明确 URL 语义（深链直达）；刷新后状态可恢复（保活/单例模式要有退出策略） |
| 通信方式 | 属性/Props（单向输入）、自定义事件/事件总线（广播）、`postMessage`（iframe） |
| **反模式** | 跨模块**共享可变全局状态**（全局 store/全局变量）——等价于后端「共享数据库」，使模块必须同步升级 |
| 数据获取 | 由模块自己的数据层或 BFF 负责；不要把聚合逻辑堆在宿主 |
| 通信契约 | 事件名/载荷进契约（版本化），与后端事件命名同样对待（本项目已有 `{域}.{动作}` 规范） |

Mezzalira 的启发式（识别微前端与组件的差别）：**对宿主暴露的 API 保持 1~2 个**、模块**自持上下文与状态**、
不为复用而设计、**粒度宁粗勿细**（产品前端模块过多＝分布式单体前端）。

## 6. 部署、版本与灰度 <a id="deploy"></a>

- **独立流水线**：每个模块自带构建、测试与部署（含契约测试）；
- **版本清单/发现**：宿主需要一个「模块 → 版本/地址」的发现机制（清单文件或发现服务），以支持无重建的版本切换；
- **灰度/蓝绿/回滚**：模块可独立灰度（按用户/租户/比例），失败可秒级回滚——这是微前端相对单体最实在的收益；
- **兼容承诺**：宿主与模块的契约（注入的上下文、暴露的事件）只增不删；破坏性变更走版本与公告（与后端接口契约同源）。

## 7. 可观测性与测试 <a id="observability"></a>

| 面 | 做法 |
| --- | --- |
| 错误归因 | 统一错误上报（Sentry 等）并按模块打标；sourcemap 统一托管 |
| 性能 | 按模块采集 Web Vitals / 资源体积；把「体积预算」纳入 CI |
| 关键链路 | 跨模块 E2E（Playwright）覆盖登录→主流程；模块单测覆盖各自逻辑 |
| 契约 | 契约测试 + 版本组合冒烟（新模块版本 × 当前宿主） |

> **本项目落地（阶段五 `03_03`，2026-09-22）**：加载失败 / 超时（10s，整个 `load()` 计时）/ 初始化异常**降级 UI**（带模块名与版本，不白屏）+ **手动单模块重试**；错误上报统一经总基类通道（`configureBase` 注入 sink）并**带模块名与版本**、按模块聚合（加载 / 挂载 / 渲染三面）；加载耗时拆 `resolve` / `setup` / `mount` 三段 + 首屏渲染耗时按模块采集；产物体积独立计量（入口闭包口径）并随**发布记录**留痕、CI 汇总；**Web Vitals（LCP / CLS / INP）按活动模块归属**；模块产物**外部 sourcemap** 随发布按版本归档、发布前强校验。观测能力经能力域基类 `BaseModuleTelemetry` + 插件基类 `BaseModuleReporter` 入链；真实后端上报通道（Sentry 类）与按模块 SLO / 告警阈值随可观测阶段。

## 8. 治理机制（Fitness Function） <a id="governance"></a>

| 机制 | 说明 |
| --- | --- |
| 设计系统 | 统一令牌与基础组件（只共享「哑组件」，不共享业务组件，避免耦合） |
| 体积预算 | 每次 PR 构建产物对比预算，超限即失败（Mezzalira：最有效的治理之一） |
| 依赖白名单 | 架构测试断言模块依赖范围（如只允许共享库 + 设计系统） |
| 模板与脚手架 | 统一工程基线，降低接入成本与漂移 |
| 平台团队 | 宿主外壳、发现机制、CI 模板、可观测由平台团队负责，业务模块自治 |
| 技术选型边界 | 允许有限异构，禁止「微前端无政府状态」（多框架同页、任意依赖） |

## 9. 在本项目中的用途 <a id="usage"></a>

| 领域 | 本项目现状 | 说明 |
| --- | --- | --- |
| 运行时隔离 | 运行时组合（MF）已引入；隔离以**约定 + 机器护栏**落地（模块源码与产物双扫描面，含 fixture 拦截）；`Shadow DOM` / JS 沙箱**本期不引入** | 触发条件（异构技术栈 / 不可信代码 / 同页多模块强隔离 / 第三方全局冲突 / 合规要求）与代价见阶段五 `03_01`《隔离增强评估》 |
| 交付治理（版本清单 / 发布 / 回滚） | **清单唯一来源**（名称 / 入口 / 版本 / 加载形态 / 可见性）与**版本发现**（清单 = 产物元数据 = 源码）落地；独立发布（三关强校验 → 产物按版本归档 → 清单指向）与**回滚**（清单版本回退、产物按版本保留）可执行；**契约版本双端校验**与发布**留痕**（JSON 真源 + Markdown 摘要）就位；灰度 / 蓝绿仅保留「按清单指向切换」 | 阶段五 `03_02` 落地（2026-09-22）；按用户 / 租户 / 比例分流与生产部署形态（静态托管 / CDN）随后续阶段 |
| 样式与令牌 | Element Plus/Vant + 主题令牌 + Scoped 风格；模块样式 scoped + 模块命名空间前缀 + 只消费 `--bms-*` 令牌（`themeTokens` 为模块令牌定义源） | 与设计令牌通道一致；隔离护栏覆盖模块源码与产物（2026-09-21 落地） |
| 依赖治理 | 单 `package-lock.json`（双端工程各自锁定） | 无版本偏斜问题；引入 MF 后需按 §4 治理 |
| 体积与性能 | 前端双端构建入 CI；性能随阶段十五/十六收口 | 可借鉴「体积预算」思路纳入 CI 前端检查 |
| 契约纪律 | OpenAPI 契约 + 类型生成 + 统一响应 | 与后端「契约即服务接口」的做法可平移到模块契约 |
| 监控 | 前端可观测**本机形态已落地**（`03_03`：失败兜底与超时 / 错误按模块归因 / 耗时与体积 / Web Vitals / sourcemap）；真实后端上报通道随阶段十三（Prometheus/Loki/…）与 Sentry 类工具按需 | 按模块归因与本机观测面板就位，后端通道接口（可替换上报实现 + 注册表）已预留 |

> 结论：本项目**当前无需**运行时隔离与版本偏斜治理；但「设计令牌、契约纪律、体积意识、按模块归因」
> 这四项是低成本且有益的准备，即使不引入微前端也值得做。
