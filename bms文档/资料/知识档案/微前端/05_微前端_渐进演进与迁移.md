## 1. 技术概述 <a id="overview"></a>

与后端一致：**渐进演进优于重写**。微前端的迁移不是「一次性换框架」，而是
「**先保留现有应用可用，再逐块把片段搬进（或搬出）组合层**」。两个方向都要能走：

- **正向**：单体前端 → 微前端（多团队独立交付、渐进替换旧栈）；
- **反向**：碎片化微前端 → 统一应用（Zalando 的教训：分散到一定规模后，统一栈的协作成本更低）。

## 2. 起点：先切分，再动手 <a id="slicing"></a>

Mezzalira 的「四支柱」：**识别（identify）→ 组合（compose）→ 编排（orchestrate）→ 通信（communicate）**。
落地前必须回答：

| 问题 | 做法 |
| --- | --- |
| 怎么切 | 按**业务域/用户任务**切（DDD 子域），不按技术层/组件切；宁粗勿细 |
| 看用户怎么用 | 分析真实路径与跳转关系（避免按产品经理假设切分） |
| 看组织怎么配 | 康威定律：片段边界要与团队边界一致（逆康威机动） |
| 边界规模 | 一个片段 = 一个团队能端到端负责的业务切片；**运行时片段 ≤ 5~8 个**为宜 |
| 技术前提 | 宿主外壳极薄（路由 + 组合 + 配置），业务知识一律在片段内 |

## 3. 迁移模式 <a id="patterns"></a>

| 模式 | 做法 | 适用 |
| --- | --- | --- |
| 宿主先行 | 先建薄壳（路由/布局/鉴权），新页面以片段接入 | 渐进替换的常规路径 |
| 新页面先行 | 新功能直接用新架构实现，旧页面暂不动 | 迁移窗口长、业务并行 |
| 旧栈包装 | 用 qiankun/wujie 等把旧页面作为片段挂入（尽量减少改造） | 旧系统不可大改时 |
| 分支抽象（前端版） | 页面组件内部做适配层，逐步切换实现 | 不引入运行时组合的单体内部演进 |
| 双跑校验 | 新片段与旧页面并行一段时间，指标对齐后再切流 | 高风险核心页面 |
| 反向统一（Zalando） | 从「每团队自管片段」收回到「统一平台 + 渲染器」 | 碎片化导致体验/协作成本过高时 |

> **迁移期的组合层（宿主/清单/代理）是必要成本**，它买的是可回退与可暂停——与后端迁移的「过渡期架构」同理。

## 4. 分阶段路线 <a id="phases"></a>

| 阶段 | 目标 | 关键交付 |
| --- | --- | --- |
| 0 准备 | 治理先行 | 设计系统与令牌、事件/属性契约、体积预算与架构检查、可观测（按片段归因） |
| 1 首个片段 | 选「不复杂也不简单」且 1~2 个月能上线的模块 | 一个端到端片段 + 独立流水线 + 灰度能力 |
| 2 建设平台 | 宿主、版本发现、CI 模板、契约测试 | 平台团队职责成型；片段接入成本显著下降 |
| 3 扩大范围 | 按优先级迁移（边缘/高频/旧栈优先） | 旧页面逐个下线；体验一致性评审常态化 |
| 4 收口 | 旧栈完全退役、治理固化为规则 | 体积/性能/一致性指标进入门禁 |

## 5. 灰度与回退 <a id="rollout"></a>

- **版本发现**：宿主从「片段版本清单/发现服务」取版本，支持不重建宿主切换片段版本（Mezzalira 与主流框架协作定义的 front-end discovery 思路）；
- **灰度策略**：按用户/租户/比例切流；片段可独立灰度与**秒级回滚**（微前端最实在的收益之一）；
- **蓝绿与特性开关**：片段级蓝绿 + 局部特性开关；避免「开关遍布所有片段」的隐性协作成本；
- **双跑校验**：新旧并行期比对指标（成功率、性能、错误率）后切流；
- **回退信号**：体验不一致投诉增加、片段间契约变更频繁、多片段发布需同步协调——即「分布式单体前端」征兆。

## 6. 与后端演进的协同 <a id="with-backend"></a>

- 微前端与后端微服务**不是绑定关系**：可只拆前端、只拆后端，或都不拆；
- 若后端走了「独立服务形态」（本项目《平台可扩展性规划》5.7），该服务的前端页面可作为**天然的第一个微前端片段**（边界与团队已经确定）；
- BFF 与片段的归属一致（前端团队拥有），避免再引入共享聚合层（见《[03 技术方案对比](03_微前端_技术方案对比.md)》§7）。

## 7. 在本项目中的用途 <a id="usage"></a>

已决策**引入微前端**（Module Federation，见《[06 项目评估](06_微前端_项目评估.md)》「讨论结论」节），落地顺序：

1. **阶段四 骨架起步**：宿主薄壳（布局 / 路由 / 片段加载器）+ 片段契约 + 设计令牌与组件契约可被片段复用；先补治理基座（体积预算已落地、OpenAPI 契约与按模块归因随阶段建设）；
2. **阶段五 运行时加载落地**：Module Federation + 片段清单 + shared 依赖 singleton；新业务页面按片段形态独立构建发布，**首个业务页面即首个片段样例**；平台页面与存量模块走构建期合并（过渡）；
3. **后续治理补齐**：隔离增强、依赖版本协商与双端 CI 验证、灰度 / 回退、按片段可观测（按 F1~F8 节奏）；
4. 任何阶段都可暂停或回退（构建期合并仍是过渡形态与安全网）。

> 反向路径同样成立：若试点发现收益不足（体积增大、体验漂移、发布并未解耦），
> 按 Zalando 经验**收回为统一构建**是理性选择，而非失败。
