## 1. 评估目的与口径 <a id="purpose"></a>

本页把《[02 取舍](02_微前端_单体与微前端取舍.md)》的收益/代价**逐条代入 BMS 的前端约束**，
产出一张可讨论的决策矩阵与一份重评触发条件。口径：

- 只验证「前提是否满足、收益是否真实、代价能否承受」，不以「先进/落后」评判；
- **决策已定（2026-09-15）**：引入微前端（Module Federation）——阶段四交付宿主薄壳与模块契约骨架、阶段五完成运行时加载与模块清单；新业务页面按模块形态开发，首个业务页面即首个模块样例；治理按最小闭环（隔离与依赖共享用基础配置，灰度与版本发现后补）。§5 决策矩阵作为决策依据存档；
- §7 触发条件转为「**治理就绪与扩展节奏**」检查项，每阶段末复盘时对照。

> **决策口径**：平台《项目规划说明》「明确不采用」清单已移除微前端条目，改列「平台能力插件化」前端段落；落地形态见平台《架构设计 · 前端架构》「前端插件化与运行时组合」节。

## 4. 代价核对（本项目要付多少） <a id="costs-check"></a>

| 代价 | 本项目具体化 | 量级判断 |
| --- | --- | --- |
| 重复依赖与体积 | 双工程已各有一份组件库；微前端会再叠模块重复（内网可接受、H5 敏感） | 中 |
| 治理与运维 | 模块流水线/版本清单/发现机制/宿主外壳，单人与单团队不可持续 | 高 |
| 体验一致性 | 统一设计令牌与组件库是当前优势；模块自治易漂移 | 中高 |
| 测试与调试 | 跨模块 E2E、契约测试、版本组合冒烟，显著增加测试面 | 中高 |
| 学习与人力 | 沙箱/版本偏斜/隔离排障经验缺乏，学习成本落在交付关键路径 | 高 |
| 与移动端叠加 | PC + H5 双工程若都微前端化，复杂度平方级上升 | 高 |
| 与阶段计划冲突 | 阶段四/五刚定「组件库 + 构建期合并 + 注册表」路线，改道成本高 | 中高 |

## 5. 决策矩阵 <a id="matrix"></a>

| 维度 | 当前取值 | 偏向 | 说明 |
| --- | --- | --- | --- |
| 团队规模 | 单人兼职 | **单体前端** | 微前端的组织动因不存在 |
| 产品形态 | 统一管理端 + H5 | **单体前端** | 体验一致性优先 |
| 技术栈 | 单栈 | **单体前端** | 无异构/迁移诉求 |
| 交付节奏 | 平台统一发布可接受 | **单体前端** | 产品随平台构建交付（免业务发版） |
| 治理能力 | 无体积预算/模块契约 | **单体前端** | 不满足微前端治理前提 |
| 性能诉求 | 内网管理端 + 轻量 H5 | 中性 | 路由分包已够用 |
| 前后端协同 | 微服务后端（9 服务独立契约，前端按服务段寻址） | **单体前端** | 无 BFF/多形态诉求（口径更新见《[03 技术方案对比](03_微前端_技术方案对比.md)》§7） |
| **综合** | — | **维持「构建期合并 + 前端注册表」；把体积意识与契约纪律作为长期准备** | 见 §6/§7 |

## 6. 演进路径（决策后） <a id="options"></a>

| 阶段 | 内容 | 状态 | 治理要求 |
| --- | --- | --- | --- |
| 阶段四（组件库） | **骨架起步**：宿主薄壳（布局 / 路由 / 模块加载器）+ 模块契约（宿主注入上下文 / 模块注册声明）+ 设计令牌与组件契约可被模块复用 | 已写入平台规划 | 体积预算（已落地）；契约先行 |
| 阶段五（插件化） | **运行时加载落地**：Module Federation + 模块清单（名称 / 入口 / 版本）+ shared 依赖 singleton；新业务页面按模块形态独立构建发布，**首个业务页面即首个模块样例**；平台页面与存量模块走构建期合并（过渡） | 已写入平台规划 | 清单与版本字段先行；独立构建产物计量 |
| 后续阶段 | **治理补齐**：CSS/JS 隔离增强、依赖版本协商与双端 CI 验证、灰度/蓝绿与回滚、按模块可观测归因 | 按 F1~F8 节奏评估 | Fitness Function 化 |
| 未来（按需） | **扩展范围**：多团队 / 多模块独立流水线、异构栈模块（此时才评估 `iframe`/`qiankun`） | F1~F2 触发 | 见 §4 |

### 6.1 已有资产与微前端能力的映射 <a id="assets"></a>

引入后平台不需要从零开始——「一致性、装配、契约、观测」四层现成，缺的是运行时那一层（按阶段四 / 五补齐）：

| 微前端需要的能力 | 平台现成资产 | 覆盖度 |
| --- | --- | --- |
| 模块契约与注册 | 前端扩展点注册表（路由/菜单、页面区域、组件、字段渲染器、卡片、主题、i18n）+ 产品接入规范 | **高**（入口需从构建期改为运行时可调用） |
| 体验一致性 | 设计令牌 + 组件库 + 前端基类体系（开放式） + 公共组合式与工具基座 | **高** |
| 边界与唯一性治理 | 模块注册（表前缀/业务码/错误码段/事件域）+ CI 校验 | **高** |
| 模块与后端的数据契约 | OpenAPI 契约 + 类型生成 + 统一响应 | **高** |
| 动态加载与分包 | 阶段五计划中的「动态导入分包 + 插件清单」 | **中高**（已是半套机制） |
| JS / CSS 运行时隔离 | 无（单构建、单 Vue 实例、Scoped 样式） | **缺** |
| 依赖共享与版本偏斜治理 | 无（双端各一份 lockfile） | **缺** |
| 模块清单/发现、灰度、回滚 | 无（单产物一次发布） | **缺** |
| 按模块可观测归因 | 无 | **缺** |

> 结论：现有准备让「构建期合并 → 运行时加载」成为**换传输层**的小步演进；阶段五落地时的补课重点在
> 「隔离 / 依赖协商 / 模块清单与灰度 / 按模块观测」四项（按 F1~F8 节奏补齐）。通用分工模型（两轴 + 五件事）见《[插件化架构 · 01 总览](../插件化架构/01_插件化架构_总览.md)》「一致性 / 差异性模型（两轴 + 五件事）」节。

## 7. 重评触发条件（什么时候必须重新讨论） <a id="triggers"></a>

| # | 触发条件（任一成立即开评） | 量化口径（建议） |
| --- | --- | --- |
| F1 | 团队规模 | 前端/产品出现 **≥ 2~3 个独立交付节奏的团队** |
| F2 | 技术异构 | 确有团队需要不同框架/技术栈（含旧栈系统需要接续） |
| F3 | 独立发布 | 产品前端需要**独立于平台发版**，且构建期合并无法满足（如每周多次、与平台节奏解耦） |
| F4 | 性能/体积 | 单产物首屏体积或构建时长成为瓶颈（如首屏 JS 超预算 2 倍、全量构建超 10 分钟） |
| F5 | 隔离/嵌入 | 需要嵌入第三方不可信前端（安全隔离诉求，iframe 先于微前端评估） |
| F6 | 多形态差异 | 出现 PC/H5/大屏/门户等多前端形态，数据形态差异大（先评估 BFF，再评估微前端） |
| F7 | 治理就绪 | 已有设计系统、**体积预算（已落地）**、按模块归因监控与契约测试体系（微前端前提） |
| F8 | 试点验证 | 选项 C 试点跑通且证明「收益 > 代价」（体积/发布解耦/回滚指标） |

> 复审节奏：每阶段末复盘时对照本表一次（`review_stage.py` 第 9 项已同时打印后端 E1~E5 与前端 F1~F8）；触发项用于决定**治理补齐与扩展节奏**（引入决策已定，F1~F8 不再用于「是否引入」）。
> **联动口径**：瓶颈在哪端先动哪端；前后端触发同时成立时**后端优先**（后端一致性与运维代价结构更重，且平台已备「独立服务」出口）。

## 8. 讨论结论（2026-09-15） <a id="conclusion"></a>

| # | 议题 | 结论 | 去向 |
| --- | --- | --- | --- |
| 1 | **是否引入微前端** | **引入**：Module Federation，阶段四骨架 / 阶段五落地，最小闭环；新业务页面按模块形态开发，首个业务页面即首个模块样例 | 平台《项目规划说明》阶段四 / 五行与「平台能力插件化」前端段落；平台《架构设计 · 前端架构》「前端插件化与运行时组合」节 |
| 2 | F1~F8 的登记与提醒 | 保留**引用式 + 复盘提醒**（与后端 E1~E5 同构），用途改为「治理就绪与扩展节奏」判断 | `review_stage.py` 第 9 项同时打印 E1~E5 与 F1~F8 |
| 3 | 体积预算入 CI | **已落地**：`pnpm run budget`（零依赖脚本）+ `budget.json` 阈值（基线 +20%），挂双端 `build` job | `apps/desktop`/`frontend-mobile` 工程与《前端开发规范》「构建体积预算」节 |
| 4 | 与后端触发联动 | **联动原则**：瓶颈在哪端先动哪端；同时成立时后端优先 | 《微服务 · 10 项目评估》对应节；复盘脚本同时展示两套触发条件 |
| 5 | `iframe` / `qiankun` 沙箱式 | **不采用**：仅当异构技术栈 / 强隔离需求出现时再评估（先 iframe） | 平台《架构设计 · 目标与约束》与「前端插件化与运行时组合」节 |
