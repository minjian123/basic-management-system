## 1. 评估目的与口径 <a id="purpose"></a>

本页把《[02 取舍](02_微前端_单体与微前端取舍.md)》的收益/代价**逐条代入 BMS 的前端约束**，
产出一张可讨论的决策矩阵与一份重评触发条件。口径：

- 只验证「前提是否满足、收益是否真实、代价能否承受」，不以「先进/落后」评判；
- **不改现行决策本身**——是否修订平台《项目规划说明》「不引入运行时远程加载 / 微前端」条目由评审拍板；
- 触发条件是「什么时候必须重新开这个会」的清单，每阶段末复盘时对照（见 §7）。

## 2. 项目约束（事实清单） <a id="constraints"></a>

| # | 约束 | 取值 / 现状 | 来源 |
| --- | --- | --- | --- |
| F-C1 | 团队 | **单人兼职**（AI 辅助），无专职前端平台团队 | 《总体项目规划》 |
| F-C2 | 技术栈 | Vue 3 + Vite + TS 单栈；PC（Element Plus）与移动端 H5（Vant）双工程 | 阶段一交付 |
| F-C3 | 集成形态 | 产品（biz/cw）前端模块**构建期合并**进平台前端应用；菜单/路由/权限走平台注册 | 平台《平台可扩展性规划》 |
| F-C4 | 产品形态 | 管理端 + 移动端，统一体验与权限一致性优先 | 平台《项目规划说明》 |
| F-C5 | 后端形态 | 单后端 + 统一 API（OpenAPI 契约 + 统一响应），无多前端数据形态差异 | 阶段一交付 |
| F-C6 | 部署 | 前端静态产物随平台发布（Docker Compose / nginx） | 《开发部署规划》 |
| F-C7 | 性能场景 | 内网管理端为主；H5 移动端审批/通知轻量 | 平台《项目规划说明》 |
| F-C8 | 治理现状 | 双端 lint + Vitest + 构建入 CI；无体积预算/片段契约/按模块归因 | CI 配置 |
| F-C9 | 经验 | 无微前端实践与沙箱/版本治理经验 | 现状 |
| F-C10 | 计划位置 | 阶段四前端组件库（地基波）→ 阶段五前端插件化 → 阶段十五前端全页面 | 平台《总体项目规划》 |

## 3. 收益核对（微前端能给的，本项目现在要不要） <a id="benefits-check"></a>

| 收益 | 本项目现状替代 | 现在是否需要 | 触发条件（见 §7） |
| --- | --- | --- | --- |
| 片段独立发版 | 产品前端**构建期合并**：业务功能免产品侧发版、随平台发布 | **否**（产品与平台同工作区、同节奏） | F1 |
| 团队独立交付 | 单人团队；产品/平台协作靠工作区与文档 | **否** | F1/F2 |
| 渐进迁移旧栈 | 无旧前端栈，前端为新建工程 | **否** | — |
| 技术异构共存 | 单栈（PC/H5 各一套组件库但框架一致） | **否** | F2 |
| 片段级故障隔离 | 单 SPA；慢页面可用路由分包与懒加载缓解 | **部分**（可先做分包） | F4 |
| 按需加载 | Vite 路由级 code-splitting 已可满足 | **已部分满足** | — |
| 独立灰度/回滚 | 平台整体灰度（发布回滚）已可覆盖 | **暂否** | F3 |

## 4. 代价核对（本项目要付多少） <a id="costs-check"></a>

| 代价 | 本项目具体化 | 量级判断 |
| --- | --- | --- |
| 重复依赖与体积 | 双工程已各有一份组件库；微前端会再叠片段重复（内网可接受、H5 敏感） | 中 |
| 治理与运维 | 片段流水线/版本清单/发现机制/宿主外壳，单人与单团队不可持续 | 高 |
| 体验一致性 | 统一设计令牌与组件库是当前优势；片段自治易漂移 | 中高 |
| 测试与调试 | 跨片段 E2E、契约测试、版本组合冒烟，显著增加测试面 | 中高 |
| 学习与人力 | 沙箱/版本偏斜/隔离排障经验缺乏，学习成本落在交付关键路径 | 高 |
| 与移动端叠加 | PC + H5 双工程若都微前端化，复杂度平方级上升 | 高 |
| 与阶段计划冲突 | 阶段四/五刚定「组件库 + 构建期合并 + 注册表」路线，改道成本高 | 中高 |

## 5. 决策矩阵 <a id="matrix"></a>

| 维度 | 当前取值 | 偏向 | 说明 |
| --- | --- | --- | --- |
| 团队规模 | 单人兼职 | **单体前端** | 微前端的组织动因不存在 |
| 产品形态 | 统一管理端 + H5 | **单体前端** | 体验一致性优先 |
| 技术栈 | 单栈 | **单体前端** | 无异构/迁移诉求 |
| 交付节奏 | 平台统一发布可接受 | **单体前端** | 产品随平台构建交付（免业务发版） |
| 治理能力 | 无体积预算/片段契约 | **单体前端** | 不满足微前端治理前提 |
| 性能诉求 | 内网管理端 + 轻量 H5 | 中性 | 路由分包已够用 |
| 前后端协同 | 单后端统一 API | **单体前端** | 无 BFF/多形态诉求 |
| **综合** | — | **维持「构建期合并 + 前端注册表」；把体积意识与契约纪律作为长期准备** | 见 §6/§7 |

## 6. 演进选项（如果将来要动，按什么顺序） <a id="options"></a>

| 选项 | 内容 | 触发/适用 | 主要代价 |
| --- | --- | --- | --- |
| **A 维持现状** | 构建期合并 + 前端注册表（阶段五口径） | 当前 | 无新增 |
| **B 治理强化**（低成本，推荐持续做） | 设计令牌统一、体积预算入 CI、按模块归因监控、契约测试习惯 | 任何阶段 | 少量工程投入，回报是可维护性与可拆分性 |
| **C Module Federation 试点** | 选一个低风险独立域（如某产品专属页面）做运行时加载试点，其余保持构建期合并 | 出现「产品侧独立发版」诉求时 | 版本偏斜治理、宿主外壳与发现机制 |
| **D 全面微前端** | 宿主 + 片段清单 + 多片段独立流水线 | 仅当 F1~F8 多项成立且治理就绪时 | 见 §4，需平台团队 |

## 7. 重评触发条件（什么时候必须重新讨论） <a id="triggers"></a>

| # | 触发条件（任一成立即开评） | 量化口径（建议） |
| --- | --- | --- |
| F1 | 团队规模 | 前端/产品出现 **≥ 2~3 个独立交付节奏的团队** |
| F2 | 技术异构 | 确有团队需要不同框架/技术栈（含旧栈系统需要接续） |
| F3 | 独立发布 | 产品前端需要**独立于平台发版**，且构建期合并无法满足（如每周多次、与平台节奏解耦） |
| F4 | 性能/体积 | 单产物首屏体积或构建时长成为瓶颈（如首屏 JS 超预算 2 倍、全量构建超 10 分钟） |
| F5 | 隔离/嵌入 | 需要嵌入第三方不可信前端（安全隔离诉求，iframe 先于微前端评估） |
| F6 | 多形态差异 | 出现 PC/H5/大屏/门户等多前端形态，数据形态差异大（先评估 BFF，再评估微前端） |
| F7 | 治理就绪 | 已有设计系统、体积预算、按模块归因监控与契约测试体系（微前端前提） |
| F8 | 试点验证 | 选项 C 试点跑通且证明「收益 > 代价」（体积/发布解耦/回滚指标） |

> 复审节奏：每阶段末复盘时对照本表一次（`review_stage.py` 已含后端 T1~T8 提醒；前端 F1~F8 目前人工对照）。
