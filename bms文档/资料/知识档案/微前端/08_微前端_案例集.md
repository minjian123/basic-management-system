## 1. 概述 <a id="overview"></a>

本页汇总公开可查的微前端实践案例，作为《[02 取舍](02_微前端_单体与微前端取舍.md)》与
《[06 项目评估](06_微前端_项目评估.md)》的事实依据。案例的共同规律：

1. 采用动因几乎都是**组织问题**（多团队独立交付、渐进迁移旧栈），而非性能；
2. 技术路线差异极大（iframe / ESI / 运行时模块），但都配套了**治理机制**；
3. 有「从碎片化收回统一」的反向案例（Zalando），说明架构可逆、演进优先。

## 2. 案例一览 <a id="cases"></a>

| 案例 | 场景 | 集成方式 | 关键设计与代价 |
| --- | --- | --- | --- |
| **Spotify** | 桌面端应用型体验（组件间通信密集） | **iframe + 事件总线** | 用隔离换解耦；内存随 iframe 销毁自动回收；通信经事件总线解耦 |
| **DAZN** | 直播流媒体，覆盖 Web/移动端/电视盒子 | **每视图仅一个微前端 + Bootstrap 编排**，编译期产物走 CDN | 片段间几乎不共享（唯一例外：支付共享库，接受同步发布）；重复 header/footer 换取独立性；显著改善低端设备启动时间 |
| **IKEA** | 电商站点（20 年单体 IRW 退役） | **ESI 片段 + 静态文件 + 自包含片段** | 小团队起步（两披萨）；「浏览器内不共享框架」；设计系统 SKAPA；从 1 个团队拆成 3 个（逆康威）；后续向边缘 SSR 演进 |
| **Zalando** | 电商主站 | Mosaic 片段 → **Interface Framework（服务端渲染组合）** | 早期碎片化导致体验不一致、接入门槛高；2018 起统一技术栈、集中部署、Renderers + GraphQL + 设计系统；90% 流量迁至新框架 |
| **Thoughtworks 观察** | 多客户咨询 | 各类 | 技术雷达长期跟踪：「几乎普遍正面」，但反复强调治理与反模式（无政府状态）；并指出 Web Components 在微前端领域落地困难 |

> 采用者名单（行业综述）：SAP、Springer、Zalando、NewRelic、IKEA、Starbucks、DAZN 等。

## 3. 逐案要点 <a id="detail"></a>

### 3.1 DAZN：按视图切分与「重复优于抽象」

- **识别**：按 DDD 子域切分，几乎每个子域对应一个 SPA；Dumb 组件层面才复用；
- **编排**：一个轻量 Bootstrap（路由、加载/卸载、配置、跨片段数据共享 API），**同一时刻只加载一个片段**；
- **决策**：片段间不共享组件与逻辑；「错误的抽象比好的重复更贵」；
- **例外**：支付 SDK 因一致性风险做成共享库，并接受「升级需两片段同步发布」的耦合；
- **治理**：自动化投资、可观测（Sentry/LogRocket）、设计系统只共享哑组件；
- **成果**：低端电视设备启动时间约减半，用户体验与团队独立性同时改善。

### 3.2 IKEA：自包含片段与静改上限

- 页面由 ESI 片段拼装，**片段自带 CSS/JS**（自包含），团队用命名空间隔离；
- 「**浏览器内不共享**」：不为复用引入全局运行时；以 **MTTR（快速修复）** 优先于 MTBF；
- 团队从 1 个 20~25 人拆为 3 个跨职能团队（倒逼出架构）；
- 后续用「静态文件 + 边缘计算」继续优化首屏与动态体验。

### 3.3 Zalando：从分散回到统一（反向演进）

- Mosaic（团队自管片段）暴露问题：**技术栈/打包/部署差异导致体验不一致、接入门槛高**；
- Interface Framework 目标：统一栈与部署流程、集中化组件版本管理、设计系统与 A/B 测试标准化；
- 代价与收益：团队「拥有片段」变为「贡献 Renderer」，所有权边界模糊化，但协作与一致性显著提升。

### 3.4 Spotify：隔离优先

- iframe 组合 + 事件总线；适用于应用型体验（片段间通信多）；
- Scott Logic 的分析将其放在「应用型」一端：通信复杂度高时，隔离的价值更大。

## 4. 教训汇总 <a id="lessons"></a>

| # | 教训 | 来源 |
| --- | --- | --- |
| 1 | 动因是组织与迁移，不是性能 | 全体案例 |
| 2 | 重复（依赖/UI 片段）是可接受成本，**错误的抽象更贵** | DAZN |
| 3 | 治理（设计系统、预算、契约、可观测）是收益的前提 | Mezzalira / Thoughtworks |
| 4 | 片段粒度宁粗勿细，运行时片段数量要克制 | Mezzalira |
| 5 | 路线选择服从约束：隔离优先→iframe；首屏/SEO→服务端组合；同栈独立发版→Module Federation | IKEA/DAZN/Spotify |
| 6 | 架构可逆：碎片化过度时可收回统一（Zalando）；试点失败可回退构建期合并 | Zalando |
| 7 | 体验一致性是底线：设计令牌与哑组件共享，业务组件不共享 | DAZN/IKEA |
