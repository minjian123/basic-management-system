## 1. 技术概述 <a id="overview"></a>

单体前端＝一个构建产物、一个发布节奏、一份依赖；微前端＝多个可独立交付的前端片段，运行期或服务端拼装。
与后端微服务一样，它的核心交换是：**用「组合与治理」的复杂度，换「独立交付」的自由度**。

但前端的代价结构与后端不同，不能照搬微服务的判断：

| 维度 | 后端微服务 | 微前端 |
| --- | --- | --- |
| 隔离 | 进程/容器天然隔离 | 共享一个浏览器运行时，隔离靠沙箱与约定 |
| 通信 | 网络调用（可失败可重试） | 同页内存调用/事件（快，但耦合更隐蔽） |
| 重复代价 | 重复部署与运维 | **重复依赖 = 用户下载体积**（直接体验成本） |
| 一致性 | 数据最终一致可补偿 | 视觉/交互必须即时一致（设计系统硬约束） |
| 组织动因 | 团队独立交付 | 同样是团队独立交付，但用户对「一个产品」的感知更强 |

## 2. 收益清单 <a id="benefits"></a>

| 收益 | 说明 | 成立前提 |
| --- | --- | --- |
| 独立开发与部署 | 每个微应用有自己的仓库、流水线与发布节奏，改一个片段不动全局 | 有清晰契约与组合层；否则只是「分布式单体前端」 |
| 团队自治 | 片段对应业务域与团队，减少跨团队排队（与后端微服务同源的组织动因） | 组织已按业务垂直拆分（康威定律） |
| 渐进式技术迁移 | 旧栈页面可逐页替换为新栈，不必一次性重写（IKEA / DAZN / 迁移场景） | 组合层支持新旧共存 |
| 独立发版降低风险 | 片段发布失败影响面小、可灰度/回滚 | 有版本管理与回滚机制 |
| 片段的强边界 | 仓库与部署边界天然强制模块化 | 需要契约纪律，否则退化为全局状态耦合 |

> Cam Jackson 总结的官方收益是：**更小更内聚的代码库、可扩展的自组织团队、可增量升级甚至重写**。

## 3. 代价清单 <a id="costs"></a>

| 代价 | 具体表现 | 缓解 |
| --- | --- | --- |
| 重复依赖与体积 | 每个片段各带一份 Vue/Element Plus，用户多下载 n 份 | 共享依赖（有版本偏斜风险）或构建期合并 |
| 体验漂移 | 视觉、交互、文案各自为政 | 设计系统 + 组件契约 + 评审 |
| 治理与运维复杂 | 更多仓库、流水线、域名、监控对象 | 平台团队/模板与 Fitness Function |
| 全局耦合风险 | 共享全局状态、互相直改数据 → 隐式跨团队耦合 | 事件通信、单向数据流、禁止共享可变状态 |
| 路由与状态复杂 | 主/子路由同步、保活、刷新恢复 | 组合层统一路由策略 |
| 测试复杂 | 跨片段 E2E、契约测试、版本组合爆炸 | 契约测试 + 关键链路 E2E + 每片段单测 |
| 可观测性门槛 | 一个页面的错误可能来自任一远端片段 | 统一埋点/Sentry、按片段归因 |
| 认知与调试 | 用户路径跨多个构建产物，问题定位链路长 | 统一 sourcemap 与 trace |

> industry 综述（Multivocal Literature Review，173 份来源）归纳的主要问题正是：
> **体积增大、代码重复、团队间耦合、监控复杂**——与上表一致。

## 4. 案例与实证 <a id="cases"></a>

| 案例 | 形态 | 结果与教训 | 详见 |
| --- | --- | --- | --- |
| **DAZN** | 每视图仅加载一个微前端，编译期产物 + Bootstrap 编排，几乎不共享（唯一例外：支付共享库并接受同步发布） | 团队独立、技术栈自由、按域加载；代价是重复（header/footer 各处复制）与观察性建设 | [08 案例集](08_微前端_案例集.md) |
| **IKEA** | ESI/SSI 片段组合 + 静态文件 + 自包含片段（含自己的 CSS/JS） | 小团队起步、渐进演进；强约束「浏览器内不共享框架」；后向边缘渲染演进 | [08 案例集](08_微前端_案例集.md) |
| **Spotify** | iframe + 事件总线（桌面端） | 隔离开销换解耦；适用于应用型体验（组件间通信多） | [08 案例集](08_微前端_案例集.md) |
| **Zalando** | Mosaic 片段（团队自管）→ Interface Framework（统一栈、集中部署、Renderers） | 早期碎片化导致体验不一致与协作困难，最终**从分散回到统一平台**——「反向演进」的典型 | [08 案例集](08_微前端_案例集.md) |
| **Thoughtworks** | 技术雷达长期跟踪 | 实践反馈「几乎普遍正面」，但强调治理与反模式（无政府状态） | [08 案例集](08_微前端_案例集.md) |
| **反方观点** | Scott Logic《You probably don't need a micro-frontend》 | 与微服务做类比不成立：浏览器的隔离/性能/一致性约束不同；多数项目不需要 | [08 案例集](08_微前端_案例集.md) |

**结论**：微前端的成功案例集中在**多团队、多技术栈、渐进迁移**三类场景；
单团队项目引入几乎只有成本（Cam Jackson 访谈原话：一人或一个团队的公司做微前端意义不大）。

## 5. 决策因子 <a id="factors"></a>

| 因子 | 偏单体前端 | 偏微前端 |
| --- | --- | --- |
| 团队规模 | 1~2 个团队维护全部页面 | ≥ 3 个团队需独立交付与发版 |
| 产品形态 | 统一体验的管理应用 | 门户型/多业务域拼装、或需逐页迁移旧栈 |
| 技术栈 | Vue 3 单栈（含 H5） | 确有异构共存或渐进替换诉求 |
| 交付节奏 | 统一发布可接受 | 各片段发版频率差异大且必须解耦 |
| 治理能力 | 无设计系统/自动化预算 | 有设计系统、体积预算与架构检查 |
| 性能要求 | 首页/首屏敏感（内网/移动端） | 可接受按需加载与首屏稍慢 |
| 团队经验 | 无微前端实践 | 有沙箱/版本治理经验（否则风险高） |

## 6. 在本项目中的用途 <a id="usage"></a>

- **决策（2026-09-15）**：平台**引入微前端**（Module Federation，阶段四骨架 / 阶段五落地，最小闭环），新业务页面按片段形态开发、首个业务页面即首个片段样例；本页的收益/代价与《[08 案例集](08_微前端_案例集.md)》案例为其提供风险与治理依据（重点：体积与依赖重复、体验一致性、治理前提）。
- **收益的替代实现**：产品 biz/cw 的页面在**构建期合并**进平台前端：统一路由、组件与权限，前端免发版交付业务功能；
  这已覆盖「多团队贡献同一产品」的大部分需求，代价是产品前端不能独立发版（当前无此诉求）。
- **何时重评**：多产品需要独立前端发版、出现异构技术栈团队、首屏体积/构建时长成为瓶颈等——触发条件见《[06 项目评估](06_微前端_项目评估.md)》F1~F8。

## 7. 常见误区速览 <a id="pitfalls"></a>

- 「微前端＝性能优化」：通常**增加**体积与加载复杂度，性能要单独设计与治理；
- 「微前端是微服务的必要配套」：两者动因相同（组织），但技术约束完全不同，不拆后端也可拆前端、反之亦然；
- 「拆了自然就独立」：无契约与治理时，共享全局状态会让片段间重新耦合；
- 「越小越好」：运行时微前端数量过多会变成「分布式单体前端」（Mezzalira：25 个运行时片段已属过多）；
- 「组件库＝微前端」：组件是开发期复用，微前端是部署期组合，两者正交。
  完整清单见《[07 常见误区](07_微前端_常见误区.md)》。
