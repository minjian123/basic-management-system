## 1. 背景与定位 <a id="intro"></a>

开发期「大规模代码查询」是人与 AI 助手共同的高频场景：跨模块调用关系、影响面分析（改一个基类影响哪些调用方）、语义定位（"认证刷新令牌在哪实现"）、历史追溯。代码规模小时 `ripgrep` + 语言服务（LSP）+ 测试反馈足够；规模上来后需要**本地代码知识库（索引）**托底——纯扫描会变慢，单一图索引又不耐规模增长（graphify 已实测淘汰，见第 3 节）。

本档案定位：**候选方案对比与测评标准**。原计划是「达到触发条件后做 A/B 评估、通过后登记选型」；
**2026-10-19 触发条件已全部突破（见 6.1），评估与落地已按第 5 节口径完成**，结论见 6.2。

## 2. 需求画像 <a id="needs"></a>

| 查询类型 | 典型问题 | 现状手段 | 规模化后的瓶颈 |
| --- | --- | --- | --- |
| 字面 / 正则检索 | 「哪里引用了 `resolve_plugin`」 | `ripgrep` | 全仓扫描随规模线性变慢、结果收敛难 |
| 符号导航 | 跳转定义 / 查引用 / 查实现 | LSP（pyright / tsc 等） | 单文件精确、跨仓库批量不便 |
| 影响面分析 | 「改这个基类影响谁」 | grep + 人工汇总 | 调用链跨层时人工成本高 |
| 语义问答 | 「实现可替换的装配逻辑在哪」 | AI 助手逐文件读 | token 成本高、易漏 |
| 历史追溯 | 「这行为何改成这样」 | `git log` / `git blame` | 基本够用 |

**消费方**：AI 助手（opencode 等，优先 MCP / CLI 接入）与人（IDE / 终端）；**约束**：数据不出内网、单人可维护（组件越少越好）、增量新鲜度（提交后分钟级可见）。

## 3. 已评估淘汰：graphify（2026-09-15） <a id="rejected"></a>

| 项 | 内容 |
| --- | --- |
| 形态 | 文档 + 代码混合知识图谱（AST 层 + LLM 语义层），工作区级产物 `graphify-out/` |
| 优点 | 文档间引用链（`contains` / `references`）查询准确；有社区 / 枢纽等图视角 |
| 淘汰原因 | **性能随规模增长明显下降**——更新与查询耗时「越用越慢」，至 2026-09 已不可忍受；1.5 万节点时即出现：宽查询命中数百节点被 token 预算截断、社区标签漂移（916 标签 vs 936 社区）、产物 242MB 维护成本高 |
| 处置 | 2026-09-15 全量卸载（工具链 / 文档登记 / dsh 与 CodeBuddy 集成）；产物与重建包备份至私有仓库 `mjs/graphify` |
| 复验点（未来同类工具先验证） | 增量索引时间随规模的曲线（是否线性恶化）、查询延迟 P95、索引 / 产物体积、更新是否必须全量重建、噪声与召回的平衡 |

**教训**：图谱类工具「演示期表现」不代表「规模期表现」；选型前必须用**倍增规模的数据**验证性能曲线，而不是只看功能清单。

## 4. 候选方案对比 <a id="candidates"></a>

| 方案 | 类型 / 原理 | 强项 | 短板 | 资源与运维 | 适配度 |
| --- | --- | --- | --- | --- | --- |
| `ripgrep`（现状基线） | 并行文本扫描，零索引 | 零运维、正则快、结果可信 | 大仓全扫随规模线性、无符号 / 语义 | 无新增 | 中小规模够用（当前） |
| **Zoekt** | Google 开源 trigram 索引 + 正则引擎（Sourcegraph 搜索内核） | 毫秒级检索、增量索引、单 Go 服务轻量、可多仓 | 无语义导航、无官方 UI | 中（1 服务 + 存储） | **规模化后首选候选** |
| Sourcegraph CE | Zoekt + SCIP + 多仓库平台化 | 功能全（跨仓检索 / 精确导航 / commit 检索）、成熟 | 重：最低 8C32G 起、组件多、运维成本高 | 高 | 偏重，暂不推荐 |
| OpenGrok | Java / Lucene + Universal Ctags | 硬件门槛低（4C8G）、符号交叉引用 | 首次查询冷启动秒级、无 AI / 语义 | 中（JVM / Tomcat） | 备选（重跨引用时） |
| SCIP + Language Server | 语言服务生成精确符号索引（pyright / tsc 等） | 跳转 / 引用 / 实现精确，可只对重点仓库启用 | 无全局正则 / 语义问答 | 低-中 | 符号导航补位 |
| Milvus + embedding | 分块嵌入向量检索（平台阶段十九已规划 Milvus） | 语义问答、可复用于文档 / 代码混合 | 需嵌入管线与新鲜度治理、成本高 | 中-高（复用既有组件） | 语义层候选（随平台 AI 落地） |
| MCP 原生代码图谱 | codebase-memory-mcp / code-graph-mcp 等 | 以 MCP 直供 agent（impact / architecture 一次返回） | 生态早期、质量参差、供应链风险 | 低 | 谨慎试点，不做主线 |

## 5. 测评标准（触发评估时按此 A/B） <a id="criteria"></a>

| 维度 | 指标 |
| --- | --- |
| 检索性能 | 冷 / 热查询延迟（P50 / P95）；单关键词、正则、组合过滤三类查询 |
| 索引性能 | 首次全量索引时间；单次提交增量索引时间；新鲜度（提交到可检索延迟） |
| 资源占用 | 内存 / 磁盘占用（对比索引源体积）；单机可承载规模上限（文件数 / 行数） |
| 语言与中文 | 语言覆盖数；中文注释与标识符（含 `\w` 语义）处理 |
| 集成 | opencode / MCP 接入方式；人用 CLI / IDE 接入体验 |
| 运维 | 组件数、升级与故障恢复、备份；单人可维护性 |
| 合规 | 内网部署、数据不出内网、权限边界 |

**评测方法**：用本仓真实任务做 A/B 对照（如「找某基类的全部调用方与派生类」「跨模块影响面分析」「语义定位某个装配逻辑」），候选方案 vs 现状（`ripgrep` + LSP）各跑一遍，记录耗时、命中质量与人工投入。

## 6. 触发条件与落地结论（2026-10-19） <a id="trigger"></a>

### 6.1 触发条件已全部突破 <a id="trigger-hit"></a>

原定「规模 + 场景双阈值，先到即评估」：

| 阈值 | 原定值 | 2026-10-19 实测 | 状态 |
| --- | --- | --- | --- |
| 后端代码行数 | > 5 万行 | **14.0 万行**（1,157 个 .py） | 已突破 |
| 前端代码行数 | —（原未设） | **20.5 万行**（961 个 ts/tsx/vue） | 参考 |
| 仓库文件数 | > 3,000 | **5,002 个**可检索文件（全工作区） | 已突破 |
| 单次全量检索 | > 1 秒 | **60~70ms** | **未突破** |

### 6.2 关键发现：瓶颈不是速度 <a id="finding"></a>

评估中最重要的一条结论，推翻了本档案 1.1 节的原假设：

- 全库 `ripgrep` 扫描 5,002 个文件仅 **60~70ms**——**扫描速度始终没有成为瓶颈**；
- 但同一关键词「权限计算」命中 **162 个文件 / 347 行**，使用者要逐个打开判断相关性；
- 因此真实成本是**结果收敛**，不是扫描耗时。

据此放弃了「外置搜索引擎加速扫描」路线（Zoekt 等），改为**自建轻量相关性检索**。

### 6.3 落地结论 <a id="result"></a>

| 项 | 结论 |
| --- | --- |
| 选定形态 | 自建检索工具：jieba 分词 + SQLite FTS5 + bm25 分列加权 + 路径加权 |
| 落点 | `bms/scripts/tools/search/`（MCP 服务 + 命令行双入口） |
| 为什么不用 Zoekt / Sourcegraph | 语料仅约 38MB 可检索文本，比 Zoekt 典型场景小两个数量级；且 Windows 原生支持不可依赖 |
| 为什么不接向量检索 | 代码检索的精确符号查找上 BM25 优于向量（见 6.4）；且引入 embedding 管线与新鲜度治理成本高 |
| 为什么不用 Meilisearch | 只支持词前缀、不支持中缀子串；索引膨胀 10~25 倍；需常驻服务，重新引入漂移风险 |
| 中文处理 | **必须先分词再入 FTS5**——FTS5 的 `unicode61` 会把连续汉字当单个 token，原生不可用；`trigram` 分词器则对两字中文词失效 |
| 实测效果 | 平均 MRR 0.74（首条即相关为主）；单次查询 1~2ms；索引 62MB / 全量重建 40 秒 |
| 部署说明 | 《[内容检索工具部署使用说明](../../工具/内容检索工具部署使用说明.md)》 |

### 6.4 2026-10 外部调研结论（供后续选型参考） <a id="research"></a>

若未来语料规模再上一个数量级（如 > 200MB 可检索文本），按以下结论复评：

- **Zoekt**：索引约 3~3.5x 语料、查询 RAM 约 1.2x 语料；但 `ngramSize=3`，**查询 rune 数 < 3 时源码退化为正则全扫**——「权限」「登录」这类两字中文词吃不到索引收益；Windows 原生支持已被上游移除，需 WSL2/容器。
- **语义 / 向量检索**：2025-2026 主流结论是**词法优先**。精确符号查找上 BM25 优于纯向量与混合检索；Sourcegraph Cody 已移除 embeddings，Cline 明确不索引。
- **文档检索**：Meilisearch 中文分词最强但只支持词前缀且膨胀严重；Tantivy 是库不是服务，需自建服务。
- 详细对比与来源见本次调研记录（工作区 `tmp/代码与文档检索方案调研报告.md`，未入库）。

### 6.5 复评触发条件 <a id="revisit"></a>

维持原「先到即评估」原则，但阈值按实测调整：

- 可检索文本 > 200MB，或单次全库检索 > 1 秒；
- 或现有工具平均 MRR 跌破 0.5（排序质量显著劣化）；
- 或出现「同义改写检索」成为高频刚需（此时才值得评估向量层）。

## 7. 组合建议（分读模型） <a id="combo"></a>

不指望单一工具全包（graphify 教训）——按读取模型分离、各自可替换（《平台可扩展性规划》「开源与商业组件可替换」原则）：

- **正则 / 字面检索**：现状 `ripgrep`；规模化后接 Zoekt（毫秒级、轻量）。
- **符号 / 跳转 / 引用**：LSP / SCIP（pyright、tsc 等），按语言就位。
- **语义问答**：Milvus + embedding，随平台 AI 能力（阶段十九）复用落地。
- **agent 接入**：统一走 MCP / CLI，工具可替换、提示词与工作流不绑定具体检索器。
