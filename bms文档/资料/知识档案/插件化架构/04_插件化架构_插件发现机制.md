## 1. 技术概述 <a id="overview"></a>

**插件发现（Plugin Discovery）**解决一个基础问题：主程序怎么知道环境里有哪些实现可用？三种主流方式——**命名约定**（扫描固定目录）、**命名空间包**（共享子包）、**包元数据**（entry points 入口点）。三者都与 Python 的导入系统有关，但发现范围、安装要求与安全边界不同。

- **定位**：插件化三阶段中「阶段三：第三方插件自动发现」的核心机制；阶段一/二可用显式注册表替代（见 [08 自建注册表](08_插件化架构_自建注册表.md)）。
- **标准推荐**：Python Packaging 官方指南推荐包元数据（entry points）方式，生态兼容最好。
- **原则**：**发现不等于执行**——发现阶段只应加载类或工厂，不执行业务初始化；初始化交由框架在生命周期钩子中显式触发。

## 2. 三种发现方式 <a id="methods"></a>

### 2.1 命名约定（Naming Convention）

约定插件放在固定包/目录下，用 `pkgutil.iter_modules()` 扫描该命名空间，再 `importlib` 动态导入。**优点**：零配置、目录可见、实现最简单；**缺点**：只能发现本包内、写在约定位置的模块，第三方安装包无法自动纳入（除非同包），扫描范围与异常处理需自行保证。

```python
import importlib, pkgutil

def discover(package: str = "app.plugins"):
    out = {}
    pkg = importlib.import_module(package)
    for _, name, _ in pkgutil.iter_modules(pkg.__path__):
        mod = importlib.import_module(f"{package}.{name}")
        out[name] = getattr(mod, "PLUGIN", None)  # 仅取对象，不初始化
    return out
```

### 2.2 命名空间包（Namespace Packages）

把 `app.plugins` 做成 **namespace package**（PEP 420），多个发行包可向同一命名空间贡献模块；安装后扫描命名空间即发现全部。**优点**：跨发行包发现、目录自然；**缺点**：一个坏包可能破坏整个命名空间，官方**不建议**把项目主顶层包做成命名空间包；插件须显式声明 `packages`。

### 2.3 包元数据（Entry Points）

发行包在 `pyproject.toml` 声明入口点组，主程序用 `importlib.metadata.entry_points(group=...)` 读取并 `.load()`。**优点**：安装即注册、标准、跨发行包、与打包生态一致；**缺点**：需正确打包安装，开发者有配置成本。

```toml
# 插件包的 pyproject.toml
[project.entry-points."bms.plugins.id_generator"]
snowflake = "bms_plugin_snowflake:IdGenerator"
```

```python
from importlib.metadata import entry_points

def discover(group: str = "bms.plugins.id_generator"):
    found = {}
    for ep in entry_points(group=group):   # Python 3.10+；3.12+ 亦可 entry_points(group=...)
        try:
            found[ep.name] = ep.load()     # 只加载类/工厂，不实例化
        except Exception as exc:           # 单个插件损坏不影响整体
            print(f"插件 {ep.name} 加载失败：{exc}")
    return found
```

## 3. 三种方式对比 <a id="compare"></a>

| 维度 | 命名约定 | 命名空间包 | 包元数据（entry points） |
| --- | --- | --- | --- |
| 发现范围 | 本包内约定目录 | 同一命名空间的多个发行包 | 环境中所有声明了该组的包 |
| 第三方自动纳入 | 否 | 是 | 是 |
| 安装要求 | 无需额外打包配置 | 需 namespace 约定 | 需在元数据声明入口点 |
| 实现复杂度 | 低 | 中 | 中 |
| 生态兼容 | 一般 | 一般 | 最好（官方推荐） |
| 安全边界 | 本包可控 | 命名空间可被他人贡献 | 取决于安装来源 |
| 典型使用者 | 简单宿主 | 大型插件体系 | pytest、OpenStack、各类框架 |

**选择建议**：阶段一/二用「显式注册表 + 命名约定」即可（可控、零依赖）；阶段三需要第三方安装即发现时，采用 entry points，并配合隔离与兼容校验。

## 4. 在本项目中的用途 <a id="usage"></a>

- **平台能力的发现分层**：平台内建实现用显式注册（启动时注册进注册表）；第三方实现用 entry points 发现，二者最终汇入同一注册表（见 [08 自建注册表](08_插件化架构_自建注册表.md)）。
- **产品扩展接入**：产品模块的挂载同理——平台按注册要素（表前缀/错误码段/事件域）发现并装配产品扩展包；入口点组可作为产品扩展包的发现约定。
- **发现与平台边界**：只允许从**受控入口点组**自动发现，不扫描任意目录、不加载未登记来源；生产环境的插件加载是显式扩展手段，不是自由放任。
- **与 CI 校验配合**：发现结果与注册要素在启动与 CI 阶段做唯一性校验，冲突即拒。

## 5. 安全与健壮性 <a id="safety"></a>

- **发现 ≠ 执行**：`.load()` 只返回对象；初始化放在生命周期钩子，避免导入期副作用。
- **异常隔离**：逐个插件 `try/except`，单个插件损坏不得中断主程序启动。
- **名称校验**：入口点名/模块名做白名单与正则校验，防止注入非法模块路径。
- **进程内无沙箱**：Python 插件与主程序同权限，不可信插件必须进程或容器隔离（见 [12 第三方插件生态](12_插件化架构_第三方插件生态.md)）。
- **版本与依赖**：校验插件声明的框架版本范围与依赖，不匹配则跳过并告警；依赖冲突在安装期暴露。
- **来源可信**：自动发现仅信任受控索引/内网源，禁止从任意网络加载。

## 6. 常见问题与注意事项 <a id="pitfalls"></a>

- **entry_points API 版本差异**：Python 3.10 之前返回 dict-like，需 `.get(group)`；3.10+ 用 `.select(group=...)` 或直接 `entry_points(group=...)`。生产代码按版本兼容处理。
- **导入即副作用**：插件模块顶层写连接、读配置、起线程，发现阶段就出问题。
- **重复名称**：多个插件注册同一名称，唯一性校验缺失时后者覆盖前者，行为不可预期。
- **静默失败**：加载异常被吞且无日志，插件「消失」无从排查。
- **命名空间包陷阱**：把主顶层包做成命名空间包，一个坏插件可导致整个包不可导入。
- **发现范围过宽**：扫描整个 `site-packages` 既慢又不安全。
