## 1. 目的与适用范围 <a id="purpose"></a>

mjbk 上的**数据层**（三库 + GitLab + Kiwi 附件）由统一脚本每日备份，并与系统层、异地层构成三层容灾：

| 层 | 承载 | 范围 | 触发 | 说明文档 |
| --- | --- | --- | --- | --- |
| 系统层 | Timeshift | 系统盘（含配置、软件） | 每日自动 | 《[Ubuntu安装部署使用说明](../../工具/Ubuntu安装部署使用说明.md)》「备份与恢复」节 |
| **数据层（本文档）** | `~/deploy/backup/backup_daily.sh` | MySQL / PostgreSQL / DM8 / GitLab / Kiwi 附件 | cron 每日 02:30 | 本文档 |
| 异地层 | 百度网盘（gpg 加密件） | 数据层当日产物 | 数据层脚本末步骤 | 《[百度网盘云备份部署使用说明](百度网盘云备份部署使用说明.md)》 |

> 成果物不作为合规存档，仅用于开发环境快速恢复。`<mjbk-IP>` 取值见《[本地资源](../../../用户文档/本地资源.md)》。

## 2. 备份总控脚本 <a id="script"></a>

| 项 | 值 |
| --- | --- |
| 落位 | mjbk `~/deploy/backup/backup_daily.sh`（仓库内不同版本纳管，见[第 8 节](#todo)） |
| 触发 | 用户 crontab：`30 2 * * * /home/minjian/deploy/backup/backup_daily.sh >> /mnt/data/backup/cron.log 2>&1` |
| 日志 | `/mnt/data/backup/cron.log`（每行 `[时间戳] daily backup: <组件>:OK/FAIL …`） |
| 凭据来源 | `~/deploy/.env`（`MYSQL_ROOT_PASSWORD` / `POSTGRES_PASSWORD` / `DM8_SYSDBA_PASSWORD` / `BACKUP_CRYPT_PASSPHRASE`）+ 百度网盘客户端 Cookie 库，**不硬编码** |
| 退出码 | 主组件（mysql / postgres / dameng / gitlab / kiwi）任一 FAIL → 退出 1；**cloud FAIL 仅记录，不影响退出码** |

组件与产出：

| 组件 | 方法 | 产物 | 备注 |
| --- | --- | --- | --- |
| mysql | `mysqldump --single-transaction --all-databases --routines --triggers --events --no-tablespaces`（gzip） | `/mnt/data/backup/mysql/all_<TS>.sql.gz` | 容器内执行后 `docker cp` 式管道直出 |
| postgres | `pg_dump --dbname=bms_dev`（gzip，**单库**） | `postgres/bms_dev_<TS>.sql.gz` | 不用 `pg_dumpall`：避免角色冲突与 `\connect` 直写问题 |
| dameng | `dexp FULL=Y`（DM 自带工具，`/opt/dmdbms/bin`） | `dameng/dexp_all_<TS>.dmp` + `.log` | 恢复用对应 `dimp` |
| gitlab | 容器内 `gitlab-backup create` → `docker cp` 到本地目录；另打包 `/mnt/ssd2t/gitlab/config` | `gitlab/<id>_gitlab_backup.tar` + `gitlab/gitlab-config_<TS>.tar.gz` | 数据包不含 secrets/ssl/gitlab.rb，故必须同时备份 config |
| kiwi | 临时 alpine 容器挂 `volumes-from bms-kiwi` 打包 `/Kiwi/uploads` | `kiwi/kiwi-uploads_<TS>.tar.gz` | 用例附件是**文件数据**，不在数据库内 |

脚本骨架（便于核对口径）：

```bash
run_step mysql    dump_mysql
run_step postgres dump_postgres
run_step dameng   dump_dameng
run_step gitlab   backup_gitlab
run_step kiwi     backup_kiwi_uploads
run_step cloud    cloud_sync          # 加密 + 上传 + 云端文件名比对
```

## 3. 保留策略 <a id="retention"></a>

| 位置 | 策略 | 参数 |
| --- | --- | --- |
| 本地 `/mnt/data/backup/<组件>/` | 按组件删除 `+7` 天 | `KEEP_DAYS=7` |
| 本地暂存加密件 `backup/cloud/<日期>/` | 删除 `+30` 天 | `CLOUD_KEEP_DAYS=30` |
| 云端 `/apps/bms-backup[/<年-月>]` | 网盘侧保留（与本地解耦） | 见《[百度网盘云备份部署使用说明](百度网盘云备份部署使用说明.md)》 |

每日另有 `0 6 * * *` 拉起 Renovate 容器（`compose/gitlab.yml`，日志 `~/deploy/renovate.log`），详见《[Renovate部署使用说明](Renovate部署使用说明.md)》。

## 4. 验证与演练 <a id="verify"></a>

### 4.1 可执行性验证（2026-09-15）

对 **2026-09-04** 的既存产物做了一次完整恢复演练（临时容器 / 临时库，用完即删）：

| 组件 | 演练方式 | 结果 |
| --- | --- | --- |
| MySQL | 新建一次性 `mysql:8.4` 容器（等待**鉴权通过**而非仅 `mysqladmin ping` 才判定就绪——后者在初始化期也会返回 OK 导致误判），全量导入 `all_2026-09-04_023001.sql.gz` | 导入退出码 0；恢复出 `bms_dev` / `kiwi` 两库，**kiwi 库 62 张表**；演练容器已销毁 |
| PostgreSQL | 临时容器 + 临时库导入 `bms_dev_2026-09-04_023001.sql.gz` | 成功无报错；内容为纯结构无表（与当时生产一致：生产 `bms_dev` public 表数 = 0） |
| GitLab | `tar -tzf gitlab-config_*.tar.gz` | 可解析，首项 `config/` + `config/ssh_host_rsa_key.pub` 等 |
| Kiwi 附件 | `tar -tzf kiwi-uploads_*.tar.gz` | 可解析（95 字节空目录包，Kiwi 附件尚未使用） |
| DM8 | 查看 `dexp_all_*.log` | 末行「成功终止导出, 没有出现警告」 |

> **数据空 ≠ 备份失败**：2026-08-28 ~ 09-04 共 8 份 MySQL 存档行数一致（3087 行）、均不含业务数据的 `INSERT` 行，原因是**当时 MySQL 尚未承载业务数据**（佐证：Kiwi 用例首行创建时间戳为 `2026-09-10`，数据是 09-10 之后才落 MySQL 的）。同一条命令在 2026-09-15 手工执行可得 54 条 `INSERT`（含用例表），命令本身有效。

### 4.2 由此暴露的校验缺陷

脚本当前的成功判据只有 `[ -s <产物> ]`（文件非空），**无法表达「数据是否完整」**：上述 8 份零业务数据的存档在当时全部判为 OK。

> 改进项（未实施，登记见[第 8 节](#todo)）：增加**行数 / 条目数校验**——把关键表行数或 dump 中 `^INSERT INTO` 计数写入 `cron.log` 供趋势比对，或对每个非空数据集设「行数必须 > 0」的断言。

## 5. 恢复步骤 <a id="restore"></a>

> 恢复前先确认**目标实例不被误写**：以下口令一律是「导入到临时对象，确认后再切换」。

| 组件 | 恢复命令（要点） |
| --- | --- |
| MySQL 全量 | `gunzip -c /mnt/data/backup/mysql/all_<TS>.sql.gz \| docker exec -i -e MYSQL_PWD=<root口令> bms-mysql mysql -uroot`（演练已验证） |
| MySQL 单库回导（误删单表时） | 先导入到临时库 `bms_restore`，比对后再 `RENAME TABLE` 迁移（**勿**用 `--one-database` 期望它能替你选库：该选项只放行同名库的语句，对 `--all-databases` 存档导入其他库时是空操作） |
| PostgreSQL | 建空库后 `gunzip -c backup.sql.gz \| docker exec -i -e PGPASSWORD=<口令> bms-postgres psql -U postgres -d <目标库>`（plain SQL 格式） |
| DM8 | `dimp SYSDBA/<口令>@localhost:5236 FILE=dexp_all_<TS>.dmp DIRECTORY=/mnt/data/backup/dameng FULL=Y`（**未演练**，受实例占用与授权限制） |
| GitLab | 停写 → 容器内 `gitlab-backup restore BACKUP=<id>` → 用 `gitlab-config_<TS>.tar.gz` 覆盖 `/mnt/ssd2t/gitlab/config`（含 secrets，缺之不可）→ `gitlab-ctl reconfigure` |
| Kiwi 附件 | `docker run --rm --volumes-from bms-kiwi -v /mnt/data/backup/kiwi:/backup alpine tar xzf /backup/kiwi-uploads_<TS>.tar.gz -C /Kiwi/uploads` |

恢复后必查：`cron.log` 最近一行、各组件产物时间戳、以及 GitLab/Kiwi 服务能否正常登录。

## 6. 日常运维 <a id="ops"></a>

| 操作 | 命令 |
| --- | --- |
| 查看今日是否跑过 | `tail -1 /mnt/data/backup/cron.log` |
| 手工补跑 | `bash ~/deploy/backup/backup_daily.sh`（幂等，产物按时间戳不覆盖） |
| 看 crontab | `crontab -l`（预期两条：02:30 备份、06:00 Renovate） |
| 产物清单 | `ls -lht /mnt/data/backup/<组件>/ \| head` |
| 占用分布 | `du -sh /mnt/data/backup/*` |
| 云同步结果 | `tail -3 /mnt/data/backup/cron.log`（含 `cloud sync: 目标=… 本地加密件=…`） |

## 7. 排障记录 <a id="trouble"></a>

| # | 现象 | 原因 | 处置 / 结论 |
| --- | --- | --- | --- |
| 1 | **备份自 2026-09-05 起停摆**（最新产物 09-04，截至 09-15 缺 11 天） | mjbk 是笔记本，**夜间休眠/挂起**（2026-09-15 07:16 有 `suspend.target` 记录）；02:30 落在挂起期被跳过，而 **cron 不补跑** | 已定位，**修复待办**：改 systemd timer（`Persistent=true`）或挂 `/etc/cron.daily`（anacron 补跑）。当前无备份覆盖 09-10 之后的 Kiwi 数据（含策展用例库），须尽快修复 |
| 2 | 一次性 MySQL 容器导入报 `Access denied for user 'root'` | 用 `mysqladmin ping` 判就绪会在**初始化未完成时**就返回 OK | 改为轮询 `mysql -uroot -N -e "SELECT 1"` 直到鉴权通过（脚本役约 12 秒就绪） |
| 3 | 用了 `mysql --one-database <临时库>` 却什么都没导入 | 该选项只放行**同名库**的语句，`--all-databases` 存档里没有该库 → 空操作（退出码仍是 0） | 全量导入到独立容器，再按需抽取 |
| 4 | PG 单库备份看起来是空包 | 生产 `bms_dev` 当时无业务表 | 属预期；兜底判据按[第 4.2 节](#verify)改进项执行后才知真伪 |
| 5 | 云同步报 `cloud 缺失: xxx.gpg` | 网盘 `upload` 对不存在目录会**静默失败且返回 0**，脚本已做 `ls` 前置校验并按文件名回查 | 已有防护；缺 monkey：见《百度网盘云备份部署使用说明》排障节 |
