## 1. 目的与范围 <a id="purpose"></a>

覆盖后端 9 个已启用服务的**容器编排、首次数据引导、一键部署 / 回滚、健康门禁与版本留存清理**——编排资产、环境变量、CLI 用法、验证与排障。语义见《架构设计 · 部署与运维》「基础设施编排」「版本与发布管理」节与《部署发布规范》「镜像与版本」「发布流程」「回滚」节。

服务镜像由 CI 服务子流水线构建 / 推送（09_01）；一键部署 / 回滚 / 门禁 CLI 为 `scripts/tools/deploy/release.py`（**仅依赖 Python 标准库**，可在部署机直接运行；本机 `python3` ≥ 3.8，mjbk 实测 3.12）。

## 2. 服务与端口 <a id="services"></a>

| 服务 | 容器名 / Compose DNS | 镜像 | 端口 |
| --- | --- | --- | --- |
| platform / identity / tenant / file / notification / search / ai / report / txn | `bms-{服务}`（DNS = 服务标识） | `${REGISTRY_IMAGE_PREFIX}/bms-{服务}:${BMS_TAG_<服务>}` | 容器内 `8000`（仅内部网络，不映射宿主端口） |

- 服务名取服务目录 `{service_key}`，与网关声明式上游（`deploy/gateway/apisix.yaml`）同口径；访问统一经边缘网关（nginx `GATEWAY_HTTP_PORT` 8088 / APISIX 9080）。
- 镜像标签**必填**（`BMS_TAG_<服务>`，无 `latest` 兜底），由 CLI 按版本台账注入。
- `org`（mdm 组织主数据）属**产品服务**：服务目录已登记（`product_key=mdm`），编排归 mdm 仓 `deploy/compose/mdm.yml`（容器 `mdm-org`），**不在本仓 `services.yml`**（2026-10-17 组织退役口径落地）；网关侧仍保留 `org` 上游与 `/api/mdm/v1/org` 产品路由，待 mdm 侧镜像构建启用后由其编排接入。

## 3. 目录与配置 <a id="layout"></a>

```text
deploy/
├── compose/
│   ├── services.yml            # 9 服务编排（Compose DNS / 仅内部网络 / MySQL 每服务库 / 边界白名单挂载）
│   └── bms.yml                 # 聚合 include（base + gateway + services + observability）
├── .env                        # 运行时变量（不入库）：DB / Redis / 镜像前缀 / 标签 / 租户 / 门禁超时
├── boundaries/                 # 边界例外白名单（容器内 /opt/deploy/boundaries）
└── releases/                   # 版本台账（不入库）：<service>.json + release-log.jsonl

scripts/tools/deploy/release.py # 部署 / 回滚 / 状态 / 清理 / 门禁 / 数据引导 CLI
```

**部署机检出与同步（2026-10-17 起）**：部署机（mjbk）持有仓库**完整检出** `<检出根> = /home/minjian/bms`，`/home/minjian/deploy` 为指向 `<检出根>/deploy` 的软链（兼容既有命令、脚本与 systemd 单元）：

```bash
git -C /home/minjian/bms pull     # 同步：编排 / 网关 / 可观测 / CLI 随仓库更新（凭据存 ~/.git-credentials，权限 600）
ls -ld /home/minjian/deploy       # -> /home/minjian/bms/deploy
cd /home/minjian/bms              # 命令一律在检出根执行（scripts/ 在检出根，deploy/ 为其子目录）
```

- **服务器本地资产**（在检出内、不入库，经 `.git/info/exclude` 本地忽略）：`deploy/.env`（凭据）、`deploy/releases/`（版本台账）、`deploy/backup/`（备份总控脚本）、`deploy/contracts/org.json`（mdm 契约）。
- **禁止在服务器手工改配置**：2026-10-17 前部署目录为**逐文件手工拷贝**（相对仓库漂移 25 个文件、缺 15 个，含边缘请求体上限、服务票据、mdm 产品路由三项功能缺口）；此后改动一律先回写仓库，再 `git pull` 生效。
- 网关 `apisix.yaml` 为生成物（`backend/ops/gateway_config.py render`），随仓库更新，禁止手改。

`.env` 关键键（见 `deploy/.env.example`「服务编排与发布」段）：`REGISTRY_IMAGE_PREFIX`、`BMS_ENV`、`BMS_IMAGE_TAG`、`BMS_DATABASE__PLATFORM{,_TENANTS}__URL_TEMPLATE`（MySQL 每服务库）、`BMS_DATABASE__*_PASSWORD`、`BMS_APP_DB_USER` / `BMS_APP_DB_PASSWORD`、`BMS_DEPLOY_TENANTS`、`BMS_GATE_TIMEOUT`、`BMS_KEEP_SHA_TAGS`、`MYSQL_ROOT_PASSWORD`（建库 / 授权）。密钥只在本文件（gitignore）。

服务容器内置配置：`BMS_REDIS__URL=redis://redis:6379/0`、`BMS_TRACER__OTLP_ENDPOINT=http://otel-collector:4318`、`BMS_SERVICE_CLIENT__PROVIDER=http`（服务间按 Compose DNS `http://{service}:8000`）、`BMS_DATA_OWNERSHIP__EXCEPTIONS_FILE=/opt/deploy/boundaries/data_ownership_exceptions.json`。

## 4. 数据引导（bootstrap，首次一次） <a id="bootstrap"></a>

按「建库授权 → 建表 → 种子」幂等执行（可重跑）。在部署机仓库检出根：

```bash
cd /home/minjian/bms
python3 scripts/tools/deploy/release.py --deploy-dir deploy bootstrap               # 全部启用服务
python3 scripts/tools/deploy/release.py --deploy-dir deploy bootstrap --service platform --service identity  # 限定子集
```

- **应用账号**：经 `mysql` 容器 root（`MYSQL_ROOT_PASSWORD`）幂等创建 `BMS_APP_DB_USER`（缺省 `bms_app`）并按 `bms\_%` 库授权。
- **建库**：`ops.provision_tenant`（平台服务库 `bms_{service}` + 服务租户库 `bms_{service}_{tenant}`；租户取 `BMS_DEPLOY_TENANTS`）。
- **建表**：逐服务以**其自身镜像**跑 `ops.init_schema --service <服务>`（平台链 + 租户链的表集幂等建表；建表能力已入镜像，`alembic/`（迁移机制）+ `ops/`）。
- **种子**：`seed_module` / `seed_tables`（platform 镜像）→ `seed_tenant`（tenant 镜像）；**字典六表已随 02_09 退役**，原 `seed_dict` 步骤与脚本一并删除。管理员建号另经 `docker compose run --rm --no-deps platform python -m ops.seed_user --tenant <租户> --username <账号>`。

> 服务镜像须先构建 / 推送并在部署机可拉取（`REGISTRY_IMAGE_PREFIX`）；`bootstrap` 依赖 `BMS_IMAGE_TAG`（或各 `BMS_TAG_<服务>`）。
>
> **全量重建（开发 / 演示库口径）**：本阶段库均为开发 / 演示库，结构不符时一律**删库重建**，不做存量搬迁——① 先 `mysqldump` 归档将删库（`deploy/backup/`，仅留痕兜底）；② `drop` 全部 `bms_*` 业务库（各服务平台库 + 各服务租户库 + 归档库 + 开发库；**保留基础设施库**：GitLab / Keycloak / MinIO 等）；③ `release.py bootstrap`（建库 → 建表 → 种子）；④ `release.py deploy --all --tag <tag>`（建表先行 → 起容器 → 健康门禁 → 写台账）。启动期自动建表**只补不建改**（不做 ALTER），故既有库结构演进须删库重建或按新基线重建迁移脚本。

## 5. 一键部署 / 回滚 / 门禁 <a id="release"></a>

```bash
cd /home/minjian/bms

# 部署（建表先行 → 起容器 → 健康门禁 → 写台账；门禁失败自动回滚）
python3 scripts/tools/deploy/release.py --deploy-dir deploy deploy --service platform --tag v0.2.0
python3 scripts/tools/deploy/release.py --deploy-dir deploy deploy --all --tag <sha 或 vX.Y.Z>

# 一键回滚（缺省回上一版本；可 --to 指定；不执行 downgrade）
python3 scripts/tools/deploy/release.py --deploy-dir deploy rollback --service platform

# 台账 / 单跑门禁 / 留存清理
python3 scripts/tools/deploy/release.py --deploy-dir deploy status [--service platform]
python3 scripts/tools/deploy/release.py --deploy-dir deploy health-gate --service platform
python3 scripts/tools/deploy/release.py --deploy-dir deploy prune --keep 30 [--dry-run]
```

- **健康门禁**：容器 `healthy`（`/healthz`）→ 容器内 `/readyz` 200 → 经网关路由可达（`/api/{服务}/v1/__gate__` 状态 ∈ {200,401,403,404}）；失败**自动回滚**上一版本并复跑门禁，仍失败保留现场（退出码 1）。
- **版本台账**：`deploy/releases/<服务>.json`（当前 / 上一版本）、`release-log.jsonl`（部署 / 回滚动作、前后版本、结果、操作者、时间）；不入库。
- **留存清理**：`prune` 经 GitLab Container Registry API 删除超窗 SHA 标签（semver 永久）；磁盘回收另经 `gitlab-ctl registry-garbage-collect`。

## 6. 采集口径（可观测） <a id="observability"></a>

- Prometheus `bms-services` / `bms-probe` 目标已切 Compose DNS `{service_key}:8000`（9 服务逐项，`/healthz` `/readyz` 探针）；**前提为经 `compose/bms.yml` 全栈拉起**（services 与 observability 同项目网络 DNS 方可解析）。
- 变更 `prometheus.yml` / `blackbox.yml` 后，因容器为**单文件 bind mount**，须 `docker compose ... up -d --force-recreate prometheus blackbox-exporter` 重新挂载才生效（`SIGHUP` 不会换 inode）。
- 详见《[可观测性栈部署使用说明](可观测性栈部署使用说明.md)》。

## 8. 排障 <a id="troubleshooting"></a>

| 现象 | 排查 |
| --- | --- |
| `required variable BMS_TAG_<SERVICE> is missing` | 直接 `docker compose up` 未给标签（刻意防 latest）；改用 `release.py deploy`（自动注入）或导出全部 `BMS_TAG_<服务>` |
| 网关路由 502（`gateway-nginx`） | nginx 启动时缓存了 `apisix` 解析地址，APISIX 重建后 IP 变化 → 502；`docker restart bms-gateway-nginx` 即解（APISIX 直连 9080 正常、经 nginx 8088 502 时优先排查） |
| 网关路由 401 | 正常（`forward-auth` 未带令牌）；门禁以此判「网关 / 认证可达」 |
| `/readyz` 非 200 | 容器内 `docker exec bms-<服务> ... /readyz` 看 checks（`database` / `redis` 必需，`catalog` 非必需）；DB / Redis 不可达则 503 |
| `/readyz` 的 `catalog` 项降级（`ServiceUnavailableError`，总体仍 `ok`） | 与 platform 可用性**无关**：查日志是否 `GET http://platform:8000/api/v1/modules/snapshot "401 Unauthorized"`——该端点鉴权未接通时（服务身份被拒）非目录权威服务启动接库校验恒降级；**重启平台或重启各服务都不消除**，须修鉴权接线（见缺陷 #111：双模依赖 `require_auth_or_service`） |
| 建表报 `No module named ops/bms_*` | 镜像未含建表能力（旧镜像）；重建服务镜像（Dockerfile 已 `COPY alembic/ ops/`） |
| 库结构与模型不一致（历史库 / 旧口径存量） | 开发 / 演示库一律**删库重建**（见第 4 节「全量重建」：`mysqldump` 留痕 → drop `bms_*` 业务库 → `bootstrap` 建库 / 建表 / 种子 → `deploy --all`）；启动期建表只补不建改（不做 ALTER），不提供存量搬迁脚本 |
| `seed_dict` 报 `no such table: sys_dict_type` | 目标库未建表（或 URL 落到 SQLite 兜底）；确认 `BMS_DATABASE__TENANTS__URL_TEMPLATE` 正确、platform 租户链已建表 |
| 回滚报无上一版本 | 台账无 `previous`；用 `--to` 显式指定目标标签 |
| 抓取目标仍 `host.docker.internal` | `prometheus.yml` 改后未重挂载：`up -d --force-recreate prometheus` |
| 版本标签被清理致回滚失败 | 调大 `BMS_KEEP_SHA_TAGS`；semver 标签永久保留不受影响 |
| 部署机配置与仓库不一致 | 部署机为仓库检出（`/home/minjian/bms`），`git -C /home/minjian/bms pull` 即同步；**手工改服务器文件**才会漂移——改动先回写仓库再 pull（见第 3 节「部署机检出与同步」） |
| 平台启动报「服务目录校验失败：库中缺登记行」 | 服务目录新增模块后未同步库行（启动接库校验按 `sys_module` ↔ `SERVICE_CATALOG` 双向对账，缺行拒启）：跑 `ops.seed_module`（幂等 upsert）；表归属库漂移（含退役表登记行残留）跑 `ops.seed_tables`（幂等 upsert + 清退不在清单的行）。两脚本与 `bootstrap` 4/4 同源 |
| 新服务首次接入起不来（`/readyz` 不过） | 缺 `bms_<服务>` / `bms_<服务>_<租户>` 库（无库即无法接库）：跑 `release.py bootstrap --service <服务>`（建库 + 只建该服务分链表，幂等；不触碰其它服务链） |
| 启动期建表报 `Unknown database 'bms_<服务>_<租户>'`（容器反复 restarting） | 部署租户集合与容器内 `[tenant].dev_tenants` 不一致：`.env` 的 `BMS_DEPLOY_TENANTS` 须覆盖 `dev_tenants` 全集（缺省 `demo,acme`），改后跑 `ops.provision_tenant --code …` 补建缺库 |

## 9. 实测结论（mjbk，2026-09-24） <a id="measured"></a>

**2026-10-17 补记（部署机检出化 + 组织退役落地）**：

- 部署机部署目录由**手工拷贝快照**转为**仓库 git 检出**（`/home/minjian/bms`，`/home/minjian/deploy` 为软链）；此前快照相对仓库漂移 25 个文件、缺 15 个（含边缘请求体上限、服务票据开关、mdm 产品路由三项**功能缺口**），本次以仓库为准全量对齐并重建网关 / 服务 / Keycloak / 可观测栈。
- 组织退役口径落地：`services.yml` 去 `org`、补 `txn`（跨服务事务管理器，05_07 实施中，dev 恒 `provider=none`），`bms-org` 容器停用（mdm 侧镜像构建启用后由 `mdm.yml` 接入）；`prometheus.yml` 抓取 / 探针目标同步由 `org` 换 `txn`。
- 网关：边缘 `client_max_body_size` 落地为 32m（此前 nginx 默认 1m，>1MB 上传经网关 413）；`apisix.yaml` 更新为含 `/api/mdm/v1/org`（mdm 产品路由）与 `/api/txn/v1`。
- 服务间调用开启服务票据（`attach_service_token=true`，此前默认关）。
- **服务目录与表归属种子同步**：平台启动做「接库服务目录校验」（`sys_module` ↔ `SERVICE_CATALOG` 双向对账，缺行即拒启）与表归属同口径对账；`txn` 加入清单后库中缺行，故按官方幂等脚本 `python -m ops.seed_module` + `python -m ops.seed_tables`（跑在 platform 镜像内）补齐——这是**每次新增模块后的固定动作**，漏跑则平台拒启。表归属种子同一动作**顺带清退**库中「未软删且不在清单」的退役表登记行（表实体由所属链迁移拆除、登记行由种子对齐；漏清退同样会让平台拒启）。
- **`txn` 首次接入数据面**：`release.py bootstrap --service txn` 建 `bms_txn` / `bms_txn_demo` 并跑 txn 分链迁移（`0001_txn_ledger` / `0002_txn_outbox` / `0003_system_fields_form_key`）；只动 txn 链，不触碰 platform / identity / org（绕开缺陷 #103）。`seed_dict`（字典种子）属 #103 报错步骤，本次不跑。
