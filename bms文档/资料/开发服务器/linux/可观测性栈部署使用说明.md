## 1. 目的与范围 <a id="purpose"></a>

覆盖 BMS 可观测性栈的部署、配置来源、应用侧接线、验证与排障——**指标（Prometheus）**、**链路（OTel → otel-collector → Tempo）**、**日志（Alloy → Loki）**、**统一展示（Grafana）**。选型与保留期见《架构设计 · 可观测性》《架构设计 · 部署与运维》「容量规划」节；编排与采集口径见《部署发布规范》「可观测性栈编排与采集口径」节。

## 2. 组件与端口 <a id="components"></a>

| 组件 | 镜像（固定 tag） | 宿主端口 | 作用 |
| --- | --- | --- | --- |
| otel-collector | `otel/opentelemetry-collector-contrib:0.115.1` | 4317 / 4318 | 接收 OTLP（gRPC / HTTP）→ Tempo；自指标 8888/8889 |
| Tempo | `grafana/tempo:2.6.1` | 3200 | trace 存储与查询（保留 72h） |
| Prometheus | `prom/prometheus:v3.1.0` | 9090 | 抓取各服务 `/metrics` / APISIX / collector（保留 15d） |
| Loki | `grafana/loki:3.3.2` | 3100 | 日志聚合（保留 30d，结构化元数据） |
| Alloy | `grafana/alloy:v1.5.1` | 12345（UI） | 采集容器与宿主日志 → Loki |
| Grafana | `grafana/grafana:11.4.0` | 3000 | 数据源 / 面板统一展示 |
| Alertmanager | `prom/alertmanager:v0.33.1` | 9093 | 告警路由 / 抑制 / 通道（08_02；配置为渲染产物） |
| blackbox-exporter | `prom/blackbox-exporter:v0.28.0` | 9115 | 探针主动探测（/healthz /readyz；08_02） |
| Pushgateway | `prom/pushgateway:v1.11.3` | 9092（容器 9091） | 阶段度量推送接收（CI 批处理指标；08_02） |

> 端口为默认值，可经 `deploy/.env` 覆盖。全部仅内网可达。

## 3. 目录与配置 <a id="layout"></a>

```text
deploy/
├── compose/
│   ├── observability.yml      # 可观测组件编排（含 alertmanager / blackbox-exporter / pushgateway）
│   └── bms.yml                # 聚合编排（include base + gateway + observability，一键）
└── observability/
    ├── otel-collector.yaml    # OTLP 接收 → Tempo；自指标
    ├── prometheus.yml         # 抓取目标（服务 / 探针 / APISIX / 组件）+ 规则与告警接线
    ├── rules/bms-slo.yml      # 基座 SLO 告警规则（08_02；业务链路锚点留位）
    ├── blackbox.yml           # 探针探测模块（http_2xx 仅 200 成功）
    ├── alertmanager.yml.tmpl  # 告警配置模板（渲染后使用；凭据经 .env 注入）
    ├── rendered/              # 渲染产物目录（alertmanager.yml 不入库）
    ├── tempo.yaml             # OTLP + 本地存储 + 72h TTL
    ├── loki.yaml              # TSDB + 30d 保留 + 结构化元数据
    ├── alloy.alloy            # docker 发现 + 宿主文件 + JSON 解析 → Loki
    ├── logs/                  # 宿主直跑服务日志目录（Alloy 只读采集）
    └── grafana/
        ├── grafana.ini
        ├── provisioning/datasources/bms.yaml   # Prometheus / Loki / Tempo
        ├── provisioning/dashboards/bms.yaml
        └── dashboards/                          # bms-overview / bms-slo / bms-stage-metrics
```

## 4. 一键拉起 <a id="up"></a>

在 mjbk 的 `~/deploy` 目录（`.env` 提供变量）：

```bash
# 全栈（基础设施 + 网关 + 可观测）
docker compose -f compose/bms.yml --env-file .env up -d

# 仅可观测栈
docker compose -f compose/observability.yml --env-file .env up -d

# 查看
docker compose -f compose/observability.yml ps
```

> `.env` 需含（缺失可临时导出）：`GRAFANA_ADMIN_PASSWORD` 与可观测端口（`PROMETHEUS_PORT` / `GRAFANA_PORT` / `LOKI_PORT` / `TEMPO_PORT` / `OTEL_OTLP_HTTP_PORT` 等，缺省值见 `deploy/.env.example`）。Grafana 管理员口令不入库。

> **首次部署 / 变更告警凭据后先渲染 Alertmanager 配置**（在 bms 仓库根执行，产物随 `deploy/` 同步到服务器；幂等，可重跑）：
>
> ```bash
> python3 scripts/tools/observability/render_alertmanager.py --env-file deploy/.env
> ```
>
> 无告警凭据时渲染为 no-op receiver（告警仅 Alertmanager UI 可见，不阻断其余组件）；凭据键位见 `deploy/.env.example`「告警与阶段度量」段。

## 5. 应用侧接线 <a id="app"></a>

服务默认（`config.toml`）已启用真实实现：

- `[metrics] provider = "prometheus"` → 每服务根路径 `/metrics` 暴露 Prometheus 文本；
- `[tracer] provider = "otel"` + `otlp_endpoint`（缺省 `http://localhost:4318`）→ OTLP/HTTP 上报 collector；
- 宿主直跑服务（当前形态）：端点取 `http://localhost:4318`（collector 宿主端口）；Prometheus 经 `host.docker.internal:8000` 抓宿主服务。
- **服务容器化后**：经 `BMS_TRACER__OTLP_ENDPOINT=http://otel-collector:4318` 覆盖，Prometheus 抓取目标改 `{service_key}:8000`（Compose DNS）。

宿主直跑并落日志供 Alloy 采集（可选，用于「日志按服务检索」验证）：

```bash
cd ~/bms-smoke/backend
export PATH=$HOME/.local/bin:$PATH
nohup uv run python -m bms_platform > ~/deploy/observability/logs/bms-platform.log 2>&1 &
```

## 6. 告警与阶段度量（08_02） <a id="alerting"></a>

**告警链路**：Prometheus 规则目录 `observability/rules/`（基座 SLO：服务指标端点不可达 / 探针失败 / 依赖未就绪 / 服务目录降级 / 5xx 错误率 / P99 延迟 / 发件箱积压）→ Alertmanager（9093）路由（warning / critical 分级、严重级抑制同告警名与服务的警告级）→ 邮件 / 企业微信 / 钉钉通道（凭据经 `.env` 注入，缺失即 no-op）。业务链路 SLO（登录 / 审批 / Socket.IO / 备份）留位登记，业务端点实现后按服务请求指标补规则。

**探针观测**：blackbox-exporter 周期探测每服务 `/healthz` / `/readyz`（`http_2xx` 仅 200 成功）；探测本身会调用 `/readyz`，使依赖指标 `bms_dependency_up` 与目录降级指标 `bms_catalog_degraded` 持续刷新（无编排探针时的被动无数据问题由此解决）。

**阶段度量**：Pushgateway（宿主 9092）接收 CI 推送的批处理指标——发布成功率 `bms_release_total{service,result}`、契约破坏数 `bms_contract_breaking_total{service}`；**真实推送已接入**：服务子流水线 `service-release` 的 `after_script` 按 job 终态推送（09_01，地址经模板变量 `PUSHGATEWAY_URL`，未配置则跳过、推送失败不阻断发布结论）；边界越界数复用运行期 `bms_boundary_cross_access_total` 与静态门禁（非零即 CI 失败）。

```bash
# 1) 规则加载与 Alertmanager 可达
curl -s 'localhost:9090/api/v1/rules' | python3 -m json.tool | head
curl -s 'localhost:9090/api/v1/alertmanagers' | python3 -m json.tool
docker exec bms-alertmanager amtool check-config /etc/alertmanager/alertmanager.yml

# 2) 探针与依赖 / 目录降级指标
curl -s 'localhost:9090/api/v1/query?query=probe_success' | python3 -m json.tool
curl -s 'localhost:9090/api/v1/query?query=bms_dependency_up' | python3 -m json.tool
curl -s 'localhost:9090/api/v1/query?query=bms_catalog_degraded' | python3 -m json.tool

# 3) 告警真实触发（停服务 → 观察 → 恢复；up 规则 1m、探针规则 2m）
kill <platform-PID>
curl -s 'localhost:9090/api/v1/query?query=ALERTS' | python3 -m json.tool   # firing
curl -s 'localhost:9093/api/v2/alerts' | python3 -m json.tool               # active
# 重启服务后复查：ALERTS 与 /api/v2/alerts 均空（解除）

# 4) 阶段度量推送（样例；真实推送由 CI 执行，数据末尾须有换行）
printf 'bms_release_total{service="platform",result="success"} 1\n' | \
  curl -s --data-binary @- http://localhost:9092/metrics/job/bms-ci -w 'http=%{http_code}\n'
curl -s 'localhost:9090/api/v1/query?query=bms_release_total' | python3 -m json.tool

# 5) Grafana 面板（浏览器）：BMS / BMS SLO 与告警、BMS 阶段度量
```

```bash
curl -s localhost:8000/metrics | head

curl -s 'localhost:9090/api/v1/query?query=apisix_http_requests_total' | python3 -m json.tool

# 6) Grafana 数据源 / 面板（浏览器）
#    http://<mjbk-IP>:3000  → BMS / BMS 可观测总览
```

## 8. 排障 <a id="troubleshooting"></a>

| 现象 | 排查 |
| --- | --- |
| `/metrics` 404 | 服务 `[metrics].provider` 非 `prometheus`（占位实现不暴露端点） |
| Prometheus 目标 down | 服务未启动 / 端口不通；宿主直跑需 `host.docker.internal`（compose 已配 `extra_hosts`） |
| Tempo 无 trace | 应用 `BMS_TRACER__OTLP_ENDPOINT` 不可达；`docker logs bms-otel-collector` 看导出错误；采样率过低 |
| 日志无 `service` 标签 | 应用日志非 JSON 或字段名不符；`docker logs bms-alloy` 看解析 |
| `trace_id` 查不到 | 结构化元数据需 Loki 3.x 且 `allow_structured_metadata: true`（配置已启） |
| 端口占用 | 改 `.env` 端口后 `up -d`；组件端口仅内网 |
| 镜像拉取慢 | 走国内加速（daemon `registry-mirrors` 或显式 `<mirror>/<image>` 前缀拉取后重打 tag）；固定 tag，不用 `latest` |
| Alertmanager 起不来 | 配置为渲染产物：先跑 `render_alertmanager.py`（产物缺失即报配置错误）；`docker logs bms-alertmanager` 看校验信息，`amtool check-config` 复核 |
| 告警不发 / 只挂 UI | 通道凭据缺失（no-op receiver）或 SMTP 不可达：补 `.env` 后重渲染 + `up -d`；看 `alertmanager_notifications_failed_total` |
| 探针无 `probe_success` | blackbox 目标未登记 / 不可达：目标与 `bms-services` 同口径（宿主直跑需 `host.docker.internal`）；`docker logs bms-blackbox` 看探测 |
| 阶段度量面板空 | 尚未有 CI 推送（服务子流水线 release job）或推送失败：查 `up{job="pushgateway"}` 与 Pushgateway UI（9092）；推送数据末尾须有换行 |
| 清空阶段度量样例 | 组删除走**推送端点** `curl -X DELETE http://localhost:9092/metrics/job/bms-ci`（返回 202；`/api/v1/...` 与 admin wipe 默认关闭不可用） |
