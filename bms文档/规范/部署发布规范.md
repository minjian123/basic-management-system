## 1. 目的与适用范围 <a id="purpose"></a>

规范本项目各环境的部署与发布：环境分层、镜像版本、发布与回滚流程，保证可重复、可追溯。
部署拓扑与编排见平台《开发部署规划》第 7/9/10 节与平台《架构设计 30 部署与运维》。
`<mjbk-IP>` 取值见《[本地资源](../用户文档/本地资源.md)》。

## 2. 环境管理 <a id="env"></a>

| 环境 | 标识 | 用途 | 数据 |
| --- | --- | --- | --- |
| 开发 | `BMS_ENV=dev` | 本地开发（mjpc），内网访问 mjbk 共享服务 | SQLite / bms_dev |
| 测试 | `BMS_ENV=test` | CI 三库集成、E2E | bms_test 前缀库（用完即删） |
| 生产 | `BMS_ENV=prod` | 客户交付（MVP 验收、信创环境） | 正式库（备份策略见第 5 节） |

> 上表为**平台示例环境**：开发服务器与开发机为跨项目共享基础设施（说明见《[开发服务器部署使用说明总览](../资料/开发服务器/linux/开发服务器部署使用说明总览.md)》）；独立部署的产品按自身环境替换环境名、主机与库名，环境分层与隔离要求不变。

- 配置分层：配置文件按环境 + 环境变量覆盖（环境变量前缀见《[命名规范](命名规范.md)》「基础设施命名」节，配置体系见平台《项目规划说明》「环境与配置」）。
- 环境间数据与配置隔离，密钥仅存在对应环境。

## 3. 镜像与版本 <a id="version"></a>

- 镜像命名：`bms-backend`、`bms-frontend`（《[命名规范](命名规范.md)》「基础设施命名」节）。
- 镜像标签与 Git 标签一致：`bms-backend:v1.2.0`；临时构建用 `main-<短sha>`，禁以 latest 覆盖发布版本。
- 镜像存 GitLab Registry（`<mjbk-IP>:5050`）；生产拉取走内网或镜像同步。
- 构建产物可复现：Dockerfile 多阶段构建 + 依赖锁定（uv.lock / package-lock.json）。

## 4. 发布流程 <a id="release"></a>

1. **准备**：main 合入发布提交；打标签 `vX.Y.Z`（《[Git协作规范](Git协作规范.md)》「版本管理」节）。
2. **构建**：CI main 流水线构建 `bms-backend`/`bms-frontend` 镜像并推送 Registry（见平台《开发部署规划》「开发工作流与 CI」节）。
3. **迁移**：先执行数据库迁移（Alembic），再发布应用（迁移先行，应用向后兼容一个版本）。
4. **部署**：Compose 滚动更新（backend 多副本逐个替换）；前端静态资源由 nginx 托管。
5. **验证**：`/healthz`、`/readyz` 通过；核心冒烟用例（登录 → 主体链 CRUD）执行。
6. **记录**：发布记录（版本、时间、变更、负责人）登记；发布后监控关键指标 30 分钟（阶段十二起）。

> 演进：数据量或规模增长后迁移 Kubernetes（规划第 7 节），发布流程平移为滚动/蓝绿。

## 5. 回滚 <a id="rollback"></a>

- 应用回滚：Compose 回退镜像标签至上一版本（`bms-backend:v1.1.0`），重启完成。
- 数据库回滚：迁移先行策略下应用回滚即可；结构回退需评估（破坏性迁移不可逆时走数据修复脚本）。
- 数据备份前置：生产发布前数据库每日备份 + PITR（Binlog/WAL）；归档库纳入备份（平台《项目规划说明》「备份与恢复」）。
- 回滚时限：发现严重问题 30 分钟内回滚；回滚后复盘根因并补充回归用例。

## 6. 发布前检查 <a id="check"></a>

- □ 代码评审通过、CI 全绿、三库集成测试通过
- □ 迁移脚本已评审并在测试环境执行过
- □ 镜像标签与 Git 标签对应，Registry 可访问
- □ 环境变量与密钥就位（`BMS_ENV` 正确）
- □ 备份任务正常、可回滚版本确认
- □ 发布窗口与值班人确认（生产）

## 7. 检查清单 <a id="checklist"></a>

- □ 环境配置分层正确，密钥不入代码
- □ 镜像标签语义化，构建可复现
- □ 迁移先行、应用兼容上一版本
- □ 健康检查与冒烟验证通过，发布有记录
- □ 回滚方案与备份就绪
- □ 模块发布：清单版本与产物版本一致、四关校验通过（版本 / 隔离 / 共享 / sourcemap）、发布记录已登记（含产物体积）、回滚目标产物保留确认（见第 8 节）

## 8. 模块发布与回滚 <a id="module-release"></a>

> 适用：运行时模块（清单 `mode: remote`）。模块产物与平台发布**解耦**——清单是模块加载与回滚的**唯一来源**；平台发布（镜像 / 迁移 / 回滚）见第 4 / 5 节。

- **清单唯一来源**：模块的入口与版本只在模块清单登记（名称 / 入口 / 版本 / 加载形态 / 可见性）；加载、发布与回滚一律以清单为准，禁止旁路（手工改入口、直接替换产物目录等）。
- **版本发现（入清单前校验）**：模块构建产出**产物元数据**（名称 / 版本 / 契约版本）；发布前校验「清单版本 = 产物元数据 = 模块源码版本」，通过才可入清单——产物与清单错位即拒绝发布。
- **发布流程**：三关强校验（**版本 / 隔离 / 共享**）→ 产物**按版本归档**（版本目录；本地开发环境为本地发布存储，生产为静态托管 / CDN 版本目录）→ 清单指向该版本 → 发布记录留痕（谁 / 何时 / 动作 / 版本 / 前后版本）。
- **回滚**：清单版本回退到上一版本（缺省上一版本，可显式指定）；**模块产物按版本保留是回滚前提**，回滚即清单指向切换（无需重构建）。回滚后须同步处理模块源码（回退版本或准备修复版本发布）；清单与源码版本不一致由清单护栏提示。
- **灰度 / 蓝绿（最小闭环）**：仅保留「**按清单指向切换**」——同一模块多版本产物并存、清单指向其一；按用户 / 租户 / 比例分流为后续能力。
- **可见性（应急停用）**：清单 `enabled: false` 停用模块（不加载、不挂载、不进菜单；保留入口与版本），恢复即改回 `true`；停用与恢复同样留痕。
- **契约变更协同升级**：模块契约版本升级（注入上下文 / 注册声明 / 清单字段语义 / 校验链变更）= 平台与模块**协同升级**——平台发布契约变更通告，模块适配并升版本、重新构建发布；契约版本不匹配的产物不得入清单、不得回滚生效。
- **版本不可变**：已归档版本不得覆盖（回滚依赖旧产物完整）；生产禁用同版本重发，本地开发重发须留痕。
- **留痕**：发布记录（JSON 真源 + Markdown 摘要）随仓库提交，与第 4 节发布记录同口径（版本 / 时间 / 变更 / 负责人）；记录另带**产物体积**（入口闭包 gzip 合计 / 最大块 / 块数 / 异步块数）与 sourcemap 标记，体积随版本可查。
- **sourcemap 归档与映射**：模块远端构建产出**外部 sourcemap**（不内联源码）；发布**归档 `dist/` 全量（含 map）**到版本目录，映射随版本保留。**发布前强校验加 sourcemap 关**（产物缺 map 拒绝发布）；映射口径：线上异常堆栈指向 `<基址>/<模块名>/<版本>/assets/<chunk>.js`，其 `sourceMappingURL` 指向同目录 `.map`，用 source-map 工具按该版本目录解析即可定位源码。生产由 nginx / CDN 托管版本目录（含 map），制品库 / 对象存储与私有化（map 不宜公开）归部署阶段。

> 模块发布与回滚的**工具落点与执行命令**见《[前端基类清单](../前端基类清单.md)》与模块工程说明；**检查项**：□ 四关强校验通过（版本 / 隔离 / 共享 / sourcemap）；□ 清单版本与产物版本一致；□ 契约版本与平台一致；□ sourcemap 随版本归档；□ 发布记录已登记（含产物体积）；□ 回滚目标产物保留确认。

## 9. API 网关配置与热加载 <a id="gateway"></a>

> 适用：边缘统一入口（Apache APISIX，standalone 文件驱动）。配置语义与 K8s 平移口径见实现侧详细设计（`项目/02_后端基座与服务化地基/任务/04_API网关与边缘/`）。

- **声明式入 Git**：网关路由 / 上游 / 认证 / 限流规则以声明式配置随仓库版本管理，**禁止在控制台手工增删**；临时变更须回写仓库后随流水线发布，否则视为漂移。
- **服务目录为单一来源**：路由 / 上游由服务目录生成（外部前缀与上游名取服务目录登记的服务标识），生成件由流水线**零漂移校验**；服务目录变更须同步重生成再发布。
- **改动生效**：配置改动经流水线校验后发布；运行时文件驱动**热加载**（网关轮询声明式文件，替换即生效，无需重启）。
- **环境差异外部化**：上游地址 / 端口等环境差异收敛进配置与环境变量，**禁止硬编码 IP**；服务间按稳定主机名寻址（Compose DNS → K8s Service）。
- **演进**：迁 K8s 阶段同语义换由 Ingress Controller / Gateway API 承载，配置模型平移、不换选型。
- **边缘请求净化与身份头**：客户端伪造身份头（`X-User-Id` / `X-Tenant-Id` / `X-User-Scopes` / `X-Service-Identity` / `X-Gateway-Identity`）由网关声明式**统一剥除**（`global_rules`），网关专属标记与身份注入落**路由级** `proxy-rewrite`（真机实测：global 规则 `headers.set` 会被路由级丢弃）；身份头契约以**边缘信任能力域常量为单一来源**（网关生成器与后端同源），后端只信任网关注入身份；真实用户 JWT / 服务 JWT 校验随认证任务接线（替换 `[edge].provider`），机制与配置结构不变。

> 检查项：□ 网关配置经仓库版本管理与流水线校验；□ 无控制台手工增删（或已回补仓库）；□ 服务目录变更已同步重生成；□ 上游地址无硬编码 IP；□ 边缘身份头契约与网关剥头 / 标记配置入 Git、与边缘信任能力域常量一致。
