## 2. 环境管理 <a id="env"></a>

| 环境 | 标识 | 用途 | 数据 |
| --- | --- | --- | --- |
| 开发 | `BMS_ENV=dev` | 本地开发（mjpc），内网访问 mjbk 共享服务 | SQLite / bms_dev |
| 测试 | `BMS_ENV=test` | CI 三库集成、E2E | bms_test 前缀库（用完即删） |
| 生产 | `BMS_ENV=prod` | 客户交付（MVP 验收、信创环境） | 正式库（备份策略见第 5 节） |

> 上表为**平台示例环境**：开发服务器与开发机为跨项目共享基础设施（说明见《[开发服务器部署使用说明总览](../资料/开发服务器/linux/开发服务器部署使用说明总览.md)》）；独立部署的产品按自身环境替换环境名、主机与库名，环境分层与隔离要求不变。

- 配置分层：配置文件按环境 + 环境变量覆盖（环境变量前缀见《[命名规范](命名规范.md)》「基础设施命名」节，配置体系见平台《项目规划说明》「环境与配置」）。
- 环境间数据与配置隔离，密钥仅存在对应环境。

## 3. 镜像与版本 <a id="version"></a>

- 镜像命名：`bms-backend`、`bms-frontend`（《[命名规范](命名规范.md)》「基础设施命名」节）；微服务按服务独立命名 `bms-{服务标识}`（如 `bms-platform`），镜像与版本按服务独立。兜底迁移工具镜像 `bms-migrate`（非必须，本阶段迁移能力已内置服务镜像）。
- 镜像标签与 Git 标签一致：`bms-backend:v1.2.0`；临时构建用 `main-<短sha>`，禁以 latest 覆盖发布版本；服务镜像临时构建用 `$CI_COMMIT_SHORT_SHA`。
- **不可变标签（按服务）**：commit short SHA 为**主标签**（每次 main 构建 / 发布，追溯单次提交、回滚窗口）；Git tag `vX.Y.Z` 流水线在**扫描通过后对同一镜像追加语义化标签**（发布引用首选）；**禁止 `latest` 作任何引用**（编排以必填变量 `${BMS_TAG_<SERVICE>:?}` 强制显式标签，无 latest 兜底）。
- **镜像留存与清理**：semver 标签**永久保留**；SHA 标签**每服务保留最近 N**（缺省 30），超窗经脚本调 GitLab Container Registry API 删除（磁盘回收另经 `registry-garbage-collect`）；回滚目标靠 semver 永久 + SHA 近窗留存保证可用。
- 镜像存 GitLab Registry（`<mjbk-IP>:5050`）；生产拉取走内网或镜像同步。
- 构建产物可复现：Dockerfile 多阶段构建 + 依赖锁定（uv.lock / pnpm-lock.yaml）；服务镜像构建上下文与锁文件口径随 `backend/Dockerfile`（`--frozen`，非目标服务源码不入镜像）；镜像内含 `alembic/` + `ops/` 迁移能力（部署流程内一次性迁移容器复用同一镜像，版本与发布严格一致）。
- **按服务构建与发布（父-子流水线）**：父流水线按变更路径调度、`trigger` 拉起服务子流水线；子流水线只测试 / 构建 / 发布该服务（镜像与版本独立），同服务发布经 `resource_group` 串行、发布 job 不可自动中断；发布后镜像经安全扫描（CRITICAL / HIGH 阻断）并推送发布度量（成功率口径见「可观测性栈」节）。
- **公共流水线模板复用（固定完整 SHA）**：服务子流水线公共模板随仓库版本管理（`deploy/ci/templates/`）；本仓以 `include: local` 引用，**跨项目引用一律固定完整 commit SHA**（以 `trigger.include.project + ref: <完整 40 位 SHA>` 作为子流水线配置，禁止分支 / 短 SHA / tag 引用）——模板升级须为下游显式提交（Renovate 可自动提升级 MR），不得静默跟随。

## 4. 发布流程 <a id="release"></a>

1. **准备**：main 合入发布提交；打标签 `vX.Y.Z`（《[Git协作规范](Git协作规范.md)》「版本管理」节）。
2. **构建**：CI main 流水线构建服务镜像并推送 Registry；tag 流水线对同一镜像追加 `vX.Y.Z`（扫描通过后），产出**发布清单** artifact（版本 / commit / 镜像 digest / 扫描结论 / 流水线 URL；不可自动采集的检查项以「人工确认」占位）。
3. **迁移**：先执行数据库迁移（Alembic），再发布应用（迁移先行，应用向后兼容一个版本）。按服务以**一次性迁移容器**执行（`docker compose run --rm --no-deps <service> python -m ops.migrate_tenants --service <service>`；镜像已含 `alembic/` + `ops/`，版本与发布一致）；迁移**向前修复优先**，仅兼容性迁移允许 downgrade。
4. **部署**：服务容器经 Compose 编排（`deploy/compose/services.yml`，服务名取服务目录 `{service_key}`、Compose DNS `{service_key}:8000`、仅内部网络经网关统一入口）；按版本台账以 `docker compose up -d <service>` 更新指定服务（一服务一容器，随规模增长演进为滚动 / 蓝绿）。
5. **验证（健康门禁）**：`/healthz`（容器 healthy）→ `/readyz` 200 → 经网关路由可达（非 502/503/504/000）逐项判定；**失败自动回滚**上一版本（软回滚），仍失败保留现场人工介入。
6. **记录**：发布记录（版本、时间、变更、负责人）登记——CI 侧发布清单 artifact + 服务器侧版本台账（`deploy/releases/<service>.json` 当前 / 上一版本 + `release-log.jsonl`）；发布后监控关键指标 30 分钟（阶段十二起）。

> 一键发布 / 回滚 / 门禁 CLI 为 `scripts/tools/deploy/release.py`（子命令 `bootstrap` / `deploy` / `rollback` / `status` / `prune` / `health-gate`），用法见《[服务编排与发布部署使用说明](../资料/开发服务器/linux/服务编排与发布部署使用说明.md)》。
>
> 演进：数据量或规模增长后迁移 Kubernetes（规划第 7 节），发布流程平移为滚动/蓝绿。

## 5. 回滚 <a id="rollback"></a>

- **一键应用回滚（按服务）**：`scripts/tools/deploy/release.py rollback --service <服务> [--to <tag>]`——读版本台账取上一版本（或 `--to` 指定），切换镜像标签 `docker compose up -d` 重启并复跑健康门禁；回滚目标由「semver 永久 + SHA 近窗留存」保证（缺件即报错提示留存参数）。回滚动作与前后版本记入 `release-log.jsonl`。
- **数据库回滚**：迁移先行策略下应用回滚即可；**迁移向前修复（forward-fix）优先**，回滚**不自动执行 downgrade**（仅兼容性迁移允许 Alembic downgrade，人工按需）；结构回退需评估（破坏性迁移不可逆时走数据修复脚本）。
- 数据备份前置：生产发布前数据库每日备份 + PITR（Binlog/WAL）；归档库纳入备份（平台《项目规划说明》「备份与恢复」）。
- 回滚时限：发现严重问题 30 分钟内回滚；回滚后复盘根因并补充回归用例。

## 6. 发布前检查 <a id="check"></a>

- □ 代码评审通过、CI 全绿、三库集成测试通过
- □ 迁移脚本已评审并在测试环境执行过
- □ 镜像标签与 Git 标签对应（semver / SHA 均为不可变标签、无 latest），Registry 可访问
- □ 发布清单 artifact 已核对（digest / 扫描结论；不可自动采集项人工确认）
- □ 环境变量与密钥就位（`BMS_ENV` 正确）
- □ 备份任务正常、可回滚版本确认（上一版本镜像留存）
- □ 发布窗口与值班人确认（生产）

## 7. 检查清单 <a id="checklist"></a>

- □ 环境配置分层正确，密钥不入代码
- □ 镜像标签语义化，构建可复现；服务镜像按 `bms-{服务标识}` 独立命名与发布
- □ 不可变标签生效：SHA 主标签 + tag 流水线追加 semver，无 latest 引用；留存策略落地（semver 永久、SHA 近窗）
- □ 服务变更按变更路径只触发对应子流水线；公共模板跨项目引用固定完整 SHA；同服务发布串行（`resource_group`）且不可自动中断
- □ 服务容器经 Compose 编排（Compose DNS `{service_key}:8000`、仅内部网络经网关）；迁移先行走一次性迁移容器
- □ 构建产物被测试复用：针对产物的测试消费**已构建的固定版本产物**（不重建）、按变更范围只跑受影响部分（优先消费同名不可变产物，同一 tag / digest）
- □ 迁移先行、应用兼容上一版本
- □ 健康门禁（`/healthz` + `/readyz` + 网关路由可达）通过；失败自动回滚可用
- □ 健康检查与冒烟验证通过，发布有记录（发布清单 artifact + 服务器版本台账 / `release-log.jsonl`）
- □ 回滚方案与备份就绪（一键 `rollback` 可用、上一版本镜像留存）
- □ 模块发布：清单版本与产物版本一致、四关校验通过（版本 / 隔离 / 共享 / sourcemap）、发布记录已登记（含产物体积）、回滚目标产物保留确认（见第 8 节）

## 8. 模块发布与回滚 <a id="module-release"></a>

> 适用：运行时模块（清单 `mode: remote`）。模块产物与平台发布**解耦**——清单是模块加载与回滚的**唯一来源**；平台发布（镜像 / 迁移 / 回滚）见第 4 / 5 节。

- **清单唯一来源**：模块的入口与版本只在模块清单登记（名称 / 入口 / 版本 / 加载形态 / 可见性）；加载、发布与回滚一律以清单为准，禁止旁路（手工改入口、直接替换产物目录等）。
- **版本发现（入清单前校验）**：模块构建产出**产物元数据**（名称 / 版本 / 契约版本）；发布前校验「清单版本 = 产物元数据 = 模块源码版本」，通过才可入清单——产物与清单错位即拒绝发布。
- **发布流程**：三关强校验（**版本 / 隔离 / 共享**）→ 产物**按版本归档**（版本目录；本地开发环境为本地发布存储，生产为静态托管 / CDN 版本目录）→ 清单指向该版本 → 发布记录留痕（谁 / 何时 / 动作 / 版本 / 前后版本）。
- **回滚**：清单版本回退到上一版本（缺省上一版本，可显式指定）；**模块产物按版本保留是回滚前提**，回滚即清单指向切换（无需重构建）。回滚后须同步处理模块源码（回退版本或准备修复版本发布）；清单与源码版本不一致由清单护栏提示。
- **灰度 / 蓝绿（最小闭环）**：仅保留「**按清单指向切换**」——同一模块多版本产物并存、清单指向其一；按用户 / 租户 / 比例分流为后续能力。
- **可见性（应急停用）**：清单 `enabled: false` 停用模块（不加载、不挂载、不进菜单；保留入口与版本），恢复即改回 `true`；停用与恢复同样留痕。
- **契约变更协同升级**：模块契约版本升级（注入上下文 / 注册声明 / 清单字段语义 / 校验链变更）= 平台与模块**协同升级**——平台发布契约变更通告，模块适配并升版本、重新构建发布；契约版本不匹配的产物不得入清单、不得回滚生效。
- **版本不可变**：已归档版本不得覆盖（回滚依赖旧产物完整）；生产禁用同版本重发，本地开发重发须留痕。
- **留痕**：发布记录（JSON 真源 + Markdown 摘要）随仓库提交，与第 4 节发布记录同口径（版本 / 时间 / 变更 / 负责人）；记录另带**产物体积**（入口闭包 gzip 合计 / 最大块 / 块数 / 异步块数）与 sourcemap 标记，体积随版本可查。
- **sourcemap 归档与映射**：模块远端构建产出**外部 sourcemap**（不内联源码）；发布**归档 `dist/` 全量（含 map）**到版本目录，映射随版本保留。**发布前强校验加 sourcemap 关**（产物缺 map 拒绝发布）；映射口径：线上异常堆栈指向 `<基址>/<模块名>/<版本>/assets/<chunk>.js`，其 `sourceMappingURL` 指向同目录 `.map`，用 source-map 工具按该版本目录解析即可定位源码。生产由 nginx / CDN 托管版本目录（含 map），制品库 / 对象存储与私有化（map 不宜公开）归部署阶段。

> 模块发布与回滚的**工具落点与执行命令**见《[前端基类清单](../前端基类清单.md)》与模块工程说明；**检查项**：□ 四关强校验通过（版本 / 隔离 / 共享 / sourcemap）；□ 清单版本与产物版本一致；□ 契约版本与平台一致；□ sourcemap 随版本归档；□ 发布记录已登记（含产物体积）；□ 回滚目标产物保留确认。

## 9. API 网关配置与热加载 <a id="gateway"></a>

> 适用：边缘统一入口（Apache APISIX，standalone 文件驱动）。配置语义与 K8s 平移口径见实现侧详细设计（`项目/02_后端基座与服务化地基/任务/04_API网关与边缘/`）。

- **声明式入 Git**：网关路由 / 上游 / 认证 / 限流规则以声明式配置随仓库版本管理，**禁止在控制台手工增删**；临时变更须回写仓库后随流水线发布，否则视为漂移。
- **服务目录为单一来源**：路由 / 上游由服务目录生成（外部前缀与上游名取服务目录登记的服务标识），生成件由流水线**零漂移校验**；服务目录变更须同步重生成再发布。
- **改动生效**：配置改动经流水线校验后发布；运行时文件驱动**热加载**（网关轮询声明式文件，替换即生效，无需重启）。
- **环境差异外部化**：上游地址 / 端口等环境差异收敛进配置与环境变量，**禁止硬编码 IP**；服务间按稳定主机名寻址（Compose DNS → K8s Service）。
- **服务发现禁硬编码 IP（可回归门禁）**：网关上游 / 限流 Redis 主机一律用稳定服务名（`{service_key}:8000` / Compose DNS `redis`），地址收敛配置层；生成件由 `backend/ops/gateway_config.py check` 断言「上游节点非 IP 字面量」，与零漂移校验同跑（CI `base-integrity` 与本地预检）。
- **边缘限流与共享计数**：边缘限流（`limit-count`）以 `policy: redis` 共享计数保证多副本一致；Redis 主机 / 密码经 `${{GATEWAY_REDIS_HOST:=…}}` / `${{GATEWAY_REDIS_PASSWORD:=…}}` 环境变量替换（端口 / 库为整数字面量——APISIX schema 要求整数）、凭据经 `.env` 注入不入库；Redis 故障按 `allow_degradation: true` 放行（可用性优先，告警兜底）；认证敏感路径（登录）走独立路由、更严档位。
- **边缘观测出口**：网关 prometheus 指标端点（路由挂 `prometheus` 插件、`plugin_attr.prometheus.export_addr`）与访问日志（`nginx_config.http`）作为观测出口；真实采集 / 展示 / 告警归可观测性栈。
- **演进**：迁 K8s 阶段同语义换由 Ingress Controller / Gateway API 承载，配置模型平移、不换选型。
- **边缘请求净化与身份头**：客户端伪造身份头（`X-User-Id` / `X-User-Subject` / `X-Tenant-Id` / `X-User-Scopes` / `X-Service-Identity` / `X-Gateway-Identity`）由网关声明式**统一剥除**（`global_rules`），网关专属标记落**路由级** `proxy-rewrite`（真机实测：global 规则 `headers.set` 会被路由级丢弃）；身份头契约以**边缘信任能力域常量为单一来源**（网关生成器与后端同源），后端只信任网关注入身份。
- **网关认证接线与网关服务身份（07_03）**：网关每条服务路由挂 `forward-auth` 转调认证服务内部端点（`http://{GATEWAY_AUTH_HOST}:8000/api/v1/auth/introspect`，`GATEWAY_AUTH_HOST` 经 `deploy/.env` 注入、Compose DNS 默认 `identity`）；认证服务按 `aud=api` 全校验用户 JWT、判公开路径（登录 / 刷新 / 验证码），通过后换发**短时网关服务 JWT**（`aud=service`）——网关 `upstream_headers` 覆盖上游 `Authorization`，**外部 access token 不透传**；`status_on_error: 503` **fail-closed**；后端以入站服务 JWT 本地验签判定可信来源（`[edge].provider = service_jwt`，生产开 `require_gateway_identity`）。认证服务不可达 / 无签名私钥即拒（不降级放行）。

> 检查项：□ 网关配置经仓库版本管理与流水线校验；□ 无控制台手工增删（或已回补仓库）；□ 服务目录变更已同步重生成；□ 上游地址无硬编码 IP（`gateway_config.py check` 护栏通过）；□ 边缘身份头契约与网关剥头 / 标记配置入 Git、与边缘信任能力域常量一致；□ 网关认证接线（`forward-auth`）启用、`GATEWAY_AUTH_HOST` 指向可达认证服务、`status_on_error` fail-closed；□ 边缘限流共享 Redis 计数与凭据外部化、认证敏感路径更严；□ 观测出口（指标端点 / 访问日志）就位。

## 10. 身份源（IdP）编排与凭据外部化 <a id="idp"></a>

> 适用：自托管 OIDC IdP（Keycloak，`deploy/compose/keycloak.yml`）。语义与客户端契约见平台《架构设计 · 认证与会话》「SSO 集成」节，实现侧详细设计见 `项目/02_后端基座与服务化地基/任务/07_认证与服务身份/`。

- **随编排一体**：IdP 容器与既有编排（`deploy/compose/base.yml` 基础设施）组合拉起（`docker compose -f compose/base.yml -f compose/keycloak.yml --env-file .env up -d`）；元数据落独立库（复用 `bms-postgres`），容器无本地状态。
- **声明式供给入 Git**：realm / OIDC 客户端以声明式配置随仓库版本管理（`deploy/keycloak/<realm>-realm.json`，启动 `--import-realm` 自动导入）；**禁止在控制台手工增删**，临时变更须回写仓库后重新导入，否则视为漂移。
- **凭据外部化（红线）**：Keycloak 管理员 / 元数据库 / 客户端 secret 等一切凭据**经环境变量 / Secret 注入**（`deploy/.env`，不入库）；声明式配置内只写占位符（如 `${KEYCLOAK_CLIENT_SECRET}`）；**凭据不落库、不入镜像、不入 Git**。
- **issuer 与访问入口一致**：IdP 对外基址（`issuer`）须与后端 / 客户端访问入口一致（`<基址>/realms/<realm>`），否则令牌 `iss` 与 Discovery 校验失败；IdP 属基础设施身份源，**不经业务网关（APISIX）暴露**。
- **演进**：迁 K8s 阶段同语义换由 Keycloak Operator / StatefulSet + 托管库承载，realm 声明式导入与凭据外部化不变。
- **服务 JWT 自签密钥与 JWKS 分发（07_02）**：BMS 自签服务 JWT（`aud=service`）的**私钥一律经环境变量 / Secret 注入**（`BMS_SERVICE_TOKEN__KEYS`，不入库 / 不入镜像 / 不落日志），公钥 PEM 可随配置下发；`keys` 按 `kid` 多密钥并行使密钥轮换**新旧并行验证**（`active_kid` 指定当前签名键）；公钥经 **`/.well-known/jwks.json`**（`identity` 服务宿主、免鉴权、豁免租户 / 边缘、直连宿主端口不经业务网关）分发。
- **realm 变更重导入**：`--import-realm` 对**已存在 realm 跳过**；存量环境的客户端 mapper / scope 变更须执行一次 `kc.sh import --override`（破坏性，需确认）或经 Admin 控制台，变更后回补仓库声明式文件。

> 检查项：□ IdP 随 `deploy` 编排可一键拉起（元数据持久化）；□ realm / 客户端声明式配置入 Git 且无控制台手工增删（或已回补）；□ 凭据全部经环境变量 / Secret 注入、声明式配置内仅占位符（无明文）；□ `issuer` 与访问入口一致、不经业务网关暴露；□ 服务 JWT 私钥经环境变量 / Secret 注入、JWKS 端点可达且只含公钥、`kid` 轮换新旧并行。

## 11. 可观测性栈编排与采集口径 <a id="observability"></a>

> 适用：指标 / 链路 / 日志标准栈（otel-collector / Tempo / Prometheus / Grafana / Loki / Alloy，`deploy/compose/observability.yml`）。语义见《架构设计 · 可观测性》，实现侧详细设计见 `项目/02_后端基座与服务化地基/任务/08_可观测性栈/`。

- **随编排一体、一键拉起**：可观测组件与基础设施 / 网关组合拉起——聚合编排 `deploy/compose/bms.yml`（`include` base / gateway / observability），命令 `docker compose -f compose/bms.yml --env-file .env up -d`；组件配置集中 `deploy/observability/`，声明式入 Git。
- **保留期 / TTL 显式**：Prometheus 指标 15 天、Loki 日志 30 天、Tempo trace 72h（MVP 单机口径，见《架构设计 · 部署与运维》「容量规划」节）；保留期为可配项，资源吃紧时按风险对策下调。
- **指标采集口径**：每服务暴露根路径 `/metrics`（免鉴权 / 免租户 / 免访问日志，仅内网可达），由 Prometheus 抓取；指标经能力域基座（`BaseMetrics` / `PrometheusMetrics`）记录并统一注入 `service` 标签，**禁止自研平行指标**；HTTP `route` 用路由模板（控基数）。
- **链路采集口径**：应用经 OTLP/HTTP（`:4318`）上报 otel-collector → Tempo；资源标签 `service.name` / `service.version` 按服务归因；OTel 为 **trace id 事实源**（日志与 Trace 同 id）；跨服务经 W3C `traceparent` 传播。
- **日志采集口径**：结构化 JSON stdout 经 Alloy 采集入 Loki；`service` / `level` 作**标签**（低基数），`trace_id` / `request_id` 作**结构化元数据**（不撑爆索引）。
- **边缘接入**：Prometheus 抓取 APISIX 指标端点（`:9091/apisix/prometheus/metrics`）；Alloy 采集 APISIX 访问日志入 Loki。
- **告警与阈值锚点（08_02）**：Alertmanager（9093）随编排一体；Prometheus 规则目录 `deploy/observability/rules/`（基座 SLO：服务指标端点不可达 / 探针失败 / 依赖未就绪 / 服务目录降级 / 5xx 错误率 / P99 延迟 / 发件箱积压，分级 `warning` / `critical` 且严重级抑制同告警名与服务的警告级）；业务链路 SLO（登录 / 审批 / Socket.IO / 备份）**留位登记**，业务端点实现后按服务请求指标补规则。**告警通道凭据外部化**：邮件 SMTP / 企业微信 / 钉钉 webhook 凭据经 `deploy/.env` 注入；Alertmanager 配置**不支持环境变量替换**，采用「模板入 Git（`alertmanager.yml.tmpl`）+ 渲染脚本生成（`scripts/tools/observability/render_alertmanager.py`）+ 产物不入库（`rendered/`）」，缺失凭据即 no-op（不阻断其余组件）；内部接口格式转换归通知阶段。
- **探针可用性观测（08_02）**：blackbox-exporter（9115）周期探测每服务 `/healthz` / `/readyz`（`http_2xx` 仅 200 成功；`probe_success` / `probe_duration`），并借此使 `/readyz` 依赖指标（`bms_dependency_up`）持续刷新；目标与 `/metrics` 抓取同口径登记。
- **阶段度量通道（08_02）**：Pushgateway（宿主 9092）承接 CI 推送的批处理指标——服务独立发布成功率（`bms_release_total{service,result}`）与契约破坏数（`bms_contract_breaking_total{service}`），Prometheus 抓取（`honor_labels`）+ Grafana「阶段度量」面板；边界越界数复用运行期 `bms_boundary_cross_access_total` 与静态门禁（非零即 CI 失败），不重复推送。**真实推送已接入**：发布成功率由服务子流水线发布 job 推送（09_01 / 09_02）；契约破坏数由契约门禁 job 推送（09_03，见第 12 节）。
- **端点外部化**：应用 OTLP 端点经 `BMS_TRACER__OTLP_ENDPOINT` 外部化（宿主 `localhost:4318` / 容器 `otel-collector:4318`），**禁硬编码 IP**；采集端点仅内网可达，生产按网络策略收紧。
- **演进**：迁 K8s 阶段 collector → DaemonSet / Sidecar、Prometheus → ServiceMonitor、Alloy → 采集 DaemonSet、Tempo / Loki / Grafana / Alertmanager → StatefulSet / Helm（告警配置改 Secret 挂载），语义不变。

> 检查项：□ 可观测组件随 `deploy` 一键拉起（`bms.yml` 聚合）、配置入 Git；□ 保留期 / TTL 显式且符合容量口径；□ 每服务 `/metrics` 可达且指标带 `service` 标签；□ Trace 可按 `service.name` / trace id 查询、日志 `trace_id` 与 Trace 一致；□ 日志按服务可检索（`service` 标签 + `trace_id` 元数据）；□ 边缘指标 / 访问日志入栈；□ OTLP 端点经环境变量外部化、采集端点仅内网；□ 告警规则加载且 Alertmanager 可达、告警通道凭据仅经 `.env` 注入（渲染产物不入库）；□ 探针 `probe_success` 可查、依赖指标持续刷新；□ 阶段度量通道可达（Pushgateway 抓取 `up=1`）、面板就位。

## 12. 契约门禁 <a id="contract-gate"></a>

> 适用：服务公开契约（OpenAPI）的**兼容性门禁**——独立基线 + 破坏性变更拦截（oasdiff）+ 接口正确性冒烟（Schemathesis）。语义见《架构设计 · 测试与质量》「CI 流水线」节与《架构设计 · 接口与集成》「服务间通信与契约」节；操作细节见《[契约门禁与契约测试使用说明](../资料/开发服务器/linux/契约门禁与契约测试使用说明.md)》。

- **契约快照与独立基线分离**：每启用服务一份公开契约快照（`deploy/contracts/<服务>.json`，随代码变更重新导出并提交，由快照 job 做零漂移校验与归档）与一份**独立基线**（`deploy/contracts/baseline/<服务>.json`，入 Git、表示已放行的兼容契约）；两者不混同。
- **破坏性变更拦截（「只加不删」）**：以 oasdiff `breaking` 比对基线 ↔ 当前公开契约，破坏性变更（删字段 / 删端点 / 改类型 / 收紧必填等）即 CI 失败并输出变更清单；非破坏性新增（新增可选字段 / 端点）放行。确需破坏时按「版本演进」**升大版本**（`/api/v2` 并行一个发布周期）并更新基线，不得原地破坏。
- **基线更新走评审合入**：基线仅经人工刷新（`ops.contract_gate baseline-update`）后随提交走评审合入，**无自动覆盖路径**（门禁 job 只读比对，不写基线）。
- **契约冒烟（Schemathesis，零 Broker）**：依据 OpenAPI 生成用例**打真实服务**，做接口正确性冒烟。**被测服务＝已构建的服务镜像**（`bms-{服务}:$CI_COMMIT_SHORT_SHA`，正是服务子流水线构建 / 发布的同一不可变产物，**测试不重复构建、不由测试源码另起进程**）；**按服务、仅本次变更的服务运行**（未变更服务不跑）；只读方法与每操作有限样例；排除探针类基础设施端点；契约测试工具与用例自足，不依赖 Broker / 契约平台。消费方 / 团队增多后再评估消费者驱动契约（Pact）。
- **门禁位置**：挂 MR / main 重验证层（父流水线 verify 阶段：`contract-gate` 为**阻断**门禁；另按服务 `contract-smoke-<服务>` **仅本次变更的服务**用已构建镜像打真实服务，同为**阻断**（2026-09-24 06_04 起；dev 环境请求侧 5xx 修复后转阻断）；档位 `deploy/ci/verify/contract-gate`，删档即关）；契约破坏数按阶段度量口径推送 Pushgateway。
- **工具版本固定**：oasdiff / Schemathesis 以固定 tag 镜像运行（登记《镜像清单》并在部署机预拉），门禁 job 与工具镜像版本可复现。

> 检查项：□ 每启用服务有独立基线且与当前公开契约比对通过（破坏性变更为零）；□ 破坏性变更被 CI 拦截并给出清单；□ 基线更新经人工刷新 + 评审合入（无自动覆盖）；□ Schemathesis 冒烟**复用已构建的固定 tag 服务镜像、仅跑本次变更的服务**（不重复构建）；□ 契约破坏数已推送 Pushgateway（`bms_contract_breaking_total`）；□ 工具镜像固定 tag 且已预拉。
