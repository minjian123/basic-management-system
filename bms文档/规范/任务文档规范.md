# 任务文档规范

> 任务文档格式契约 · 状态与工时唯一落点

## 1. 目的与适用范围 <a id="purpose"></a>

本规范定义**任务文档**（父任务/域总览 + 子任务文档 + 任务附属文档：任务级设计、实施记录）的固定格式，是项目任务的**统一契约**：文档即任务登记载体，状态/日期/工时以任务文档为唯一落点（进度事实源为三类项目文档）。

- 适用于 `bms文档/项目/{阶段}/任务/` 下全部任务文档（阶段0 准备期、阶段一 项目骨架已按本规范编写）。
- 本规范只约束**文档怎么写**；管理口径（主题命名、描述三段式、父任务、负责人、状态与工时）以《[项目管理规范](项目管理规范.md)》为准，两者配套。
- **强制契约**：任务文档必须符合本规范规定格式；字段缺失、行格式不符即为不合格文档，需修正后方可进入阶段验收。
- 与《[文档生成规范](文档生成规范.md)》、《[需求文档规范](需求文档规范.md)》同时适用。

## 2. 文件组织 <a id="files"></a>

一个阶段的任务文档分两层（与需求域一一对应）：

```text
任务/
├── {NN}_{域名}.md                        # 父任务/域总览：父任务信息 + 子任务清单
│   └── 例：01_环境与工具链.md、02_仓库与CI.md
└── {NN}_{域名}_{序号}_{任务名}/           # 子任务目录：一条任务一目录
    ├── {NN}_{域名}_{序号}_{任务名}.md     # 子任务文档
    │   └── 例：01_环境与工具链_05_备份体系.md
    ├── 设计/                             # 任务级详细设计（可选，可多份）
    │   └── 例：01_详细设计_01_{任务名}.md  # {任务序号}_详细设计_{设计序号}_{任务名}
    └── 实施/                             # 任务实施记录（任务完成后生成）
        └── 例：01_实施_01_{任务名}.md      # {任务序号}_实施_{实施序号}_{任务名}
```

- 域编号两位（`01`/`02`/`03`…），与需求编号前缀、WBS 域对应。
- 子任务目录名与其内子任务文档同名（含**序号**与**任务名**）；域号已由前缀 `{NN}_{域名}` 承载，序号不重复域号。
- 设计/实施文档名中的**序号**为该任务内同类型文档的顺序号，从 `01` 起（与任务序号区分，如任务 02 的首份设计为 `02_详细设计_01_{任务名}.md`）。
- 父任务（域总览）映射 WBS 父级（域级任务）；子任务目录映射 WBS 子任务。
- `设计/`、`实施/` 为任务附属目录，仅在对应产物存在时创建，不建空目录。

## 3. 父任务/域总览文档格式 <a id="parent"></a>

父任务文档固定章节：

| 章节 | 标题（固定） | 锚点 | 内容 |
| --- | --- | --- | --- |
| 域说明 | `## 1. 域说明` | `intro` | 对应 WBS 域、覆盖范围、依据 |
| 子任务清单 | `## 2. 子任务清单` | `list` | 本域全部子任务汇总表（下表） |
| 工时合计 | `## 3. 工时与依赖` | `effort` | 子任务工时合计、关键依赖、风险 |

**子任务清单表**列固定为（顺序不可变）：

```markdown
| 编号 | 任务 | 工时（重估） | 状态 | 完成日期 | 任务文件 |
| --- | --- | --- | --- | --- | --- |
| 01 | mjbk Ubuntu 基础 | 4h | 已完成 | 2026-08-15 | 01_环境与工具链_01_mjbk_Ubuntu基础.md |
| 05 | 备份体系 | 4h | 未开始 | — | 01_环境与工具链_05_备份体系.md |
```

- **编号**：`{序号两位}`（域内唯一），与需求编号的序号、文件名序号一致；主键为「域号 + 序号」。
- **工时（重估）**：`{数字}h`；未定填 `—`。
- **状态 / 完成日期**：口径见第 6 节。
- **任务文件**：相对链接，指向子任务文档。

## 4. 子任务文档格式（核心结构单元） <a id="task"></a>

### 4.1 任务信息表 <a id="meta"></a>

子任务文档以「任务信息」表承载全部可解析字段，表结构固定：

```markdown
# 01-5 备份体系

## 1. 任务信息 <a id="meta"></a>

| 项 | 值 |
| --- | --- |
| 编号 | 01-5 |
| 父任务 | 01_环境与工具链.md |
| 对应需求 | 01-5 |
| 工时（重估） | 4h（重估上调：含恢复演练） |
| 依赖 | 01-1（机械盘）、01-3（三库）、02-1（GitLab） |
| 负责人 | minjian |
| 状态 | 未开始 |
| 完成日期 | — |
```

**字段契约**：

| 项（固定） | 值格式 | 说明 |
| --- | --- | --- |
| 编号 | `{序号两位}`（域内唯一） | 任务主键，与文件名、清单表一致；跨域引用写 `{域号}_{序号}` |
| 父任务 | `[父任务名](父任务文件)` | 映射 WBS 父级；子任务必填 |
| 对应需求 | `[需求编号](需求文件#r{编号})` | 关联需求，用于互链 |
| 工时（重估） | `{数字}h`（可附括号说明） | 取首个 `{数字}h`；与计划表一致 |
| 依赖 | `{序号}（{说明}）、…`（域内）；跨域 `{域号}_{序号}` | 前置任务编号，映射甘特依赖 |
| 负责人 | `{账号}` | 当前一律 `minjian` |
| 状态 | 见第 6 节 | 状态唯一落点之一 |
| 完成日期 | `YYYY-MM-DD` 或 `—` | 仅「已完成」有值 |

> 本表是**唯一**承载状态/日期/工时的位置（任务文档侧）；文本正文其它位置不作数。

### 4.2 任务正文 <a id="content"></a>

「任务信息」表之后固定三节，对应描述三段式（《项目管理规范》第 4 节）：

| 章节 | 标题（固定） | 锚点 | 说明 |
| --- | --- | --- | --- |
| 任务内容 | `## 2. 任务内容` | `content` | 「内容」段（编号清单） |
| 完成标准 | `## 3. 完成标准` | `accept` | 「完成标准」段 |
| 参考文档 | `## 4. 参考文档` | `ref` | 「参考文档」段 |

```markdown
## 2. 任务内容 <a id="content"></a>

1. 三库：cron 每日 02:00 dump 至 `/mnt/data/backup/{mysql,postgres,dameng}/`，保留 7 天
2. GitLab：容器内 `gitlab-backup` 每日执行，落 `/mnt/data/backup/gitlab/`

## 3. 完成标准 <a id="accept"></a>

各备份文件按期生成；至少完成一次从备份恢复的验证。

## 4. 参考文档 <a id="ref"></a>

- 《开发部署规划》第 8 节
```

### 4.3 章节顺序 <a id="order"></a>

子任务文档元素顺序固定：`# 标题 → ## 1. 任务信息（表）→ ## 2. 任务内容 → ## 3. 完成标准 → ## 4. 参考文档`。

## 5. 实施文档（任务执行记录） <a id="impl"></a>

子任务完成后，在任务目录 `实施/` 下生成实施记录（命名 `{任务序号}_实施_{实施序号}_{任务名}.md`，实施序号从 `01` 起），记录**实际实施过程**：做了什么、怎么做的、遇到什么问题、如何处置、验证结果与偏差遗留。实施文档是任务执行的事实留痕，供复盘与后续任务复用。

**固定章节**（顺序不可变）：

| 章节 | 标题（固定） | 锚点 | 内容 |
| --- | --- | --- | --- |
| 实施信息 | `## 1. 实施信息` | `meta` | 固定字段表（见下） |
| 实施概览 | `## 2. 实施概览` | `overview` | 步骤总览（逻辑关系可用 mermaid）+ 结果小结 |
| 实施过程 | `## 3. 实施过程` | `process` | 按步骤记动作、关键命令与结果 |
| 问题与处置 | `## 4. 问题与处置` | `issues` | 问题/现象、原因、处置与落点 |
| 验证结果 | `## 5. 验证结果` | `verify` | 对照完成标准的验证方法与实测结果 |
| 偏差与遗留 | `## 6. 偏差与遗留` | `deviations` | 与设计的偏差、未决项与后续动作 |

**实施信息表**字段固定（缺省 `—`）：任务 / 对应需求 / 详细设计 / 实施日期 / 实施人 / 实施环境 / 提交 / 结论。

口径：

- 只记**事实**：命令、版本、路径、结果按实际记录（涉及工具/版本先核实），禁止编造。
- 实施过程含关键命令与输出摘要，保证可复现；失败与返工同样记录。
- 不写修订记录（《文档生成规范》9.1 节），修订由 git 承载；本机私有信息（账号、内网地址等）不入库。

## 6. 状态与工时口径 <a id="status"></a>

任务文档「状态」取值固定为下表：

| 文档状态 | 含义 |
| --- | --- |
| 未开始 | 登记未动工 |
| 进行中 | 已动工未完 |
| 部分完成 | 一部分就绪、余量未完 |
| 已完成 | 全部达标 |
| 搁置 | 主动挂起 |

- 「完成日期」仅「已完成」有值；回写目标为「任务信息」表内状态/完成日期两行 + 父任务清单表对应列。
- 工时规则：编写必填工时；重估后在计划表同步，保证三处一致（需求元信息行/任务信息表/计划表）。

## 7. 检查清单 <a id="checklist"></a>

- □ 父任务域总览 `{NN}_{域名}.md` + 子任务 `{NN}_{域名}_{序号}_{任务名}.md` 命名一致
- □ 子任务清单表六列表头与顺序正确，编号唯一且与文件名一致
- □ 子任务「任务信息」表八项齐全（编号/父任务/对应需求/工时/依赖/负责人/状态/完成日期），缺省 `—`
- □ 任务内容/完成标准/参考文档三节齐备，对应描述三段式
- □ 状态取值在第 6 节集合内；已完成才有完成日期
- □ 工时 `{数字}h` 可被提取；子任务工时合计与父任务一致
- □ 任务完成后在 `实施/` 下生成实施记录，第 5 节固定章节齐备
