## 1. 目的与适用范围 <a id="purpose"></a>

规范本项目的测试组织与执行：分层清晰、命名统一、用例统一入库（平台用例库）、CI 自动执行并带覆盖率门禁，
保障三库兼容与安全基线，按标准测试流程闭环（计划 → 设计 → 执行 → 缺陷 → 回归 → 准出 → 报告）。
总体策略见平台《项目规划说明》「测试策略与测试流程」节，
CI 流水线见平台《开发部署规划》「开发工作流与 CI」节与《[部署发布规范](部署发布规范.md)》，命名约定见《[命名规范](命名规范.md)》「测试命名」节。

## 2. 测试分层 <a id="level"></a>

| 层 | 范围 | 工具 | 执行时机 |
| --- | --- | --- | --- |
| 单元测试 | 纯逻辑：校验器、权限计算、工具函数、服务层单测 | 后端测试框架 + 轻量文件库 | 本地预检 + CI 手工触发 |
| 集成测试 | 接口 + 数据库 + 缓存：接口全链路、三库方言 | 后端测试框架 + 免启服务器直连应用 | CI 手工触发的重验证层（连接经环境变量注入） |
| E2E 测试 | 浏览器主流程：登录、RBAC、核心单据 | 浏览器自动化工具 | CI 手工触发的重验证层 |
| 压测 | 500 并发 / P99 ≤ 1s（阶段十四验收） | 压测工具（场景脚本在测试资产仓） | 阶段验收 |
| 验收测试（UAT） | 用户按验收清单逐项人工走查（MVP 验收前） | 人工（用例平台登记结果） | MVP 验收前 |

稳定性 / 可靠性：MVP 验收前对核心链路（审批、实时推送、任务调度）执行 7×24 长稳运行与故障恢复演练，结果入测试报告。

### 2.1 被测物与执行范围（强制 · 通用） <a id="artifact"></a>

> 适用于**一切针对构建产物的测试**（服务镜像、前端产物、运行时模块产物、安装包、契约冒烟等）——不因「测试类型不同」而豁免。判据一句话：**测试消费产物、不生产产物；变更驱动、不全量重跑。**

1. **被测物＝已构建的固定版本产物**：先构建 / 打包得到**不可变版本**（镜像固定 tag、产物版本），测试一律**直接复用该产物**运行；**测试过程不得自行重新构建、不得绕过产物另起源码进程或临时构建物**。同名不可变产物在构建与测试之间须为同一份（同 tag / 同 digest）。
2. **按变更范围只跑受影响的部分**：按变更路径 / 受影响对象（服务、模块、包、产物）**只测变更者**，未变更者不重跑；共享底座变更按其影响的集合放行，禁止「一处改动即全量重跑所有产物测试」。
3. **例外必须先上报、不得自行放行**：确无可用产物、或确需源码级 / 特殊形态测试的，**不得以「这次情况不一样」为理由自行绕过本节**——须逐项向用户说明差异、取得确认并登记（口径同《[AI开发规范](AI开发规范.md)》「不擅动」与《项目管理规范》确认纪律）。
4. **可重现**：被测产物版本一旦确定即固定（固定 tag / digest），保证问题可**固定重现**；禁止在测试中引入随提交漂移的临时构建物作为被测物。

> **实现位置**：本节所述变更影响推导（选测）、并行档位、覆盖率门禁与重命令拦截的**唯一实现**位于跨仓工程化工具包（`engkit`），各仓只保留行为零回退的入口；仓间结构差异一律落仓根 `engkit.toml` 配置（字段口径见 engkit 文档《工程化工具包说明》§4），**不得在仓内另写第二套推导或判定实现**。

#### 2.1.1 变更影响分析：推导依据 <a id="impact-derive"></a>

「变更 → 受影响测试 / 受影响前端包」的推导**只有一份共享实现**，本地预检与 CI 均只经其命令行入口取值；**禁止任一侧另写映射规则**（两侧各维护一套推导是「一处改动即全量重跑」复发的根源）。

推导依据三类，缺一不可：

1. **目录同构**：源码包目录 ↔ 同构测试目录（按目录层级一一对应）；
2. **导入关系**：源模块被测试文件**直接或传递**引用（跨目录引用、经中间模块的间接引用都算）；
3. **工作区依赖**：前端包之间经工作区协议的依赖，取其**反向闭包**（改被依赖包 ⇒ 依赖它的包全部受影响）。

工程与前端包一律**按目录自动发现**，**不维护白名单**——新增工程 / 新增包即自动进入推导范围；但必须同步登记到全量执行范围与覆盖率采集范围（见 2.1.5）。

#### 2.1.2 双重收敛与差集口径 <a id="impact-converge"></a>

先按**目录同构**取候选，再用**导入关系**收敛到真实引用者。两重缺一不可：只做同构会漏跨目录引用（被广泛引用的公共模块最典型），只做导入关系会漏「测试目录按功能组织、但不显式导入该模块」的覆盖。

差集必须**显式**处理，不得默认忽略：

| 场景 | 处理 |
| --- | --- |
| 源码有目录、测试有同名目录 | 同构直接命中 |
| **仅源码有**目录（无同名测试目录） | 候选为空，完全交给导入关系兜底；仍无命中则按 2.1.3 退化 |
| **仅测试有**目录（无同名源码目录） | 同构永不命中，仅当测试文件自身变更或导入关系命中时选中 |
| **测试文件自身变更** | 必须选中该文件自身（改测试必须跑该测试） |

#### 2.1.3 退化条件与显式输出 <a id="impact-degrade"></a>

选测不做「假精细」：命中下列任一条件即**退化为该工程 / 全部工程全量**，并**显式打印原因与命中模块**（不得静默）：

| 触发 | 判定 |
| --- | --- |
| **全局变更** | 工程依赖清单、锁文件、迁移脚本、部署与 CI 配置等跨工程共享文件的变更 |
| **基础模块** | 单工程受影响测试文件数超过**绝对阈值**，或占该工程全量之比超过**占比阈值**（阈值可配） |
| **无引用者** | 该工程有变更模块，但选中的测试集为空 |
| **变更基准不可解析** | 取不到对比基准（浅克隆 / 基准分支不存在）⇒ **强制退化全量** |

最后一条尤为关键：基准不可解析时若按空集跳过，会被当作「无后端变更」而**假绿**——必须显式退化，宁可多跑。

#### 2.1.4 覆盖率扩圈（门禁口径不降级） <a id="impact-expand"></a>

缩小测试范围后覆盖率必然下降，**不得以降低门禁解决**，须以「扩圈」补齐：

1. 跑完选中的测试 → 读覆盖率报告；
2. 若门禁目标模块未达标，把**缺口行所属模块**反查其引用测试，并入测试集**重跑**（缺口模块可能不止最初变更模块）；
3. 扩圈有**轮次上限**；**无新增测试**或**轮次用尽**即退化工程级全量重跑一次，并显式说明原因（不静默放弃）；
4. **门禁目标恒为最初变更模块**——扩圈只扩大「跑哪些测试」，不扩大「门禁范围」。

覆盖率门槛与维度口径见《[AI开发规范](AI开发规范.md#coverage)》「覆盖率要求」节，本规范不复述数字，**也不因选测而打折**。

#### 2.1.5 预检与 CI 两侧一致性 <a id="impact-consistency"></a>

1. **同一实现**：两侧共用同一份推导实现与同一套执行入口，禁止任何一侧维护独立规则或独立退化逻辑；
2. **同一基准**：变更基准两侧取同一来源（合并请求用合并请求差异基准、直推用提交前基准）；取不到时两侧**一致地**显式退化全量；
3. **登记对账**：按目录自动发现的工程必须同时登记到**全量执行范围**与**覆盖率采集范围**——只落目录不登记会导致全量档漏跑、覆盖率范围漏计，且不报错；
4. **护栏**：上述口径由机器护栏锁定（同一来源 / 新增工程必登记 / 退化显式 / 扩圈不静默），改推导或执行实现时护栏用例必须一并跑；
5. **度量可见**：选测结果（选中测试文件数 / 全量数 / 是否退化 / 扩圈轮次 / 覆盖率目标模块数）必须在预检与 CI 输出中可见，便于复盘与度量。

#### 2.1.6 执行侧配套口径 <a id="impact-execution"></a>

1. **并行档位可配**：并行执行按逻辑核数自动或按固定并发（可关）；**并行下用例结果必须与串行一致**，出现不稳定由用例自身修（数据隔离 / 独占标识），不得整体退回串行掩盖问题；并行数据隔离的落点须覆盖由配置派生的文件库目录（各 worker 独立），否则用例间会互相看到对方写入的行。
2. **自测按需**：治理 / 护栏脚本的自检仅在变更触及对应脚本或其依赖时执行；全量档保留全跑口径；变更不可判定时**全跑**（不静默跳过），跳过须逐条打印原因。
3. **重复面划界**：服务级测试仅在**本服务有直接变更**时执行；仅共享底座（依赖锁文件 / 构建文件 / 共享库）变更时，服务测试由共享层测试兜底，服务侧照常构建与发布；判定失败或基准不可解析时**保守执行**（宁可重复不漏测）。
4. **覆盖率采集前置**：覆盖率采集必须在**被测模块导入之前**启动（由测试框架启动入口或等价机制保证）；禁止使用晚于测试框架初始化的探针口径——导入期执行的行会整片漏计，表现为门禁假失败或「恰好达标」的假通过。合并并行数据后由统一门禁脚本判定，门禁口径与维度见 2.1.4 所指节。
5. **并行档位按执行规模选，不一律并行**：并行有固定启动开销（进程拉起 + 每 worker 独立导入依赖），**执行规模小时并行反而更慢**。口径：
   - **全量 / 多目录 / 预检 / 选测** → 并行（各工程 `addopts` 已缺省配置，调用方**不必传参**；CI 同口径）；
   - **单文件 / 单用例调试** → 串行（并行档位下加 `-n 0`），秒级出结果；
   - 两条命令在 IDE 任务里各备一条（「后端：当前文件用例（串行）」/「后端：全量用例（并行）」），按场景选；
   - 并行不得改变用例语义与结果，也不得以「并行慢」为理由把全量退回串行；实测交叉点与耗时数据登记在采用该口径的任务实施记录中，不在本规范复述。
6. **并行下「进程唯一标识」必须错开**：凡依赖每进程唯一标识的生成器（典型是雪花 ID 的 WorkerId），并行执行时须按 worker 分配不同取值——缺省值固定为 0 时，多个 worker 会在**同一毫秒**各自从序列 0 开始，产出**相同 ID**（实测后果：跨库 2PC 用例的 XA `XID` 由全局事务 ID 派生，撞上另一 worker 已开的同名分支，MySQL 报 `XAER_DUPID`）。公共隔离夹具已按 `PYTEST_XDIST_WORKER` 注入 `BMS_APP__WORKER_ID`（`gwN` → N+1，串行 0）；新增此类全局生成器或依赖它的用例时，须同时给出并行隔离口径，不得以「本地串行跑得过」判定通过。
7. **真库用例的探针对象须自带唯一性**：多 worker 共用同一测试库时，固定表名 / 约束名的探针会互相建删（`already exists` / `doesn't exist` / 达梦 `Object is modified`）。探针表名与唯一约束名加进程随机后缀（仍由用例自建自删），不靠「串行执行」掩盖。

## 4. 测试数据 <a id="data"></a>

- 固定夹具与种子与初始化数据分离（平台《项目规划说明》「测试策略与测试流程」）。
- 每个测试独立数据隔离：事务回滚或唯一键后缀，禁止用例间共享可变状态。
- 密码等敏感测试数据用固定测试值，不入真实凭据。
- CI 三库测试库以前缀区分并独立于开发数据（建库 → 建表 → 测试 → 删库），口径见平台《开发部署规划》「常驻数据库」节。
- 本地测试用独立库文件与独立端口，不占用开发库与开发服务端口。

## 5. 用例管理（平台用例库） <a id="cases"></a>

- **平台**：部署服务器常驻（复用平台数据库），为**唯一用例库**——手工与自动化用例统一登记（含用例编号），测试代码以用例 ID 标注关联；执行结果经官方插件导入平台归档，平台统计执行情况与历史。
- **编号口径（强制）**：用例编号**以平台为准**——新增用例先在平台创建并取得编号，再回填代码标记与任务测试记录；平台既有编号不得复用或改派其他含义，代码标记与任务文档引用的题面须与平台一致，出现错位即按文档缺陷整改。
- **产品口径**：平台项目承载**策展用例**（人工设计、一任务一条，是执行统计与验收取数的唯一来源）；「自动化用例（CI）」是流水线导入的执行记录（一测试函数一条、数量大且编号连片），不参与策展编号与统计。
- **编号回读（强制）**：编号**全局自增且跨产品共享**（CI 导入会占用大量连片编号），策展用例编号必然跳号——登记后以登记脚本**回读的实际编号**回填代码标记与任务测试记录，**不得按「上一号 + 1」推算**；已停用编号不得复用或改派含义。
- **工具与留痕落点**：批量登记 / 维护 / 导出与对账脚本记在测试资产仓（见 §14，路径写纯文本），登记输入与平台快照留痕在其 `scripts/kiwi/cases|exports/`。新增批次流程：写输入文件 → **试运行自查** → 登记并回读编号 → 回填代码与任务测试记录。**用例台账已退役（2026-10-13 拍板）——编号与批次一律以平台为准，不再本地留痕**；对账工具的已知口径缺口随测试资产仓文档登记。
- **内容与组织**：用例名称 / 描述 / 分类使用中文；按模块分类 + 标签组织，前端页面 E2E 用例按页面模块分类承载；平台界面以官方简体中文翻译为主、浏览器自动翻译兜底；缺陷链接指向缺陷单。
- **用例设计方法**：等价类划分 / 边界值 / 场景法 / 错误推测；关键业务链路（审批、权限、收付款、归档）用场景法覆盖主路径与异常路径。
- **优先级与风险**：用例按高 / 中 / 低三级优先级；核心模块（认证、RBAC、工作流、审计、收付款）高风险用例优先设计与执行。
- **可追溯性**：用例与模块 / 功能点及验收项双向追溯（用例 ID 标注所属模块与对应验收项），保证需求全覆盖、无孤儿用例。
- **执行方式**：重负载执行（全量回归、三库集成、压测）以 CI 为主，不占本地开发资源；本地仅在明确需要时小范围执行（执行前与开发确认）。本地预检脚本按此分档：**无参即快速档**（只静态 + 基座 / 边界 + 护栏自测），**推送前定向档须显式 `--push`**（静态 + 按 git 变更自动定向的受影响工程用例与**变更源文件**覆盖率门禁，并带单步 / 总体耗时预算护栏），**全量档须显式 `--full`**——即「本地不缺省跑全量」，全量与集成交 CI 按需触发。
- **预检只在推送前跑（机器强制）**：预检是推送前门禁，工作树有未提交改动（含未跟踪文件）即拒绝执行、零步骤执行；开发中改完即测一律走开发环（`scripts/tools/preflight/测试改动内容.sh`）。场景闸门、审计与 `--allow-dirty` 逃生口（仅快速档）的口径见《[AI开发规范](AI开发规范.md)》「开发环 / 推送环」节。

## 6. 覆盖率要求 <a id="coverage"></a>

- **覆盖率要求（门槛 / 维度 / 落地方式）以《[AI开发规范](AI开发规范.md#coverage)》「覆盖率要求」节为唯一权威口径**，本规范不复述数字；工程侧命令、门禁 job 与校验脚本与该节保持一致。
- 覆盖率作 **CI 门禁与本地预检硬门禁**（同口径）：低于门槛流水线失败、阻断 MR 合入；**本地不达标不得推送**（不得靠 CI 兜底，避免「本地放过、CI 才暴露」）。
- **本地全量口径与集成用例定位**（2026-10-25 拍板，任务 `04_05`）：全量门禁按**全仓登记包**判定，**不设排除清单、不以集成用例承担覆盖率**——凡本地不依赖外部服务即可到达的分支（含达梦会话模式、库级咨询锁等外部资源专有路径）一律以 **sqlite 真库 + 替身**（假引擎 / 假连接 / 局部替身）覆盖；`pytest.mark.integration` 用例只承担深层语义验证，其**跳过与否不改变门禁结论**，也不作为缺口豁免理由。
- **测试产物落点（强制）**：跑测试 / 联调产生的一切非源码文件**不得落仓库根、`backend/` 根或任何源码目录**，按类归位——
  - **覆盖率采集数据与门禁报告**：落**仓内缓存目录 `.cache/coverage/`**（`engkit.toml` 的 `[coverage].data_file`，三仓同口径；xdist 分片 `<data-file>.<pid>` 合并后自动清理）；
  - **日志 / 截图 / 一次性脚本与调试输出**：落**工作区 `tmp/`**（不入任何仓）；
  - **本地调试凭据**（如开发密钥 `deploy/.dev-keys.local`）：落**仓级 `deploy/`**，文件名以 `.local` 结尾（`*.local` 已忽略，永不入库）。
  - 例外仅一种：CI 归档的 `backend/coverage.json` 属**显式证据产物**，由 CI 以 `--cov-json` 指定路径，不作本地默认落点。

## 9. 缺陷管理 <a id="defect"></a>

- **载体**：平台 Issue + 里程碑（按阶段 / 版本关联）；用例平台缺陷链接指向对应单。
- **分级**：P0（阻断主流程 / 数据安全）、P1（严重功能缺失 / 可用性降级）、P2（一般缺陷）、P3（轻微 / 建议）。
- **流程**：上报（含复现步骤与关联用例 ID）→ 指派修复 → CI 回归验证 → 关闭；P0/P1 缺陷阻断 MR 合入，修复后回归通过方可合入。
- **自动上报（自动化测试失败时）**：MR 与 main 流水线任一自动化测试失败即**全自动**生成复现包（现场 dump + 失败堆栈 / 日志 + 复现清单，归档到缺陷备份目录），并按「用例 ID + 失败摘要」指纹查未关闭同源缺陷单：不存在则自动创建（含提交、用例 ID、现场路径、环境标记、流水线地址），已存在则追加评论附新现场路径；自动单打标签留痕，人工补充复现步骤与定级（P0-P3）后进入指派修复；接口令牌用 CI/CD 变量注入（机器人账号，勿入库）。
- **AI 辅助修复（指派修复环节）**：扫描自动上报的未关闭缺陷单，按复现包定位根因并生成补丁——**双轨**：本地模型（内网零费用）优先，定位不了或置信度低且显式允许时升级云端模型（**先经敏感信息过滤，现场内容严禁外发**）；成功则机器人推送修复分支并提 MR（描述引用指纹与诊断）并评论缺陷单；**人工 review 合入、CI 回归通过后人工关闭**，AI 不自动合入 / 关闭；无法定位时评论标注需人工处理。复现验证：检出对应提交 + 导入现场 + 跑复现命令。
- **人工上报（UAT / 探索性测试）**：按缺陷模板手动生成缺陷单，或直接建单并按现场数据约定归档。
- **缺陷单模板**：字段骨架（概要 / 分级与影响 / 复现步骤 / 复现环境 / 现场数据 / 处置与关闭条件）见测试资产仓模板目录（纯文本路径，模板不随平台仓入库）。
- **现场数据（缺陷重现）**：P0/P1 缺陷必须附**问题现场数据库 dump**（P2/P3 视可复现性可选）——与代码提交、用例 ID、运行环境标记一并归档到缺陷备份目录（dump 含业务数据，**不入 Git 仓库**，随每日备份保留）；修复验证按「提交 + 用例 + 现场导入」重建问题现场，确认缺陷消失且无回归。

## 10. 回归策略 <a id="regression"></a>

- **冒烟回归**：每次 MR 与发版前执行——登录（含图形验证码）、主体链 RBAC 权限（按钮显隐与字段权限）、核心 CRUD 主链路。
- **全量回归**：每阶段末与 MVP 验收前执行全部自动化用例（单元 / 接口 / 前端组件 / E2E），结果导入用例平台归档。
- **探索性测试**：MVP 验收前由开发 / 用户对新功能区开展探索性测试，发现项入缺陷库。

## 11. 进入与准出标准 <a id="exit"></a>

**进入准则**（进入全量回归与 UAT 的前置条件，同时满足）：

- 冒烟回归通过（登录、主体链 RBAC、核心 CRUD 主链路）；
- CI 流水线绿色（单元 / 接口 / 前端组件测试通过）；
- 用例就绪：平台用例登记完成，用例 ID 与代码关联一致。

**准出标准**（阶段交付与 MVP 验收，同时满足）：

- P0/P1 缺陷清零；
- 功能用例通过率 ≥ 98%；
- 安全专项用例集全部通过；
- 压测达到 500 并发 / P99 ≤ 1s；
- MySQL / PostgreSQL / 达梦 DM8 三库 CI 通过；
- 覆盖率达标（口径见《[AI开发规范](AI开发规范.md#coverage)》「覆盖率要求」节）；
- **界面类交付对照原型 / 布局设计核对通过**（《[原型审查规范](原型审查规范.md)》§4.9：无缺失页面、无裸骨架、无实现命名泄漏；对照结论已登记）。

## 12. 测试报告 <a id="report"></a>

## 13. CI 执行策略 <a id="ci"></a>

| 流水线 | 内容 |
| --- | --- |
| 代码流水线（**手工触发，推送不建流水线**） | 冒烟 + 基座完整性（基座路径改动时）+ 后端 lint / 类型检查 / 测试（覆盖率门禁）+ 工具脚本 lint（`scripts/tools`：ruff check + format）+ 基座包门禁（lint / 类型 / 单测 + 契约套件）+ 前端 lint / 单测（双宿主）+ 双端构建 + 模块注册清单校验 |
| 服务子流水线（父-子流水线，手工触发时全服务拉起） | 只跑该服务：工程级测试（`services/{服务}`）+ 本服务包覆盖率门禁（口径见《[AI开发规范](AI开发规范.md#coverage)》）→ 按服务镜像构建 → 发布（推送 + 镜像扫描 + 发布度量）；共享 / 工作区路径变更由父流水线全量测试兜底 |
| 重验证层（手工触发时随全量执行） | E2E + 三库方言集成测试 + 按服务镜像构建 / 发布 / 扫描（服务子流水线）+ 契约快照存档 + **契约门禁（oasdiff 破坏性变更拦截 + Schemathesis 打真实服务冒烟；冒烟复用已构建的固定 tag 服务镜像、按服务仅跑本次变更的服务）** + 报告归档 + 测试结果导入用例平台 |
| 定时 / 安全 | 安全用例集、依赖漏洞扫描 |

- 执行口径：单人开发期直推 main（不走 MR），多人协作期恢复 MR 门禁（见《[Git协作规范](Git协作规范.md)》）。
- **触发口径（2026-10-26 用户拍板）**：**推送不触发流水线**——各仓 `workflow.rules` 已删除 `push` 与 `merge_request_event` 分支，推送**无需**再加 `-o ci.skip`；CI 改为**按需手工触发**（`scripts/tools/ci/trigger.py`、GitLab 界面 Run pipeline 或 `POST /projects/<id>/pipeline`），**手工触发即全量**（无 Git 推送事件的流水线里 `rules:changes` 恒为真）。**推 `vX.Y.Z` tag 仍自动建流水线**（发布语义）。日常验证以**推送前的本地预检**为准（定向用例 + 覆盖率硬门禁），CI 只承担按需的全量 / 集成复核，**不承担「首次暴露」职责**；详见平台《开发部署规划》「开发工作流与 CI」节。
- 重验证层以仓库**分档开关文件**为守卫（各 job 只守自己的档、删档即关档；未开档时仅基础层执行）；档位与开启状态见《[部署发布规范](部署发布规范.md)》。
- CI 基础镜像预装运行 / 开发依赖，业务 job 零安装（构建、缓存与镜像策略见《[部署发布规范](部署发布规范.md)》）。

## 14. 测试资产落点与组织 <a id="asset"></a>

测试相关的东西分散在**五处**：只有**方法 / 规范与测试代码**随平台与工程，其余测试资产（模板 / 数据 / 压测场景 / 用例维护脚本）不进平台仓，
放在工作区平级的独立测试仓，保持「平台仓只关心平台」：

| 类别 | 落点 | 归属 |
| --- | --- | --- |
| 测试方法 / 规范 | 本文档、平台《架构设计 · 测试与质量》 | 平台 |
| 用例本体 | 平台用例库（外部系统，不在 git） | 平台（外部） |
| 测试代码 | 各工程的测试目录 | 各工程内 |
| 测试记录与报告 | 任务目录 `测试/NN_测试_xx.md`、阶段 `NN_测试报告_<阶段>.md` | 项目文档 |
| **测试资产** | 独立测试仓（`test文档/`、`scripts/`） | **测试仓** |

### 14.1 测试仓与软链 <a id="asset-repo"></a>

- 测试仓与平台仓、产品仓在工作区**平级并置**，文档根按项目命名为 `test文档/`（与 `bms文档/`、`biz文档/` 同构）。
- **双向软链，两侧均不入 git**：平台仓根 `test文档` → 测试仓文档目录（供平台侧导航）、测试仓根 `bms文档` → 平台仓文档目录（供测试侧引用平台规范）；平台侧软链已写入 `.gitignore`，防止误 `git add` / `git clean` 损坏。
- **平台仓文档正文不写真链接指向测试文档**：CI 只 clone 平台仓，软链目标不存在会被基座校验判断链；需提及时写**纯文本路径**。
- 软链在 Windows 克隆与代码托管网页端不可用，文档工作区以 Linux 为准。
- 资产明细见测试仓内资产总览（纯文本路径）。

### 14.2 资产边界 <a id="asset-boundary"></a>

**判据：会不会被 CI 直接调用（脚本被流水线执行）？会 → 留平台仓的治理脚本目录；不会 → 测试仓。**

据此留在平台仓的是：基座完整性校验、状态登记（基座完整性 job）、缺陷三件套（失败自动上报链）、治理与度量脚本（阶段度量与复盘）；脚本的具体命名与落点见工程说明。

### 14.3 新增测试资产的落点判定 <a id="asset-decide"></a>

判定顺序（三步，避免把资产放错仓库）：

1. **先查权威表**：测试仓资产总览（五类资产的落点与归属），已在表中的按表落；
2. **再按判据**：不在表中的按 14.2 判据——会不会被 CI 直接调用？会 → 平台仓治理脚本目录；不会 → 测试资产仓；
3. **记录落点**：测试仓内的落点在资产总览登记（含现状与待办）；平台侧只在本文档体现**类别**，不逐项登记文件。

测试仓已就位资产（纯文本路径）：用例（模板 / 探索性记录）、模板（测试记录 / 阶段测试报告 / 缺陷单）、脚本（用例登记维护导出 / 压测场景骨架 / 数据集骨架）。

### 14.4 测试公共基座（强制 · 新增用例） <a id="asset-testing-base"></a>

后端测试的**公共能力单源**落 `backend/libs/bms_core/src/bms_core/testing/`（基座包内，产品仓 `from bms_core.testing import …` 直接复用），禁止在测试目录内另写一套：

| 能力 | 入口 | 契约 |
| --- | --- | --- |
| 基类 | `BaseTestCase`（总基类）→ `DbTestCase` / `ApiTestCase` / `ServiceTestCase`（能力层）→ 具体测试类 | 资源一律走 fixture；基类只做方法别名与模板钩子 `prepare` / `assert_invariants` / `cleanup`（子类覆写钩子，不覆写 `setup_method` / `teardown_method`）；允许无限层派生，扩展的方法与夹具随继承链复用 |
| 统一事务 | `DbTestCase` 的 `db_session` | 外层事务 + savepoint，patch `SessionFactory.create` 使被测代码复用同一事务；用例结束整体回滚，不落盘、无跨用例污染 |
| 统一报错 | `assert_error(target, code=…, status=…)` / `assert_no_error(target)` | `target` 自动识别异常实例 / 响应对象 / JSON dict；禁止再并列手写 `exc.value.code == …` 与 `resp.json()["code"] == …` |
| 统一日志 | `log_events(source)` / `assert_logged(source, event=…, level=…, **字段)` | `source` 兼容 `capsys` 与 `caplog`；structlog JSON 行由基座解析，禁止各文件手写 `_records()` |
| 统一输出 | `stdout_text` / `stderr_text` / `assert_output` / `run_cli(*args)` | capsys 读取统一入口；ops / scripts 入口测试用 `run_cli` 一次拿到退出码与输出 |
| 公共夹具 | `bms_isolate_settings` / `platform_db` / `reset_request_context` / `reset_plugin_registry` / `clear_tenant_cache` | 各 `conftest.py` 只保留服务专属接线，并以 3 行 `_plugin_fixtures` 包装显式启用公共 autouse 夹具；**不得**再复制这些实现 |

约束：

- 新增测试必须使用上述入口；存量测试按「被改动即迁移」推进，不得新增第二套事务 / 断言 / 日志封装。
- `bms_core.testing` 自身纳入基座覆盖率门禁（行 + 分支 **100%**），新增能力须同步补用例。
- 调试断点集中在 `bms_core/testing/`：用例级问题先在基座 helper 下断点，不得逐个测试类改。
