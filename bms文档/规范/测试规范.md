> 本规范写**测试组织与执行的原则与口径**。**用例台账、模板、压测场景与用例维护脚本**等测试资产在独立测试资产仓（见 §14；正文只写纯文本路径）；治理脚本是否留平台仓按 §14.2 判据；具体命令、文件与配置明细不在本规范重复，随《[部署发布规范](部署发布规范.md)》与工程说明执行。

## 1. 目的与适用范围 <a id="purpose"></a>

规范本项目的测试组织与执行：分层清晰、命名统一、用例统一入库（平台用例库）、CI 自动执行并带覆盖率门禁，
保障三库兼容与安全基线，按标准测试流程闭环（计划 → 设计 → 执行 → 缺陷 → 回归 → 准出 → 报告）。
总体策略见平台《项目规划说明》「测试策略与测试流程」节，
CI 流水线见平台《开发部署规划》「开发工作流与 CI」节与《[部署发布规范](部署发布规范.md)》，命名约定见《[命名规范](命名规范.md)》「测试命名」节。

## 2. 测试分层 <a id="level"></a>

| 层 | 范围 | 工具 | 执行时机 |
| --- | --- | --- | --- |
| 单元测试 | 纯逻辑：校验器、权限计算、工具函数、服务层单测 | 后端测试框架 + 轻量文件库 | MR 流水线 |
| 集成测试 | 接口 + 数据库 + 缓存：接口全链路、三库方言 | 后端测试框架 + 免启服务器直连应用 | main 重验证层（开关激活后；连接经环境变量注入） |
| E2E 测试 | 浏览器主流程：登录、RBAC、核心单据 | 浏览器自动化工具 | main 重验证层（开关激活后） |
| 压测 | 500 并发 / P99 ≤ 1s（阶段十四验收） | 压测工具（场景脚本在测试资产仓） | 阶段验收 |
| 验收测试（UAT） | 用户按验收清单逐项人工走查（MVP 验收前） | 人工（用例平台登记结果） | MVP 验收前 |

稳定性 / 可靠性：MVP 验收前对核心链路（审批、实时推送、任务调度）执行 7×24 长稳运行与故障恢复演练，结果入测试报告。

## 3. 命名规范 <a id="naming"></a>

| 对象 | 约定 | 示例 |
| --- | --- | --- |
| 后端测试文件 | `test_模块.py` | `test_user_api.py` |
| 测试类 | `TestXxx` | `TestUserApi` |
| 测试函数 | `test_行为_期望` | `test_create_user_returns_201` |
| 前端测试 | `组件名.spec.ts` | `UserForm.spec.ts` |
| E2E | 功能描述命名 | `login.spec.ts` |
| 压测脚本 | `scenario_场景.py` | `scenario_登录.py` |
| 用例 ID 关联 | 自动化用例标注平台用例编号，与平台用例一一对应；**先登记平台用例再写代码**（后端用例标记、前端用例名称内标注、E2E 注解三种写法） | 如 `describe('根系基类（Kiwi 698）', …)` |

## 4. 测试数据 <a id="data"></a>

- 固定夹具与种子与初始化数据分离（平台《项目规划说明》「测试策略与测试流程」）。
- 每个测试独立数据隔离：事务回滚或唯一键后缀，禁止用例间共享可变状态。
- 密码等敏感测试数据用固定测试值，不入真实凭据。
- CI 三库测试库以前缀区分并独立于开发数据（建库 → 迁移 → 测试 → 删库），口径见平台《开发部署规划》「常驻数据库」节。
- 本地测试用独立库文件与独立端口，不占用开发库与开发服务端口。

## 5. 用例管理（平台用例库） <a id="cases"></a>

- **平台**：部署服务器常驻（复用平台数据库），为**唯一用例库**——手工与自动化用例统一登记（含用例编号），测试代码以用例 ID 标注关联；执行结果经官方插件导入平台归档，平台统计执行情况与历史。
- **编号口径（强制）**：用例编号**以平台为准**——新增用例先在平台创建并取得编号，再回填代码标记与任务测试记录；平台既有编号不得复用或改派其他含义，代码标记与任务文档引用的题面须与平台一致，出现错位即按文档缺陷整改。
- **产品口径**：平台项目承载**策展用例**（人工设计、一任务一条，是用例台账、执行统计与验收取数的唯一来源）；「自动化用例（CI）」是流水线导入的执行记录（一测试函数一条、数量大且编号连片），不参与策展编号与统计。
- **编号回读（强制）**：编号**全局自增且跨产品共享**（CI 导入会占用大量连片编号），策展用例编号必然跳号——登记后以登记脚本**回读的实际编号**回填代码标记与任务测试记录，**不得按「上一号 + 1」推算**；已停用编号不得复用或改派含义。
- **工具与台账落点**：批量登记 / 维护 / 导出与对账脚本、策展用例批次台账记在测试资产仓（见 §14，路径写纯文本）。新增批次流程：写输入文件 → **试运行自查** → 登记并回读编号 → 回填代码与任务测试记录 → 追加台账；对账工具的已知口径缺口随测试资产仓文档登记。
- **内容与组织**：用例名称 / 描述 / 分类使用中文；按模块分类 + 标签组织，前端页面 E2E 用例按页面模块分类承载；平台界面以官方简体中文翻译为主、浏览器自动翻译兜底；缺陷链接指向缺陷单。
- **用例设计方法**：等价类划分 / 边界值 / 场景法 / 错误推测；关键业务链路（审批、权限、收付款、归档）用场景法覆盖主路径与异常路径。
- **优先级与风险**：用例按高 / 中 / 低三级优先级；核心模块（认证、RBAC、工作流、审计、收付款）高风险用例优先设计与执行。
- **可追溯性**：用例与模块 / 功能点及验收项双向追溯（用例 ID 标注所属模块与对应验收项），保证需求全覆盖、无孤儿用例。
- **执行方式**：重负载执行（全量回归、三库集成、压测）以 CI 为主，不占本地开发资源；本地仅在明确需要时小范围执行（执行前与开发确认）。

## 6. 覆盖率要求 <a id="coverage"></a>

- 后端：核心模块（认证、RBAC、工作流、审计、收付款）行覆盖率 ≥ 80%；整体 ≥ 70%。
- 前端：核心组件与状态逻辑覆盖，计入整体门槛 ≥ 70%。
- 覆盖率作 CI 门禁，低于门槛流水线失败、阻断 MR 合入。

## 7. 三库方言测试 <a id="three-db"></a>

- 集成测试默认用轻量文件库快速执行；**main 流水线**跑 MySQL / PostgreSQL / 达梦 DM8 三库迁移 + 核心用例（复用常驻三库）。
- 方言差异重点用例：分页、日期、字符串、布尔、主键类型映射、大小写（详见《[数据库开发规范](数据库开发规范.md)》「SQL 口径（三库兼容）」节）。
- 三库任一失败即阻断；方言兼容问题在开发期暴露，不在交付期。

## 8. 安全测试用例 <a id="security"></a>

CI 定期执行的集中安全用例集（平台《项目规划说明》「测试策略与测试流程」），至少覆盖：

- 越权：跨用户 / 跨租户资源访问
- 注入：SQL / 命令 / XXE 注入样本
- XSS：富文本与 `v-html` 场景
- 上传绕过：类型伪造、超大文件、路径穿越
- 限流爆破：登录 / 验证码失败锁定
- 脱敏泄露：响应与日志无敏感字段明文
- 会话安全：会话劫持、会话踢出即时生效

## 9. 缺陷管理 <a id="defect"></a>

- **载体**：平台 Issue + 里程碑（按阶段 / 版本关联）；用例平台缺陷链接指向对应单。
- **分级**：P0（阻断主流程 / 数据安全）、P1（严重功能缺失 / 可用性降级）、P2（一般缺陷）、P3（轻微 / 建议）。
- **流程**：上报（含复现步骤与关联用例 ID）→ 指派修复 → CI 回归验证 → 关闭；P0/P1 缺陷阻断 MR 合入，修复后回归通过方可合入。
- **自动上报（自动化测试失败时）**：MR 与 main 流水线任一自动化测试失败即**全自动**生成复现包（现场 dump + 失败堆栈 / 日志 + 复现清单，归档到缺陷备份目录），并按「用例 ID + 失败摘要」指纹查未关闭同源缺陷单：不存在则自动创建（含提交、用例 ID、现场路径、环境标记、流水线地址），已存在则追加评论附新现场路径；自动单打标签留痕，人工补充复现步骤与定级（P0-P3）后进入指派修复；接口令牌用 CI/CD 变量注入（机器人账号，勿入库）。
- **AI 辅助修复（指派修复环节）**：扫描自动上报的未关闭缺陷单，按复现包定位根因并生成补丁——**双轨**：本地模型（内网零费用）优先，定位不了或置信度低且显式允许时升级云端模型（**先经敏感信息过滤，现场内容严禁外发**）；成功则机器人推送修复分支并提 MR（描述引用指纹与诊断）并评论缺陷单；**人工 review 合入、CI 回归通过后人工关闭**，AI 不自动合入 / 关闭；无法定位时评论标注需人工处理。复现验证：检出对应提交 + 导入现场 + 跑复现命令。
- **人工上报（UAT / 探索性测试）**：按缺陷模板手动生成缺陷单，或直接建单并按现场数据约定归档。
- **缺陷单模板**：字段骨架（概要 / 分级与影响 / 复现步骤 / 复现环境 / 现场数据 / 处置与关闭条件）见测试资产仓模板目录（纯文本路径，模板不随平台仓入库）。
- **现场数据（缺陷重现）**：P0/P1 缺陷必须附**问题现场数据库 dump**（P2/P3 视可复现性可选）——与代码提交、用例 ID、运行环境标记一并归档到缺陷备份目录（dump 含业务数据，**不入 Git 仓库**，随每日备份保留）；修复验证按「提交 + 用例 + 现场导入」重建问题现场，确认缺陷消失且无回归。

## 10. 回归策略 <a id="regression"></a>

- **冒烟回归**：每次 MR 与发版前执行——登录（含图形验证码）、主体链 RBAC 权限（按钮显隐与字段权限）、核心 CRUD 主链路。
- **全量回归**：每阶段末与 MVP 验收前执行全部自动化用例（单元 / 接口 / 前端组件 / E2E），结果导入用例平台归档。
- **探索性测试**：MVP 验收前由开发 / 用户对新功能区开展探索性测试，发现项入缺陷库。

## 11. 进入与准出标准 <a id="exit"></a>

**进入准则**（进入全量回归与 UAT 的前置条件，同时满足）：

- 冒烟回归通过（登录、主体链 RBAC、核心 CRUD 主链路）；
- CI 流水线绿色（单元 / 接口 / 前端组件测试通过）；
- 用例就绪：平台用例登记完成，用例 ID 与代码关联一致。

**准出标准**（阶段交付与 MVP 验收，同时满足）：

- P0/P1 缺陷清零；
- 功能用例通过率 ≥ 98%；
- 安全专项用例集全部通过；
- 压测达到 500 并发 / P99 ≤ 1s；
- MySQL / PostgreSQL / 达梦 DM8 三库 CI 通过；
- 覆盖率达标（核心 ≥ 80%、整体 ≥ 70%）。

## 12. 测试报告 <a id="report"></a>

- **自动化报告**：后端与前端自动化测试报告随 CI 产物归档。
- **阶段汇总报告**：每阶段末输出（用例执行统计、缺陷统计、覆盖率、风险与遗留项），纳入平台《项目规划说明》「文档计划」交付项；MVP 验收前输出总测试报告。
- **模板**：任务测试记录与阶段测试报告的结构骨架见测试资产仓模板目录（纯文本路径）；平台侧只承载产出物（任务 `测试/NN_测试_xx.md`、阶段 `NN_测试报告_<阶段>.md`）。
- **测试复盘**：阶段末报告含经验教训小节（测试过程问题与改进项），MVP 验收后整体复盘一次。

## 13. CI 执行策略 <a id="ci"></a>

| 流水线 | 内容 |
| --- | --- |
| 代码流水线（MR 或单人期直推 main） | 冒烟 + 基座完整性（基座路径改动时）+ 后端 lint / 类型检查 / 测试（覆盖率门禁）+ 基座包门禁（lint / 类型 / 单测 + 契约套件）+ 前端 lint / 单测（双宿主）+ 双端构建 + 模块注册清单校验 |
| 服务子流水线（父-子流水线，按变更路径调度） | 只跑该服务：工程级测试（`services/{服务}`）+ 本服务包覆盖率门禁（≥70%）→ 按服务镜像构建 → 发布（推送 + 镜像扫描 + 发布度量）；共享 / 工作区路径变更由父流水线全量测试兜底 |
| main 重验证层（开关激活后） | E2E + 三库方言集成测试 + 按服务镜像构建 / 发布 / 扫描（服务子流水线）+ 契约快照存档 + **契约门禁（oasdiff 破坏性变更拦截 + Schemathesis 打真实服务冒烟）** + 报告归档 + 测试结果导入用例平台 |
| 定时 / 安全 | 安全用例集、依赖漏洞扫描 |

- 执行口径：单人开发期直推 main（不走 MR），多人协作期恢复 MR 门禁（见《[Git协作规范](Git协作规范.md)》）。
- 免跑层口径：纯业务文档（项目 / 规划 / 设计等）推送不建流水线；基座路径（规范 / 资料 / 资源 / 基座文档清单）改动触发基座完整性校验；基座入口《文档首页》属高频改动点、**不在触发路径**，其链接自洽由本地链接校验兜底——勿将其加入触发路径，否则每次纯文档推送都会拉起整条冒烟层。
- 重验证层以仓库**分档开关文件**为守卫（各 job 只守自己的档、删档即关档；未开档时仅基础层执行）；档位与开启状态见《[部署发布规范](部署发布规范.md)》。
- CI 基础镜像预装运行 / 开发依赖，业务 job 零安装（构建、缓存与镜像策略见《[部署发布规范](部署发布规范.md)》）。

## 14. 测试资产落点与组织 <a id="asset"></a>

测试相关的东西分散在**五处**：只有**方法 / 规范与测试代码**随平台与工程，其余测试资产（模板 / 数据 / 压测场景 / 用例维护脚本）不进平台仓，
放在工作区平级的独立测试仓，保持「平台仓只关心平台」：

| 类别 | 落点 | 归属 |
| --- | --- | --- |
| 测试方法 / 规范 | 本文档、平台《架构设计 · 测试与质量》 | 平台 |
| 用例本体 | 平台用例库（外部系统，不在 git） | 平台（外部） |
| 测试代码 | 各工程的测试目录 | 各工程内 |
| 测试记录与报告 | 任务目录 `测试/NN_测试_xx.md`、阶段 `NN_测试报告_<阶段>.md` | 项目文档 |
| **测试资产** | 独立测试仓（`test文档/`、`scripts/`） | **测试仓** |

### 14.1 测试仓与软链 <a id="asset-repo"></a>

- 测试仓与平台仓、产品仓在工作区**平级并置**，文档根按项目命名为 `test文档/`（与 `bms文档/`、`biz文档/` 同构）。
- **双向软链，两侧均不入 git**：平台仓根 `test文档` → 测试仓文档目录（供平台侧导航）、测试仓根 `bms文档` → 平台仓文档目录（供测试侧引用平台规范）；平台侧软链已写入 `.gitignore`，防止误 `git add` / `git clean` 损坏。
- **平台仓文档正文不写真链接指向测试文档**：CI 只 clone 平台仓，软链目标不存在会被基座校验判断链；需提及时写**纯文本路径**。
- 软链在 Windows 克隆与代码托管网页端不可用，文档工作区以 Linux 为准。
- 资产明细见测试仓内资产总览（纯文本路径）。

### 14.2 迁移边界 <a id="asset-boundary"></a>

**判据：会不会被 CI 直接调用（脚本被流水线执行）？会 → 留平台仓的治理脚本目录；不会 → 测试仓。**

据此留在平台仓的是：基座完整性校验、状态登记（基座完整性 job）、缺陷三件套（失败自动上报链）、治理与度量脚本（阶段度量与复盘）；脚本的具体命名与落点见工程说明。

### 14.3 新增测试资产的落点判定 <a id="asset-decide"></a>

判定顺序（三步，避免把资产放错仓库）：

1. **先查权威表**：测试仓资产总览（五类资产的落点与归属），已在表中的按表落；
2. **再按判据**：不在表中的按 14.2 判据——会不会被 CI 直接调用？会 → 平台仓治理脚本目录；不会 → 测试资产仓；
3. **记录落点**：测试仓内的落点在资产总览登记（含现状与待办）；平台侧只在本文档体现**类别**，不逐项登记文件。

测试仓已就位资产（纯文本路径）：用例（模板 / 台账 / 探索性记录）、模板（测试记录 / 阶段测试报告 / 缺陷单）、脚本（用例登记维护导出 / 压测场景骨架 / 数据集骨架）。
